## 0. 执行摘要

MiLAi 当前不再被定义为“一个带向量库的长期记忆插件”，也不再把最终回答、语义完备判断或隐藏 Reader 放在 Memory Server 内部。它更准确的定位是：

> **一个面向长期 Agent 的持久 Memory Control Plane：以 Evidence 为底座，以 Versioned Canonical State 为长期知识状态，以 Retrieval State 管理检索连续性，以 Host Cognitive State 承载 Codex 的工作认知，并通过 Activation / Reconciliation / Governance 控制这些状态何时读取、何时更新、谁有权改变。**

系统核心职责分工：

```text
Codex
  ├─ 理解用户任务
  ├─ 推理 / 规划 / 工具调用
  ├─ 判断普通回答是否充分
  ├─ 形成 residual query
  ├─ 生成 Host Cognitive State 语义变化
  └─ 最终回答

Host / Launcher
  ├─ 绑定 tenant / principal / project / task / session
  ├─ Session-start memory activation
  ├─ 必须发生的 prefetch / checkpoint timing
  ├─ 捕获真实执行事件
  ├─ 冻结 reconciliation event window
  └─ 校验并应用 Codex StateDelta

MiLA MCP
  ├─ 暴露稳定工具契约
  ├─ 认证 / scope 注入
  ├─ Read / Capture / Proposal / Review / Revoke / State 工具
  └─ 返回 Evidence Context 与治理结果

MiLA Runtime
  ├─ Evidence persistence
  ├─ Canonical Claim / ClaimVersion
  ├─ RetrievalContinuationState
  ├─ Host Cognitive State persistence
  ├─ Scope / authority / revocation / temporal correctness
  ├─ FTS / retrieval / shadow fine acquisition
  ├─ CAS / idempotency / RLS / TTL
  └─ Audit / deletion / cleanup

PostgreSQL
  └─ Canonical persistence substrate
```

当前工程主线已完成：

```text
Phase A  Memory MCP baseline                    PASS
Phase B  Host continuity                        PASS
Phase C  Event-grounded reconciliation          PASS
Phase D1 Non-destructive persisted frontier     PASS
Phase D2 Explicit intra-source lexical          SHADOW
```

当前明确未宣称完成：

```text
Dense acquisition                               NOT REQUIRED / NOT CLAIMED
D2 product effect                               UNKNOWN
Fine acquisition → public frontier integration  NOT CLAIMED
Formal 500 holdout                              UNCONSUMED
```

# 1. 设计原则

## 1.1 Evidence ≠ Truth

MiLA 记录“发生过什么”，但不会因为一条观察被写入就自动把它提升为长期事实。

```text
Observation
   ↓
Evidence
   ≠
Canonical Claim
```

Evidence 是不可原地改写的原始观察及 provenance。它可以来自：

- 用户消息；
- Assistant 可观察输出；
- Tool result；
- Shell / test / git / file event；
- 外部系统事件；
- 已授权的数据源。

## 1.2 Canonical State 必须版本化

MiLA 不采用传统：

```sql
UPDATE claim SET value = ...
```

而采用：

```text
Claim C42
  ├─ V1
  ├─ V2
  └─ V3 ← current
```

每次正式变化产生新的 `ClaimVersion`。旧版本保留历史和 lineage。

## 1.3 Proposal ≠ Commit

Canonical 修改必须经过治理路径：

```text
Evidence
   ↓
Proposal
   ↓
Review / Governance
   ↓
ClaimVersion
```

普通 recall、Working State、Host inference 都不能直接改 Canonical。

## 1.4 Context ≠ Memory State

一次 MCP resolve 返回的 Context 只是当前推理窗口的一次有损视图：

```text
Memory State
   ↓
Query-scoped Context
```

没有进入 Context 不等于不存在；进入 Context 也不等于成为 Canonical。

## 1.5 Projection 是可重建读取视图，不是控制策略

FTS、Dense、Current-state view、Profile view、Context renderer 都属于 projection / read model。

Projection 用于：

- 加速；
- 索引；
- 组织；
- 展示。

它不保证 Agent 会主动使用，也不承担“什么时候调用 memory”的控制职责。

## 1.6 Host Cognitive State ≠ Canonical State

Host Cognitive State 表示：

> Codex 当前如何理解任务。

它可以包含：

- goal；
- requirement；
- decision；
- hypothesis；
- failed approach；
- blocker；
- open question；
- next action。

它是 `HOST_WORKING` authority 下的非 Canonical semantic cache。

## 1.7 Runtime 负责机械正确性，Codex 负责语义认知

```text
WHEN to access / reconcile   → Host policy
WHAT changed semantically    → Codex
HOW to apply safely          → Host + MiLA
WHAT is Canonical            → Governance
```

这避免 MiLA 内部再复制一个隐藏 LLM Reader / Planner。

# 3. 四种核心数据/状态对象

## 3.1 Evidence

回答：

> 系统真实观察到了什么？

核心属性：

```yaml
Evidence:
  evidence_id:
  source_type:
  source_ref:
  subject_id:
  observed_at:
  valid_time: optional
  content:
  content_hash:
  permission_snapshot:
  retention_state:
  provenance:
```

约束：

- append-only；
- 不能原地改写；
- revoke 后不能继续作为有效 grounding；
- summary / derived state 不能冒充原始 Evidence。

---

## 3.2 Canonical State

回答：

> MiLA 经过治理后当前正式接受什么？

核心对象：

```text
Claim
ClaimVersion
ClaimHead
OpenIssue
Proposal
Review
```

示例：

```text
Claim: database_port

V1 = 5432
V2 = 6432  ← current
```

读取 current state 时，不要求 Codex 重建所有历史。

Canonical 变化路径：

```text
new Evidence
   ↓
Proposal(SUPERSEDE)
   ↓
expected_version_id check
   ↓
Review(APPROVE)
   ↓
ClaimVersion Vn+1
```

---

## 3.3 RetrievalContinuationState

回答：

> 当前 query lineage 已经检索到哪里？

这是 Runtime-owned mechanical state。

核心内容：

```yaml
RetrievalContinuationState:
  state_id:
  root_state_id:
  predecessor_state_id:
  generation:
  principal_binding_digest:
  scope_digest:
  snapshot_as_of:
  seen_anchor_evidence_ids: []
  seen_rendered_turn_ids: []
  frontier_candidate_refs: []
  route_cursors: {}
  exhausted_routes: []
  budget_history: []
```

它不能包含：

- goal；
- decision；
- blocker；
- hypothesis；
- semantic completeness。

它只解决：

```text
第一次查了什么
第二次从哪里继续
哪些 exact Evidence 已经看过
当前 snapshot 是什么
```

---

## 3.4 Host Cognitive State

回答：

> Codex 当前如何理解任务？

它是：

```text
semantic
fallible
non-canonical
append-only versioned
scope-bound
CAS protected
```

推荐 payload：

```yaml
task:
  active_goal:
  current_question:
  phase:
  completion_conditions: []
requirements: []
established: []
hypotheses:
  active: []
  invalidated: []
decisions: []
failed_approaches: []
blockers: []
open_questions: []
memory_needs: []
next_actions: []
```

Runtime 不解释这些字段；Codex 负责语义。

Runtime 只负责：

```text
state identity
version
scope
TTL
payload
CAS
Evidence refs
audit
```

# 4. 两个记录平面

## 4.1 Evidence Plane

用于保存真实、可追溯内容。

特点：

```text
高保真
长期存在
可被 Canonical / retrieval / reconciliation 引用
```

## 4.2 HostExecutionEvent Plane

用于 State reconciliation 的稀疏认知触发索引。

它不是完整执行日志。

典型事件：

```text
DIALOGUE_TURN_OBSERVED
FILE_SET_CHANGED
TEST_RESULT_OBSERVED
COMMAND_RESULT_OBSERVED
GIT_COMMIT_OBSERVED
TOOL_RESULT_OBSERVED
TASK_BOUNDARY_OBSERVED
SESSION_BOUNDARY_OBSERVED
CONTEXT_COMPACTION
```

关键原则：

```text
Event 记录 Host 观察
不预编码 decision / requirement / hypothesis
```

例如：

```text
用户说：
“先别改数据库，我们换个实现。”
```

Event 只能记录：

```text
DIALOGUE_TURN_OBSERVED
```

是否意味着 requirement / decision 变化，由 Codex reconciliation 决定。

# 5. Memory Activation Policy

MCP 工具可见并不等于 Codex 会主动调用。

真实实验已证明：

```text
explicit callability   PASS
natural resume GET     NEGATIVE
```

因此 MiLA 将 Activation 与 Tool Execution 分离。

## 5.1 三种 Activation

### AUTO

模型自己决定。

适合：

- exploratory recall；
- ambiguous historical dependency；
- residual continuation；
- exact memory_get。

### HOST

Host 确定性触发。

适合：

- session-start TASK state prefetch；
- checkpoint reconciliation；
- 高置信历史依赖预取；
- capture pipeline。

### EXPLICIT

要求当前用户明确授权。

适合：

- Proposal mutation；
- Review approve/reject；
- Evidence revoke；
- namespace cleanup。

# 8. Non-destructive continuation（D1）

第一次：

```text
milai_memory_resolve(query)
→ Context A
→ context_id = ctx-123
```

如果 Codex 判断不够：

```text
milai_memory_resolve(
  residual_query,
  previous_context_id="ctx-123"
)
```

Runtime：

```text
same principal
same scope
same root snapshot
resume persisted frontier
exclude exact seen Evidence
return novel Evidence
append successor retrieval state
```

关键原则：

> 第二次调用不能破坏第一次已经呈现的 Evidence。

Context budget 从一次性竞争转为跨调用累计。

---

# 9. Explicit intra-source lexical acquisition（D2 SHADOW）

D2 当前只做 SHADOW，不改变公开 Context。

目标问题：

```text
coarse source/session 已经找到
但需要的具体 turn/span 没被直接召回
```

目标链：

```text
coarse source/session acquisition
   ↓
explicit intra-source lexical retrieval
   ↓
direct turn/span candidate
```

当前安全边界：

```text
只在 coarse pool 内展开
PostgreSQL 重验 exact coarse Evidence ID
按 (source_type, session_id) 隔离
不跨 source 串池
不改 public Context
不改 continuation frontier
不改 Canonical
```

未来只有在真实 failure 或正式 Research seal 下才评估是否进入产品路径。

# 12. 删除 / 撤销路径

MiLA 不采用普通 DELETE。

```text

   ↓

   ↓

   ↓

   ↓
```

删除原则：

```text

```

# 13. Host Continuity

自然 MCP adoption 已被证明不可靠，因此跨 Session 连续性由 Host 管理。

## 13.1 Session start

```text
milai codex launcher
   ↓
resolve repo / worktree / branch / task_ref
   ↓
working_state_get(TASK)
   ↓

  render bounded HOST_WORKING bootstrap
   ↓

```

Bootstrap 明确标注：

```text

```

# 14. Event-grounded Cognitive Reconciliation

模型会操作 memory，但不会稳定意识到“自己的 State 已经变化”。

因此：

```text
Host owns WHEN
Codex owns WHAT
MiLA owns persistence
```

## 14.1 Dirty

Change candidate Event：

```text
DIALOGUE_TURN_OBSERVED
FILE_SET_CHANGED
TEST_RESULT_OBSERVED
COMMAND_RESULT_OBSERVED
GIT_COMMIT_OBSERVED
TOOL_RESULT_OBSERVED
```

Boundary Event：

```text
TASK_BOUNDARY_OBSERVED
SESSION_BOUNDARY_OBSERVED
CONTEXT_COMPACTION
```

Boundary 不自己制造 dirty，只触发“检查是否需要 reconcile”。

## 14.2 Checkpoint Gate

```text
active task
AND unreconciled change exists
AND (
  session boundary
  OR task boundary
  OR compaction
  OR threshold reached
)
```

# 15. StateBasisCursor

每个 Cognitive State version 记录它已经综合到哪里。

```yaml
StateBasisCursor:
  event_journal_epoch:
  event_position:
  event_contract_version:
  reconciled_at:
```

定义：

```text
B0 = previous State basis
B1 = visible high watermark at reconciliation start
Window = events in (B0, B1]
```

只有 State payload 与 Basis 在同一个 exact-head CAS 成功时，Basis 才前进。

失败：

```text
State not written
Basis not advanced
Events remain dirty
```

# 16. StateDelta Protocol

Codex 不直接写最终 State。

输入：

```yaml
previous_state: {}
event_window:
  from_position:
  through_position:
  events: []
current_task_context:
  task_ref:
  repo_ref:
  worktree_ref:
  branch:
  session_ref:
```

输出：

```yaml
StateDelta:
  base_state_id:
  base_version:
  basis_from_position:
  basis_through_position:
  changes:
    blockers:
      op: REPLACE
      value: []
      reason_event_ids: []
    next_actions:
      op: REPLACE
      value: []
      reason_event_ids: []
  no_material_change: false
```

V1 不开放 arbitrary JSON Patch。

规则：

```text
missing field = KEEP
allowed field = REPLACE/CLEAR
binding cannot change
Basis cannot be model-controlled
reason_event_ids must belong to frozen window
```

# 17. Host apply

```text
1. GET State Vn
2. freeze Event Window (B0, B1]
3. Codex returns StateDelta
4. Host validates Delta
5. Host deterministically applies Delta
6. validate payload / refs
7. MiLA exact-head CAS append Vn+1 + Basis B1
8. events > B1 remain dirty
```

因此：

```text
semantic diff   → Codex
mechanical apply → Host
version safety   → MiLA
```

---

# 18. Resume recovery

如果上一个 Session checkpoint 失败：

```text
State V7 / Basis 18472
Events 18473..18531 remain
```

新 Session：

```text
load V7
compare event watermark
18531 > 18472
→ reconcile pending window
→ State V8 / Basis 18531
```

所以 State maintenance 不依赖“模型记得主动 update”。

> **尽量减少不必要的 memory work。**

## 23.1 推荐读路径

```text

 ↓

 ↓
Canonical / exact fast path
 ↓ miss
Lexical
 ↓ need
Temporal / structured
 ↓ need

 ↓ need

```

## 23.2 Context

```text
Anchor before hydration
Distinct Evidence before presentation richness

```


# 25. 失败归因模型

```text
Task failed
  │
  ├─ should access memory but did not
  │    → Activation failure
  │
  ├─ memory called, source not found
  │    → Acquisition failure
  │
  ├─ source found, required turn absent
  │    → Fine coverage failure
  │
  ├─ first result insufficient, continuation no gain
  │    → Continuation failure
  │
  ├─ cross-session state stale/wrong
  │    → Reconciliation failure
  │
  ├─ correct State/Evidence visible, Codex wrong
  │    → Host reasoning failure
  │
  └─ scope/authority/Canonical violated
       → Hard architecture failure
```

# 27. 增量开发原则

## 27.1 Failure-driven development

以后所有新机制都必须回答：

> 哪一个真实 Codex / 用户 failure 迫使我们增加它？

没有真实 failure，不开发。

## 27.2 Feature first, hardening second

先实现最小正确闭环：

```text
feature
→ real E2E
→ failure
→ only then harden
```

避免先为理论异常实现大量复杂机制。

## 27.3 Engineering / Research 双模式

### Engineering

```text
unit test
integration
real E2E
subagent review
regression
```

### Research

只有算法/论文 claim 才使用：

```text
sealed dataset
formal holdout
preregistered metric
A/B effect run
```

## 27.4 Subagent review by default

开发审查默认：

```text
Functional Reviewer
Architecture Reviewer
Generalization Reviewer
Simplicity Reviewer
```

人工审查只在高风险 release、不可逆操作或正式 gold benchmark 时介入。

# 28. Anti-overengineering Contract

```text
1. 不为尚未发生的 failure 实现复杂机制。
2. 优先通用数据结构，不优先领域状态机。
3. 优先一个可复用 primitive，不增加大量专用工具。
4. 不重复实现已有 authority boundary。
5. 普通工程不使用研究级 preseal 负担。
6. 不在每个 turn/tool call 后 reconcile。
7. 不把 Working State 变成 mini Canonical。
8. 不把 Event journal 变成第二份完整 execution log。
9. 不用 hidden Reader/vLLM 修复 Host reasoning。
10. 真实 E2E 可用性优先于接口“看起来完整”。
```
