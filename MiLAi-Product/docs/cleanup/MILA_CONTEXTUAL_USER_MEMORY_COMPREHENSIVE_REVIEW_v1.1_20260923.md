## 1. 对原规划与上传评审的总体判断

### 1.1 原规划值得保留的部分

1. **长期记录与当前适用关系分离。** 情境切换先调整 UserView，不把一次例外自动改成长久偏好。
2. **Host 保有语义责任。** 服务提供查询、读取、写回与版本能力，不默认再运行独立画像控制器。
3. **关注与采信分离。** 被取回、被展开、被引用都不等于事实被证实。
4. **局部可逆、长期可纠正。** 暂不采用不全局失效；明确更正需要进入未来实际使用。
5. **强简单与外部方法共同评价。** 普通画像、普通工具笔记不能被禁止记条件、例外和来源。
6. **Core、Assisted、反馈条件及成本保持可说明。** 这些区分必须落实到运行配置，而非只出现在免责声明中。

这些是 P 已有的有价值设计，不必因为收益尚未证明而推倒。[P §0、§3–7、§12–17]

### 1.2 上传评审最重要的纠正

R 对原计划“复用已有卡片、工作区、版本、检索”的笼统表述提出了正确质疑：**概念已经存在，不表示产品对象、公开接口和实验对象相同。**

R 记录，Product 可直接使用的是 Working State、Host Note、Evidence 和治理后的 Claim；Lab 的 MemoryCard、Workspace、Attention 和 Revision 是研究实现。Note 当前的直接发现方式是 literal substring，State 的机械引用处理主要识别 Evidence，而非通用 Note-version 依赖。全面物理清除也没有因为提供 Note tombstone 就完成。[R §1、§3.2–3.4]

因此，原计划的工作量应从“几个 Lab 文件加一条接线”调整为：

> 一个通过公开接口工作的 Host 方法原型；若承诺更强的版本依赖、共享与清除，再明确列出对应 Product 工程。

### 1.3 不能由评审意见推出的结论

- P0 不等于全部功能必须一起做完，才能观察一次方法行为。R 已明确优先级针对完成声明，不是统一研究闸门。
- 原生终点问答不足以验证全部机制，不等于该 benchmark 没有价值。
- 未训练 Host 的实现可行，不等于自然使用率或收益已成立。
- 普通条件笔记可能打平，不等于用户画像必须重新固定为一份不可更新文档。
- 104 项既有测试通过，不代表此次新画像方案已实现。

## 3. 对象与身份：不先创建“用户画像数据库”

### 3.1 建议的最小对象映射

| 逻辑用途 | 第一版载体 | 说明 |
| --- | --- | --- |
| UserView、WorkState、AttentionIntent | 一个 Host 工作对象，必要时经 Working State 保存 | 一个命名空间中的子结构足够；不是三份独立持久表 |
| 长期条件性偏好/经验 | Product Host Note | 仍为 HOST_WORKING；不因长期保存变成 Canonical |
| 原始用户陈述、业务观察 | 合法来源；适用时使用 Evidence | 不自动把模型推测或第三方文本改成用户原话 |
| 修订记录 | Note 的准确版本、操作回执与明确的变更依据 | 原因和语义支持不是普通 CRUD 自动证明的结果 |
| 当前输出材料 | Host/服务层的有界投影 | 可重建，绑定准确来源，不成为新的事实权威 |
| benchmark 与评分制品 | Lab | 不进入 Product 的依赖或在线配置 |

[R §3.4] 的映射已合入 P §4、§9，替换原来的泛化描述。

### 3.2 身份至少分清四个含义

这是对 R 身份建议的进一步细化：

- **数据 owner/授权主体**：谁有权访问这份记忆。
- **执行 Host**：当前是哪一个客户端、任务或分支在工作。
- **陈述来源作者**：这句话是谁说的、来自何处。
- **陈述所指对象**：偏好或要求属于用户本人、客户、同事还是任务受众。

前两项由可信绑定控制访问和隔离；后两项既包含来源事实，也包含可错的语义解释。模型说“这是我的用户的偏好”不能改变 owner，更不能取得别的 principal/project 的数据。

首个双 Host 范围建议严格写为：**同一授权 owner、同一 project、兼容的可信 principal binding，两组明确不同的 task/branch 绑定。**没有相同绑定或明确委派时，不因 owner 标签相同而推导共享。交接使用可复查记录或副本，不让 B 直接修改 A 的私有 State head。[R §3.1]

首版不需要跨 principal 委派和跨 project 全局画像同步；这些不是局部方法验证的前置条件。

## 4. 新鲜度和安全：四个判断，不是一枚 valid 标记

| 判断 | 主要依据 | 第一版推荐行为 |
| --- | --- | --- |
| 可披露性 | 服务端当前授权、撤销与保留状态 | 不可读时阻断相应内容及能确定的派生披露 |
| 精确版本 | 实际读取的对象版本/digest 与对应当前视图 | 明示发生变化，触发有关视图复查；合法历史仍可精确读取 |
| 当前适用性 | 任务、受众、用户要求和反馈 | Host 重新判断，不自动删除长期内容 |
| 语义充分性 | 对当前具体问题实际取得的证据 | Host 可保留未知；不由 CAS 或完整字节认证 |

R 对前三项的区分是必须采纳的关键改进。[R §3.2] 第四项在 P 中已有，应一并放入同一合同。

内部引用按实际对象区分，不能给不可变 Evidence 虚构 Note 式 revision：Evidence 使用准确 ID/digest/范围；Note 使用 ID/version/digest；Claim 使用其真实版本标识。FILE 来源仅有 Host 声明时，应保留该可信度边界，不自动宣称服务器验证了原作者或文件权限。[R §3.2、§3.4]

### 4.1 局部关注不要求每轮重读全池

建议允许延续的是“下一步优先看什么”的工作安排，而不是“其他信息永久无关”的结论。问题/受众变化、相关依赖版本变化或新反馈出现后，Host 重新评价受影响部分。不能只用 task_id 相同来判断语义仍然适用。

无关新来源不必触发全池重发，但服务并不自动知道所有新增材料是否语义无关。因此，当前用户要求和真实新反馈仍直接进入 Host；有限的引用依赖检查不能成为屏蔽未知反证的理由。

### 4.2 不把局部优化变成更弱的披露保证

如果一个不透明持久 State 已混入不可披露内容，而系统不能可靠定位受影响字段，仍需沿当前合同隐藏该 payload，不能为了维持任务焦点从缓存取回受限文字。Host 之后可以使用仍可读的材料形成新的、来源清楚的视图。

对含 Note 派生内容的 State，原型可信接入层还需在启动／恢复呈现前通过公开接口复查已记录来源；当前 launcher 与 Runtime 的 Evidence 检查不提供这一通用 Note 保证。未实现或复查失败时不注入对应 State，报告恢复受限，不能先披露正文后补检查。此项已列入计划 W1 与首阶段验收。

首版只对显式、直接依赖作机械处理是可行的；但应诚实标注它的覆盖范围。模型漏报引用不能得到披露豁免。保守来源集合可用于安全约束，却不能被解释为每条来源都支持该 State。

### 4.3 不承诺跨 Host 的瞬时一致

版本变化发生在读取之后时，另一个 Host 可能仍在处理旧快照。建议规定“本次响应对应什么准确快照/版本”，下一合法读取或受支持通知再触发复查。不要写成所有外部 Host 立刻停止使用旧内容，也不要以无限重验替代一个明确的一致性合同。

## 5. 方法必须从分工图推进为一页可执行政策

R 的八条政策草案适合作为 v1.1 的基础。[R §4] 建议候选的最小差异固定为以下闭环：

1. **当前要求优先进入理解。** 历史 State 不过滤新用户要求或真实反馈。
2. **只为具体缺口取材。** 已有信息足够时直接完成任务；查询应对应一个会改变回答的未知点。
3. **更新当前适用关系。** 受众、目的、约束或来源解释变化时，调整 UserView，而不是直接翻转长期画像。
4. **局部变化与持久更正分开。** 一次情境例外只作用于当前任务；有范围、有来源且允许保留的持久变化才更新 Note。
5. **焦点允许返回。** 未选材料不删除；返回旧情境时重新检查适用性，而非自动采用旧结论。
6. **让 State 产生实际后果。** 在支持的接入方式中，State 影响下一查询、精确读取或下一次材料投影，不能只增加一段总结。
7. **维护不阻断已成功工作。** 记录失败不重复业务动作；未知提交先核对，不换 ID 盲写。
8. **记录可错、可以不更新。** 无新增依据不制造新版本；无后续价值不强制保存。

以上不是新的 Runtime 状态机，也不要求每步分别调用一次模型。其政策文本、输入位置、可用工具和运行边界需要版本化，才能与 HOST_TOOL_SIMPLE 区分。

普通方法仍允许自然记录情境、例外和来源。候选的主张不是“只有我有权限使用这些字段”，而是固定的组织与更新规则是否在相同能力下更有效。

### 5.1 对隐式偏好的保守规则要有明确适用范围

“隐式推断先放在局部理解”适合作为首版策略，但不能无说明地变成“所有隐式偏好永不持久化”。否则，与隐式偏好 benchmark 的研究目标可能发生偏移。

建议首版明确选择：未确认解释主要留在工作 State；需要持久保留假设时，必须另行规定授权、来源、范围和可错性质。不要把假设写成已确认人格，也不要为了保证隐式任务得分而无限扩写画像。是否引入持久的条件性假设，属于可比较的后继政策，不是本次默认新增模块。

## 6. 一个确定的 Host 接入，而不是“可以有 hooks”

R 已引用自然 Working State 不采用的历史记录，说明仅提供工具不能保证使用。[R §3.6] 首版选定本地 [launcher.py](../../integrations/mcp/src/milai_mcp/launcher.py) 路径，以 **ASSISTED / STARTUP_PREFETCH** 交付。当前 launcher 未向子服务传 `--catalog`，[codex_full.py](../../integrations/mcp/src/milai_mcp/codex_full.py) 默认 `legacy`，因此没有闭环需要的 Note 工具；实施须新增受控透传并在方法配置中显式选 `ordinary-memory-v1`。该接线尚待开发，不能按现状列为已复用完成。

| 时点 | 谁负责 | 最小行为 | 不能据此声称 |
| --- | --- | --- | --- |
| 启动 | 可信 launcher | 建立 principal/project/独立 task/branch 绑定，核对工具目录并预读同作用域 State | State 一定有价值、最新或被使用 |
| Host 正常工作 | 原有 Host 工具循环 | 按固定政策查询、读取与可选写回 | 启动 launcher 已经逐轮装配请求或捕获响应 |
| 检索结果到达 | Host | 依据真实返回重新判断；此时才能消费新材料 | 前一轮计划已经包含尚未取得的证据 |
| 显式交接/需续接时 | Host 显式工具保存 | 有真实工作产物才写回；记录独立保存回执 | 进程退出/业务 final 等于 checkpoint 已成功 |
| 保存失败/结果未知 | §7.2 中各对象的恢复合同 | 分别报告业务、Note 与 State 结果 | State 具有 Note 操作查询工具，或自动重做已完成业务 |

当前 launcher 是预读后启动外部 Host 进程，没有逐轮请求装配、响应工作产物接收或自动结束捕获。需要这些能力时，在 Lab 的受控 Host adapter 中明确实现请求、响应和 checkpoint 边界，另标 **ASSISTED / PER_TURN_CONTROLLED**；不能只估为结束时的薄接线。严格 State 消融和逐轮 presented 确认须等相应边界真实可控。`--mcp-url` 兼容路径的身份和 task 由服务端拥有，不允许本地参数覆盖。

Core、启动预读 Assisted 和逐轮受控 Assisted 分开报告；读取发生不证明语义利用。任何模式下，未调用、没有写回、没有呈现确认均保留在整体结果中。首阶段验收已落实到计划 §15.1：实际 tools/list 与授权绑定、启动顺序、真实保存回执、两类 UNKNOWN、空更新／受限 State、时间边界；逐轮能力另行验收，不按 launcher 启动成功推定完成。

## 7. Revision：首版收敛到单 Note，补清跨对象时序

### 7.1 单条更正的最小路径

> 获取旧 Note 的准确版本及依据 → Host 提出有范围的新内容 → Note CAS 提交 → 获得明确回执 → 当前 State 改为依赖已确认版本 → 必要时保存 State → 后续任务精确读取。

这条路径首先是顺序操作，不是新建跨对象事务。R 已说明 ChangeRecord 与单条 CAS 不自动提供多对象原子性。[R §3.4、§4]

### 7.2 必须定义的部分成功结果

| 实际情况 | 合理结果 |
| --- | --- |
| Note 更新成功，State 保存失败 | 新 Note 保持已提交；State 不冒称同步成功，恢复时重新核对 |
| 本地解释已更新，Note CAS 失败 | 当前可以保留有依据的局部判断；不宣称长期记录已经更正 |
| Note 提交结果 UNKNOWN | 使用原 operation_id 经 milai_note_operation_get 核对；不换 ID 重写，不更新“已提交新版”依赖 |
| State 提交结果 UNKNOWN | 没有对应操作查询工具；保留原 operation_id、state_id、expected_version、payload 及完整请求与作用域，必要时按合同受控重放相同请求；无自动重试或换 ID |
| 两个 Host 竞争同一旧版 | 后提交者读取真实当前版本再判断，不按最后写入覆盖 |
| 多条 Note 需要修改 | 逐条报告部分成功，或另做明确事务设计；首版不默认全局原子 |

上述差异由 [ordinary-memory-v1 合同](../../contracts/mcp/ordinary-memory-v1.md)和[恢复实现](../../integrations/mcp/src/milai_mcp/recovery.py)明确规定。当前 State GET 或缺少回执不能单独证明进行中的原写入失败；业务完成、Note 提交和 State 保存分别报告。

Working State 稀疏更新属于 Host 侧便利：先在可读、版本明确的基底上合并受控命名空间与保留依赖，再完整替换 CAS。**未提供 work_update 或空稀疏 patch `{}` 表示不更新；明确提交到 Runtime 的 `payload={}` 是合法的空载荷完整替换，不删除历史版本。**读取结果的 `{}` 必须结合 status、payload_withheld、warnings 与版本解释，不能将 ABSENT、EXPIRED、withheld 或服务不可用都当空白新建后覆盖。[请求模型](../../runtime/src/milai/domain/host_cognitive_state.py)、[返回实现](../../runtime/src/milai/application/host_cognitive_state.py)

### 7.3 机械派生与语义关联分开

精确绑定旧 Note 版本的摘要、索引和缓存可以失效或重建。另一个独立主张引用过旧 Note，不代表它全部错误；只能定位待复查范围，由 Host 根据其他依据判断。

当前行为结果必须关联当时真正返回/呈现的版本。任务后生成的新版本没有资格获得该任务已发生的效果记录。服务返回、Host 呈现和实质使用仍分层记录。

## 8. 检索：必须承认 Note 路径的现状，也不能因此退回无价值片段

R 记录 Product Note 搜索当前是 literal substring、创建时间与 ID 分页、256 字符片段；统一入口不会因此自动获得 Note 的 dense/temporal 检索，也不检索 Working State。[R §1、§3.5]

### 8.1 第一版最小路线

- 使用已支持的 Note 发现入口与准确 ID 读取，先跑通可追溯路径。
- 搜索片段只用于定位，实际需要采用的条目精确读取后才进入可用材料包。
- Host 在形成笔记时保留短、完整的条件单元；服务器只对已声明段落/单元作预算内组织。
- 多次读取带来的调用成本照计；尚未实现的批量读取不能列成已有功能。
- 需要更强 Note 检索时，单列 Note 索引扩展及其更新、权限、删除和版本语义，不将 Evidence 的已有能力转算过去。

### 8.2 两层 baseline 比较

**系统级：**完整 Memobase 与 MiLAi 各自采用自己的形成和检索过程，比较质量与完整成本。结果属于整套系统。

**机制级：**使用相同合法来源/候选能力，普通条件笔记与候选只改变当前视图、查询或投影中的指定部分。结果用于解释具体政策。

MiLAi 的 Note 词法发现弱于外部方法时，系统级落后仍是有效结果；但不能不排除取得差异，就把它全部归因于 State 设计。反之，给候选增强检索却保留弱简单基线，也不能宣称纯 Attention 收益。

## 9. 隐私与删除：既不能虚报，也不把生产清除当成全部研究的先决条件

R 明确记录 Note 目前存在逻辑删除，而物理清除及备份清除未完成。[R §3.3] 这一点应当纳入原规划的真实工作量。

建议区分四种请求：

| 用户意图 | 产品行为目标 | 不应混称 |
| --- | --- | --- |
| 本次不要个性化 | 本次输入不使用可选画像 | 删除长期数据 |
| 不要记住这段内容 | 不产生被禁止的持久副本或派生画像 | 仅在最终答案不说出来 |
| 停止返回既有记录 | 逻辑隐藏/tombstone 与相应依赖阻断 | 正文和备份已经物理清除 |
| 清除已有内容 | 按已声明范围清除主存、历史与派生物，并处理备份范围 | 纯 MCP 能抹除外部 Host 已收到的所有副本 |

研究使用允许的合成数据，可以先验证局部理解、持久更正和后续消费；但需要明确这是原型，不承诺尚未实现的真人长期数据清除。

**涉及真实个人数据的保存与删除承诺，必须由相应产品合同和工程支撑。**不能以“先做研究”为理由规避现有权限或明示的不保存要求。

本次补充建议：清除还应考虑再导入、缓存重建、操作回执或调试日志重新暴露内容的问题。可以采用最小必要的来源与删除状态控制，具体取决于产品承诺；不要把内容散列一律认定为完全不含个人信息，也不要为此先建设一个无限范围的数据治理平台。

## 10. Benchmark 与实验：保留选择，改正证明目标

我同意继续以 P 中的 PersonaMem-v1/v2 为主，不因 R 提及新版本就自动更换。本文不重新核验其当前许可证或数据发布状态；沿附件记录制定实验结构，实际执行仍使用固定制品。

### 10.1 三个结果系列

| 系列 | 主要研究问题 | 主单位 | 不能外推的结论 |
| --- | --- | --- | --- |
| 原生历史问答 | 历史与当前用户视图是否改善当下回答 | 按 persona/共享历史聚合的问题 | 自主跨任务修订或自然 MCP 调用 |
| 顺序回放 | 情境变化、返回和长期更正怎样影响后续使用 | 完整用户/任务序列 | 原生官方时间线之外的新成绩 |
| 自然 Host/交接 | 实际调用、读写、恢复及任务价值 | 独立任务或完整交接流 | 给定脚本查询的效果自动泛化到任意客户端 |

R 的这项分类应直接成为结果目录与表格结构，而非只是正文提醒。[R §6]

### 10.2 首版对照保持强而有限

原生 QA 主方法继续保留 PROFILE_INCREMENTAL、HOST_TOOL_SIMPLE、MEMOBASE_NATIVE、MILAI_CONTEXTUAL_STATE；QUERY_ONLY 是诊断。预选可容纳样本保留 FULL_HISTORY，不能裁剪后称为完整历史。

顺序回放优先使用普通条件笔记、候选及一个最有信息量的消融，不要求每条序列都跑全部外部系统。

HyperTrace 的选择反馈条件独立标记，不能将当前答案通过 chosen 通道交给隐藏标签实验。不同数据集、不同反馈条件的分数不能直接相减后归因。

### 10.3 反馈与接入是正交维度

建议配置分开记录：

```text
feedback_regime: HISTORY_HIDDEN_LABEL | CHOICE_FEEDBACK_REPLAY
integration_mode: CORE | ASSISTED
assistance_scope: NONE | STARTUP_PREFETCH | PER_TURN_CONTROLLED
execution_protocol: NATIVE_ENDPOINT | SEQUENTIAL_REPLAY | NATURAL_HOST
```

这只是拟议实验配置，不是 Product 公开 Schema。CORE 使用 NONE，ASSISTED 声明真实实现的辅助范围；接入方式不改变标签可见性。选择少量能回答研究问题的组合，不跑满乘积矩阵。

### 10.4 A→B→A 不能只测听懂当前指令

若最后一步重新给足了全部所需偏好，所有方法不用旧 State 也可以答对，那么它主要测当前条件理解。要测连续状态价值，后续任务需要早先的理由、约束或已完成工作，而各臂仍有相同合法历史访问能力。

不强制模型按“暂停—恢复”指令行事，不自动添加正确 UserView；让历史真的有用途，再比较如何复用。派生事件只按前瞻协议释放，结果不混入官方原生分数。

## 11. 消融需要阻断真实数据路径

### 11.1 STATE_LOG_ONLY 不能仅关闭投影

如果 State 仍进入 Host 上下文，它可以改变下一条 query；查询改变又会改变材料，即便服务端采用 STATIC 投影。R 对此的指出完全成立。[R §6]

建议根据问题只拆一条边：

- **State→查询**：在一个固定合法检查点中，固定来源/投影能力，比较有无该状态对查询的影响；下游结果标为指定续接诊断。
- **State→投影**：固定查询和取得的候选，在同一快照上比较静态投影与候选选择。
- **State 跨步继承**：后续 Host 不继承旧工作记录，但保留合法原始历史取得能力，并计入重建成本。

任何“去掉 State”的实验都要检查它是否仍留在历史工具响应、摘要、缓存、旧 assistant 消息或恢复载荷里。

这些局部干预不自动成为整套方法的端到端纯单变量实验。自由动作会产生不同的真实反馈，不能播放另一个动作的历史结果来维持表面相同输入。

### 11.2 TASK_LOCAL_ONLY 必须放在后续任务里看

独立终点题各自重建同一历史，通常无法识别上一任务的持久修订价值。应在一条完整序列中比较：当前任务都允许纠正，只有一臂将有依据的变化提交为长期记录，后续任务再按相同合法能力读取。

未发生修订仍进入总方法结果。某项机会确实存在但候选没有修订时，也不能因此从分母删除；无机会才记 NA。

### 11.3 APPEND_WITH_CURRENT_VIEW 是必要的强简单参照

保留不可变历史同时展示最新更正，并不要求复杂认知算法。候选若只因旧新版本不再并排混淆而获益，应承认主要是当前视图工程或普通更正组织的价值。只有在相同清楚的当前视图下，形成/使用政策仍改善任务，才能继续定位更深贡献。

## 12. 数据时序：本次建议补入的派生物泄漏风险

P 与 R 已正确强调 v1 排他上界及 v2 答案隔离。还需将同一时间边界扩展到所有派生物。

**任何派生内容及影响检索的统计，都不能依赖截止之后的信息。**不能用未来历史形成画像、摘要、上下文化向量或查询引导，再仅过滤原始事件。

只依赖单个不可变事件与固定转换、且转换未利用未来历史的向量允许预计算复用；候选资格、截断/排序与依赖统计仍须遵守当前授权及截止点。跨历史形成的向量、聚类或全局统计不能套用这一例外。约束对象是真实信息依赖，不是生成计算发生的墙钟时间。

历史构建缓存至少绑定合法 persona/历史身份、准确排他截止点、数据制品版本、形成政策/方法版本与作用域，另锁相关模型和转换配置；查询相关投影绑定实际查询条件。单事件缓存绑定不可变来源与转换身份，在消费时复查资格。更晚截止点产生的 Note head、State、摘要和查询引导不能服务更早题目。

最少覆盖：截止为 0、刚好在更正前、刚好在更正后、同历史多个截止点以及查询顺序不单调。其目的只是验证时间边界，不建立新的全库审核框架。

v2 中标准答案可在评价层构成未标正确性的候选集合；这是多选题格式的一部分。禁止的是让正确性标记、展开目标画像、未来证据或当前 chosen 在回答前进入方法。不同实验臂使用相同题面和选项排列规则。

## 13. 指标、成本与泛化主张

### 13.1 首先选定能接受的产品收益形式

TEST 前确定以下一种或少量预定形式：

- 质量不明显下降，生命周期成本或延迟下降；
- 成本增幅在预设容忍范围内，质量有实际有用的改善；
- 明确降低错误持久化/旧经验误用，同时任务质量与完整成本仍可接受。

质量非劣界、最小有用改善、成本容忍度及危害上限应按用途与 DEV 波动确定。本文不补造尚无依据的固定百分点，不在看见 TEST 后挑一条刚好通过的标准。[R §6]

### 13.2 更新指标必须定义机会和分母

“情境例外被误持久化”的分母来自预定例外情境；“明确更正后沿用旧主张”的分母来自具有后续相关任务的更正序列。机会不能由候选是否真的写出 patch 来定义。

没有评分标注时，使用前瞻的来源审阅规则与盲化判定，保留未知；不以 State 中有没有某几个关键词代替语义正确性。

### 13.3 完整成本包括被省略得最容易的部分

形成画像、Host 生成 State、状态反复注入、检索和原文读取、Note/State 保存、版本派生更新、失败、回执核对、交接均计入。无服务端生成不等于零额外推理。

例如，反复向 t 次请求加入长度约为 s 的 State，会新增量级约为 t×s 的输入规模；实际计费还取决于缓存与 Provider 记录，不能把该估算直接换成金额。只有最终请求与真实账单才能确认净节省。

共享历史构建一次可以摊销，但要报告摊销对象和次数；不要把一次建库成本在每题重复记，也不能把它移出比较后称为免费。

### 13.4 泛化须按实际开发暴露命名

v1 和 v2 都参与方法调试后，在两者未见用户上测试，支持的是多来源分布内的未见用户表现，不是从未见来源的零样本迁移。要研究后者，需指定一个来源用于方法调整，再固定版本进入另一来源；适配字段格式与依据语义失败改政策分开记录。

独立单位是 persona/共享历史簇或完整序列，重复 seed 只估计运行波动。英文合成历史上的结果不证明中文真实用户普遍收益。小型中英混合工程回归可以检查入口和召回，但不能冒充中文泛化确认。

## 14. 开源项目的吸收方式：保留四项，不再扩清单

以下角色延续 P 与 R 的已述核查，不是本次重新运行上游：

| 项目 | 保留用途 | 第一版不做 |
| --- | --- | --- |
| LangMem | 普通 Host 工具分工与强简单方法 | 不因借鉴工具形式替换整个 Runtime |
| Memobase | 完整画像/事件/当前上下文的外部 baseline | 不删去其真实模型筛选再称原生复现 |
| HyperTrace | 工作假设与长期偏好的分离；反馈研究参照 | 不把标准答案改成当前题的合法历史反馈 |
| OpenViking | 直接查询、分层展开与避免重复意图规划 | 不导入整套数据库或自动增加许可未明确的新依赖 |

代码、数据、运行模型各自固定来源与费用。P 中未锁定整仓 commit、LICENSE 与代码不同版本等问题应在实际复用前整理。此整理用一份最小 lock 即可，不要求重新建立繁重的供应链研究平台。

## 15. 修订后的开发路线

### 15.1 第一阶段：可运行、可比较的单 Host 原型

完成 F01–F03 中与本次路径直接相关的合同，以及 §6 的 ordinary catalog 接线和 §7.2 的恢复边界：可信绑定，一个 Working State 命名空间，单 Note 更正，准确读取，普通工具基线与候选一页政策。复用当前公开能力，限制数据范围，明确依赖检查属于该 Host 原型，不伪称全客户端产品保证。按计划 §15.1 留下可检查证据，不把待开发项改成已完成。

并行建立 Memobase 本地参照与 v1/v2 数据薄适配；不要求所有外部方法部署完毕才让普通 Host 和候选运行。

首个结果不是“State 能保存”，而是：一个合法历史缺口引发实际查询，材料进入当前理解，后续任务有机会使用它；无记忆必要时能够直接完成工作。

### 15.2 第二阶段：运行中的方法改进与顺序验证

围绕实际失败修改一个通用操作：错误范围持久化、未取得条件、返回原场景失败、更多查询却无效，或版本更正未影响消费。保留该次版本和费用。

同时完成预选的顺序回放，不以第一道题获胜为前提；数据来源不足或方法无法运行时报告具体限制，不靠增加接线测试替代研究。

### 15.3 并行产品化路径：产品生命周期能力

仅对计划要承诺的能力明确开发：通用 typed dependency 检查、共享授权、必要的物理清除/备份范围、发布适配器与对应真实 PostgreSQL 验证。不同能力可独立交付，不把它们隐藏为“最后接一下”。

研发原型可以先完成；本路径不作为限定数据、现有权限内的独立评价的统一前置条件。未交付的能力仍列为未实现，不能在用户数据产品说明里承诺。若某项评价确实依赖尚未实现的能力，先实现对应项或收缩评价范围。

### 15.4 并行研究路径：固定方法的独立评价与收缩

原型的必要接入正确、方法与评价条件冻结后，即可选择强简单对手，在预先保留的用户/来源/序列上评价，无须等待 §15.3 全部产品化完成。Core、启动预读与逐轮受控 Assisted 分表，未见用户与未见来源分别命名；只做最能解释结果的一至两项消融，模型执行遵守实际授权与预算。

最终决策可以是：保留候选、只保留某一形成规则、只保留投影或版本工程、回到普通工具方法，或者明确覆盖不足。任何决定都不能由测试通过数、写入次数或曝光次数替代。

## 17. 建议正式采用的结论

> MiLAi 情境化用户记忆的总体方向可进入增量开发。原规划中的对象、身份、版本依赖、状态生命周期和实验处理仍需落实到固定接口与政策。第一版以同一授权绑定下的单 Host/有限交接、一个 Working State、条件性 Host Note 和单条 CAS 更正形成可运行闭环；更强的通用依赖、跨主体共享和物理清除属于单列的 Product 承诺。原生问答评价历史利用，顺序回放评价局部适用与后续修订，Core/Assisted 自然接入评价真实使用。方法收益由强简单/外部对照、未调试用户及完整成本建立，而不是由状态字段或工程检查建立。

**最终评审意见：总体设计有价值，主要修订已进入计划正文，可按其明确范围增量实施。可行性限于声明的接入与能力；研究创新仍需超过强简单方法的独立结果。**

最有希望保留的创新候选是：**情境切换主要改变局部适用视图，持久变化才修订长期记录；这一区分实际改变后续取材与使用，在需要恢复旧情境时仍保留有效知识。**它需超过普通条件笔记与普通当前版本视图，不能只以 Attention、State、Revision 三个名称共同出现为依据。
