# MiLAi 情境化用户记忆
## Attention—State—Revision 总体设计、开发规划与 Benchmark 方案

**设计主张：共享有来源的记忆，各 Host 维护自己的当前理解；Attention 选择和组织材料，State 保留适用关系，Revision 只持久化有依据的长期改变。**

本文把此前的可逆记忆使用、选择性聚焦、依据范围修订、跨 Host 续接和动态用户画像，收敛到同一条可实现的方法线上。只采用已经公开实现、许可可核实的项目作为代码与算法参考；开放数据的许可与实现代码的许可单独处理。

本次完成的是设计文档，不是代码开发或实验执行。当前仓库的联合 Revision／Attention 批次继续保持暂停；本文不替换其冻结任务、预算和算法，不借用历史剩余额度。[P1–P3]

本正文在已合入[源码对照评审](MILA_CONTEXTUAL_USER_MEMORY_DESIGN_REVIEW_v1.0_20260923.md)与[综合评审](MILA_CONTEXTUAL_USER_MEMORY_COMPREHENSIVE_REVIEW_v1.1_20260923.md)的 v1.1 上，进一步纳入 Evidence／Note 关系与统一操作修改计划，内容版本为 **v1.2**；保留原 `v1.0` 文件名作为既有链接入口。`supersedes_plan_sha256` 指本次修订前的 780 行 v1.1；历史评审中的原计划散列仍指 658 行 v1.0，不是当前正文。以下开发与验收项均为计划，未因文档更新而成为已实现能力。

本次主要修订落点：§3.5 统一操作合同，§4.4 来源与记录关系，§6.5 关联读取，§7.5 来源／Note 分步提交，§9.4 开发切片，§13.6 接口对照及 §15.4 验收。既有情境化记忆政策继续保留，接口变化与方法变化分别版本化。

## 0. 执行摘要与主要决定

### 0.1 本轮应交付什么

开发一个可关闭的“情境化用户记忆”方法：在不训练 Host 模型、不默认增加服务端生成模型的前提下，利用 Host 的正常查询、阅读和写回，维护有来源、可修正、可返回的当前用户理解。用户画像不是唯一的固定文档，而是长期信息集合在当前任务中的可解释视图。

按三个完成层级交付，避免把方法原型、产品承诺和研究结果混为一项：

| 层级 | 应交付内容 | 完成边界 |
| --- | --- | --- |
| 首版原型 | 同一授权绑定下的单 Host、一个 Working State 命名空间、条件性 Host Note、单条 CAS 更正、普通工具基线与候选政策；随后增加一次有限交接 | 只承诺该接入真实支持的读取、依赖复查和写回；不冒称任意客户端均支持 |
| 产品生命周期 | 按实际承诺补通用版本依赖、跨主体共享授权、物理清除及备份范围、发布适配器 | 单列 Product 工程、ADR／迁移与相关真实数据库验证 |
| 研究确认 | 强简单与外部比较、原生问答／顺序回放／自然 Host 分表、冻结方法后的独立评价及完整成本 | 工程通过不替代收益证据；允许保留简单方法或报告未建立收益 |

实现可以增量推进，不要求某一组件先赢 benchmark 才允许集成下一组件。限定在允许的数据与现有权限内的方法研究，可以与产品生命周期建设并行。

### 0.2 采用与不采用的方案

| 决定 | 首版安排 |
| --- | --- |
| 产品基本形态 | MCP 记忆服务；Host 保持原有求解与业务工具循环 |
| Host 操作 | 默认记下内容、按可信引用保留来源、按准确版本修改记录；不要求先判断正文应属 Evidence 还是 Note |
| 对象边界 | 统一操作入口与返回外壳，保留来源快照、Note 版本、Working State 及治理后 Claim 的差异；不合表、不自动提升权威 |
| 语义判断 | 由 Host／用户提供，Runtime 不判断偏好真假或是否应当切换路线 |
| 长短期分离 | 长期条件性记录与任务局部用户视图分开；两者共用来源与版本能力 |
| Attention | 优先使用 Host 的具体子问题、读取选择和短工作记录，不要求每轮输出固定模式 |
| State | 自由文本为主，技术外壳绑定任务、来源版本和更新位置；不建立人格标签大全 |
| Revision | 先明确对象与范围，再提交准确前驱；保留历史，但不无限传播语义修改 |
| 学习 | 首版不训练 Host、不建 RL 平台；反馈统计保持可选且不充当事实权威 |
| 外部参考 | LangMem 的 Host 工具分工、Memobase 的画像与事件组织、HyperTrace 的工作假设、OpenViking 的直接检索与分层读取 |
| 主验证来源 | PersonaMem-v1 与 PersonaMem-v2 文本数据；两者回答不同问题，分表报告 |
| 辅助验证 | LongMemEval 的更新／时间／拒答能力；已有 DB／OS 仅做通用回归，不冒充画像验证 |
| 暂不纳入默认范围 | 未核实许可的代码、PrefEval／PRISM 的受限材料、大规模多模态、第二求解模型、新的图数据库 |

### 0.3 什么可以算进展

工程进展是方法能够通过真实 MCP／Host 接口工作；方法进展是当前理解与后续取材确实改善了选择；研究进展是同一版本在未参与调试的用户与任务上取得质量—成本证据。三者分别报告。

最终可以只保留一个简单的有效增量。若普通条件性笔记和相关检索已经同样好，则删除没有增量的特殊控制，不维护一套为了概念完整而存在的流程。

## 1. 当前依据与需要继承的实验教训

### 1.1 最新代码状态与历史结果分开

沿用前轮 GitHub 只读核对的固定提交 `main@5f233a16829b9c2db603153b0e7d28dd6edb2188`。根 README 明确 Product、Lab、Archive 的职责；该快照的状态与联合运行说明记录：Revision／Attention 运行时候选已合并，真实联合实验未开始，用户指令仍为“上传代码，不启动实验”。[P1–P3]

直接可复用的 Product 对象是 Working State、Host Note、Evidence 与治理后的 Claim 及其公开接口。Lab 的 MemoryCard、Workspace、选择投影和 Revision 属于研究实现，不是可直接导入 Product 的同一套卡片 API。Working State 当前按完整 payload CAS 替换，机械依赖主要识别 Evidence；Note 仍属 HOST_WORKING，提供词法发现、准确版本读取与逻辑删除。通用 Note-version 依赖、全面物理清除以及超出现有授权绑定的共享都是待实现项，具体映射见 §4、§9。[I1–I4]

当前 `compact-memory-v1` 已将普通保存简化为 `milai_memory_save(content, operation_id)`，默认创建 Note；读取可直接复用服务返回的 `read_arguments`。它仍以 ADD_NOTE／UPDATE_NOTE／CAPTURE_EVIDENCE 路由不同写入，并保留相应权限与恢复合同。本文的增量是减少来源捕获及修改时的手工字段组织，不把已有默认保存和引用读取重复记为新功能。[I7]

当前 Evidence capture 中的 speaker、source_ref、observed_at 等仍可由调用者声明；compact 对应路径的 permission_snapshot 已由服务端可信绑定形成。已有来源字段不证明外部用户确实说过这些话，新增来源句柄也不能仅由模型自行填写后获得可信地位。Note 的 Evidence 引用已经参与可读性检查，并非两个尚无关联的对象。[I8–I9]

当前 Attention 的全池状态有效性与一轮滞后，是旧候选的明确设计，不在本文中静默改动。[P3–P4] 最新 Utility 批次结论仍是 `KEEP_SIMPLE / BENEFIT_NOT_ESTABLISHED`，不能以发生过选择或曝光推导可重复收益。Product 记录的自然 Working State 采用分别为 0/8、0/4；仅注册工具不保证形成与保存有价值的 State。[P9–P10]

原 v1.0 转述的 9 月 16 日报告称：v0.6 在 DB／OS 正式比较未达到质量和成本收益标准；v0.7 已出现功能轨迹，但仍保持 UNPROVEN。当前未取得这些附件原件及固定归档身份，因此仅保留历史线索，不将其作为本轮独立核实的事实或当前状态依据。[P5–P8]

### 1.2 从失败中导出的设计要求

| 已有观察 | 本方案中的直接响应 |
| --- | --- |
| 选择与修改发生，不自动带来质量提升 | 每项创新必须对应“下次提供什么／保留什么／改变什么”的操作差异 |
| 经验可能把检查变成额外义务 | 记忆优先替代重复理解与查找，而不是强制增加检查清单 |
| 输出格式与额外复核曾增加成本 | 优先正常工具调用、稀疏写回；不增加逐轮 Reviewer 或修格式模型 |
| 旧版、新版呈现与实际使用容易混淆 | 分开记录 returned、presented、Host 报告使用和任务结果，不以曝光计数证明收益 |
| 短单任务没有真正的状态持续机会 | 主验证转到原生多会话画像与用户偏好数据，而非反复跑短 DB 题 |
| 一个组、几个任务无法支持泛化 | 数据从开始按用户／来源划分；固定方法迁移是主交付，不是无限延期的附加项 |

此表为基于来源的设计推论，不是对旧实验重新归因。已有负结果、失败、未知账务与未运行位置均保留。[P5–P8]

### 2.2 参考实现与 MiLAi 增量必须分别命名

`MEMOBASE_NATIVE` 保留其画像形成、事件维护、筛选和上下文预算过程；变更 Provider 或存储接线时列出移植差异。不能删去内部模型步骤后仍声称是完整 Memobase。

`HOST_TOOL_SIMPLE` 采用 LangMem 式正常搜索与记忆管理，由共同 Host 自行决定写什么、何时查。普通方法允许形成条件、暂存和纠正；不能禁止 baseline 自然使用候选也想实现的合理行为。

`MILAI_CONTEXTUAL_STATE_v0.1` 是本文拟议的新方法标识，不覆盖 v0.6、v0.7 或已冻结联合候选。它组合采用局部状态、查询意图和有界修订；不声称是四个上游系统的完整复现。

`HYPERTRACE_FEEDBACK_REFERENCE` 仅用于真实或明确模拟的选择反馈条件。其 PersonaMem-v2 适配器将 `correct_answer` 设为 chosen，并按 persona 组织问题序列；这不是原生“读取聊天历史、隐藏答案”的评测流程。原适配器中的 `gt_profile` 只能进入评价，不得进入 Host 或更新输入。[O3、O9]

### 2.3 本轮不引入的新依赖

不将参考记忆系统串成产品处理链；不为画像增加图数据库；不新增常驻推理控制器；不训练 Host 权重；不建设通用 bandit／RL 平台。外部基线放在 Lab 的独立环境，产品保持自身可部署依赖边界。

## 3. 总体架构：一个服务核心，两个接入级别

### 3.1 逻辑数据流

```text
当前用户要求、已授权历史、真实新反馈
                  │
                  ▼
           外部 Host 正常工作
       形成子问题、解释来源、决定行动
                  │
          MCP 查询／读取／写回
                  ▼
           MiLAi 记忆服务层
   按对象检索 → 准确读取 → 选定 Host 有界组包
                  │
     ┌────────────┴────────────┐
     ▼                         ▼
任务局部 Working State     已提交的条件性长期记录
当前理解、焦点、返回入口   用户信息、经验、更正关系
     │                         │
     └──────────来源与版本──────┘
                  │
                  ▼
            既有 Runtime
       权限、CAS、幂等、生命周期、存取
```

Attention 是 Host 对本次材料需求的表达与落实；State 是可错的当前理解；Revision 是有更大影响范围的持久语义变更。它们共享来源与版本，不共享同一种更新语义。

### 3.2 Core MCP

纯 MCP 模式只承诺控制自身的查询响应、读取、写入与修订服务。服务不天然知道 Host 完整上下文、最终是否成功或哪些材料被模型使用，也不能删除 Host 已持有的历史响应。

默认查询快路径不增加生成模型调用。语义子问题由 Host 提供；既有 embedding、词法与精确检索的费用照实记录。无法判断相关性时允许返回有条件的材料，不能伪造“充分性已通过”。

### 3.3 Assisted Host

首版继续选定 Product 的本地 `integrations/mcp/src/milai_mcp/launcher.py` 启动路径，以 **ASSISTED / STARTUP_PREFETCH** 交付。现有代码已经执行可信绑定、TASK State 预读和 bootstrap 注入，但启动子服务时没有传 `--catalog`；`codex_full.py` 默认使用不包含 Note 工具的 `legacy`。实施须新增受控 catalog 透传；v1.2 将日常操作基线从此前计划的 ordinary 配置改为 **`compact-memory-v1`**，ordinary 保留为兼容／诊断配置。每次只启用所选目录，核对实际 tools/list、服务端绑定与各分支权限，不改变产品默认目录或既有授权。[I1、I5、I7]

统一意图增量采用 §3.5 的独立可选目录，与 compact v1 使用同一 Host 和现有后端比较；目录尚未实现前，不把拟议值当作可运行配置。catalog 透传与来源检查仍属待开发，不能按现状声称闭环已具备。

| 时点 | 首版责任与能力 | 尚未提供的保证 |
| --- | --- | --- |
| 启动前 | launcher 从可信配置绑定 principal／project／独立 task/branch，读取同作用域 State，形成有界 bootstrap | 预读不证明该 State 新鲜、充分或被模型使用 |
| Host 正常工作 | 同一 Host 按固定政策使用搜索、准确读取与可选 State／Note 写入；查询结果到达后才进入后续判断 | launcher 不逐轮接管请求，也不替 Host 生成工作记录 |
| 需续接或显式交接 | Host 有真实工作产物时通过公开工具保存；分别记录业务完成与保存回执 | 外部进程退出／业务 final 不等于 checkpoint 已提交；首版无自动结束捕获 |
| 保存失败／UNKNOWN | 按 §7.2 区分 Evidence、Note 和 State，保留原操作请求并报告部分成功 | 不重复业务动作，不为未知提交自动更换 ID |

若后续研究需要逐轮材料投影、精确 presented 确认或完整 State 消融，须在 Lab 的受控 Host adapter 中实现明确的请求装配、响应接收与 checkpoint 边界，另标 **ASSISTED / PER_TURN_CONTROLLED**。这些不是当前 launcher 的既有回调，也不能只估为结束时的薄接线。未捕获真实请求时 presented/use 保持未知，相关消融不能声称已严格阻断。

已有 `--mcp-url` 路径可用于兼容已配置的服务，但服务端拥有身份和 task 绑定；不能用本地 task 参数改写它。本轮不同时新增第二套接入。Core、启动预读 Assisted 与逐轮受控 Assisted 分别记录，未调用、未写回和没有呈现确认均保留在整体结果中。

### 3.4 多 Host

首个交接限定为同一授权 owner、同一 project、兼容的可信 principal binding，以及两组明确不同的 task/branch 绑定。不能依赖 `default-task:{project_id}` 区分并发任务，也不能只凭相同 owner 标签推出共享。身份与任务绑定由可信接入层形成，模型不得自行指定授权主体。

Host A 与 Host B 各自维护任务局部视图；交接使用来源可复查的记录或副本，不让 B 原地修改 A 的私有 State head。A 的“暂不采用”不能使 B 的共享记忆消失；B 接手任务时，交接记录是待结合新要求解释的输入，不是必须执行的命令。跨 principal 委派和跨 project 同步另列产品范围。

并发写共享记录仍使用准确前驱和 CAS。冲突后通过公开读取取得当前版本供 Host 重新判断，不假定错误回执已经包含最新内容；不以文本差异不重叠推断语义必然兼容。跨 Host 同步不保证外部模型已经阅读或修改了原有想法。

### 3.5 Host 统一操作的拟议合同

正式采用以下原则：**Host 决定保留什么、整理什么、修改什么；可信接入记录实际取得路径；服务依据准确引用执行权限、版本、依赖与恢复合同。**默认调用不要求按真假、说话者或“是否有依据”判断 Evidence／Note，但返回仍保留作者、加工方式、版本、治理地位及可修改性。

首个公开增量拟用独立可选目录 `compact-memory-v2`，这是计划标识，当前代码尚不接受此值。保留 v1／ordinary／legacy 的原有行为，不向同一目录追加两套别名。沿用统一 save/read/search 等操作；在新目录内用有限、可生成的输入模型表达下列意图，不引入任意 action + JSON 分发器，不增加分类 Agent。具体字段在 EN1 的 ADR 与合同中冻结。

| Host 意图 | 最小输入与路由 | 必须保留的限制 |
| --- | --- | --- |
| 记下内容（默认） | 内容、操作 ID、可选来源引用 → 创建 Note | 无来源也可保存想法、转述或计划；作者是提交者，不认证正文主张 |
| 保留来源 | 可信接入发布的 source_handle、操作 ID → 核对准确材料后捕获，或复用已有 Evidence 引用 | 不要求模型重写原文；现有 Evidence 被引用不代表延长保留期或获得新权限 |
| 修改记录 | 服务返回的 target_ref、新内容、操作 ID → 按目标实际能力执行 CAS | target_ref 携带 Host 实际读过的版本；Evidence 不原地修改，Claim 不进入普通写入 |
| 原文与整理都需要 | 先完成来源保留，再以确认的引用创建 Note | 首版明确分步调用及回执；组合请求按 §7.5 实施，不默认双写或原子提交 |

普通 MCP 只掌握调用参数和服务已有材料；没有可信来源句柄时，只能保存调用者整理，或明确报告来源保留不可用，不能把同一文本改标为已核验用户原话。用户意图明确要求保留原始来源而句柄不可用时，不静默降级为“原文已保存”。

Assisted 接入只有在授权范围内实际取得消息／工具响应后，才可发布相应句柄；当前启动 launcher 不拥有逐轮聊天内容。EN3 首先实现服务可核对的来源，外部 Host 消息捕获在真实事件边界可用后再启用，缺失能力单独报告。读取权限也不自动授权形成新的持久副本。

来源句柄绑定可信发布者、租户／principal／project、来源事件或准确版本、内容 digest／范围与取得路径；区分认证提交者、声明作者和已观察作者，不预设三者相同。由可信接入保存并校验映射，不依赖正文自述或模型生成的 URL；每次消费重新检查当前资格。目标引用绑定原对象与读取版本，服务不得自动取最新 head 替换 expected_version 后套用旧稿。引用中的能力说明只是提示，不授予操作权限。

幂等 ID 仍必须稳定；可信 SDK 可以在发送前生成并保存，裸 MCP 调用保持显式要求。新目录复用原后端操作的 ID 命名空间与权限检查，不因改工具外壳而重复写入。只改变入口的切片不迁移数据；新增持久关系或生命周期保证时，另按 §9.4 补 Product ADR、迁移与测试。

## 4. 信息模型：内容开放，技术外壳明确

### 4.1 最小对象

| 逻辑对象 | 首版载体／接口 | 责任与实现边界 |
| --- | --- | --- |
| SourceRef | 实际来源及公开引用；方法层区分 Evidence ID/digest/范围、Note ID/version/digest、Claim 的实际版本 | 当前 Note `source_refs` 仅接受 EVIDENCE／FILE；方法层类型不能直接冒充新增公开字段。FILE 是 Host 声明，不证明服务器核验了作者或文件权限 |
| ConditionalMemory | Product Host Note 的读取、创建、更新与操作回执 | 仍为 HOST_WORKING；持久保存不升级为 Canonical |
| UserView + WorkState + AttentionIntent | 一个 Host 工作对象，经 Working State get/update 保存 | 任务局部理解、工作位置与取材意图放在同一受控命名空间；Host 合并后通过完整替换 CAS 提交 |
| 原始陈述／观察 | 允许读取及保留的来源；适用时使用 Evidence | 来源作者与陈述所指对象分开；模型推断不转写为用户原话 |
| ChangeRecord | 单 Note 的准确前驱、新内容、操作回执与方法层变更依据 | 复用单条 CAS；变更理由的语义支持、多 Note／State 原子提交不是 CRUD 的现有保证 |
| ResponseReceipt | 服务 returned 版本；受支持接入另记录实际 presented | use 默认未知；投影可重建，不成为新事实权威 |
| benchmark／评分对象 | MiLAi-Lab | 不导入 Product，也不成为线上配置 |

以上是方法层约定，不新增七张表或七类公开工具。首版主要实现一个工作对象、有限组包和单 Note 更正。Runtime 当前不会自动检查任意 Note-version 依赖；Host 原型需在消费已记录引用时复查，通用产品保证另列工作项。

身份同时记录四种含义：数据 owner／授权主体、执行 Host／任务、陈述来源作者、陈述所指对象。前两者控制权限与隔离，后两者是来源事实及可错解释，不能相互替代。

### 4.2 State 内容示意

```text
当前任务：为业务团队整理项目汇报。
当前用户视图：此次要求结论与风险优先；实现细节不是本次重点。
依据：本轮用户要求；过去技术讨论偏好仅在技术讨论场景适用。
尚未确定：篇幅限制是否是一次性要求。
暂缓：内部技术推导，保留来源入口，用户转回技术讨论时重新采用。
下一取材：上线风险与业务影响，不重复读取全部个人偏好。
```

示例不是对真实用户建立的画像，也不是每次必须填写的表格。真实任务简单时可以只保存一句工作记录，或者完全不保存。

### 4.3 必须分开的语义

用户原话与 Host 推测分开；个人偏好与客户／受众要求分开；发生过的事件与当前仍有效的判断分开；相关性与可信度分开；暂缓与长期否定分开；语义更正与权限撤销分开。

一条信息被多次检索、被多个 Host 复述或被摘要重复，不增加独立证据数量。服务不因高效用分数就将一项推测升级为事实。敏感属性默认不主动推断或长期保存；源数据中的隐私限制需要传递到派生视图，而不是仅过滤最终回答。

首版将未确认的隐式偏好主要留在局部工作 State，按 §17 的允许保留范围处理。这是候选政策选择，不是“所有隐式偏好永不持久化”的产品定律。若后继方法保留条件性假设，须另行明确授权、来源、范围与不确定性，并单独比较，不能为得分把假设改写为已确认人格。

### 4.4 Evidence、Note 与引用关系

Evidence 保存一次来源取得／提交的内容快照；Note 维护作者希望持续修订的记录，每一版正文仍不可变。二者都可能忠实或错误，都不因对象名称获得真实性认证。模型输出也可以被记录为某次实际输出的来源，但这最多证明模型当时写过什么；用户亲写的笔记也可作为来源，不因名称叫笔记而失去来源价值。

| 关系 | 能说明什么 | 首版实现边界 |
| --- | --- | --- |
| 内容取得／加工关系 | 原样保留、准确摘录或后续整理；内容从何处实际取得 | 可信句柄核对字节／范围；模型声明来源时保留未核验边界 |
| 披露依赖 | 哪些来源的当前权限或撤销会限制记录返回 | 继续复用 Note 对已声明 Evidence 的资格检查；一个来源不可读时，当前不透明 Note 版本整体隐藏 |
| 语义支持／反驳 | 某份材料怎样支持或反驳某个判断 | 属于有作者、可错的解释；source_refs、hash、引用次数不自动认证支持关系 |

当前 Note 返回 `source_relation=HOST_DECLARED`，其 Evidence source_refs 已参与披露阻断，不能静默改成“普通相关链接”或“服务器认可的证明”。FILE 引用仅为声明；增加 Note-version 引用、引用片段和更细粒度披露都要另列合同，不能绕成 FILE 以规避依赖检查。[I9]

一份来源可关联多份记录，一份记录也可关联多份来源；允许仅有来源或独立想法，不强制 Evidence → Note → State 三步流水线。混合原话、解释和计划的文档默认是作者整理，有准确摘录时再附范围，不逐句强制分类。不把所有 Note 复制为 Evidence，也不凭正文相同合并不同时间的实际观察。

删除 Note 不自动撤销共享 Evidence；来源不可读会限制相关 Note 的返回，但不会自动证明其全部结论错误。引用不扩大 Note 的 owner／principal/project 访问范围，Note 被使用、引用或长期保存均不升级为 Canonical。

## 5. Attention—State 双向算法

### 5.1 双向作用的实际操作

**State → Attention：**已有状态指出当前真正需要的信息和未决条件，Host 形成更具体的查询或读取选择；不是把整份 State 一并塞进每次 search。

**Attention → State：**新材料改变当前用户视图与工作安排，包括适用范围、主体归属和不确定性；不是只调整相关性分数。

**反馈 → 两者：**用户更正和真实业务结果先改变当前理解，再按需要改变下一次取材；长期修订是另一个决定。

### 5.2 固定的一页候选政策与执行顺序

`MILAI_CONTEXTUAL_STATE_v0.1` 的首版政策如下；政策文本、输入位置、可用工具与接入边界共同版本化，不以 `host.normal_decision` 这一职责名称替代方法定义。

1. 当前要求与真实反馈直接进入理解，旧 State 不过滤新要求。
2. 只为会改变当前判断的具体未知点查询；已有材料足够时直接完成任务。
3. 受众、目标、约束或来源解释变化时更新 UserView，先改变当前适用关系。
4. 情境例外保持任务局部；有来源、有范围且允许保留的持久改变才提交 Note。
5. 暂缓材料保留返回入口；返回原情境时重新检查条件，不自动采用旧结论。
6. State 在支持的接入中影响下一查询、准确读取或材料投影；只生成总结不算完成双向作用。
7. 维护结果与业务结果分开；失败不重复业务动作，未知提交按原请求核对。
8. 无新增依据不制造新版本，无后续价值不强制保存；未维护的任务仍进入方法结果。

实际执行遵循 Host 工具协议：查询 → 接收真实结果 → 后续正常决策；单 Note 更正 → 获得明确提交回执 → 更新本地依赖 → 必要时保存 State。工具调用与结果完整配对，不能用尚未取得的证据，也不能先将 UNKNOWN 的 Note 新版写成已提交依赖。以上步骤不要求分别调用模型，也不强制在每次业务响应中输出结构化 State。

普通工具基线拥有相同合法工具、来源和预算，也允许自然记录条件、例外及更正。候选差异是固定的形成与使用政策，不是独占某些合理字段。

### 5.3 关注意愿与充分性分开

当前联合 Attention 候选把状态绑定到全池，并采用一轮生命周期；聚焦移除来源后可能无法刷新全池声明，从而恢复 baseline。这是原方法的已记录行为，不在原实验中改变。[P3–P4]

关注意愿是可延续的工作安排；相同 task_id 不能证明情境仍适用。目标、受众、相关版本或真实反馈变化时，复查受影响部分；不因未重读全池而自动重发全部材料。分别判断四个问题：

| 判断 | 依据与责任 | 首版动作 |
| --- | --- | --- |
| 可披露性 | 服务端当前授权、撤销与生命周期 | 阻断不可读内容及可确定的派生披露；不从旧缓存补回受限文字 |
| 精确版本 | 实际引用版本／digest 与公开接口的当前视图 | 已记录依赖变化时标为待复查；版本旧不等于历史内容非法或错误 |
| 当前适用性 | Host 对目标、受众、约束及反馈的解释 | 重建有关 UserView，不自动删除长期知识 |
| 语义充分性 | 当前问题实际取得的证据 | 允许未知；CAS、完整字节或来源存在均不证明充分 |

首版 Host 只对显式依赖复查；Runtime 的 Evidence 检查不等于通用 Note-version 验证。模型漏报引用不能成为披露豁免，保守来源集合也不证明每条来源都支持当前结论。不透明 State 混入不可披露依赖且无法可靠分离时，沿现有合同隐藏 payload，再用仍合法的材料形成新视图。[I2–I3]

含 Note 派生内容的持久 State 在启动／恢复呈现前，也须由原型的可信接入层通过公开接口复查已记录来源；当前 launcher 尚未提供这项 Note 检查。未实现或复查失败时不注入相应 State，明确报告恢复受限，不能等正文已发给 Host 后再把检查算作披露阻断。这是所选原型需要补齐的接线，不升级为 Runtime 已有的全客户端保证。

新的用户要求与真实反馈始终直接进入 Host，不能被有限依赖清单过滤。一次返回记录其实际快照／版本；并发更正后的下一次合法读取再复查，不承诺外部 Host 瞬时一致。

### 5.4 无须迭代的情形

材料足够时直接回答；没有新证据时不反复提高确信；没有后续用途时不写 State；没有历史细节缺口时不强制回读；没有长期变化依据时不修订用户记录。停止维护不是失败，也是合理方法行为。

## 6. 查询与上下文组包的详细设计

### 6.1 查询流程

1. 从可信连接绑定 principal／project／task 和权限；模型参数只表达已授权范围内的查询意图。
2. 按对象选择真实可用的发现入口，不把 Evidence／Claim 的检索能力转算给 Note。
3. 准确读取需要采用的对象，记录实际版本；不将 latest 等同于 true。
4. 在支持的 Host 接入中，根据当前需求形成有界材料包，保留权限、版本和继续读取入口。
5. 预算包括正文、来源、版本、目录与协议包装；分别记录服务 returned 和可验证的 Host presented。

| 对象 | 当前可用能力 | 不能默认获得的能力 |
| --- | --- | --- |
| Host Note | literal substring 发现，按创建时间／ID 分页；搜索片段 256 字符，采用前按 ID／版本读取 | 任意自然语言语义召回、dense／temporal Note 索引、全语义覆盖 |
| Evidence | 合法来源发现、metadata 浏览与 `milai_evidence_get` 原文读取 | 观察自动成为已接受事实 |
| Claim | 治理后检索；`milai_memory_get` 按 CURRENT_CANONICAL 返回，另记实际版本 | 为仅有聚合结果的材料虚构准确历史读取地址 |
| Working State | 在已绑定作用域 get/update | 全局 State 搜索或统一搜索中的 State 召回 |

统一搜索仍保留各来源的独立状态、权限与部分覆盖语义。[I1、I4] 需要 Note 语义检索或批量读取时单列索引／接口扩展，覆盖更新、权限、删除和版本语义。

### 6.2 三种粒度，不强制三次调用

入口视图用于定位；需要采用的完整小单元经准确读取后进入材料包；原始来源用于复查。当前 Note 搜索返回片段，不能声称一次搜索已经得到完整单元。首版优先在写入时形成短而完整的条件笔记，必要的展开与分页成本照计；批量读取尚未实现时不列为已复用。

条件、例外与否定句应保持在同一可用单元。完整性依赖明确的来源／段落边界或 Host 写入规则，服务不能从任意截断文本自动证明语义完整。超预算时返回明确预览与继续入口，或选择已声明的较短完整单元；生成新摘要不是默认补救。

### 6.3 空选择与冲突

空选择只清除可选记忆，不清除当前用户任务、最近真实反馈、必要前序事实或授权条件。被排除正文不得从采用备注、旧摘要或 Frame 中换一种写法再次注入。

已知冲突保留有关各侧及来源；没有足够预算同时呈现时，明确表示未覆盖，提供后续读取。不能只留下支持旧画像的一侧。服务不能声称自动识别全部自然语言冲突；Host 的冲突判断仍可错。

### 6.4 效率默认值

DEV 可采用：查询返回 4–6 个完整单元、额外记忆正文目标 1,500–2,000 tokens、任务 State 目标 400–800 tokens、一次普通问题最多一轮额外取材。它们是可调起点，不是认知规律或生产保证；复杂合法任务允许在共同预算中增加读取。

服务只有自身 token 计数或调用者声明余量时，不能承诺整个 Host 请求一定装得下。启动预读只控制 bootstrap 预算；逐轮受控 Assisted 实现后，在最终请求组装处使用实际 tokenizer。Core 明确报告自身响应体积及计数模型。

### 6.5 统一返回与来源展开

复用 compact 已有的服务端引用适配，逐步让搜索、保存与读取返回可直接复用的读取／修改引用。Host 无须从正文或 UUID 猜类型；服务内部仍按目标类型路由并逐项鉴权。共同外壳至少保留对象身份、准确版本或内容 digest、作者／来源声明、加工方式、治理地位、可用操作及来源展开入口；这些信息不得被扁平化为一个无差别 memory 文本。

当前整理可直接用于工作，需要核对时按引用展开来源；不强制每次重读所有原文。Note 正文分页与来源分页分别保留完整性标记，历史读取仍受当前权限限制。新的统一引用不能成为跨 Note/Evidence/Claim 权限的通行证。

现有搜索是 Note 词法分支与 governed resolve 的有界组合，后者不是任意原始 Evidence 的完整全文搜索。保留各分支的 NOT_AUTHORIZED／UNAVAILABLE／TIMEOUT／MISS、分页与覆盖状态；Note 命中不能掩盖另一路不可用。入口统一本身不增加 Note 语义召回，索引扩展按 EN4 独立验证。

相关整理与原文可关联展示，重复摘录或摘要按共同出处标明，不计作多份独立佐证。不同时间的真实观察仍保留不同事件身份，即便正文相同。去重只减少重复呈现，不抹掉事件、版本、来源或撤销边界。

## 7. Revision：有边界的长期变更

### 7.1 修订对象选择

| 观察 | 首先改变什么 | 长期变更的条件 |
| --- | --- | --- |
| 当前要求换了受众或格式 | UserView／AttentionIntent | 不直接修改一般偏好 |
| 当前任务不满足旧经验条件 | 当前采用关系 | 旧经验本身过宽或有错时才修订 |
| 用户明确说明“以后在此场景都如此” | 条件性长期记录 | 保留声明、范围、时间与权限 |
| 用户指出“那是客户的要求，不是我的” | 主体归属与当前采用 | 若已有错误长期记录，针对其准确版本更正 |
| 后来的事实变化 | 时间与当前版本关系 | 不把旧时点的真实记录追认为当时错误 |
| 一次行为有多个解释 | 当前待确认假设 | 不直接扩大为长期画像 |

### 7.2 一次提交应完成什么

首版收敛到单 Note：读取旧 Note 的准确版本及依据 → Host 提出有范围的新内容 → 服务按权限、前驱和作用域执行 CAS → 明确 COMMITTED 回执 → 当前 State 改为依赖已确认版本 → 必要时保存 State → 后续任务读取。语义依据不充分时保留局部判断，不通过 `valid=true` 自行认证真值。

这是顺序提交，不是 Note／State 跨对象事务，也不默认提供多 Note 原子修改。原用户授权之外的 Canonical 变更不属于本方案。

| 实际情况 | 必须报告与执行的行为 |
| --- | --- |
| Note 成功，State 保存失败 | Note 保持已提交；State 不冒称同步成功，恢复时重新核对依赖 |
| 本地解释已更新，Note CAS 冲突 | 可保留有依据的局部解释；读取真实当前 Note 后重新判断，不宣称长期更正成功 |
| Note 提交 UNKNOWN | compact 使用 `milai_memory_status` 的 NOTE_WRITE 目标，ordinary 使用 `milai_note_operation_get`，均关联原 operation_id；未明确提交前不改为“已提交新版”依赖，不换 ID 盲写 |
| Evidence 捕获 UNKNOWN | 当前没有独立捕获状态查询 API；保留原操作 ID 与完全相同的来源包，按合同受控精确重放，不以重新抓取的内容替换原请求 |
| State 提交 UNKNOWN | 无对应操作查询工具；保留原 operation_id、state_id、expected_version、payload 及完整请求和作用域。按合同核对，必要时仅受控重放完全相同的请求；不自动重试或换 ID |
| 两个 Host 竞争同一前驱 | 冲突后重新读取与判断，不以最后写入或文本差异不重叠推断可合并 |
| 多 Note 更正 | 逐条报告部分成功；需要原子性时另做事务设计 |

读取当前 State 或缺少回执不能单独证明一个进行中的原写入失败。业务完成、Evidence 捕获、Note 提交和 State 保存分别记录；任何维护恢复都不自动重复业务动作。新入口只包装各对象真实存在的恢复能力，不虚构通用 operation_get。[I1、I6–I7]

Working State 稀疏更新仅是 Host 侧便利：在可读且版本明确的基底上合并受控命名空间与保留依赖，再完整替换 CAS。**未提供 work_update 或空稀疏 patch `{}` 表示不更新；明确提交给 Runtime 的 `payload={}` 是合法的空载荷完整替换，不删除历史版本。**读取结果中的 `{}` 必须结合 status、payload_withheld、warnings 与版本解释，不能将 ABSENT、EXPIRED、withheld 或服务不可用混为“空白新建”。冲突后重新读取与合并，UNKNOWN 按上表处理。[I2–I3]

### 7.3 自动传播仅限机械派生物

准确依赖旧版本的摘要、缓存和索引可以失效或重建；独立结论只定位待复查范围，不按“引用过旧条目”自动删除。首版 Host 管理自己记录的依赖与缓存，通用服务端 Note-version 传播属于 §15 的 Product 工作项。

若后续扩展 Note 索引，新版提交与索引准备不同步时须返回实际版本，或回退到当前原文／词法发现；不能把旧 embedding 标为新版 embedding。当前 Note 的 DIRECT 路径不因此被描述为已有异步向量索引。

回滚是新的更正或恢复关系，不抹掉已发生操作。当前 Note 删除是逻辑删除，返回 `physical_deletion_supported=false`、`history_retained=YES`；不能宣称已清除正文、历史或备份。物理清除、派生状态和外部副本边界按 §17 分别定义并列 Product 工程。[I1]

### 7.4 效用与版本

当前任务使用 revision 1，结束后产生 revision 2，结果只关联实际使用的 revision 1／当时经验包。revision 2 的效果等待后续消费。新版不继承旧版的实测高分，但保留前驱及修订理由，不能通过反复改写清掉不良历史。

### 7.5 来源与整理的分步提交

优先复用已存在且当前可读的来源引用；确需新捕获时，顺序为：验证保留意图和 source_handle → 捕获准确来源并取得明确回执 → 以该来源引用创建／修改 Note → 按需要保存 State。来源内容或取得过程被纠正时记录新的观察及明确更正依据，不改写成“当初收到的就是新版”。

| 子操作结果 | 恢复与后续行为 |
| --- | --- |
| 来源未捕获或结果 UNKNOWN | 不创建声称已关联该新来源的 Note；先核对／精确重放来源操作 |
| 来源已提交，Note 明确未提交 | 保留来源成功回执；只处理未完成的 Note，不重复抓取来源 |
| 来源已提交，Note UNKNOWN | 查询原 Note 操作；不重新提交整组请求，不分配新 Note ID 规避未知结果 |
| 来源随后不可读或权限变化 | 后续 Note 写入／读取执行当前资格检查，不用本地缓存绕过；分别报告此前提交与当前可读性 |
| Note 已提交，State 未保存 | 按 §7.2 报告部分成功，不回滚业务或冒称 State 已同步 |

首版可由 Host 执行显式两步调用，不增加跨对象事务。若提供一次请求的便捷组合，可信适配层必须保存两个子操作的稳定 ID、原始请求与确认进度，并在重启／超时后沿用它们；整个组合不能只返回一个不区分子操作的 success。来源失败不伪造关联，Note 失败也不自动撤销仍合法共享的来源。以上恢复要求不授权后台自动重试或扩大保留范围。

## 8. 一个完整的用户情境与交接例子

初始记录是“技术架构讨论时希望保留依据与取舍”，有明确来源。用户随后说“这次给业务团队看，只要风险和结论”。Host 建立业务汇报视图，Attention 读取风险、影响和项目限制；技术细节暂时不展开。这里不发生长期偏好翻转。

用户接着说“现在我们自己讨论算法，把推导展开”。Host 恢复技术视图，读取之前保留的入口；不是先把长期画像从“喜欢简短”改回“喜欢详细”。恢复材料是为了当前判断，旧结论仍接受新反馈。

之后用户明确说“以后所有对外汇报都先写风险”。在允许保存的范围内，Host 提交这一带场景条件的长期记录。另一个 Host 在同一 project 和兼容授权绑定下接手新任务时，可以检索该记录，仍需根据当前受众判断适用性；跨 project 不自动共享。

如果用户纠正“那是这个客户的要求，不是我的一般偏好”，Revision 只修正相关主体／范围，其他技术偏好保留。共享知识变化与各 Host 的当前焦点分开处理。

本例用于解释运行逻辑，不能作为候选预先知道答案的正式 benchmark。开发可以把同类例子做成小型回归，但画像收益最终由未调试的公开数据和真实交互条件检验。

PrefEval 的代码仓库许可证为 CC-BY-NC-4.0，PRISM 的模型回复含非商业限制。它们不进入默认可复用代码或产品数据依赖；如后续有明确适用的研究授权，单独使用，不称为不受限开源组件。[B7–B8]

### 10.3 PersonaMem-v1 的重要对照

官方 issue #41 有使用者报告：仅给问题和选项也能获得较高分，并列明模型版本与采样控制限制。本次没有复现该数字，不能认定所有版本都已失效。[B9]

本方案因此对预定评价集合保留 `QUERY_ONLY` 对照，报告历史带来的增量，不按这个对照事后答错的题筛选“有效样本”。可在预选小部分任务做选项位置平衡，但不改官方主题目、不给候选定制新选项，也不反复抽样择优。

### 10.4 不能强行让 benchmark 承担不存在的能力

v1 的原生终点问答适合检查历史到当前响应，不天然提供完整在线反馈学习。v2 的问题行也不应被任意排序后声称是真实用户时间线。当前主评测称为“历史记忆与当前用户视图评价”。跨 Host 或任务内反复 State 更新，需要单独的顺序回放／接入条件，并说明它与原生问答的差异。

| 结果系列 | 研究问题与主单位 | 不外推的能力 |
| --- | --- | --- |
| 原生历史问答 | 按 persona／共享历史聚合，比较历史利用与当前回答 | 不直接证明自主跨任务 Revision 或自然工具采用 |
| 顺序回放 | 以完整用户／任务序列比较情境切换、返回与更正的后续消费 | 派生序列成绩不并入官方原生分数 |
| 自然 Host／交接 | 以独立任务或完整交接流观察真实调用、保存、恢复和价值 | 给定查询的服务效果不等于任意客户端自然采用 |

## 11. 数据适配与信息泄漏边界

### 11.1 PersonaMem-v1

按 `shared_context_id` 读取历史，使用 `history[:end_index_in_shared_context]` 的排他上界；索引等于上界的事件不可见，上界为 0 时历史为空。模型可以看到当前问题、普通多选任务的未标答案选项以及截止以前的合法会话；不能看到未来对话。

`correct_answer`、`groundtruth_info`、证据定位字段、未来更新标签、题目类型的诊断标记留在评价层。不能用它们选择来源、形成理想画像或指导长期写回。

原生问答中，同一 persona 的多个评价问题不写回共享记忆；单列的顺序回放才按预定协议允许后续消费。原生各题从独立 State 副本回答，防止先前测试题的选项或回答污染后续题。在相同合法历史边界可复用构建结果，但缓存必须满足下述信息依赖规则。构建真实发生一次时按一次计账，不重复记入每题，也不消失。[B1–B3]

**时间边界同时约束派生物及影响检索的统计。**不得用截止之后的信息形成画像、摘要、上下文化向量、聚类或查询引导，再仅过滤原始事件。更晚历史形成的 Note head、State 或摘要不能用于更早题目。

只依赖单个不可变事件与固定转换、且转换未利用未来历史的向量可以预计算复用；候选资格、截断／排序及依赖统计仍须只使用当前授权且在截止范围内的材料。跨历史形成的向量或全局统计不能套用这一例外。验收针对真实信息依赖，不要求所有独立向量在每个截止点重复生成。

历史构建缓存至少绑定 persona／历史身份、准确排他截止点、数据制品版本、形成政策／方法版本与作用域；另锁相关模型、转换配置，查询相关投影还须绑定实际查询条件。单事件缓存绑定不可变来源与转换身份，消费时重新检查资格。覆盖截止 0、更正前／后、同历史多个截止点和查询顺序不单调，不能仅按 persona 复用最后生成的画像。

### 11.2 PersonaMem-v2

使用 `train_text` 开发、`val_text` 选版本、`benchmark_text` 固定评价。数据卡声明这些分区按 persona_id 无重叠，实施时仍要对实际文件和历史关联做检查。[B4]

模型只读取相应合法文本历史和 `user_query`。标准答案文本可在评价层参与构造未标正确性的候选选项；各臂使用相同题面和选项排列规则。正确性标记、结构化目标 preference、证据定位、完整展开画像、未来证据或当前 chosen 均不得在回答前进入记忆形成或 Host 输入。

第一版独立编写薄适配器，不直接使用 HyperTrace 的 `_records_to_users()` 来宣称复现历史问答。该适配器把标准答案转为 chosen 反馈，只适合单独标明的反馈序列实验。[O9]

对隐私请求，分别判断允许读取、提炼、持久化与本次使用；不默认先把全部历史永久导入 Evidence，再检查“不记住”。评价还要检查错误持久化、跨作用域返回与派生画像，不能只检查最终回答。基准中合成的敏感信息不成为产品默认收集许可。

### 11.3 LongMemEval

剥离 `has_answer` 与 `answer_session_ids` 等定位标注后，按时间顺序提供原始会话。`question_date` 属于当前问题的时间背景；目标 answer 不进入方法。`oracle` 只可作为显式上界诊断，不作为候选正常输入。[B5]

先复用已有已开放 DEV 数据；历史受保护的 Formal500／确认池不因新画像规划自动开放。若需新确认来源，单列当前授权与暴露状态。

### 11.4 反馈、接入与执行协议分别配置

```text
feedback_regime: HISTORY_HIDDEN_LABEL | CHOICE_FEEDBACK_REPLAY
integration_mode: CORE | ASSISTED
assistance_scope: NONE | STARTUP_PREFETCH | PER_TURN_CONTROLLED
execution_protocol: NATIVE_ENDPOINT | SEQUENTIAL_REPLAY | NATURAL_HOST
```

这些是 Lab 拟议配置，不改变 Product 公开 Schema。CORE 使用 NONE；ASSISTED 声明实际实现的辅助范围，不跑满组合矩阵。

HISTORY_HIDDEN_LABEL 只提供合法历史，测试答案不回流。CHOICE_FEEDBACK_REPLAY 先预测并计当前结果，再释放预定反馈；标准答案构造的反馈标为模拟标签反馈，不声称真人选择。HyperTrace 与候选使用相同反馈时点，当前题不得重答择优。接入方式不改变标签可见性，真实反馈与模型生成内容分开。

不同反馈条件、接入范围和执行协议分表；不能通过不同数据集的分数差推导反馈的因果收益。

## 12. 主方法比较：不要只与旧 MiLAi 比

### 12.1 四个主要方法与一个诊断

| 方法 | 运行方式 | 回答的问题 |
| --- | --- | --- |
| PROFILE_INCREMENTAL | 一份持续更新的普通画像；同样可记条件、例外和来源 | 单一但可更新的普通画像是否已经足够？ |
| HOST_TOOL_SIMPLE | 共同 Host 正常使用搜索、读取和自由笔记，不要求专门双向状态政策 | 合理的工具式 Host 是否已经可以实现同样价值？ |
| MEMOBASE_NATIVE | 保留上游画像／事件形成、筛选与组包；完整费用计入 | 候选是否超过可运行的外部画像系统？ |
| MILAI_CONTEXTUAL_STATE | 本文局部用户视图、Attention 双向更新与有边界 Revision | 新的组合是否有质量—成本增量？ |
| QUERY_ONLY（诊断） | 当前问题与相同选项，不继承历史 | 分数有多少可能来自题面，而非记忆？ |

上下文能容纳的预选样本可另跑 FULL_HISTORY，作为不压缩的强参照。容纳不了时明确为窗口限制，不能静默裁剪关键历史后称为完整历史基线。

### 12.2 公平性

系统级比较保留各方法自己的形成、发现和组包过程，完整 Memobase 与 MiLAi 的差异归于整套系统。机制级比较固定合法来源／候选能力及后端，只改变指定的形成、当前视图、查询或投影政策。Note 词法发现较弱造成的系统级落后仍是有效结果，但不能全部归因于 State；给候选增强检索而保留弱基线，也不能称为纯 Attention 收益。

各方法相同 solver、Provider 配置、合法历史、当前问题、权限及任务工具；记忆形成与呈现可以不同，因为这正是算法。普通方法不被禁止写条件或重新检查。

Memobase 的内部形成／筛选模型调用全部计费；若为了统一模型而改 Provider，只报告该本地配置。不得把候选的高质量记录免费送给 baseline 后仍比较完整生命周期。

采用同一外层资源包并报告实际消耗；不同算法内部调用结构不同，不用一个总生成数上限隐藏各自实际求解机会。基线原生必需过程与额外维护拆开显示，不人为令对手无机会答题。

## 13. 实验安排：开发、迁移与贡献解释共同推进

### 13.1 E0：完成一条真实端到端流程

用一个预选 DEV 用户历史和多个合法时间点，运行普通方法与候选：历史导入、查询、当前 State、回答、新反馈、局部更新、必要长期修订、下一次检索。没有值得修订的事实允许不写；不通过脚本强制出现 patch。

E0 用于使完整方法真的可用，不承担泛化结论。机械 mock 只测参数和版本，不替代真实模型在该流程中的行为。无需重跑所有旧 Gate 或全库长回归才能开始局部开发。

### 13.2 E1：方法级开发比较

第一批计划每个主来源选择最多 8 个用户／历史组、每组最多 4 个预选问题；四个主要方法最多形成 256 个答题位置，QUERY_ONLY 最多另 64 个。这个算术上界不是模型调用上界，也不是现在的授权额度。若真实可用独立组更少，按实际覆盖报告，不拆同一用户凑数。

选样覆盖不同任务主题、历史长度、偏好更新与无更新、主体归属及无关材料，依据数据内容前瞻选择，不按候选结果挑题。首次完整流程包含在这批中，不重复收费。

开发允许修改政策、表示与投影，但新版本与旧版本分列。观察首先回答“什么工作发生了变化”，而不是每轮再加一句“请注意”。

### 13.3 E2：固定版本的独立评价与迁移口径

v1：先按 persona／共享历史关联分组，在任何候选测试结果出现前固定 DEV、VALID、TEST；建议约 20%／20%／60%，实际清单由制品盘点确定，不能承诺一个未核实的用户数。

v2：沿原生 train／val／benchmark 分区；在 benchmark_text 中固定一个主题分层、用户完整的评价子集，或资源允许时评完整分区。子集与全文成绩分别命名。

跨来源评价属于开发总目标，不以 E1 首题获胜为条件。正式确认仅在代码和政策稳定后进行；如果迭代过程中已经查看并使用了测试失败，相关来源降为开发暴露，新确认结论不从同一批中提取。

v1/v2 都参与政策调试后，在两者未见用户上的结果属于多来源分布内的未见用户评价。只有某一来源未参与政策调整，固定方法进入该来源时，才报告未见来源迁移；字段适配与根据语义失败改政策分开记录。同模型结果不称为跨模型证据，英文合成历史结果也不证明中文真人长期收益。

### 13.4 E3：最有信息量的消融

| 拆解 | 主要控制 | 可解释什么 |
| --- | --- | --- |
| STATE_LOG_ONLY | State 仍生成并计费，但后续 Host、查询与投影均不消费；检查实际请求中的残留 | 生成记录与真正用于后续工作的区别；单关投影不足以实现 |
| REBUILD_VIEW | 后续步骤不继承旧工作记录，从同样合法历史重建；检查消息、缓存与恢复载荷 | 连续 State 是否值得；重建成本计入 |
| TASK_LOCAL_ONLY | 在完整序列中允许当前纠正，但不提交长期更正，后续任务仍有相同来源读取能力 | 长期 Revision 对后续消费的增量；独立终点题不足以识别 |
| APPEND_WITH_CURRENT_VIEW | 普通追加更正，但显式展示最新关系，旧版可读 | 候选是否只是解决版本混用，而非需要特殊修订政策 |
| SHARED_RECORD_NORMAL_USE | 候选已生成的记录交给普通消费方式 | 特殊消费是否必要；记录形成费用不免费消失 |

每次按真实问题选一至两项，不一开始跑满五项乘积矩阵。无总体收益也可以做有目的的局部拆解，但拆解不能无限替代跨来源主表。

需要单独分析 State→查询时固定来源／投影能力；分析 State→投影时固定查询与候选快照。State 若仍出现在旧工具响应、assistant 消息、摘要、缓存或恢复载荷中，就不能声称已移除其影响。首版启动 launcher 无逐轮请求控制，不直接承担上述严格消融；使用已实现的受控接入并验证最终请求，否则报告未验证。

自由动作产生的真实反馈可能不同，不能把另一臂动作的历史结果强行回放为本臂反馈。APPEND_WITH_CURRENT_VIEW 是顺序更正的必要强简单参照；若它已达到同等收益，应将贡献收缩为当前版本视图工程。

### 13.5 E4：真实 MCP 与多 Host 使用

固定一个 Host／solver，只替换记忆服务策略；未调用工具、没有呈现确认或没有写回都进入主结果，不能筛掉。可以先做给定查询的服务对比，再做自然调用；前者不证明自然工具使用。

多 Host 只安排 §3.4 范围内的一次交接：同 project、兼容 principal binding、不同可信 task/branch。A 形成工作产物，B 结合当前要求接手；对照是同来源访问能力的普通交接笔记。稳定条件、受众变化、长期更正和无关更新分别观察；没有业务副作用回滚承诺。

如果数据需要额外构造 A→B→A 或受众变化，标为派生回放，不混入官方分数。合成改写只用于诊断，保留原来源与变更，不给 Host 注入正确状态标签。

A→B→A 的最后一步须确实需要早先的理由、约束或已完成工作，各臂保留同样合法历史访问能力。若当前指令已重述全部答案所需信息，该例主要测当前条件理解，不能证明连续 State 价值。

### 13.6 E5：统一接口的独立对照

先在同一 Host、相同来源、权限、后端、记忆政策与资源条件下比较 compact v1 和新意图目录。基线必须使用 v1 已有的默认 Note 保存与服务返回引用，不强迫它先分类或手工重建参数。普通保存已经足够简单时，新入口打平是合理结果。

预选片段覆盖用户原话、工具回执、Host 总结、无来源想法、混合引用、临时例外、明确更正、陈旧目标版本、来源撤销与捕获／写入 UNKNOWN；保留未调用、失败和没有后续使用的任务。工程故障注入测试与真实模型任务分开，前者不计为自然采用收益。

分阶段识别贡献：先保持可见材料和检索不变，测意图与引用组织；再在两臂都拥有同等真实来源接入的条件下比较句柄使用；最后才单独比较 Note 检索扩展。旧 compact 无法表达可信取得保证的部分，按接入能力差异另报，不将新增输入信息的收益全部归于工具简化。配置另记实际 catalog/输入合同版本与来源接入能力，不与 Core/Assisted 混为一个字段。

结果报告任务完成与后续误用、来源错误归属、补填／纠错调用、完整 tokens／延迟、陈旧版本覆盖或旧内容沿用情况。操作选错减少只支持易用性结论；后续可沿既有 PersonaMem 顺序回放检查情境例外与持久更正，不为新入口另建大平台或逐题改提示。E5 不自动增加 §13.2 的答题位置或当前模型额度，执行规模随实际授权单列。

## 14. 指标、统计与成本

### 14.1 主结果

主表报告原生任务分数、按用户聚合的正确性／偏好遵循、回答覆盖、完整 tokens、模型／MCP／业务调用、延迟与失败。不同 benchmark 不合成一个总智能分。

更新质量另外报告：情境例外被误写成长久偏好的比例、主体误归属、明确更正后仍沿用旧主张、稳定条件下无谓改写、无依据用户属性、隐私限制违反。数据没有对应标注时，用预选样本的盲化人工审阅，明确它不是官方指标。

统一接口另报来源取得路径与作者归属错误、目标版本错误、必要补填调用及保存后能否再次找到记录。接口操作成功、来源捕获准确和自然语言召回是不同指标，不以其中一项代替另两项。

机会与分母由预定任务定义：“例外误持久化”以有例外机会的情境为分母，“更正后沿用旧主张”以有后续相关任务的更正序列为分母，不以候选是否写出 patch 决定入组。有机会但未修订仍进入分析，无机会记 NA；方法主表保留所有预定用户、未写 State 和未确认呈现的任务。没有标注时按前瞻审阅规则保留未知，不以关键词是否出现代替语义判断。

### 14.2 评价成本与可靠性

PersonaMem 的选择题优先用可确定的选择解析与原生答案匹配；格式失败保留。自由文本子集评价按固定 rubric，先完成一次有限的人工校准；不让候选训练时知道 rubric 中的逐题答案。

LongMemEval 官方评价包含模型判定。沿用公开脚本时固定 evaluator、提示和版本；若使用同一个 Qwen 作为 Judge，明确同模型限制，并抽查分歧样本。不要为了输出合法 JSON 反复升级 Judge 再混成同一次确认。

### 14.3 样本独立性

按 persona／共享历史、在线完整流、交接任务簇分析，不把一位用户的多道题、多个窗口或多个 seed 视为独立用户。报告配对回收与回退及按用户／来源簇计算的区间。首批 DEV 只报告观察，不许诺显著性。

实际功效需要预先声明最小有用差异，并结合开发方差与独立簇数量确定。不存在“满 100 题就证明泛化”的固定门槛。运行波动采用预选少量完整配对重复，不重跑直到获胜。

### 14.4 全成本公式

```text
生命周期成本 = 来源处理与建库
             + 每次查询／embedding／排序
             + Host 回答与状态维护
             + State 重复注入与准确来源展开
             + 长期修订与派生更新
             + 失败、原操作核对／受控重放及交接

评价成本单列：原生评分、人工审阅、模型 Judge。
开发代理成本单列：不与 solver tokens 合并。
```

同一库在同一方法中真实构建一次，则列一次构建费，并另报声明摊销任务数的生命周期成本。使用别的方法形成的共享库用于消融时，保留构建来源与成本。

辅助 tokenize、model-info 与 embedding 请求单列，不把“生成次数”写成全部 HTTP 次数。没有反馈不记失败；未知用量不填零；没有费率不编造费用。本文不指定未经账本估算的巨大全局调用矩阵。

### 14.5 TEST 前固定收益标准

根据产品用途与 DEV 波动，预先选择“质量非劣且成本下降”“成本增幅可接受且质量有实际改善”或“错误持久化／旧经验误用下降且质量成本仍可接受”。在固定评价前填写质量非劣界、最小有用改善、成本容忍度和危害上限，并锁定机会分母与用户簇分析规则。本文不补造无依据的百分点，也不允许观察 TEST 后再挑选通过的标准。

## 16. 创新候选与淘汰规则

| 候选 | 相对普通方法的实际差异 | 支持它的证据 | 需要删减或改写的信号 |
| --- | --- | --- | --- |
| C1：情境视图而非画像翻转 | 当前情境切换主要改局部 State；长期更新另决策 | 新场景正确适配，返回原场景不丢偏好，误持久化减少 | 普通条件笔记已同样好且更便宜 |
| C2：State 与取材双向交互 | 当前未决条件产生具体查询，返回又修正适用关系 | 下一轮材料与判断改变，超过 STATE_LOG_ONLY | 只有状态文字更长，实际材料或任务无增量 |
| C3：可逆关注与有界 Revision | 暂时不采用不全局失效；语义更正只影响明确范围 | 保留未受影响能力，纠正后影响后续任务 | 改写扩大义务，或只解决普通版本视图问题 |
| C4：黑盒 Host 下的服务价值 | 不训练模型，少量工具与可选状态接入 | 自然 MCP／Assisted 各有清楚质量与成本收益 | 只在强制调用、完整轨迹回报下有效，却对外声称纯 MCP |

条件画像、Host 工具、假设维护与分层检索都有开源先行实现。组合名称不是创新证明。最终可以只保留形成规则、投影方式或一条修订语义；其余回归普通 Host。

统一 Evidence／Note 操作首先是接口与可靠性增量。只有在正确使用现有 compact 的对照下减少操作负担、保住来源与版本，并改善后续工作，才进一步讨论方法贡献；仅改名、隐藏枚举或减少工具数不单独构成创新证据。

公开研究材料的机制启发不等于临床迁移。本项目保留从人类外部工作记忆与执行支持方法得到的启发，但不声称模拟 ADHD、操纵模型内部 attention 或诊断真实用户心理。

## 17. 风险与前瞻性

**过度画像与生命周期：**只保留与用户目标相关且允许保留的信息；不能把隐式行为无限推断为敏感身份或人格。分别定义下列行为，不能用一个“删除”开关混称：

| 用户意图 | 行为与当前边界 |
| --- | --- |
| 本次不要个性化 | 本次不使用可选画像，不等于删除长期数据 |
| 不要记住这段内容 | 不建立被禁止的持久副本／派生画像；读取许可不自动包含持久化许可 |
| 停止返回既有记录 | 逻辑隐藏／tombstone 及有关依赖阻断；当前 Note 历史仍保留 |
| 清除已有内容 | 主存、历史、派生物和备份范围另作 Product 清除合同；当前未实现全面物理清除，纯 MCP 不保证抹除外部 Host 已接收副本 |

清除设计还需覆盖再导入、缓存重建、操作回执和日志重新暴露；不能一概把内容散列视为无敏感性。允许的合成数据原型可先行，但真实个人数据承诺必须有对应合同与工程支持；现有权限及明示不保存要求始终适用。

**自我强化：**相同来源的摘要、引用和再次阅读不构成新证据；用户在有限选项中选择也不自动支持普遍偏好。

**版本漂移：**后续检索与派生物精确关联版本；当前视图不是唯一真相，冲突可保留。

**反馈稀疏：**没有反馈时使用固定策略；反馈类型分开。不把服务成功当任务成功，不把 Host 自判当用户选择。

**依赖过重：**首版无生成模型的服务快路径；仅一个 Host 参考适配器。需要语义提炼时让 Host 使用已有调用位置，并报告成本。

**前瞻扩展：**接口允许后续增加局部证据关系、轻量效用重排、更丰富场景和多模态来源。但这些不是当前必须实施的子系统。只有真实失败指向具体缺口时，才扩展相应能力。

## 18. 交付边界与实施起点

本计划的实施起点是 W0/EN1：锁定 Product 公共对象、身份、意图与引用合同；随后 W1/EN2 补齐 launcher 的可选目录接线，以 compact v1 为既有基线，逐步加入 EN3 可信来源、W2/W3a 局部政策与单 Note 更正。同步准备 v1/v2 分组与字段白名单。EN4 的必要产品能力和 W5 独立评价按各自前提推进，不等待首题获胜才安排迁移。

本次按“生成修改计划写入”的要求，仅修订本文为内容 v1.2；两份既有评审保留历史版本。没有修改实现、公开合同、Schema/API/权限/Canonical 行为，未安装实验依赖、调用 solver／Judge／embedding、恢复旧批次或改变服务。本轮仅核查文档差异、引用与一致性。前轮 Evidence／Note 评审的 16 项 compact 测试属于既有接口核查，未在本轮重跑，也不证明拟议目录、可信句柄或新方法已实现。无迁移、部署或数据库回滚需求；产品继续保持 EXPERIMENTAL / CANDIDATE / NO-GO FOR SCHEMA FREEZE。
