# MiLAi v0.2-04：先降低单次使用成本，再考虑记忆确认

## 1. 本次修订的决定

用户指出单次使用及实验总消耗过高。因此撤回 v0.1 的“先追加 100 万 token 补四次 N5，再考虑 200 万 token 使用 pilot”优先安排。这些额度从未获执行授权，也没有写入实验配置。

现在先回答：完成一个普通续做任务究竟需要多少成本，哪些是可避免的环境失败、重复读取和上下文开销。已有 10% 相对节省门槛不足以证明可用性；若整个任务仍要十万级累计 token，就不能仅凭比 A0 便宜一些继续扩大实验。

## 2. 已知成本：保存很便宜，整个任务仍然很贵

以下是 [原机器总账](../../../MiLAi-Lab/studies/active/MILA_V02_PAYLOAD_FIDELITY_RESULTS.json) 的历史结果，不是新实验：

| 对象 | 已观察成本 | 应如何理解 |
|---|---|---|
| 4 次普通笔记 G | 平均 245,706 tokens / 123.58 秒 | 这是普通任务与笔记生成的共同成本，不是免费准备 |
| 6 次 F：完整 A0 + 文件 | 平均 132,394 tokens / 60.92 秒 | 基线本身开销也很高 |
| 6 次 S：相同文件 + 保存的笔记 | 平均 104,178 tokens / 55.71 秒 | 已有局部相对收益，绝对成本仍不适合直接作为轻量记忆流程推广 |
| 原样保存动作 | 0 模型 tokens，约 0.086–0.238 秒 | 保存接口本身不是此次模型消耗主体 |

这里的 token 是一整个 Host 任务的累计 input+output，不是一次 MiLAi 保存/查询调用的费用，也不是单个请求的上下文长度。此前 100 万是整批建议额度，不是一次调用，但这不改变单次任务仍然昂贵的事实。

17 次分配、16 次实际模型会话累计 2,402,257 tokens，其中 input 2,382,863、output 19,394；cached input 1,965,056，约占 input 的 82.47%，非缓存 input 为 417,807。缓存是 input 子集，不能重复计数，也不能把所有 raw tokens 按同一个价格解释。没有实际计费单价与账单，本轮不推算金额或断言“费用下降了某个百分比”。

## 3. 历史日志已发现的具体浪费

对 12 次已完成续做做只读复核：

- 共 24 次非零退出工具调用：12 次 `python` 不存在、11 次 `python3` 不存在、1 次 `jq` 不存在。Agent 为读取已有 JSON 历史付出了额外失败与改写命令的步骤。
- 一次 advisor_email/F 中，相同的 540,357 字节历史输出出现两遍；其他续做也出现数万至数十万字节的历史输出。
- 整体约 99.19% raw tokens 是 input。应优先检查固定输入、历史/工具输出与多步执行中的上下文复用，而不是只减少最后几百字答案。

这些能证明工具环境与读取链路存在可修复问题，但不能直接证明它们各占多少计费 token：逐请求模型输入未观察，工具日志也可能在送入模型前被截断。不能将日志字节当模型输入，或把有缓存直接等同于浪费。修复后的实际节省仍待验证。

## 4. 调整后的开发顺序

| 优先级 | 工作 | 新实验模型调用 | 出口 |
|---|---|---:|---|
| C0：只读成本审计 | 复核已有 usage、失败类型、重复输出、固定配置与产物大小；列出可测与未知项 | 0 | 完成：历史用量重算一致，固定组件按字节记录，逐请求输入及金额仍未知 |
| C1：最小环境与读取修复 | 先让受支持的通用 JSON/文本读取命令在隔离环境中真实可用；必要时提供有界、可续读的通用历史读取方式 | 0 | 完成：Python/python3/jq与通用分页读取器，22项相邻测试、12容器/24命令重放通过 |
| C2：单次绝对成本审查 | 核验固定输入和控制能力，先确定可承受的单任务 token/时延/实际费用上限 | 0 | 审查完成：提出20k tokens/30秒待验证目标；硬控及金额未核验，付费NO-GO，另列轻宿主独立方案 |
| C3：最多一个新配对 | 若获授权，同一现有任务在修复后的相同环境中 F/S 各一次；不重做 G，不加 reviewer、备用样本或自动重试 | 条件安排 2 次，当前未授权 | 只判断低成本路径能否正常工作，不作 N5 确认或泛化结论 |

C0/C1 先以一个小工程增量交付，建议 0.5–1 个工作日内给出可复核的改动或阻塞；不为了成本审计再搭大平台。这里的“0 模型调用”指不新增实验 Host/Provider 会话，不宣称执行者本身的开发劳动或本次对话免费。

## 5. 成本控制与公平比较

优先级调整为：任务正确与权限安全 → 单次绝对成本可接受 → 相对净收益。保留 A0 是当前默认决策，不表示当前重型实验 Host 的费用已经可接受。

先以“普通续做从十万级降到万级累计 token”作为方向；可将每任务不超过 20,000 raw input+output tokens 作为首个待验证工程目标，而不是已实现指标或自动授予的预算。最终费用/时延上限在 C2 明确；达不到时先停，不机械追加额度。

当前 runner 的累计启动闸门、300 秒 watchdog 和 120k 提醒都不是请求级 token 硬封顶。新试跑前必须说明实际可用的控制方式、在途超额风险和允许上限；控制不可核验或固定开销已超目标，就不启动付费试跑，先提出更轻运行路径的独立方案。

修复需作用于新比较的两臂：完整来源、普通文件、原有查源/保存能力均保留。不得删 F 的文件、隐藏历史、强迫只读笔记，或由离线 gold 指定运行时检索片段。有界读取必须保留完整材料的继续读取路径，内容不足时如实报告，不靠少答或读不到信息达成低成本。

换模型、推理设置、Host 或上下文装配方式属于新条件，必须建立同条件的新基线，不能接进旧 N5 确认结果；本轮未进行任何此类运行变更。
