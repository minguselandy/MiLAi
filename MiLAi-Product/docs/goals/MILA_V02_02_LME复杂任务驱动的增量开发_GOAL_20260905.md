# MiLAi v0.2 后续 Goal：LME 复杂任务驱动的增量开发

## 1. 本轮要交付什么

保留已可用的完整 A0，用 LongMemEval（LME）的长历史与复杂问题暴露真实瓶颈，每次只修一个影响可用性的环节，并验证修复是否值得保留。主线仍是“当前任务取证 → 正确理解 → 必要时保存 → 后续复用”，不是另起一个检索平台或自动维护框架。

用户已明确允许使用 LME case 进行实验。本 Goal 已按条件出口完成，见[Lab执行与终态记录](../../../MiLAi-Lab/studies/active/MILA_V02_LME_INCREMENTAL.md)：14次分配均有终态，来源会话ID泄露的失败及修复保留；L1未确证值得进入B1的问答缺陷，L2/L3不进入。独立导入优化在三组完整484事件中将串行准备约165秒降至4–5秒，捕获/投影/公开返回核对一致。L4两次真实更新、四组U/V的8次后续均正确，但计入生成后两条历史均未回本。保留完整A0与Lab导入提速，不启用自动维护。Lab133项测试及全部gates通过；仅停止本轮自建服务、数据保留。没有Formal500正式评分、Product代码变更或公网部署。下文保留原开发安排、预算和门槛，不将未进入阶段追认为已运行。

本轮交付分三层，不要求同时成立：

1. 工程可用：复杂历史可导入、任务可运行、失败可定位、成本有记录，现有 A0 不退化。
2. 当前任务收益：一个小改动在完整 A0 对照下改善答题/任务进展或降低实际使用成本。
3. 延续收益：一次真实保存，计入生成和保存成本后，在不同后续任务中仍有净价值。

自动维护只有在第 3 层出现证据后才进入后续候选；“写入成功”“续做成功”“多找到几个片段”分别报告，不能互相替代。

## 3. 开发优先级

| 优先级 | 做什么 | 暂不做什么 |
|---|---|---|
| P0：可复跑与低成本诊断 | 复用现有 Host runner，接入已开放的 LME source-only 包；补分阶段耗时与失败定位 | 新实验平台、全量可观测性系统、重建已经修好的启动依赖 |
| P1：一个影响任务的证据缺口 | 根据当前 trace，选取证、准入/呈现或解释中的一个瓶颈做小修复 | 同时改查询、召回、提示、State 表示，导致无法判断哪一项有效 |
| P2：保存是否回本 | 两条复杂历史、真实更新前后、每条两个不同后续任务 | 每轮自动保存、常驻 reviewer、统一事件消费/记忆重建循环 |
| P3：普通任务中的接入 | 仅把通过验证的改动保留为局部或可选能力；观察真实任务文件与 State 的分工 | 用构造 LME 续问直接宣称生产可靠性或自然维护已解决 |

capture 性能是一条可以独立交付的工程小增量，不必等待语义候选胜出。先复用长连接/现有捕获入口和就绪等待；只有测量显示 Product 路径需要改动时才动 Product。不为测试速度新增批量写 API 或绕过公开捕获、权限和投影合同。

## 4. 增量安排与出口

| 阶段 | 开发交付 | 随开发完成的验证 | 下一步条件 |
|---|---|---|---|
| L0：接好复杂任务 | 新研究专用 pin；source-only LME 适配；完整 A0；分阶段耗时与原始回执 | 非模型边界/装配检查，最多 2 次 Host smoke | 身份、来源隔离、工具能力和结果可核对 |
| L1：定位首个瓶颈 | 复用已有 LME trace，生成“来源 → 候选 → 返回片段 → 外显判断”的逐例记录 | 用公开接口重放已知查询；必要时 1–2 次受控诊断，明确非效果证据 | 有可复现的一般性失败；否则保留 A0，交付诊断与工程改进 |
| L2：一个小修复 | 只改一个主要行为；补邻近测试与正确控制 | 6 对开发比较：4 个复杂案例、2 个普通查找控制 | 按 Lab 预定规则判断任务收益、损坏与成本；无增益停止该候选 |
| L3：冻结后开发复核 | 冻结候选、预算、数据交付方式与评分口径 | 另 6 对未参与本轮调参的 opened-development 案例 | 通过才保留有限适用范围；失败不回头调该批样本 |
| L4：保存净价值探针 | 复用公开 Working State 更新与真实恢复，保留任务文件 | 2 条复杂历史 × 2 个不同后续任务 × U/V；另计更新生成成本 | 只有有来源的真实更新才进入；无机会则记 NOT_EVALUABLE，不强造收益 |

建议工程投入：L0–L1 约 0.5–1 个开发日，L2 约 0.5–1 日，L3 约 0.5 日，L4 约 0.5–1 日。它们是小增量估算，不是连续执行承诺；依赖、模型等待和真实任务间隔另记。首轮先做 L0–L2，不一次启动所有阶段。

L4 不以 L2/L3 候选获胜为必要条件：完整 A0 如果已产生有复用机会的真实更新，也可按独立预算做保存价值探针。当前取证改善与保存收益是两个可分别失败的问题。两条都没有收益时允许完整收尾，不用“必须正向”驱动扩大实验。

### 4.1 L1 怎样决定 L2 改哪里

| 最先确认的失败 | 最小开发方向 | 验证时必须保留的区别 |
|---|---|---|
| 合法材料没有进入候选 | 测普通查询改写/现有取证通道能否找回；有稳定缺陷再修实现 | 更换查询是新取证，不是沿旧 context 翻页 |
| 候选已有、公开片段缺失 | 检查预算截断、证据身份、准入/呈现及已有续取路径；做无静默丢失的小修复 | 返回新 ID 不等于返回必要片段；不能牺牲原本有用内容换分 |
| 返回材料完整、回答仍错 | 用同证据包受控重放定位时间、去重、来源归属或聚合问题 | 后续实际模型输入若不可观测，不能断言模型确实看到了全部证据 |
| 答案正确但准备/反复查源过慢 | 分开修 capture、重复装配或可测的重复开销 | 合理的当前来源核对不是无效重复；离线导入提速不是模型推理收益 |
| 当前正确、下次重犯且新 State 未保存 | 先做 L4 更新前后对照 | 不直接跳到自动保存策略；文件延续的贡献单列 |

L1 分类留在 Lab，不新增运行时错误 enum，不将案例 ID、答案词、gold turn 或离线失败标签编入 Product。

### 4.2 第一批可执行工作单

1. 核验当前 manifest 与安装路径，创建新研究 pin/config；历史锁和前轮结果原样保留。
2. 从已开放案例建立白名单 source-only 小包，执行容器不接触答案、评分标签或整份 corpus。
3. 将它接到现有完整 Host runner；导出实际 bootstrap、可用工具目录、来源方式和预算。
4. 对一个复杂案例和一个普通控制做 smoke；用现有 trace/公开查询诊断首个可修复缺口。
5. 有依据才实现一个小修复；先跑定向测试，再按预定两对一批完成 L2。
6. 输出“修复/未修复的瓶颈、有效比较、失败分配、质量与成本、下一阶段进入与否”，再决定是否开启 L3/L4。

## 5. LME 的具体用法

详细案例、分组、评价与预算合同归 Lab：[MILA-V02-02 实验规划](../../../MiLAi-Lab/studies/active/MILA_V02_LME_INCREMENTAL_PLAN.md)。本 Product Goal 只保留开发决策接口。

- 复杂案例优先覆盖跨会话集合/计数、多证据组合、时间关系、知识更新；长历史和干扰材料保留，不只导入答案附近片段。类别不足就报告缺口，不从 Formal 临时补样。
- 普通用户/助手历史查找作为低开销控制；证据不足时合理弃答与有足够依据却未完成任务分别评价。
- 原生 LME 问答检验当前取证与回答；从其历史衍生的多轮任务单列为 `LME_DERIVED_CONTINUATION`，检验恢复与复用，不冒充原生 LME 成绩。
- 用同一问题反复询问最多证明答案缓存效果。L4 的两个后续任务必须不同，且在更新生成前固定、不提供给更新生成器。
- 端到端主对照保留 A0 原有文件/搜索、完整 MCP、预读和保存能力；默认两臂均能读取该 case 的同一份合法历史文件。历史只经 MiLAi 可读的配置只能作为另列的受限检索诊断。
- 已开放案例不是严格盲留出。L3 只能称“冻结后的开发复核”，记录历史暴露；Formal 500 不正式评分，不能宣称从未访问过其底层源文件。

## 6. 预算与停止规则

| 增量 | 模型启动次数上限 | 组成 |
|---|---:|---|
| 第一轮 L0–L2 | 16 | 最多 2 次 smoke + 6 对比较的 12 次 + 最多 2 次诊断/失败重试 |
| 第二轮 L3 | 12 | 6 对冻结后复核；只在候选通过开发门槛后开启 |
| 第三轮 L4 | 12 | 最多 2 次更新生成 + 8 次 U/V 重访 + 最多 2 次失败诊断/重试 |

40 次是三个增量均进入时的最大分配数，不是必须跑满的样本指标。失败、偏离、显式更新生成和受控诊断均占预算；复用已有合格结果不重复计数。第二轮没有隐含重试额度；工程失败允许修复，但不足的配对明确报告，不用偷偷追加运行补齐。

默认每次模型会话 300 秒、24 次工具动作 watchdog，每批最多 4 次/1,200 秒在线预算；case 初次 capture/readiness 单独设置最多 300 秒并记录，失败停止该 case。capture 并发只使用已确认可承受的容量，不同时堆叠多个历史导入。预算值需在第一批执行前落入配置并验证实际 watchdog。

120k rollout tracking 继续只当软提醒，不宣称原始 token 硬上限已实现。报告所有可得 input/output token、cache 子集、墙钟及未知量；如任务规模确需更高预算，在受影响的新批次分配前记录原因并对两臂一致调整，已超时结果保留。不得因一侧失败临时给它单独加轮次或换 seed。

出现越权/标签泄露/静默覆盖/错误来源采信立即停该候选；普通工程故障修一般原因后保留旧失败。在已覆盖目标瓶颈的连续两批中没有可解释的改善或关键证据增量，不继续扩散候选。超过本 Goal 总预算、开启 Formal、改变公网或扩大数据库/权限语义，均不是本文默认许可。

## 8. 验收、交付与后续边界

工程验收先运行定向测试，再按改动包运行 Ruff、mypy（如配置）、pytest、build。Lab 改动还需 boundary 检查；涉及捕获、投影、CAS、scope、撤销或并发行为时补真实 PostgreSQL 测试。历史 123/160 的通过数不能抵本轮验证。

交付至少包含：实际改动与不变量影响、pin 与运行身份、各批次终态、逐例质量/成本、更新前后与后续记录、已运行/未运行检查、适用范围、回退方式。只停止本 Goal 创建且身份核对过的服务，保留既有与本轮数据；任何删除需要单独明确范围。

可接受终态：

- `COMPLETED_KEEP_BASELINE`：工程/诊断交付完成，未证明候选净收益，继续使用 A0。
- `COMPLETED_KEEP_SCOPED_IMPROVEMENT`：通过开发与冻结后复核，只保留已证实范围的小改动；不自动启用记忆维护。
- `PARTIAL_EVIDENCE_INSUFFICIENT`：可用性改进已交付，但有效配对、合法来源、标签或预算不足；逐项列出未完成内容，不把不足伪装成负面或正面结论。

只有 L4 显示保存净收益，下一份 Goal 才考虑一个可选的普通任务边界接入，并先与简短任务笔记等更简单方式比较。若是显式 checkpoint 产生的收益，仍按条件能力报告；自然触发与误触发开销需要独立验证。真实用户任务作为后续外部可用性检查，不能靠改写 LME 问题替代。

继续保持：A0 默认；D2 SHADOW；Product-11 已封存结论不变；不新增训练、Dense/图存储、持久 Basis 或自动循环；公网不变；`Schema 0.1.x EXPERIMENTAL / NO-GO FOR SCHEMA FREEZE`；创新性与自动维护收益仍待证。
