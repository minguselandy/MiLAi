# MiLAi Host Cognitive Affordance Layer 设计开发规划

## 0. 文档目的

本文规划 MiLAi 下一阶段的一条独立架构路线：

> 将此前设计中尚未真正实现、且高度依赖语义理解与模型推理的 State / Planner / Memory Intention 能力，以 **Codex 可见、可持久、可自行维护的 Host Cognitive Affordance** 形式开放，而不是继续在 MiLA Runtime 内部实现大量生成式状态机或隐藏 Reader。

核心目标不是“伪装这些能力已经由 MiLA 实现”，而是明确提供：

```text
MiLA 提供：
  state container
  persistence
  versioning
  scope
  evidence reference validation
  lifecycle
  MCP affordance

Codex 提供：
  semantic interpretation
  task understanding
  requirement decomposition
  hypothesis / decision / blocker management
  memory need planning
  residual query generation
  sufficiency judgment
  state maintenance
```

必须长期保持：

```text
Host Cognitive State != Canonical State
Host Cognitive State != Evidence
Host Cognitive State != RetrievalContinuationState
Host Cognitive State != authority source
```

本规划不替代 Product-11。Product-11 继续解决 deterministic retrieval 机制：Explicit Evidence Acquisition 与 Non-Destructive Continuation；本规划解决的是 **Host 语义认知状态的可用性与持久化**。

# 1. 背景与问题

## 1.1 当前已经成立的产品边界

当前 Codex 产品主链已经收敛为：

```text
User
  ↓
Codex
  ├─ semantic reasoning
  ├─ tool loop
  ├─ shell / file / calculator
  └─ final answer
       │
       │ Streamable HTTP MCP
       ▼
MiLA MCP
       │
       ▼
MiLA Runtime
  ├─ PostgreSQL persistence
  ├─ Evidence
  ├─ Canonical State
  ├─ FTS / Dense retrieval
  ├─ authority / scope / time
  └─ governance
```

正常 Codex 读路径已经冻结以下原则：

```text
internal Reader calls                = 0
vLLM calls                           = 0
EvidenceLedger                       = 0
automatic semantic retry             = 0
recall-side Canonical mutation       = 0
semantic COMPLETE inside MiLA        = 0
final answer generated by MiLA       = 0
```

Codex 负责“是否充分、是否继续查、如何回答”；MiLA 负责“哪些 Evidence 当前合法、可见、未撤销、属于哪个 scope / snapshot”。

## 1.2 仍未实现但曾设计过的大量语义 State

此前 MiLA 架构设计中出现过：

```text
TaskState
TaskRelation
ActiveGoal
CurrentQuestion
RequirementState
MissingRequirement
NeedState
OpenIssue working representation
HypothesisState
DecisionState
FailureState
BlockerState
MemoryPlan
MemoryIntention
ResidualCue
ReFind planner
Sufficiency / COMPLETE
NextAction
CompletionCondition
Context focus / keep / avoid-repeat
```

这些能力如果全部变成 Runtime 原生状态机，会引入：

```text
LLM classifier
semantic extraction
state transition policy
schema proliferation
conflict resolution
hidden model dependency
runtime latency
state drift
hard-to-audit semantic correctness
```

而 Codex 本身已经具备强大的：

```text
task decomposition
working-memory abstraction
planning
hypothesis formation
error diagnosis
requirement tracking
semantic query rewriting
self-reflection
```

因此新的设计原则是：

> 对需要确定性与治理证明的状态，继续由 MiLA Runtime 原生实现；对强语义、强推理、Host 本身已经擅长的状态，先暴露为 Codex 可自行维护的 persistent cognitive affordance。

# 2. 目标架构

## 2.1 四层 State 架构

```text
L0 Evidence
   “真实观察到了什么”
        │
        ▼
L1 Canonical State
   “MiLA 经过治理后当前接受什么”
        │
        ▼
L2 Host Cognitive State
   “Codex 当前如何理解任务、还缺什么、下一步是什么”
        │
        ▼
L3 Context
   “当前推理窗口真正暴露给 Codex 什么”
```

对应 ownership：

| Layer | Owner | Authority | Typical content |
|---|---|---|---|
| Evidence | MiLA | source/provenance | user turn, assistant turn, tool result, test, file change |
| Canonical State | MiLA | governed | ClaimVersion, currentness, profile projection |
| Host Cognitive State | Codex | `HOST_WORKING` | goal, requirements, hypotheses, decisions, memory needs |
| Context | MiLA renderer + Codex | none | current retrieved evidence / visible state |

## 2.2 与 RetrievalContinuationState 的严格分离

Product-11 规划的：

```text
RetrievalContinuationState
  seen evidence IDs
  seen rendered turn IDs
  frontier candidates
  route cursors
  snapshot
  budget history
```

是 Runtime-owned mechanical state。

本规划的：

```text
HostCognitiveState
  goal
  requirements
  known
  missing
  hypothesis
  decisions
  blockers
  memory needs
  next actions
```

是 Codex-owned semantic state。

禁止：

```text
RetrievalContinuationState.payload ← semantic task state
HostCognitiveState ← canonical truth
HostCognitiveState ← route cursor / frontier truth
```

## 3.2 不能 Host 化的 Runtime 原生能力

以下能力仍必须由 MiLA 确定性实现：

```text
Evidence identity
Evidence provenance
ClaimVersion identity
Canonical currentness
valid time / observed time
scope / tenant / project / principal
permission / authority
retention / revocation
RLS
snapshot
canonical position
exact identity hard dedup

route cursor
frontier exhaustion proof
proposal optimistic locking

```

原则：

> Codex 可以提出解释、计划、需要、偏好；但不能自证 authority、currentness、permission、revocation、frontier exhaustion 或 canonical truth。

# 4. HostCognitiveState 设计

## 4.1 最小领域对象

建议新增一个通用对象，不为每个 State 单独建表：

```yaml
HostCognitiveState:
  state_id: opaque UUID
  root_state_id: UUID
  predecessor_state_id: UUID | null
  version: integer

  tenant_id:
  principal_binding_digest:
  project_id:
  scope_type: SESSION | TASK | PROJECT
  scope_ref:

  authority: HOST_WORKING
  schema_name: codex-cognitive-state-v1
  payload_json: {}

  created_at:
  updated_at:
  expires_at:
  state_digest:
```

## 4.2 推荐 payload 模板

```yaml
task:
  active_goal:
  current_question:
  relation_to_previous:
  phase:
  completion_conditions: []

requirements: []
known: []
missing: []
hypotheses: []
decisions: []
failed_approaches: []
open_issues: []
blockers: []
memory_needs: []
memory_intentions: []
next_actions: []
context_preferences: {}
```

这只是 Host-facing recommended shape，不是 Runtime semantic schema。

Codex 允许增加：

```text
files_touched
tests_pending
constraints
owners
milestones
references
experiment_notes
```

MiLA 不理解未知字段，只保存、版本化和校验安全边界。

## 4.3 可选 Evidence 引用

Host entry 可以引用 Evidence：

```yaml
known:
  - id: K1
    text: "Product-10 regression primarily came from budget displacement"
    basis:
      - evidence_id: E201
      - evidence_id: E207
    basis_relation: HOST_ASSERTED
```

Runtime 保存时只验证：

```text
Evidence exists
same tenant / project / scope
not revoked at validation time
identity valid
```

Runtime 不判断：

```text
Evidence 是否在语义上 entail 该结论
```

因此必须标记：

```text
basis_relation = HOST_ASSERTED
```

不能叫：

```text
VERIFIED_GROUNDING
```

# 5. 生命周期与版本模型

## 5.1 Append-only semantic working state

HostCognitiveState 建议也采用版本链：

```text
WS/V1
  ↓
WS/V2
  ↓
WS/V3
```

不用 ClaimVersion 那么复杂，但避免 silent in-place overwrite。

价值：

```text
追踪 Codex 任务理解如何变化
定位错误 hypothesis 何时形成
观察 decision 如何收敛
研究哪些 affordance 真正被使用
```

## 5.2 CAS

更新要求：

```text
expected_version == current_version
```

否则：

```text
STALE_WORKING_STATE
```

第一版不实现复杂 merge。

## 5.3 Scope

支持：

```text
SESSION
TASK
PROJECT
```

建议默认：

```text
SESSION TTL: hours
TASK TTL: days / configurable
PROJECT TTL: long-lived, still HOST_WORKING
```

## 5.4 删除与失效

HostCognitiveState 不是 Canonical，所以可以有更简单 lifecycle：

```text
ACTIVE
ARCHIVED
EXPIRED
DELETED
```

但其 Evidence reference 如果随后被 revoke：

```text
state payload 不自动重写语义
reference metadata 标记 stale/unreadable
下一次 get 返回 warning
Codex 自行决定如何更新 working state
```

禁止 recall 自动改写 Host state。

# 7. Codex 诱导协议

## 7.1 MCP Server Instructions

冻结为最小 affordance 提示：

```text
You have persistent HOST_WORKING state.

Use it when useful to preserve your working understanding across
non-trivial tasks and sessions.

It may contain goals, known information, unresolved requirements,
decisions, failed approaches, blockers, and next actions.

It is non-canonical.
```

MCP 的通用 mutation / untrusted-memory 安全指令仍保留，但 working-state affordance 本身
不强制每轮 GET/UPDATE、不规定必填字段、不强制 Evidence refs。HC-4 测量的是
affordance usefulness，不是 prompt compliance。

## 7.2 使用策略

不要求 Codex 每轮读或写 State。下列仅作产品设计背景，不注入 HC-4 Host prompt：

```text
任务开始 / 恢复          → get
重大目标变化              → update
关键 decision             → update
关键 failure / blocker    → update
memory need 变化          → update
任务完成                  → final update / archive
普通小步骤                 → 不更新
```

# 9. 真实工作流示例

## 9.1 跨 Session 恢复任务

用户：

```text
“继续 Product-11。”
```

Codex：

```text
1. milai_working_state_get(TASK)
2. 读取：
   active_goal
   current_question
   missing
   next_actions
3. 必要时 milai_memory_resolve(...) 获取真实历史 Evidence
4. 开始修改代码 / 测试
5. 重大进展后 milai_working_state_update(...)
```

示例 working state：

```yaml
task:
  active_goal: "prove persisted-frontier continuation"
  current_question: "can Call 2 resume the exact previous frontier without reacquisition?"

known:
  - "Product-10 failure includes budget displacement"

missing:
  - "persisted-frontier continuation proof"

next_actions:
  - "implement RetrievalContinuationState repository"
  - "add operation fingerprint idempotency"
```

## 9.2 Memory Need / ReFind

Working State：

```yaml
memory_needs:
  - id: M2
    need: "find why approach B was abandoned"
    status: OPEN
```

Codex：

```text
milai_memory_resolve("Why was approach B abandoned?")
```

得到 Evidence 后：

```yaml
memory_needs:
  - id: M2
    status: RESOLVED
    evidence_refs: [E31, E44]
```

若不够：

```text
Codex 自己形成 residual query
→ milai_memory_resolve(previous_context_id=...)
```

这实现：

```text
semantic ReFind planner = Codex
mechanical continuation = MiLA
```

## 9.3 Working Decision 升格为 Canonical

Codex Working State：

```yaml
decisions:
  - "Use operation fingerprint instead of MCP request ID"
```

这仍是 `HOST_WORKING`。

若用户明确确认该决定，并需要长期项目事实：

```text
Evidence capture
  ↓
Proposal CREATE/SUPERSEDE
  ↓
Review APPROVE
  ↓
ClaimVersion
```

绝不能：

```text
working_state_update
→ automatic canonical write
```

# 10. 安全与正确性不变量

必须长期保持：

```text
I1  HostCognitiveState authority == HOST_WORKING
I2  HostCognitiveState cannot directly create/update ClaimVersion
I3  HostCognitiveState cannot raise authority
I4  scope/tenant/project not model-controlled
I5  Evidence refs validated by exact identity only
I6  Host-asserted semantic linkage != verified grounding
I7  recall does not mutate HostCognitiveState
I8  recall does not mutate Canonical State
I9  revoked Evidence cannot remain presented as currently valid grounding
I10 RetrievalContinuationState is independent from HostCognitiveState
I11 Codex cannot assert FRONTIER_EXHAUSTED as Runtime fact
I12 mutation still follows Evidence / Proposal / Review / Revoke semantics
```

```text

repository

```


## Phase HC-2 — HTTP MCP Tools

实现：

```text

```

```text
single 7337 Streamable HTTP MCP

```

测试：

```text
tool catalog exact
HTTP auth
input schema
CAS error mapping
cross-scope denial
state version roundtrip
```

## Phase HC-3 — Codex Affordance Instructions

只使用简短 instruction，不写大型 planner prompt。

验证 Codex 是否自然使用：

```text
active_goal
requirements
memory_needs
decisions
next_actions
```

不得加入 case-specific 提示。

## Phase HC-4 — Real Coding Usability

执行结果（2026-09-04）：A0 passive 为 0/8；A1 bounded guidance 为 0/4。共 12 个真实
fresh-Codex task、3 条 chain，但没有 ACTIVE State，所以 continuation/usefulness 分母仍为 0。
这证明 persistence substrate 可用不等于 Codex policy 会主动采用。当前 HC-4 不再增强 prompt；
若研究 session-start prefetch / session-end update，必须另开 Host-managed Goal，并放弃
`Codex self-maintained cognition` claim。

冻结合同：

```text
4 条连续 coding chain，每条 3～5 个真实新 Session
target 16 session-tasks；minimum 10 tasks / 3 chains / 6 continuation sessions
minimal affordance instruction；不强制 GET/UPDATE、字段或 Evidence refs
Runtime/schema/State-type changes = 0
```

至少测试：

```text
multi-session task continuation
failed approach recovery
cross-session decision recovery
memory need + residual search
state stale/CAS conflict
working state correction
working decision -> governed canonical promotion
```

建议 10-20 个连续 coding tasks，而不是纯 QA benchmark。

# 13. 成熟度模型

以后所有新 State 先走“Host affordance → Runtime primitive”的升级路径：

```text
Stage 0  Concept only
Stage 1  Prompt / affordance only
Stage 2  Persisted Host Cognitive State
Stage 3  Hybrid: Host proposes, Runtime deterministically validates part of it
Stage 4  Native MiLA Runtime primitive
```

例子：

```text
ActiveGoal
  Stage 2

RequirementState
  Stage 2 initially

MemoryIntention
  Stage 1/2

TaskRelation
  Stage 2

RetrievalContinuationState
  Stage 4

Canonical ClaimVersion
  Stage 4

Scope / permission / revocation
  Stage 4
```

只有真实使用证据证明某个 State：

```text
高频
稳定
对成功有显著贡献
Host 自维护错误率高
值得确定性化
```

才升级成 Runtime primitive。

# 14. 不做什么

本阶段不做：

```text
不恢复隐藏 Reader
不使用 vLLM 做 state extraction
不实现 RequirementState 专用 Runtime 状态机
```

# 18. 最终设计原则

MiLAi 以后不应默认：

```text
“想到一个认知 State，就必须在 Runtime 中实现一个新算法。”
```

而应采用：

```text
先暴露认知 affordance
  ↓
让 Codex 在真实任务中自行使用
  ↓
持久化其 Host Working State
  ↓
观察使用频率、稳定性、收益与错误模式
  ↓
只有值得系统化的 State
再升格为 MiLA Runtime primitive
```

最终形成：

```text
MiLA
  = Evidence / Canonical / Retrieval / Governance / Persistence

Codex
  = Semantic cognition / Working State / Planning / Sufficiency / Residual Need
```

这条路线保留了 MiLA 的确定性和治理能力，同时最大化利用 Codex 已有的模型推理能力，避免重复构建隐藏 Reader、Planner 和大量脆弱的语义状态机。
