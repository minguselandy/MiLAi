# 2. 方法反思：为什么选择这条修复路线

## 2.1 不继续优化模型重复抄写确定性事实

【设计推断】当前系统让模型既做任务规划，又填写事实字段、JSON 正文、来源、scope 和修订动作，再用代码验证重抄是否正确。这增加了可出错的表达面，也可能增加付费重试；现有调用级 trace 尚须确定各类开销的实际占比。[R04,R06,R11]

更小的职责划分是：程序保留和投影它已经观察到的结果；模型决定什么语义值得记、属于哪个情境、应与哪条旧记忆关联。事实投影不是免费语义 writer，也不是替模型修答案：输出明确来自工具，而不是伪装成模型通过了字段测试。

## 2.2 可行方法的取舍

| 候选 | 可行性与代价 | 决定 |
|---|---|---|
| 继续加“必须查历史/必须改旧卡”的提示 | 成本低，但此前历史提示未让 Host 搜索；无法可靠解决记录身份 | 保留一个 Prompt-only 对照，停止连续堆叠 |
| 保留模型重抄，用更严格 schema 校验 | 有利于机械格式，仍有重复表达和语义消费问题 | 作为旧 Field-grounded 对照，不作新默认 |
| 增加 verifier/纠错 agent | 额外生成和新的判错器，可能掩盖首次错误 | 不采用 |
| 回执派生 + 一次有界交付 + 候选增量修订 | 复用现有 Store/journal，变量可拆，工具合同可迁移 | 推荐验证路线 |
| 大图、独立 Attention、RL writer | 当前断点不要求这些能力，增加调参和复现负担 | 暂缓 |

## 2.3 创新性边界

HiMem 已涉及 Episode/Note 与冲突再整合；Hindsight 已区分事实、经历与信念；EAL-Bench 已研究记忆错误传播和事件溯源。自动读取、日志投影、版本检查本身也不能冒称全新算法。[W01–W03,W04]

候选贡献应是一个受限命题：**源事件、语义记录身份与操作事实之间的关联，能否在固定预算下减少“错误记录—错误读取—错误行动”的跨会话传播，并比强简单回执系统保留更多正常任务效用。**

若强简单方法同样有效，应采用其实现、收缩论文主张。新颖性不以“必须保留某模块”为前提。

# 3. 最小架构：一个服务、同源视图、一个读入接口

## 3.1 结构

```text
真实 user / tool 事件
  → 既有 Source / Journal（保留角色、身份、原始字节或哈希）
  → 操作观察视图（确定性派生） + 语义记忆（模型增量 patch）
  → 同一个 MemoryService + 来源/版本关联索引
  → prepare_context：每用户回合一次有界证据交付
  → Host 自主推理与合法业务工具
  → 新实际事件 → 派生更新；必要时语义修订
```

这里的两个视图不是两套竞争性真相数据库。操作视图由实际来源重建，语义记忆保留独立断言性质；模型没有修改真实观察视图的工具。业务世界仍是业务世界，Memory 不是实时业务数据库的替代。

## 3.2 四项不变量

| 不变量 | 必须成立的内容 | 明确不保证 |
|---|---|---|
| 来源不放大 | 派生事实指向实际事件与字段；引用存在不等于语义正确 | 不证明第三方服务自身永不出错 |
| 身份不猜测 | 更新的是已发现的 record/object；相似检索只生成候选 | 不自动解决所有语义共指 |
| 时间不偷换 | 历史观察带当时版本/时间；现在状态需要合法发现 | 不把最后入库等同于业务最新 |
| 效果不重放 | 相同事件重放幂等；unknown 先查实际结果 | 不承诺任意外部系统 exactly-once |

## 3.3 最小接口草图

```text
observe(actual_event, adapter_contract) -> capture_receipt
prepare_context(public_request, owner_scope, budget) -> evidence_packet
revise(candidate_handle, semantic_patch, source_refs) -> revision_receipt
```

这些是职责草图，不是已存在的 CLI 或可直接调用 API。优先在现有 `MemoryService` 和 method hooks 中实现，不先搭新平台。`kind`、`scope`、`basis` 可沿用既有元数据；避免一次升级所有公共 schema。

# 4. 确定性操作观察：从“重抄再验证”改为“引用式派生”

## 4.1 通用、但不假装零领域知识

每个应用适配器只声明公开工具合同：对象身份路径、可投影字段路径、字段类型、可比较的业务版本、响应完整性及必要的效果语义。核心算法不得出现 benchmark 名、案例 ID、商品词、文稿标题或正确答案。

JSON Schema 只描述结构与类型，不能自行推出“failed 表示没有副作用”“approved 表示已经发布”。这些含义必须来自公开应用合同；缺少合同就保留原始观察，不生成肯定业务状态。

第一批复用 reservation 与 document 两个已有工作流。文稿的发布只表示 sandbox 持久化记录，不代表外部受众真正收到内容。[R10]

## 4.2 每条派生观察保留的最小信息

| 信息 | 产生者 | 用途 |
|---|---|---|
| source_event_id / source_hash | 可信捕获路径 | 溯源、去重与重放 |
| object_ref / owner | 真实 lookup 或实际回执适配器 | 身份与访问范围 |
| field_path / literal_value | 公开合同中的确定性读取 | 防止模型改写事实值 |
| resource_version / valid_time | 实际返回或可信应用元数据，允许未知 | 新旧观察比较 |
| observed_at | 真实捕获时间 | 只表示何时观察，不替代业务有效时间 |
| adapter_version / completeness | 公开适配器 | 重建、字段缺失与版本兼容 |

一个响应可以包含多个对象、多个字段。来源是证据，不是只能消费一次的令牌。去重粒度采用“事件＋对象＋字段＋投影版本”，允许同一事件支持多个不同事实和语义关联；同一事实重复处理不新增独立事件。

## 4.3 不再要求模型把事实值写两遍

工具成功返回后，事实视图直接由原回执生成并持久化；Host 可以写注释或计划，但注释独立标注 `unchecked` / `plan` / `inference`。不把注释混进受支持字段，不替换最终答案。

例如原回执是 `label_status=pending`，系统派生的可信字段仍为 pending。即使模型注释声称“全部完成”，也不得改变派生字段。该注释和最终回答仍需评分；不能因为结构化视图正确就把整次交互判为可靠。

普通偏好不需要业务回执。用户说“我偏好简短回答”，可记作用户表达的偏好；“订单已退款”若只来自用户消息，保存的是用户陈述，不升级为业务系统确认。

## 4.4 缺失、迟到与冲突

缺失字段不是 null、false 或 deleted；只在公开合同明确表示清除时生成清除事件。部分响应只更新已观察字段，不能以未返回字段覆盖既有事实。

优先按同一资源可比较的业务版本确定“最新观察”；不同来源或不可比较版本发生冲突时保留冲突，不按到达时间静默覆盖。历史版本继续可查询。只有客户端时间而没有业务版本时，界面应显示“最后观察于…”，不显示“当前事实已验证”。

Unknown 只记录结果未知，不能抹掉此前确认的历史事实，也不能假设它仍对当前动作有效。

## 4.5 幂等与可重建性

对于相同适配器版本，重复输入同一事件应得到相同派生事实集合。事件顺序有业务意义时不要求任意排列结果相同；仅对可比较版本的乱序到达检查不被旧事件回滚。

更换适配器版本时重建新视图并保留身份，不能把重建后的记录计作新业务执行。观察捕获、投影和索引提交的边界分别记录；投影失败时原事件可保留为 pending，但不能返回“记忆全部更新成功”。

# 5. 历史消费：一次有界证据交付，而不是强制工具调用

## 5.1 先做定位实验，再选择默认策略

在同一真实 bank、相同历史问题上比较：A 自主 search/read；B 每回合一次自动普通检索交付。使用同一 Host、工具、预算和源记录。先判材料是否送达，再判答案是否正确。

如果 B 仍错，继续检查材料和消费；不能立刻增加 selector。若 B 改善，结论是“交付策略有用”，不是“Memory 表示更优”。对所有记忆基线开放相同 B 策略，再比较方法差异。

自动检索是 harness/application 的可见读入行为，不伪造 Host tool call，也不使用 `required tool_choice`。

## 5.2 普通检索输入与证据包

查询仅使用当前公开用户消息，以及真实应用已经提供的 owner、会话和已发现对象引用。不给 future question、scorer、隐藏任务依赖、故障注入标签或标准计划。

继续复用 StrongRawRAG 的词法＋dense 检索与融合，不另造检索模型。权限硬过滤在检索与呈现前完成；模型推断的 scope 只作软信息和展示，未知 scope 不被一律排除。

证据包采用统一、轻量结构：相关历史观察、最后观察到的对象状态、有关语义卡、简短原始证据及来源/版本句柄。只带有相关依据的条目；没有材料时返回真实空结果，不强行塞入记忆。

## 5.3 预算与缓存

开发初值：每个用户回合一次预取；材料总预算 2,048 tokens，候选记录最多 6 条；可在开发集比较 1,024/2,048 两个预算。它们是初始配置，不是已测最优值。

同一回合的 ReAct 续接复用固定证据包；发生新观察或修订后，只刷新受影响条目。记录 bank_revision 和 packet_hash，不能拿缓存掩盖过时记忆。Host 主动追加查询仍可用并计费。

预算包括真实来源片段、元数据和字段视图，不只计算正文。省略必须可追踪，完整源留有按需读取入口。不能给 MiLAi 额外材料却让基线在同名预算内少看信息。

缓存节省检索计算，不等于模型输入 token 免费；重复进入实际 HTTP 的材料仍按真实 usage 统计。

## 5.4 防止证据回流污染

检索材料、系统提示、旧摘要、工作状态和已生成的证据包不是新的原始事件。禁止把它们再次摄入并提升为新的 user/tool 证据。真正助手建议仍可作为助手建议保存，不能冒充用户决定。

来源回链最多展开到真实叶子事件，避免摘要引用摘要形成循环。历史问题与当前问题都可以看到适量历史/最后观察信息；不靠“上次”“现在”等某种语言专属关键词硬编码正确分支。

# 6. 增量语义维护：让更新沿着已有记录身份发生

## 6.1 来源回链解决跨语言找卡

建立可重建的 `source_event_id → record_id / revision` 关联。原始中文源被检索到时，可直接发现引用它的英文记忆卡；该关联来自历史提交记录，不靠将中文业务 key 模糊改写成英文 key。

同时保留词法与现有多语言 embedding 的候选检索。密集检索暂不可用时退回真实原文与来源回链，并记录降级；不能宣称跨语言语义召回成功。

## 6.2 候选句柄与读取时版本

候选返回短句柄，其服务端绑定内容包括 owner、record_id、读取时 revision 与支持来源。模型可以选择句柄做更新，无需再次生成 UUID。

`expected_revision` 必须来自模型实际看到的候选版本。提交时发现新版本就返回冲突；不得临时取最新版本填入 expected_revision 来让检查通过。当前代码的自动填充是静态风险，需要用并发/交错测试确认修复效果。[R12]

相似度最高或候选恰好只有一条，不等于语义上必然应更新它。语义目标由模型在已交付候选中选择；程序只验证句柄、权限、版本和来源。

## 6.3 小 patch，而不是反复重建整张卡

复用现有 `manage_memory` 的 opt-in 分支或内部 patch 合同，支持 append、revise、明确 supersede、no_change。模型提出 content/scope/basis 的局部变更，程序保留未修改的元数据和历史。

普通语义卡允许人工语言表达，但保存用户陈述时必须能关联到实际 user 事件；选择多段来源时保留角色。精确引文/片段匹配只能证明文字存在，不能证明模型的概括、主体和适用范围正确，仍需独立语义评价。

找不到目标时不得把“更新失败”隐瞒为 CREATE 成功。可保存实际原始消息并返回“原内容已保留，关联修订未完成”；原卡继续可读。用户明确要新增无关联事项时正常 append，不为了更新率强行合并不同事实。

## 6.4 一次边界形成的职责与公平性

纯工具观察只做确定性投影，默认不调用语义 writer 重抄字段。语义内容需要维护时，复用现有 writer_policy，在一个冻结的已观察事件边界最多执行一次常规批量 patch；Host 已完成同一语义提交则不再重复写。

首批采用同步、可计费、可读回的边界操作，不增加常驻后台进程或纠错 agent。保留原自主写入作为对照；自动边界维护是单独策略，不能冒充原方法不变。

拒绝后不无限修复。相同错误指纹重复出现时不重复盲试；默认保存 pending；如预先启用修复，在既定总预算内额外最多一次显式新提案，常规维护与修复合计最多两次调用。此上限是可用性策略，要同时测正常修复被截断的比例。

## 6.5 Semantic/Episodic 的位置不变，但不加复杂度

保留可选 kind；semantic 支持修订/supersede，episodic 倾向保留历史。它们不是两套强制 Store，也不决定权限和真实性。

范围、主体、时间与断言性质比类别名更重要。继续保留 Flat/Type × 无Scope/有Scope 的小型对照；若类型无独立收益，默认以 Flat+Scope 实现使用能力，不改变 Grounded Agent Memory 主方向。

# 7. 恢复、资源生命周期与效率

## 7.1 按实际证据区分三个窗口

| 窗口 | 已知与未知 | 合法恢复 |
|---|---|---|
| W1：业务效果后、回执持久化前 | 效果可能存在，记忆不能假设成功或失败 | 调用公开 discovery；没有决定性结果就保留 unknown |
| W2：回执持久化后、投影提交前 | 真实源已在，事实视图可能缺失 | 重放同一事件的确定性投影，不重做业务 mutation |
| W3：记忆提交后、最终应答前 | 记忆已提交，回复未交付 | 读取既有提交回执，不重复更新或业务动作 |

若后端查询最终一致、查无对象不证明无副作用，不得据此马上重试。只有公开合同给出权威 no-effect 或幂等重试语义才允许重复 mutation。用户授权与当前前置条件仍由共同业务层负责。

原 v13.1 把部分 W3 故障限定为实际 UPDATE。新架构没有该 UPDATE 的路径应标 N/A，不能改称已经覆盖旧 W3。另定义“事实投影提交后故障”并单列新语义；跨方法按共同可到达边界比较。

## 7.2 Mem0 修复只改生命周期，不改算法

证据采集必须在底层 Store/Qdrant 关闭前完成，之后用独立 SDK 重开核对。采用明确的 context manager 关闭顺序，不吞掉 close/snapshot 错误。

保留 `observed_events_v1` 与旧载体身份；原始角色和 tool 结果不变，未闭合轨迹不标成 completed dialogue。修复后运行新的冻结 cohort，旧三条工程失败不改分、不补答。[R06,R10]

## 7.3 同一逻辑服务内的增量索引

优先加入 source→record、object→observation、operation/event→commit 的可重建索引。索引不是新的事实权威，丢失时从现有来源和提交历史重建；索引版本落后不得返回已验证更新成功。

当前代码的全记录/历史扫描是审查风险。先测调用次数、扫描记录量、p50/p95 与增长曲线，再决定是否优化。热路径优先只处理 dirty 事件、受影响记录和有界候选，不做全 bank 再序列化。

保持首批协作串行 SQLite 的能力范围。SQLite 的事务能力不自动保证上层 SDK 跨多次 put、两个数据库或外部业务效果原子；无公共事务 API 时，采用可检测 pending＋幂等重放，不绕过 SDK 私有连接制造未验证原子性。[W05]

## 7.4 效率目标，不承诺未测加速比

程序派生回执的新增 LLM 调用为 0；每用户回合自动预取最多一次；同一语义边界新增常规维护最多一次；启用一次显式修复时合计最多两次，修复单独计费。持续服务路径和刻意每步启动新进程的验收路径分别计时。

正式检验目标是：相同效用要求下，比旧 Field-grounded 减少维护/重试 token；相同预算下不显著降低 clean 完成率。与 Receipt-RAG+ 同样好且更贵时，不以“架构优雅”为理由保留复杂方法。

# 8. Baseline 与公平性：不能靠给自己更多能力获胜

## 8.1 四个主臂

| ID | 方法 | 必须提供的能力 | 作用 |
|---|---|---|---|
| B2+ | StrongRawRAG+ | 原始事件的词法+dense 检索、一次公共预取、真实角色与时间 | 通用强简单基线 |
| B6+ | Receipt-RAG+ | 与 MiLAi 相同的确定性事实投影；原文检索和简单语义摘要后备 | 直接检验增量关联机制是否必要 |
| X1 | Mem0-TraceEqual | 已修复关闭顺序；同一观察包和冻结摄入边界；保留原生抽取语义 | 外部系统对照 |
| M | MiLAi v13.2 | 同源事实视图＋候选身份增量修订＋有界交付 | 新候选 |

B6+ 明确强于旧 B6：它不再因为只保存业务回执而必然丢失普通偏好。这里用原文与简单摘要补齐一般使用能力；摘要成本真实计入。旧 B6 原结果不改名，新 B6+ 不是已发表框架。

NoMemory、FullHistory、RollingSummary、Ordinary-Matched 和 Prompt-only 用作公共任务参照/关键诊断。旧 v13.1 Field-grounded 在小型回归与成本表保留，不铺成全量主臂。

SimpleMem-Text 是已有接入的第二外部系统，预算与微型合同可完成后进入公共主表或固定确认切片。Hindsight 是证据/可追溯主张的重要近邻；HiMem 是双类型主张近邻。若未复现就披露，不能宣称优于它们；现阶段不为凑数量新接入多个框架。[R13,W01,W02]

## 8.2 共同条件

所有主臂使用相同 Host、业务工具、guard、公开对象 discovery、当前输入与观察流；新预取策略和公共解释提示同样开放给基线。不给任何方法隐藏真实状态、任务标准计划或 evaluator 派生的对象 ref。

机制表匹配形成边界、可见历史和材料上限；完整系统表允许各框架原生节奏，但单列它造成的费用与行为差异。共同 reader 的 backend 比较不冒称原框架完整 ask/reflect 复现。

每方法只给同数目的少量配置候选，全部在开发来源上选择。不得对 MiLAi 连续优化，而用未调过的随意 top-k 作为 StrongRawRAG。

## 8.3 防止三个伪收益

自动预取优势必须通过“所有方法同样预取”的对照保留下来；自动事实写入优势必须与 B6+ 相比；额外 metadata 和原文回退必须计入同一材料预算。

只读记忆自动交付不等于强制业务动作。NoMemory 保留合法当前查询；当前世界可重新发现的任务不声称记忆是必要条件。历史经过/当时意图等仅在旧源存在的信息，必须来自真实历史而非人为藏掉正常工具数据。

# 9. 实验矩阵：先定位，再整体比较

## 9.1 E0：旧结果收口与可用性回归

先完成 45 条旧尝试的证据状态表；在新配置上复跑固定 24 个正常开发检查，并加入来源误绑、交错版本更新、同源多对象、迟到观察四类机械回归。

保留原 22/24 阈值作为工程使用门槛，同时要求两个旧更新失败各有直接修复证据；不把只修这两个暴露案例解释为泛化。泄漏、假提交成功、协议读入 gold 是受影响运行的硬停止项。

## 9.2 E1：投影方式 × 交付方式的最小 2×2

|  | 自主 search/read | 一次公共有界预取 |
|---|---|---|
| 模型提案式 Field-grounded | 旧机制参照 | 隔离交付改变 |
| 确定性观察派生 | 隔离维护改变 | 新操作链路 |

相同场景、原始输入与工具合同，其他差异记录并固定。先用固定观察流检验形成/交付机制，再做完整 Agent 运行。模型自然不产生字段冲突时报告发生率低，不能人为塞错误后宣称降低了自然错误率。

故意注入冲突、重复、乱序属于机械/鲁棒性测试，单独报告，不混入自然失败分母。

## 9.3 E2：来源回链与增量更新

固定同一读入策略和形成节奏，比较旧 target_query、来源回链候选、来源回链＋读取版本句柄/patch。测试中文→英文卡、英文→中文卡、同名不同事项、用户纠正、两条并发修订和历史查询。

主要指标：正确原记录更新率、非意图重复卡率、错误合并率、版本冲突检出率、最终回答与已提交版本的一致性。目标不是“所有 create 都改成 update”，而是正确关联应修订的事实。

## 9.4 E3：四主臂两个工作流

先以已有六故事在文稿工作流运行四主臂，共 24 条开发轨迹，旧已曝光故事不算新任务。质量设置沿用事前已声明的每消息 24 次生成；共同 12 次预算另立条件，不与旧失败拼表。[R10]

进入新 pilot 后，建议 12 个新的基础任务，两个工作流各 6 个；每任务配 clean 与一种平衡异常条件，即 24 个条件实例，四主臂共 96 条轨迹。它们是规模规划，不是已生成输入。

正式第一版以 60 个基础任务（两个工作流各 30）×2条件×4方法＝480 条轨迹规划；异常包括 partial、known-no-effect、unknown/effect、unknown/no-effect、stale。每种异常预计约 12 个实例，不足以单独证明零风险。

同一基础任务的多个变体/方法/seed 不是独立样本；必须按基础任务配对，必要时按共享任务模板家族聚类。不得只改商品名称就算多个独立任务结构。

## 9.5 E4：公开任务作为外部锚点

MERIT 复用官方任务、工具和 scorer；新方法适配不得带入 future user message 或 gold。pilot 18 arc、正式 90 arc 仍作预算候选，按领域/难度分层，完整 arc 保留。环境可见性与记忆接口改变时，明确称“官方任务上的受控 backend 比较”，不是完整原生复现。[R14]

MemSyco 优先验证 scope 与有效个性化；源池修订完成前不运行新 pilot。三个任务分别报告，不合成总记忆准确率。一次性全历史形成与增量形成要匹配比较，否则只解释为系统配置差异。

EAL-Bench 只在方法自然支持其可见授权历史时补充；不得从隐藏 ledger 构造工具证据。其 oracle source gate 是诊断条件，不是 MiLAi 可部署组件。[W03]

## 9.6 条件性消融

只有 E1–E3 支持继续时才扩展：去掉来源回链、去掉增量修订、只保留 B6+；类型/Scope 做 2×2 小切片。State–Attention 必须在正确记忆实际送达、普通 Q/W 仍不足的情况下再比较 Q/W/A。

每次删除一个机制，同时记录调用与材料预算变化；不把额外上下文、writer 或更高调用上限隐藏成结构创新。

# 10. 泛化性：核心不变，验证边界明确

## 10.1 四种泛化不能混称

| 泛化维度 | 冻结与测试方式 | 能支持的结论 |
|---|---|---|
| 新实例/新任务结构 | 任务图/模板家族整体留出，不只更换名称 | 同领域结构外推，取决于实际覆盖 |
| 新工具 schema | 只增加公开字段映射，核心与提示不改；测缺失/新增字段、多对象 | 接口迁移能力；机械成功不等于任务泛化 |
| 跨语言 | 中文/英文及双向源—卡不一致，统一算法 | 仅对实际测试语言的适用性 |
| 跨模型 | 固定配置，另家族分别做 reader 迁移与端到端形成 | 第二家族缺失时不能声称已验证 |

预订和文稿工作流都已进入设计视野，因此在它们上测试不称“全新未知领域”。真正零调参迁移需要在核心冻结后引入尚未用于方法开发的工作流/任务家族。

第三种新 schema 可以先用合成公开工具合同做零模型合规检查，不为了第一篇论文另建大型环境；它只能支撑接口一般性。

## 10.2 防止模板特化

核心实现禁止读取 benchmark case_id/seed/domain gold；不硬编码 Cedar、reservation 的具体实体值或文稿固定标题。可以读取工具公开声明的字段路径和效果合同。

各领域适配器只负责输入输出解释，不含正确动作序列、答案模板和基于故障类型的分支。报告新增适配器配置、代码范围及所需人工语义定义；不能把领域知识藏进配置后宣称完全无需适配。

## 10.3 长程与规模分开测

性能试验可用 100、1,000、10,000 条可控事件测索引增长、重放和 p95，这不等同于长程语义能力。自然长程仍沿原方向：两个 owner、各 20–30 个 session、15–25 个真实事项，只有小型方法成立后再做。

不得随机灌入无意义文本来制造 Attention 或压缩优势。真实项目完成、临时覆盖、偏好修订、历史/当前查询可以产生自然干扰。[U01]

# 11. 数据、评分与资源限制：修订计划，不伪造条件

## 11.1 先保护来源组，不先凑题数

当前来源审计：新 pilot 预留前 Scope/Valid/Personalized 为 270/63/95 行，预留组件后为 250/7/54 行。Valid 总 350 行仅 45 个来源组；按题数先抽 pilot 会耗尽大部分剩余来源。[R08]

v13.2 不再把“各100题”当不可调整的算法验收标准。先导出 metadata-only 的来源关联图和可用独立组数，再发布新分组清单；优先用已曝光来源进行工程开发，保留稀缺新组作最终验证。

题数减少不能只写“仍够发表”；要报告独立组数、区间精度与受限结论。七行不被宣传为充分独立的更新验证。

## 11.2 尚未读取的预留样本怎样处理

本轮报告说新 Pilot-S 只预留 ID，题目与 gold 尚未读取。这是重新设计抽样的可能窗口，不是自动回收许可。[R08]

默认仍排除所有旧曝光/预留组件。只有可审计证明内容、输出和评分都未进入开发人员或模型上下文，且没有方法选择依赖这些样本时，才在任何新内容访问前登记协议 amendment。保留原 registry，追加旧状态、新用途、依据、审批和新 hash；不能覆盖历史记录。

不能确认访问历史时不回收。可以保留小规模辅助结果，并将主要结论建立在有独立来源的 MERIT 与新生命周期任务上。公开任务替换和规模变化必须写明，不假装原方案已完成。

## 11.3 评分不依赖不存在的服务

当前没有额外独立 Judge 或第二模型家族，不再重复询问，也不默认购买、下载或部署。[R02]

业务目标、字段支持、副作用、回执/版本可做确定性评分，scorer 与 runtime 隔离。自由文本和范围使用需要独立评分；现有同族 Judge 或 Root 复核只能作开发诊断。准备匿名、盲序、带固定 rubric 的审查包，但没有第二位独立审查者时不能将其称为独立评审。

未来有独立人员或模型时可按冻结答案评分，不重生成挑结果。评分预算单列。评测系统不参与运行时纠错，也不把 oracle-fix 的结果并入主表。

# 12. 指标、统计与 Go / Pivot / Stop

## 12.1 不用一个总分掩盖链路

| 维度 | 指标 | 分母/限制 |
|---|---|---|
| 完成性 | completed、budget_exceeded、truncated、infra_error、NOT_RUN | 全部计划轨迹与已尝试轨迹分别列 |
| 事实性 | unsupported operational claim、支持字段保留、角色误归属 | 结构化与自由文本分开；无法判定不填0 |
| 消费 | 有关历史是否送达、是否被正确解释 | 合法历史可用的预定任务；不能只统计成功读取 |
| 维护 | 正确更新、错误合并、重复卡、冲突检出 | 有明确更新义务的案例 |
| 行动 | 错误提案、guard 拦截、实际错误/重复副作用 | 三者分开；被拦截不算模型正确 |
| 效用 | native task、完整 arc、clean 成功、完整生命周期成功 | 全部条件；不把完成消息当成功 |
| 效率 | 实际调用、输入/输出 token、embedding、p50/p95、存储 | 维护、回退、失败、重启、评测分别记账 |

结构化事实从实际回执派生而正确，是实现不变量，不足以证明论文贡献。必须测它对真实错误提案、最终回答、恢复与正常效用的影响。

## 12.2 统计合同

按来源历史/arc/基础任务配对，预先确定主要比较 M vs B6+，M vs B2+ 为次要比较。按真实依赖结构做 cluster bootstrap；独立 cluster 太少时只作描述性分析，不借大量 seed 制造精度。

主实验共同报告效用差和成本差。计划将 clean 成功率的非劣界设为5个百分点作为讨论起点，须在正式结果前冻结；95%区间不能排除更大退化时只能说非劣未证实。p值不显著不是无退化证据。最终样本量用 pilot 的配对差异/变异与预定精度确定，不看到显著性才停止。

基础设施故障不悄悄删除；另外报告可评分样本结果和缺失上下界。原预算耗尽是真实系统结果，扩容后另立 cohort，不能抹去原失败。

## 12.3 决策规则

| 观察 | 决定 |
|---|---|
| 新方法修复版本/历史消费，成本下降，clean 不受明显损害 | 可进入独立 pilot，尚不等于研究成立 |
| 所有收益都由共同预取解释 | 将预取作为工程默认，收缩表示贡献 |
| B6+ 同样或更好 | 优先采用简单实现；不继续叠类型/selector |
| 安全提高但大量正常任务失败 | 报告安全—效用权衡，优先修可用性 |
| 在同一工作流有效、换 schema/结构即失效 | 缩小适用范围，排查 adapter 特化 |
| 缺独立来源/评分/第二家族 | 继续不依赖它们的工作，相关主张保持未证实 |
| gold 泄漏、静默改结果、共享 owner 污染或假保存回执 | 停止受影响运行，先修实验合同 |

普通语义失败不停止所有独立安全任务；方法晋升与是否继续采集证据是不同决定。

# 14. 迁移、版本与复现

## 14.1 旧数据不重写成新成功

保留旧 `optional` / `explicit_receipt_v1`、旧 Field-grounded 与旧 source schema。v13.2 opt-in 开启；旧 content-only 记录继续以未验证身份读取，不自动提升业务字段可信度。

## 14.2 文档与配置精简

每个新 cohort 只需要一个运行manifest、一个逐轨迹结果表、一个来源/预算摘要；它们由实际记录派生。不要为每个微小检查增加一套人工状态系统。

实验身份至少固定：代码/CLI、环境与SDK、实际模型route、工具/schema/profile、提示、写入与交付节奏、来源组、故障语义、预算、scorer、预定比较与停止规则。报告提交SHA不能代替执行SHA。

## 14.3 连续成本

最新仓库快照为 7,461 次 generation、15,742,294 generation tokens、538,303 embedding tokens，其中 v13.1 增量1,316次/4,335,208/121,373，包含48次同族Judge；本次规划没有新增实验usage。[R02,R15]

所有新批次接续权威原账本；缓存、失败、重启、索引构建和维护分项报告。unknown usage 不能擅填0。美元/GPU小时只有实际测量或可核计价时报告，不由token猜测。
