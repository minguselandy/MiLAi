## 1. 本轮决定：不要再把已读存档当成模型工作上下文

### 1.1 目标

让普通Host连续处理查询、更正、历史和业务续办时，下一次模型调用只包含当前任务真正需要的材料；无关正文可以退出工作上下文，需要时还能按实际引用重新装入。

用户不必操作“第几层记忆”，也不必理解record、revision和cursor。模型通过既有读取工具选择信息，程序根据实际结果更新工作状态并构造下一次输入。

本轮首先交付以下行为：

1. 搜索默认给出轻量候选，选中后再打开事项正文及必要条件。
2. 在多个事项之间切换时，当前工作集可以替换，不再无限追加旧工具正文。
3. 当前、原始来源和实际保存历史可以按问题目的分别显示。
4. 提交后刷新受影响的当前视图；重开、遗忘和剩余任务继续使用原生命周期。

**不以token越少越好。** 完整必要证据优先于更短输入；收益应最终表现为更好的任务完成、限定保持或可用性。

### 1.2 已有能力直接复用

上一份规划和已核对源码表明：现有系统已有搜索、事项读取、原文读取、历史版本、分页、读取进展、共同维护、Append-only和实际回执；`_cache_writer_items()`保存已读材料，`_writer_packet()`从累计材料构造Writer输入。[S1][S4]

因此，不重建分页工具，不新建Host专用事实库，也不再增加一位运行时“记忆管理Agent”。需要补齐的是：

> **已读存档 → 当前选中引用 → 实际材料 → 本步模型视图。**

### 1.3 当前问题的适用范围

已有大包输入失败支持改进交付方式；小输入、空旧库也发生过正式空输出。因此，“所有问题都来自记忆太大”仍是假设，不是结论。[S1，§1–2]

本设计主要针对上下文累积、无关材料竞争、重复读取、当前与历史混淆，以及编辑时同时处理过多事项。它不会自动证明来源归属正确，也不会自动消除所有漏写或条件解释错误。

## 2. 总方向与设计边界

### 2.1 五条主线如何落到本轮

| 主线 | 本轮要求 |
|---|---|
| Grounded Memory | 目录和工作笔记只导航；断言依据来自实际正文、来源和回执 |
| Verified Object References | 记忆引用不授予业务权限，不替代实际对象发现和当前状态查询 |
| Semantic/Episodic Memory | 事项、Episode与原文按协议读取；不复制出第二份长期事实系统 |
| Grounded Revision | 修改时显示完整必要语义；程序保留未编辑内容，不从未读内容猜新关系 |
| Lifecycle Recovery | 换出不删除；恢复使用实际引用、版本、原操作和当前权限，避免重复效果 |

保留原“普通检索→Working State→Host”结构，以及一个逻辑MemoryService。[S2，第299–342行]

旧v13.4的Simplify仅限制当时未建立必要性的复杂关系消歧选源分支；本轮不恢复该分支，也不把该结果扩大为“工作上下文无需改进”。[S3，第54–65行]

### 2.2 本轮明确不做

不引入SHA、替代哈希、内容指纹或全对象复验门禁；不增加常驻Reviewer、反复纠错Agent、竞争事实库、全局知识图谱、强化学习或复杂概率选源器。

不按人名、领域、题号和benchmark答案写路由规则。不强制所有消息保存，不将抽取候选直接转成记忆，不把私有推理草稿当正式操作。

不进行大规模目录重构。既有owner、来源可见性、版本冲突与实际业务效果检查仍由负责的边界执行一次；避免将相同规则复制到状态、视图、工具、编排和提交五个地方。

## 3. 架构：状态控制引用，视图控制展示，MemoryService保留原件

```text
当前请求＋当前权限＋原始事件
                 │
                 ▼
       已有Host／维护执行状态
       └─ 小型 memory_view
          焦点、读取目的、驻留引用
                 │
        选择实际需要的事项
                 ▼
   既有search/read/source/history/page
                 │
        实际读结果与原提交回执
          ┌──────┴──────┐
          ▼             ▼
      已读存档       当前工作集
      保留轨迹       可换入换出
          │             │
          └──────┬──────┘
                 ▼
      本步记忆视图＋本步工具说明
                 │
                 ▼
           同一个现有Agent
       读取／编辑／业务／回答
                 │
                 ▼
   实际结果更新状态，重建下一步输入
```

**状态不是prompt，已读存档不是工作集，工作集不是新的事实库。** 不把整个checkpoint或数据库对象直接序列化给模型。

### 3.1 三个集合必须分开

| 集合 | 含义 | 更新方式 |
|---|---|---|
| 可访问材料 | 当前权限允许访问的来源、事项和历史 | 由MemoryService及应用边界决定 |
| 本轮已读材料 | 实际返回过的版本、页面、来源区间和读回执 | 复用已有读取进展，记录实际结果 |
| 当前驻留材料 | 下一次模型调用需要展示的材料 | 按当前焦点替换，不只追加 |

“已读过”不能阻止正常重新装入；“已经从当前上下文换出”不等于“忘记了”；“可访问”也不等于“模型已读”。

### 3.2 硬预算与软选择

沿用调用方真实窗口、输出预留和消息预算，计算实际system、工具schema、当前请求、目录、正文与结果的总输入。

活动材料可以有一个软目标，但不强制为了该目标截掉必要条件。超出软目标且仍可容纳时，优先保留自足语义；超出硬容量时明确分页、选择较少事项或保留未完成工作，不静默丢弃。

首版不引入新的容量常数，不自动增加读取或生成额度。额度不足以完成动态探索时，保留已有材料并说明不足；更高预算只作为后续明确配置选择，不能隐式扩容。

## 4. 最小工作状态：只保存当前工作所需的引用和选择

### 4.1 新增状态应当很小

优先在现有线程／请求checkpoint下增加`memory_view`。不新建State数据库，不重复维护一套业务计划、权限或回执。

| 字段 | 内容 | 责任 |
|---|---|---|
| `focus` | 当前事项或自然语言子问题，允许空值和多事项 | 模型语义选择；调用方已有明确对象时直接复用 |
| `read_goal` | 当前规则、保存历史、原始表述等读取目的 | 使用当前请求含义，不按关键词硬编码 |
| `resident_refs` | 本步要显示的记录／来源／页面引用与实际版本 | 根据工具结果增减，整体可替换 |
| `pending_refs` | 关联已有未完成工作项，不复制其状态 | 复用维护checkpoint或完整请求journal |

`coverage`和实际读回执继续使用现有`read_progress()`，不要再存一份不同步的同义数据。查询时间、日历和当前能力也从已有请求状态读取。

每个引用至少区分材料类型、实际对象、版本或来源区间，以及当前／历史视图。优先复用既有类型，只有跨模块确需共享时才增加一个小型公共类型。

### 4.2 设计示意，不是现成API

```json
{
  "focus": "项目P：解释当前安排与过去保存的例外",
  "read_goal": "current_and_saved_history",
  "resident_refs": [
    {"kind": "record", "id": "matter_17", "revision": 3, "view": "current"},
    {"kind": "record", "id": "matter_17", "revision": 2, "view": "saved_history"}
  ],
  "pending_refs": ["existing_request:remaining_answer"]
}
```

这份状态没有正文，没有真假分数，没有模型自报的业务完成，也没有第二份权限。

### 4.3 不加入容易变成新平台的字段

首版不增加“全量目标树、世界模型、证明对象、语义完整度分数、每条断言审批状态、全局重要性矩阵”。实际接入需要哪个小字段，再添加哪个。

模型可提出“需要查看取消依据”，但这只是下一步工作选择；不能把“我认为证据充分”当确定性事实。

## 5. 状态驱动的读取：按需要直达，不强制走完固定层级

### 5.1 候选目录

搜索返回真实候选身份、已有事项描述、已有主体线索、版本、正文规模和可继续读取的入口。目录不默认带全部正文与完整支持结构。

首版复用已有dense排序与候选合并，不同时换embedding、reranker或检索算法。候选数量与来源权限的变化另行记录，不能将更大检索范围混称为展示优化。

已知实际ID可以直接打开；短而明确的新事实在空库中可以直接形成。不要强迫所有消息先搜索。

目录优先使用已有描述或原文摘录，不为每次查询调用模型生成新摘要。来源已捕获但没有语义形成时，应保留既有原文入口，不让“先有成功记忆”成为发现原始事件的前置条件。[S1，§2.3]

### 5.2 事项级完整打开：首版的默认语义单位

首版打开选中事项的完整正文、必要来源信息和已记录的条件／例外关系；不再同时打开所有候选。

“必要语义包”是：

> **目标内容＋实际相关限定＋一般／例外关系＋所需支持。**

关系尚未明确时，保留该事项完整正文。没有结构边不能证明其他限定与本次修改无关。

若单个事项本身超出硬容量，使用既有分页，明确正文尚未读完。不能让只读部分的模型执行整记录覆盖，也不能由程序把它遗漏的部分偷偷补回后仍称原全量重写。

### 5.3 按目的读取三种历史

| 用户实际问题 | 证据对象 |
|---|---|
| “我当时说了什么” | 原始Source及必要相邻语境 |
| “你当时保存了什么” | 实际已提交修订，不是用户请求 |
| “那天什么安排适用” | 有来源依据的生效时间、范围和一般／例外关系 |

当前任务可能需要两种或三种一起读取，不强制单标签分类。一个后来的报告可以明确回顾过去，但报告日期本身不能自动成为过去事实的生效时间。

### 5.4 探索查询沿用根请求身份

搜索词可以根据当前焦点细化；根请求、owner和权限不变。复用原调用方支持的子查询身份，不改写原用户请求，也不禁用现有公共请求绑定来绕过限制。

若现有接口确实不能表达子查询，只做一个兼容参数扩展；不为每个查询新建一套权限或账本。

## 6. 当前工作集：换出正文，保留可恢复引用

### 6.1 换入

实际读结果进入已读存档；选中要用于下一步的结果进入`resident_refs`。目录本身不产生“正文已读”或“来源已支持”的结论。

取得缓存中的可见同版本正文后，可以不再访问外部源；该正文在本步实际显示后才算进入当前上下文。其prompt token仍照常计量。

### 6.2 保留

修改前保留当前来源、目标正文及必要限制；执行后保留实际回执及回答需要的结果。当前用户明确约束和应用给出的能力不能因换出而消失。

优先保留模型当前选定的少量事项与最近实际结果，初版不建立复杂重要性评分或全局淘汰算法。

### 6.3 换出

已完成且与下一步无关的大正文退出当前工作集，留下实际记录／回执引用。完整存储和已读轨迹不删除。

如果最终回答仍需比较多个已处理事项，应重新装入这些事项的实际必要正文；不能靠一句“前面已确认”回答精确金额、日期或范围。

### 6.4 重装与无进展读取不是一回事

| 情况 | 正常处理 |
|---|---|
| 同一版本已经驻留，再次读取相同页 | 返回已有材料或简短提示，不重复追加长正文 |
| 同一版本读过但已换出，现在重新需要 | 正常重新装入，不因coverage存在而拒绝 |
| 需要此前遗漏的页或来源区间 | 使用实际游标继续读取 |
| 同样搜索反复返回同样结果且没有新需求 | 使用已送达材料回答，或说明仍缺少的信息 |

不按“读取过两次”一律停止；使用已有实际进展与根请求预算，不为每个事项重置预算。

## 7. 模型视图：每步重建，不把整个状态塞进prompt

### 7.1 默认展示顺序

1. 当前用户请求、当前限制和正在处理的问题。
2. 当前实际证据：选中正文、必要条件、原文与历史身份。
3. 实际任务结果：已提交什么、仍未提交什么、有哪些未知。
4. 可以继续打开的候选或页面，及确实尚未读取的材料。

“不确定”来自实际资料缺口或模型明确保留的解释，不用一个统一confidence数值掩盖其来源。

### 7.2 示例：展示已知关系，不推导不存在的关系

以下是构造示例；假设实际来源明确说“一般安排对白班和夜班均适用”。如果来源只说整体频率，就不能展示为各班分别适用。

```text
当前任务
解释项目P夜班的当前安排，以及之前实际保存的例外。

当前记录：版本3
一般安排对白班和夜班均为每周三次。
开始时间未确定，节假日暂停。
夜班每周四次的局部例外已经撤销。
依据：实际一般规则、更正与撤销来源。

已保存历史：版本2
当时实际保存过夜班每周四次的例外。
这是历史记录，不是当前安排。

材料边界
已读取版本2和3；没有证据说明开始时间已经确定。
本轮没有进行实时业务查询。

可继续读取
原始撤销片段；更早保存版本。
```

普通最终答复不需要暴露内部operation、UUID或游标。用户要求审计时再显示实际来源与版本。

### 7.3 消息与工具合同

持久对话轨迹继续保存，模型调用前临时构造本步输入。当前工作集字段采用替换语义，不与不断累积的消息日志使用同一更新方式。

工具调用和结果必须成对保留；不留下孤立ToolMessage，不把模型计划重新包装成实际观察。不能因为压缩上下文，就执行私有reasoning中的草稿。

在导航阶段只显示需要的读取能力；准备编辑时显示选中目标的编辑说明；业务能力始终来自当前权限。展示策略可以隐藏无关操作细节，不能凭空增加允许执行的动作。

### 7.4 当前与历史刷新

实际提交后刷新受影响事项的当前视图；已发行的旧版本仍是历史，不重新贴成当前。无关事项不必整库刷新。

视图用途改变时也重新构造呈现：同一记录版本，对不同查询时间／范围可能有不同适用说明。实际读取与渲染缓存应考虑这些已有参数，而非仅按record_id复用。

外部业务是否改变仍由真实lookup／observe决定，不能靠记忆版本缓存保证实时性。

## 8. 与写入、编辑和恢复的衔接

### 8.1 沿用已有写入方法，不同时改变算法

保留`single_pass`与`extract_then_edit`，以及B0/B1/B2/M/Append-only。首版改变材料交付与驻留，不新增抽取器或更强审核器。

当前来源不能只剩候选摘要；相关原文在执行对应事项时应实际可读。提取为空仍可根据原文维护，候选非空也不强制保存。

| 方法 | 首版读取要求 |
|---|---|
| B0／B2全量重写 | 被选择事项的完整替换范围及必要旧支持 |
| B1／M局部编辑 | 首版同样完整打开选中事项，程序保留未修改结构 |
| Append-only | 当前来源及判断重述、变化归属所需的旧材料；不覆盖旧事实 |

单元级局部读集后置：只在事项级功能可用后扩展明确合同，不将其收益混入首轮展示比较。[S1，§6.2–6.3]

### 8.2 一次根请求可以处理多个事项

使用既有根请求下的工作项组织多事项维护；同一来源不重复捕获，已有一次候选提取不因换页而反复执行。

同一记录相关变化优先放在同一次修改容器内。必须多次编辑时，后一次使用实际最新版本，不同时提交基于同一旧版本的冲突提案。

工作项身份在实际调用前确定并持久化，重开不按页面顺序重新编号。导航、读取和编辑都计入同一个真实调用预算；不要在Host里再套一个独立预算的Agent。

### 8.3 空结果反馈

资料中的PR #106修正了“没有维护回执却声称已有记录”的反馈。实施时继承实际已有修复，不重新建设相同功能。[S1，§1.3]

- 无语义回执：说明本轮未提交，不能称已有记录无需更新。
- 有实际记录／版本的无变化回执：按其实际范围说明no_change。
- 有实际提交：说明具体提交，不自动等于全部语义要求正确。
- 没有本轮写权限：不写入，保留当前限制。

这是反馈规则，不是强迫模型输出非空。

### 8.4 完整请求与显式续办

纯记忆保存的未完成任务复用已有维护checkpoint；业务、记忆和答复仍分别使用实际回执。状态视图只引用这些进度，不创建另一套完成状态。

| 发生位置 | 恢复要求 |
|---|---|
| 未发送模型调用 | 当前允许时继续未处理工作 |
| 模型结果未确认 | 保留原unknown；需要时明确建立新尝试，不默默重复旧请求 |
| 提案已保存、提交结果不清楚 | 先核对原操作，不重新生成一份代替 |
| 部分事项已经提交 | 保留真实完成项，只处理允许的剩余项 |
| 业务完成但记忆未保存 | 读取实际业务结果，只补记忆，不重做业务 |
| 仅最终答复失败 | 重新表达实际结果，不重新执行已完成动作 |
| 当前权限或可见性改变 | 重新通过原读取边界，不从缓存带回被撤销内容 |

换出的正文不是恢复障碍，因为状态保留真实引用；但来源已不可见时不能用旧工作笔记替代。

## 9. 代码实现：最多先增加一个小型工作集模块

### 9.1 三个职责，不是三个新服务

```text
选择本步引用
    select_view_refs(state, actual_read_progress)

取得实际材料
    materialize_view(existing_reader, refs, current_request)

构造本步输入
    render_model_input(request, state, actual_materials, current_capabilities)
```

这些是设计示意。第一步不一定独立调用模型：已选中的实际事项、上一工具结果和当前任务通常可直接复用。只有需要新的语义选择时，才由现有Agent正常选择读取动作。

工作集函数不能直接创建业务事实、调新模型或调用scorer。异步或后台调度不是本轮依赖。

### 9.2 代码落点

| 位置 | 实施内容 | 不在此处增加的内容 |
|---|---|---|
| `memory/working_set.py`，确有需要时新增 | 小型引用状态、驻留替换、纯视图辅助函数 | 数据库、模型、业务调度、Reviewer |
| `memory/functional.py` | 目录与已有正文／来源／历史工具的投影 | 领域识别规则、隐藏读取 |
| `methods/functional_edit_memory.py` | 已读缓存与resident分离，当前目标Writer输入，提交后刷新 | 第二份事实正文、完整性门禁层层复制 |
| `methods/edit_maintenance.py` | 将现有维护接到同一工作状态，继续原请求与工作项 | 独立Agent循环、重复账本 |
| `methods/edit_memory.py`／`edit_features.py` | 选中目标的现有schema与映射 | 同时重做所有编辑算子 |
| 普通Host调用入口 | 每次模型调用前使用统一投影 | 把全部方法逻辑写进runner |
| benchmark／external入口 | 调用同一工作状态和读取实现，保留predict/score分离 | 专用答案提示、gold路由、评分时回写记忆 |

原本能用现有类型表示的字段不再新增DTO。共有类型确需变更时，由一个负责人修改现有contracts。第一版不创建框架式策略工厂或多个“管理器”。

### 9.3 配置收敛

最多新增一个视图策略项，例如`memory_view_mode = legacy | state_driven`，与已有recipe和编辑方法分开。

这是待接入名称，不是当前CLI已支持的参数。目录长度、材料额度和调用次数先沿用原配置，不增加十余个自由开关。

固定两阶段和动态继续读取可以在同一实现中通过调用方策略选择；首版不要求用户手动选择多个算法组合。

| 顺序 | 交付包 | 实际完成标志 |

### 10.1 包A：先让视图可用

执行前只读核对一次实际分支及已有修复，避免重复开发。上一轮文档记录的暂停或提交身份不当作本次最新事实，也不据此启动旧实验。

读取目录、打开事项与原文均走既有服务；空语义库仍可访问合法原始来源入口。先完成正常查询，不先开发全量评分。

### 10.2 包B：真正控制每次模型调用

检查模型调用点是否使用当前resident，而不是仅在UI显示更短目录、底层prompt仍注入全部旧正文。

保持原始事件和完整轨迹持久化。工作集换出只改变下一步模型输入；工具结果和操作身份继续可恢复。

### 10.3 包C：完成用户任务的剩余环节

同一实际事项修改后，当前视图及时更新；用户问历史时能选对证据层。纯查询不因state变化而自动提交记忆。

补齐明确保存请求的未提交反馈和显式继续，继承已有业务恢复。发现语义漏写可记录问题，先继续完成其他功能；越权、数据损坏和重复业务效果必须先处理。

### 10.4 包D：再接实验，不回头堆架构

使用现有入口保存预测、实际前后状态和读取轨迹，之后再评分。阶段性提交说明用户已经能够完成的流程、尚有的语义缺口，不用测试数量作为开发成果。

**工程完成不要求先证明算法优势，但必须有一条真实可执行的普通使用链。** 不以论文显著性作为集成前置条件，也不把执行完成宣传为语义全部正确。

## 12. 开发中的反思：用实际断点改代码，不加新的审批流程

每个开发包交接时，在已有问题表补一条短记录即可；没有新问题无需写“复核通过”长报告。

| 反思问题 | 出现问题时的动作 |
|---|---|
| 这次添加的是用户需要的能力，还是为了让旧接口勉强兼容的新包装？ | 优先删除重复包装，保留一个主路径 |
| 本来能直接读到的内容，是否被新增状态或工具步骤挡住？ | 恢复简单直达路径，不再追加补救Agent |
| 是否把本应一起理解的条件拆开了？ | 扩大该事项的必要语义包，而不是增加拒绝规则 |
| 程序已知的引用、版本或权限，是否又要求模型重复填写？ | 在负责边界继承实际信息，不重复生成 |
| 失败最早发生在定位、交付、编辑，还是最终解释？ | 只改最早有证据的断点，不同时改整条链 |
| 新功能是否真的改变了模型收到的请求？ | 看一次实际payload与用户流程，不只看状态字段存在 |

“先完成”不等于无视问题；“反思”不等于每个提交重开架构设计。先修阻断正常使用的问题，其他语义缺口集中到后续实验。

## 13. 检查策略：开发期少量必要检查，完整实验后置

### 13.1 开发过程中

只运行直接受影响的既有导入、类型、格式和必要行为检查；出现一个真实回归，再补一个最小复现。

不执行每次提交都跑全套benchmark、每个字段新增多组拒绝测试、每个说明改动跑全部Judge、反复核对所有历史产物等流程。既有合并CI按实际变更范围保留，不额外扩展人工门禁。

必要边界不能因为“少测试”而删除；同一边界也不必在多个模块反复测试。

### 13.2 合流后复用三条连续使用流程

| 流程 | 一次串起来观察什么 |
|---|---|
| 保存→两个事项查询→切换→重开 | 正文会换出、需要时重装、记录实际持久化；原始来源仍可达 |
| 更正→例外→撤销→当前与历史问答 | 新版本及时呈现，未改条件不被藏掉，历史不是当前，最后查询不写库 |
| 部分业务→只补保存→只读重开→遗忘 | 真实业务不重复、剩余保存有回执、当前权限有效、遗忘后不由缓存恢复 |

沿用已有例子或五条冒烟中的相应步骤，不另建一套独立测试框架。这里只证明接线与正常行为可观察，不把三条流程称为统计验证。

普通语义错误记录后继续其余步骤，不为修复每一句表述不断扩大提示或重跑全部流程。

## 14. 功能完成后的集中实验与算法优化

### 14.1 第一轮先跑一个完整候选

在既有开发数据上检查：状态驱动后，实际请求是否更聚焦，任务是否完成，必要条件是否被遗漏，以及累计调用是否过多。

优先复用已有暴露案例和实际前态，包括小输入空提案、长材料、多事项、未重述限定、历史、例外和不足信息。不为证明方案有效专门只挑长上下文失败。

本轮不先要求五个编辑方法、两个recipe和三种展示方式全部交叉运行。

### 14.2 第二轮只比较交付方式

| 条件 | 实际含义 |
|---|---|
| D0 既有方式 | 当前一次性材料交付或累计页面路径 |
| D1 简单分阶段 | 目录后一次选择并打开，随后完成任务 |
| D2 状态驱动 | 同一目录和工具，按焦点替换工作集，必要时继续读取 |

固定同一模型、合法来源范围、实际前态、候选池和编辑器。Reader比较固定持久状态；Writer比较使用相同原始来源和旧状态，并用共同Reader评价。

需要搜索更多来源时单列扩展设置，不能只给D2更多原文或更多候选。普通Host的Episode原文可用性不自动改变benchmark原来的`include_raw=False`协议。[S1，§14.4]

### 14.3 只记录有解释价值的指标

任务侧：新要求落实、未改语义保持、主体／来源／时间范围、合法撤销、最终回答与真实业务效果。

工程侧：峰值输入、累计输入输出、生成与读取次数、重复无进展读取、实际提交／空输出／拒绝、容量失败和unknown。

主要事实从已有轨迹和保存预测取得，不为每个页面新增Judge。官方评分沿用原口径，补充语义分析单列；实际读取、操作提交和回答正确不得相互替代。

用户主动暂停、未运行方法和未确认响应分别记录，不能把未运行部分填零。多道问题共享一次早期身份漏写时，既保留完整QA分母，也指出共同根因，不把它们当许多独立历史。

### 14.4 根据结果做减法

| 观察结果 | 下一步 |
|---|---|
| D1与D2相当，D2调用更多 | 采用D1，保留状态视图但去掉不必要探索 |
| 上下文更小却漏掉例外 | 修必要语义包，不继续缩短正文 |
| 长输入改善，小输入仍空输出 | 承认上下文只是部分原因，单独检查维护选择／正式输出 |
| 状态正确但答案仍错 | 只改Reader证据组织，不先改存储或检索 |
| 所有材料都已送达，目标仍未更新 | 聚焦语义编辑，不新增读取层 |
| 仅增加读取次数取得改善 | 增加同调用预算对照，不把全部收益归给state |
| 强简单方法同样或更好 | 采用简单方法，完整五条主线继续交付 |

### 14.5 长历史与研究确认最后执行

共同功能候选确定后，再用已有B0/B1/B2/M与Append-only比较必要机制。65／277历史可以是同一连续运行的中间和最终观察，不为两个里程碑重复完整运行。

保留用户、外部任务、完整Host与新故事确认仍按原计划在候选冻结后执行。它们是最终效果验证，不是每个小补丁的前置测试。

## 15. 创新与通用性：先明确可检验机制，不预先保证效果
