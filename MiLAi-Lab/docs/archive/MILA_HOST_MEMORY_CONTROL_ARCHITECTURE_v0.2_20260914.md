# MiLAi 可恢复工作区记忆调控：详细架构 v0.2

> **实现目标：在已有 HiAgent/H_ONCE 与真实反馈维护基础上，做出一套完整运行的 Host 方法，使工作记录真正参与材料选择、分支转换、行动安排、交付和中断续接。**
>
> **开发顺序：复用已经运行的方法底座 → 集成明确的创新候选 → 随开发做短距离行为检查 → 完整版本形成后再进行系统比较。**
>
> 本文是新增设计，不是已实现声明；不改写既有负结果。政策可以调整，机械运行结构应当清楚。配套执行规划见 [开发规划 v1.0](MILA_HOST_MEMORY_CONTROL_DEVELOPMENT_PLAN_v1.0_20260914.md)。

## 0. 决策摘要

首版采用 **一个 Host、同一模型、两个逻辑职责、一个串行工作区写入者**：

- **Controller（维护与工作安排）**：读取真实新反馈，修订短工作记录，保留候选入口，选择当前问题、需要展开的材料与下一种操作。
- **Actor（任务求解与执行意图）**：在该工作集里完成分析、读取、修改、验证或提出最终交付。它仍能质疑旧记录，不能把 Controller 当事实权威。

两种职责可以由同一个 Provider/model 的分离调用完成，不增加独立部署、后台认知服务或多 Agent 协商。Controller 不直接执行终端命令；Actor 的业务动作仍走已有执行合同。

完整首版包含：依据维护、实际工作集管理、候选与返回卡片、显式历史回读、有界交付复核、检查点与同循环恢复。它们共享一个循环，不各自建设一个 Agent。训练、自动提示优化、图记忆、多模型路由、后台并发维护不在首版。

“完整”是能力和运行关系完整，不是每条轨迹必须出现所有行为，不是每个组件先赢一次才能继续开发，也不是全部创新已成立。

## 1. 来源事实、继承边界与设计变化

### 1.1 最新结果是起点，不从最早的工作区草案重新开发

最新报告 R1 记载：

| 已有内容 | 本版处理 | 不能放大的结论 |
| --- | --- | --- |
| H_ONCE：闭合段首次展示时摘要，段内缓存，当前段与主动展开段保留详情 | 直接复用其分段、摘要缓存、来源身份与显式回读能力 | 6 次摘要、15 次复用不证明质量不降的净效率收益 |
| EvidenceHost：尚未维护的已完成动作/观察，在下一 Actor 前独立维护 | 沿用这个可靠的维护时点，扩展维护结果的控制用途 | 记录实际送入不等于正确解释或影响了行动 |
| EVIDENCE_1 与 INCREMENTAL 同调用数、同原生结果，前者多 215 tokens | 保留旧入口与结论；新方法用新标识，不能就地覆盖 | 不把该负结果改称“没有测试”，也不外推到完整新架构 |
| 原生 retrieve/分支返回未出现；没有迁移评分 | 针对缺少运行链的部分开发和检查 | 单元测试不冒充自然回读、跨任务收益或语义恢复 |
| 末版 adapter v0.2.1；报告记录 4497 PASS / 1 SKIP | 作为该版本历史工程结果，不重新从零接 Provider/Harbor | 本文未取得源码仓库，也未重跑这些测试 |

历史 R2 记录的“14 条共同 Host 轨迹仅一次工作区替换”解释了为什么不能继续仅依赖 Actor 顺手填写可选字段；R1 已通过独立维护取得了实际进展，两段历史不能混成同一种失败。[R1][R2]

报告中源码路径是仓库相对路径，不是本会话已挂载的源文件。实施时只核对相关入口与依赖，不重新扫描整套历史证据。

### 1.2 显式替代旧设计中的三项约束

| 旧取舍 | 本版取舍 | 原因 |
| --- | --- | --- |
| 所有维护必须与 Actor 同调用 | 允许独立 Controller，后续再研究融合 | 先保证方法运行，不假定基础模型已具备训练型多部分输出能力 |
| 记录更新完全取决于 Actor 可选字段 | Host 在真实反馈/恢复等生命周期提供维护调用；内容可保持不变 | 保证维护机会，不强制“制造变化” |
| State 主要作为追加文本 | Controller 同时产生工作安排与材料选择，装配器落实 | 使记录进入后续实际操作，而非只丰富措辞 |

旧报告、旧配置与旧政策保持原样。以上变化只适用于新增 Lab 方法；A0、Runtime 权限、Canonical 与公开 Schema 冻结状态不变。[R3]

## 2. 方法动机与创新候选

### 2.1 要解决的真实问题

第一应用仍是持续代码维护、工程排障与复杂研究协作：旧验证有成本、判断有适用范围、问题会被中断、后续反馈可能改变一部分而非全部依据。目标是减少重复解释、无信息增益的重试、错误沿用、无谓推翻和过早交付。

不是以“写了多少 State”“切了多少分支”为目标；不是模拟 ADHD，也不将人类支持方法的临床效果外推到模型。借鉴的是外部化目标、暂记念头而不立即行动、保留返回入口及协调探索与收敛的功能思想。

### 2.2 首版完整纳入的四个候选增量

| 候选 | 实际操作差异 | 预期行为 | 主要风险 |
| --- | --- | --- | --- |
| **N1 依据范围维护** | 不只摘要过程；新反馈后保留仍成立的部分，改写受影响的判断范围 | 少把局部测试/代码意图当整体完成；少因一处失败推翻全部工作 | 错误压缩、虚假证据标签、自信地维护错误 |
| **N2 联想—焦点—采信分离** | 联想先进入小卡片；当前工作集只展开被选内容；材料选择不等于认定其正确 | 容纳替代方向而不让全部候选占据当前输入 | 错误选材、反证遗漏、无谓维护 |
| **N3 可逆返回** | 暂放路线保留问题、原因、来源与返回起点；再次展开后重新判断采用关系 | 降低切换与重建成本，避免永久否定或自动恢复 | 旧路线绑架当前目标；卡片无限增长 |
| **N4 面向交付的控制衔接** | 下一步要解决的不确定性成为显式工作安排；最终草稿进入同一 Controller 作有界检查 | 让重要缺口真正影响调查或交付边界 | 变成过度测试、两模型角色循环自证 |

检查点恢复是 N3 的运行扩展；选择性维护首先通过新反馈去重、批处理与缓存实现，不独立建设“元认知调度器”。

**可逆的是记忆对当前行动的采用关系，不是事实真值，也不是权限。** “必要条件失效则停止沿用；阻塞消失只触发重新检查；当前依据充分且符合目标才重新采用”是首个候选政策，不是 Runtime 自动判定规则。

这些是本版的待验证设计。组成操作各有先行工作，不能把组合命名或字段设计直接当作已确认创新。

## 3. Baseline 与相关项目如何进入设计

| 项目 | 实际借鉴点 | 本版处理 |
| --- | --- | --- |
| HiAgent [S1] | 用子目标分块工作记忆，过去段摘要，当前段保留细节，需要时取回历史 | 首个方法 baseline；继续使用本地 H_ONCE，但标注缓存与终端移植差异，不冒充未经修改的原论文复现 |
| Mastra Observational Memory [S2] | 生命周期中的观察整理，以及整理内容与后续上下文、原文回读的连接 | 借维护机会与消费路径，不引入其框架依赖；先同步，不复制后台系统 |
| MemR³ [S3] | 证据—缺口状态驱动检索/反思/回答路由 | 借鉴“状态必须影响下一操作”；不照搬“gap 为空就安全完成”或穷尽后强制回答 |
| ACE [S4] | 从反馈提取经验，局部维护上下文条目 | 借条目级更新；不另建 Reflector/Curator，也不预设开源所有分支均已复现 |
| AgentFold [S5] | 主动上下文管理及训练获得的同响应控制能力 | 作为后续融合/训练参照；单调用高效化不是首版先决条件 |

本次核验的是公开论文/文档的相关机制；HiAgent 两个 GitHub raw 文件的重新读取未成功，不把上轮源码审阅冒充本轮又一次成功取证。实现可依据已留存版本与本地 R1 工作成果核对。

不能用“别人只做存储、MiLAi 做控制”作新颖性论证。候选差异应收敛到：**依据范围的可修正维护如何与实际工作集、返回操作、交付安排共同改变后续行为**。开发产物需要保留明确增量，而不是拼接五套项目。

## 4. 总体架构与职责

```text
                  用户目标 / 最新要求 / 真实工具反馈
                                │
                 ┌──────────────▼───────────────┐
                 │ 原 Host：绑定、事件、权限、预算 │
                 └──────────────┬───────────────┘
                                │ 新事件或生命周期事件
                 ┌──────────────▼───────────────┐
                 │ Controller（同模型独立调用）    │
                 │ 修订记录 + 当前问题 + 选材      │
                 │ ACT / RECALL / DELIVER        │
                 └──────────┬───────────┬───────┘
                            │           │ RECALL
                 ┌──────────▼──────┐    ▼
                 │ Workspace       │  既有来源/轨迹读取
                 │ 当前记录 / 卡片  │    │ 原文或明确缺失
                 │ Frame / 引用    │◄───┘
                 └──────────┬──────┘
                            ▼
                 ┌─────────────────┐
                 │ ContextAssembler│ ← 当前原始反馈不可被旧焦点屏蔽
                 │ 选择性实际呈现   │
                 └──────────┬──────┘
                            ▼
                 ┌─────────────────┐
                 │ Actor            │
                 │ 原生动作或交付提议│
                 └────┬────────┬───┘
                  动作│        │最终草稿
                      ▼        └──→ 有界 Controller 复核
                 原执行器            │
                      │          交付 / 继续工作
                      ▼
                 真实结果 → 事件记录 → 下一轮

             Workspace + 可持久来源 + 未处理观察位置
                               ↕
                 CheckpointPort（既有公开能力）
                               ↕
                  冷恢复进入同一个控制循环
```

这不是组件都要单独部署：Controller、Actor 和循环属于一个 Host；Workspace 与 Assembler 可以是两个小的本地模块；Sources、Provider、执行器和 Checkpoint 是既有能力的适配。

### 4.1 边界

- Host 控制层作语义判断；Runtime 仍只管身份、scope、权限、版本、CAS、幂等、生命周期与存取。
- Controller 没有独立的世界写入权限，不直接执行终端命令，不读取隐藏 verifier。
- Actor 获得工作安排，不获得额外授权。可以否定工作记录，必须看到当前原始要求与相关新反馈。
- 纯算法代码通过小 Protocol/回调使用来源、模型、执行器；公开 SDK 接线放在 `tools/` 边界，不让 Lab 核心直接 import Runtime。[R3]
- 不把网页、日志或 Note 的指令转成高优先级系统政策。派生记录仍是数据，即使由 Controller 写出也不提升可信级别。

## 5. 数据模型：少量技术结构，自由认知内容

### 5.1 可信外壳复用原 Host

任务/用户绑定、运行 ID、政策版本、事件编号、来源句柄映射、调用账务、未结业务操作、当前目标版本属于可信外壳，模型不能创设或覆盖。用户目标不只保存在模型摘要中。

分别记录：原事件是否存在、是否组装、是否实际发送、哪次维护接受了更新。它们都不等于模型已经理解。

### 5.2 三个主要工作对象

```text
WorkspaceSnapshot                         # Host 本地版本化载体
    working_note: str                     # 当前工作的简短依据与位置
    cards: map[HostHandle, MemoryCard]     # 有返回价值的线索或分支
    frame: FocusFrame                     # 下一操作的工作安排
    accepted_input_cursor                 # 上次接受更新所对应的事件位置
    revision / source dependencies        # Host 填写，不是事实正确性

MemoryCard
    text: str                             # 问题、依据、范围、暂缓/返回说明，自由表达
    source_refs: list[SourceHandle]        # 已公布来源，定位不是证明
    revision / provenance                 # Host 填写

FocusFrame
    question: str                         # 当前要解决什么，不强制必须两个假设
    intent: str                           # 下一步目的，不是强制执行的命令
    selected_refs: list[KnownHandle]       # 可含来源/卡片/段；类型由注册表解析
```

`cards` 不是语义知识图谱。首版不需要关系预测器、统一事实分数、依赖传播 DSL 或固定的 ACTIVE/PARKED/TRUE 枚举。当前“关注谁”由 Frame 表达；其余卡片保留入口。卡片正文可以明确“错误，已更正”，程序不据关键词自动改变权限或完成任务。

原则上只形成有后续使用价值的卡片；普通小任务可以只有 `working_note`，也可以不更新。若小快照整版替换更可靠，可先用整版替换；条目级更新用于避免每轮重写不变返回卡片，不以复杂 patch 语言为目标。

### 5.3 Controller 的最小输出合同

以下是拟议内部协议，不是已有 API 或新的公开 Runtime Schema：

```json
{
  "workspace_update": {
    "working_note": "当前依据与未决位置；允许为空或保持旧值",
    "put_cards": [
      {"handle": null, "text": "需要保留的新入口", "source_refs": ["src:17"]}
    ],
    "retire_cards": []
  },
  "frame": {
    "question": "当前问题",
    "intent": "下一步要取得什么进展",
    "selected_refs": ["src:17"]
  },
  "dispatch": {"kind": "ACT", "refs": [], "delivery": null}
}
```

允许 `workspace_update=null` 表示记录不变；Frame 可以更新而正文不变。`put_cards.handle=null` 请求 Host 分配句柄；已有句柄才可以替换。新建卡片当轮以工作更新呈现，Host 发布新句柄后可在后轮显式选择；首版不需要复杂的响应内引用解析。`retire_cards` 只让卡片退出正常目录，历史仍保留，不删除原始证据。

操作路由只有三个技术选项：

| 操作 | 程序实际做什么 | 不代表什么 |
| --- | --- | --- |
| ACT | 按 Frame 装配，调用 Actor | 不代表某假设已被证实，也不强迫某个命令 |
| RECALL | 读取已知合法历史/来源，结果回到当前循环 | 不代表当前证据更真实，不自动恢复旧行动 |
| DELIVER | 仅在已有最终草稿的交付复核阶段，输出原草稿或同轮修订文本 | 不代表 verifier PASS 或世界任务已完成 |

这是显式操作接口，不是“发散→聚焦→暂停→恢复”的固定认知状态机。若 Provider 对此格式不稳定，缩小内部载体或用现有结构化输出能力；不要挤坏原 Actor 业务参数，不靠猜测截断 JSON 派发动作。

### 5.4 更新接收与引用安全

Controller 基于某个不可变输入快照生成；Host 仅在该快照仍是当前有效输入版本时接受更新。首版串行、单写者，通常无需复杂竞争处理；若期间收到用户新指令，旧结果保留为过期产物，不覆盖新目标下的工作区。

机械检查仅验证类型、容量、已知句柄、scope、来源可披露性和版本绑定，不验证语义结论真假。未知句柄不能触发任意文件读取。失败时保留旧状态，原始新事件不消失。后续投影从事件记录读取尚需呈现的观察，而不是只依赖循环内临时的 `new_events` 变量，避免 RECALL 或复核绕转吞掉原反馈。

关注引用、披露依赖、业务回执分开：从焦点移除来源不等于删除派生内容的权限依赖；记录中说“完成”不替代执行结果。

## 6. 生命周期与完整运行算法

### 6.1 何时进行 Controller 调用

机械生命周期保证维护机会，但不强制模型修改内容：

| 事件 | 默认处理 |
| --- | --- |
| INIT：首次任务 | Controller 根据任务与初始资料形成工作安排；一个简单任务也可以直接安排回答 |
| 新用户要求/目标变化 | 在下一业务动作前重新控制；旧目标摘要不能覆盖新要求 |
| 一批已完成动作的真实反馈 | 在下一 Actor 前维护一次，可合并同一合法并行批的结果 |
| 请求 RECALL 并得到新展开内容 | 进入 Controller 更新/路由；按真实调用计费，这是相对旧 EvidenceHost 的显式扩展 |
| 只重新装配、同一事件被重放、没有新信息 | 复用已接受控制结果，不再次调用维护 |
| RESUME | 先机械核对待定业务操作和来源，再把恢复记录及未处理观察交给 Controller |
| FINAL_PROPOSAL | 按第 9 节进入有界交付复核，不读取隐藏评分 |

去重按事件身份、输入覆盖位置和政策版本，而不是按工具输出文字相同。两次不同的真实执行即使输出相同，也不能假装是同一事件；其条件与时间可能不同。

需要独立 Controller 的模式默认“每批新反馈一次”，不是先训练一个触发器决定要不要维护。首版完整运行后，才比较批处理、延迟维护和同调用融合。

### 6.2 运行伪代码

```text
state = load_or_initialize_workspace()
reconcile_pending_operations_if_resuming()

while existing_run_budget_allows():
    new_events = ingest_real_new_events()

    if control_needed(new_events, lifecycle_event):
        control_input = assemble_controller_input(
            trusted_goal, state, new_events, available_source_index,
            optional_final_proposal
        )
        proposal = call_same_model(role="controller", input=control_input)
        state, dispatch = mechanically_accept_or_explicitly_degrade(proposal)
    else:
        dispatch = reusable_control_decision()

    if dispatch.kind == RECALL:
        if recall_expansion_budget_available():
            observations = read_authorized_known_sources(dispatch.refs)
            append_visible_recall_results(observations)
            continue
        else:
            expose_recall_limit_to_actor_without_claiming_evidence_exhausted()
            dispatch = ACT

    if dispatch.kind == DELIVER:
        require_existing_final_proposal_and_review_phase()
        deliver_user_facing_text(dispatch.delivery)
        break

    actor_input = assemble_actual_workset(trusted_goal, state, new_events)
    actor_output = call_same_model(role="actor", input=actor_input)

    if actor_output is final_proposal:
        if bounded_delivery_review_available():
            enqueue_final_proposal(actor_output)
            continue
        deliver_with_known_scope_and_unresolved_items(actor_output)
        break

    if actor_output is source_recall:
        perform_normal_authorized_read_and_log_result()
        continue

    execute_original_business_action_once(actor_output)
    append_actual_result_or_unknown_operation_status()
    checkpoint_at_configured_safe_boundary_if_needed()
```

该伪代码表达职责顺序，不承诺任意 Host 具有这些函数名。实际实现复用原 Provider 的账务、超时、取消、未知请求停发与原动作合同。

### 6.3 动作和控制如何真正耦合

耦合不依赖“请关注”四个字：Controller 的 Frame 必须决定下一次 Actor 的工作提示与已展开来源；其余未选正文退出自动回放但可读取。记录中的未决条件通过 `intent` 成为一次可执行的调查目的，Actor 再选择具体合法工具。

Actor 不盲从 Frame：若原始新观察否定 Frame，可以选择另一行动，并留下简短可见说明。说明用于调试，不要求完整推理链，也不按是否“服从 Controller”评分。

每个动作记录它基于哪个 Workspace/Frame 版本发出。版本关联只证明运行联系；需要对照才能支持记录导致改善。

## 7. 依据维护、联想与可逆返回的实际实现

### 7.1 记录形成与修订

Controller 的默认政策要求保留“对后续选择重要的依据与范围”，而不是复制所有过程。代码描述、执行成功、针对某项要求的观察是不同证据层次；不必给它们建硬性枚举，但正文不得把其中一种伪装成另一种。

收到局部失败时，尝试定位受影响的判断，保留未受影响的约束；收到不同批次、版本或人群的材料时，允许拆分适用范围，而不是强制把新旧结论二选一。新来源不自动比旧来源可信，时间新旧也不是唯一裁决标准。

已证明错误则更正；尚无依据则保留不确定；旧限制仍成立则继续保持。必要验证不是无谓重复，未作某测试也不必然意味着结论不可接受，取决于任务与其他证据。

### 7.2 联想不抢占当前操作

Controller 或 Actor 可提出一个还没证实、但可能改变问题理解的线索。该线索进入卡片，默认只以简短目录项存在；不自动配发工具调用，不自动加入答案，不自动替换当前焦点。

随后 Controller 可以选择展开它，也可以保留当前路线。初步阅读、复现和了解接口都是正常 ACT，不强制每一步先有多个明确假设。

目录按来源/创建时点/机械分页提供，不通过隐藏任务答案排优先级。当前目标与新观察始终可见；原始材料中的指令不能借联想卡片变成控制政策。

### 7.3 暂挂与恢复不是业务回滚

暂挂操作的最小真实效果是：记录返回入口，使该路线的详细过程不再持续占据 Actor 输入。恢复操作是：选择其引用、取回原始上下文、收到当前变化、重新判断。

程序不运行“如果 blocker 字段为空则激活”的语义规则。未知新风险可以改变判断；曾经恢复的路线也可以再次暂停。控制状态可以非单调变化，不以状态表只前进为目标。

切换分支不恢复文件快照、不撤销已发生副作用。一个真实业务动作是否应回滚，仍是新的合法任务决策和执行，不属于认知返回的隐含效果。

### 7.4 防止局部修订造成全局遗忘

当前工作的 `working_note` 可完整替换；暂挂卡片按条目替换，未触及卡片保持不变。原始事件只追加，旧版卡片可在研究日志恢复。

这在程序层避免每次更新顺手删除全部返回入口，但不证明语义修订正确。卡片太多时先机械归档与分页，必要时在已有 Controller 中提出一次合并；不新建独立语义整理服务。被归档不是被证明无价值。

## 8. 工作集装配与容量

### 8.1 Controller 与 Actor 不共用一个未经区分的巨大输入

| 输入对象 | Controller | Actor |
| --- | --- | --- |
| 用户真实目标、最新要求、工具/权限合同 | 必须保留适用部分 | 必须保留适用部分 |
| 新的真实观察及必要完整消息组 | 必须可见，过长采用明确分页 | 必须可见，不能只看到维护后的结论 |
| 当前短记录、Frame | 读取并可修改 | 作为可错工作材料使用 |
| 返回卡片 | 当前相关正文 + 有界目录 | 当前选中正文 + 有界返回入口 |
| 历史段 | 当前段必要细节与缓存摘要；按需回读 | 已选择内容、近期完整交互；其余可恢复 |
| 最终草稿 | 仅交付复核阶段 | 正常生成 |
| 隐藏 verifier/gold/其他臂记录 | 禁止 | 禁止 |

角色与信任级别保持原 Host 规则。派生记录不放入可以覆盖用户要求的高优先级政策通道。

### 8.2 实际投影

```text
ActorInput = 真实任务与有效约束
           + 当前工作安排（可错）
           + 当前工作记录
           + 新观察 / 未结业务操作 / 协议必需消息
           + 当前段的必要完整交互
           + 按引用选择的历史正文
           + 有界可恢复目录
```

同一来源、版本、范围已经在当前输入时不重复追加。过去 `work_update` 的原始响应完整归档，但不逐版作为普通历史重发。否则“短工作区”会演变成叠加旧版本的长工作区。

当前段也可能太长：不能承诺它永远完整装入窗口。先用原有分页/范围读取；若需要段内折叠，由已有维护过程生成有出处的局部摘要，保留最新完整交互与原文入口。机械装配器不能自行编摘要。

### 8.3 参数与预算不是认知规律

最新报告的模型、窗口、thinking 等只作为历史兼容起点，执行前从实际 Provider profile 确认，不把旧值视为当前服务保证。[R1]

工作记录与卡片采用软长度目标，硬限制只来自真实载体和请求容量。可沿用现有能工作的容量起步，不恢复 512-token 业务交付门，不强迫每轮写固定数量的卡片。

```text
可选材料容量 = 实际输入容量
             - 当前受保护输入
             - 必要近期交互
             - 当前记录与目录
             - 格式安全余量
```

输出预算分为 Controller 和 Actor；二者分别明确预留，同一模型的两次调用分别计账。Actor 不再被迫与大工作区更新争抢一个 JSON 外壳。

受保护输入超限时，明确分页/分块、部分呈现与来源入口；无法安全分块则按原 Host 方式停止。不能悄悄删最新反证，不无限触发短摘要重试。

### 8.4 保留两种诊断投影，但不是两道门

正常候选使用实际 managed 工作集。需要解释贡献时可以使用共同投影，禁用政策特有选材；不要求共同投影先胜出。旧 `COMMON_CONTEXT` 的受控回放与自由运行中“相同来源权限”不同：各臂动作不同导致后续输入不同是正常处理结果。

## 9. 有界交付与避免无限反思

### 9.1 最终草稿是可复核提议，不是世界成功回执

Actor 产生最终草稿后，同一个 Controller 可接收：原用户要求、当前结果、必要原始证据、工作区及草稿。它选择：

- DELIVER：接受草稿，或在同次调用中改成有根据、有范围的交付文本；
- ACT：指出一个值得继续解决的具体问题，返回正常执行；
- RECALL：取回已有记录中确实有必要复核的内容，再作决定。

最终草稿是 Actor 的待交付产物，不是新增环境证据；不能用草稿中的断言反向证明工作已经完成。Controller 不能读取隐藏测试，不能把“自审通过”写成业务完成证明。证据缺口可能通过论证、已有观察或明确限制处理，不强制每次补测试。

### 9.2 预算规则

默认每个任务目标版本最多一轮专门交付复核；如复核建议继续，Actor 完成正常工作后再次提议交付，不因为草稿变了就自动再获得一次复核。允许在后续配置中改变这个有界数，但不能用“继续检查”无限重置。

RECALL 可设置少量连续展开机会（例如开发初值 2 次），这是防止控制回路独占预算的技术限制，不是“两个检索就一定够”。耗尽时把限制告知 Actor，允许有边界地继续/交付，不谎称证据已经穷尽。

用户要求立即停止、授权失效、状态不明或共同预算耗尽时，不为了完成内部复核继续调用。能交付多少据实说明，没有证据不伪造完成。

### 9.3 与“又增加一个 Judge”的区别

它不评分、不输出论文标签、不决定 verifier 真值；它是候选求解过程中的一段计算，影响用户交付，全部计入方法成本。其效益必须与同结构普通控制政策或关闭该环节的版本比较，不能被当作免费评价。

## 10. 检查点与恢复：同一算法的生命周期延伸

### 10.1 保存内容

检查点保存 Workspace、Frame、有效政策/载体版本、可持久来源定位、接受维护的事件位置、最后 Actor 呈现位置，以及未处理观察或其可靠指针。业务操作状态由既有执行记录持有，不让模型正文代管。

原则上先使被引用的归档内容可持久读取，再提交指向这些内容的检查点 head。没有可靠归档的临时文件路径不能当成可冷恢复来源；恢复所需资料不在本地持久范围时，应使用既有公开存储方式或明确标为不可恢复。

工作记录变化不等于每次落盘。明确中断、交接、上下文压缩边界或用户保存请求时保存；正常会话先用内存和已有事件日志。控制写入频率与突然崩溃后的重建窗口是取舍，不同时承诺零成本和任意时点无损。

### 10.2 公开能力接入

以 `CheckpointPort` 适配已有公开 Working State 接口，语义 payload 留在 Host 私有命名空间。读取当前 head、保留不属于插件的字段、按既有 CAS 完整替换；不修改 Canonical，不偷换 TTL/scope，不默认双写 Note。

旧设计 R3 记载过公开 GET/UPDATE、payload 大小及 TTL 规则，但本次没有读取对应当前源码；实现须核对实际 SDK/ADR 能力，再绑定可支持的容量、引用及有效期。不能按旧文档数值自动扩容量。[R3]

保存失败不重放业务动作。CAS 冲突不自动合并两份认知判断；单写者首版公开读取并交由现有冲突处理。payload 被限制披露不等于空状态，更不等于可以写空覆盖或从缓存绕过。

### 10.3 恢复步骤

```text
读取当前真实用户要求与授权
→ 公开读取 checkpoint
→ 核对来源仍可读取、版本与归档可用性
→ 用公开操作状态处理未结业务副作用
→ 收集未处理观察与当前新变化
→ Controller(RESUME)
→ 按同一 Frame/Actor 循环继续
```

冷字节恢复、工作位置恢复和语义任务恢复分别报告。只恢复进程内序列化文件是本地恢复，不冒称 MiLAi 公开持久化链；强制中断的开发演示不冒充原生 benchmark 自带的多会话成绩。

## 11. 失败、降级与完整成本

| 失败 | 本版行为 |
| --- | --- |
| Controller 格式/引用错误 | 不接收该次更新；保留真实观察；按配置显式回退到普通可运行路径或停止，不能静默换方法 |
| 记录语义错误 | 新观察继续可见，允许模型改正；不由程序篡改为正确记录 |
| 原动作非零退出 | 作为真实任务反馈处理，不自动等同环境崩溃 |
| 工具执行异常/未知副作用 | 沿既有接口停止/状态核验；区分正常 exit code 与异常载荷，保留 R1 中已有修复 |
| Controller 回读重复或无进展 | 按有界回读预算把控制交回 Actor，显示限制；不按语义关键词强切解法 |
| 模型用量或发送状态未知 | 沿原停发核账规则，不自动重试，不将未知记为零 |
| 工作区超容量 | 优先减目录与不变旧正文、原材料分页；不截掉否定条件，不重放已成功业务动作 |
| 来源权限变化 | 不披露受限原文及受限派生记录；不可用状态进入正常决策 |
| 检查点失败 | 当前会话可继续与“可冷恢复”承诺分开 |
| 候选反复拖累工作 | 关闭相应功能或方法，保留该轨迹的真实失败与回退记录 |

基础设施复用不等于其保证不存在。必要的身份/操作完整性/隔离检查保持；静态全仓哈希、全回归和历史审计不嵌入每一步模型决策。

### 11.1 先完整运行，再优化

优先使用已证实发生的 H_ONCE 缓存；同一新反馈批只维护一次；不变卡片不重写；全文按需展开；维护与交付复核共用一个 Controller 实现；不平行放置另一个 Summarizer、Reviewer、Router。

缓存只适用于相同来源字节/范围、同政策/模型配置且资格仍适用的计算；复用摘要不是复用当前结论为真。语义工作区不跨 trial 自动共享，避免污染比较。

后续再尝试事件批处理、控制/行动融合、较小维护模型或训练。每次优化既测成本也测质量，不把“少调用”本身当成功。

```text
N_total = N_actor + N_controller + N_summary + N_other_model_calls
C_total = 全部输入输出 + 工具/回读 + 保存恢复 + 失败与重试
```

RECALL 本地读取没有模型生成时只记读取成本；引发新的控制调用则另记生成。final review 已在 Controller 类别内，不能再重复记账。原生 verifier 和环境准备分列；开发代理成本与实验模型成本分列。

## 12. 方法配置与适配方式

保留旧入口，不创建大矩阵：

| 配置 | 用途 |
| --- | --- |
| H_ONCE（既有） | HiAgent 派生方法参照；按原合同运行 |
| INCREMENTAL（既有） | 既有同维护时机普通摘要；解释历史结果与维护增量 |
| WORKSPACE_SIMPLE（新增） | 使用新架构的全部同等能力与调度，政策为普通进度维护/正常复核，不限制其自然写条件或返回线索 |
| MILAI_RWC（新增） | 同新架构，使用本文候选记录形成、焦点与可逆返回政策 |

EVIDENCE_0/1 仍保留复现入口，但不自动作为推荐默认。开发时按问题选择一对比较，不每个增量都跑完四种模式。新增模式的名字属于 Lab 方法选择，不修改业务 Runtime 枚举。

新架构的普通控制对照必须拥有相同维护机会、选材/回读权限、交付机会和资源。与 H_ONCE 比较的是方法组合；与 WORKSPACE_SIMPLE 比较主要解释政策差异。原生普通 Host 参照在怀疑外壳拖累时少量使用，不能为了它重建另一条大入口。

跨环境适配只改变工具、观察、来源和持久化映射；核心政策不能按 task_id 选择正确答案。首版接现有 terminal/Harbor，另支持现有轨迹回放用于调试；不在首版同时接六个框架或 SaaS。

### 13.1 策略内容示意

**Controller 共同部分**：目标与来源边界；真实新反馈；记录可错；只输出可检查的工作产物；不把计划当结果；预算与原动作限制。

**候选增量部分**：

> 围绕当前工作维护有助于下一次选择的依据与适用范围。新反馈可能只改变局部，不要无故丢弃仍成立的工作；也不要把旧结论当权威。可以暂记新线索而不立即调查或采信。选择当前最值得推进的问题与材料，允许先了解问题。必要条件失效则停止沿用；暂停原因消失只是重新检查的理由。返回旧路线时重新看当前依据与目标。重要缺口应影响下一步安排或交付范围，不要求没有价值的反复检查。

**Actor 共同部分**：

> 工作安排和记录是可错的辅助材料。结合当前原始任务与观察选择合法动作；可以修改工作安排。原始结果未支持的内容不要写成已验证；最后给出任务允许的交付与限制。无需输出完整内部推理。需要旧细节时可以显式读取。

这只是实现起点，不冻结为永不可改的算法定义。不得加入已知 benchmark 检查名、任务专用步骤或隐藏答案。

## 14. 随开发的简单验证与创新判读

每加入一个能力，先让真实循环走过，再看是否有帮助。可控响应/回放用于验证接线，短真实任务用于观察模型自主使用，完整原生任务用于检查最终工作。三种证据分开。

| 设计动作 | 接线检查 | 小效果问题 |
| --- | --- | --- |
| 维护到 Frame | 新反馈进入一次维护，Frame 实际送入 Actor | 未决条件是否开始改变下一步，而非只增加措辞？ |
| 选材 | 选中原文实际出现，未选正文退出但可读 | 是否减少冗余而不遗漏必要依据？ |
| 卡片返回 | 保存、暂退、合法回读、原上下文重现 | 是否少重建，是否发生错误自动恢复？ |
| 交付复核 | 草稿→同 Controller→交付/继续，有界结束 | 是否减少无依据完成，又不无谓增加工作？ |
| 冷恢复 | 新 Host 公开读取/本地读取分开，接续未处理观察 | 是否保留工作位置并吸收新的要求？ |

不要让原生任务为了“覆盖架构”被强行安排暂停和恢复；没有机会就报告未观察。可用现有真实轨迹的受控检查点演示功能，但标为 replay/checkpoint diagnostic，不当完整原生成绩。

在可用的公开 benchmark 上用同一完整政策；开发可以修改，但迁移任务不逐题换政策。每次改动保留一句“观察→机制差异→预期行为”。一次打平不要求整条开发停工；反复无增量且没有新解释时删减或关闭，不靠扩大架构为旧失败辩护。

有效性、可用性、泛化性和创新性分别看：原生结果；完整成本与人工特修负担；同一政策跨非调试任务；与最接近方法的操作差异和必要拆解。共享候选记录给普通 review 打平，首先限制消费政策贡献，不抹掉记录形成成本与可能价值。

## 15. 完整首版的交付定义

完整首版应能从现有入口运行，Controller 有确定生命周期、真实反馈影响工作安排、装配器真实选材、历史可合法回读、草稿可有界处理、工作位置可保存并从同一循环恢复；每项能说明哪些已单测、已回放、已真实模型运行、尚未自然观察。

它不要求所有 benchmark 获胜，不以高更新率、词语命中或测试数为主成果。若公开持久化因实际接口缺口未完成，必须标为首版恢复能力未完整交付，而不是用本地 JSON 替代后声称全部完成；其他能力仍可独立保留和开发。

最后保留三份核心产物即可：可运行代码与政策；轻量配置/运行记录；一份设计差异和效果边界说明。原始输入输出沿现有日志存放，不再建设报告/审批平台。
