# MiLAi：基于实际效用与证据的设计改进建议 v2.0

## 执行摘要

**下一版不再增加“更谨慎”的认知要求，而是让经验少制造义务、让修订有明确依据、让正常 Agent 在不需要记忆时能够直接工作。**

当前已有完整 Lab 载体，且 DB/OS 正式比较已完成。需要改进的是当前 RB＋采用／修订方法，不是重新建立 RWC、OM 或持久化架构。独立 OM 保持其算法与比较身份，不因为它局部正确率较高，就把它叠在 RB 下方。

本建议保留三条主线：

1. **以增量任务价值选择经验。** 在已修复的实际输入过滤上，学习区分“语义相关”与“在当前任务、当前行动预算下值得采用”，允许检索有候选但选择不注入。
2. **以可核对反馈修订经验。** 区分当前解释、当前采用关系、长期经验内容；一次成功、失败或空返回，不直接升级为永久规则。
3. **以完整上下文和业务事实维持可用性。** 旅行先修事实取得与约束使用，OM 按完整请求容量整理，运行波动通过可行的服务核对与重复配对处理。

本轮外部检索的主要参考是 MemRL、ExpeL、CRITIC、CHIME、Mastra OM 与 vLLM 官方文档。**优先新增的方法参照只选 MemRL；其他工作先借鉴具体操作，不部署为一串新 Agent。**所有新方法仍须与 Native 比较，不能只赢过当前较弱的 RB 就认定有净价值。

以下用 [E] 标识附件证据、[S] 标识外部来源；未标为事实的算法、阈值与安排均为设计提案，不是已实现或已验证结果。文档没有重开旧额度，也未改变报告时点仍在运行的旅行批次。

## 1. 从最新结果出发，不重复修已经修好的问题

### 1.1 当前正式结果

| 方法 | DB 固定库 | DB 在线 | OS 固定库 | OS 在线 |
|---|---:|---:|---:|---:|
| Native | 85% | 79% | 68% | 74% |
| OM | 89% | 87% | 76% | 70% |
| RB | 79% | 81% | 71% | 71% |
| MiLAi | 80% | 80% | 71% | 66% |

每列同批 100 题，四方法共 1,600 次执行均已有评分。这里不是 1,600 个独立任务，固定库与在线设置也不能简单混成一个样本。MiLAi 四列测试 tokens 是 Native 的 2.80、2.84、2.64、2.61 倍；建库另计。OS 在线的 −8 个百分点及报告区间需要保留，但本次没有原始配对数据，不能重新核算区间或估计因果。[E1]

正式旅行在报告时点未形成四方法完整比较：Native 30 组、RB 24 组、MiLAi 4 组；OM 已结束的 6 组均因容量中断，另有 3 个建库组同类失败。本文不推测此后的进度。[E1]

### 1.2 新旧诊断必须分开

| 最新事实 | 当前应该做什么 | 不应该继续说什么 |
|---|---|---|
| 严格只展示所选经验已修复；24 题均 13 题正确，tokens −14.1%，3 回收/3 回退 | 保留修复，研究选择本身的有效性 | “selected_refs 仍完全不起作用” |
| 正式在线发生 7 次旧文修改，后续使用待核对 | 分析修改依据、版本消费与后续效果 | “自然修订始终为零” |
| 额外样本检查仍可耗尽原生业务轮数 | 改经验的行动后果及步骤安排 | “再加一次预算提醒即可解决” |
| 元数据重复修复将一请求 25,808 降到 7,127 tokens，旅行仍超窗 | 检查完整请求各组成、整理触发和失败后继续路径 | “重复元数据仍是唯一容量问题” |
| 相同首轮请求 100 对中 82 对文本不同，最终 85/79 题 | 记录服务配置并做有界重复配对 | “temperature=0 保证确定性”或“全部差异都是噪声” |

上述改善是有效工程或局部成本成果，当前整体方法的负结果也有效。不能用内部某机制不够完善取消全部失败，也不能用修改次数确认创新。[E1]

## 2. 外部研究怎样直接帮助开发

### 2.1 参考选择与使用边界

| 参考 | 实际可借鉴的操作 | MiLAi 的用途 | 不照搬的部分 |
|---|---|---|---|
| **MemRL** | 先相似性召回，再按反馈学习的记忆效用排序；不改 LLM 权重 | 新增最直接的效用选择基线；公开仓库列有 LLB 的 DB/OS 入口 | 不把最终成功同时当作每条经验的因果贡献或事实正确性 |
| **ExpeL** | 用成功/失败经验对照提炼并编辑洞见，保留可参考的成功经历 | 改善“总要检查”一类过度概括；把具体情境与一般规则分开 | 不为复制整套经验采集而增加许多在线重试 |
| **CRITIC** | 以外部工具反馈支持对输出的修正 | 修订必须有检查对象和反馈；复用现有业务查询与测试 | 不每步增加独立 Reviewer，不使用隐藏答案 |
| **CHIME** | 先判断结果涉及计划、执行或其他因素，再更新相应记忆 | 直接近邻，提醒“做错了就惩罚所有记忆”不合理 | 归因仍由模型作出，不视为因果真值；不先引入两套 Planner/Executor 库 |
| **Mastra OM** | 观察与归并、近期原文、来源恢复，归并替换当前日志 | 参考长历史生命周期与容量处理 | 不照搬另一模型窗口的阈值，也不叠加在当前 RB 热路径 |
| **vLLM 官方可重复性支持** | batch invariance 与其硬件/模型限制 | 为相同请求不同响应提供一条可检查的工程路径 | 不未经核对就改共享服务，不保证当前精确模型组合已支持 |

MemRL 的论文使用两阶段检索及基于环境 reward 的效用更新；仓库 README 明确列出 `memrl/run/llb_rl_runner.py`、DB/OS 配置和兼容服务入口。[S1][S2] 本次未成功取得该核心 runner 的完整正文，因此没有签发源码复现或本地可运行结论。

ExpeL 与 CRITIC 分别提供了“从不同实际经历形成规则”和“以外部反馈支持纠错”的设计依据。[S3][S4][S5] 自我反思不是不可用，但它不能因为由同一个模型重复说了一次，就自动获得更强证据。早期内在自纠研究的结果也只适用于其研究设置，不应外推成所有模型永远不能自纠。[S6]

CHIME 是 2026-09-02 的直接近邻。论文的归因主要是冻结模型的结构化反思，不是反事实实验；其设计可参考，但其自报归因不能替代 MiLAi 的独立使用检查。[S7]

### 2.2 不再进行 baseline 替换循环

Native、当前 RB、本地 OM 和当前 MiLAi 版本全部保留。优先只新增 **MemRL 的忠实实现或明确标注的机制移植**。

共用环境、来源权限和账务，不强制把 MemRL 的自身检索与更新过程改成 RWC 的控制路由。尤其先确认在线 reward 在原 benchmark 和当前实验合同中是否允许提供给方法；若原设置只允许隐藏 evaluator 离线评分，就不能偷偷把该分数给 MemRL 或 MiLAi。可另列公开结果反馈设置，或先评价支持阶段学得效用的冻结版；不冒称原生在线算法完全复现。

OM 的质量对照位置继续保留，但昂贵的全方法全矩阵不是每次开发必需。短 DB/OS 的首要参照是 Native、当前 RB/候选及新效用选择；长历史条件再纳入 OM。

## 3. 方法目标：从“加入经验”转向“选择记忆如何影响行动”

### 3.1 三种内容不要继续混在同一种强指令里

**原始经历**：当时收到什么、执行什么、返回什么，保持来源和时间。

**条件性经验**：在什么情境中，哪种做法可能有效，已有证据覆盖什么范围。

**当前工作判断**：本任务现在采纳哪一部分、仍缺什么、下一步可能做什么。

它们可以继续使用现有卡片与自由文本，不需要三个新数据库或 Runtime 语义类型。差别在形成与消费：观察不自动成为规则，规则不自动成为当前命令，当前不采用不等于删除规则。

### 3.2 统领算法

```text
原生任务、当前真实证据和行动机会
    → 检索候选经验（保留既有检索器）
    → 选择：不注入 / 适用经验的紧凑部分 / 有目的地取回细节
    → 实际输入投影（继承已修复选择合同）
    → Actor 使用原业务工具推进任务
    → 真实反馈
         ├─ 先修正当前解释或采用关系
         └─ 有依据且有后续价值时，提议长期经验新版本
    → 更新后的有效视图在后续任务中使用
```

这不是新增每步“先判断—再批准—再复核”调用链。第一版继续使用已有采用与任务后提炼的位置，替换其判断目标；后续再将低成本选择从昂贵采用调用中下移或蒸馏。

Native-first 表示保留正常求解路径、允许无记忆决策，并非“先让 Native 完整失败，再运行候选”。后者会增加前置尝试、改变预算和可见反馈，若研究必须单列。

## 4. 开发增量 A：带拒绝选项的效用选择

### 4.1 相似性回答不了是否值得采用

MemRL 使“相似召回”与“效用排序”分开，正好对应当前“过滤已经生效却没有准确率净增量”的问题。[S1] 但其效用估计并不天然等于相对 Native 的增量收益，因此 MiLAi 的扩展要保留无经验参照。

选择对象是实际要呈现的**一个经验组合或片段包**，而不是先给每张卡片虚构独立贡献。不同条目可能互补或相互干扰，不能默认逐项收益可加。

### 4.2 目标函数只是设计目标，不是假装已有准确预测器

令 x 为当前任务/合法观察/剩余行动机会，a 为记忆呈现方案，a=∅ 为不注入可选经验。希望学习：

\[
\Delta U(x,a)=\mathbb E[Y_a-Y_\varnothing\mid x]
-\lambda_t\,\mathbb E[\Delta T\mid x,a]
-\lambda_b\,\mathbb E[\Delta B\mid x,a]
-\lambda_l\,\mathbb E[\Delta L\mid x,a].
\]

Y 为任务质量，T 为额外文本计算，B 为额外业务行动，L 为延迟。权重是用途相关配置，不是一个通用“创新分数”；公开结果仍分别报告各量。业务上限继续按原环境执行，不能用目标函数覆盖硬约束。

**当前没有这样的预测器。**初版可以在现有采用调用中先表达“这条经验解决什么已存在的缺口、会替代什么工作、是否引入新的必要步骤”；它是可错估计，需要由开发数据校准，不是提交审批。

### 4.3 可实现的两步版本

**A1：不训练权重的实用版本。**复用已有检索，输入紧凑候选；采用器可以明确选择 ∅，或者选有限经验及适用说明。默认不呈现被拒绝建议。对于短任务，经验若只是增加一串无特定目标的验证要求，应降低采用价值；并非按 DB/OS 名称一刀切禁用。

**A2：小型效用选择器。**在开发/支持任务上收集有限、独立环境的同起点经验/无经验对照，用任务与经验嵌入、明确的环境预算、来源质量类别、呈现长度等特征，学习组合是否帮助及其成本。可从简单校准回归/检索邻居效用开始，不先训练新 LLM 或建立完整 RL 服务。

特征不能包含测试标签、task ID、后来答案、候选最终是否成功。不能用当前 100 题反复调参数再称这些题是独立验证。没有配对动作分配概率与覆盖的旧日志，不能直接当作无偏离线策略评价数据。

冷启动不能简单将所有新经验判零后永不使用。在支持/开发阶段保留少量前瞻安排的探索，或回退为已知的相似检索参考；正式确认不在看到分数后调阈值。具体探索量服从独立资源安排，不是生产任务随意试错。

### 4.4 对收益信用保持克制

任务成功时，未被选中、未被提供、没有机会发挥的经验不获得信用。已提供也不等于因果有用；优先记录“暴露与结果”，有配对证据后才称增量。

同一次调用的模型置信度只能作为提议强度，不能作为客观可信概率。若采用 CHIME 式归因作为弱标签，应与可核对来源并列，定期在开发分叉中检验，不能直接升级为事实。[S7]

### 4.5 与原始创新方向的联系

低门槛联想保留在候选池；主要工作集根据当前价值选择；不注入是可逆暂停而非永久删除。需要时可返回历史，但过去“高效”不赋予当下行动权限。创新应落在条件效用及其与实际决策的联系，而不是把一个 Q 分数改名为注意力。

## 5. 开发增量 B：经验应该替代重建，而不是增加检查清单

### 5.1 从实际案例抽象通用规则

DB 223 多做一次样本检查后越过三轮额度，是步骤分配问题；不能单靠少一次维护调用解决。[E1]

建议将采用说明由“请遵守这些过去总结”改为：

> 这些经历仅作为条件性参考。当前材料已经给出哪些必要依据？还有哪个未知会改变操作或答案？所选经验能够减少哪一项重复重建，或者避免哪一个具体错误？

这是正常 Actor/采用器可用的政策，不要求每次填三个字段，不引入检查价值 Reviewer。

### 5.2 经验表示的改变

不是将“写入前先看 schema、看全部数据、再做验证”缩短为一个更短的强制句子，而是保留其条件。例如：

```text
过去因字段定义未明确而选择了错误列；在类似不确定情况下应先核对字段。
本记录没有证明：字段和条件已明确时仍要扫描全部数据。
```

示例只说明表达原则，不是给实际任务注入正确 SQL 或固定解法。实际记录必须由支持/开发轨迹中的材料形成。

同时保留具体成功经历作为例子，与一般建议分开；成功经历是参考，不自动变成可执行宏，不盲目复制标识符、环境状态或数据。

ExpeL 的成功/失败对照和洞见编辑，为这种形成方式提供方法参照。[S3][S4] 不将单条模型反思当成同等强度的经历证据。

### 5.3 最小行动原则不是最少调用原则

有目的的查询、回归验证和必要权限确认仍然合理。尤其真实写入的风险不能为了 benchmark 得分而削弱。

如果当前事实已足以做正确选择，额外泛查没有价值；如果需要餐厅实体、OS 路径状态或数据库结构而尚未知晓，真实查询可能不可省。两个场景并不矛盾。

“不确定”不能总被翻译成“再查一次”；应先判断不确定的是用户目标、语义范围、外部事实还是执行结果。任务自身含全部依据时，重新对照需求可能足够；缺外部事实时，则必须从合法来源取得或明确说明缺口。

## 6. 开发增量 C：有证据的修订、可撤回的当前有效版本

### 6.1 三个修订对象

| 对象 | 示例 | 处理位置 |
|---|---|---|
| 当前任务解释 | 将记录级平均误解成分组后平均 | 当前工作状态与 Actor，不必修改经验库 |
| 当前采用关系 | 经验为真，但当前条件不适用 | 采用/投影；可以暂退，不删除 |
| 长期经验内容 | 原“总要验证”建议被实际反例证明过宽 | 既有更新与版本接口，保留原文与依据 |

不再把任何失败都路由成经验修改，也不让任何“不适用”都产生永久补丁。

### 6.2 空返回不等于失败，也不等于完整成功

DB 372 从 `[]` 推出“更新后总要查询验证”，缺少支撑该普遍化的证据。[E1]

下一版首先共同明确原业务工具的返回含义：返回的是数据行、受影响行数、确认状态还是错误？空列表究竟代表什么，须以工具合同和实际实现为准。这里补的是正常接口说明，所有臂共享，不是隐藏业务答案。

若现有环境不提供受影响行数，不应为了候选加入额外结果后继续声称原生同条件；可以保留未知，或使用原有合法查询。更不能把运行器的隐藏成功标签塞进修订输入。

### 6.3 用已有维护调用生成有依据的变更提议

提议至少能定位：旧经验版本、被修订的主张或范围、支持变更的合法来源。具体解释继续使用短文本；Host 检查引用和版本，不认证蕴含关系。

- 直接且明确的反证，可以立即在当前视图中停止沿用错误内容，并产生限定范围的新版本。
- 只有模型猜测或结果歧义时，保留观察/疑问，不自动扩展为全局规则。
- 当前条件不适用时，优先改变采用关系，不改坏原条件下的经验。
- 新版需要在后续相关任务真正呈现后，才能讨论修订收益；未使用不是失败率 0，也不是成功。

可以在现有版本记录上保留“当前生效版本”和“尚待支撑的变更提议”，不用新增多级审批服务。内容修订后不无条件继承旧版效用，因为决策对象已经改变。

### 6.4 借鉴外部反馈，但保持范围

CRITIC 用工具交互支持输出修正。[S5] 在 MiLAi 中应优先利用已产生的真实结果；需要新增检查时，说明其要验证的具体主张并计入业务机会。不能把它复制为每步额外审查。

一次修订的正确性与它是否值得保存是两个问题。反证可能只支持“这次情况例外”，不支持“所有环境都应该增加操作”。ExpeL 的对照经验可以帮助发现这种范围差异，但仍不能替代后续泛化检查。[S3]

### 6.5 七次修改的最有价值读法

以已有日志制作七行简表即可：

```text
旧主张 → 当时可见反馈 → 实际修改 → 是否缩小或扩大范围
→ 后续是否选中该 revision → 是否真的进入请求 → 下一步/任务结果
```

不要为此重建审计平台。若修改从未再使用，则现有整体分差不能由它解释。若已使用后增加了不必要检查，就是需要保留的修订危害证据，不因“修改获准”而免责。

## 7. 旅行专线：先让计划依赖事实，再研究记忆贡献

### 7.1 不把所有旅行失败算成 Memory failure

31 人验证中 29 人未查询业务工具，且出现凭空选餐厅的案例；该小验证提示不一致，不能估计严格的方法效应。[E1] 另一项 MemoryArena 匹配研究同样报告其比较系统在旅行整组成功率上均为零，且主动说明方法和样本限制。[S11] 这提示旅行底层任务不简单，但不能替本地失败提供现成因果解释。

本次读取的官方 `run_travel.py` 与示例展示了环境、Agent、记忆包装和前序计划的衔接，`example_travel_planner.py` 标明 `agent.act` 内包含完整 ReAct 循环。[S9] 但本次未取得 `agent/travel_planner.py` 的完整正文，不能声称核对完其解析、提示和所有查询逻辑。

### 7.2 优先修一个共同求解循环

目标：当前要求/前序实际选择 → 识别缺少的外部事实 → 用合法业务工具取得候选 → 按已知约束选择 → 形成计划。

先对照本地与上游的同一首个请求及一次正常工具交互：工具是否实际可见、参数和输出格式是否匹配、最终格式是否意外压制动作、内外轮数如何计数。只补有证据的接线差异，不再设计一个旅行专属大型 Agent。

对于实体选择，优先使用已提供的真实计划或合法工具返回中的名称/标识与属性。存在于返回集合只能证明来源存在，不能证明预算、时间或跨人约束全部成立。不得读取隐藏 evaluator 来筛出唯一标准实体。

给 Native、RB、OM、MiLAi 同样的可用工具、共同求解说明和当阶段应有历史；前序计划使用各臂真实产出，不由人工修好。若改了共同 scaffold，新版本另报，不能归功于记忆特殊政策。

### 7.3 可行的可用性诊断，而不是强迫调用工具

把失败区分为：本阶段没有收到该有的历史；当前实体或属性没有来源；有来源但条件理解错；各局部条件满足但联合约束失败；计划格式/交付失败。

已有事实足够时可以不查。主要观察“关键选择是否有可用依据”，不是查询次数是否增加。需要外部事实而没有取得时，不能靠补一个更漂亮的最终复核解决。

约束求解器或公开事实校验工具可作为未来共同 scaffold 能力；若增加就给所有方法，并单列工具增强结果。它不是本轮优先要求，更不能包装成 Memory 独立贡献。

## 8. OM 容量：按整个请求做整理，而不是只看单个阈值

### 8.1 保留现有修复，增加统一容量关系

当前元数据去重已有效，但仍超窗。[E1] 历史使用说明里的 12k/16k 是当时模型与方法配置，不是所有调用都能装下的保证。[E2]

对每种角色 r，实际发送前应满足：

\[
T_{\mathrm{instruction},r}+T_{\mathrm{required},r}
+T_{\mathrm{recent},r}+T_{\mathrm{memory},r}
+T_{\mathrm{refs},r}+T_{\mathrm{output},r}+\epsilon_r\le W_r.
\]

必须计入完整 wire、聊天模板、工具 schema 和实际输出预留。阈值用于决定何时整理，不是硬容量上限；Actor 能装下也不代表 Observer/Reflector 能装下。

### 8.2 有界 observe-and-shrink

达到预计安全余量时，只取能容纳的一批尚未观察原页；成功后更新精确覆盖位置并替换当前视图。日志归并后必须检查实际长度和压缩是否取得进展；没有缩短时不要无限调用，也不要追加新日志而让旧全文继续常驻。

旧来源正文和完整映射保留在宿主来源注册表，普通输入只给必要引用。没有呈现、没有成功整理的页面不能被标记成已消费。当前目标、未结操作与原生必须保留的内容不能被旧焦点静默丢弃。

Mastra 官方将归并作为当前观察日志的替换，并承认阈值不是硬上限；还记录了模型归并不够短时需要有界结束的问题。[S8] 这里应借生命周期原则，不直接搬其大窗口默认参数或后台系统。

### 8.3 不用更强模型掩盖算法差异

更大窗口或更强 Observer 是可用性选项，但应作为单独配置比较，并报告成本。当前单模型比较不静默换模型。缓存能节省费用要有 Provider 实际命中与计费证据；少重发文字只先称输入减少。

## 9. 运行波动：有技术路径，但不重开无边界的推理基础设施项目

vLLM 官方说明默认不保证可重复性，在线服务可使用 batch invariance；当前文档将其列为 beta，并限制硬件和已验证模型组合。[S10] Thinking Machines 的技术分析讨论了批处理变化导致浮点归约路径变化的可能机制。[S12] 这些给出候选解释，不证明本地 82/100 文本差异已经定位到该原因。

优先从现有记录确认模型版本、实际 seed/采样参数、thinking、聊天模板、vLLM 版本、量化、并行和请求格式是否一致。按已有授权使用可见配置，不操作共享 GPU 或重启服务。

若开展隔离服务诊断，先确认当前精确 Qwen3.6-35B-A3B-FP8 与实际内核受支持，再考虑 `VLLM_BATCH_INVARIANT=1`。当前官方 tested list 中存在部分 Qwen3/MoE/FP8 组合，并不等于已覆盖本地这一精确模型。新设置先小范围检查，再统一用于后续比较，不把结果回填旧分数。

如果暂时不能改服务，研究仍可继续：同一来源/任务配对，轮换臂顺序，预设少量重复，报告分歧和区间；选择政策的调参与评估任务分开。重复次数不增加任务多样性。即便同一 seed，也不假定不同长度请求经历相同随机路径。

5 条在线流不足以支撑很强的跨流稳定性主张；不能对 100 个流内样本做独立样本假设。下一轮优先增加独立流/任务结构覆盖，而非只增加同题重跑。

## 10. 总体架构与最小实现形式

```text
                       当前目标与真实新反馈
                                 |
                     原生 Host / Actor 执行主干
                                 |
                    可选的记忆影响选择（含 ∅）
                      /                        \
               不注入额外经验              条件性经验包
                      \                        /
                       实际工作输入与业务动作
                                 |
                             真实结果
                      /                        \
              当前理解/采用修正          既有任务后经验整理
                                               |
                                   证据关联的版本提议与效用记录
                                               |
                                     后续任务再次选择与使用

    横向共同能力：完整容量预算、来源分页、日志、隔离、交付、显式交接
    独立参考算法：Native / RB / OM / MemRL（拟新增）
```

不新增四个认知服务。可在当前采用器、经验提炼器和投影器增加三个逻辑接口；以下是设计名称，不声称仓库已有这些 API：

```python
select_experience(task_view, candidates, utility_state, resource_view) -> selection
propose_revision(used_versions, current_evidence, prior_experience) -> optional_delta
project_context(required_view, selected_experience, source_window, role_limit) -> request
```

效用信息和来源/版本挂在 Host 内部侧记录上，语义仍由模型处理。公开 Working State、Canonical、权限和 CAS 不增加新语义职责。

空库、无合适候选、无有用更新时应低负担继续；但“无状态可依赖”不能用来假装已有精确历史。任务要求的前序事实与可选策略记忆分开：拒绝一条旧策略，不删除用户当前约束或同组前序计划。

已有 RWC/OM/Adaptive 配置作为历史方法保留；当前 RB 增量用独立新版本，避免共享工具改动悄悄覆盖已评分方法。

## 11. 开发与实验：从一开始包含跨域验证，不再只调几个失败案例

### 11.1 开发切片

| 切片 | 主要交付 | 伴随验证 | 不扩展什么 |
|---|---|---|---|
| D0：证据整理 | 七次修订的后续使用表；角色成本；部分分歧轨迹；本地与上游差异 | 只读已有记录 | 不重跑 1,600 项，不哈希全仓历史 |
| D1：效用选择 | MemRL 算法核对与最小接入；当前采用器的 ∅ 和条件效用版本 | 支持/开发任务上的真实选择与有限配对 | 不同时部署全部新记忆项目 |
| D2：经验形成与修订 | 情境—经历—范围表达；反馈关联更新；新版生效视图 | 旧版/新版/不修订的短续接与真实后续使用 | 不额外建立每步 Judge |
| D3：共同可用性 | 旅行真实工具循环、OM 全请求容量；服务波动的有限核对 | 已失败请求/任务的局部回归，版本单列 | 不偷改原生 verifier、不默认升级共享服务 |
| D4：固定版跨域比较 | DB、OS 与完整旅行组；必要的第二模型 | 新方法与 Native/强方法对照，质量和全成本 | 不把已调题重新包装成未暴露确认 |

D1/D2 可以共同开发，也可让 D3 并行。完整迁移是预设交付，不以某道开发题先获胜为条件；底层不可用时如实交付覆盖不足，不用另一个机械单测替代。

### 11.2 最小但足够有判别力的对照

**主比较**：Native、已冻结的当前 MiLAi、选定新候选；引入 MemRL 时增加完整方法参照。RB、OM 在各自相关问题中保留，不要求每个局部测试都跑全体。

**形成对照**：同一合法支持经历形成普通规则与条件性经验，共同消费；测记录形成而非 Actor 提示。

**选择对照**：相同库和检索候选，比较当前语义采用与新效用选择，保留不注入分支；真实投影一致。

**修订对照**：同一旧经验、同一时点反馈之后，新版、旧版/只追加各自在独立后续环境工作；不把被修订任务先前的正确率归因于其后发生的修改。

**共同求解政策对照**：预算与事实取得的改善也给 Native。Native 同样提升时，先承认一般求解收益；不能只给候选更强工具使用提示。

不一次建设完整因子矩阵。先用最能区分当前解释的对照，再把确定版本带到另一任务族；所有实际成本保留。

### 11.3 将记忆直接需要与一般技能迁移分开

DB/OS 可以验证相似任务的经验迁移与负迁移；旅行完整组可验证前序选择/约束的续接。实例级历史事实与过程建议必须分开读写，否则拒绝过程建议时可能连必需历史都被丢掉。

固定库冻结共享内容和效用状态，测试只允许本任务临时工作记录。在线任务流按约定反馈在任务结束后更新；若加入原生结果 reward，就明确其可见时点和所有方法的一致权限。两类结果分开。

选任务按预定义来源/结构分组，不按候选获胜筛选；新政策先在开发数据上选择，后续使用未参与该版修改的任务或清楚标注的迁移集合。同域重跑、改名、换 seed 不能代替跨结构覆盖。

DB、OS 已经都被评测，不自动等于再无可用确认来源；具体以数据暴露记录决定。缺少真正未调试来源时说明局限，不臆造新的“未打开集”。

### 11.4 统计与资源应避免新的机械目标

报告任务正确率/组成功率、回收与回退、业务轮数、全部模型 tokens、延迟及支持库形成/索引成本。不同 benchmark 不强行平均成一个分数。

固定任务按任务/模板配对，在线按独立流及顺序分析，旅行按完整组。采用适合相关性的区间与少量预先固定重复；没有逐题数据时不重算或承诺显著性。

质量—成本比较首先看原生业务约束下能否完成；另设共同宽预算敏感性条件可以解释截断，但不代替原生结果。不能给新方法免费维护，也不能只比较便宜成功样本。

不在缺少逐角色账单时再拍一个巨大总生成数。先用现有日志估计成本，分配开发、主域迁移、旅行与第二模型各自预算。资源不足应缩小主张，不将泛化无限后移或用更多单元测试充数。

## 12. 创新主张怎样收敛

### 12.1 可保留的两个主候选

**候选 I：行动机会约束下的可拒绝经验迁移。**不同于只按相似度或无条件 top-k，将不采用作为真实决策，比较经验带来的任务增量与业务行动、计算和延迟成本。

**候选 II：证据限定的经验再整理。**使用中发现冲突时，修正恰当对象和范围；修订依据与效用信用分开，允许新版本被重新评价或撤回。

联想与采信分离、可逆暂停、稳定性—可塑性继续作为贯穿规则。选择性控制现在是这两个候选的组成，不新建一个元控制器。

### 12.2 新颖性限制

MemRL 已覆盖效用检索，ExpeL 已覆盖经验对照和洞见编辑，CHIME 已覆盖先归因再更新，CRITIC 已覆盖工具支持纠错。[S1][S3][S5][S7] 因此不能把其中任意操作本身称为首创。

潜在差异应具体到：**在有限业务机会下，以无经验行为为参照选择影响；用明确证据限定修订范围，并检验修订是否改善后续采用而非扩大检查义务。**这是一项候选组合及其可分解操作，不是本次检索已经证明的文献空白。

“工具成功”“revision 增加”“少发 token”“写了适用范围”都是中间现象。正收益须由实际任务及成本支持；独立贡献须由近邻比较与必要消融支持。

## 13. 本轮不做什么

不再次修已生效的过滤合同；不为了补丁数强迫修订；不追加“更仔细、更充分验证”提示；不把所有失败都归因于记忆；不把两份模型意见当独立证据；不把 OM 完整套到 RB 热路径；不为精确复现服务建新平台；不在正式批次中途换配置；不以容器/接口/单元测试数量作为创新进展。

可以借鉴成熟算法解决可用性，设计保持开放。若最终条件性经验＋普通 Actor 就足够，删除多余 Controller；若只有一般行动政策有用，按一般 Agent 改进报告；若新选择只是恢复 Native 而仍明显更贵，称为负迁移缓解，不称综合突破。
