# MiLAi 情境化用户记忆开发 Goal

> 历史版本：本文的 Product 优先实施顺序已被 [Lab 优先开发 Goal v2.0](../MILA_CONTEXTUAL_USER_MEMORY_DEVELOPMENT_GOAL_v2.0_20260923.md)替代。以下保留原 v1.2 内容，不作为本轮执行指令；归档仅调整状态、来源路径和相对链接。

**目标：交付一条易用、可修改、可续接的记忆路径：Host 记下理解、保留实际来源、修改已有记录，并在后续任务取得正确版本。优先完成代码与真实接口联调。**

本 Goal 从[开发计划 v1.2](../../../MiLAi-Product/docs/cleanup/MILA_CONTEXTUAL_USER_MEMORY_DEVELOPMENT_PLAN_v1.2_20260923.md)抽取首版实施范围，按用户最新要求简化开发过程。原计划保留架构背景和后续研究方向；本 Goal 决定本轮开发顺序与完成条件。研究比较、外部基线和大规模评测不作为开发前置条件。

本文内容版本为 v1.2，保留原文件名；§5.1–§5.5 保留多 Agent 分工，本次按用户指定统一采用 Sol xhigh 常规档、Luna max 窄任务档、Astra xhigh 疑难档。尚未开始本 Goal 的代码实现或 MiLAi Host 联调。开发 Agent 与被开发系统中的 vLLM Host 是两套角色，模型选择和费用分别记录。

执行本 Goal 时可以使用 vLLM 模拟 Host 做开发联调；这项用户授权不需要因历史文档中的模型准入流程而重复申请。历史联合实验、已有结果和旧预算仍保持各自状态，不借用它们开展新一轮正式实验。

## 1. 开发方式

1. **先做完整路径。** 一次完成一个能实际保存、读取或更正的增量，验证通过后继续下一项；不先建通用框架。
2. **代码与合同一起落地。** 新接口用一份简短 ADR 和对应合同说明关键选择，随实现维护，不设置独立评审阶段或逐阶段批准。
3. **只验证实际风险。** 优先复用现有测试；新增测试覆盖新行为和容易损坏的权限、版本、恢复边界。普通重命名、函数提取、文案修改不另建测试。
4. **优化正在修改的结构。** 公共逻辑只保留一份；内部使用已验证的类型，直接调用明确职责的函数。出现真实重复时再提取，不提前建设多层策略、注册器或插件系统。
5. **减少重复防御。** 输入在入口解析，权限和版本由负责操作的层检查；内部不反复判空、转换类型或吞异常。动态权限与并发版本仍须在实际读写时检查。
6. **保持开发连续。** 普通实现选择、局部修复和相关测试由开发者直接完成。只对影响目标的真实缺失信息澄清，不为每个切片生成审计、准入或复核报告。

开发记录保持一处：本 Goal 的进度表。详细接口写合同，运行输出放忽略目录，交付时给一份简短结果。无需并行维护多套 tracker、证书与完成审计。

多 Agent 只用于能独立推进的开发切片。小修改由一个 Agent 完成；涉及相同文件或尚未明确的接口先顺序处理。并行后的额外协调与返工必须少于节省的开发时间，不以开满并发作为目标。

## 2. 首版交付范围

| 能力 | 本 Goal 要完成的行为 |
| --- | --- |
| 统一操作 | 默认记下内容；按返回引用修改；按已取得来源的引用保留或关联。Host 不根据正文真假选择 Evidence／Note |
| 准确来源 | 支持已有 Evidence，以及选定适配器实际取得、通过公开捕获接口保存的消息／工具结果；来源元数据由接入代码组织 |
| 统一发现与读取 | 复用现有 Note 发现与 governed resolve；返回可直接使用的记录引用、准确版本及来源入口，保留各分支状态 |
| 当前理解与更正 | 条件性长期信息放 Note；本次情境和工作位置放一个 Working State；修改 Note 后再保存引用该版本的 State |
| 后续续接 | 同一授权绑定与任务下，恢复时复查已记录依赖，再向 Host 提供当前视图；一次显式交接可复用同一读取路径 |
| 可运行 Host | 一套薄 vLLM 驱动连接真实 MCP 与隔离开发数据；模型自然决定查、读、写和回答 |

首版沿用现有 Evidence／Note 表、权限、CAS 和生命周期。Note 仍是 HOST_WORKING；来源记录证明收到过什么，不认证正文正确。已有 Evidence 引用也不追认历史作者已被可信接入核验。

Note 语义索引、通用服务端 Note-version 依赖、跨主体共享、全面物理清除、图数据库、画像分类模型、RL、多模型 Judge、PersonaMem 完整比较及外部系统复现留在后续工作，不与本 Goal 捆绑交付。

## 3. 最小实现设计

### 3.1 操作与引用

沿用 `compact-memory-v1` 已有默认 Note 保存和返回引用能力。新增可选 `compact-memory-v2` 实现意图与目标引用，保持旧目录行为；该名称当前只是拟议配置，完成注册和合同后才可使用。

| 意图 | 实现方式 |
| --- | --- |
| 记下内容 | 内容与稳定操作 ID 默认创建 Note，可选来源；没有来源的想法和转述也能保存 |
| 修改记录 | 使用服务返回、包含原读取版本的 target_ref；路由到 Note CAS，不自动换用最新 head 覆盖旧稿 |
| 保留来源 | source_handle 首先复用服务已有准确来源引用；需要新来源时由可信适配器取得并调用现有捕获接口，确认后返回引用 |
| 来源加整理 | 明确分成来源取得／保存、Note 写入两个步骤；复用已保存来源，分别呈现结果 |

采用有限输入模型和直接分支路由，复用现有 handler。返回对象可以保留实际类型、作者、加工关系、版本和能力，Host 通过复制引用操作，无需自己构造存储类型。引用不授予额外权限。

source_handle 不先建设独立注册中心。首版用已有服务对象引用，加上选定适配器对实际来源事件的映射。对新消息，适配器从实际收到的消息构造来源包，在明确保存意图下捕获；模型不填写 speaker、permission_snapshot 或伪造用户原话。无法取得的外部消息直接说明不可保存原文，仍允许另存 Host 自己的整理。

来源捕获 UNKNOWN 时保留原请求与 ID，沿既有合同恢复；Note UNKNOWN 查询原 Note 操作；State 没有独立操作查询接口。错误在所属边界表达，不添加通用重试引擎、跨对象事务或自动补偿。必要的原请求与回执复用驱动的运行记录，不另建账本平台。

### 3.2 来源关联与 State

Note 的 Evidence 引用继续作为披露依赖，不能降格成普通链接；来源不可读时依照现有合同隐藏关联正文。FILE 声明不能替代机器可检查的 Note-version 依赖。摘要与来源相同不增加独立佐证数量。

State 使用一个受控命名空间，保存短工作记录、当前适用条件、下一步及准确引用。Host 对可读基底做局部合并，再提交完整 payload CAS；没有变化时不写。明确提交空 payload 与“不更新”继续区分。

首版由受控 Host 适配器在恢复呈现前，通过公开接口复查已声明的 Note／Evidence 引用。无法复查的派生 State 不注入；这项保证只属于该适配器，不描述为 Runtime 已有的全客户端依赖传播能力。长期 Note 与 State 分步提交，各自报告结果。

Attention 首先体现为 Host 根据当前问题形成具体查询、按需展开材料，并修正局部理解。使用一页简短政策即可，不增加调度模型、强制逐轮总结或隐藏的自动画像任务。

## 4. vLLM Host 开发路径

用户已允许使用 vLLM 模拟 Host。开发联调采用下面的真实调用路径：

```text
合成用户消息 → vLLM Host → 薄工具驱动 → 公开 MCP → 现有 Runtime / PostgreSQL
                  ↑                       │
                  └────真实工具结果─────────┘
```

1. 从配置读取 vLLM endpoint 和模型名，复用现有 HTTP／MCP 客户端；不复制历史 runner 的完整实验控制流程。
2. 从 MCP `tools/list` 取得当前目录，转换为模型工具描述；接收模型 tool calls，调用公开工具，再按对应调用 ID 返回工具结果。
3. 同一个 Host 完成理解、记忆操作和回答。使用正常工具选择，不预写正确调用序列，不让另一个模型替它修参数或评分。
4. 驱动持有真实输入消息，来源包直接从该输入生成。合成消息始终标为开发材料，不作为真实用户画像或真实客户端效果证据。
5. 默认单并发、每个场景最多 8 次模型往返、每次输出上限 1,200 tokens，超时显式配置。它们是开发默认值，可按实际任务调整，不设逐次申请流程；达到上限就记录当前结果并定位问题，不自动扩批或反复跑到成功。

vLLM 的自动工具调用需要模型匹配的 tool parser、工具兼容 chat template 和相关启动配置；先确认实际安装版本。参数依据 [vLLM 官方工具调用文档](https://docs.vllm.ai/en/latest/features/tool_calling/)，不硬编码某个模型通用可用的 parser。本 Goal 不要求改造共享推理服务；已有适用端点可直接接入。

当前 [v02 本地 runner](../../tools/run_v02_local_vllm.py)采用 JSON-action Host 和旧目录工具集合，可参考其公开 MCP 调用方式，不能直接当作新目录已打通的证明。新驱动优先使用原生 tool calls；若开发端点只能使用显式 JSON-action 模式，配置中单独标明该模式，不将其宣称为原生工具兼容性结果。

只需保存配置摘要、Product 版本、实际工具请求／结果、模型最终回答及可取得的 usage／耗时。usage 缺失记未知，不伪造成本，也不因此增加另一个 tokenizer／Judge 流程。开发产物放 Lab 的 Git 忽略目录。

Host 是模拟的，记忆服务调用是真实的，两者分别说明。这里不需要完整研究臂和收益评价；以后开展 Product-backed 效果实验时再按 Lab 规则固定 product lock。vLLM 暂不可用时继续独立的接口开发，保留 Host 联调未完成状态，不以 mock 代替完成条件。

### 5.1 多 Agent 的默认组织

默认 **一个主 Agent＋两个执行 Agent**，只有存在额外独立任务时才临时增加一个窄任务 Agent。本次会话工具提供的上限是包含主 Agent 在内共 4 个活跃槽位；它是本环境限制，不是所有 Codex／API 的统一上限。子 Agent 不自行扩建团队，不设常驻 Reviewer、Tester 或架构委员会。

| 角色 | 写入范围与责任 | 并行条件 |
| --- | --- | --- |
| 主 Agent：接口与集成 | 同一份 ADR／公开合同、Goal 进度；`server_factory.py`、`codex_full.py`、`launcher.py`；必要的共享 Runtime 改动 | 先给出最小请求／返回示例与引用语义，然后做实际集成；不重复执行子 Agent 的整项任务 |
| Product Agent | 新目录的有限输入、路由与返回引用模块，以及自己负责的相关测试；推进 D1 和 D3 服务侧 | 不直接改主 Agent 持有的共享接线；复用现有 handler，保持 v1 行为 |
| Host Agent | Lab 的 `tools/contextual_host_adapter.py`、单一开发配置及相关测试；推进 D2、D3 接入侧与 D4 | 只用公开 MCP；可先接 compact v1 完成真实工具循环，再接新目录 |
| 窄任务 Agent（按需） | 指定范围的源码定位、确定性配置／文档修改或独立的小型修复 | 必须有明确产物和独占文件；没有独立任务就不启动，命令可直接执行时不专门派 Agent |

这个分工采用官方多 Agent 文档建议的“独立任务并行、共享文件协调”原则，具体角色和并发数是 MiLAi 的开发选择。[OpenAI 多 Agent 文档](https://developers.openai.com/api/docs/guides/agents-api/multi-agent)

默认使用共享工作区，**同一文件同时只有一个写入者**。子 Agent 交付后，主 Agent 接管该文件完成集成；冲突通过重新分配所有者解决，不让两个 Agent 反复覆盖。只有确实需要同时改变重叠文件且任务足够大时才用独立 worktree，不为每个小任务复制仓库与环境。

共享依赖锁、环境安装、数据库生命周期与 Git 分支操作由主 Agent 统一协调。局部纯测试可并行；数据库迁移、最终包级检查和同一 vLLM 端点的联调集中执行。现有用户改动不能因另一 Agent 的任务而撤销。

### 5.2 模型与推理强度

以下是用户确定的开发分派配置，不是模型在 MiLAi 上已经建立的性价比排名。当前工具目录与本地模型目录均提供 GPT-6 Astra／Sol／Luna；具体账户、上下文与服务档位以执行环境为准。官方分别将 [Sol](https://developers.openai.com/api/docs/models/gpt-6-sol)定位于复杂编码与 Agent 工作，将 [Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)定位于聚焦任务，将 [Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)定位于最困难的综合工作。

| 工作 | 默认模型与强度 | 调整条件 |
| --- | --- | --- |
| 主 Agent 的分派、普通集成与完成判断 | `gpt-6-sol / xhigh` | 保持主 Agent 也做代码，不成为纯协调层；跨层疑难交 Astra xhigh |
| Product 新目录、Host 工具驱动、一般修复 | `gpt-6-sol / xhigh` | 来源身份、CAS、UNKNOWN 或披露依赖仍使用该常规档；实质疑难再交 Astra xhigh |
| 窄范围查找、文档与已明确的机械修改 | `gpt-6-luna / max` | 涉及业务语义或超出窄任务范围时交 Sol xhigh，不因单价低扩大职责 |
| 尚未解开的跨层故障或关键设计取舍 | `gpt-6-astra / xhigh`，按需介入 | 带最小复现、已尝试内容及准确问题；解决后回到 Sol xhigh，不逐项重复审核 |
| MiLAi 开发联调中的 Host | 配置指定的 vLLM 模型 | 按其实际工具调用／thinking 能力配置，不把 OpenAI reasoning 档位直接套到 vLLM |

按职责固定使用上述三组模型与推理强度，常规任务直接从 Sol xhigh 开始，窄任务直接用 Luna max，疑难问题直接用 Astra xhigh。不自行降低用户选定的推理强度；成本优化通过缩小上下文、减少重复分派和控制返工实现。

发生一次有依据的修复后仍重复遇到同一推理障碍，或开始时已经确认是高耦合难题，就转 Astra xhigh，不要求先耗尽多轮常规模型重试。缺文件、接口尚未提供、环境启动失败先处理依赖，升级模型不能替代这些工作。疑难解除后，后续常规工作回到 Sol xhigh；明确独立的窄任务再交 Luna max。同一任务不让多个模型同时做完整解答。

当前主会话模型由运行环境选定，不能靠子 Agent 参数改变。表中的 Sol xhigh 主 Agent 是后续可配置会话的执行约定；本次文档修改不声称已经切换主模型。后续子 Agent 分派显式填写对应模型与推理强度；执行环境无法接受指定组合时说明实际限制，不静默替换。

### 5.3 分派、上下文与交接

每个任务只携带：**目标、相关合同／文件、允许写入的文件、依赖、最小验证命令和完成产物**。子 Agent 自己读取适用 AGENTS.md 与局部源码，不复制整段会话、全仓代码和所有历史评审。相同职责的续作优先复用原 Agent，避免反复建立上下文。

本会话在为子 Agent 单独指定模型／推理档位时，使用 `fork_turns="none"` 或必要的少量近期轮次；`fork_turns="all"` 会继承父模型与强度，不能同时覆盖它们。以下仅为现有 `collaboration.spawn_agent` 工具的分派示例，不是新增项目配置或已经执行的代码任务：

```json
{
  "task_name": "memory_api",
  "model": "gpt-6-sol",
  "reasoning_effort": "xhigh",
  "fork_turns": "none",
  "message": "执行 Goal D1 的新目录输入与路由。只写分配的模块和相关测试；共享接线由主 Agent 修改。先读所涉 AGENTS.md 与已确定合同。完成后返回改动路径、可调用入口、验证命令结果及待接线项。"
}
```

实际分派应补齐准确路径，不把“分配的模块”留成含糊指令。现有工具不是任意 vLLM endpoint 的 Agent 宿主；vLLM 继续用于 §4 的 MiLAi Host，不冒称已替换开发子 Agent。

交接只需：改动文件、实际接口／行为、运行过的命令与结果、一个明确的剩余问题（若有）。直接查看代码 diff，不在消息里重复整段实现。需要换模型接手时，先停止原写入者，传递当前产物和未解决点；不重做已完成的探索，也不假定 followup 会改变原 Agent 的模型。

### 5.4 在 D1–D5 中怎样并行

| 阶段 | 主 Agent | Product Agent | Host Agent |
| --- | --- | --- | --- |
| 起步 | 确定最小意图／引用合同与文件所有者，给一组请求／回执示例 | 阅读相邻路由，准备 D1 局部实现 | 接已有 compact v1，开始 D2 真实 MCP 循环 |
| 第一段 | 接目录注册与 launcher 配置，解决两侧的真实接口问题 | 完成新目录保存／修改／读回 | 完成 vLLM 工具调用与结果配对；接口提供后接新目录 |
| 第二段 | 确定 D3 来源发布者与回执语义，串行处理共享接线 | 实现来源引用及分步结果，不复制存储路径 | 接实际消息来源；再按准确 Note 引用实施 D4 恢复与 State |
| 收尾 | D5 集成、一次相关包检查、开发场景及最终说明 | 只修自己模块的失败 | 只修驱动／State 的失败 |

D3 先共享准确引用与来源取得约定，再分别实现两侧；D4 的持久引用须以 D1/D3 的实际合同为准。同一 Host 文件中的 D2/D4 由同一 Agent 接续，不为追求并发再派一个 State Agent。依赖尚未到位时做可独立部分，不能用假回执提前声称完整路径已完成。

等待子任务时，主 Agent 做不重叠的集成工作；没有独立工作就等待，避免高频轮询、反复索取长报告或同题重做。若多数时间消耗在协调和冲突上，立即缩为一主一执行或单 Agent。

### 5.5 性价比与成本选择

截至 2026-09-23，官方 API 短上下文价格如下，单位为美元／百万 tokens。表中输入是不含缓存的普通输入，Fast 为原 Priority 档位。[OpenAI API 定价](https://developers.openai.com/api/docs/pricing)

| 模型 | Standard 输入／输出 | Fast 输入／输出 |
| --- | --- | --- |
| GPT-6 Luna | $0.10 / $0.50 | $0.20 / $1.00 |
| GPT-6 Sol | $2.00 / $10.00 | $4.00 / $20.00 |
| GPT-6 Astra | $10.00 / $50.00 | $20.00 / $100.00 |

该表是 API 参考价，不是 Codex 订阅账单或本会话实付金额。长上下文、缓存、工具与服务档位按实际用量结算；本会话模型工具声明 Priority，且 spawn 参数没有服务档位开关，不能把 Standard 价格冒称实际费率，也不能声称已降到 Standard。自行部署可配置开发会话时，可优先比较 Standard，只有节省的等待值得溢价时才选 Fast。

例如每项工作若恰好消费 10,000 个普通输入和 2,000 个计费输出 tokens，Standard 下 Luna／Sol／Astra 分别是 $0.002／$0.04／$0.20，Fast 下各翻倍。这只是同 token 用量的算术示例，模型实际完成同一工作所需 tokens、修复次数和质量并不相同；不能据此承诺固定节省比例。

真正比较的是**完成一个可交付切片的总成本与墙钟时间**：主 Agent 的协调、所有子 Agent 的上下文与输出、返工、集成及 vLLM GPU 时间都计入。计费输出包含实际收费的推理用量，不能仅按最终可见回复估算。[推理 token 说明](https://developers.openai.com/api/docs/guides/reasoning)

只从现有记录保留每个切片的模型／档位、可取得的用量、耗时、是否一次完成及返工原因，不另建成本平台。在用户指定的三组档位下优化任务分工：Luna max 需要频繁解释或返工就转 Sol xhigh；Sol xhigh 已直接解决的任务不送 Astra 再审；疑难由 Astra xhigh 处理。并行只在缩短关键路径时启用，不能把更多 Agent 等同于更低费用。

## 6. 最少且有用的验证

### 6.1 开发时

| 改动 | 最小检查 |
| --- | --- |
| 新目录和路由 | 复用 compact 测试中的默认保存、返回引用、逐分支权限与恢复用例；为新目录补对应参数，不整套复制测试 |
| 版本与来源接线 | 直接检查旧版本更新冲突、来源不可读时的返回、来源成功而 Note 失败的恢复；已有底层用例足够时不重复新增 |
| State／Host 驱动 | 检查工具调用与结果配对，以及恢复前依赖复查；普通内部函数不做逐函数镜像测试 |
| 纯整理与文档 | 使用相关静态检查或文档链接检查，不触发模型批次、全仓数据库回归 |

优先从现有 [compact 测试](../../../MiLAi-Product/integrations/mcp/tests/test_compact_memory.py) 和 [launcher 测试](../../../MiLAi-Product/integrations/mcp/tests/test_launcher.py)扩展。覆盖真实新行为的少量用例优先于“大量测试都通过”的数字。

vLLM 开发联调保留三个连续场景即可：

1. **保存与再用：**记录一条条件性偏好和一个无来源工作想法，后续通过真实搜索／读取找到并使用。
2. **来源与更正：**取得一条合成用户消息，保留原文并写下整理；用户澄清适用范围后，修改整理，原文仍可核对。
3. **情境与续接：**技术讨论→客户汇报→返回技术讨论，恢复 State 时复查引用，临时要求不覆盖一般偏好。

并发冲突、撤销和 UNKNOWN 用确定性工程测试覆盖，无须让模型随机撞出故障。联调失败后只重跑受影响场景；不按题目加关键词、特殊分支或新提示版本掩盖通用问题。不为本 Goal 增加 benchmark、统计显著性、外部 baseline 或消融门槛。

### 6.2 交付时

受影响代码稳定后集中运行一次所属包要求的检查。MCP 包执行 `uv run ruff check src tests`、`uv run mypy`、`uv run pytest -q`、`uv build`。修改 Lab 代码时执行其 boundary、pytest、ruff、mypy 和 build 既有检查；Runtime 没有变化时不重复跑 Runtime 全量。

真实保存与续接联调使用隔离开发数据库。若修改 CAS、权限、撤销、删除或迁移行为，补对应真实 PostgreSQL 用例；这类验证不能用 mock 替代。无相关改动时不另外搭建故障矩阵或重跑全仓数据库集合。无新增变化、失败或未解问题时，不重复已通过的检查。

## 7. 完成条件与交付

以下完成即可结束本开发 Goal，不等待研究证明：

- 新目录可实际选用，默认记下内容、来源关联、版本修改和读取均通过公开接口运行。
- vLLM 驱动完成三个开发场景，保存真实请求与回执；当前支持的来源和恢复范围有明确说明。
- 来源与整理保持区别，CAS、现有权限、披露依赖和 UNKNOWN 行为没有被统一外壳绕过。
- State 能在选定适配器中恢复，失效或不可复查的依赖不会被静默注入；不承诺未实现的全客户端能力。
- 相关检查通过，代码没有引入重复存储路径、分类模型、通用工作流引擎或 Product→Lab 依赖。
- 提供一份简短启动说明和交付记录，说明实际改动、运行方式、已跑检查、未完成项及回退方式。

回退优先切回已有 catalog，已提交的 Evidence／Note 不随开关删除。首版预计无需 Schema 迁移；若实际新增迁移，交付时说明其独立回退限制。产品继续保持 CANDIDATE、Schema EXPERIMENTAL / NO-GO FOR SCHEMA FREEZE；开发完成仅表示本节功能范围完成。

本 Goal 的首个动作是主 Agent 确定 D1 的最小接口与文件分工，随后 Product／Host 两个切片推进 D1/D2；普通小修继续单 Agent。实际代码交付与联调优先，不增加多 Agent 审核阶段或大型实验前置条件。
