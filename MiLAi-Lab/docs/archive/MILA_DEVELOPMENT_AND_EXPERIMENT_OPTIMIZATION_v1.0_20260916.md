# MiLAi 开发与实验优化建议

## 0. 总决定

**下一阶段不再扩建记忆架构，也不再用单个短题反复检验全部创新。保留当前 RB＋采用／修订研究路线，优先兑现“选择控制实际输入”，继而研究行动约束下的经验使用，以及有反馈依据的正确对象修订；在已有 DB、OS、旅行载体上同步安排方法开发和未调试任务验证。**

整体研究问题收敛为：

> 在有限计算和业务行动机会下，Host 能否决定哪些经验现在值得使用、使用到什么范围、什么新证据需要改变当前判断，并使经验最终减少错误或重复工作，而不是增加额外义务？

这是对已有总架构的增量优化，不是推翻原始方向。N1 依据范围维护、N2 联想与投入分离、N3 可逆重新判断、N4 有依据地行动与收敛继续保留，但不要求每个任务都演示四项能力。

**两条工作线同步组织：**开发线修复和改进明确的操作关系；验证线在预先确定的其他任务族、完整任务流和第二执行域上检查同一版本。没有必要等待某一道题赢了才安排泛化，也不能拿尚未形成实际处理差异的实现继续扩样。

本文只提出开发与实验建议，不恢复已暂停实验、不改代码、不重新开放旧预算。来源事实、用户此前核查与本次建议分别标明；没有取得本轮 RB 路线源码、逐题账本及全部配对结果。

## 1. 当前证据与结论

### 1.1 最新 DB 结果：两种设置各 100 项

| 方法 | 固定经验库 | 在线学习 |
| --- | ---: | ---: |
| Native | 90/100 | 88/100 |
| OM | 93/100 | 88/100 |
| ReasoningBank | 76/100 | 77/100 |
| MiLAi | 81/100 | 82/100 |

最新简报明确：两种设置使用同一批 100 道题，不能合并成 200 道独立题。MiLAi 比 RB 均高 5 个百分点，但统计区间尚不能确认达到原先设定的有用收益。MiLAi 测试 tokens 约为 Native 的 4 倍、RB 的 1.24–1.26 倍；OM 固定库测试 tokens 约为 Native 的 22.5 倍。固定经验库形成成本另计。[S1]

**当前方法选择：这些 DB 条件下，Native 是主要实用参照。**MiLAi 当前没有替代 Native 的综合依据；不能只因略胜 RB 就推广。OM 的最高正确率也不自动抵消其很高成本。上述倍数是所报告范围的 tokens，不是美元费用、算力倍数或完整生命周期成本。

### 1.2 其他载体与机制

| 证据 | 当前判断 | 对优化的意义 |
| --- | --- | --- |
| 200 次 MiLAi DB 主执行中，自然回读与获准经验修订均为 0 | 组合方法已经测试；修订再使用贡献未建立 | 查清运行机会与更新位置，不强制产生补丁 |
| 旅行 v0.4：55/58 有终态、50/58 有非空计划、1/58 完整通过，无整组通过 | 可用性与解题质量明显分离；调整混合了输入时机与等待时间 | 分开修基础规划、约束消费与跨会话记忆 |
| 旅行支持库：OM 20 组中 13 组容量中止，RB 1 组容量中止 | 支持库形成及输入组织存在可用性限制 | 容量修复对相应方法独立版本化，失败形成成本保留 |
| OS：完成 15 题后遇空历史记录断言，已修处理，但没有受影响题终态及完整后续比较 | 运行故障，不是该题已判模型错误；OS 泛化未建立 | 恢复原生运行能力，不以新 benchmark 取代未完成域 |
| 旧 RWC 卡片有完整映射，后续仅见截断预览而误判数据缺失 | 保存不等于呈现、呈现不等于理解 | 选中的必要内容需要完整且有范围的展开 |
| 旧 OM 观察把 104 写成 102，但正确原始反馈仍可见且任务通过 | 任务成功不证明观察准确 | 纠错应回到来源，不把摘要作为权威 |

这些内容来自最新简报。[S1] OS 明细不足，不利用“15、受影响一题、后续86题”自行拼出总任务数。

### 1.3 此前用户逐轨迹核查：不能冒充本次原始日志复核

用户此前报告，在找到的 11 个“Native 正确、MiLAi 错误”DB 案例中，10 个触及轮数上限。任务 62 需要 INSERT…SELECT；采用器认为检索到的 UPDATE 经验不直接适用，selected_refs 为空，但三条经验仍全部进入 Actor。额外结构／数据检查使它在三轮业务限制下未及时完成插入。任务 94 则把记录级平均值理解成组总数的平均值，随后围绕错误解释反复验证。[U1]

这些观察支持两个开发优先级：选择必须实际控制投影；经验不能无条件添加检查步骤。它们**不证明**每次额外检查都是经验导致，也不代表最新全量错误中有 10/11 属于同一原因。最新简报没有附上这些原始请求，本轮未独立复核。

## 2. 继承以前哪些改进，停止哪些惯性做法

| 保留并落实 | 不再作为默认研究做法 |
| --- | --- |
| 一个 Host 执行主干，原生工具、反馈、权限和预算 | 在每个 Actor 前叠加多层语义维护 |
| 任务内 State 与跨任务经验分开 | 把当前理解错、经验不适用、经验错误都叫长期修订 |
| 低频整理、按需控制、不变记录复用 | 为让维护“出现”而降低阈值或强制每题建卡 |
| 原始目标与真实新反馈独立可见 | 旧 Frame 过滤当前用户要求与反证 |
| 空选择、暂不使用和及时交付都是合法行为 | 把检索命中等同必须注入，把更多检查等同更可靠 |
| 原始来源可恢复，当前视图不重复堆旧版本 | 卡片只给预览却让模型当全文；所有元数据每轮重发 |
| 形成、保留、消费、选材、修订贡献分别解释 | 同信息 review 打平就否定整个形成算法 |
| 同规则跨任务和跨域验证进入主线 | 一题调参—局部打平—关闭，迁移永远未启动 |
| 工程检查针对变更，稳定代码集中交接 | 用全仓 PASS 数量、报告数量代替方法进展 |

此前总设计关于“执行快循环、整理慢循环、按需控制”和“一个当前工作认知视图”继续有效。[S4] 但当前被测候选是 **RB＋采用／经验修订**，并非旧 Adaptive 或 OM 为底座；不将旧 RWC v0.4 与旅行 MiLAi v0.4 混为同一版本。[U1]

## 3. 总体开发结构：改三个联系，不新增认知系统

```text
用户目标、原生工具合同、真实行动预算
                  │
           原生 Actor 执行主干
                  │
        RB 检索获得候选经验集合
                  │
      采用：选择现在值得使用的经验
                  │
      投影：仅展开实际选择的经验
                  │
  Actor：用当前证据与可用经验完成任务
                  │
              真实工具反馈
        ┌─────────┴─────────┐
 当前任务解释／采用关系修正   有依据的长期经验修订候选
        │                          │
 即时进入后续任务输入       复用既有提炼／维护时机
        └─────────┬─────────┘
          当前交付与以后任务的经验复用
```

OM、Native、RB 保持各自独立算法；不为了统一代码而统一维护频率，不把 OM＋RWC＋RB 同时堆进每条任务。

程序处理引用、版本、投影、预算和提交；模型判断相关性、适用范围与下一步目的。不按任务 ID、SQL 动词、固定失败次数或 State 关键词硬编码认知流程。

## 4. P0：让采用判断真正控制 Actor 输入

### 4.1 先兑现已有合同

设检索候选为 R，采用器选择集合为 S，必须满足 S⊆R。Actor 的附加经验区由 S 构造，而不是始终渲染 R：

```text
Actor 输入 = 原生任务与真实反馈
           + 实际选择的经验正文
           + 与这些经验对应、确有用途的采用说明
           + 合法任务内工作记录
```

**S 为空，本轮不自动附加这些经验及其派生行动建议。**空列表不能通过 truthy/falsy 回退被解释为“展示全部”。缺省、沿用旧选择、显式清空按当前真实接口分别落实，不擅自替换现有合同。

被排除经验仍在库内，不撤销读取权限、不删除原件。后续相关时可以重新选取；暂退当前输入与永久遗忘分开。

### 4.2 检查最终发送内容，不只检查 selected_refs 字段

潜在重复入口包括：经验正文、采用说明、Frame、摘要、历史 assistant 消息及系统附加提示。选择没有通过某个入口，不能从另一入口全文复述被排除建议。

采用器的排除理由可以留在日志；无需每轮向 Actor 重讲“以下三条不适用的经验分别建议了什么”。但不允许删除独立且仍有效的用户要求、真实反馈或必要安全约束，只因为它们与被排除经验文字相似。

这是明确内容路径的修复，不建设一个通用语义去污服务。采用器已经看过的材料不能“撤回未见”；本修复控制 Actor 后续投影，不声称消除了全系统既有暴露。

### 4.3 选中后的内容质量也要保证

相关原文或卡片若只有预览，要显示范围与展开入口。决定依赖的关键映射、否定条件等不能静默被截掉。依现有容量按合法范围展开，不将“改为全部全文常驻”当唯一修复。

最小邻近测试：空选择、部分选择、已选内容完整／分页状态、未知引用、取消选择后不再经旧默认插槽重复注入、新真实反馈不被过滤。测试证明投影合同；真实任务比较才证明选择质量。

**P0 属于实现正确性，不是独立算法创新。**它减少干扰的实际效果以及是否误删有用经验，仍需实测。

## 5. P1：让经验服从任务行动约束

### 5.1 分清两个预算

| 预算 | 计入什么 | 不能混淆什么 |
| --- | --- | --- |
| 业务行动预算 | 原生环境计数的 SQL、工具回合、阶段动作等 | 减少维护调用不自动增加三轮 DB 的 SQL 机会 |
| 认知计算预算 | Actor、采用、自判、提炼、摘要、修订等调用和 tokens | 维护“不占业务回合”不等于免费 |

现有 RWC 保留最后一次 Actor 与交付机会的原则继续保留，但它不等价于预留完成业务写入的机会。[S3] 当前 RB 入口是否继承了相应规则，需要源码核对，不能据历史文档宣称已经具备。

Host 将实际原生剩余行动机会、final 的计数语义和必要时限提供给 Actor。不得按每题新增一个硬编码计划，也不能把多条命令包装成一次调用绕过原生计数。

### 5.2 候选使用政策

> 经验应帮助确定哪些已有信息可以复用、哪项未知会改变下一步、怎样保留完成必要操作的机会。不要因经验包含检查建议，就把检查无条件追加为前置步骤。

检查的价值依当前问题判断：它是否补齐必要信息、区分主要解释或降低实际风险？已有信息足够时可直接执行；不足时允许必要检查。不是“短任务永远不查结构”，也不是“剩一轮无论风险都写入”。

任务 94 对应的改进重点是对齐原始需求的对象、范围、聚合单位，而不是对同一错误解释反复执行验证。这些可用一行任务内记录表达，不为每题增加一个语义 Judge。数据库特定诊断可以在开发中出现；拟推广的规则应适用于 OS 的目标范围、旅行的人员／日期／组约束等不同对象。

### 5.3 经验形成也应减少过度概括

复用现有提炼位置，比较普通经验与保留适用条件的经验。避免把某一次成功轨迹抽象为“所有写操作都要先完整扫描”；失败分析也不能把预算耗尽直接写成方法本身永远错误。

有用记录可以说明“在什么前提下这一步有必要／可以省去，以及依据是什么”。它不是新的确定性规则库，不能保证抽取一定正确。支持库改变必须作为形成规则变化单列，不能与只改消费的试验混算。

## 6. P2：纠正正确的对象，形成可验证的修订闭环

### 6.1 三个对象分开

| 对象 | 例子 | 处理与生命周期 |
| --- | --- | --- |
| 当前任务理解 | 把记录级平均值错解为组总数平均值 | 修订本任务解释与下一动作；不默认修改长期经验 |
| 当前采用关系 | 一条 UPDATE 经验对当前 INSERT 不适用 | 本任务不采用或仅采用可迁移部分；原经验可以仍然正确 |
| 经验内容及范围 | 无条件“必须全量检查”的经验被合法反馈反驳 | 有依据时收窄、更正或替换有效版本，保留来源与旧版追溯 |

零获准修订不能自动证明修订接口坏了，也不能证明所有任务都没有修订机会。冻结库若禁止持久写回，补丁为零可以符合合同；在线流则可以检验长期更正。任何情况下都不能为提高补丁数而强迫改写。

### 6.2 更新时机优先复用现有调用

先沿当前代码核对：已使用经验 ID、Actor 实际反馈、旧经验正文是否进入已有自判／提炼调用，能否允许输出一个可选修订。若已有轨迹提炼阶段足以完成，优先增加有来源的修订选项，而非新增每步 Reviewer。

任务内可直接更正工作判断。只在存在关键冲突、缺少会改变决定的历史细节时，才使用已有回读／维护路径。不能把“先回读”当所有重新判断的必经仪式。

停止任务后才产生的经验修订，不能解释当前任务已经发生的成功；它的收益必须在后续相关任务中观察。使用当前反馈即时修订，则可以研究当前后续选择。

### 6.3 修订的最小证据

```text
旧经验及来源
 → 当前任务是否实际使用
 → 当时合法可见的冲突／新条件
 → 模型提出的修订及作用范围
 → 新版本确实进入当前或后续输入
 → 行动或最终结果是否改善／受损
```

SQL 执行成功不证明需求解释正确；失败 reward 也不自动告诉模型错误在哪里。隐藏答案、只供评分的 verifier 明细不能回流在线纠错。只有 benchmark 合同本来向 Agent 提供的反馈可以用于在线更新。

原经验只有部分被否定时允许收窄；基础依据被推翻时允许整体重建。删除、权限撤销和 Canonical 治理继续沿原系统，不与认知“暂挂”混用。

## 7. P3：降低真实维护成本，分别处理 OM 与 RB 路线

### 7.1 不将旧经验生成额外行动当成默认安全性

当前空选择即使投影正确，采用器已经发生的成本也不会消失。第一版先保留独立采用，使行为可检查；后续可比较在既有 Actor 输入中先给精简目录、按需取得详情，或在已有调用中形成采用结果。后者可能需要额外读取，也可能错过有用经验，不能预称更便宜。

不再把“必须同调用”设成总前提。已有联合输出能力可靠时再融合，不为省一次调用损坏业务输出；更小模型或学习型调度是后续独立变量，不在本轮同时引入。

### 7.2 OM 容量与高开销是另一条具体问题

先利用实际发送请求拆分：近期原文、观察正文、来源元数据、重复目录、提示与回读内容各占多少；归并究竟是否触发并成功。简报不足以判定 22.5 倍成本的唯一来源，不能先把它全归为阈值过高。[S1]

可修复已确认重复投影、无变化重写、日志或元数据无界重发等问题；历史按需分页，受保护新反馈和真实来源继续可达。不能为了容量直接让原文消失后再声称没有信息损失，也不能把原文被隐藏导致 baseline 变弱当公平比较。

OM 修复单独版本化，使用相同任务目标、业务限制及合法来源，不强制改成 RB 或 RWC 的维护时机。主方法比较保留一个可用且合理配置的 OM，不以当前昂贵配置作为方便击败的唯一对手；原费用与失败仍保留。

### 7.3 三时间尺度原则继续适用

执行在正常 Actor 循环完成；累积材料在方法定义的时点整理；认知重规划按实际需要介入。子目标改名不应天然调用整套维护。不存在未处理反馈时不重复整理；Actor 已接收与维护已覆盖分别记录。[S3][S4]

## 8. Baseline：保留现有方法，增加的是解释力而非项目数量

| 对照 | 核心用途 | 运行建议 |
| --- | --- | --- |
| Native | 判断完整方案是否值得，相同合法历史和工具下的实用参照 | 所有主要跨域评价保留；不人为删减正常历史 |
| ReasoningBank | 判断检索经验与 MiLAi 增量的差异 | 保留忠实本地实现及已知移植差异；不把当前分数外推为原论文能力 |
| OM | 判断观察整理与长期历史组织的质量—成本关系 | 保持独立；长历史任务尤其重要，局部选材诊断不必每次全跑 |
| 当前 MiLAi | 记录当前成本和负迁移，作为开发回归 | 保留冻结版本，不每个正式任务都作为第五臂重复运行 |
| 改进 MiLAi | 只加入当前明确的选择／使用／修订变化 | 与 Native、RB 组成主要对照；按任务需要纳入 OM |

在没有新的、具体的算法缺口前，不接入更多完整 Memory 系统。新颖性判断后续针对真正有效的操作与已有近邻复核；本文没有新增外部查新，不能声称已经排除了已有等价方法。

## 9. 实验优化：机械检查只保护处理差异，主结果回到任务与泛化

### 9.1 三类验证各司其职

**接线检查**：空选择不回退、选中内容实际呈现、反馈不丢、补丁正确应用。少量可控响应足够，不统计认知收益。

**开发行为检查**：使用已有轨迹和少量完整任务，观察某项修改怎样改变行动。可以改政策与组合，保留版本和失败。

**方法与泛化评价**：核心方法固定，用未参与本版调试的任务族、独立任务流和第二环境运行。不能用前两类的成功代替这一类。

开发负结果不自动阻断泛化计划。环境不可用、授权不足或无法形成有效处理可以停止受影响运行，但须报告未完成；不能每次以“先等第一题胜出”为由永久推迟迁移。

### 9.2 首个开发比较：明确分开修投影与改政策

可复用检索候选与已保存的采用判断，先比较：

- A：当前行为，仍展开展示全部经验；
- B：严格按同一份采用结果选择呈现。

固定选择结果能够隔离投影差异，但只支持共享前缀之后的诊断。若后续动作不同，必须在各自等价环境中得到自身动作结果；没有环境分叉时只能报下一动作选择，不填原生成功。

随后在完整任务中运行真实采用＋投影，不复用候选独占的理想记录。第二项比较再固定修好的投影，研究普通消费与行动约束政策。最后才针对有具体问题的修订联系选择拆解。

首轮开发可以取 **约20–30项已暴露 DB 任务**作工作量参考：包含双方都对、双方都错、MiLAi回收、MiLAi回退，并覆盖不同任务结构；不只选择11个Native独对失败题。这是诊断选样，不是总体效果估计或统计功效承诺。若完整配对表尚无，先从已有记录整理，不额外调用模型去“生成分组”。

### 9.3 同计算机会的解释性对照

行动约束政策若也帮助 Native，收益可能属于一般求解改进。可在开发子集加入 Native＋相同简短行动约束提示，或普通同调用 review。它不被强迫额外调用，也不被禁止自然记录条件。

候选若只靠额外思考获益，应在实际相近成本工作点比较；不要求每题为“同调用数”给简单方案强加无用计算。需要时再设置一个独立 compute-matched 对照，单列其算法与成本。

## 10. 冻结库、在线流与多会话分别验证

### 10.1 冻结库迁移

支持集形成库 M_support，并冻结。测试任务仅可以生成任务内临时覆盖，结束后丢弃；测试1的结果不改变测试2使用的共享库。

分清两种比较：同一个固定库、不同使用政策，研究消费／筛选；各方法自行形成的固定库再比较，研究端到端形成＋使用。共享库形成费用不消失，不能把共享制品称为每个方法都独立建立的成果。

### 10.2 在线持续学习

每条流从规定的初态开始，各方法独立命名空间。先完成并评分当前任务，再仅用合同允许的反馈更新，进入下一任务。对照共享同一任务顺序，不能共享彼此经验或最终答案。

只有后续任务真的使用了更新后的经验，才有长期修订的收益机会。后半程分数更高不自动说明学会了；同任务序列对照与多个独立流用于排除顺序和难度影响。具有固有顺序的任务不得为了统计方便任意重排。

### 10.3 旅行的完整组验证

一组所有人员和阶段是主要依赖单元，不将58个人当58个独立任务组。先保持给定计划、前序计划、工具和等待条件一致，再比较 Native／原生历史基线、RB、候选，OM按完整方法计划加入。

首先利用原生合法反馈和离线约束分项，区分实体选取、日期／预算等要求理解、跨人员依赖、格式与终止。具体失败类别必须来自实际任务和checker，不预设所有旅行失败都属于遗忘。

当前58人验证已用于调试。正式组核心政策固定；前序人员真实计划是合法历史，人工改好的理想计划不能替代前序实际产物。只有明示的受控诊断允许共享固定前缀，并单独报告。

不要求旅行基线先达到完美成功率才允许研究；若各臂共同失败主要来自基础规划，应先归为共同能力问题，不把强行增加记忆修订次数当补救。

## 11. 泛化安排：放入主交付，不做“赢了再说”的附件

### 11.1 三个既有载体各承担一个主问题

| 载体 | 主问题 | 必须保留的边界 |
| --- | --- | --- |
| DB | 有限行动机会下的负迁移、选择与任务完成 | 保留原生轮数；不能靠候选专属延长掩盖多余检查 |
| OS | 同一规则在不同工具、目标和执行形态下是否有效 | 修复空历史运行故障；不把未评分当0；不逐题改认知政策 |
| 旅行／MemoryArena当前子域 | 跨人员、多会话约束续接和后续修订 | 完整组、相同信息时机、相同超时合同；原生评价与方法副作用分开 |

Terminal-Bench已暴露短题继续作可用性回归，不再作为创新与跨域证明的唯一数据。

### 11.2 数据划分与建议量级

当前DB100题已有正式成绩且部分题用于轨迹诊断。不能将它们重新命名为本版全新确认；也不能仅因为读了汇总表，就断言每道题都已被逐题调参。依据实际访问与修改记录区分开发使用、仅汇总暴露和未调试任务。

正式同版本验证应使用合法可用、未用于该版形成的新分区，按模板、schema／原问题来源等相关簇划分，不能只改实体名称。**可将约100个DB任务、约100个OS任务、30–50个完整旅行组作为覆盖量级的规划起点**，不是已有可用任务数量、当前预算或功效保证。具体范围要按可用未调试来源、最小有用差异、配对波动和实际费用确定；资源不足时缩小主张，而不是用重复同题冒充覆盖。

现有正式旧版本按原合同停止或收尾；修复版单列。若OS只修与方法无关的记录器并允许继承旧成绩，应说明具体等价边界；一旦改变认知政策或预算，就另建版本，不能续填成旧版完成。

### 11.3 三层泛化主张

1. **跨任务**：同一政策用于未参与调试的任务结构。
2. **跨域／持续工作**：同一更新与采用规则用于OS和完整旅行组；工具适配不偷偷加入逐题答案。
3. **跨模型**：选定方法后在第二个合适模型上不调认知政策地验证，角色与容量差异单列。

第二模型是较强泛化主张的工作包，不作为当前本地修复的入口。不能只选主模型上获胜题迁移；没有执行就报告证据仍限于当前模型。公开任务未被本项目调试使用，不保证训练数据未见。

## 12. 贡献拆解：只运行能改变判断的比较

| 问题 | 对照 | 结果如何解释 |
| --- | --- | --- |
| 选择是否真正有价值 | 同候选与采用结果：全注入 vs 严格投影 | 兑现选择合同的行为影响；不是单凭修bug确认新颖 |
| 行动约束规则是否只是一般提示 | Native＋共同简短政策；候选同政策 | 普遍帮助两者时，报告一般策略收益而非记忆独有 |
| 候选形成的内容是否有用 | 同前缀，普通／候选形成，固定消费 | 形成／维护的增量，形成成本计入 |
| 特殊消费是否必要 | 同时点同一记忆，普通／特殊消费 | 打平先删除特殊消费，不直接否定形成价值 |
| 旧经验修订是否有必要 | 相同更新机会，允许修订旧条目 vs 仅追加／任务内临时修正 | 区分跨任务旧内容更新与额外摘要、临时纠错 |
| 返回依据是否有用 | 相同来源能力，有／无具体返回入口 | 观察恰当重新使用，不奖励RECALL数量 |

无需全因子矩阵。先围绕明确问题选最有信息量的一对；整体组合可以先开发，但整体胜出先报组合。修改了检索、经验生成、投影和预算四处时，不能把全部提升归给其中一句政策。

## 13. 结果、成本与统计口径

### 13.1 主结果

主表按域和任务制度分开报告：任务质量、当前交付、业务动作与轮数耗尽、全角色计算成本、无有效评分原因。DB固定库与在线不合并；旅行人员率与组通过率并列；OS基础设施未运行／未评分独立。

主结果保留全部预定任务，不按“是否写卡片／修订”筛选。机制机会与采用率是解释性分层，不成为删除失败的资格门。原生判错与无有效评分分开，运行可用性同时计入总体交付统计。

配对报告至少包括双方都对、候选独对、基线独对、双方都错。净多5题不等于5胜0负；当前精简包不支持重算配对显著性或置信区间。

### 13.2 两种成本表

- **运行期成本**：所有Actor、采用、自判、提炼、摘要、复核、失败调用，检索／embedding、工具、时间。
- **生命周期成本**：再加入支持库形成、索引、失败形成、存储／恢复和必要维护；共享建设成本说明实际发生次数及摊销条件。

分别报告成功任务成本和全部尝试成本，不能只挑便宜成功样本。没有实际费率和缓存计费字段，不将raw tokens直接换美元；没有统一计时范围，不把各层span相加当墙钟。

对运行T个后续任务的经验库，可报告：

C_total(T)=C_support+C_index+Σ[C_actor+C_adopt+C_update+C_tools]。

不提供材料没有支持的回本任务数。采用器拒绝全部经验时其成本仍计入；最后一次任务结束后的提炼若方法确实执行，也不能为成绩好看删账。

### 13.3 主判断与不确定性

质量与成本构成二维比较。实用收益可为质量提高且代价值得，或在预先约定的质量容忍范围内显著降低成本；不要求所有指标同时提升，也不能只报告正确率或只报告速度。

原来“预设有用收益”的数值与完整统计区间未随简报提供，先引用其未达到的结论，不另造通过阈值。新正式比较在看结果前确定最小有用差异、质量下限和可接受费用。

独立DB任务按实际相关簇作配对分析；在线任务按完整流、旅行按组处理相关性。少量流的区间可能很不稳定，应展示逐流结果，不把80/100个流内任务当相互独立样本。不同任务类型分数不随意平均成“总智能分”。

## 14. 开发排程与最小交付

| 工作包 | 做什么 | 开发交付 | 对应实验 |
| --- | --- | --- | --- |
| W0 已有证据定位 | 读取当前RB路线的最终请求、实际选择、业务轮数和维护记录 | 一个简短的源头—选择—实际输入映射及配对失败分布 | 不新增模型；仅解释已有事实 |
| W1 真实投影 | 修空选择、部分选择、重复入口和预览范围 | 可关闭的投影修复、邻近测试、一次完整真实调用链 | 已暴露不同结果类型的开发配对 |
| W2 使用政策 | 当前目标／范围与行动机会进入既有消费，删无条件检查义务 | 普通与候选同能力配置、可迁移规则 | 固定投影后比较；必要时Native同政策 |
| W3 正确对象修订 | 临时解释、采用与长期经验更新分离，复用提炼位置 | 可用的更新路径、真实反馈和后续消费记录 | 冻结库临时覆盖、在线追加vs修订 |
| W4 载体可用性 | OS记录器局部修复；旅行容量、实际前序计划与已知接口问题 | 原生入口继续工作，失败和差异保留 | 相同设置下的基线与候选；不另建平台 |
| W5 同版本泛化 | 预留新DB结构、OS域、完整旅行组和必要第二模型范围 | 固定方法、真实未调试覆盖与完整成本 | 主比较不依赖首题胜出；无法执行如实未完成 |

W1–W3可以增量组合；W4与选样准备并行。W5属于该阶段研究交付，而不是永远可跳过的“有信号以后”。没有必要每改一行提示就另写Goal，也不能将全部工作包变成新的A–E。

仓库改动只落在实际RB方法入口、Actor经验投影、已有预算信息、已有提炼／修订函数和当前benchmark runner；具体函数路径未取得源码，不在本文编造。旧RWC／Adaptive文件是参考资产，不据此指定当前RB必然改这些文件。

工程检查按影响：投影改动检查空／部分选择和受保护反馈；修订改动检查版本、来源和后续投影；OS异常只测对应运行链；纯政策不重跑长全仓和公开持久化。最终代码交接仍完成项目要求的适用检查，未完成就准确列出覆盖。

## 15. 资源与停止决定

本文不设置一个必须耗尽的总生成矩阵。先依据既有逐角色账本，估算每个任务／完整组在原生业务限制下的费用，再分别固定开发包、主DB／OS比较、旅行组和第二模型的范围。旧预算已经暂停或关闭，不自动转入。

同一方法版本、相同来源下出现相同失败且没有新解释，不继续抽样等偶然阳性。可以继续另一任务族的计划验证来检验适用边界；停止某个版本不是否定整个方向。

以下决定都应被允许：

| 观察 | 建议决定 |
| --- | --- |
| 过滤修复减少了回退，但仍不如Native | 保留正确实现；研究的是降低负迁移，尚无正净收益 |
| 候选与Native相当，却持续支付高采用成本 | 缩小适用范围或研究低成本介入；不推广全任务默认 |
| 选中经验时有帮助，整体不帮助 | 主指标仍按全任务；研究可泛化选择，而非只汇报事后有用子集 |
| 形成规则有用，普通消费打平 | 保留形成规则、删除额外消费流程 |
| 当前任务解释被纠正，长期经验未更新 | 报任务内纠错，不冒称跨任务经验修订 |
| 修订后后续任务更好，也未显著伤害原适用场景 | 保留稳定性—可塑性候选，继续跨流确认 |
| 只有DB特定提示有用 | 保留应用优化，不主张通用State创新 |
| 多域相同规则质量／成本有用，消融支持关键操作 | 才推进独立创新表述与更强确认 |

## 16. 统领性结论与交付边界

**保留大框架：原生执行主干、可错工作状态、可复用经验、真实来源和受治理存取。优化三条核心联系：选择→实际输入，经验→有限行动，反馈→正确对象修订。**

可用性可以借鉴既有方法，创新不必覆盖整张架构图。真正可能成立的贡献，是在有限资源下恰当地调节经验影响：有用时采用，不适用时退出，证据变化时修订，并使这些变化跨任务改善工作。

本次交付是一份开发和实验优化建议，未更改任何方法版本、参数、数据、历史结论或产品默认；未运行项目代码、模型实验、benchmark、公开恢复或回归。实验保持暂停。
