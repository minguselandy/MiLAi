## 2. 源码诊断：分页已经存在，缺的是受控的“当前可见工作集”

### 2.1 已有能力，不再重建

`memory/functional.py`已有`search_memory`、`read_memory`、`read_source`；显式选择接口还提供`read_memory_history`、`read_memory_revision`、`read_fragment`、`read_page`。历史索引已经区分保存修订和原始来源。[R7]

`FunctionalEditMemory`已有按记录／版本／区间／页面记录的读取进展，可报告`new_evidence`和`no_new_evidence`。[R6]

`edit_maintenance.py`已有`combined_dense`与`per_candidate_dense`、来源边界分批、单轮／两阶段编排、原操作恢复；逐候选定位不是待从零实现的功能。[R5]

PR #105已把已有Episode描述的词法匹配接到真实原文读取；描述不是独立证据。benchmark的`include_raw=False`并未因此改变。[R3]

### 2.2 最重要的三个结构问题

**问题A：拆新消息，不等于减少旧上下文。** `plan_source_batches()`先定位旧记录，再保留K及旧语境，通过拆当前来源使请求可容纳。若占用主要来自旧记录／schema，继续拆新消息仍会重复旧负担，还可能拆开本次更正的条件。[R5]

**问题B：实际已读缓存被用于重建整个Writer输入。** `_cache_writer_items()`累计实际Reader页面和工具来源；`_writer_packet()`再遍历累计items组合材料。缓存记录已经交付过什么是合理的，但“曾经读过”不意味着每次后续调用都应再次看到全部正文。[R6][R8]

**问题C：当前功能Writer对局部方法也先要求整记录完整。** `_writer_packet()`不仅要求全部单元完整，还要求关系数量完整，之后才生成可编辑记录。仅在外面加一个分层目录，并不能直接获得“只读一个单元就局部编辑”的能力。[R8]

本轮先解决事项级选择和工作集替换，减少同时展开的事项。单元级有限读集作为随后明确的合同扩展；不能偷偷取消完整读取条件，同时宣称原编辑机制未变。

### 2.3 另一个待观察的风险：语义形成失败后的来源可发现性

当前自动Episode描述索引主要从实际已提交条款建立。没有语义提交时，不一定有新的描述入口；但原始来源本身仍然保存，仍可能通过已有原文入口读取。不能夸大成“完全无法恢复”，也不能认为Episode描述查询已经解决全部初始身份漏写。[R5]

新目录应允许发现已捕获来源的真实ID、角色、时间和原文摘录，不要求先有语义摘要。初版使用现有源索引与原文片段，不新增摘要调用或从姓名问题反推用户身份。

## 3. 本轮设计决策

### 3.1 核心方案

**检索候选保持可达，默认只交付目录；模型选中事项后展开完整必要语义；来源和历史按需读取；当前工作集可以替换，完整轨迹继续持久保留。**

先实现同一组读操作与工作集，再提供两种调度：固定两阶段、ReAct式按需读取。ReAct是候选调度策略，不是新的记忆库、审核Agent或必经长流程。

### 3.2 保持五条主线

| 主线 | 本轮落实方式 |
|---|---|
| Grounded Memory | 目录不作证据；实际来源／条款正文才进入断言依据；主体、语气、计划状态不因缩减输入消失 |
| Verified Object References | 目录ID不授予业务能力；对象和实际效果沿用真实lookup／receipt，权限从当前请求取得 |
| Semantic/Episodic Memory | 语义事项与Episode原文两类入口可按协议使用，不增加竞争Store或重复原文 |
| Grounded Revision | 开放目标及必要条件后再编辑；保留未编辑结构与支持；重写、局部编辑、追加仍为不同机制 |
| Lifecycle Recovery | 工作集只持久化引用、读取进度及实际动作身份；重开先对账，再按当前可见性重新装入材料 |

原v13.4的Simplify保留，但只约束未建立必要性的复杂关系消歧选源分支。本轮改变普通交付和工作状态，不复活多假设平台，也不以此宣称新算法成立。[R13][R14]

### 3.3 本轮不做

不迁移数据库，不新建全局图平台，不训练新的记忆管理器，不扩展认知／概率模块，不增加常驻Reviewer。不将`{}`自动转成候选写入，不执行模型推理草稿，不强制所有消息保存，不靠无限重复提案取得成功。保留必要的owner、版本、可见性和实际副作用边界，但不逐层重复检查完整对象或加入SHA替代品。

## 4. 信息交付的四层：可以直达，不强制四步走完

| 层 | 默认内容 | 使用边界 |
|---|---|---|
| L0 当前任务 | 当前请求、当前权限、查询时间／日历、当前完整事件或明确的待处理原文范围 | 当前更正不能只剩模型摘要；短消息可直接处理 |
| L1 候选目录 | 真实事项ID、版本、已有事项描述、已有主体线索、正文规模、条件／历史存在提示及可打开位置 | 只导航；不根据描述直接声称事实已确认或已保存 |
| L2 事项正文 | 选中事项的实际条款、必要条件、一般规则、相关例外、原支持和明确时间 | 首版按事项完整读取；不是截取数值而隐藏限制 |
| L3 原文／历史 | 实际来源区间及相邻语境、实际保存修订、相关Tool回执 | 原话、保存历史、有效历史、实时业务分别处理 |

目录描述优先复用已有`matter_description`或原文摘录，截断标明省略；初版不为了生成“漂亮目录”额外调用模型。已有主体信息可以显示；没有时不得把owner、登录用户、speaker自动填为被描述的人。

L0是始终可见的任务与权限，不是必须向模型解释的内部层级编号。用户无需选择“第几层”；Agent通过普通工具访问。简单问题可以直接使用已在当前上下文中的真实材料。

### 4.1 目录与正文的边界

`search_memory`在新交付模式下返回有界目录而不是全部K10正文；其排序仍复用当前dense。首轮固定候选池大小与既有比较一致，减少的是默认展开内容，不是让其他方法看不见候选。

目录只暴露查阅身份，不以此发行可执行业务引用或把正文标为已读取。实际`read_memory`／`read_source`仍通过原边界产生对应读回执及映射。

结果分页保留真实遗漏数及游标。未命中、未展开、当前不可见、当前确无足够证据须分别表达；不得把前两者扩大成“从未保存”。

### 4.2 开放事项的“必要语义包”

一次打开至少包含目标条款及已记录的相关条件；涉及例外时包含一般规则、例外范围、共享条件及活动／撤销状态。链接展开依据实际关系，不依据gold或模型凭空推断。

可表示为：

`当前目标 + 已记录的适用条件 + 相关一般/例外端点 + 对应来源引用`

它是可观察的局部材料包，不是“完整语义依赖已经穷尽”的证明。关系尚未结构化时，保留同事项完整正文并允许读原文，不靠缺少关系边证明内容无关。

超出软工作集目标时优先让完整语义包进入硬容量以内；超过硬容量时继续按原段落／单元分页，明确哪些未读。不可静默删除例外或用摘要替代必须保持的限制。

### 4.3 区分三种历史

- “我当时说过什么”：读取Source原文。
- “你当时保存了什么”：读取实际提交的记录版本。
- “那天适用什么”：结合真实断言有效时间和范围；报告时间不替代生效时间。

这是一般性的读取目标，不采用中文关键词或日期故事名称硬路由。模型选择查询目的，程序呈现实际数据。历史索引只是入口，不等于历史正文已经被交付。

## 5. 有界工作集：分开存档、可见上下文与任务进度

### 5.1 三个对象不能混用

| 对象 | 保存什么 | 生命周期 |
|---|---|---|
| 已读存档 | 原实际页面、来源、版本、回执、调用身份 | 持久保存以便恢复与解释，不因上下文换出删除 |
| 当前工作集 | 本次模型调用选中的正文、来源、目录和最近实际结果 | 可替换；每次调用重新构造，不不断追加旧正文 |
| 任务进度 | 当前任务、尚未处理事项或来源区间、实际提交引用、遗漏与未确认状态 | 放入既有checkpoint／维护记录；不是语义事实库 |

首版不要求模型生成长总结。事项完成后，可由程序保留`record_id/revision/receipt_id`和简短效果状态，把大正文换出。后续回答若需要具体事实，重新装入对应可见正文；“以前看过”的标记不能替代当前证据。

### 5.2 最小工作集操作

以下是内部设计接口，不是已经存在的新CLI：

```text
catalog(query)                     -> 现有候选的导航投影
open(record/source/revision/page)   -> 调用现有读取，装入实际材料
focus(selected_items)              -> 选择下次调用保留的已读材料
render(task, capabilities)          -> 构造当前真实模型输入
apply_existing_edit(proposal)       -> 原编辑器／事务／实际回执
```

`catalog/open`映射现有公共工具，`focus/render`尽量作为Host内部操作，不新增一组互相重叠的Agent工具。工具名称、字段只在原接口确实无法表达时做兼容扩展。

### 5.3 换出与重开规则

当前修改的来源、目标及必要条件在提交前保留；完成的无关事项优先换出。换出不删除Source、不撤销历史授权、不增加独立支持。

当前版本改变时，新任务读取新版本；已经发行的旧快照仍表示历史，不能重新贴成当前。工作集中的短别名只在其映射内使用，不把`r1/u1/e1`跨映射重新解释；提交绑定实际版本和当前映射。

遗忘后，重建工作集和恢复都通过既有可见性边界，缓存、摘要、Episode和已读存档不能让内容重新进入模型。

消息投影必须保留合法的工具调用／结果成对关系。可以从持久轨迹重建干净的下一轮请求，不能留下孤立ToolMessage或把计划概括成已执行动作。不把私有reasoning导出为记忆或正式编辑。

### 5.4 不重复发明读取进展机制

复用`read_progress()`的记录／版本／区间／游标身份，区分：新证据、同证据重新装入当前工作集、没有推进。重新装入已读证据有正常用途，不应一律禁止；但同一已在当前工作集的页面不必重复大段返回。

没有新证据时，直接利用现有材料回答，或说明还缺什么；不要在同一检索页无限循环。沿用调用方真实剩余调用额度，并留出完成答复的机会；不按每个事项重置额度。

### 5.5 根请求与探索查询分别绑定

当前部分入口会把公共查询绑定到原请求。新增探索查询应使用同一根请求下面的显式子查询／读取身份，不修改原始请求文本，也不通过禁用`PUBLIC_QUERY_CHANGED`允许漂移。

身份、owner、权限由根请求约束；查询内容可以在该范围内正常细化。检查在原边界执行一次，不为每个搜索词建立一套新的权限系统。

## 6. Writer管理：先减小同时处理范围，再比较语义算子

### 6.1 初版完整路径

1. 保留本次实际来源；两阶段模式最多先调用已有一次候选抽取。
2. 显示相关事项目录；模型选择要打开的事项，或者在真实空库／独立新事实时直接形成。
3. 打开选中事项和必要来源；编辑时使用当前事项对应的小schema。
4. 调用原全量／局部／追加实现提交；实际回执更新任务进度与当前视图。
5. 尚有独立变化时转下一个事项；已完成正文换出，当前新消息的未处理部分保留可达。

多个事项共享同一原文时，原文身份只出现一次，不重复算成多次独立来源。两个变化针对同一记录时，优先放在该记录的同一个修改容器，避免重复目标及部分冲突。

抽取候选是临时提示。候选漏掉内容不禁止Editor从真实原文处理；候选非空不要求强制写入。无意义的寒暄、纯查询和重述仍可不写。

### 6.2 保持三类编辑方法的真实含义

| 方法 | 编辑前实际需要看到什么 | 不允许的捷径 |
|---|---|---|
| B0／B2全量重写 | 被选中事项的完整替换范围及相应旧支持 | 只读部分正文，由程序暗中补完整张卡后仍称全量重写 |
| B1／M局部编辑 | 首版仍完整打开目标事项；后续可按明确局部读集扩展 | 把未送达单元标为已读、自动接受新语义关系 |
| Append-only | 当前真实新陈述及去重／时间解释所需旧材料 | 从候选摘要自动生成事实或静默覆盖旧卡 |

全量目标超过单次硬容量时，记录实际限制，不把它转成局部编辑掩盖失败。若必须改变记录组织，先形成新的共同候选，并在各方法从独立空库运行时采用，不能手工整理理想旧状态。

### 6.3 单元级局部读集的后续扩展

当前`_writer_packet()`要求整记录完整，必须显式处理这个实现边界。建议先交付事项级分层版本，然后在同一工作流中补充局部读集：

- 映射中仅列实际交付的可编辑单元及其关系边界；读取元数据不自动等于读取正文。
- 程序从实际版本复制未编辑单元及原支持，不让模型重新生成它们。
- 新值、关系改变、撤销仍由实际来源支持；不可从未展开正文自动借用新断言的依据。
- 条件变更可能影响多个内容单元，按已有关系显式展开，不局限于“只改一个字段”。
- 缺少必要边界时先读取，不使用gold补齐；跨记录语义依赖仍由模型选择，不启动全库传播器。

此扩展是新的局部编辑输入合同，实验必须单列其作用。首轮交付方式比较不混入该变化。

### 6.4 来源归属和身份：保留必要上下文，不建立固定姓名规则

每个活动事项保留实际speaker、被描述subject的已有信息、原文语气、报告时间、有效时间和计划／完成区别。模型选择证据，程序沿用实际来源属性；不让模型再次猜来源角色。

“来自Assistant”的元数据不能自动纠正正文中的“User reports”。对冲突精确值，保留其实际陈述归属和原User报告，不因出现顺序把后者升级为用户确认。身份关系必须有来源，不能从owner或评测题中的姓名填入。

原始Episode读取可用于找回遗漏身份，但只在协议允许时启用。检索找回与事后持久修订是两种动作：只读查询不能偷偷写库。

## 7. ReAct式调度：一个Agent的工具循环，不是新增审核团队

### 7.1 最小控制器

```text
输入：当前任务、当前能力、可访问记忆、既有调用预算
repeat within existing budget:
    从当前工作集构造下一次请求
    模型选择：读取 / 正式维护 / 直接回答 / 说明不足
    读取 -> 既有工具获取实际材料，更新当前工作集
    维护 -> 既有编辑器提交，记录实际结果，刷新受影响视图
    回答或不足 -> 返回真实输出与实际状态
```

不要求用户看到Thought文本，不把推理草稿作为命令。仅实际工具选择、正式提案、观察和答复进入执行合同。

控制器复用当前Host循环和调用方provider callback；不在Host内部再套一个拥有独立预算的Agent。benchmark适配器使用同一控制逻辑，不复制另一套语义提示。

**兼容现有维护阶段。** 当前`maintain_event`的旧模式承诺每来源批次至多一次抽取、一次编辑；新披露模式不能暗中改变旧结果的这一含义。[R5] 在新模式中，将目录选择与只读探索插入`locate → edit`之间；若一个事件需分多个事项处理，使用同一根请求下已持久化的少量工作项，来源不重复捕获，抽取不逐事项重跑。工作项及操作身份在调用前确定，重开沿用，不以页面顺序重新编号。已提交工作项不再生成；一次编辑未确认时先按原身份核对，不用新的工作项ID绕过未知状态。能在一个小工作包中处理的相关目标仍合并为一次编辑。选择、读取和各事项编辑全部计入同一调用预算，新版调用数量与旧每批一次协议分开报告。

### 7.2 保留简单快路径

已在当前工作集且足够的信息可以直接回答；空库中的短而明确的事实可直接形成；已知ID可直接打开。不强制每个消息先搜索，再读来源，再读历史。

一次完整合法读取即可完成的任务，不必采用ReAct的多轮探索。固定两阶段已达到同等效果时，保留更简单的方式。

### 7.3 正式空结果保持合法，但反馈不夸大

无回执空输出：`not_committed`。

有实际版本回执证明内容不变：`no_change`。

有实际提交回执：`committed`，只说明对应操作，不代表全部新要求完成。

当前没有写权限：如实返回本次未写，不能由旧请求恢复权限。

不新增强制“必须选择一个候选”的语义门禁。需要统计真实空输出与未完成请求，但不让模型自报的“全部处理”成为程序真值。

## 8. 生命周期衔接：重点补纯记忆任务，不重做已有业务恢复

当前已登记业务请求的空保存仍保持incomplete；PR #106明确指出，纯memory-only路径没有登记同一套application完整要求。[R2][R3]

本轮应在既有维护checkpoint中保留明确保存请求及其实际来源，允许“继续保存刚才那条信息”定位原任务。不要为纯记忆请求伪造业务对象或重建一个通用工作流引擎。

恢复时区分：

| 断点 | 处理 |
|---|---|
| 未发送模型请求 | 可在当前允许下继续原未处理输入 |
| 模型请求未确认 | 先核对原请求；需要新尝试时用明确新身份，历史unknown不覆盖 |
| 正式提案已保存但提交未确认 | 查询原操作回执，不重新生成或重复提交 |
| 部分事项已提交 | 保留已完成项，只处理当前允许的剩余事项 |
| 业务已完成、记忆未完成 | 读取实际业务结果，只补记忆，不重复业务mutation |
| 已完成但最终答复失败 | 以实际状态重新反馈，不重做原动作 |
| 来源已遗忘／权限改变 | 工作集重新检查可见性并服从当前限制 |

已读材料换出后，恢复重新读取原版本；不能把旧工作笔记当永久证据。Episode整理、用途激活沿用现有实现，回放不增加独立事实支持；本轮不扩展脑模拟或概率模块。

## 9. 容量与成本：峰值上下文和总工作量分开

### 9.1 不混用普通Host与benchmark配置

已读取的公共Host配置使用65,536窗口、8,192输出预留、24次消息调用上限、3次追加读取、8,192普通材料额度；公共prefix配置使用同窗口但32,768输出预留。实际被冻结运行的完整配置仍以其保存原件为准，公共配置不能代替私有实际参数。[R10][R11]

因此，新交付模式从调用方容量对象取得真实余量：

`当前输入 + 输出预留 + 原有余量 <= 模型窗口`

不能把32,256作为全部入口统一输入上限，也不能为了让ReAct成立自动增加读取次数、输出预留或总预算。

### 9.2 工作集软目标与硬容量

可在新开发配置中试用约8k的活动材料软目标，优先容纳一个完整事项及必要原文；这只是可调工程起点，不是人脑常数或新的运行许可。超软目标但未超硬容量时可保留完整必要材料；无法容纳时明确分页或受限状态。

模型真实请求的system、tools/schema、目录、活动正文、最近结果全部计量。不要只测材料字段，遗漏工具schema的成本。

### 9.3 最小观测

复用现有日志记录：每步输入／输出tokens、调用次数、实际读取ID／版本／区间、当前工作集大小、峰值输入、无新材料读取、实际提交／空输出／拒绝、最终回答和usage unknown。

总输入为各调用之和；峰值是单次最大值。ReAct峰值下降但总输入增加，必须同时报告。不将新选择或工具调度调用记为“免费”，也不以成本下降作为首版功能验收的必要条件。

## 12. 开发顺序：先完整候选，再集中评测

### P0 采用实际基线，保留暂停与历史

未来获准开发时先确认PR106是否已合并；未合并则将其一行反馈修复作为单独基础补丁，不重做。保留4e与505原结果。只记录本次实际代码版本和配置，不做文件摘要清单。

### P1 交付目录、事项打开和可替换工作集

Reader和Writer共用一个目录／读取投影；首版按事项完整打开。普通Host能完成查询、历史阅读、来源追溯以及一条记忆更正。短任务直接执行，不强制多阶段。

### P2 接通固定两阶段与有限ReAct

用同一读取层实现固定一次选择和动态继续读取。每次调用从工作集重建；沿用现有权限、provider、回执、调用配额与恢复。调整候选范围必须明确，不在默认模式偷偷改变K或来源权限。

### P3 补齐管理与恢复

纯保存任务的未提交说明与显式续办；旧版本、当前版本和来源的选择；换出后重新读取；来源遗忘；业务完成后的记忆保存。先做用户可见完整链，不等待每项先证明新颖性。

### P4 统一集中测试与方法选择

只有完整实现后才启动下面的开发集比较。真实模型运行依执行授权与实际可用资源；不把旧全部五方法评分结束当新实现的科学前置条件。

**局部读集扩展在P1–P3基础可用后实现，不与首次交付方式比较混在一起。** 首版即可通过“一次只展开相关事项”降低上下文；不必等所有语义局部性问题解决才交付。

## 13. 开发期检查只保留最小必要集合

修改期间只运行直接受影响的既有导入、类型、格式及功能检查。发现新bug时补一个最小复现，不围绕每个字段生成一批新准入测试。不重跑旧Judge来证明代码可导入。

合流后统一做五条冒烟，不把它们变成五个研究阶段：

| 流程 | 核心检查 |
|---|---|
| 保存→查询→重开 | 真实正文和来源可读；没有回执不得称已保存 |
| 更正→保留→历史 | 新变化落实；未改条件保留；保存历史不同于原始消息 |
| 一般规则→例外→撤销 | 打开目标时条件不隐藏；撤销不复活已失效规则；无整体到成员的推断 |
| 纯查询→换出→重读→遗忘 | 不偷写；已读材料可再装入；遗忘后不可由缓存恢复 |
| 部分业务→只补记忆→反馈 | 原业务不重复；当前权限有效；剩余保存与已完成业务分开 |

崩溃、数据损坏、越权、重复业务效果先修；一般语义错误记入问题表，继续其余流程后集中优化。检查通过不表示算法优势，失败保留不意味着无限延期功能交付。现有合并CI保持，取消额外人工添加的无关全矩阵要求，而非删除必要业务约束。

## 14. 集中实验：先证明交付改进，再检验编辑算法

### 14.1 三个交付对照

| 名称 | 方法 | 意义 |
|---|---|---|
| D0 Eager | 当前K10及相应材料的一次性装包 | 真实当前基线 |
| D1 Staged | 同候选目录→一次模型选择→打开选中事项→执行／回答 | 衡量简单分阶段是否足够 |
| D2 Progressive | 同目录→按需事项／来源／历史读取→有界工作集→执行／回答 | 衡量动态探索的净收益 |

D1选择一次后不反复检索；D2可继续读取，但都使用同一基础模型、实际前态、候选池、来源访问策略和最终编辑器。目录与选择调用也计费。首轮固定recipe和一个现成方法，不展开3交付×2recipe×5编辑器的大矩阵。

可采用B1作为不含条件关系的首个机制载体，并在M上验证集成；这是下一实验建议，不等于已选择B1为最终算法。选择过程须在看新结果前记录。

### 14.2 只读与写入分别隔离

**只读实验：**固定实际记录状态与原始问题，只改变交付方式。Reader不写库，避免把新维护收益混入读取结果。

**写入实验：**复制同一实际前态与当前来源，只改变交付；使用同一个固定Reader评价更新后的状态。保留输入原文和未改条件，不能由评估器预先注入正确记录。

如果同时换Reader表达和Writer交付，属于集成候选结果，不称单因素因果证据。

### 14.3 第一轮材料不另建大benchmark

从已有曝光案例预先选取覆盖：小输入空提案、长输入、普通值更正、未重述限定、多事项更新、局部例外与合法撤销、真实保存历史、资料不足。建议先用约8–12个实际事件／状态—问题对，另加五条功能冒烟；样本数是有限开发范围，不是统计功效声明。

不只选旧超限案例，不只选条件机制可能取胜的故事。保留小上下文错误，检验“长度并非唯一原因”。选择后不因方法失败替换案例。

同源多问题、多个格式和重复seed不计为独立历史。若一处身份漏写造成后续多题错误，报告根因及受影响题数，主QA分母仍完整保留。

### 14.4 来源权限的公平性

普通Host可以使用已接通的Episode原文路径，但当前benchmark的`include_raw=False`不是自动改成true。[R3]

第一轮机制比较在三组共同合法来源池内展开。若研究“原文辅助读取”，另立`source-assisted`设置，让Eager、Staged、Progressive都有相同原文访问能力；原作者主协议分数保留原名，扩展结果单列。

不得只给D2全原文、给D0语义卡，然后把收益归为ReAct。HaluMem的gold记忆、更新标签、未来问题只用于评价，不进入Writer；原作者使用参考更新文本的检索诊断也不得反馈修改历史。

### 14.5 评价指标与失败分层

主表保留：新要求完成、未改语义保持、非法强化／错误归属、合法撤销、完整QA和任务效果。官方指标按原定义与全部机会分母报告，有效Judge分母另列。

工程表保留：容量失败、正式空输出、拒绝、未确认、中断、读取未推进、峰值输入、累计tokens、调用和延迟。偶发无效输出不静默修补；真正空结果与解析失败分开。

空输出合法不等于漏写一定合理；`no_change`只由实际对应回执支持。索引命中、打开目录、程序字段存在和提交次数均不是语义准确率。

### 14.6 采用规则

- D1与D2相当：采用D1，不为ReAct名称保留额外循环。
- D2只降低峰值，却增加漏证：先修展开边界，不宣布优化成功。
- 长输入改善、小输入仍空：上下文策略有效但不充分；下一轮单独处理正式输出或维护选择。
- 各方式都读到正确材料却仍错：回到语义修订、主体归属或Reader解释，不继续调检索。
- D2在新要求、保持和QA上有净改善：作为共同交付候选，再比较B0/B1/B2/M/Append-only。
- 普通局部或强追加式同样有效：保留简单方法，缩小条件机制的主张。

功能可用性不要求先达到论文显著性；研究结论需要同版真实对照。基于四个开发用户的单次结果只做有限判断，不预告“稳定领先”。

### 14.7 长历史和外部确认后置但不取消

先完成新的开发交付比较，再选择一个候选沿自身实际状态运行65／277历史；65可作为同一次277运行的观察点，不重复收费。16个保留用户继续留到方法冻结后，不用于修目录或调prompt。

保留LongMemEval现有描述性子集、RawRAG、RollingSummary及已接入的A-MEM适配；不强制第一批重新部署全部外部项目。最后用同一候选做完整Host、业务恢复和新的故事确认。保留原计划未完成范围，但不让它们成为本轮每个小补丁的准入关卡。

## 15. 创新定位与反思

ReAct交替取证、MemGPT上下文换入换出、渐进披露本身已有研究与工程先例，不能把这些组件名称当作原创。[W1][W2][W3]

MiLAi值得检验的具体候选是：

> **在来源、范围与历史可追溯的前提下，用事项及其必要条件作为工作集单位，将读取与局部修订共同约束在实际送达的材料上，是否能减少持续记忆中的附带损坏和读取漂移？**

可能的贡献是“读写共用的条件保持工作集”和相应实证，不是新图数据库。它必须与普通两阶段、相同表示的普通编辑和强追加式对照比较。

保持自信的方式是提出具体机制并实现，不是预先宣称有效；保持思辨的方式是排除输入权限、材料量、更多调用和弱基线等替代解释。未开源或未正式发表的工作只影响可复现性和比较方式，不作为停止创新的理由。

认知上的类比限于“长期记录大、当前工作上下文小”；不设人脑容量常数，不把激活当真实性，不为概率形式新增一层自动事实晋升。
