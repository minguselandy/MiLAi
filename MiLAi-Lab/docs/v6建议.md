# MiLAi 当前评估：从“能够维护记忆”转向“能在真实任务中恰当地使用和维护记忆”

**当前最重要的进展，是普通记忆已经形成了真实可核对的创建—修订—取材—回答链。下一步最重要的工作，不是继续增加记忆类型，而是减少记忆管理对 Agent 正常完成任务的干扰。**

我建议把下一阶段的目标收敛为：

> **让同一个 ReAct Agent 根据实际观察，按需检索、局部修订、适时持久化；已有信息足够时直接行动，没有新依据时不制造记忆，有更新时不破坏其他仍然有效的认识。**

以下以最新上传报告为准。报告中的 **v6 是开发 Goal，实际方法版本为 v10、摄入协议为 v25**，不能与前面报告的方法 v6、v7直接混为同一实现。本文没有重跑实验或独立审计源码；现状判断来自报告，后续方法属于建议设计。

---

## 一、当前应该怎样判断：可以继续真实任务验证，但还不是自主记忆策略已经成立

### 1. 已经取得的进展，应当承认并保留

| 方面       | 最新证据                          | 准确判断                   |
| -------- | ----------------------------- | ---------------------- |
| 真实写入     | 最终执行了 11 次 CREATE、18 次 REVISE | 不再只是“接口存在”，已经发生实际维护    |
| 修订后的使用   | 当前理解进入搜索材料及答案                 | 指定错误的修复链已经形成           |
| 主体归属     | 三个指定案例达到本轮归属要求                | 限定回归通过，不等于一般人物理解已经可靠   |
| State 接线 | State 内容实际进入有效查询              | 接线成立，但不是自主选择何时使用 State |
| 最终评分     | 三个原题、五条路径全部通过                 | 开发回归通过，不是五个独立样本上的泛化证明  |

这些结论都由最终记录支持。尤其值得保留的是：报告没有把自然一批中的零次 REVISE 误判为失败，也没有把普通修订当成 H1—H6 的验证。 

**因此，不应再把“模型根本不会修订”作为当前主要诊断。**

但也不能据此认定长期运行已经稳定：最新五条最终路径涉及的是 12—14 条消息的短历史，不是对先前完整长历史案例的同版本重新验证。

### 2. 当前的核心缺口，不是更多机制，而是三个“适当”

**适当的维护单位：**修改哪一项认识，而不是重写整个人的画像。

**适当的证据强度：**哪些是用户陈述，哪些只是模型解释，哪些只是尚未执行的建议。

**适当的行动时机：**现在应该查记忆、改记忆，还是直接调用业务工具完成任务。

当前实验对前两项暴露了实际问题，对第三项主要验证了适配器编排的流程，还没有充分验证自主策略。

## 二、最需要重视的四个问题，以及它们背后的原因

### 问题一：记忆仍容易退化成“滚动人物小传”

报告显示，v1003 的一张卡同时包含志愿服务、AI 法律、隐私、就业、影视和讨论组；v977 自然批形成五张事项卡，在线更新却逐步聚为一张宽卡。

这次没有因此失分，但它对持续使用不利：

> 后续只想修改一个事项，却必须重新生成多个无关事项；读取一个偏好，也会带入大量不需要的内容。

**可能的原因是，系统虽然要求“同一事项才修订”，但交付给模型的旧对象仍然更像一段相关人物叙述，而不是一个边界明确的可维护事项。**这是架构推断，不是报告已经完成的因果验证。

这里不应该继续追加“不要过度合并”这一句提示。报告已经说明现有提示包含相同要求。

### 问题二：有来源的文本，被模型写成了比来源更强的认识

最终 v1003 卡把 AI 兴趣进一步解释为最初从事志愿工作的动机；全部 11 张当前卡的 certainty 都是 `explicit`，但正文包含模型推断。

这说明：

**来源绑定解决“这段表达引用了什么”，尚未解决“表达强度是否超过了依据”。**

当前 assistant-only 持久用户事实边界有价值，但混入一条 user 来源，不会使整段因果解释自动成立。

真正需要改进的不是再增加一个事实审核 Agent，而是让模型更容易表达：

> “用户分别说了 A 和 B；目前没有依据断言 A 导致了 B。”

### 问题三：State 还可能把假设带入检索，并反过来影响取材

最终 State 在第一次读取前写了“没有相关历史”，实际记忆却存在相关内容，而且这段否定进入了有效查询。结构化 coverage 仍为 UNKNOWN，所以本次没有跳过检索，但文本状态与实际观察不一致。

这类问题的危险不只是“State 写错一句话”，而是潜在的循环：

```text
尚未观察
→ 被写成不存在
→ 进入查询或筛选
→ 更难取得反例
→ 原判断被继续保留。
```

报告尚未证明整个循环已经发生；但应当在把 State 升级为主动控制器前处理这个风险。

### 问题四：当前证明了“按流程调用”，没有证明“知道什么时候值得调用”

State 路径由适配器要求先执行 `memory_state`，再执行搜索；同题作答 tokens 比 ordinary 高约 54.6%，两者都通过，且历史分别构建，不能归因成 State 的独立开销或收益。 

**这不是说 State 没用，而是其价值问题尚未被正确提出：**

> 它应该解决某个正在发生的信息缺口，而不是成为所有任务必经的开场手续。

## 三、真实 ReAct 对记忆提出的要求，与“先建库再答题”不同

ReAct 的关键是推理与行动交替进行，行动产生的新观察会改变后续计划；它并不要求固定执行一套“先思考、再搜索、再记录”的工具模板。原论文的交互任务也强调根据环境反馈调整行为。([react-lm.github.io][1])

所以，MiLAi 需要服务的基本过程应是：

```text
理解当前任务
→ 判断下一步需要什么
→ 直接回答、使用业务工具，或访问记忆
→ 观察实际结果
→ 修正当前判断
→ 必要时维护长期记忆
→ 继续任务。
```

而不是：

```text
任何输入
→ 提取用户画像
→ 更新 State
→ 搜索记忆
→ 重新整理记忆
→ 最后才尝试完成任务。
```

CoALA 也把访问内部记忆和操作外部环境放入同一个决策过程。因此，**记忆操作应是 Agent 可以选择的行动，而不是独立于任务、必须先完成的一套仪式。**([arXiv][2])

### 我建议采用一个中心原则

> **任务进展优先，记忆维护有依据，额外管理有理由。**

这不是降低来源、版本或权限要求。它意味着这些确定性约束由程序承担，而模型主要决定三件语义工作：

**现在缺什么？新观察改变了什么？什么值得在以后继续使用？**

# 四、建议的方法：观察驱动、事项局部、按需取材

不必为下一版创造一个复杂的新名字。可以把方法直接描述为：

> **基于实际观察的局部记忆维护：以当前任务状态承接临时判断，以可独立修订的事项承接持久认识，通过同一 ReAct 循环按需读取和更新。**

下面是最小完整设计。

## 1. 保留三个用途，不新增三套存储系统

| 用途         | 保存什么                      | 默认不做什么           |
| ---------- | ------------------------- | ---------------- |
| **原始观察**   | 实际收到的用户输入、取得的文档、工具返回及其身份  | 不把全部观察自动升级为永久知识  |
| **当前工作状态** | 任务目标、当前约束、已经看到的结果、待解决问题   | 不把猜测直接写成用户属性     |
| **持久理解**   | 有后续复用价值的偏好、项目约定、已验证范围内的经验 | 不持续复述整段对话或整个思考过程 |

这可以直接复用 Observation、TaskState 和 MemoryCard／Interpretation。

LangGraph 的官方设计同样区分线程内状态与跨会话记忆；但这种分层本身不是新的方法贡献。对 MiLAi 更重要的是让每种内容进入正确生命周期。([Docs by LangChain][3])

**一个重要补充：任务状态被 checkpoint 保存，不等于它变成了永久用户画像。**中断后继续同一任务可以恢复；开始无关新任务则不应自动继承。

## 2. 记忆单位改为“可独立修订的事项”，而不是“一句话”或“一个人物”

建议判断标准是：

> **如果这部分内容改变了，另一部分可以继续保持原样，它们就有理由分开维护。**

例如：

```text
事项：影评博客的当前状态
事项：fan-trailer 创作经历
事项：当前观影方式偏好
```

三者可以相关，但不应仅因同属电影话题就合成一张不断增长的卡。

写入目标交付可以先用现有字段组织为：

```text
事项：影评博客的当前状态
主体：当前用户
当前理解：已经停止更新，不再作为当前活动
适用范围：影评博客，不涉及其他电影创作
依据：……
目标版本：……
```

**首版不需要主题注册表、本体、实体图或新的拆分算法。**先让现有候选卡以这种方式呈现，允许自然 CREATE，继续使用已有 REVISE。

已有宽卡也不需要全库重新整理。只有被实际修改或明显妨碍使用时，才处理相应部分。没有充分依据时，不应为了“局部化”把原卡中的其他内容丢掉。

官方记忆设计也指出，持续扩大的单一 profile 与记录集合各有代价：前者更新容易变重，后者需要处理过度新增、过度更新和检索关系。这正说明“全部拆小”也不是答案。([Docs by LangChain][3])

## 3. 持久正文表达认识，引用结构表达依据

当前持久正文仍残留 s0、s2 等批内别名，虽然底层 `source_refs` 绑定准确，但正文脱离批次后无法解释。

建议继续收敛为：

**正文可独立阅读；结构字段保存引用；展示时由程序生成本轮引用入口。**

不要在自然语言正文中要求模型反复抄写来源编号，也不要用正则盲目替换所有类似 `s0` 的字符串。对于需要逐段归属的内容，再使用明确的结构引用，不提前把所有记录改成句级证据图。

## 4. `explicit` 表示陈述来源，不表示系统认证正确

首版可以不增加复杂评分模型，只调整表达要求：

* 直接陈述与推断分开表达。
* 不必要且无依据的动机推断直接省略。
* 有价值的假设可以保留，但必须保持为假设。
* 混合了重要推断的记录，不能因其中有直接陈述就整体标为 `explicit`。

也不要反向走极端：把所有记录标为 `uncertain`，再靠少用记忆降低风险。**目标是表达强度与依据相称，不是普遍降低置信度。**

# 五、把记忆放回真实 ReAct：什么时候读、什么时候写、什么时候什么都不做

## 1. 默认不强制独立 State 开场

当前上下文若已经给出任务目标和约束，Agent 可以直接搜索或操作业务工具。

只有遇到目标变化、跨步骤待办、材料冲突或需要保留明确缺口时，才显式维护 State。

建议的行动规则如下：

| 当前情况             | 推荐行动                  | 不应强制附加的动作         |
| ---------------- | --------------------- | ----------------- |
| 已有材料足以完成任务       | 回答或执行业务工具             | 再搜一次记忆、再写一次 State |
| 缺少过去的用户／项目信息     | `memory_search`       | 先写一段“没有历史”的判断     |
| 命中摘要，但范围、时效或依据不清 | `memory_read` 原文／相关版本 | 全库重新整理            |
| 用户只改变本次任务要求      | 更新任务上下文               | 永久修改一般偏好          |
| 新来源明确改变了某项持久认识   | CREATE 或 REVISE       | 更新所有语义相似卡         |
| 当前只是提出建议或计划      | 暂留工作状态                | 记成用户采纳或行动已完成      |
| 工具给出真实结果         | 先使用结果继续任务；有复用价值再保存    | 把每条返回都压成长期经验      |
| 没有新依据、没有值得保留的变化  | 不写入                   | 为提高“机制使用率”制造操作    |

**零次写入可能是正确行为。**最新五条答题路径没有 `memory_save`，对这些查询本身不构成问题；但也不能据此证明面对新反馈时一定不会误写，或一定能够及时写入。

## 2. State 只记录已经知道的事与待查问题

首轮可以是：

```text
目标：完成当前客户报告。
已知约束：本次外发只写结论。
待查：这是一次性要求，还是该客户的长期约定？
检索情况：尚未检索。
```

不应该是：

```text
该用户没有相关历史。
```

而且，**State 的全部自由文本不应无差别拼进查询。**

查询优先使用当前问题、明确实体、任务范围和待查概念；“没有证据”“可能不存在”等推测不应变成排除性条件。

这不是屏蔽否定句。例如“用户明确不想参加集体活动”可以是重要检索内容；区别在于它来自真实材料，还是来自尚未观察时的猜测。

## 3. 工具结果先进入工作状态，不自动进入用户画像

真实 Agent 必须区分：

```text
我建议这样做。
我已经发起操作。
工具返回执行成功。
结果通过了某项检查。
用户确认这符合需求。
```

这五件事不是一个事实。

例如，一次文档检查通过，只支持：

> 这份文档的这个版本通过了这个检查。

它不支持：

> 用户满意；所有后续文档都应该这样写；这个方法在所有项目上有效。

同样，工具超时不证明操作一定没有发生；后续应依据工具能力核对状态，不能直接把“失败”永久记成事实。

这类判断不需要新增结果审核 Agent。首先应由工具回执提供准确执行状态，再由同一 Host 根据实际范围形成表达。

## 4. 保存时机采用“自然边界”，而不是每一步都整理

建议保留三种明确的同步写入机会：

**用户明确要求记住，或明确修改长期约定时。**在声称“已经记住”之前取得成功回执。

**任务中发现旧理解会继续误导后续行动时。**读取正确目标后局部修订；不能只在当前回答中绕开。

**形成有后续价值的结果，或需要中断续接时。**保存简短事项或工作状态，而不是整段推理。

其余时候允许不整理。原始来源是否长期保留，仍遵守现有保留范围；不能把“接收了来源”说成“已经永久保存”。

LangMem 将在线写入明确视为一种延迟和任务负担上的取舍。这支持选择写入时机，而不是要求每个回合都进行一次记忆维护。([LangChain AI][4])

**当前不需要后台服务、夜间反思或第二个记忆模型。**

## 六、最小执行结构：一个 Host、已有工具、真实观察驱动

下面是目标逻辑，不是本轮已经实现的代码：

```text
接收合法输入，登记实际来源，恢复当前任务状态。

循环：
    组织当前目标、近期真实观察、工作状态和已取得材料。
    由同一 Host 选择下一项行动。

    若可直接完成：
        返回答案或完成结果；不强制附加记忆操作。

    若需要外部行动：
        执行业务工具。
        将实际回执交给 Host，继续任务。
        不自动把计划、失败推测或工具文本升级为长期事实。

    若需要记忆：
        执行 search / read，返回当前理解及必要依据。

    若需要维护：
        提出 CREATE / REVISE。
        程序验证来源、目标版本和执行边界，返回真实结果。

    若无法继续：
        明确缺失信息或实际失败；
        不伪造成功，也不通过无限记忆调用拖延任务。
```

其中，程序可以记录“工具完成”“版本改变”“材料取得”等确定性状态；**语义判断仍由 Host 完成，不应写成程序自动验证了理解正确。**

也不需要要求模型公开或持久化完整思考过程。记录简短行动理由、实际工具调用、来源和结果，通常更便于诊断，也更不容易把猜测累积成事实。

# 七、一个真实使用案例：记忆应当改善工作，而不是成为另一项工作

下面是建议的开发场景，**不是已经运行的实验**。

任务是用本地文档工具维护项目报告，工具实际读写文件并返回检查结果。

### 第一轮：处理一次性要求

用户说：

> “这次给客户 A 的变更说明只写结果，内部迁移记录仍保留原因。”

Agent 可以查看相关项目记忆和文档。已有一般约定要求详细解释，但当前请求只覆盖本次外发材料。

正确做法是：

**采用任务覆盖完成本次报告，保留内部文档要求，不把“用户普遍喜欢简短”写进长期记忆。**

### 第二步：遇到工具反馈

文档检查发现缺少必要的“适用范围”章节。

Agent 根据真实回执补充并再次检查。此时记住的是任务进展，而不是：

> “客户偏好增加适用范围章节。”

工具规则与客户偏好属于不同来源。

检查通过后，可以记录文件版本、检查结果及必要的续接信息；不能因此宣布用户已经认可。

### 第二轮：收到真实长期反馈

用户后来明确说：

> “以后客户 A 的外发材料都采用这种结论式写法，内部材料不变。”

这次才有依据修订持久事项：

```text
事项：客户 A 的外发材料表达要求
当前约定：结论优先
范围：客户 A 的外发材料
不改变：内部技术记录的解释要求
依据：本次明确反馈
```

### 第三轮：新任务复用

新会话再次制作客户 A 的报告时，不需要用户重复这项约定；但制作内部迁移记录或客户 B 的材料时，不能无条件照搬。

**这样的连续过程，才同时检验了记忆的适用性、更新、保持、后续复用，以及真实任务完成。**

它比“强制调用一次 State，再答对一道问题”更接近你现在需要的能力。

# 八、可用性优先：记忆维护失败，不应无条件拖垮当前任务

建议明确以下降级行为。

| 失败                 | 应如何继续                  | 不能声称什么             |
| ------------------ | ---------------------- | ------------------ |
| 检索没有命中，但当前输入已足够    | 依据当前输入继续完成             | 不能宣布用户从来没有相关历史     |
| 写入被拒，但新事实已经在当前上下文中 | 当前任务可继续使用新事实；持久化失败单独说明 | 不能说“已经长期记住”        |
| 旧记忆与当前明确要求冲突       | 核对适用范围；本次合法要求先进入任务状态   | 不能机械覆盖全部长期理解       |
| 找不到完成任务必需的信息       | 定向读取、必要时询问，或说明具体限制     | 不能为了完成率编造缺失事实      |
| 多次操作没有新材料或有效变化     | 改变有理由的行动，或结束并报告限制      | 不能继续换同义 query 制造进展 |

这不是重新设置全局预算硬停止。最新报告明确说明累计硬停止已经解除；下一步应尊重这个设置，同时维持单次模型容量、工作流可继续性和可解释的停止条件。 

**“可降级”也不等于把全部失败都改算成功。**任务结果与记忆结果应分别记录：

```text
任务完成，记忆未保存；
记忆更新成功，任务未完成；
二者均完成；
二者均未完成。
```

# 九、成本优化：优先减少管理性输入，而不是压缩用户所需内容

最终验证中，输入占生成模型 tokens 的 94.0%，作答阶段达到 97.3%；材料元数据约占交付材料的 40.7%。这些数字支持优化公共表示，但还不能证明具体某部分导致了全部开销。 

建议顺序是：

### 第一，去掉没有决策价值的重复说明

完整散列、重复对象身份、空字段、同一回执中的多次正文，优先留在程序制品中。

Host 需要的是：

> 什么内容、谁提供、当前什么状态、适用哪里、怎样继续读取。

不是内部对象的全部序列化。

Anthropic 的工具设计经验也强调语义明确的标识和简洁／详细视图，而不是默认向模型展开所有内部字段。([Anthropic][5])

### 第二，让下一轮取得“增量上下文”，但不急着重启复杂差量机制

先检查已有请求中的实际重复：

**重复工具说明、同一轮重复正文、宽卡被完整重写、State 的额外起始回合。**

不要立刻新增缓存层、复杂历史裁剪或 H5 控制器。最新报告也没有测得事务复制是主要瓶颈。

在长任务中，确实需要压缩工作上下文时，应保留目标、未完成动作、关键结果和可重新读取的引用。后续无法确认旧材料仍在模型窗口内，就允许重新读取；不能仅凭“以前展示过”永久抑制。

按需取得材料与结构化工作笔记已有明确工程先例，但其成本和信息保持仍需在自身任务上测量。([Anthropic][6])

### 第三，减少不必要的维护回合

**一次无需调用的 State，可能比精简几十个引用 token 更值得优化。**

同理，没有新依据时不重写宽卡，比先把宽卡重写后再压缩更直接。

但减少调用不能以漏记明确长期反馈为代价；最终应比较“完成同一任务并维持必要记忆”的总成本，而不是单次操作价格。

# 十、下一阶段的最小验证：保留三题回归，再增加一种真正的连续工作证据

不建议立即扩大到多模型、多个 Agent 环境和全部候选。

## 1. 先完成四项针对性修复

| 优先项      | 最小改动                         | 验证重点           |
| -------- | ---------------------------- | -------------- |
| 事项边界     | 改善旧目标的事项、范围和依据交付；允许独立 CREATE | 改一件事，不覆盖无关事项   |
| 证据强度     | 直接陈述与推断相称，减少无依据因果连接          | 正文正确性不再仅依赖引用非空 |
| 引用表达     | 临时别名退出持久正文，结构引用保持准确          | 脱离批次后仍可理解      |
| State 行为 | 取消默认强制开场；未知与不存在分开            | 只有实际缺口才增加管理动作  |

这些都是现有模块内的修改，不需要新的类型体系或审核 Agent。

开发仍可复用已暴露案例，但不能把修复后再次通过称为新增独立证据。最终三题已经反复用于迭代，报告也明确没有建立单项因果与泛化。

## 2. 再安排一个小型真实工具任务链

优先选择本地工作区任务，例如：

**读文档 → 修改内容 → 执行检查 → 处理反馈 → 新会话续接。**

工具应真实执行，不能用人工编好的“执行成功”字符串冒充结果。用户反馈可以预先固定，但必须与 Agent 已观察到的历史范围一致。

它作为工程与使用诊断单独报告，不混入 MemSyco 的原生分数。

评估重点是四项：

| 维度        | 具体问题                       |
| --------- | -------------------------- |
| **任务结果**  | 文件或实际操作是否达到要求，而不只是回答说完成了？  |
| **记忆适当性** | 是否误把建议、尝试、失败猜测写成事实？        |
| **跨任务保持** | 新会话是否记住需要保留的约定，同时不携带一次性例外？ |
| **额外负担**  | 记忆管理增加了多少调用、输入、等待与失败机会？    |

这类“检查实际环境结果”的方向与 τ-bench 通过最终数据库状态验证工具任务的思路一致；但 τ-bench 本身不是对你跨会话记忆机制的现成证明。([arXiv][7])

## 3. 对照先少而强

真实任务的第一轮可以只比较：

**当前 ordinary** 与 **轻量的新运行策略**。

这是系统可用性比较，不应归因成某一个模块的新算法收益。

随后需要恢复研究结论时，再加入强原文检索，并固定同粒度记录、相同合法信息和可比预算。

单独研究 State，则应从同一份兼容历史产物创建独立执行副本，只改变读取侧策略；不能直接使用当前分别建库的两条路径，也不能靠改写所有权标志强行共享。报告已经明确这种差别。

**不要为了证明 Agent 自主，就要求它必须走某条固定工具序列。**正确任务可能存在多种有效路径；工具评估也应避免把某个预期策略当成唯一正确策略。([Anthropic][5])

# 十一、对研究方向的总结性调整

原先“迟到澄清—支持关系修订”的方向仍值得保留，但现在不应该让整个运行系统围绕它旋转。

建议区分两层：

**系统层：**提供来源准确、事项清楚、按需使用、可局部修订的记忆能力。

**研究层：**在确有迟到澄清和独立支持的情况下，检验显式支持修订是否超出普通局部更新的能力。

先把普通路径用好，再激活 H1、H2。否则复杂机制只能叠加在宽卡、过强解释和强制控制流程上，其真实价值很难被看到。

当前最有启发性的科学问题，可以重新表达为：

> **对持续工作的 Agent，什么情况下值得把一次观察转化为持久理解，什么情况下只应保留为任务状态或原始材料？这种选择能否减少错误写入和后续重复工作，而不牺牲及时适应？**

这是一个可研究的问题，但“按需写入、任务态与长期记忆分离”已有先例；不能仅靠这个表述认领方法创新。真正贡献仍要来自具体选择机制和对照证据。

# 最终建议

**保留现有 ordinary、来源绑定、版本保护、冻结制品和实际失败记录。下一版不推倒重建，不新增候选，不扩张到通用记忆平台。**

优先完成三个变化：

**第一，把记忆从“按人物和话题累计叙述”改成“按可独立修订的事项维护”。**

**第二，把 State 从固定前置步骤改成真正的工作状态：只表达已观察内容、明确约束与待查问题，不把猜测变成检索事实。**

**第三，让持久化由真实新证据和复用需要驱动：建议不是采纳，计划不是完成，工具成功不是用户满意，当前例外不是长期偏好。**

这三项比增加更多记忆事件、支持计算或反思步骤，更直接地服务真实 ReAct。

**最终验收不应是“用了多少次 memory 工具”，而应该是：Agent 更少要求用户重复背景，更少重复已经完成的工作，能够接受新的变化，且不会因维护记忆而把本来能完成的任务做坏。**
