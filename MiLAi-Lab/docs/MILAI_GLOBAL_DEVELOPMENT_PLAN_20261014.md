## 01｜执行摘要：先做什么，为什么做

**总目标：让 MiLAi 在持续变化的长历史中，以必要而不过量的证据支持正确任务结果，同时正确维护当前状态和历史。** 研究核心是“哪些信息值得维护、变化影响哪些含义、回答需要哪些证据”，不是增加记忆层级、操作数量或验证平台。

首轮只推进三个可以落到正常调用链的改动：原文检索不再扫描语义形成历史；中文检索使用一致的实际分词；细粒度命中后交付自包含证据片段，而不是默认打开整份会话或整条事项。模型接入、字符 patch、语义总结和更大实验矩阵均不作为这三个改动的前置条件。

| 开发次序 | 首个可交付结果 | 最快能回答的问题 |
|---|---|---|
| A：检索基础 | 新的原文查询路径与中英文检索样例 | 查询是否真正找到相关来源，是否去掉无关历史扫描？ |
| B：证据交付 | 同一批来源按问题交付必要片段和关联条件 | 是否减少主 Reader 输入、调用与遗漏？ |
| C：状态维护 | 独立命题与完整受影响含义的更新 | 是否同时改对目标、保留非目标、保存历史？ |
| D／E：按需视图与共享入口 | 有用的当前状态视图；Benchmark 与 Host 共用核心 | 语义层是否有独立贡献，实验收益能否进入正常使用？ |
| F：策略学习 | 针对已定位瓶颈的选择或更新策略 | 训练能否优于简化后的非训练方法？ |

A、B 构成主线，C 可并行。D、E 随实际功能需要接入；F 属于条件性研发。每完成一个功能切片，就运行直接相关的少量真实案例，不等整套方案完成再取反馈。

**第一批不做：**不建新审核 Agent、通用策略框架、第二套来源库、通用知识图谱、额外账本或 CPU 大模型推理优化平台；不为所有历史模式补一套新兼容层；不把全仓清理、全量 Oracle 或全部旧实验补完作为编码门槛。

## 02｜基线事实与架构取舍

### 2.1 已有能力不是待办

现有 Lab 已包含独立 Source 检索、语义记录与历史版本、条件与例外关系、引用式保留、`single_pass`／`extract_then_edit`、S0／S1／S2、J1-budgeted、排序适配和可选 `patch_text`。开发应复用它们，不能把“再次实现相同能力”记为新进展。[R2][R3][R4][R6][R7]

Product 与 Lab 也不是同一个运行时：Product 的正常 `agent-memory` 路径向外部 Host 提供证据上下文；Lab 自己实现了 Reader 和实验编排。本规划先统一 Lab 内部的方法代码，之后通过 Product 的公开边界接入，暂不进行数据库迁移或合并两套运行时。[R10][R11]

### 2.3 从事实到决策

保留来源、版本、条件关系与实际回执底座。调整三件事：把粒度协调放在新算法接入之前；让语义状态承担当前适用性和紧凑表示，而不是重复原始叙事；用任务收益与全生命周期成本决定是否维护和使用状态。

旧 S2、J1、patch 和排序接口作为显式实验选项保留。新配置明确选择起点，不全局改默认值，也不把历史结果隐式迁移到新条件。短历史无收益不作为最小长历史机制实验的否决条件；只停止重复扩大已经没有信息价值的同类试验。

## 03｜目标架构与最小数据语义

### 3.1 四种粒度分开设计

| 层次 | 基本单位 | 应承担的工作 |
|---|---|---|
| 存储层 | 原始事件、来源与不可变版本 | 保存实际观察、支持精确重开与可见性处理 |
| 编辑层 | 可独立变化的完整命题及其条件 | 变更目标含义，保留不受影响的信息 |
| 检索层 | 自包含交流片段、命题与事项线索 | 找到可能回答问题的具体位置 |
| 交付层 | 回答问题所需的证据组合 | 携带主体、时间、条件与必要原始支持 |

命题拆分不等于逐字切碎。否定、量词、主体、指代和适用条件必须随命题保持；句子不完整时扩大到完整表达或交流上下文。反过来，命中一个 unit 也不应无条件把整个 record 送入最终输入。[R4][R6]

### 3.2 正常路径

```text
来源：已捕获且当前可见的原始 Source
检索：原文片段 ＋ 必要时维护的命题、条件和状态视图
读取：问题 → 候选位置 → 必要证据组合 → Reader／Host
结果：回答或真实行动
补读：仅针对明确缺口，回到候选选择与证据组合
```

首轮仍由一个 MemoryService 门面拥有来源与状态。新证据组合在请求内构造，索引与缓存可重建，不建设第二个事实存储。原始来源存在不代表永久保留；用户的可见性撤销与删除语义继续适用。

### 3.3 来源、状态、计划、事实的区别

来源报告时间、实际事件时间、生效区间和提交时间分别解释。状态是对来源的当前解释，不是外部世界真值。计划、推测、愿望、用户自述、工具观察分别保留其含义，不因格式合法而升级。

历史问题按所问时点取可用版本；来源到达顺序限制当时能知道什么，生效时间解释当时适用什么，二者不能互相替代。重开历史仍服从当前的来源可见性，不能借旧快照读回已经撤销的正文。

### 3.4 模型与程序的职责

模型决定问题需要哪些事实、事件改变什么、哪些限定相关、哪里仍不明确。程序完成真实身份和版本绑定、原件读取、预算计量、无歧义的引用式保留以及实际提交。

不要用程序猜测自然语言真假，也不要让模型重新生成程序已知的 ID、时间元数据和保存回执。将必要检查集中在外部输入、来源读取和提交边界，不在每个内部辅助函数反复检查同一份已规范化数据。

## 04｜开发工作包 A：原文查询基础

**目标：**建立能够作为长期方法参照的原文路径。先消除中文分词与无关扫描问题，再谈大模型重排。

**主要代码位置：**`memory/service.py` 的 `sources()`、`search_sources()`；`memory/retrieval.py` 的 `flat_bm25_rank()`、`raw_exchange_units()`；现有 `tests/memory/test_source_retrieval.py`。当前源码中原文查询会取得形成状态，BM25 使用空格切词；这两个问题均有直接代码依据。[R3][R4]

### A1：把可见来源枚举与形成状态计算分开

首个提交增加或提取一个仅枚举可见 Source 的内部路径，供 `search_sources()` 使用。`sources()` 的原有形成状态展示可以保留，但不再是检索必经步骤。来源正文、排序所需时间和 owner 范围不变。

本步骤不改数据库结构，不重新生成语义记忆。先比较相同银行、相同问题的返回来源与查询耗时，确认改动删除的是无关工作，而不是遗漏应检索的来源。

### A2：中英文采用一致的检索分词

复用或提取现有 `_lexical_tokens()`，查询与候选使用同一种规范化。中文不能把整句当作唯一 token；英文大小写、标点与数字处理也应一致。原文正文不被改写。

保留历史 RawRAG 的固定分词条件以支持旧实验；新的检索策略只在新开发配置显式使用。首轮以词法召回为主，已有 dense 可作为并行候选来源；先测召回缺口，不默认增加 query-rewrite 模型。

### A3：按实际耗时决定是否做增量索引

当前 BM25 查询会重建索引，语义检索包含 Python 全扫描。第一批只记录已有查询的建索引、检索和打开材料耗时。若重建开始占用明显时间，再复用当前缓存设施，以来源身份和新增／撤销事件更新检索键。

缓存只保存可重建的检索数据；命中后仍通过现有来源读取路径取得实际正文。不要为了预测的规模问题提前部署新向量数据库。

### A 的最小实验与完成条件

先跑一组中英文正常查询，包含无空格中文改写、同名主体、否定句、工具来源和超过候选配额的历史。再用一段已有开发用户的较长前缀做真实查询。样本可从 8—12 个问题起步，数量是反馈预算，不是验收门禁。

完成条件：正常路径返回预期相关来源，原文检索不再计算形成状态，相同来源读取仍可用；报告命中、错配与成本。若召回已经足够而答案仍错，转向 B，不继续堆检索器。

## 05｜开发工作包 B：自包含证据组合与短读取路径

**目标：**让细粒度命中真正减少模型工作，而不是只改变大材料的顺序。

**主要代码位置：**`memory/retrieval.py`、`memory/reader_projection.py`、`memory/working_set.py`；`runners/edit_benchmarks.py` 的 `_source_first_materials()`、`_rank_materials()`、`_answer_view()`。共享读取策略在本工作包需要修改时才提取到 `methods/`，不预先重构整份 runner。[R4][R5]

### B1：优先交付自包含的交流片段

用现有 `turn`／交流边界形成检索候选，保留与用户语句相连的必要助手或工具回复。单元命中时打开命中命题、其实际条件／例外关系和必要支持来源，而不是无条件返回整条事项。

片段必须带可解释的主体、来源角色、实际时间与原文范围。遇到代词、跨句否定、共同前提或同轮澄清，扩大到语义完整的上下文；不以截取前 N 个字符冒充完整证据。粗 session 仍可作为补读入口，不要求一次性删除旧分段方式。

### B2：将事实载荷与内部操作信息分开

模型默认接收短标签、事实正文、相关角色／时间／条件和必要的支持片段。数据库定位、长 ID、完整内部映射保留在程序侧，由已有短引用绑定。审计信息可以继续保存，但不因已经保存就全部进入每次模型输入。

语义视图与其支持来源构成一个可选证据组合。程序只沿已存在或本次明确给出的关系带入依赖，不自动根据文本相似度生成“支持”。补入多少原文由本题需要决定，不把该视图的全部历史来源重复装入。

### B3：从全池分页改为有目的的选择

候选描述用于定位，不当作最终事实。选择阶段输出必要条目及优先顺序，现有预算函数按整体输入成本准入；准入结果和实际排除项反馈给同一读取流程。默认不再先按“所有原文优于所有语义”固定分组。

首个 MVP 保留现有模型，先在预算内选出一组证据并回答。只有出现明确缺口，例如主体不明、缺旧版本、缺条件、缺实际业务观察，才发起补读。正常 lookup 不要求读完全部 pending；计数、穷举或范围完整性问题则需要覆盖声明的查询范围，不能把普通 lookup 的提前停止复用成完整性证明。

停止条件由当前证据与任务决定，不由“材料处理流程已经走完”决定。补读仍计入同一个查询总预算，耗尽时给出实际可回答的部分与缺口。

### B4：固定最终回答目标

最终 Reader 始终接收原始问题和明确的用户约束。分页生成的 `read_goal` 只作内部取证计划，默认不作为最终问题改写；需要传递时单独标注为计划而非用户要求。对照试验固定最终目标文字，以隔离选择策略的真实影响。[R2][R5]

### B5：伴随修复现有排序接线

排序容量不足、排序调用额度不足发生在 Reader 状态保存前时，应沿现有逐题失败路径记录；不伪造分页状态，不因一个已知读取失败终止其他独立题。该项是前序代码审查定位的可达路径，实施时补一个集成复现，而不是先建异常平台。[R5]

排序调用不能仅预留“一页＋回答”后就认为后续一定可完成。优先使排序产生证据子集，避免再全池重读。只有批内排名时，不把各批交错输出称为全局最优；后续需要时用少量共同候选或一次候选汇总比较补足跨批次判断。

### B 的最小实验与完成条件

复用 A 的真实来源与冻结到达前缀，比较现有全材料路径和新证据组合。开始选 8—12 个必须分页或存在明显无关内容的问题，同时保留少量 direct 问题，验证简单场景不增加无用调用。

关键结果是必要证据进入最终输入、答案完成度、累计输入与调用。某条短路径答对却漏掉必要否定或条件，不计成功；少读但损害质量应调整证据闭包或补读方式，而不是直接增大固定 top-k。

## 06｜开发工作包 C：完整命题更新与时间表达

**目标：**让更新正确作用于含义，而不以字面差异最小化作为目标。

**主要代码位置：**`methods/edit_memory.py`、`methods/edit_maintenance.py`、`methods/edit_features.py`、`memory/edit_units.py`。复用现有内容单元、条件关系、局部操作、引用 keep 与版本提交。[R6][R7][R8]

### C1：形成可独立变化的命题

形成阶段让不同主体、属性和作用域尽量落入独立内容单元，共用条件使用现有关系连接。不能按逗号机械拆分，也不为了追求“原子化”删除语境。一个语气、量词或否定共同支配多个对象时，拆分后的每个命题都必须保留它。

对旧库采用读写时局部处理：只有命中的复合事项需要更新时，才在一次正常提案中拆分或重述相关内容。首轮不批量迁移全部旧数据，不追求理想初始化。

### C2：改写完整的受影响表达

简单独立值变化可以继续用 `patch_text`；共享谓词、否定、量词、时间区间与例外变化优先用现有 `replace`／`append`／`retract` 表达完整含义。需要旧含义重述时，通过现有来源路径重交付必要旧正文；当前修改证据和仍保留的旧支持分别记录。

例如，“喜欢苹果、梨和葡萄”变为只不喜欢苹果，目标状态应明确表达“不再喜欢苹果；仍喜欢梨和葡萄”。词语保留不足以证明后两项仍为肯定。不要再围绕原食品案例追加专用提示，以新的并列、否定和共享条件样本测试泛化。[R2]

多个独立修改若落入同一目标，首个实现可以直接用一次普通 replace，而不是急于扩展多 patch 语法。每次提交同步处理确实受影响的条件和总述，未涉及事项原样保留。

### C3：减少重复语义加工

对一个明确事实变化，先试现有 `single_pass`：当前事件、必要目标与支持直接进入 Editor。复杂多事项事件再比较 `extract_then_edit`。首轮在声明的事件类别上比较，不为路由再增加一个 LLM 分类调用。

测试基于同一个真实 before 状态；“空提案”既可能是正确保持，也可能是漏写，应按事件是否确需变化判断。新流程不能通过永远不写或一律追加新记录取得虚假的保持率。

### C4：保留时间原话，精确字段只承载有依据的值

修改 Extractor 的时间任务：保留来源中的原始时间表达；有明确日期或可靠锚点时才填现有精确字段，未知字段省略。Writer 复用该表达及来源，不再为了完整 schema 二次推断出一个日期。未来计划的日期不证明事件已发生。

优先用正文和既有 applicability 字段表达，首轮不引入复杂时间本体。确有不能表达的相对时间需求，再增加最少的非权威解释字段，并明确它不是程序观察的时间。当前存储的报告、捕获和提交时钟保持各自含义。[R2][R6]

### C 的最小实验与完成条件

从真实开发来源与新增合成机制故事组成 12—24 个更新事件，包含必须改、无需改、局部例外、历史纠错、渐进变化、同名主体与模糊时间。每条从实际形成状态继续，不用手写理想 before 替代系统能力。

更新联合成功必须同时满足：目标含义正确、非目标含义保持、来源／模态／时间忠实、所需历史可读。当前状态判断与带原文 Reader 判断分开；Reader 靠原文恢复正确答案，不抵消存储损伤。

## 07｜开发工作包 D：按需状态视图与最小依赖维护

**目标：**让语义层提供原文路径难以低成本提供的当前适用性、历史解释和压缩收益。

不默认在每条消息后重写综合摘要。原始捕获、明确状态更新、跨事件综合分开。当前没有需要时保留原文；存在反复查询、冲突状态或需要压缩的事项时，才沿现有 consolidate／修订路径构造视图。

首个实现只利用已存在的条件、例外和来源关系，为实际需要的状态视图记录依赖的 unit／revision。不要凭语义相似度建立大型自动依赖图。变化发生后，仅刷新明确依赖它的视图；没有可靠依赖时重开相关原件并局部重算，不暗中声称视图仍为最新。

来源选择与支持粒度须匹配：旧支持存在，只说明它曾支持某些内容，不能自动支持整段新文字；不同时间、作用域或主体的命题不能用“最后一次报告覆盖全部”处理。

D 的价值通过三种观察区分：原文独立回答、带必要支持的状态视图回答、实际状态内容审查。仅在诊断中测试“只给语义视图”，用于判断其自身可用性，不把无支持语义输入作为默认产品模式。

选择一个有多轮规则变化的完整故事：未来生效前后查询、未受影响项目、撤销例外、过去记录纠错。若状态视图只增加输入且不能提高质量或复用成本，缩减该类视图职责，保留原文路线，不继续增加摘要层级。

## 08｜开发工作包 E／F：共享调用路径与后续策略学习

### E：让方法收益进入正常使用

随 B、C 实际改动提取方法函数。建议只形成两个清楚的内部调用边界：读取策略接收问题、预算和来源访问能力，返回实际证据组合；更新策略接收当前事件、目标状态与来源，返回既有操作提案。命名和类型沿仓库风格，不建设插件框架。

Benchmark 负责合法数据到达、实验顺序和结果保存；Functional Host 调用同一核心，不复制第二套选择规则。Host 接收用户任务、实际工具和当前结果，不把整套内部审计状态反复塞入模型包。业务对象状态仍取自实际应用观察，记忆不替代实时查询与真实行动。

Product 接入安排在 Lab 新链路得到实际收益之后，先把证据组合通过公开适配接口交给 Product Host。保持 Product／Lab 的存储与权限边界，不直接导入 Lab 私有模块，不宣称两个运行时天然等价。用同一个保存—更正—查询故事检查实际跨入口行为，而不为接入先做整库迁移。[R10][R11]

### F：只训练已经明确的决策瓶颈

候选存在但常漏选，才优先训练证据选择；正确目标和来源已给出但仍改错，才优先训练更新。训练数据来自开发事件、实际 before／after 和标注的目标变化与非目标约束，不使用最终保留用户或测试答案指导在线写入。

可借鉴 MemSifter 的任务效用方向，或记忆操作策略学习的组织方式；本规划不要求首轮复现训练。当前 MemSifter CPU pilot 没有形成质量结论，应保留已有接口，等待合适部署条件后用一个真实排序题检查端到端可行性，不继续扩建 CPU 推理框架。[R2][R9]

先尝试监督或偏好学习，再考虑强化学习。离线奖励同时考虑后续任务改善、更新损伤和额外成本；必须包含“应该改”和“应该保持”，防止全不写或全追加。读取与写入先分开训练；只有各自有效且存在共同收益，再尝试联合策略。

## 09｜实验设计：机制比较与完整系统比较分开

### 9.1 四组问题足以覆盖本轮主张

| 组别 | 主要现象 | 最小比较 |
|---|---|---|
| 检索组 | 中文改写、同名主体、历史超过候选配额 | 旧原文路径与 A |
| 读取组 | 多余上下文、跨轮指代、条件／否定、需要补读 | 同一实际候选池下旧 Reader 与 B |
| 更新组 | 局部变化、保持、例外、纠错、模糊时间 | 相同真实 before 下旧更新与 C |
| 长期组 | 多轮变化后仍能回答当前与历史问题 | 最强原文基线与 A＋B＋C／D |

计数和穷举单独标记，因为它们对范围覆盖的要求不同。不要用 lookup 的停止成功替代范围查询的正确完成。

### 9.2 样本与迭代节奏

接通可以从 6—8 条真实输入开始，筛选使用约 24 个问题或更新事件，之后只扩大最有希望的两个条件。数字可按资源与失败信息量调整，不形成“未完成所有前置样本就禁止开发”的门禁。

长历史机制试验无需等待短历史分数上涨：选择 2—4 段已有开发历史，长度自然超过当前原文候选或输入预算，在同一连续运行中观察短段、中段和完整前缀。题目选择依据时间、长度和任务类型，不能看到新结果后只挑胜例。

保留用户以完整历史为单位隔离；最终候选选择后才用于确认。大量来自四个开发用户的 QA 不是大量独立用户证据。

### 9.3 两类实验控制

机制比较固定主 Reader、来源可见范围、问题与日期、预算和抽样规则；一次主要改变一个因素。同池读取可以复用已保存的实际召回和对应旧版本，只重开该题当时可见来源，不从最终银行重新检索早期问题，不写测试答案或 ActivationIndex。

完整系统比较允许各方法使用自己的写入与读取策略，报告全部成本和部署差异。共享形成成本只计一次并单列，不能从系统成本中消失；不同大小模型的 tokens 不能单独代表价格或速度。

算法比较采用共同用户任务的总预算，不要求保持旧系统每个内部阶段的僵硬配额。新增小模型消耗、主模型输入节省和额外补读全部计入同一方法成本。[R2]

### 9.4 随机性与评价

沿用已保存的官方标签，不择优重判。新的结果保存实际输出、模型设置与执行条件。对影响研发结论的少量分歧题，做两臂对称的来源审查；将任务完成、来源忠实与 Judge 格式有效分开。

若同一最终输入也出现明显波动，可在新候选开始前声明少量配对重复；保留全部重复，不取最好一次。固定 seed 不能被当作服务端绝对确定性的保证。置信区间按用户／历史分组解释，开发小样本首先用于筛选与定位。

### 9.5 候选去留不只看一个准确率

质量提高且成本可接受，进入下一批；质量相近但实际延迟和成本明显下降，保留为效率候选。证据已正确交付而答案仍错，优先检查 Reader；原文可答而状态损坏，回到 C／D；关键来源始终不在池中，回到 A。

短样本差异主要来自 invalid 或相同输入波动时，先解决这一小部分可解释性，不扩全矩阵。没有达到目标机制条件的实验标为“不足以区分”，而不是宣布整条方法无效。

## 10｜指标与结果记录

### 10.1 主指标

| 维度 | 建议口径 | 容易误读的情况 |
|---|---|---|
| 任务结果 | 全部实际尝试中的正确数；invalid、已知缺答分别列出 | 正常 stop、提交成功都不是任务正确 |
| 更新联合成功 | 目标正确且非目标保持且来源／时间忠实且历史可用 | 字符相同不是语义保持 |
| 原文取证 | 必要来源进入候选与进入最终输入的比例 | 全池交付数不是有效证据数 |
| 系统成本 | 形成、更新、索引、排序、读取的分项与总和 | 只算最后一次 Reader 会隐藏重复成本 |
| 交互代价 | 实际调用数、累计输入、时延；适量重复下统计分位数 | 少量样本的 P95 不宜作稳定服务承诺 |

计划机会、实际尝试、完成、缺答、未运行分别列数；未运行不填零。模型状态未知保留未知，已确认只读失败按既有策略保存，不自动重试有未知业务效果的操作。无需为此另建风险平台。

### 10.2 复用现有逐题结果

只在现有结果字典增加必要字段，已有同义字段直接复用。以下是语义约定，不是必须建立的新 schema：

```json
{
  "case_id": "actual-case-id",
  "variant": "readpack-dev",
  "runtime_code": "actual-commit",
  "retrieval": {"candidate_count": null, "final_evidence_count": null},
  "quality": {
    "task_result": "unreviewed",
    "target_change": null,
    "non_target_preserved": null,
    "source_faithful": null
  },
  "cost": {"write_tokens": null, "rank_tokens": null, "read_tokens": null},
  "status": "not_run"
}
```

上例 `null` 表示尚未运行或没有观测值；实际结果中，只有确认为零的用量才填零。能由现有 HTTP／usage 文件计算的值，汇总时计算，不新增重复日志。输出正文、证据与状态已有产物继续作为分析依据。

成本回收按用途判断：语义构建增加的开销，需要由后续任务质量或重复查询节约补偿。若状态视图的查询阶段也更贵，就必须展示额外质量价值，不能只以“以后可能摊薄”解释。

## 11｜任务分配、合并顺序与正常链验收

### 11.1 可并行分工

| 角色 | 首批责任 | 与其他工作的接口 |
|---|---|---|
| 集成者 | 固定当前起点、正常入口、结果汇总与一次端到端联调 | 只维护小公共输入输出，不为所有包新建协议 |
| 开发 A | 可见来源枚举、分词、查询成本 | 向 B 返回实际来源和命中位置 |
| 开发 B | 证据组合、选择与补读、Reader 目标稳定 | 消费 A 的来源；交付真实正文与引用 |
| 开发 C | 命题形成、更新动作、模态与时间 | 复用来源与提交；提供可用状态与支持 |

资源不足时按 A→B→C 串行执行，不要求固定人数。共享模型服务沿既有实际资源安排使用；文档不假定有新 GPU、预算或正在运行的实验。

### 11.2 建议提交序列

1. 原文枚举解耦与分词修复，附直接回归和查询结果。
2. 细粒度命中与自包含材料交付，保留旧入口。
3. 最终目标固定、预算内选择及必要补读，伴随排序失败接线修复。
4. 独立命题与简单 single-pass 更新，复杂事件继续旧配方。
5. 条件／时间／受影响概括处理，用新的连续故事验证。
6. 提取实际复用的方法函数，并接入正常 Host。

这是推荐顺序，不是必须拆成六个 PR。每个提交围绕能运行的功能切片，避免一个 PR 同时改变来源、模型、表示和 Judge。

### 11.3 一条贯穿开发的故事

使用一个新建的合成开发故事，不冒充用户真实数据：先保存“A 项目通知李明；B 项目通知王芳；外部通知先确认”。随后输入“10 月 20 日起 A 改为赵敏，其他不变”；再输入一个临时例外和一次明确撤销。

沿正常 CLI／SDK 依次查询生效前、生效后、B 项目、共同确认规则和实际修改历史。检查例外撤销是否仅撤销例外，而不是删除一般规则或恢复已经到期的旧规则。

最后请求忘记故事中的指定信息，沿现有能力检查实际撤销范围和重开结果，不把业务取消、语义撤回、可见性撤销和物理擦除混为一谈。只执行已有能力支持的范围，不为这条研发故事先建设新删除平台。

合成故事验证接线和机制；真实开发历史验证模型能力。两者都不能单独替代最终保留用户测试。

### 12.2 已核验的现有 CLI 示例

下列展示已存在入口的阶段用法，使用现有基线配置，不包含 A—F 尚未实现的新能力。需要已有可运行的 Lab 环境和配置中的本地模型／数据路径；此文档生成过程没有执行这些模型命令。[R12]

### 12.4 可直接交给开发者的任务说明
