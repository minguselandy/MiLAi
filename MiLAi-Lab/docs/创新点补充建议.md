你的判断指出了一个实质问题：**前面的 RSR 设计把“迟到澄清后的纠错”当成了整个系统，而它实际上只应该是完整记忆系统中的一种变更。**如果围绕这一种事件单独搭建数据结构、检索逻辑和修复流程，最终很容易得到一个擅长特殊案例、却难以持续运行的原型。

我建议保留这个研究问题，但重新组织方法：

> **MiLAi 的系统目标是维护“在当前证据、情境和时间条件下仍可使用的理解”；新增、补充、临时覆盖、真实变化、解释纠错、冲突、压缩和遗忘，都通过同一套维护与取材机制处理。**

RSR 不再是系统名称或唯一流程，而是其中的 **reinterpretation，即重新解释已有材料**。

下面给出完整的目标设计。它以附件中的 Lab 六层架构和四个工具为基础，不引入另一套独立记忆服务。**新增机制均属于建议实现，未在本轮修改或审计你引用的本地源码。**附件目前也明确区分当前实现、目标设计和已有验证。

# 一、先把系统完整性与论文贡献分开

完整工程设计与清楚的科学问题并不冲突。应当采用以下分工：

| 层面        | 应解决的问题                         | 不应承诺什么             |
| --------- | ------------------------------ | ------------------ |
| **系统目标**  | 记忆从形成到使用、修订、恢复、退出的完整生命周期       | 不能因为功能齐全就称为新范式     |
| **方法机制**  | 如何维护可撤回的支持关系，并让所有取材入口遵守当前修订状态  | 不能把字段、版本和引用本身认领为创新 |
| **论文主假设** | 这种维护是否减少错误理解复现，同时保留有效知识，并值得其成本 | 不能用总体准确率代替机制证据     |

因此，系统的问题应扩大为：

> **在持续输入和任务切换中，如何以有限维护成本，使原始材料、当前理解和实际返回给 Host 的内容保持一致？**

这里的“一致”不是指所有材料必须没有矛盾，而是：

**已经知道存在更正、适用范围变化或未决冲突时，系统不能在另一条读取路径中仍把旧解释当作无条件结论。**

这一目标自然覆盖你提出的六个缺口，也比“专门处理迟到澄清”具有更好的工程完整性。

# 二、整体架构：沿用六层，但让它们共享同一套记忆语义

附件已经有输入适配、记忆核心、检索材料、任务控制、Host 执行和持久化评估六个逻辑层。问题不是缺少层数，而是**各层对“这份材料现在还能怎样使用”的理解还没有完全统一**。

建议保留现有层次，增加下面的职责。

| 现有逻辑层        | 下一版应补齐的职责                        | 明确不承担的职责                   |
| ------------ | -------------------------------- | -------------------------- |
| **输入适配层**    | 绑定来源、事件顺序、合法前缀；区分新事件、重复接收和来源取得错误 | 不根据文本自述改变真实消息角色；不暴露评分字段    |
| **记忆核心层**    | 保存理解单元、支持组、修订历史和适用条件；执行局部变更      | 不把结构合法性认定为语义正确性            |
| **检索与材料层**   | 发现候选；解析其当前状态；补齐必要更正；按预算返回材料      | 不把向量命中直接当成当前可用结论           |
| **任务控制层**    | 维护本次主体、任务、时间和疑点；选择当前适用视图         | 不因一次任务切换而重写长期画像            |
| **Host 执行层** | 提出语义变更、判断未决关系、使用材料完成任务           | 不伪造来源、版本或操作成功              |
| **持久化与评估层**  | 一致保存来源、支持关系、变更回执、进度和失效状态；隔离评分    | 不把旧 checkpoint 或缓存当作独立事实来源 |

**核心变化只有一个：所有层围绕同一份“理解及其支持关系”工作。**

写入不再只改变一段正文；读取也不再只取出一段正文。

# 三、数据模型：不是给 Note 加字段，而是明确四种不同对象

建议核心状态只保留四类对象。索引、摘要视图和材料包都属于派生结果，不再成为另一套独立记忆正文。

## 3.1 四类对象

| 对象                         | 保存什么                           | 是否允许修订                         |
| -------------------------- | ------------------------------ | ------------------------------ |
| **Observation：原始来源**       | 实际取得的正文、角色、事件、会话、时间、范围         | 不通过语义修订覆盖原文；取得错误用明确替代关系，遗忘另行处理 |
| **Claim：理解单元**             | 一项可独立维护的命题、主体、情境、有效期和作者判断      | 可以新增版本、拆分、失效或重新激活              |
| **Justification：支持关系／支持组** | 哪些来源片段、前提理解及条件，共同支持或反对某项 Claim | 可以被更正、撤回或替换                    |
| **ChangeSet：变更记录**         | 变更原因、目标版本、实际执行差分、未决对象和执行回执     | 已提交记录不覆盖；后续纠错产生新变更             |

TaskState 继续作为任务覆盖层，不需要变成第五种长期知识系统。

### 理解单元的粒度

建议采用：

> **一项能够独立改变真假判断、归属、范围或有效期的理解，作为一个维护单元。**

这不等于每句话都必须拆成多个极小事实。拆分过细会增加提案、关系和检索成本。

例如：

> “用户在内部技术讨论中希望详细解释，但客户交付材料通常简洁。”

可以拆成两个能独立修订的条件性理解；但一个必须联合理解的因果解释，不应机械拆成若干失去关系的词条。

**对照组必须使用相同粒度。**否则无法排除你指出的“只是把记忆拆小了”的解释。

## 3.2 无来源想法仍然可以保存

新设计不能把 MiLAi 变成“没有外部证据就不能记录任何东西”的数据库。

附件明确允许独立想法、暂定解释和工作假设。它们应继续存在，只是标注为 Host 的假设，不能伪装成用户事实。 

因此，需要分开：

* **记录是否存在且结构合法；**
* **是否有外部材料支持；**
* **是否适用于当前任务；**
* **是否仍有未解决争议。**

不能用一个 `active=True` 或一个 confidence 数字同时表达这四件事。

# 四、支持关系必须有执行语义：共同支持、替代支持与反对证据

你提出的“组内共同需要、组间替代依据”应当直接成为核心合同。

## 4.1 最小支持组语义

假设结论 \(P\) 有两条依据：

$$
J_1=\{A_1,A_2\},\qquad J_2=\{A_3\}.
$$

其中 \(A_i\) 是具体的、带范围的支持项，而不是整份来源。

则：

$$
\operatorname{Supported}(P)
=
\operatorname{Usable}(J_1)
\lor
\operatorname{Usable}(J_2),
$$

而：

$$
\operatorname{Usable}(J_1)
=
\operatorname{Usable}(A_1)
\land
\operatorname{Usable}(A_2).
$$

撤回 \(A_1\) 后，\(J_1\) 不再成立；但只要 \(J_2\) 仍适用，**不能直接删除 \(P\)**。

这里的 `Usable` 应同时检查当前版本、作用域、有效期、生命周期和依赖状态。它表示“按照已记录解释仍可作为支持”，**不是程序证明内容为真**。

还需要明确：

> **替代支持不等于统计独立。**

同一事件的三份摘要可以形成三个访问入口，但不能据此把置信度乘三。来源谱系应保留，首版不要对相关证据做未经校准的概率合并。

## 4.2 未知不能被压成 false

支持项可能存在三种结构状态：

| 状态  | 含义                   |
| --- | -------------------- |
| 可用  | 已声明条件满足，依赖未发生需要核对的变化 |
| 不可用 | 已撤回、超出有效范围、已遗忘或明确失效  |
| 待核对 | 新变化可能影响它，但尚未完成语义判断   |

如果一个支持组待核对，另一个支持组仍可用，结论可以依据后者继续使用；如果所有支持组都不可用或未决，则不能继续以“证据充分”的状态返回。

这比“任意依赖变化就删除所有下游记录”更符合你的目标。

## 4.3 撤回支持，不等于证明相反结论

必须分别维护：

$$
S^+(P)：支持P的依据,\qquad S^-(P)：反对P的依据。
$$

这允许区分：

| 支持情况      | 应表达的状态         |
| --------- | -------------- |
| 有支持、无相关反对 | 当前有依据支持        |
| 有支持、有相关反对 | 存在冲突，需按范围和时间处理 |
| 无支持、有反对   | 原结论受到反驳        |
| 两边都不足     | 缺乏足够依据         |

**删除“用户喜欢简短”的错误支持，不能自动生成“用户喜欢详细”。**

这对于第三方归属澄清尤其重要。

## 4.4 首版不要实现完整逻辑证明器

只维护实际声明过的支持组，不自动枚举全部可能证明，也不展开所有组合。

对于循环依赖，应至少阻止：

```text
P 支持 Q
Q 又成为 P 唯一的依据
```

在没有独立来源或明确假设根节点时，不能让这种循环产生“有证据支持”的状态。

这些是工程语义，不是新的逻辑理论；它们的价值在于让操作可测试。

# 五、时间语义：保留两条时间线，再保留原始事件时间

你的双时间建议应采纳，但需要防止混成普通的“按日期取最新”。

| 时间            | 回答的问题                   |
| ------------- | ----------------------- |
| **来源时间**      | 这条消息或事件什么时候发生？          |
| **有效时间／任务范围** | 这项理解描述的要求在什么时候、什么任务中适用？ |
| **系统理解时间**    | 系统从什么时候开始采用这项归属，什么时候修正？ |

查询至少支持两个维度：

$$
\operatorname{Resolve}(q;\operatorname{valid\_at}=v,\operatorname{known\_at}=k).
$$

例如：

**“当时系统怎样理解？”**
使用当时已经取得的证据与归属版本。

**“根据现在掌握的信息，回看当时应该怎样理解？”**
允许使用后来取得的澄清，但有效时间仍指向过去。

**“现在应该怎样处理？”**
使用当前合法证据下、当前任务适用的理解。

这里不能把“现在回看”表述成已经恢复客观真相；它仍然只是当前证据下的最佳理解。

在 benchmark 中，`known_at` 必须绑定题目允许的历史截止点，不能因为系统已经处理了更多历史，就把未来澄清带入过去的问题。附件已有合法前缀和缓存身份约束，这些规则应延伸到支持关系与更正索引。

# 六、统一维护算法：八类输入，一套处理流程

工程完整性的关键，是不要给每种记忆事件写一套互不兼容的逻辑。

## 6.1 统一事件语义

| 输入事件      | 主要变化             | 不应该发生什么         |
| --------- | ---------------- | --------------- |
| 新信息       | 新增来源、理解或支持项      | 不自动永久化所有内容      |
| 补充佐证      | 增加替代支持或补全共同支持    | 不把同源重复当独立佐证     |
| 临时要求      | 新建 task 范围的覆盖    | 不改变长期默认         |
| 真实状态变化    | 调整有效区间，建立新状态     | 不抹去过去曾成立的状态     |
| 解释纠错      | 修订旧材料的主体、范围或命题归属 | 不覆盖原始来源         |
| 未决冲突      | 保留正反依据及不确定性      | 不机械采用最近一句       |
| 整理与压缩     | 合并展示、去冗余或建立派生视图  | 不产生新的无来源“事实”    |
| 遗忘／生命周期退出 | 撤销访问、处理相关支持和派生内容 | 不与解释纠错共用粗粒度删除操作 |

**RSR 对应其中的“解释纠错”，而不是支配其他七类事件。**

## 6.2 一个统一执行流程

建议将每次维护分为五步：

### 第一步：取得新材料，并定位可能受影响的对象

候选不能只有相似 Note，应联合使用：

**新输入相关检索＋来源反向引用＋支持关系反向索引＋主体／情境／时间条件。**

先取得若干语义种子，再沿已声明关系扩展。

这里要明确两种不同的完备性：

> **结构展开完整，不代表语义影响定位完整。**

程序可以完整遍历已知关系，但如果最初根本没有记录“这份摘要来自那次客户要求”，就仍可能漏修。

因此应记录：

```text
候选是否被预算截断；
已遍历哪些已声明依赖；
哪些作用域仍未核对；
是否存在尚未处理的广泛澄清。
```

不能把一次 top-k 返回当成完整撤回集合。附件目前只保证向 Host 提供相关旧记录，并不保证它们覆盖全部影响对象。

### 第二步：Host 提出统一 ChangeSet

一次提案可以同时包含：

```text
新增理解；
增加支持组；
撤回某个支持项；
改变主体、情境或有效期；
创建临时覆盖；
登记未决关系；
标记需要进一步读取的对象。
```

每项变化都应附带具体原因引用，不能只写“因为最近的信息不同”。

**结合新增澄清，旧材料不再足以支撑原先概括**，是合适的解释；不应把它改写成“系统当时就应知道旧推断必然错误”。

### 第三步：验证并提交局部变更

程序验证引用、版本、用户边界、已读要求及操作结构。

但一次语义修订中的：

```text
撤回旧支持 → 加入新支持 → 更新当前理解
```

应当作为一个局部原子变更组执行，避免出现“旧支持已经删了，新支持却失败”的半完成状态。

这与“整批全部回滚”不同：

* 同一个相互依赖的变更组，要么完成，要么不完成。
* 不同变更组可以分别成功或失败。
* 原始来源已保留的事实单独回执。

这需要对当前逐项执行语义作明确增量，而不是假装现有代码已经提供这种保证。附件目前明确说明操作顺序执行，一项失败不会回滚之前的成功项。

### 第四步：重算受影响的支持状态与视图

变化沿反向关系传播，但不是统一级联删除。

正确处理是：

```text
某项支持被撤回
    → 对应支持组失效或待核对
    → 检查是否还有其他有效支持组
    → 保留、标记争议、降为假设，或暂时退出当前视图
```

仅重建受影响部分。

首版让 Memory view 由短理解单元、支持状态和条件确定性组合，不默认再调用一次 LLM 生成摘要。

### 第五步：更新所有依赖当前状态的读取结果

至少包括：

**当前记录入口、原文关联更正、派生索引、TaskState 中的引用、材料缓存及 coverage。**

处理完存储层，不代表修订已经完成。**变更的完成范围必须包括它能影响的读取路径。**

# 七、读取设计是另一半核心：返回“材料及其当前解释状态”

你提出的原文重读问题，是这版设计中最需要补齐的部分。

## 7.1 不能再让 search 和 read 直接返回裸材料

所有入口应共用一个材料解析器：

> `memory_search`、`memory_read`、邻接展开、来源展开、缓存命中，都先解析当前有效状态，再组织返回内容。

索引只负责定位对象。它返回的旧文本片段不能绕过当前状态解析直接交给 Host。

材料包至少包含：

| 内容            | 用途            |
| ------------- | ------------- |
| 原文或当前理解的准确正文  | 保留实际材料        |
| 对象、版本和具体范围    | 明确读到什么        |
| 主体、情境、有效期     | 判断当前适用性       |
| 当前支持／争议状态     | 避免把存在记录当成可信结论 |
| 与本次使用有关的更正或限制 | 防止旧材料诱发已知错误   |
| 未覆盖信息与预算状态    | 不把截断材料当完整证据   |

这里的更正必须与原文分开展示，不能悄悄改写引文。

例如：

```text
原始材料：
“这次给客户的汇报只保留结论。”

当前相关解释：
后续澄清将该要求限定为客户交付约束，
不再足以支持“用户在所有技术交流中喜欢简短”。

依据：
原始来源 S1；澄清来源 S2；当前归属版本 A7。
```

## 7.2 定义“必要关联材料”，而不是每次展开整张关系网

不是所有读操作都需要看到所有历史。

对于当前准备采用的材料，只补齐：

**足以说明其当前用途的一组有效依据，以及会改变这种用途的已知更正、反对或限制。**

读取历史原话时，可以按历史模式返回；回答当前偏好时，则必须考虑当前有效的修订。

这可以形式化为：

$$
\operatorname{Bundle}_t(r,q)
=
\{r\}\cup
\operatorname{RequiredContext}_t(r,q).
$$

`RequiredContext` 是依据已声明关系和当前查询选出的必要关联材料，不是程序已经发现所有语义相关事实的证明。

## 7.3 预算应按整个材料组计算

如果旧原话已经放入上下文，而更正因为 token 不够被截掉，系统依然可能重新制造错误。

因此，材料选择单位应从“一个命中片段”改为“一个可解释的材料组”。

简单实现就足够：

1. 计算候选材料组的增量 token 成本。
2. 对共享来源与更正去重。
3. 按相关性与增量成本选择。
4. 预算不足时降低正文展开程度，而不是优先丢弃决定适用性的条件。
5. 无法完整呈现时，标记不足，不认证为充分。

这属于工程算法选择，不能把“按收益／成本贪心装包”包装成新的优化理论。

## 7.4 更正本身也必须可修订

不能把第一次澄清永久变成不可撤销的规则。

如果后来发现澄清也有误，系统应重新维护它的支持关系。否则你只是把“错误原始理解”替换成了“错误更正”。

同样，若外部 Host 已经在自己的对话窗口中保留旧内容，MiLAi 不能声称能够控制所有绕过工具的读取。**读取一致性的保证应限定在经过 MiLAi 的材料路径和明确管理的任务上下文中。**

# 八、把生命周期补完整：整理、增长、恢复与遗忘

## 8.1 整理应该先改变视图，再考虑改变语义存储

建议区分三种维护：

| 维护方式            | 是否需要语义模型 | 对支持关系的要求        |
| --------------- | -------- | --------------- |
| 相同对象重复显示、相交范围合并 | 不需要      | 不改变来源身份或支持数量    |
| 多个理解单元的紧凑组合     | 首版不需要    | 保留条件和当前版本       |
| 跨记录语义合并、抽象新规律   | 需要时才调用   | 明确建立派生支持，保留可撤回性 |

持续摘要重写确实存在退化风险，但相关研究已经直接检验了这种现象。因此，这一设计是必要控制，不应认领为新的发现。([arXiv][1])

存储增长也不能靠无限拆分解决。应报告来源数、理解单元数、支持项数、每次更新的受影响规模，以及视图压缩比。

如果为了节省容量而移除原始依据，应明确降低可核查性。**保留一份压缩摘要不能被表述成仍保留完整原始证据。**

## 8.2 缓存必须服从记忆状态，而不是反过来

建议缓存身份至少考虑：

```text
用户与合法历史范围；
方法和模型身份；
当前记忆变更代数；
相关对象版本；
任务情境；
材料范围与视图策略。
```

为了避免每次变化都清空所有缓存，可以使用对象级依赖指纹；但首版采用较粗的用户级变更代数也可以，只需报告成本。

旧向量允许暂时存在，但命中后必须重新解析对象状态。新记录尚未完成 embedding 时，应仍可通过词法索引或小规模增量候选访问，避免“修订成功，却暂时找不到新理解”。

## 8.3 checkpoint 应保存同一个逻辑状态

至少共同保存：

**来源、理解版本、支持组、变更回执、摄取进度、未决范围、遗忘状态。**

不能只保存新理解，却仍恢复旧支持关系；也不能推进摄取游标，但遗漏该批变更。

需要区分两个概念：

> `durable` 表示跨任务保留，
> `checkpointed` 表示已经保存到可恢复介质。

二者不是同一个保证。

对于本地单进程 Lab，可以采用局部状态副本验证、统一替换与明确 checkpoint 回执，不必引入分布式事务框架。当前附件也明确说明现有版本检查不等于数据库或分布式 CAS。

## 8.4 遗忘与语义修订必须保持不同

| 操作         | 处理对象                  |
| ---------- | --------------------- |
| **解释修订**   | 改变某项来源如何支持某个理解        |
| **当前不适用**  | 改变任务中的选择，不删除知识        |
| **时效结束**   | 退出相关当前视图，历史可能仍保留      |
| **用户遗忘请求** | 按指定范围撤销保留和访问，处理相关派生内容 |

遗忘涉及的理解可能仍有其他合法支持，此时不能机械删除整个结论；但也不能保留含已遗忘内容的正文，再声称只剩“独立支持”。

旧快照恢复仍需要外部于被恢复快照的最新遗忘状态，才能防止复活。附件已经披露这一边界，下一版不能因为新增支持关系就宣布问题自动解决。

# 九、接口和成本：四个工具保留，内部增加变更合同

不建议向 Host 暴露十几个新工具。

| 工具              | 建议增量                                           |
| --------------- | ---------------------------------------------- |
| `memory_save`   | 接受理解更新、支持组变化、有效期变化及明确遗忘等不同意图；返回真实 ChangeSet 回执 |
| `memory_search` | 搜索来源与理解，但通过统一材料解析器返回                           |
| `memory_read`   | 支持当前／历史读取语义；关联必要更正；保持原文与解释分离                   |
| `memory_state`  | 更新任务主体、情境、疑点及引用；不自动永久化                         |

内部新增对象由程序分配身份。模型可以提交新内容及其依据，但不能提前伪造尚未创建的真实引用。

## 回执必须同时回答四个问题

```text
请求有没有被合法接收？
哪些对象实际发生了变化？
是否仍有版本冲突或未处理影响？
这些变化是否已经 checkpoint？
```

“工具有返回”不能等于“修订成功”。

你指出的嵌套 `VERSION_CONFLICT` 统计问题，附件确实记录为现有缺口；它应当先于任何更新效果实验修复。

## “每批一次提案”应是默认预算，不是虚构能力

一次调用可以完成已提供材料范围内的语义提案，随后由程序确定性应用和组合视图。

但如果提案发现“过去几个月的相关理解都可能需要修订”，而实际只读到了其中一部分，就只有两种诚实选择：

**在显式预算内再取得材料并继续处理，或者保留未决影响范围。**

不能同时要求：

> 一次调用、只看少量旧记录、自动修正全部历史、还保证没有遗漏。

如果仍采用每批一次调用，超出本批能力的部分应登记为未完成，并在后续同步维护或相关读取时处理；不能在报告中算作修复完毕。

# 十、创新性重新判断：完整架构也已有强近邻

你补充 BeliefBank 和 Kumiho 是必要的。本轮进一步核查还发现 **MemTX**，它使“全方位工程化”这条路线也必须谨慎定位。

| 工作                        | 已核实的机制                                  | 对 MiLAi 的约束                                |
| ------------------------- | --------------------------------------- | ------------------------------------------ |
| **BeliefBank，EMNLP 2021** | 外部可演化信念存储、加权 MaxSAT 修订、已知信念反馈给模型        | 外部维护可修订认知、无需重新训练不是新方向。([ACL Anthology][2]) |
| **Kumiho，2026**           | 版本化信念、依赖关系、修订与检索的联系；明确讨论整体替换、细粒度记录和语义合并 | 必须排除粒度、普通依赖失效和当前版本过滤的收益。([arXiv][3])       |
| **MemTX，2026**            | 事务化信念提交、类型化级联修复、失效视图隔离；明确限定其运行时保证       | 事务、撤回传播、派生视图重建都不能重新认领为新机制。([arXiv][4])     |
| **STITCH，2026**           | 情境意图构造及基于兼容性的检索                         | 情境字段和意图筛选本身不足以构成贡献。([arXiv][5])            |

这不意味着完整设计不值得做。它意味着：

> **工程应当借鉴这些成熟思想；论文则必须证明一个比“我也实现了这些思想”更具体的差异。**

我认为最有希望的研究增量是：

### 1. 支持保留的局部修订

撤回被新证据削弱的具体支持，而不是删除所有相关记录；并验证独立支持下的有效理解仍然保留。

### 2. 写入与读取共享修订状态

更正不仅进入当前 Note，也约束原文、摘要、邻接和缓存等取材入口，减少错误理解重新出现。

### 3. 有限预算下的影响定位

区分“已经处理的已声明依赖”和“尚未确认的语义影响”，比较更广泛维护与按需维护的质量—成本边界。

**这三点仍然只是候选贡献。**尤其是前两点，与信念维护和已有记忆系统存在实质重合，需要操作级比较，不能现在宣布新颖性成立。

## 脑科学在这里应处于什么位置？

Gershman 等人的计算模型把“经验归于哪个潜在原因”和“如何更新关联”分开，并允许通过改变结构解释或改变已有关联来处理预测误差。它支持把“归属判断”和“内容更新”分离这一计算动机。([eLife][6])

但支持组、版本、缓存和提交语义主要来自计算机系统设计，不是神经科学推导结果。

因此，论文可以说 **受到记忆归属与修改理论启发**，但不宜声称整套工程是在模拟人脑，更不需要再增加 ADHD 或脑区映射来解释每个模块。

# 十一、实验设计：先三组，再验证写入—读取是否真的协同

你建议的首轮三组合理，应采纳，但需要把控制条件写清楚。

## 11.1 首轮三个主臂

| 实验臂           | 能力                           | 排除的解释                  |
| ------------- | ---------------------------- | ---------------------- |
| **原始材料检索**    | 同样的合法历史、澄清信息、强检索和可比推理预算      | 结构化维护是否根本没有必要          |
| **同粒度普通记忆更新** | 相同粒度、主体、情境、时间和来源信息；允许普通更新与重读 | 收益是否仅来自拆小记录、表达更清楚或再读一次 |
| **支持维护＋统一取材** | 在上述基础上维护支持组、局部撤回及关联更正读取      | 完整新增机制的实际价值            |

普通更新组不能故意做弱。它也应该能够把澄清写进记录，使用相同的新证据，并获得相当的调用预算。

对于机制归因实验，可以让各组取得相同候选材料；对于完整系统实验，则允许各方法按自身流程使用相同的合法历史，比较真实成本。

## 11.2 之后只增加四项关键消融

| 消融                 | 要回答的问题               |
| ------------------ | -------------------- |
| 支持组改为普通来源列表        | 收益是否确实依赖共同／替代支持的语义   |
| 关闭回溯归属，但保留同信息更新    | 修改旧支持关系是否有独立价值       |
| 修订存储保持不变，关闭关联更正取材  | 错误是否会从原文、邻接或缓存路径重新出现 |
| 给简单基线相同额外 token／调用 | 收益是否只是多了一次反思或回看      |

写入维护与读取关联可以构成一个小型 \(2\times2\) 对照，但不需要把系统所有开关展开成巨型矩阵。

**如果只修存储已经足够，读取闭环就主要是工程保护；如果只有读取关联有效，就不能把提升归因于复杂支持维护。**

## 11.3 公开测试与工程诊断分开

**MemSyco-Bench** 的范围控制、有效记忆选择和正确个性化，可以检查“不过度使用、不沿用错误版本、也不通过完全不用记忆作弊”。其官方仓库已提供这些任务和统一评估入口。([GitHub][7])

**STALE** 检查状态更新、错误前提抵抗和隐含行为适应，其仓库同时包含 CUPMem 的逐会话更新与冲突读出流程。([GitHub][8])

继续复用现有 PersonaMem 与 LongMemEval 适配，但保留原题、合法历史和评分边界。附件已经要求原始任务不改写、诊断标签不进入 Host。

自建诊断主要验证以下执行条件：

| 诊断                      | 观察目标           |
| ----------------------- | -------------- |
| 一项共同支持失效，但另有替代支持        | 是否误删仍有效理解      |
| 澄清后重新读取旧来源              | 是否再次产生旧错误      |
| 当前任务退出                  | 临时覆盖是否泄漏到新任务   |
| 来源与理解发生多次更正             | 是否错误地永久固化第一次澄清 |
| 修改后恢复 checkpoint 或命中旧缓存 | 是否恢复陈旧状态       |
| 变更组中发生版本冲突              | 是否出现半修订或错误成功统计 |

这些是工程和机制诊断，不能混入原生 benchmark 成绩。

公开任务若没有“旧证据重新归属”的直接标签，应明确核心证据仍有缺口。总体分数提高不能填补这个缺口。

## 11.4 指标至少分四层

**任务层：**原生准确率或任务得分、正确使用记忆率、未完成率。

**语义层：**目标修订正确率、有效支持误删率、错误理解复现率、临时要求持久化率。

**执行层：**真实变更成功、版本冲突、部分成功、待核对范围、材料关联覆盖。

**成本层：**摄取、维护、检索、回答、重试与 Judge 的实际调用、tokens、延迟和存储增长。

Host 与必要 Judge 可以继续通过 vLLM 运行，但同模型评判仍应标注为同模型自评；固定 rubric 并不自动等于复现官方榜单。

# 十二、开发顺序：按依赖关系推进，而不是先造完整平台

| 阶段            | 应实现什么                               | 完成判据                           |
| ------------- | ----------------------------------- | ------------------------------ |
| **第一阶段：正确执行** | 修复回执分类；定义支持组、变更组和时间字段；局部提交          | 冲突不被计为成功；支持撤回不会误删替代支持；原文不被修订覆盖 |
| **第二阶段：读取闭环** | 来源反向索引、统一材料解析器、关联更正、缓存失效            | search、read、邻接和来源展开对当前修订状态一致   |
| **第三阶段：生命周期** | checkpoint 一致恢复、task 退出、未决维护范围、遗忘传播 | 恢复不混用旧关系；临时要求不跨任务；已声明遗忘边界可验证   |
| **第四阶段：模型验证** | 三主臂、原生公开任务、关键机制诊断                   | 说明收益来自哪里，以及付出了多少成本             |

不建议首版增加完整图数据库、概率逻辑求解器、多 Agent 审核、后台循环反思或学习型管理策略。

但是，**不引入这些重组件，不等于只做几个字段。**真正的工作量集中在支持关系语义、影响定位、统一读取和恢复一致性上。

# 最终结论

你的修订建议应当采纳，尤其是支持组、双时间、影响定位、原文读取关联以及单次提案的真实成本边界。它们使 RSR 从一个概念性更新操作，变成能够放进持续运行系统的机制。

进一步的定位应是：

> **MiLAi 是一个维护条件性理解及其支持关系的文本记忆系统。它用统一的变更流程处理新增、补充、临时覆盖、真实变化和解释纠错，并让所有取材入口反映当前修订状态。**

论文则集中证明：

> **在相同历史、相同记录粒度和可比计算预算下，支持保留的修订与关联更正取材，是否比普通记忆更新更少复现已知错误，同时保留仍有依据的认识。**

**工程要完整，科学主张要集中。**完整性不应通过增加模块来体现，而应通过一个更严格的验收条件体现：

**同一项理解，无论从当前记录、原始来源、摘要、邻接还是恢复状态中被取得，系统都能说明它在什么条件下仍可使用、哪些部分已经更正、哪些问题尚未解决。**
