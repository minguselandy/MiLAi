# MiLAi Lab：记忆维护、材料读取与创新候选开发 Goal

**完整开发本轮 Lab 记忆能力，通过固定的小规模原生 benchmark 比较候选机制；整理代码与功能开发同步推进。以实际效果和成本决定保留哪些机制，不预设创新成立，不安排 Product 迁移。**

本版以制定时的 Lab 工作树为起点，吸收两份创新建议中的支持关系、统一维护、读取关联和生命周期设计。文档版本 v3.0 与方法版本是两件事：起点为 `contextual-user-memory-v3`，当前增量实现为 v6。第 2 节保留制定时的诊断；实际交付状态见第 11 节及结果说明文末。

## 1. 本轮范围与执行原则

1. 完整实现统一操作、准确来源与版本、条件性理解、修订、State/Attention、材料组织、恢复和遗忘；按可运行的纵向增量交付。
2. 实现一个增量，就在对应的少量原生题目上检查行为。小规模实验贯穿开发，不等全部功能叠加后才找问题。
3. **不运行全量 benchmark、全仓 pytest 或全模型矩阵。** 旧 formal-v1、formal-v2 不恢复；旧产物和结论保留。
4. 测试集不修改、不补写澄清、不插入自造更正、不按答案裁剪历史。适配器解释上游协议，方法只看到合法输入。
5. Host 及需要的 LLM Judge 使用 vLLM；Judge 只参与离线评分。普通确定性评分继续使用原生规则。
6. 先读具体实现，再借鉴一个可说明的机制。参考项目源码已提前准备；不把多个外部框架部署成新的运行时。
7. 使用直接函数、少量明确类型和本地状态。外部输入解析一次，内部按类型使用；不增加分类 Agent、常驻审查 Agent、通用事务平台或层层兜底。
8. 允许实验否定候选。完成开发不以正向分数为条件，也不要求把六个候选全部打开作为默认方法。

本 Goal 的“完整”限定为情境化用户记忆这条 Lab 主链，不扩展到其他历史研究、训练项目、跨服务并发、生产数据库或 Product 接口冻结。

旧四题中，PersonaMem 三题的两种记忆方法均未答对，LongMemEval 一题均答对；这没有证明候选有效。新的 v3 接线不能沿用旧成绩。四题已经暴露，只作兼容性检查，不称为新候选的独立验证集。

旧 formal-v2 停止时已有 67 份答案，尚无 Judge 结果；停止状态、原始输出及历史成本保持原样。小题数也可能包含很长历史，故本轮同时限制题数、历史构建和模型调用，不能只报告作答阶段成本。

## 3. 代码组织：按职责抽取，保留入口

### 3.1 记忆核心的目标结构

```text
src/milai_lab/methods/
  contextual_user_memory.py       # 原导入入口与小型兼容外壳
  contextual_memory/             # 随对应功能逐步形成，不提前创建空框架
    models.py                    # 引用、观察、理解、支持组、变更与回执
    store.py                     # 当前版本、历史、任务状态、本地恢复
    revision.py                  # 变更组提交、反向关系、支持重算
    retrieval.py                 # 索引、BM25/向量候选、时间与邻接定位
    materials.py                 # 当前视图、必要关联、范围合并、预算
    service.py                   # 四工具分派及 State/Attention 装配
```

依赖方向为 `models ← store / retrieval / revision ← materials ← service`；`revision` 不依赖检索排序，`materials` 通过确定的状态查询读取修订结果。语义种子由 service 交给 revision，不让两个模块互相调用。继续复用 Workspace 和 Attention 中适合的组件，避免复制整个旧实现。

提取模块时先保持行为、回执、顺序和预算不变；新机制作为下一项明确行为变更加入。无需为了达到上述文件形状而拆出只有一两个转发函数的模块，也不按行数机械拆分。

| 位置 | 目标职责与实施边界 |
| --- | --- |
| `providers/contextual_vllm.py`（拟新增） | 迁移已有 vLLM 传输与配置，供 Host 和 Judge 复用；不建设通用 Provider 插件系统 |

## 4. 统一记忆语义与生命周期

### 4.1 逻辑对象

| 对象 | 最小职责 | 改变方式 |
| --- | --- | --- |
| Observation | 接入实际取得的来源、角色、事件／会话身份、原文与时间 | 原文保留；采集错误通过替代关系说明；按用户遗忘和生命周期删除 |
| Claim | 可以独立修订的一段理解，包括作者、主体、适用条件、不确定性和有效期 | 建立新版本；不要求把每句话都拆成逻辑命题 |
| Justification | 指向某个 Claim 版本的支持组或反对组；组内为共同依据，组间为替代路径 | 增加、撤回、限定范围；保存准确来源版本／范围与适用条件 |
| ChangeSet | 本次实际变更、原因引用、各组回执及尚未处理对象 | 已提交记录不覆盖，纠错产生后续变更；不无期限复制待遗忘正文 |
| TaskState | 当前任务采用的版本、情境、未决点、覆盖判断及临时覆盖 | 任务局部变化；不自动改写长期默认 |

这是一套逻辑模型，不意味着必须增加五套数据库。首版使用 dataclass、字典和已有本地 checkpoint。支持项可直接嵌在 Justification 中，不再为其建立通用图服务。

没有外部来源的想法仍可保存。**存在、是否有支持、是否适用、是否有争议分别表达。** 程序不能根据“用户说”“已验证”等正文设置可信来源，不能将 `verified=true` 当成真实性认证。

### 4.2 支持状态

- 一个支持组内的必要项共同成立；同一 Claim 可以有多个替代支持组。移除其中一组，不自动移除另一组仍支持的理解。
- 组状态为 `USABLE / UNUSABLE / PENDING`。计算依赖当前任务、世界有效时间与系统当时已知信息，不把未知条件一律解释为不成立。
- `USABLE` 表示声明的支持路径在当前条件下可用，不是语义真假证明。反对证据保留争议，不机械地让最近一句获胜。
- 每个支持项绑定目标 Claim 的准确版本、来源版本／摘录范围和支持范围。命题、主体或条件发生实质改变时，不把旧支持自动转给新命题。
- 同源摘要和复制件不能作为新增独立观察；“替代路径”也不自动意味着统计独立。
- 仅由循环互相支撑且没有可用外部根的关系不能自证为 `USABLE`；首版限制提交的依赖组为无环关系即可，不开发完整逻辑证明器。
- 已有 `source_refs` 仅迁移为 provenance。不能猜测原来列表表达 AND 还是 OR；新实验需要支持语义时，从相同原生历史重建该候选的记忆。

维护 `source/version → support groups` 和 `claim/version → dependents` 两个直接反向索引。先用新信息检索相关种子，再沿已声明关系定位影响；只重新计算受影响的组及其替代支持。没有被记录的语义联系仍可能遗漏，不能把遍历完反向索引称为“已找全所有影响”。

### 4.3 三类时间与八类事件

记录来源事件时间、理解的世界有效区间和系统获知／修订时间。未知时间允许为空，不伪造精确日期。历史查询同时使用 `valid_at` 与 `known_at`；系统后来知道的更正不能泄漏进当时的顺序回放。

| 输入 | 必须实现的行为 |
| --- | --- |
| 新信息 | 保留来源，创建必要理解，允许 task-only 或不持久化 |
| 补充佐证 | 补全共同支持或新增替代支持，保留共同出处 |
| 临时要求 | 建立当前任务覆盖，长期默认仍保留其原适用范围 |
| 真实状态变化 | 结束旧有效区间，增加新状态；保留旧状态曾经成立的信息 |
| 解释纠错 | 修改旧材料所支持的主体、范围或命题，不改写原始表达 |
| 未决冲突 | 呈现正反依据与待确认事项，不强行生成确定画像 |
| 整理压缩 | 优先合并展示和派生视图，保留回到原文的入口 |
| 遗忘／退出 | 处理正文、依赖、索引、缓存、checkpoint 和受管日志；不能用解释纠错的粗粒度删除替代 |

RSR 是其中的解释纠错机制。不能只实现撤回场景，就宣称完整记忆生命周期已经完成。

### 4.4 一次提案与局部变更组

```text
发布实际来源
  → 检索相关理解，展开必要旧来源与已声明关系
  → 当前 Host 提出一次有界 ChangeSet
  → 程序解析引用／版本／用户边界／操作结构
  → 提交相互依赖的局部组，分别返回真实结果
  → 重算受影响支持，登记未决对象，使当前视图失效
  → 读取路径按新状态组织材料
```

“撤回旧支持、增加新支持、更新同一理解”属于一个局部原子组。首版在内存中准备该组的差分，验证后一次替换相关状态，随后使用现有原子文件写入方式保存快照；不引入分布式事务。不同组可以分别成功，已经保留的原始来源单独回执，不承诺整批回滚。

同批新建 Claim 与支持组允许使用提案内别名，例如 `new:c1`；服务在提交组时映射为真实引用。别名只在这一提案内有效，后续读取始终返回真实版本引用，避免为了获得新 ID 强迫 Host 再调用一次。

统一回执至少表达：实际成功项、冲突／失败项、仍待处理项、可继续使用的引用。`VERSION_CONFLICT`、`PARTIAL`、`PENDING` 不得因为顶层没有 `ERROR` 就计为完成。复用回执应反映原操作结果；语义失败不进行自动无限重试。

### 4.5 统一读取与材料包

四工具继续为 `memory_search / memory_read / memory_save / memory_state`。Host 选择保存来源、记下理解、修订目标或改变任务状态，不先选择 Evidence／Note。

所有路径共享同一个当前状态解析：搜索摘要、准确版本读取、原文范围、邻接展开、缓存命中以及恢复后的读取。原文正文保持准确，相关更正和当前适用状态作为独立关联材料呈现；不得把旧原文替换成模型整理后仍称为原文。

材料包按“当前理解＋必要来源＋相关更正／限制”整体计预算。预算不足时优先保留必要限制，缩小原文范围或返回明确的展开引用；不能只留下脱离更正的片段，也不静默截掉让语义成立的条件。默认只展开与当前查询、命中范围和当前解释相关的关系，不遍历整张图。

先实现稳定会话序号、真实 BM25、同来源多范围命中、范围合并和时间／邻接读取；这些检索改善应作为公共基础供比较臂共享，避免把修订收益与更好的检索器混为一谈。任务日期可以由适配器提供，语义时间条件由 Host 从合法问题表达，不能读取 gold 相关会话索引。

### 4.6 恢复、遗忘与权限

checkpoint 保存同一逻辑状态的对象、版本、支持组、已提交变更、任务覆盖和未决队列；派生向量缓存绑定真实内容／版本及 embedding 身份。方法 schema 改变时明确版本，旧快照不得被静默解释成新语义。

遗忘处理受 Lab 管理的来源、派生正文与持久副本，并维护最小删除标记，防止恢复旧 checkpoint 后重新出现。删除标记不能只放在可能被回滚的旧快照内部；可使用每用户一个独立的小型本地删除记录，恢复时应用。benchmark 原始文件保持不动，评测档案可读与持久记忆删除的区别要在运行配置说明；执行遗忘后的同一方法不可从档案自动重新摄入被禁止保留的内容。

语义撤回只改变支持或当前解释，不能据此把原始历史抹去；真实遗忘又不能被“历史不可修改”阻止。Lab 无法擦除外部 Host 已经看到的聊天记录，只能约束自己后续交付及受管存储，不声称远程撤回已发生。

## 5. 六个候选：逐项实现，实验决定取舍

H1/H2/H3 是优先研究假设，H4 是条件性记忆假设，H5/H6 首先作为工程及效果探索。制定本版时它们都尚未实现或证实，当前状态见 §11；支持维护、版本管理、情境检索和事务本身已有先例。

| 候选 | 可实现的增量 | 最小对照与判别问题 | 首选小样本／主要指标 | 取舍与创新边界 |
| --- | --- | --- | --- | --- |
| **H1 支持保留的局部修订** | AND/OR 支持组、准确范围、反向索引；只撤回受影响的支持 | 相同粒度、相同候选材料的普通更新；另用极少数确定性例子检查全后代失效与替代支持保留的差别 | MemSyco valid selection＋personalized use；错误旧偏好使用、有效理解误删、任务得分 | 最有希望形成具体机制比较；公开题未出现替代支持时不能据其正确率宣称证明了 AND/OR 增益 |
| **H2 更正随材料交付** | 原文、摘要、缓存和邻接材料均关联当前更正；整体预算 | 同一修订快照、相同检索，比较普通读取与关联读取 | MemSyco valid selection／scope；STALE PR；旧理解再次被采用、原生得分、材料 tokens | 若存储修订已足够，则降为工程一致性；不能单凭多给一段答案相关文本称为新机制 |
| **H3 有预算的增量影响维护** | 同步完成已知结构失效，语义未决对象入小队列；按查询相关性继续处理 | 同样已声明关系下，立即完成全部已知闭包与按需维护比较 | STALE 少量长历史；已声明影响覆盖、未决数、任务完成、维护 tokens／时间 | 研究质量—成本边界；不得把未处理部分冒充完成；不新增后台 Agent |
| **H4 区分状态变化、临时例外与解释纠错** | 用同一 ChangeSet 改有效期、task 覆盖或原支持归属；维护 `valid_at/known_at` | 已有 subject/context 字段＋普通整条更新，对比不同事件操作真正产生不同状态 | MemSyco scope／valid selection；PersonaMem 少量顺序题；范围错误、历史泄漏、原生得分 | 字段本身不新；研究的是不同修订操作是否减少临时要求的永久化及错误回溯 |
| **H5 按当前上下文增量交付材料** | 精确版本／范围合并；只对确实仍在当前上下文中的材料省略重复正文，更新后的限制仍交付 | 相同候选、相同预算，比较重复完整材料与差量材料 | MemSyco、PersonaMem 的多轮工具读取；重复字节、调用数、任务得分 | ReMe/OpenViking 有强先例；首先是成本优化，不预设论文贡献 |
| **H6 从必要原文重新整理** | 在已有一次提案中加入相关理解的必要原始依据，重新建立有范围的支持；避免只从旧摘要继续概括 | 相同原始档案权限和调用上限，比较仅旧理解提示与附带必要原文；报告实际输入差异 | MemSyco scope／personalized use；PersonaMem 条件性偏好；范围保留、得分、摄入成本 | 参考 ReMe/HiMem；若收益仅来自额外上下文，标为材料供给收益，不能归因为新修订算法 |

H5 的交付记录须绑定 Host 轮次／上下文代次、真实对象版本与实际范围。上下文被压缩、换任务或恢复到新 Host 时清理或重新确认；`seen` 不可直接复用为“还记得”。首版只省略能够由当前请求消息列表确认存在的材料，不建设额外模型压缩流水线。

H3 延迟的是进一步的语义重整理，不是已知失效标记、遗忘或权限变更。一次摄入默认仍只调用当前 Host 一次；确有未决需求时，后续任务可消费有界队列，最多增加一次显式补充提案，并计入成本。

候选采用有限、显式的 profile，不组成六个布尔开关的全部排列。主机制先比较 H1，再比较 H1＋H2；H3、H5、H6 分别做单因素成本／效果比较，H4 在条件性任务单独比较。无收益或成本不合算的实现保留最小结果记录，整理掉不再使用的分支。

## 6. 小规模 benchmark 协议

### 6.1 数据与固定规模

| 数据集 | 本轮用途 | 单次规模 | 准备状态与限制 |
| --- | --- | --- | --- |
| MemSyco-Bench | 首轮候选筛选；当前记忆、范围及有效个性化 | 预选筛选 12 题；另 12 题确认，每组各三类任务各 4 题 | 原始文件、ID 和 SHA 已固定；适配与 Judge 已实现；实际执行范围见第 11 节 |
| STALE | 间接变化、旧前提抵抗、隐含行为适应 | 预选 T1/T2 各 2 场景共 12 probe；实际因长历史成本只尝试首个 T1 的全部三问 | 适配和原生组评分已实现；数据版本 `617c51dc200b`，原文件通过上游 LFS SHA-256 校验；其余场景未运行 |
| PersonaMem-v1/v2 | 偏好、主体与条件性记忆的兼容和跨任务检查 | 按需要选 4–8 个原题，优先共享历史；不扫描全库作答 | 复用已下载原始文件与现有适配；旧四题只作已暴露回归 |
| LongMemEval | 时间和来源检索能力的局部检查 | 按需要选 4–8 题，保留对应完整合法历史 | 复用现有数据；不跑 500 题，不把长历史按 gold 相关片段裁剪 |

实际固定清单保存在 `data/manifests/contextual-memory-v3-memsyco-small.json`。选择规则为种子 `20260923`，在每个预先声明任务内按 `SHA256(seed:commit:task:id)` 排序：前 4 题筛选，再 4 题确认。只用任务和 ID 选取，不根据答案或方法结果挑题，不生成修改后的样本副本。

STALE 清单为 `data/manifests/contextual-memory-v3-stale-small.json`：同一种子，在 T1/T2 内分别按数据版本、类型和 uid 的 SHA-256 顺序选择前两个场景，保留其完整三问及原始历史。下载完整上游文件用于准确读取所选场景，不代表运行全量评测；不启用上游利用相关会话标注裁剪干扰历史的可选路径。

每个候选先运行最相关的一到两个任务切片，即 4–8 题、两个臂；只有初步有用的至多两个候选进入确认组。确认组只在候选版本固定后使用，使用后标为已暴露，不能反复称为保留集。STALE、PersonaMem 和 LongMemEval 按候选所需覆盖执行一次小批次，不要求六个候选遍历四个数据集。

MemSyco 还有 evidence conflict 与 objective fact 两个任务，源码和原题均已取得；本轮不默认扩大到全部五类或 1,550 题。若当前候选没有相关机制，不为增加表格数量安排它们。

### 6.2 合法输入与原生评分

- MemSyco Host 只接收 `dialogue` 和 `question`。`memory` 是 gold 记忆，`evaluation` 是答案／rubric，`metadata` 与任务标签属于评测侧；不能把 `memory.policy` 当成路由指令，也不向 Host 提示本题属于哪个评分任务。
- STALE 使用上游 haystack、真实消息顺序、原始日期及当前 probe；旧／新状态标注、解释和相关会话答案索引只在评测侧。三个 probe 从同一摄入快照各自启动，前一问的回答和评分不进入后一问。
- PersonaMem 使用官方历史前缀及选项组织规则；LongMemEval 保留原生问题、问题时间与合法历史。共享历史的不同问题默认从同一历史快照独立启动；需要顺序适应的原生协议单独标识。
- 先冻结答案，再按已固定的原生 rubric 评分。Host 与 Judge 使用独立请求，Judge 不访问候选名称及方法 trace；可以使用同一 vLLM 服务，但报告具体模型，不能称为独立模型验证。
- MemSyco／STALE 的原生 Judge 输出可能比 LongMemEval 长，按各自 schema 设置输出预算，不复用当前 `max_tokens=32` 后截断评分。保持 rubric 和解析语义，仅替换传输为 vLLM。
- 原生公开脚本若规定其他 Judge 型号，本轮结果注明为“原生题目／rubric＋本地 vLLM Judge”，不能冒称官方榜单同条件分数。

### 6.3 对照与归因

主比较最多三个臂：`RAW_RETRIEVAL`、`ORDINARY_MEMORY`、一个明确版本的候选。原文检索臂直接从相同合法档案取材；普通记忆臂采用相同粒度、同一基础检索器与普通增改，不故意设为不会更新的弱基线。

机制比较固定候选材料、检索配置、Host 模型、调用上限和总输入预算，仅切换待测机制。完整系统比较允许流程不同，但使用相同合法档案并报告实际总成本。因对象模型不同而不能共享候选生成时，明确记录该差异；不能把整条流水线变化的收益归给单个支持操作。

H1/H2 若都有初步效果，再做一次极小的写入／读取 2×2：普通更新＋普通读取、支持维护＋普通读取、普通更新＋关联读取、支持维护＋关联读取。可分成两个双臂批次复用同一组题和固定摄入产物，不另开全数据矩阵。普通更新臂也可产生更正链接，避免关联读取在该臂被人为禁用。

### 6.4 执行预算与停止方式

默认先单并发；稳定后 Host 最大并发 2，Judge 1。每题沿用有界工具循环，默认最多 8 次 Host 生成；正常历史摄入每批一次提案。不要为每条原始消息调用一次模型。

runner 已实现持久运行预算对象，默认上限如下；每次运行仍以冻结配置中的具体值为准。

| 项目 | 筛选批次 | 确认／长历史批次 |
| --- | ---: | ---: |
| 原生问题／probe 上限 | 12 | 24 |
| 比较臂上限 | 3 | 3 |
| Host＋Judge 生成请求上限，含失败尝试 | 160 | 256 |
| Host＋Judge 已知输入／输出 tokens 上限 | 1,000,000 | 2,000,000 |
| embedding 已知 tokens 上限 | 2,000,000 | 4,000,000 |

按运行配置记录明确上限，准备发请求时用已知输入量及最大输出预留量检查剩余预算；不引入跨研究的复杂预算平台。长历史预估不适合当前小批次时，在运行前减少题数或分批，保留所选原题完整历史；不能在看到答案后换题或裁掉干扰内容。

达到任一上限即停止发新请求，保存已有结果及未完成项。上游没有报告 usage 时标为未知，保留请求上限与本地输入估计，不记成零。失败与有限重试均计数，最多进行一次传输或输出格式重试；题目未完成不从分母里消失。

一个候选完成一次筛选和一次针对性修复检查后先归纳问题；没有明确、通用的修复理由就不反复调参刷同组分数。默认不运行多个 Host 型号、随机种子或采样温度。

### 6.5 必须报告的结果

1. 原生各任务得分、分子／分母、未完成数、未判定数；同题配对的改善／退化清单。不将不同数据集的不同指标随意平均。
2. 从 trace 可确认的来源归属错误、旧版本使用、重复材料、版本冲突误报；语义误用只有原生 rubric 或明确人工诊断依据时才计数。
3. 历史摄入、修订维护、作答、Judge、embedding 分阶段的请求数、tokens 与耗时。未知 GPU 时间保持未知。
4. 已声明关系的受影响对象数、处理数、待处理数，以及替代支持被保留的情况。没有关系 gold 的公开题不报告虚构的“真实影响召回率”。
5. 实际共享缓存节约与各臂独立冷启动估算分开；只归给第一个臂的共享 embedding 费用不能直接用于宣称后续臂更便宜。

小样本用于发现方向、失败类型和成本，不据 4–12 题宣布普遍优越或统计显著。若多个候选同分，优先保留结构更简单、调用更少且没有新增关键退化的版本。

## 8. 简洁实现与必要验证

### 8.1 编程约束

- 在 JSON、模型输出、磁盘恢复和工具入口进行一次必要解析。内部传递有类型对象，不在每层重复 `isinstance`、默认空字典和同义字段猜测。
- 版本比较、来源身份、用户边界、删除传播、真实部分失败属于业务语义，保留明确检查。减少防御性包装不能变成静默覆盖或伪报成功。
- 捕获能够处理的具体异常。只在 runner 的单题边界归档失败；不在每个函数放 `except Exception` 后返回空结果。
- 一个对象的字段有一个含义，一个状态有一个解析入口。先修回执合同，再让 ingestion 和在线 Host 共用，不保留两套互相补丁的成功判定。
- 不建立插件注册中心、万能后端接口、图数据库、分布式事务、后台 Dream 流水线或自动 Reviewer 链。配置只列实际比较的有限 profile。
- 每次改动顺手清理所在模块的重复逻辑和命名；不将其他历史研究目录纳入重构。

### 8.2 验证范围

benchmark 优先验证实际任务行为。只有 benchmark 不直接观察的机械语义才补很少的定向例子：共同／替代支持、提案别名与局部原子性、嵌套冲突回执、合法时间前缀、准确范围和恢复／遗忘。例子服务于不同失败机制，不把同一实现展开成大量参数排列。

纯文档及清单更新只检查 JSON、路径、数量、互斥分组和源文件散列。本轮开发使用修改文件的静态检查、受影响的已有单测以及当前小样本；包边界发生变化时再运行 `milai-lab-check-boundary`。不为仅改文档运行 pytest，不为普通局部实现运行全仓 pytest、全包构建或大型合成验收平台。

如果改动了打包入口，则做一次对应构建；如果引入新类型接口，则检查受影响模块。通过后不无故扩大验证范围。已有 Lab 通用交付命令中的全套检查不作为本 Goal 的默认要求，按用户本轮“小规模、开发优先”的范围执行。

## 9. 开发协作与模型成本

默认由一个主开发者保持架构和结果一致；确有独立任务时启用一个或两个短期 worker，不建立长期多层团队。以下采用用户指定模型档位，表示任务分配偏好，不宣称价格或性能排行。

| 角色 | 模型／推理强度 | 合适任务 | 不应同时修改的范围 |
| --- | --- | --- | --- |
| 主开发／常规实现 | Sol xhigh | 核心整合、普通功能、实验归因、文档与结果收敛 | 协调 service、公共 models、run 配置和默认 profile |
| 下载 worker | Luna high | 仅下载数据集、项目源码和测试集，记录下载身份 | 不承担实现或语义判断 |
| 窄任务 worker | Luna max | 明确字段映射、散列核对、固定选样及少量机械检查 | 不独自改支持语义或并发改公共合同 |
| 疑难问题协助 | Astra xhigh | 支持语义冲突、无法定位的跨层错误、候选归因难题 | 聚焦一个已复现问题，给结论后退出，不常驻审核 |

可并行组合为“主开发做记忆核心，worker 做数据适配／评分”；待公共类型明确后才并行材料模块。任务交付包含改动、最窄验证和剩余问题即可，不安排双重审查或阶段批准。

vLLM 实验由一个调度入口持有配置与预算，各 worker 不自行启动服务或重跑 benchmark。复用相同合法历史及能够证明相同的中间产物；会受候选语义影响的摄入结果不得跨候选错误复用。
