# MiLAi Lab v12 Goal：让失败修订能够修好，让维护完成反映实际结果

**目标：消除当前真实任务中“已读仍误拒、局部更新难以合法提交、失败修订被静默终结、业务成功后维护无法恢复”的故障；在共享能力不减少的前提下，降低公共合同与失败恢复开销。先完成开发，再用少量原生故障场景验证，不增加记忆候选。**

状态为 IMPLEMENTED_PENDING_SMALL_VALIDATION。用户已授权完整执行 v12；A—D 核心实现和窄检查已完成，现按[冻结身份](../data/manifests/contextual-memory-v12-development-freeze.json)进入 E 的已暴露原生后缀诊断。原规划时的只读事实保留在[分析及改造设计](MILA_CONTEXTUAL_USER_MEMORY_V12_FAILURE_ANALYSIS_AND_REPAIR_DESIGN_20260925.md)及[诊断清单](../data/manifests/contextual-memory-v12-planning-diagnosis.json)，实施情况见[v12 开发记录](CONTEXTUAL_USER_MEMORY_V12_DEVELOPMENT_20260925.md)。v11 仍按负面／不确定效果结项，其结果与费用不重写。

## 1. 为什么这次优先级要变化

v11 当前 R3 已修缓存过度失效、检索统计和安全错误码投影。本 Goal 继承这些改动，不重复列为待开发功能。

当前仍有以下真实问题：

| 问题 | 证据 | 本 Goal 要交付的改变 |
| --- | --- | --- |
| 同一来源换一个句柄后仍被判未读 | arc1 A0 读取 m10 后获得同对象正文 m19，继续引用 m10 再被拒 | 使用现有会话的准确对象／版本／范围可见事实 |
| 合法局部修改被主体及依据合同阻碍 | 五份提案的当前纯主体校验重建均为 ABOUT_SOURCE_NOT_CITED | 清楚交付主体锚点和可继承依据，优先用已有 delta |
| 修订全被拒，却维护 complete | arc2 A1 三次金额修订失败后 processed，下一集按旧金额退款 | 未解决写入尝试进入现有维护状态，可修复、放弃或继续 pending |
| 业务成功后仍漏写或卡住 | arc1 A0 维护中止；A2 业务通过却未回写完成状态 | 保留业务结果与待维护内容，同轮续接并验证当前卡 |
| 输入成本集中在公共合同 | 固定合同分段约占输入 60.23%；当前 Basis 投影约 0.32% | 优先压缩公共工具表达，之后再判断是否优化 sidecar |

这是问题驱动的修复 Goal。不是把上一版“继续减少 State”当成固定答案，也不是重做所有 CRUD、主体或事务设计。

## 2. 范围与不能被误解的约束

Lab-only；ordinary 保持默认；Product 不改动、不迁移。保留现有来源、准确版本、可见范围、权限、删除和业务执行日志。State 不授权业务动作，也不能证明外部业务已经完成。

不新增候选、支持模式、H1—H6、Jev、审核 Agent、图数据库、多决策槽或训练控制器。不换 Host 权重，不扩展 benchmark。本轮修复所需 MERIT 源码及原生制品已在本地，不需要为开发下载新记忆框架。

源代码修复先完成，确定性窄检查随后完成，再选择最小必要的真实诊断。测试用于回答一个具体问题，不能变成机械跑完大量清单。累计请求、tokens、复核次数保持 null，连续保留所有失败费用；单工作流上下文容量、并发和明确停止条件仍有效。

若新代码运行失败，不根据预算耗尽直接放弃已授权开发；也不凭“累计没有上限”反复运行同一失败配置。每次新增真实调用应对应新的修复或待验证解释。

## 3. 完成标准先于工作项

以下结果比新增函数数量或测试数量重要：

1. **能合法修订：**已交付的新要求能进入正确的原卡；已通过其他别名读取的同一准确来源不会误拒。
2. **能解释拒绝：**真实未读、主体关系冲突、错误引用种类等错误能引导下一步，不只返回无法行动的失败状态。
3. **不会假完成：**Host 已尝试且仍需完成的写入不能消失为 processed；明确可选放弃与合法零写入仍能结束。
4. **能恢复且不重做业务：**真实业务结果已经保存，恢复只处理未完成维护，当前记录随后可以被正常读取和使用。
5. **能指出成本变化：**共享合同压缩及恢复改善有本地或小样本证据；未证实的总效率与方法收益继续保持未证实。

这里只要求所选原生诊断范围的工程结论，不要求每个旧样例反复调到通过，不以固定 20% Basis 占用或一定比例 token 降幅作为通过条件。

## 4. 工作安排与依赖

主顺序：**A 固定故障 → B 修可写性 → C 修失败收敛 → D 精简公共合同 → E 冻结后小验证。**

D 的零模型测量可以与 B/C 开发交错，但默认不把多个不相干协议变更揉成一次不可解释的修改。若 D 会扩大当前修复范围，可先完成 B/C 的有限验证，再以单独身份推进 D。

| 工作包 | 必做内容 | 可交接产物 | 开始下一步的依据 |
| --- | --- | --- | --- |
| A：故障定位材料 | 复用本次诊断，保留失败提案、准确绑定、前后状态和缺失证据 | 紧凑案例清单、现有行为的窄复现 | 能直接说明应改哪个函数及预期结果 |
| B：可见性与局部写入 | 准确对象级可见性；主体锚点／依据继承投影；可行动错误 | 最小代码改动、受影响检查 | 相同合法输入不误拒；真实无效输入仍拒绝 |
| C：失败收敛与恢复 | 待处理写入尝试；成功／明确放弃／pending；恢复保留 | 同一维护入口、必要快照接线 | 不再假 complete，也不把普通 no-change 卡住 |
| D：公共合同成本 | 从同一 schema 生成短工具说明，减少重复展示 | 旧新静态 token 对照、兼容性检查 | 模型仍能表达同一操作，未削弱能力 |
| E：真实诊断与总结 | 少量原生故障片段，必要时一条最终连续链 | 冻结身份、真实结果、失败与连续成本 | 得到有限通过或明确剩余问题，不追加方法候选 |

研究性 Attention 比较不在必做工作包。只有修复验证后仍有充分理由、且自然机制机会已明确，才另行安排后续研究。

### A. 固定故障，不再泛化猜原因

本次已完成只读源码与制品核对，可直接作为起点。实施时只补代码变更需要的最小复现：

- 别名不同而准确来源相同的可见性案例。
- 同主体修订移除身份来源的提案，以及合法继承版本。
- 三次修订拒绝后 processed 的维护状态。
- 已有业务成功回执、尚未完成维护的恢复状态。

旧 trace 含完整任务与业务数据，继续留在 ignored 目录。Git 只收精简的结构事实或独立构造的合同用例，不能将 benchmark 原文大量复制成项目测试数据。

五次主体错误目前只做过纯校验重建。若实施时需要完整确认，先在隔离状态重放确定性验证路径；不得把纯函数结果冒称完整历史重跑。

### B1. 修复准确对象级可见性

优先修改 Host 引用解析与 HostSession 可见性查询之间的窄接口。使用当前 resident transcript 中的准确对象版本、hash 与范围；保留别名作为不可变 locator。

不能单纯删除 binding.spans 检查后全部放行。每个写入分支仍核对其实际需要的可见范围；来源、目标全文和 patch 范围各按现有语义处理。已经清理的正文、其他对象或更新版本不能被借用。

完成依据：已有误拒案例通过，真正未读与旧版本案例仍被准确拒绝。无需新增持久表。

### B2. 让已有 delta 成为可直接使用的局部修订方式

交付当前目标时，简洁表达主体锚点、继承关系、新增可用来源和准确目标版本。只在适用时建议现有 content_patch＋basis_mode=delta；不强迫每个更新都用 delta。

对于保留主体却撤回必要身份来源的提案，返回安全的字段位置、当前可见别名及合法选择。保留主体就继承对应关系；真正改变主体需要显式新依据。程序不能自动撤销用户提出的关系移除，也不自动把所有用户消息认作同一主体。

局部正文变化不应附带无必要的 subject/context 重写。完整替换仍保留，满足真实语义变化需要。源码已有功能优先调整说明与投影，不新建第三条更新路径。

### C1. 统一失败尝试的去向

在当前维护结构中记录真实尝试过但未完成的写入，包括 Host preflight 拒绝及服务端完全拒绝。与已有 partial/pending 操作协调，避免记录两份。

记录只包含继续修复所需的信息：准确目标或可定位字段、尝试身份、公共错误、必要观察引用和处理状态。重试应沿同一目标收敛，不累积一串重复待办。

明确三条路径：

    修复后真实提交 → 清除该操作失败
    可选写入明确放弃 → 留下简短原因，不能声称已保存
    尚需处理 → pending，保留恢复材料

只要有未解决且未明确放弃的尝试，processed 不能将其擦除。反过来，没有失败尝试、没有可信接入的必存要求时，合法零写入可以正常结束。

程序能关闭“操作失败”，不能据此证明新正文正确。不要用自动语义匹配判断任意两份提案等价；目标明确时按目标及同一次修复的操作身份关联，不能因同卡任意一次成功就清除全部失败。确有歧义时由 Host 明确处理少量剩余项。

### C2. 保持业务状态与维护状态分开

沿用现有 begin_action／finish_action 及同轮恢复，不新造执行日志。业务已成功的回执必须在后续维护失败时继续可恢复。

恢复状态包含必要的新观察及目标引用，避免失败维护被清理后只剩旧卡可查。若新字段进入持久快照，声明新的格式或兼容策略，不静默装载不兼容旧 checkpoint。

处理“没有提出维护”的问题时，先用共享材料交付当前事项与业务结果，观察 Host 是否正确修订；不增加强制每条工具结果都写卡的规则。这项语义限制必须单列验收，不能被 C1 的失败追踪冒充解决。

### D. 压缩公共合同，先不动方法

本地 tokenizer 先比较当前固定 system、工具 schema、状态投影与材料的体积。已知主要热点是公共合同；State 投影不是当前优先对象。

用同一 schema 导出简短工具说明，保留字段语义、必要互斥分支、引用及权限合同。完整 schema 继续用于真实验证／解码。不要维护第二份手写工具规范；不要为取工具说明增加模型调用。

若压缩后写入合法性或理解明显变差，就保留必要说明，接受较小降幅。目标是完成任务的总成本，不能为了输入变短而增加拒绝与补读。

只在有剩余证据时进入两个可选分支：

- **截断仍阻断普通维护：**选一个失败前缀，检验一项明确的输出容量或已有推理配置调整；同权重、新身份、完整费用。
- **重复 sidecar 仍明显：**再考虑省略等价于 no-change；clear 与 null 的现有区别保持。先核对 decoder，不增加 State patch 动作。

两个分支都不是无条件必须开发的功能。不因计划写了名称就照单实现。

## 5. 测试与真实验证安排

### 5.1 窄检查

从已有文件选择实际受影响的断言，不默认执行整套测试：

| 位置 | 需要证明的边界 |
| --- | --- |
| tests/unit/test_contextual_host_adapter.py、test_contextual_sessions.py | 准确可见性、不同别名、旧版本与已清理正文 |
| tests/unit/test_contextual_material_view.py | 主体锚点和安全错误可行动；来源／卡片类型清晰 |
| tests/unit/test_contextual_maintenance.py | 完全拒绝、preflight 拒绝、修复、放弃、合法 no-change |
| tests/unit/test_contextual_runtime_recovery.py | 已成功业务后维护恢复，不重复业务，不丢必要观察 |

复用能覆盖的现有测试，仅为真实缺口补小用例。涉及 schema 时增加部署 decoder 的零模型检查；纯材料说明变化不跑无关全量构建。

### 5.2 真实诊断按失败链选择

在 B/C 的代码及窄检查完成后，冻结新源码、协议、配置及诊断输入，再运行同一 vLLM Host。默认从已暴露数据选必要前缀，不先买新样本：

| 诊断 | 最小观察链 | 范围说明 |
| --- | --- | --- |
| 更正被拒后沿用旧值 | 原卡 → 明确更正 → 合法修订 → 下一原生任务读取／行动 | 优先验证 arc2 A1 已发生的金额问题；不硬编码金额 |
| 成功业务后的恢复 | 已保存真实结果 → 修复记忆 → finish → 当前卡读取 | 优先验证 arc1 A0；本来已经发生的业务不能再次执行 |
| 零尝试的漏维护 | 当前事项 → 业务真实完成 → Host 维护 → 后续当前视图 | 使用 arc1 A2 已暴露问题检查剩余语义缺口 |

每项先判断现存状态能否按新身份合法导入。不兼容则重建必要原生前缀，计入全部请求。不能编辑身份 hash、改 CAS、替换来源来强行装载。

不重跑 v11 六条轨迹，不为比较增加模型臂。先验证共享 ordinary 写入／维护路径；只在某个剩余问题明确来自 Basis 接线时，补那一配置的必要片段。源场景来自 A1/A2，不代表所有诊断都必须保留方法比较。

若最终需要给出“当前默认完整运行”的结论，选择一条已暴露原生 arc，在最终源码与初始世界上连续完成；片段通过不能替代它。此项仅用于当前版本运行验收，不宣称未见效果或泛化。

### 5.3 失败时怎样继续

新的失败保留原请求、结果和费用。先判明是实现 bug、写入合同、Host 语义选择、容量还是任务机会不足。修复具体原因后使用新身份复核必要片段，不能每次把整套任务重新跑一遍。

若 Host 合法执行但语义仍差，报告真实边界，并判断小改动是否有依据；不要添加订单号、金额、case ID、动作名称或 benchmark 专用禁词规则。没有足够证据支持下一修改时，应交付已完成部分及明确剩余问题，而不是宣布方法有效。

## 6. 记账和报告的最小集合

继续使用现有 trace、summary 和 manifest。新增分析只服务于以下问题：

| 问题 | 所需记录 |
| --- | --- |
| 为什么写不进去 | 写入路径、目标版本、拒绝发生层、公共原因、最终是否修好 |
| finish 是否真实 | 实际提交、未解决尝试、明确放弃、业务结果与维护状态 |
| 恢复是否安全有效 | 原操作身份、业务执行次数、恢复后当前卡与必要观察 |
| 哪里还贵 | 输入／输出、截断、补读、修复请求、公共合同及材料分段 |
| 方法是否被实际使用 | 真实有效 query 来源与返回、版本通知；没有发生就保留零 |

段内 tokens 仅作解释，provider usage 作为总账。不要把无法分离的共享 reasoning、反事实额外调用精确归因给 State。embedding、Judge 和开发代理开销分列；不把跨模型 tokens 相加称为精确货币费用。

v12 账本从新运行开始连续增加，并引用封存的 v11 总计：238 次生成、2453097 generation tokens、14274 embedding tokens，unknown=0、Judge=0。其 F 子集为 184／1873368／12324，不能再次与 v11 总量相加。失败、恢复和诊断调用均计入，不重置旧账本。

MERIT 原生 scorer 不变。本轮不需要额外 LLM Judge；将来确需使用时通过 vLLM，单列费用。业务原生通过、Host complete 和语义维护正确分别报告。

## 7. 模型分工与开发性价比

推荐一个 Sol xhigh 负责 Host、维护和恢复的集成，减少多个代理同时改关键执行路径造成的返工。

只有实施时明确安排并行任务，才将窄任务交给 Luna max：本地制品统计、限定投影函数、导航与文档检查等。Astra xhigh 仅处理已经定位且普通实现难以解决的合同冲突；不设置常驻审核层。已授权的下载或 Git 发布可由 Luna high 执行，但本文档本身不发起发布。

Host／运行实验保持一个入口、并发 1。源码并行不等于模型实验并行，避免并行调用污染费用和环境状态。

本轮规划未启动子代理。实施前按当时授权和实际任务拆分使用代理，不把角色表当作必须开齐所有模型的要求。

- 源码／协议／配置与诊断输入的冻结清单。
- v12 开发记录和小规模结果文档，分别写工程完成、语义限制、费用及未运行项。
- 如有新兼容格式，明确恢复方式；原始运行库和旧结果不覆盖。

不预先创建空的成功报告。原始模型输出、业务世界、数据库、权重和完整 benchmark 继续 ignored；Git 只纳入必要源码、测试、模板、紧凑清单和报告。

当前设计与 Goal 的状态不能随着文档提交自动变成 implemented。建议状态：

    PLANNED_NOT_STARTED
      → IMPLEMENTED_PENDING_SMALL_VALIDATION
      → 限定范围的验证结论

负面／不确定结果允许以 COMPLETE_WITH_NEGATIVE_OR_UNCERTAIN_EFFECT 如实结项，前提是授权范围内开发及必要诊断已完成。关键修复尚未完成时不能因为已有检查通过或模型请求昂贵而标记完成。

## 9. 后续研究何时再开始

本 Goal 不承诺 Attention 胜过 Notes。满足以下事实后再讨论方法比较：

1. 普通修订、失败恢复和当前事项维护不再被已知合同问题阻断。
2. 任务自然存在 active decision 内的信息缺口或依据变化，不能靠修改原生会话制造。
3. 预取没有已经提供全部所需信息，或者重核确实改变需要核对的材料。
4. Notes、Basis 与 Attention 共享同样的合法信息、CRUD、业务日志、恢复和公共工具表达。

没有这类机会，就继续以工程修复结果结束；不为了证明“功能使用了”强制搜索、引用卡片或填写 gap。若后续具备机会，先明确一项可识别的控制差异，再选择新的原生小样本。当前两条已暴露实例继续只作开发回归。

**本版以修好具体问题为成功依据：该更新的记录能更新，失败不会消失，已完成业务不会重做，剩余成本能够解释。新的方法主张必须等匹配的实验，而不是继续从更多代码路径中推导。**
