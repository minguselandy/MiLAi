# MiLAi Lab 开发状态评估报告

**当前 Lab 已形成可以继续研究和小规模复现的记忆原型，六个候选具有实现入口，八类生命周期具有程序路径；本轮尚未证明候选在任务质量和总成本上稳定优于普通记忆。普通记忆继续作为默认合理。**

工程完成需要限定为本轮研究原型的最小范围交付：长历史摄入仍不稳定，若干候选的关键机制没有在公开样本中触发，State/Attention 的主动闭环未进入这六个候选的运行配置，结构整理也仍有明显余量。Goal 的完成状态可以保留，但不能据此宣称完整行为覆盖、稳定长期记忆或研究创新已经得到验证。

## 2. 当前架构与代码组织

### 2.1 实际运行链

```text
固定原生题目与合法历史
  → 数据适配：TaskInput / EvaluationCase 分离
  → CLI：配置、模型／数据／源码身份、有限预算
  → runner：按臂和准确历史分组
       → 摄入：每批一次 Host 提案
       → 记忆核心：来源、理解、版本、支持、当前任务
       → 检索：BM25 + 向量 RRF、时间与会话邻接
       → 材料：准确范围、必要关联、全文或差量交付
       → Host：有界工具循环及实际回执
  → 作答冻结
  → 原生评分规则或独立请求的 vLLM Judge
  → 任务结果、未完成项、分阶段成本
```

### 2.2 默认配置实际开启什么

当前默认是 `ordinary`：普通版本化增改、共享 BM25／向量检索、普通全文材料、每批一次摄入和批量 embedding。默认只有一条已暴露 MemSyco 题，最多 24 次生成和 150,000 生成 tokens；它是轻量执行入口，不是完整评测规格。配置建立后未另行运行这个单题默认批次，普通记忆的真实执行证据来自已有比较臂。

一个需要在后续介绍中讲清的事实是：`ordinary`、`support`、`events` 及其 H2/H3/H5/H6 变体的 `contextual` 均为 false，Host 工具列表包含 search/read/save，**不包含 `memory_state`**。独立的 `state` profile 才开启该工具。

因此，当前支持对象和 TaskState 已存在，也能通过程序路径操作；这六个候选批次不能证明 Host 主动更新 State、Attention 随之改查材料的完整循环有效。条件性支持所需的 `state.conditions` 如何在真实 Host 流程中建立，也需要对应接线和执行证据。

## 3. 记忆流程与生命周期完成度

### 3.1 来源与理解的关系

Observation 记录适配器实际取得的原文、角色及事件／会话信息。Interpretation／MemoryCard 维护可以修订的理解。Justification 以准确版本和可选来源范围声明支持或反对关系，ChangeSet 保存实际执行的变更组及回执。

统一工具使 Host 可以表达保留来源、记录理解和修订目标。程序仍保留出处、加工关系和版本差异；来源可定位不等于语义真实，`USABLE` 也只是声明路径在当前条件下可用。

支持计算已经区分组内共同依据、组间替代支持、未知条件、反对关系和版本失效。独立想法可以没有支持。旧 `source_refs` 不被自动猜成 AND/OR 关系，这一点符合原设计。

### 3.2 八类生命周期

| 生命周期 | 代码状态 | 当前验证可以说明什么 |
| --- | --- | --- |
| 新信息 | 来源发布、普通保存及 claim 创建已实现 | 多批短历史真实摄入完成，长历史仍有失败 |
| 补充佐证 | 支持／反对组、AND/OR、准确引用及局部提交已实现 | 机械例子覆盖共同和替代支持；H1 公开切片每个 Claim 仅一个支持组，未验证替代支持收益 |
| 临时要求 | `task_override`、任务切换清理、耐久快照排除已实现 | 有定向例子；H4 真实批次未触发该操作 |
| 真实状态变化 | `state_change`、有效期与已知时间读取已实现 | 有定向例子；真实事件操作未激活 |
| 解释纠错 | `reinterpret`、显式支持组迁移、新版本已实现 | 有定向例子；公开批次没有形成足够的真实纠错链 |

| 遗忘／退出 | 正文及依赖清理、独立删除记录、旧快照恢复检查、受管日志清理已实现 | 定向例子覆盖受管实例；不涵盖其他运行制品及已发送的远端请求 |

八类事件“有程序路径”的表述成立；“Host 已稳定掌握八类事件并在原生任务中验证完成”的表述不成立。遗忘的本地范围、历史时间读取和极小材料预算的边界仍需要继续明确，不应被一个“生命周期完整”的标签遮蔽。

### 3.3 摄入失败修复的实际边界

旧 STALE 运行中，一个历史块的提案失败后，后续 probe 会继续尝试同一未完成历史，产生额外请求，早先失败的 probe 却未得到答案。当前源码已改为：同一精确历史组先构建一次，失败传播给该组所有 probe，其他历史或臂继续。

这项修复解决了隐式重复调用和费用控制问题，现有 runner 定向用例也覆盖了“一次失败构建、三问收到失败、其他臂继续”。但它没有解决提案截断、重复来源引用和非法来源范围。当前代码与 STALE 冻结源码只在 runner 文件不同；该修复没有在 STALE 原批次上进行新的端到端重跑。

## 4. 六个候选的实验结论

所有“通过／正确”均指该批原生 rubric 与本地 vLLM Judge 的结果。这里的小样本分数用于描述已发生的现象，不作为稳定泛化估计。

| 候选 | 已观测结果 | 机制覆盖与归因限制 | 当前判断 |
| --- | --- | --- | --- |
| H1 支持保留修订 | 四题筛选：普通记忆 4/4，支持臂 2/4；生成 tokens 增约 15.3% | 没有形成替代支持或撤回比较；一次越界来源范围被拒绝，但该题最终通过，不能据此解释两道退化 | 实现存在，当前系统配置无收益，核心假设未被充分检验 |
| H2 更正关联读取 | 同摄入快照：全文 1/4，关联读取 2/4；作答 tokens 增约 57.7% | 实际增加出处与理解关联，没有真实解释修订／来源更正 | 保留接口，收益不能归因于“更正随旧材料交付” |
| H3 有界影响维护 | STALE 的 eager/pending 臂分别完成 2/3、1/3；无原生评分 | 没有 Claim→Claim 支持项、待复核队列或 maintenance 调用 | 关键机制未激活，结论未定 |
| H4 区分状态变化、例外与纠错 | scope 四题两臂均 2/4；候选生成 tokens 增约 43.5% | 三种新增事件操作均为零；实际主要是 claim 和 justification | 有实现，但未验证事件区分收益 |
| H5 当前上下文差量交付 | 筛选全文 1/4、差量 3/4；确认全文 3/4、差量 2/4 | 筛选与确认方向不一致；确认省 tokens，未保持任务质量 | 不设默认，保留实验入口 |
| H6 必要原文重整理 | 原文确实进入提案；长历史只完成 12/17 块，最终答案 0/3 | 三次输出截断；未完成工作量不能用于证明更便宜 | 材料路径已执行，端到端效果未确定 |

H1/H4 的写入 schema、提示和对象内容不同于普通臂，属于系统比较，不能单独归因到一种支持运算或事件。H2/H5 使用共享摄入快照，读取方式的比较更清楚，但仍包含后续 Host 调用与作答选择的变化。

### 4.1 H5 确认结果的准确解读

| 指标 | 普通记忆 | 支持记忆全文 | 支持记忆差量 |
| --- | ---: | ---: | ---: |
| 原生 valid-selection 通过 | 2/4 | 3/4 | 2/4 |
| 作答请求 | 17 | 24 | 24 |
| 作答 tokens | 213,640 | 363,767 | 324,618 |
| 加回各自历史和 Judge 的独立生成 tokens | 235,332 | 386,586 | 347,022 |

差量相对同一支持快照的全文读取减少约 **10.8% 作答 tokens**、约 **10.2% 独立生成 tokens**，正确数减少一题。它相对普通记忆的独立生成成本仍高约 **47.5%**，不能将“相对支持全文省钱”转述为“比当前默认更省钱”。实际共享历史费用只在批次总成本中计一次。

本次进一步阅读唯一退化题 `v11_000664` 的两份答案及原生评分。两臂都正确识别用户从集体徒步转为偏好独处。全文臂据此给出推荐；差量臂认为历史没有具体路线／地点推荐，因此拒绝提供推荐，Judge 判为未完成任务。两臂这道题的旧偏好污染均为零。

这说明退化表现在“知道偏好后如何完成当前任务”，并没有直接证明差量交付丢掉了最新偏好。现有证据不足以进一步确定差量呈现、模型生成波动或其他中间选择分别贡献多少。下一步应先诊断这种任务边界误解，不凭单题将失分归因于删除了必要记忆。

### 4.2 STALE 结果不能当成九题全错

STALE 本批仅使用预先选定的首个 T1 场景：50 个 session、594 条消息、完整原始历史。三个 probe 应从各臂相同摄入快照独立启动。

三臂九项请求中，三份答案完成，六项 Host 未完成。原生 Judge 联合评价同一场景三问，各臂均未凑齐三问，因此实际调用 Judge **零次**。三份完成答案也未获有效判定，不能将 summary 中零正确计数理解为 Judge 判了九题错误。

H6 发生 14 次旧原文交付、56 页材料，共 49,720 材料字节，证明接线确实被使用；没有证明这种材料供给改善了最终任务。其余三个固定 STALE 场景以及 T2 类型没有运行。

## 5. 真实执行规模与成本

统计范围仅为本轮六个 `v3-*` 批次，包含初始联调，不混入旧四题、formal-v1/v2 或其他历史研究。请求数包含失败尝试；生成 tokens 为 Host 与 Judge 的输入／输出合计。

| 批次 | 请求作答／完成／有效评分 | 生成请求 | 生成 tokens | embedding 请求 | embedding tokens |
| --- | --- | ---: | ---: | ---: | ---: |
| D1 联调 | 6 / 4 / 4 | 34 | 178,721 | 11 | 4,275 |
| H1 筛选 | 8 / 8 / 8 | 57 | 386,667 | 14 | 9,541 |
| H4 筛选 | 8 / 8 / 8 | 68 | 440,071 | 10 | 5,515 |
| H2/H5 筛选 | 12 / 12 / 12 | 78 | 634,290 | 10 | 8,836 |
| H3/H6 STALE | 9 / 3 / 0 | 66 | 1,320,945 | 82 | 339,553 |
| H5 确认 | 12 / 12 / 12 | 85 | 950,766 | 35 | 9,938 |
| **合计** | **55 / 47 / 44** | **388** | **3,911,460** | **162** | **377,658** |

388 次生成中包含 44 次 Judge，其余为 Host 的摄入、维护或作答请求。六批 summary 的 usage 缺失数均为零；共享 GPU 归属耗时与实际货币费用未确定。tokens 是计算消耗证据，不能直接换算为未经核实的价格或 GPU 成本。

55 项是不同臂／批次的作答请求数量，不是 55 道独立原题。去重后涉及 **13 道 MemSyco 原题与一个 STALE 场景的三问**。MemSyco 的 24 题固定清单实际使用了 9 道筛选题和 4 道确认题；其中个性化应用任务仅有一题联调，两个臂均未正常完成。确认组的另外八题未使用。

STALE 消耗本轮约 33.8% 生成 tokens 和 89.9% embedding tokens，却没有有效任务评分。这些开销提供了执行失败诊断，尚未形成 H3/H6 的效果比较。下一轮的性价比应优先改善完成率和机制激活，而不是增加候选数量或扩大题量。

跨批次模型配置、方法版本、索引和提示存在变化，不可把各批最佳答案拼成一个方法成绩。独立冷启动估计与实际共享缓存费用必须继续分开，候选排在缓存命中的后面不构成内生成本优势。

## 6. 当前主要问题与优先级

### P1：长历史提案完成率限制研究推进

已发生的失败包括 4,096 输出 tokens 截断、`source_refs` 重复导致整份提案结构校验失败、准确范围越界及版本冲突。STALE 中实际拒绝的局部组分别为 5、6、3 组；其中范围错误各三组，版本冲突为 2、3、0 组。

当前 48,000 字符历史分块、最多 16 项操作和支持关系输出，在该 Host／输出预算下没有稳定完成。重复调用修复能够减少额外费用，但不能替代协议完成率改善。

建议后续优先简化一次提案的表达负担：由程序提供准确来源范围／句柄，模型引用已经取得的范围；按实际输出容量组织摄入批次；保持原始历史与顺序不变。一次只改变一个协议因素，用固定场景检查是否能完整摄入并产生原生三问评分。不要叠加修复 Agent、自动无限重试或静默放宽真实版本／范围错误。

### P1：实现的机制没有转化为 Host 的实际操作

H1 只有单组支持，H3 没有跨理解依赖，H4 没有事件操作；H2 命中的是普通出处关系。这些不是纯粹的统计样本不足，而是当前样本、历史分块、候选可见材料和 Host 操作方式尚未形成目标机制的使用链。

后续小样本比较应先用既有 trace 回答：出现过需要该机制的合法信息吗，相关旧对象是否交付给 Host，Host 是否提出操作，程序是否执行，回答是否使用结果。只记录这几个必要计数即可，不新建大型 benchmark 平台。固定公开题缺少该事件时，明确标为未覆盖，不能改写题目或给 Host 透露 gold 来强行触发。

### P1：来源约束可能被 Host 误解成回答范围限制

H5 的具体退化答案已呈现这一现象：模型知道用户当前偏好，却把“历史没有现成推荐”作为不完成推荐的理由。H1 的结果记录也包含将推荐任务收窄为历史检索的问题。

建议区分记忆中已经确认的用户信息、可基于当前任务提供的一般建议，以及需要补充信息才能给出的具体结论。来源约束应防止编造用户经历，不应使正常生成建议必须在历史里找到逐字答案。是否由某种材料呈现加剧该问题，需要后续独立比较，当前不能作因果定论。

### P1：State/Attention 的完整闭环尚无本轮执行证据

当前 profile 定义和 `memory_tools()` 明确排除了六候选的 `memory_state`。因此，当前结果不能同时作为“支持修订有效”和“主动 State/Attention 有效”的证据。

建议先明确下一轮是否需要这条闭环。若需要，用一个有限 profile 接通现有工具、当前条件和已有检索，不新增 Agent；观察 State 是否改变真实查询与取材，再决定保留。不应仅因类和字段已经存在就将其列为已验证能力。

### P2：代码抽取后仍有集中状态与全量复制

`store.py` 主要承载支持关系，workspace、来源、历史、向量、TaskState 等仍集中于主类。`revision.py`、`retrieval.py`、`materials.py` 直接访问该类的多项内部字段；模块边界已经出现，状态所有权尚未充分收敛。

`apply_changeset()` 对每个局部组深拷贝多项状态，包括 workspace、sources、history、vectors 和 revisions。它提供简单的本地回滚实现，但计算／内存工作并不限于该组实际触及的对象。当前没有证据证明它已成为主要耗时，不能把推测写成测得的性能瓶颈。

后续可先把历史构建、作答执行和结果汇总从 runner 分开，令状态对象有明确所有者；只有在现有小样本计时显示复制成本值得处理时，再将提交改为受影响状态的差分。避免同时增加通用事务框架或对全库进行性能压测。

### P2：检索和材料边界还需准确表述

共享检索已实现真实 BM25，但 tokenizer 使用连续字母／数字／Unicode 词字符匹配。只读检查显示，`我喜欢简短回答` 被当成一个完整词项，与查询 `简短回答` 没有共同 BM25 词项。向量路径可能补足这类召回，本轮英语 benchmark 无法验证中文检索质量；当前不能宣称已完成中文词法检索适配。

材料组装支持关联预算，但极小预算下连引用占位元数据也可能放不下，现有实现保留引用而非保证任意字节上限。当前 pending 队列不提供历史队列重放。受管删除不涵盖外部已发请求、其他运行目录和作为评分制品保留的最终答案。以上是应保留的具体限制，不需要扩展为本轮生产系统工程。

### P2：复现身份较完整，交付版本尚未固化

本次验证六批 `sources.json` 的 166 个文件版本与对应 manifest 散列一致；48 份已有答案文件与冻结答案散列一致。48 份制品中包含一份未正常完成的 `no_progress` 答案，因此正常完成仍是 47 项，另外七项没有答案文件。

H5 确认批的 33 个被记录源码文件与当前工作树全部一致；STALE 批只有 runner 与当前不同，符合随后修复调度的记录。其他早期批次有相应增量差异，不能直接用当前源码冒充当时版本。

这些机制让本地批次可追溯，但当前重要实现和配置尚未形成 Git 提交。后续若需要交接一个可复用版本，应明确代码、数据、模型和配置身份；不把单个仓库 HEAD 当成未提交工作树的身份。本次未创建提交、回滚 tag 或推送，也未核对远端新提交。

## 7. 创新性与研究价值判断

**目前可确认的价值主要在工程基础和可检验的研究接口，尚不是已得到实验支持的新方法贡献。**

来源与整理分离、支持依赖、版本修订、混合检索、上下文去重、事务式提交均有既有项目和研究先例。当前已经参考本地源码，避免了仅凭概念名称堆叠设计；参考实现的存在也要求研究结论具体到操作差异，而非重新宣称这些概念本身新颖。

| 方向 | 当前可主张的价值 | 暂不能主张的结论 |
| --- | --- | --- |
| 支持保留修订 | 可表达共同／替代支持，局部操作与反向关系有实现 | 比普通更新或既有信念维护更有效 |
| 读取关联当前更正 | 各材料路径具有关联接口，准确原文与整理保持区别 | 已减少公开任务中的错误解释复活 |
| 有界增量维护 | 已知结构失效与进一步语义复核分开，有明确未决状态 | 已找到更优的质量—成本边界 |
| 情境与时间事件 | 任务覆盖、真实变化、解释纠错可区分执行 | Host 已可靠识别这些事件，且优于普通条件性文本 |
| 差量交付 | 能验证当前上下文中准确版本／范围，实际减少交付正文 | 在保持质量下稳定节省总成本 |
| 原文约束整理 | 原始依据进入同次提案，未展开范围明确 | 已改善长期概括漂移或长历史完成率 |

最值得保留的研究路线是：用同一合法材料与相同粒度，观察选择性修订是否保住其他有效支持，以及当前更正是否改变后续原文使用。实现和实验应围绕能被实际触发的单个问题收敛。H5 暂作为工程选项；H3/H6 先解决执行和覆盖，才具备比较方法收益的前提。

本次没有运行外部项目基线，也没有进行新的全面文献检索，不能据此宣布超过 MemTX、CUPMem、HiMem、ReMe 或其他记忆系统。

## 8. 后续工作的建议顺序

这些建议不改变已关闭 Goal，也不自动启动新实验。

1. **保留普通记忆默认与当前冻结结果。** 新的失败修复及提示变化使用新的方法／运行身份，不修改旧分数和已暴露清单。
2. **先解决一个长历史场景的完整执行。** 优先简化提案、来源范围引用和分块输出负担；只用固定完整场景，最多两个有明确差异的臂，不改原题或干扰历史。
3. **整理两个主要职责中心。** runner 分开历史构建、作答和汇总；核心明确状态所有权。结构调整与方法变化分开，复用已有窄回归。
4. **选择一个真正可触发的候选继续研究。** 在未修改的原生题中确认事件和可见材料，再比较 4–8 题；优先 H1 或 H2，不同时叠加全部候选。State/Attention 如需参与，应明确列为本次差异。
5. **同时检查任务完成和总成本。** 不能以省 tokens 掩盖拒答／未完成，也不能把正确陈述偏好等同于完成用户请求。只保留有解释力的少量指标。

继续遵循开发优先的约束：不运行全量 benchmark、全仓 pytest、多模型矩阵；不新增常驻审查者或审批阶段；必要的来源、版本和真实失败检查保留。已有样本不能回答的问题，允许明确得出“未覆盖”或“无法判断”。
