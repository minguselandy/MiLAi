## 1. 执行摘要：停止扩大架构，集中打通五个转换

当前系统已经拥有来源捕获、统一MemoryService、语义/情景记忆、局部算子、条件/例外、引用式保留、多键检索、工作集、业务对象、恢复及评分入口。问题不是这些名称缺失，而是相邻环节对“材料、状态、完成”的含义仍不一致。[G2]

本轮首先修复以下转换：

| 转换 | 当前实际问题 | 本轮结果 |
|---|---|---|
| 保存状态 → 模型材料 | Host与benchmark分别装包；Host修复没有覆盖benchmark | 共用一套语义投影，访问能力仍由入口决定 |
| 候选选择 → 可执行读取 | 选中后才发现最终请求超限 | 使用真实投影成本规划，超限有明确的未交付材料及继续路径 |
| 当前请求 → 允许的独立工作 | 纯保存被误解释为业务动作，业务解析错误阻断保存 | 分开业务、保存、读取、遗忘及当前限制，复用已有执行边界 |
| 当前证据 → 正确修订 | 候选强化、空提案、旧肯定来源支持新撤销、复合条款损伤 | 减少重复生成，保留语义强度，变化与实际证据对应 |
| 实际结果 → 恢复与反馈 | 本轮早先提交、当前可见状态、原任务剩余项混淆 | 根据原回执核对已完成与剩余工作，当前权限优先 |

**首批工程优先级：共同Reader投影与容量规划 → 纯保存/恢复完整链 → 源于证据的局部编辑。** 检索继续复用 `record` / `record_units`，不再从零实现；多轮导航、生成参数及额外排序属于后续小对照，不成为集成前置条件。

### 1.1 本轮不改变的总方向

保持 **Grounded Memory、Verified Object References、Semantic/Episodic Memory、Grounded Revision、Lifecycle Recovery**，一个逻辑MemoryService。记忆允许保存解释、计划、偏好和经历，但记忆文字不能创造业务身份、实际效果或授权。[H1]

原v13.4的Simplify只结束当时未建立重复必要性证据的复杂关系消歧选源分支；本轮不恢复该分支，也不将其解释为否定普通检索、工作集或局部修订。[H2]

## 3. 全局诊断：不是单一“上下文太大”，而是表示、控制、证据与生命周期错配

### 3.1 结构完整不等于语义完整

模型正常stop、JSON合法、来源ID真实、数据库提交成功分别证明不同事情。任何一项都不能证明新事实被忠实表达、旧条件被正确保持或用户任务已经完成。

已知的“小输入但输出重复空白到length”“旧姓名已保存但Reader补出未知组成”“旧肯定来源被选为撤销依据”，说明容量之外还有独立的生成与推断问题。[G2][G3]

**修复原则：把程序确定的身份、版本、原值和实际效果交还程序；模型只承担必要的语义选择。** 不把语义判断伪装成可由字段校验解决的问题。

### 3.2 同一服务没有保证同一模型呈现

Host经 `_record_units()` / 分页 / 驻留视图；benchmark经 `answer()` / `_answer_view()` / `reader_messages()`。benchmark保留渲染正文和结构化单元等多种表达；Host已移除部分重复整版视图。相同Store并未避免两处投影分叉。[G4][G5]

**已确认：** f8的Host修复没有进入36→409的benchmark路径。

**推断：** 模块边界虽然分清，但共同语义呈现仍由runner与Host适配器分别拥有，是同类问题反复出现的重要工程因素。不能据此断言全部语义错误来自重复文本。

### 3.3 容量是末端拒绝，不是完整计划

当前选择器可以选择多个完整事项，最终请求才检查token总量。目录字符数也不等于真实投影成本。模型选择“相关的8条”与系统能够“同时展示这8条”是两个问题。

三种预算必须分开：单次读取页面额度、驻留材料额度、完整模型请求额度。两页分别低于8192，不意味着它们与请求、工具说明和来源合并后仍可容纳。

**不采用“多加200 tokens就修好”的结论。** 190只是这次失败的差额，不是所需系统余量的估计。

### 3.4 检索、目录选择、正文交付各自会丢信息

最新报告已更正：某些目标rank15/16或20处于K10外，不能再叫“Selector没打开”；另一些身份事项rank3/4确实进入池，却未被打开。whole命中摘录也只是获胜键前240字符，不是已定位的答案句。[G2][G6]

**固定池多读不能发现池外内容。** 在同一个失败上继续添加导航，不一定修到最早断点。

### 3.5 原始经历与语义解释的补救能力尚不能混称

`EpisodeIndex`已能按可见来源读取原件，派生描述只是定位线索；`_index_episode_descriptions()`这条路径的描述来自实际提交单元。[G8][G9]

因此，不能默认“Editor没写也无所谓，Episode总能把漏掉事实检索回来”。原文捕获、Episode注册、原文检索和派生描述检索需要分别可用。本次未穷尽所有来源捕获入口，不将此风险误报为原文已经丢失。

**后续要求：** 正常Host在获准时可经已有原文入口找到已捕获经历；语义形成失败不能被记为原文未捕获。benchmark的 `include_raw=False` 不因这项功能而静默改变。

### 3.6 请求解释被当成了强控制信号，但其语义仍未校准

最新CURRENT路径对结构有效的操作列表计算 `allow_business_mutation=bool(operations)`，同时标记 `semantic_correctness=unchecked`。[G7]

**已确认代码事实：** 该布尔值来自解析后的具体计划。

**重要限制：** 它不是独立的自然语言授权证明。真实对象ID正确，也不能证明用户请求了这个动作。最新业务故事没有额外真实效果，不代表以后不可能误请求。

后续要让可信应用能力、当前限制和模型解释保持不同来源；不得让通用schema校验或“非空计划”替代宿主原有授权。对实际不可逆业务继续使用宿主已有的确认/权限机制，不新增一个模型审核层。

### 3.7 模态、主体、时间与修订范围在中间转换中失真

- “考虑”在Extractor先变为“计划”：先修抽取与候选表达，不只修Editor。
- “用户报告姓名”被Reader拆成未报告的组成属性：主体字符串存在不等于组成关系有依据。
- 原始来源肯定旧规则，却被提议撤销：旧支持不能自动支持新否定。
- 修改复合clause中的一个值，其他含义丢失：编辑范围小不等于语义变化小。
- 报告日期、保存日期与生效日期不同；查询not_found不等于业务操作失败。

这些断点由公开报告分别确认；不能统一归因条件关系或thinking。[G2][G3]

### 3.8 局部失败被放大成整条历史中断

一次只读问答的HTTP前超限会终止后续自然历史。旧结果应保持该实际终态；但产品功能与下一版实验协议可以设计更合理的局部失败隔离。

必须区分：已知未发送的只读请求、已确认length、响应未知、写入结果未知、业务效果未知、Store故障。它们不应该共用“全部重试”或“全部永久终止”的策略。

### 3.9 配置和验证积累正在超过实际用户收益

PR #119当次为86提交、53变更文件，混合工程能力、生成形式、实验结果与兼容处理。数量本身不是质量问题，但多种候选同时演化，已使“哪个入口使用了哪项修复”成为实际风险。[G2]

后续不再新增一串默认模式来逃避选择。对当前可用路径做一次收敛：一个功能候选配置，保留原实验配置可重放；归档配置不会被重新解释为新默认。历史记录继续保留，日常交接只展示当前能力、剩余缺口和下一工作。

|---|---|---|---|

| **SeCom，ICLR 2025**；作者公开项目 | 用主题连贯片段组织对话，压缩去噪用于检索 | 对新事件/事项保持主题连贯性；索引去噪与回答证据分开 | 不能直接删除限定或用压缩原文覆盖Source；不照搬反思训练流程 [R3] |

| **ReAct，作者公开论文/项目** | 交替进行工具操作与基于观察的下一步决策 | 保留有限按需读取，简单任务直接完成 | 不强制每题多轮，不执行私有推理草稿，不以导航调用数为进展 [R5] |
| **Trustcall，公开工程项目；JSON Patch为RFC 6902标准** | 生成局部补丁而非反复重建大对象；项目另含校验修复机制 | 只借鉴补丁与引用式保留；程序复用未改内容 | 不引入自动重试/审核循环；JSON Patch只定义操作语义，不证明命题真实 [R6] |
| **RARR，ACL 2023 Long Papers** | 依据检索证据修订无支持内容，并尽量保持原输出 | 将变化落实、未改内容保持、支持一致分别评价 | 不复制回答后自动纠错流程来改写分数，也不视其为连续记忆完整解法 [R7] |
| **LangGraph/LangMem，官方文档与公开SDK** | 分开线程checkpoint、长期Store及记忆形成/管理；显式组织工具与任务 | 保留一个Store与既有checkpoint；共同函数由不同入口调用 | 不等于MiLAi已获得跨系统exactly-once，不为采用API重写框架 [R8] |
| **Lost in the Middle，TACL 2024** | 观察相关材料位置改变引起的长上下文利用下降 | 减少无关和重复包装，独立检查材料送达后解释错误 | 不能据此证明MiLAi所有错误由上下文长度引起 [R9] |
| **Anthropic Context Engineering，官方工程资料** | 轻量引用、按需材料、上下文整理和任务相关工具 | 少量固定任务说明 + 当前证据 + 剩余工作；调用前重新构造视图 | 不把工程经验当MiLAi效果证据；不自动用摘要替代事实 [R10] |

### 4.1 本轮的综合方法，而非“拼装所有论文”

采用四种不同粒度，各自有明确目的：

| 粒度 | 目的 | 设计 |
|---|---|---|
| 持久事项 | 保存可维护语义 | 主体/主题连贯，原来源与版本可回溯 |
| 检索键 | 找到相关材料 | 整体键 + 现有自足单元键；可重建，无事实权威 |
| 编辑单元 | 限制修改范围 | 实际独立变化的内容；未改部分按引用延续 |
| 阅读语义包 | 保证当前理解完整 | 当前目标 + 已有必要条件/例外/来源，而非任意切片 |

这四种粒度不必相同。共同引用将它们联系起来，而不是把它们变成四套数据库。

### 4.2 暂不引入的外部能力

本轮不新增图数据库、RL训练、压缩模型、长期审核Agent、通用NLI核对服务或第二生成模型家族。LLMLingua类有损压缩可以后续独立研究，但当前先消除结构重复和不必要任务，保留Sources、模态与限定。已存在的激活和用途估计保持可选，不用于宣称事实真实或获得业务权限。

## 5. 总体修复设计：一个事实底座、一个共同视图、现有分项任务

### 5.1 五条主线的完整功能合同

| 主线 | 必须可用的正常功能 | 本轮重点 |
|---|---|---|
| Grounded Memory | 保存真实Source；形成有来源语义；结果与失败可读取 | role/origin/主体/模态不在跨阶段转换中被错误加强 |
| Verified Object References | 真实lookup/receipt建立对象；执行仍受当前权限约束 | 显式分开操作开始、查询缺失、部分成功、当前对象状态 |
| Semantic/Episodic Memory | 经历可追加、语义可修订；在获准路径回到原文 | 原文与派生摘要分离，形成失败不被误报为没有捕获 |
| Grounded Revision | 更正、局部例外、共享条件、合法撤销、历史读取 | 少重写旧内容；支持“保留”与支持“改变”分工明确 |
| Lifecycle Recovery | 重开后核对实际效果，只完成当前允许的剩余工作 | 只读/写入/业务未知分开；按trace回执而非末个数组判断 |

### 5.2 拟议调用关系

```text
当前请求 + 可信应用权限
        │
        ├── 原任务引用/剩余事项（控制，不是世界事实）
        └── 当前Source/实际Tool观察（证据，不是执行授权）
                         │
                现有提取/定位/编辑
                         │
                 同一MemoryService
                         │
           普通检索 → 引用工作集 → 共同材料投影
                         │
                 完整请求容量规划
                         │
            Host / benchmark各自允许的工具与读取
                         │
                回答或实际工具执行
                         │
             回执刷新与原请求剩余工作
```

此图是本轮拟议衔接关系，不是宣称新增模块已经实现。对象引用、读取资格、权限和事务继续在原负责边界执行。

### 5.3 少量函数，不建设新框架

优先整理到现有 `memory/` 与 `methods/`。以下名称是职责示意，不是已可直接调用的API：

```python
project_record(record, *, purpose, evidence_mode)
render_memory_material(records, sources, *, purpose)
assemble_model_input(task, material, *, stage)
plan_delivery(selected_refs, *, remaining_budget, access)
```

共同投影接收已经取得的实际材料，默认不查询Store、不读取gold、不调用模型、不修改记忆。材料获取由现有Reader完成；provider继续负责模板、实际token计算与调用，不引入具体方法语义。

**不把标准化投影变成第二份持久语义状态。** 现有记录和来源仍是存储内容，投影是本步可重建的视图。

## 6. 工作包A：统一记忆投影和完整请求容量（首要）

### 6.1 先解决重复表达，而不是删内容

1. 将benchmark `reader_messages()`与Host `_record_units()`中的共同语义投影提取为一个实现。
2. 一个实际单元的正文在一份Reader材料中只出现一次；其角色、主体、必要时间、直接关系及支持仍就近可读。
3. 对同一来源可使用短引用和一张来源表，但避免多层嵌套 `$ref`、空值继承和版本默认规则都交给模型反复还原。
4. 只有确认渲染正文没有额外语义时，才以单元表示替代它；不能证明的记录继续保留原表达并单列差异。
5. 不为省token把未知时间变成无限有效，不把未声明条件变成已满足，也不合并当前断言与已撤销历史。

**这是语义保持的投影收敛，不是对原Source做文本压缩。** 离线对一个已失败包比较字段与片段即可，不建立全库哈希验证系统。

### 6.2 共用投影，不伪造相同访问能力

- Host可以按原权限使用 `read_source`、历史版本、分页工具；当前显示引用不能算正文已读。
- 固定池benchmark若原本已交付 `revision_evidence` 正文，首轮等信息修复必须继续交付它。
- benchmark没有相应工具时，不得删掉原文并放一个无法调用的“读取入口”。
- 新的按需原文benchmark属于单独协议，所有方法拥有相同访问能力并记录费用。
- 普通事实的正文、来源角色、时间/范围以及必要关系是研究信息条件；UUID包装和重复副本不是额外事实。

### 6.3 三层预算，统一按实际模板计算

完整请求约束为：

```text
T(本步消息 + 工具/输出说明；实际模板与thinking设置)
+ output_reserve + margin <= context_window
```

当前冻结M使用的输入上限是 `65536 - 32768 - 512 = 32256`。新规划不热改该历史配置，也不把Host的8192页面额度当成benchmark输入上限。[G3]

各事项单独成本只用于选择提示；最终多个事项的联合成本以完整投影为准，不能简单累加包含重复表的估算值。短引用、去重和模板会影响联合成本。

### 6.4 已选材料仍放不下时，给出正常继续路径

首个修复版本先在原八事项失败输入上验证等信息去重，保留原池、选中事项、来源、预算和模型模式。

若去重后仍放不下，使用一个明确的新功能配置：

- 读取计划保留全部已选引用，按现有语义完整事项安排页面或批次；不静默丢掉后来事项。
- 当前问题及用途始终驻留；当前处理事项和必要条件共同展开。
- 已读正文可换出，后续需要时可重装；`read_progress`不是“禁止重读”表。
- 跨页比较使用实际可重读证据；工作笔记只作定位提示，不能替代原始依据。
- 需要同时比较的内容仍不能容纳时，回答明确限定已取得证据和未完成部分，保留剩余读取，而非猜测或谎称完整。

不强制所有请求走多轮。不增加新的Planner模型；确有容量或证据缺口时，现有Agent才继续读取。超限发生在HTTP前，重新规划还未发送的读取不是重复执行业务，也不是对未知调用的盲重试。

### 6.5 完成标志

同一实际记录在两个入口经相同投影呈现；当前失败包进入真实模板时有可执行结果或明确续读计划；必要主体、条件、原文访问边界没有因去重改变；旧运行失败保持原样。

## 7. 工作包B：当前请求、独立任务与恢复

### 7.1 复用已有修复，不重新发明分类模式

保留现有四字段scope和CURRENT工具，先使用 `fef4603` 的明确空业务计划表达。选择一套完整候选配置，旧v8/v9等格式继续按原快照重放；不因新问题立即增加v10/v11。

当前请求可能同时包含：不再办理业务、读取结果、保存结果、另行更正偏好、撤销某来源。它们是不同作用范围，不能压成一个全局“读/写”标签。

### 7.2 解释与授权分离

- 模型提出当前请求的语义解释；旧任务卡只帮助解析指代。
- 可信宿主提供实际可读范围和可执行能力；模型输出不能自行扩大它们。
- 空业务计划是正常情况，不得强制生成目标对象。
- 非空业务计划和真实对象ref仍不等于“用户已经明确要求此动作”。保持宿主已有操作授权/确认。
- 业务分支解析失败时，只有记忆许可和来源确已独立明确，才继续不依赖该业务分支的保存；否则保持未完成，不猜权限。

### 7.3 控制与事实按功能分区，不按消息整块删除

当前输入中“不要重复预订”是执行限制；“提醒改为周五”是新更正。同一条消息允许两者共存。控制区不当作业务完成证据，新事实仍须保留其实际Source范围。

不把用户全文直接提升成可信系统权限。单System模板可以保留稳定指令并标识当前请求文本的用户来源；其业务权限依然由原程序边界决定。不要依赖换一个消息角色就宣称语义或注入问题已被解决。

### 7.4 请求完成由分项结果组成

优先复用已有business、semantic_memory、feedback状态，而不是再新增总状态机：

| 事项 | 正常完成条件 | 常见误判 |
|---|---|---|
| 业务 | 实际查询/工具回执证明该获准事项的效果 | 调用开始、请求已接受被当成成功 |
| 原始经历捕获 | 实际Source回执可读取 | 等同于语义记忆已更新 |
| 语义保存 | 有对应提交/确认；语义质量另评价 | 一个无关提交被当成整项保存完成 |
| 反馈 | 用户收到与实际业务及保存状态一致的说明 | completed函数返回值代替用户任务结果 |
| 遗忘 | 对指定可见范围撤回，派生缓存/读取遵守该变化 | 当前不可见被说成从未保存 |

只读新请求不得继承旧写授权。只补保存不得重复业务。某消息最终 `maintenance=[]` 也不能抹去本轮trace中早先已发生的提交。

### 7.5 恢复按实际风险处理

| 中断位置 | 处理 |
|---|---|
| 模型/工具请求尚未发送 | 从已有输入继续，必要时重做投递计划 |
| 最终Reader已确认length | 保留缺答；依既有已声明策略继续后续只读任务或显式新尝试 |
| 模型响应未知 | 原unknown保留；不冒充无调用或免费失败，不自动猜提案 |
| 记忆提交结果未知 | 按原operation ID查回执，确认之前不发同效果的新提交 |
| 业务效果未知 | 用现有discover/observe核对真实对象，只做当前获准剩余动作 |
| 只剩最终反馈 | 重建实际结果说明，不重做业务和记忆 |
| Store故障/数据损坏 | 保留最早异常并停止相关写入，不自动清理数据 |

功能模式与科研首尝试协议可以不同，但必须显式声明，不修改旧冻结实验的失败身份。

### 7.6 完成标志

使用已有业务六消息链：部分业务 → 补足业务 → 只补保存 → 只读 → 遗忘 → 重开。实际效果无重复，保存与未保存如实区分；遗忘不触发无意义的新事实保存；重开不恢复已撤回来源。

## 8. 工作包C：来源保持的变化提取和局部修订

### 8.1 先修中间表示的语义强度

候选提取的目标是“当前来源中的候选陈述与变化线索”，不是提前生成最终真值。利用已有字段和原始片段表达主体、计划/可能/完成状态及时间，不强制新增一串置信度字段。

“考虑课程”保留考虑；“希望减少工作时间”保留愿望；“助手建议收入数值”不变成用户自报。必要时候选更接近原句，宁可少概括，不靠更多强约束提示迫使模型变得确定。

Editor仍看到实际Source，候选只提示。来源ID相同不保证候选内容忠实；不能把抽取输出用作独立证据增加权重。

### 8.2 复用引用式keep，彻底减少旧文重抄

- 本轮保留单元由实际引用延续正文、支持和归属。
- 新值、改变的断言和撤销选择真实支持该变化的来源。
- 普通全量重写仍明确选择其完整保留集合；遗漏单元不被程序偷偷补回。
- 普通局部编辑/条件化局部编辑的未触及部分继续保留，保持与全量重写的区别。
- 显式空支持、错目标和不受支持的改文不自动纠正成合法。

新格式可要求 `creates` / `records` 两个可空容器，但不得强制非空。空提案、格式失败、确认截断和提交拒绝分别记录。不要用“非空变多”替代变化落实率。

### 8.3 编辑单位围绕独立变化组织，不全库重整

对新形成/当前已受影响事项，尽量分开可以独立变化的值与限定。例：岗位、收入值、季节波动、储蓄用途是不同含义；修改收入值不必重新生成全部内容。

但不能机械按逗号或每句拆分。若条件依赖上下文，保留完整自足条款；首版没有可靠关系时打开完整事项。已经正确的旧记录不为“统一格式”全部重写。

### 8.4 条件与例外操作以实际范围为依据

| 变化 | 正确实现要求 |
|---|---|
| 同范围更正 | 改目标内容，保留未撤销条件及其支持 |
| 增加例外 | 建立实际局部覆盖关系，不删除一般规则 |
| 修改共同条件 | 改实际共享条件，不误移到不相关对象 |
| 撤销例外 | 解除该覆盖；仅在一般规则仍有效时恢复其适用 |
| 撤销一般规则 | 不自动证明反面规则为真 |
| 历史纠错 | 保留报告与更正来源，区分当时保存和当前解释 |

关系两端有支持，不等于关系有支持。旧来源肯定规则，不能拿来证明本轮撤销。当前的保护性拒绝可能避免损伤，但不算Editor成功完成任务。

### 8.5 业务观察不应反复被模型重新判定

复用既有 `ObservationProfile` / 字面候选 / VerifiedObjectRef，提供真实操作名称、查询/执行类别、观察时间、对象及分项字段。`not_found`表示该次查询未发现对象，不自动表示某次预订失败；旧查询也不覆盖后来真实成功。

通用观察字段由适配器合同提供，不在记忆核心写死预订/文档关键词。公开来源没有某字段时不从隐藏world补齐。记录实际字段不等于承诺业务实时不变，需要当前状态时仍查询。

已捕获观察可以在语义整理失败后被如实读取；必须告诉用户“实际结果可查，语义整理尚未完成”，而不是把原文捕获伪装成全部保存成功。

### 8.6 完成标志

现有规则/例外链能完成真实更正和撤销，未改含义保持；补保存能使用实际新结果，正文不把控制指令或运行元数据编成事实；抽取、编辑和Reader的首个语义错误能从现有轨迹中分别定位。

## 9. 工作包D：读取目的、候选召回与语义完整交付

### 9.1 保留现有record_units，不再重做检索算法

现有键为事项整体及带直接关系的单元文本，按记录最大余弦去重。[G6] 本轮先检查其使用效果，不用有限病例命中就切默认。

需要分开四种情况：未形成；形成但池外；池内未选；已完整交付但答错。只有相应层发生断点才改相应模块。

### 9.2 内部召回量与模型正文量分离

允许后续候选配置分别控制候选池大小和正文预算。内部较宽的候选不等于把全部正文送入prompt。先保留K10对照，再单列一个更宽池；新增候选数、线索成本和读取调用都计量。

最大余弦存在键数量效应：给某记录新增键不会降低该记录自身的max分数，但跨记录排名可能变化。这只是数学性质和设计风险，不是已确认失败原因。先观察实际键/长度与排名分布，不先加惩罚参数或学习排序器。

已有BM25/交错比较可作为普通对照；若同K、同信息下没有额外价值，就不采用。无必要时不引入BGE稀疏服务、ColBERT、多reranker和查询改写模型。

### 9.3 导航线索应诚实，而不是补答案

实际获胜whole键的前240字符只是目录线索。候选描述过泛时可以改善现有事项描述的可读性，或提供真实命中单元；不根据gold或当前问题中的姓名自动创造别名/主体。

主体、条件、例外存在明确关联时，随相关事项一同打开；缺少关系时不猜“必然无关”。简单全池/普通排序装包仍应作为强对照，避免Selector成为每题新增的失败点。

### 9.4 按用途读取，而非由打开内容定义用途

复用已实现 `read_goal`，保持当前适用、原始表述、实际保存历史的区别。问题与日期不需要再由新模型重复分类。

当前版未包含内容不能证明过去没保存；本次K10没有命中不能证明全库不存在；已遗忘记录不允许从旧缓存重新展示。可提供的存在性/历史元数据也要遵守当前可见性，不能以审计为名恢复已撤回内容。

### 9.5 认知启发的边界

保留已有情景快速记录、语义整理、有限工作记忆和可选激活函数。这是组织分工，不声称模拟了人脑全部机制。内部回放不是新证据；检索有用性不是事实概率；激活不覆盖来源、权限或时间适用性。

概率或学习选择器后置。只有需要且有校准数据时才研究，当前不以模型自报confidence决定事实保存或业务执行。

## 10. 工作包E：运行闭环、可用入口与报告收敛

### 10.1 统一配置，不继续叠模式

建立一个可用候选配置，明确入口、memory arm、record/record_units、staged/可选继续读取、各阶段thinking、实际窗口/输出/余量和失败策略。旧配置原样留作历史，不修改缓存或旧请求含义。

模型模板与实际调用必须由同一组设置生成；只用真实已部署模板做一次相关接线检查，不用宽松mock模板宣称服务一定支持。未知部署问题如实列出，不能通过猜测推荐参数修复。

### 10.2 以正常任务为功能单位

正常使用提供一条明确入口完成：保存/查询、更正/历史、原文回看、例外撤销、业务结果保存、显式续办与遗忘重开。benchmark调用共同方法而不是复制另一套业务逻辑。

不为用户暴露大量实验版本枚举；当前默认说明只展示所选候选。普通Host状态里保存引用、当前目的与剩余任务，不向模型倾倒所有旧审计日志。

程序追加的真实回执可用于产品反馈，但原始模型答案、程序追加材料和最终公开交付分别保存。不得先用程序补正答案，再把修正后的表现当作模型记忆QA的提升。

### 10.3 把已完成响应保存到相应粒度

复用已有每请求response与每题结果，避免会话末尾失败使前两题只能留在散落HTTP目录。汇总器同时报告完整会话数与已完成题数；两者不等价。

对旧36的46+2结果保持原身份，可在离线分析中读取最后2题，但不补成第22份完整预测。新协议可让已知只读失败按题记录后继续，在启动前一次声明；默认旧fail-fast不追溯变更。

### 10.4 测试做减法，不删除必要边界

开发期间只运行直接受影响的既有导入/类型/格式检查及正常SQLite流程。修复跨入口投影时，至少让Host和benchmark各走一次同一投影；这是防止修错路径，不是扩展验收平台。

不新增SHA/替代哈希/逐文件身份证明，不建reviewer循环，不为每个提示重跑五臂。已有权限、对象、事务、遗忘和未知副作用处理保持在其负责边界，不在每层重复判断。

### 10.5 文档不再替代开发

现有状态页顶部只保留：当前代码/实际运行、已经闭合的结果、下一项工程工作。旧时点移至清楚的历史区或链接，不删除失败。任务交接最多记录实际能力、文件、一个运行示例及剩余断点。

## 11. 多Agent开发与合流安排

采用 **1名集成者 + 3名开发者**，并行写代码，不在运行时给每次记忆维护增加三位Agent。

| 角色 | 负责范围 | 文件归属与交付 |
|---|---|---|
| 集成者 | 公共合同、完整请求配置、runner接线、合流与实际资源调度 | 共享runner/配置唯一主写者；一个功能候选 |
| Agent A：读取与容量 | 工作包A及D的共同投影、装包和读取路径 | `memory/`共同投影、现有working_set；提出Host/benchmark薄适配补丁 |
| Agent B：来源与编辑 | 工作包C、已有Episode/Observation衔接 | `methods/edit_memory.py`、`edit_features.py`、局部单元相关模块 |
| Agent C：请求与恢复 | 工作包B及E的完整结果、续办和遗忘 | `application/`、共同维护与反馈；与集成者约定runner接线 |

每人独立worktree与临时数据库。共享文件先交接接口再合流，不同时重写主入口。引用只绑定实际记录与来源，开发者不能给fixture直接填正确结果。

真实Qwen/BGE/Judge由一位负责人串行调度，先核对真实运行和终态；代码并行不代表可占用多个共享推理任务。本次文档没有启动这些角色或任务。

### 11.1 实施顺序（不设逐项科研准入）

| 波次 | 工作 | 结束时得到什么 |
|---|---|---|
| 合流准备 | 核对当前PR和已有能力；锁定文件所有权及小接口 | 不重复建设，旧实验不热改 |
| 并行实现 | A共同投影/容量；B变化/keep；C纯保存/恢复 | 各自正常使用例与必要补丁 |

| 统一评价 | 完整候选运行既定开发数据，再按首个断点优化 | 决定采用哪一组简单机制 |

某条普通语义案例失败，记录并继续其他功能；越权、重复不可逆效果、Store损坏和确定接线崩溃先修。工程功能完整不需要先显著优于baseline，算法优势也不能由冒烟代替。

## 12. 实验规划：先有一个完整候选，再做少量可解释比较

### 12.1 开发期只使用已有材料

- **容量接线：** 复用原8事项、32,446-token输入；检查新投影实际模板和语义字段，0模型即可先发现接线问题。
- **Host冒烟：** 复用已经准备的三链20消息，不增加新的20个审批步骤；这仍是已曝光开发材料。
- **旧结果评分：** 可离线评价36已保存前缀，不重跑Writer/Reader；只报告相应首用户部分，不当完整效果。

不把离线fit、页面可容纳或mock流程当真实模型成功。

### 12.2 第一轮集中评价：判断完整候选是否可用

选定一个候选后，运行四开发用户既有前缀，从各自实际空库形成。机会数从该批真实数据读取，不照抄另一批分母。收集预测、实际状态和Reader结果后再统一评分。

主要目标是找剩余首个断点，先不声称任何条件机制优势。若通过正常功能流程而仍有语义错误，按归因选择一个改动，不重新设计总架构。

### 12.3 最小机制对照，最多逐次回答一个问题

| 研究问题 | 固定条件 | 唯一变化 |
|---|---|---|
| 共同去重是否有效 | 相同实际前态、选中事项、原文、预算、Reader及采样 | 原投影 / 共同语义投影 |
| 检索粒度是否补回必要事项 | 相同真实记录、问题、K与读取实现 | record / 已实现record_units |
| 额外导航是否值得 | 相同池、正文预算、工具权限、最终Reader | 普通装包 / staged；确有剩余问题才加state_driven |
| 条件算子是否保护语义 | 相同实际前态、来源、表示和生成配置 | 普通局部修改 / 条件化操作 |
| 简单任务模式选择 | 相同真实输入和schema | thinking单一设置；不同时改温度/presence/预算 |

不能将这些开关交叉成全因子大矩阵。已有相同请求却不同输出的观察说明随机性需要保留；必要的匹配重复在运行前固定次数，保留全部结果，不投票选最好答案。

### 12.4 方法主表继续使用强简单对照

| 方法 | 含义 |
|---|---|
| B0 | 普通文本全量重写；决定完整保留集合，引用保留只减少抄写 |
| B1 | 普通文本局部编辑 |
| B2 | 条件表示 + 全量重写 |
| M | 条件表示 + 局部/例外操作 |
| Append-only | 有来源和时间的新事实追加，以共同Reader解释当前/历史 |

所有方法共用合理可用的来源、底座、检索配置和访问能力。形成阶段不接收未来问题或gold。各方法自然运行会形成不同状态，这是整体系统比较的真实组成；固定前态小对照另外解释机制。

不能因没有UPDATE就判Append-only失败。内部节点数、保留字数和提交次数只能解释行为，最终比较新要求、适用性、历史与任务效果。

旧505的B1/B2负结果继续保留；形成召回较高、个别用户受益或条件关系节点为零，都不能单独证明关系机制有效/有害。不同源码、不同用户前缀、不同失败策略不组成排名。

### 12.5 长历史与最终确认保持原范围，后置执行

同版本五方法各自空库运行四用户65/77/62/73，合计每法277、五法1385会话；首65是同轨迹子集，不重复起跑。每法原完整开发范围595更新/705QA来自既定协议，最终以实际manifest核对。[G2][G11]

之后保留原计划：native32机会/12会话/4用户、drift/recovery、必要M消融、固定更紧预算、最终冻结后的16保留用户、LongMemEval及RawRAG/RollingSummary/A-MEM实际适配、同候选Host135case/192message和冻结后新故事。A-MEM callback适配不冒称未经修改的作者系统复现。[G11]

这些是最终交付范围，不是每个补丁的前置清单。旧未选用户曾整行解析的事实不改写；保留用户不能用于语义调参，不声称其数据从未被任何程序解析。

### 12.6 最小评价指标

| 维度 | 记录方式 |
|---|---|
| 来源与机会覆盖 | 当前事件是否实际交付；更新/QA全部机会数 |
| 检索与读取 | 必要事项已存在否、进池否、被选否、正文/原文实际到达否 |
| 变化落实 | 应新增/更正/撤销的语义是否完成；合法no-op单列 |
| 非目标保持 | 仍有效内容是否损坏；原本就不存在的内容不计保持成功 |
| 忠实性 | 主体、说话者、可能性、计划/完成、时间/范围与关系支持 |
| 功能完成 | 业务、原文捕获、语义保存、反馈、遗忘按实际请求分项 |
| 成本与可用性 | 各阶段调用、实际token、峰值完整输入、截断/超限/unknown、明确未运行 |

Correct/全部机会表示获得Correct标签的比例，不等于把invalid标签判成错误；同时报告有效判断分母和缺答。提前中断前缀有选择偏差，不能估计整批结果。

同家族Judge与开发Agent复核不是独立确认。既有开发预算不强制新增第二生成家族；最终论文按能完成的独立人工核查和实际证据说明限制。

### 12.7 局部失败策略必须在新运行前一次声明

新benchmark可将已知只读容量失败或已确认最终length记录为该题缺答后继续自然历史，前提是维护状态不被QA改变、费用/缺答/分母齐全。unknown业务/写入和Store损坏不能套用该规则。

这是一项可用性和完整观测设计，不是把旧失败变成功。旧36继续FAILED；旧21+2不拼成新版本完整历史；失败样本不能从主分母删除。默认兼容路径保留，研究新配置显式命名。

## 13. 思辨与创新：把贡献落在转换机制上

### 13.1 待检验的主问题

> 在保留真实事件历史的前提下，来源关联的局部修订与语义完整读取，能否比强追加式记忆和普通编辑更可靠地落实变化，并减少范围、时间及非目标含义损伤？

共用投影和修复入口是工程必要性，不单独包装成新算法。多键检索、JSON补丁、事件存储和ReAct已有先例；引用这些工作是缩小可检验贡献，不是因某论文存在就禁止MiLAi创新。

### 13.2 三个可落地假设

| 假设 | 可支持的证据 | 不能当作证据 |
|---|---|---|
| 语义自足的读取包比重复多层对象更易用 | 同信息下少超限、任务质量不降或改善 | 仅token变少、仅格式合法 |
| 引用式保留减少非目标损伤 | 更新完成与仍有效限定保持同时改善 | 仅不发生删除、仅拒绝更多 |
| 显式条件/例外在连续变化中有净收益 | 同前态的例外增加/共同条件变化/撤销及后续问答改善，并在新历史确认 | 节点变多、个别故事通过、跨版本比较 |

若staged与多轮相当，保留staged；若B1与M相当，采用普通局部编辑；若Append-only更可靠，也可以成为功能默认，论文如实报告条件机制的边界。

### 13.3 数学约束只描述可计算边界

拟议视图记为 `V_t = P(M_t, E_t, goal_t, access_t)`；P只投影实际状态与来源，不生成新事实。

拟议工作集选择满足 `T(Render(W_t, goal_t)) <= B_t`；T使用真实模板，B是当前声明预算。满足预算不等于证据充分，依赖闭包也仅包含已记录关系，不等于发现了全部自然语言依赖。

更新写为 `M_(t+1) = Apply(M_t, delta_t)`；Apply保证程序定义的版本与操作效果，不证明delta语义正确。将这三种边界写清，能避免把工程不变量当作“可信记忆定理”。

### 13.4 开发时只保留一条反思记录

每个工作包交接记录：实际现象、最早断点、本次改变、仍未解决。特别检查：

- 修复是否进入所有实际使用入口，而不只通过自己的mock？
- 模型是否又在重复生成程序已知信息？
- 为减少上下文，是否藏掉了理解主体/例外所必需的内容？
- 只是把失败移到下一环，还是用户的完整任务真正改善？

这是开发笔记，不是审批表，不要求每次改动开启新评审或新实验矩阵。
