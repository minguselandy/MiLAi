# MiLAi Lab v12：先解决写入与恢复失败，再研究决策控制收益

**本轮最应解决的，是“已理解的新要求没有合法写进去，失败又被当成处理完成，随后旧记忆驱动了错误业务动作”。v11 已经降低 Basis 占用；继续围绕 State 增加字段、控制动作和指标，触及不到这条主要故障链。**

下一版以三个结果为中心：Host 能用现有增量路径完成局部修订；失败后能够修复或明确保留未完成状态；业务成功后只续接维护，不重做业务。公共提示与工具合同的压缩随后进行，Attention 效果比较暂缓。ordinary 保持默认，但其普通写入和维护合同同样需要修复。

本文是基于当前源码与保存轨迹的开发设计，未实施修复、未运行 pytest 或 benchmark、未新增模型调用。配套 [v12 Goal](MILA_CONTEXTUAL_USER_MEMORY_DEVELOPMENT_GOAL_v12.0_20260925.md) 规定工作顺序；[只读诊断清单](../data/manifests/contextual-memory-v12-planning-diagnosis.json) 保存本次核对和派生统计。v11 已关闭的 Goal 与结果保持原样。

## 3. 新定位：十五次拒绝并不是一个原因

逐项阅读现存调用与材料后，拒绝可分为：

| 类别 | 次数 | 本次定位 | 应采用的处理 |
| --- | ---: | --- | --- |
| 引用被认定未读正文 | 8 | 其中 1 次已通过另一别名读过同一来源；其余 7 次没有这种证据 | 修正准确对象级可见性；真正未读时保留读取要求或使用现有增量继承 |
| patch 原片段不存在 | 1 | 把主体元数据中的内容当成正文片段替换 | 清楚分开正文 patch 与元数据修改，不增加模糊匹配 |
| source 字段收到卡片句柄 | 1 | 引用种类错误 | 在目标材料及错误中说明来源与依赖的可用位置 |
| 已 dispatch，但旧回执丢失原因 | 5 | 当前主体校验重建均得到 ABOUT_SOURCE_NOT_CITED | 交付主体锚点及合法修改方式；保留重建范围说明 |

调用路径还揭示了一个值得优先利用的现成能力：

| 已执行写入方式 | 提交成功 | 拒绝 |
| --- | ---: | ---: |
| CREATE，完整依据 | 14 | 1 |
| REVISE，现有 delta 依据 | 10 | 1 |
| REVISE，完整重列依据 | 8 | 13 |

这不是匹配任务的因果比较，不能宣称 delta 成功率一定更高。但它说明增量路径已经真实可用，下一轮不应再设计一套新的增量 API。优先让 Host 在合适的局部修改中正确使用它。

## 4. 修复一：读取事实应绑定准确对象，不应绑定单个展示别名

### 4.1 已确认的故障

arc1 A0 最后一次维护中，第一次写入因 m10 未读被拒。Host 随后读取 m10，服务返回 m19，完整交付同一来源的 [0,404) 范围。再次写入继续使用 m10，仍被认定未读。

两个句柄对应同一准确来源，m10 是原有的链接句柄，m19 是后来的正文句柄。正文仍在当前 transcript 中。当前 Host 在解析写入字段时直接检查所选别名的 spans；它没有使用同一对象已经通过其他句柄交付的事实。

这不是“模型应该再认真读一次”。模型已经调用了读取，程序对已读事实的判断过窄。

### 4.2 最小改法

保留别名不可变及其定位作用。写入授权改用现有 HostSession 的当前可见绑定：

    输入别名
      → 解析准确对象、版本和范围
      → 在当前可见交付中查询该准确对象
      → 按本操作需要的正文范围核对
      → 执行现有写入校验

HostSession.refresh_visibility 已按准确引用汇集可见范围，应复用这份事实。必要时提取一个窄的“解析引用并查询可见范围”函数，供来源引用、目标读取及 patch 使用；不建立第二份持久可见性账本。

验收需要同时满足：

- 同一准确来源已在其他别名下交付，原链接别名可以定位该来源并使用实际可见范围。
- 只有链接而从未交付正文，仍不能当作已读；不同版本或不同来源不能借用可见性。
- 已从 transcript 清理的正文不继续取得授权。范围检查、删除、权限及来源 hash 校验继续有效。
- MemoryCard 仍检查已交付的准确版本；不得把旧别名自动改绑最新版。

这只修复一项已确认的误拒，不将另外七次真实缺少正文的拒绝全部取消。

## 5. 修复二：把局部修改的依据合同交付清楚

### 5.1 为什么金额已改对，提案仍不能提交

当前主体模型允许以某一来源的 speaker 定位主体。_about_view 要求这份来源仍在最终 source_refs 内；actor 型主体也需要对应的引用依据。MERIT 当前接入没有为用户消息提供稳定 actor_ref，因此旧卡可能依赖原始消息作为主体锚点。

arc2 A1 的三次金额修订都保留了旧主体，却从最终依据中移除了原主体来源。第一次使用 delta，也明确删除了这项依据；随后完整替换只列新消息及业务回执。当前约束因此拒绝这些提案。

本次利用实际交付的卡、别名与来源元数据，重建三次修订和另外两次后续写入，并只调用当前纯主体校验函数。五次均得到 ABOUT_SOURCE_NOT_CITED。**这是确定性前置条件复核，不是历史模型重跑；原始核心错误文本已经丢失，仍不能排除其他校验失败。**

这个问题暴露了写入端与展示端的不对称：程序知道哪些关系是主体定位的必要条件，Host 却容易把它们当成可以随旧金额一起删除的内容依据。

### 5.2 优先完善现有材料，不急于重做主体模型

交付可修订卡时，用短信息说明：

| 项目 | 向 Host 表达的事实 |
| --- | --- |
| 准确目标及版本 | 本次修订的是哪张当前卡 |
| 主体与事项 | 这张卡关于谁、哪一个订单或文件要求 |
| 主体锚点 | 保留当前主体时，必须保留哪项来源关系 |
| 现有依据 | 哪些关系可由 delta 继承；哪些新增引用尚需读取 |
| 允许的修改路径 | 局部正文变化用 patch＋delta；真正改变主体／范围等元数据时走明确替换 |

这些都是程序已知的事实，不需要语义 Agent，也不要求每次增加一轮查询。只交付与当前目标有关的信息，不能再附整套存储报表。

以下名称只是拟议投影含义，不要求机械新增同名数据库字段：

    target: 已交付当前卡
    identity_anchor: 保留当前主体所依赖的来源
    inherited_basis: 当前已存在且 delta 可保留的关系
    new_basis: 本次新增且已交付的依据

### 5.3 局部修订的预期路径

同一主体、同一事项，只修改金额或执行状态时：

    已读目标版本
      ＋ 准确 content_patch
      ＋ 本次新增依据
      ＋ 真正需要撤回的关系
      → 现有 delta 路径提交

未变化的元数据与关系由程序按现有合同继承。Host 不必为了更改一句话重列全部旧来源，也不应为顺便润色 context 而被迫走完整替换。

仍保留完整替换能力。主体、适用范围或结论真正变化时，应明确提交新内容和所需依据，不能一概强制 delta。

### 5.4 必须保留的语义边界

- 原来源继续作为主体或历史谱系依据，不意味着其中的旧金额仍是当前结论，也不能多算为一份独立支持。
- Host 明确撤回某项关系但会破坏当前主体合同，应返回具体冲突及修复入口；不能静默取消撤回或偷偷补回关系。
- 新消息的 role=user 不证明它和所有旧消息属于同一现实主体。不能为了通过测试统一改成 current_user，也不能从 benchmark 标签推导 actor。
- 真正撤回来源、变更主体的情况按现有显式合同处理。只有小范围修复仍不能表达合法更新时，才考虑把主体定位关系与内容依据进一步分开；这不是本轮必建的新实体系统。
- 正文 patch 只处理正文。元数据中的旧片段不在正文中时返回准确错误，不能用近似替换碰运气。

### 5.5 错误需要可行动，但不泄露内部内容

R3 已恢复安全错误码，应保留；下一步只补实际需要的定位：

    错误代码
    ＋ 发生问题的字段
    ＋ 已交付的目标／来源别名
    ＋ 合法下一步

例如明确说明“删除这项来源将使当前主体无依据；保留主体时使用继承路径，改变主体时提供明确新主体依据”。不把任意内部异常原样送进模型，不引入全局错误处理框架。

## 6. 修复三：失败提案不能从维护终结中消失

### 6.1 当前完成状态为什么失真

当前 maintenance.committed 记录成功提交以及部分完成／pending 操作；完全拒绝的提案通常直接返回。Host preflight 拒绝更不会进入这条提交路径。semantic_frontier 因而看不到这些尝试过但尚未解决的维护意图。

arc2 A1 金额修订失败后的终结包含：

    committed_changes = []
    unsettled_operations = []
    missing_required_persistence = []
    semantic_decision = processed
    status = complete

在本例中，“没有未决提交”被当作“没有尚未解决的维护”。两者不同：Host 已经三次明确尝试更新，只是没有成功。

该新金额观察也没有进入后续可搜索的持久来源快照。它仍可在诊断 trace 中找到，但下一 episode 正常检索不能依靠 trace 自动补回。因此旧卡继续成为行动依据。

### 6.2 在已有维护上下文中保留少量待解决尝试

增加的是失败处理语义，不是第二套任务队列：

1. 只在 Host 实际尝试了持久写入且失败时，记录本轮待处理的写入尝试。
2. 能绑定目标时保存准确目标；在 preflight 阶段不能绑定时，保存可公开错误与已交付字段位置，不猜目标。
3. 重试同一局部修订时合并到已有待处理项，避免每次失败多出一张“待办”。
4. 程序提供成功提交与未解决尝试的摘要，Host 不再重填完整来源—提交对应表。

相关失败可以有三种后续：

| 后续 | 处理 |
| --- | --- |
| 已修好并实际提交 | 程序关闭该次操作失败；语义是否充分仍由 Host 负责 |
| Host 明确判断这次可选写入不应继续 | 简短说明放弃原因，保留此次决策，不冒充已保存 |
| 仍需修复、证据不足或容量耗尽 | 维护保持 pending，保留足够的目标与观察以便恢复 |

不能仅因同一张卡后来有一次成功写入，就把这张卡的全部失败尝试清除。优先沿同一次修复的操作关联确定对应关系；确有多个待处理含义时，让 Host 只对这些剩余项明确处理。目标相同能定位操作，不能证明语义问题相同。

只有出现未解决尝试时才需要额外表达。零写入可以正常完成；没有长期价值的例行查询不应因此被强制保存。放弃可选写入也不能越过可信接入已指定的必须持久化要求。

### 6.3 不把 finish_turn 变成更重的关卡

实施顺序必须先修可见性、合法修订路径和错误交付，再接入未解决尝试。否则只会将“错误 complete”换成“永远 pending”。

收敛后的终结应区分：

    业务实际结果：成功／失败／未知
    记忆维护：已处理／仍未完成
    真实提交：由程序给出
    未解决尝试：仅保留本轮需要继续处理的少量项

评估时不仅检查非法 complete 是否消失，还要检查 Host 能否最终修好；新增 finish 拒绝数量下降并不是唯一目标，陷入更多阻塞同样是失败。

### 6.4 沿用现有恢复路径

RuntimeStore 已保存业务 intent 与真实 result，已有同轮恢复能力。不需要重建事务系统。

新的维护待处理信息若需要持久化，应进入现有 runtime/session 快照，并同步更新兼容身份。未完成时保留原请求、实际业务结果和必要观察；续接只完成尚未完成的维护。已确认业务成功不能再次执行；结果未知仍按已有核实路径处理。

跨版本诊断不能直接改旧库 identity 来装载，也不能把业务请求换一个 session ID 后重做。需要新运行身份、明确兼容导入，或从原生初态重建必要前缀。

### 6.5 没有尝试过的漏维护，另行处理

失败尝试追踪抓不到 arc1 A2 的“业务结束，根本没有提交完成状态”。应沿现有普通路径同时交付当前事项卡与真实结果，让 Host 判断是否改变当前理解，并在共享维护提示中明确这种判断。

不能将每份工具回执自动转成卡片，也不能用 benchmark 的正确答案指定必须更新哪张卡。真实应用中明确的“请记住”可由可信接入建立要求；普通 benchmark 问题及评分标签不能偷偷变成写入授权或持久化标签。

这一项需要真实 Host 的后续卡片与行为验证。程序能证明提交发生，不能证明所有应保存的含义都已覆盖。

## 7. 成本优化顺序应按测量调整

### 7.1 先压缩公共合同

F 总输入为 1509625 tokens。按已有冻结 tokenizer 的分段估算：

| 分段 | tokens | 相对总输入的量级 |
| --- | ---: | ---: |
| 固定提示与完整工具合同 | 909248 | 约 60.23% |
| 当前 Basis 投影 | 4821 | 约 0.32% |
| 历史 sidecar | 21196 | 约 1.40% |
| 固定合同中的控制说明 | 23040 | 已包含在第一行，不能再次相加 |

这些分段并非严格可加的 provider 账单，不能宣称删去某字段就精确节省同等 tokens；共享推理成本也不能独立归因。但优化位置很清楚：当前状态投影已经较小，公共工具合同更值得处理。

源码中 Host 将所有工具的名称、说明和完整 JSON Schema 放入 system 消息，同时为结构化动作配置 response_format。这里只确认 system 中的 schema 占输入；不假定 decoder schema 又按同样大小计费。

建议从同一工具定义生成简洁的模型视图：保留操作目的、必要字段、互斥分支和关键写入限制；完整 schema 继续用于本地验证及已支持的结构化解码。业务工具名称和关键说明保持原意。

不手写第二套会漂移的参数规范，不增加“查工具目录”的额外模型回合，也不先删掉 baseline 本可使用的工具。先比较静态输入量，再用同一失败任务核对合法提案和任务完成。公共压缩对 Notes、Basis 和 Attention 一致适用。

### 7.2 截断是实际执行成本，不能只做宣传指标

F 的 39 次截断累计消耗 484243 tokens，占全部 generation tokens 约 25.8%。截断输出均未执行部分 JSON，这项边界正确，应保留。

当前恢复主要重复提示输出短动作或答案，仍沿同一推理／输出合同继续请求。连续六七次截断已说明：原样重试不保证产生更短的合法维护动作。具体有多少由 Basis、合同、工具失败或业务推理造成，当前证据不能精确拆开。

推荐顺序：

1. 先消除误拒与模糊错误，避免模型围绕无法解释的失败反复推理。
2. 压缩公共工具合同，保持读取、写入和恢复能力。
3. 在同一失败位置观察剩余截断，区分连续推理耗尽与 JSON 体本身过长。
4. 仍有问题时，只检验一个明确的推理／输出容量假设，而非扫描参数网格。

不能盲目加大 output cap，也不必把 4096 当作不可改变的原则。如果修复后的普通维护仍被它截断，可以在相同权重和任务前缀下，比较一次适度增加容量的诊断；或在当前 provider 已有支持且合同核对后，诊断较轻的推理模式。二者不同时修改，实际设置另存运行身份。

判断看有效动作、维护完成、全部失败成本与业务正确性；不只看单次 completion 长度。未来方法比较各臂使用相同推理合同。未知支持的 vLLM 功能先核对本地实现及官方资料，不能在计划中当作已具备。

### 7.3 Sidecar 仍有优化空间，但不是首要工程包

A1 请求占用为 16/71，A2 为 12/56，稀疏状态已经出现。可是 41 次 NO_STATE_CHANGE 都来自已空状态的 clear 或 null-gap；arc2 A2 的 28 份可解析响应甚至没有 null。

这说明低占用不等于低生成负担。若共享路径修复后它仍占明显成本，再考虑让未提供 sidecar 的普通动作等价于“不改变”，明确 clear 仍独立。先验证现有 decoder 合同兼容，不急于增加 patch、多个 decision slots 或新的 State 策略。

## 8. Attention 没有收益，不应靠强迫调用解决

F 中只有一次 Host 主动 memory_search。它使用显式 query=address，却把 m0 放入 known_at，调用失败。有效 gap 查询、gap 新材料和自动版本通知均为零。

另外两项源码事实解释了为什么这个样本不能识别控制收益：

- prime_session 已在接收本轮新观察前，用共享普通检索预取相关卡片与来源。后续可能根本不缺需要再次搜索的材料。
- 八次同事项变化都跨原生 episode；Basis 按 session 重置，活跃采用又全部是 source 或空集合。没有自然形成“仍采用旧卡版本的活跃决策，随后卡变版”的窗口。

因此保留三种不同结论：工程路径存在；本样本没有实际自动 gap／版本通知；方法收益尚未确立。不能从 A2 两次 5/5 推导 Attention 有效，也不能从调用为零直接推导 resolver 有 bug。

当前已暴露两个实例主要适合写入、维护与恢复回归。方法实验恢复前，只需确认原生任务确实有：

    当前仍采用的判断
      → 一个会改变行动的信息缺口或依据变化
      → 旧材料不能直接消除该缺口
      → 正常操作中有重新取材／重核机会

不移除 baseline 的合法预取，不修改原生消息顺序，不强制引用 MemoryCard，不将“接下来发送确认”当作信息缺口。原任务中没有机会，就报告不适用；不以模型自己写了 gap 作为应触发的 gold。

A1/A2 在每个实例中的首个规范化 provider 请求相同，实际动作仍不同。当前部署下 temperature 0 不保证逐字可复现；当唯一方法差异分支从未执行时，不能用分数差异估计其因果收益。解决办法是选择可识别的问题与干预，不是立即大量重复已暴露任务。

| 位置 | 本轮需要的责任 | 应避免的扩张 |
| --- | --- | --- |
| runners/contextual_host.py | 引用解析、当前可见性消费、记录真实失败尝试、精简公共合同 | 同时重写业务执行与全部控制逻辑 |

| methods/contextual_memory/write_contract.py | 保留现有 delta／完整替换；必要的描述收敛 | 模糊 patch、静默补来源、再造新协议分支 |

## 10. 开发后怎样验证

### 10.1 先完成开发与窄检查

优先复用现有 Host adapter、sessions、material view、maintenance、runtime recovery 测试。覆盖实际失败边界即可：

- 同对象的另一个已读别名可以使用；真正未读、旧版本、已清理正文不能借用。
- 同主体局部 delta 合法；删除主体锚点返回准确原因；字段种类和 patch 位置不混淆。
- 完全拒绝与 preflight 拒绝都进入待处理尝试；真实修复清除；可选放弃与合法零写入可以终结。
- 业务已成功但维护中断，恢复只做维护；新的失败状态不能变成永久阻塞。

只修改文档时不运行这些测试。本轮文档形成后，实施阶段才按受影响范围运行；不为了数量增加镜像实现测试或全量组合。

### 10.2 再做少量已暴露故障诊断

不重开 v11 的六条封存轨迹。使用新身份创建以下诊断，数据、世界与 scorer 都保持原生：

| 诊断 | 选择理由 | 必须观察的实际结果 |
| --- | --- | --- |
| 金额修订及后续消费 | arc2 A1 已证明旧值进入业务 | 修订真实提交；下一原生请求取到当前值；执行回执与用户新要求一致 |
| 已退款后的维护恢复 | arc1 A0 已证明业务成功而维护失败 | 已读句柄不再误拒；完成状态写入；退款只发生一次 |
| 成功业务后的漏维护 | arc1 A2 原生通过仍漏写 | 当前卡能表达真实完成结果；无需另增相互竞争的完成卡 |

这些是开发回归，不是新的独立效果证据。开始时按问题选择最小必要前缀或原生后缀，不预定将三项都扩成完整五集。

旧快照若兼容性不能明确成立，就从原生初态重建必要前缀，并计入费用。重放片段只能报告片段结果；若要声称当前配置完整 arc 通过，必须在最终冻结身份从原始初态连续完成该 arc，不能拼接旧前缀和新后缀。

每次真实调用前给出一个待检验修复和预期可见回执。失败后先定位原因，只有新改动或新证据才开展下一次复核；这不是累计次数硬停止，也不是允许原配置无限重试直到通过。

### 10.3 成本比较保持可比

新旧工具投影可先用本地 tokenizer 做零模型比较。真实局部对照保持目标、观察、业务初态、模型、推理合同与可用能力一致。旧版本没有完成的轨迹，不能简单用更小 token 总数宣称效率更好。

最少报告：写入尝试／成功／拒绝原因，拒绝后的修复回合，维护与业务各自状态，重复业务次数，输入／输出／截断费用，embedding 与必要 Judge。恢复成本包含原失败成本；部署维护成本与 benchmark 评分成本分列。

MERIT 沿用原生 checker，本轮诊断不需要另加 LLM Judge。以后确需语义判断时使用 vLLM，保留原分数，附加诊断不改 rubric。未知标签保持 unknown。

## 11. 继续做与暂缓做的分界

以下是按问题推进的顺序，不是全部必须完成的功能清单：

| 优先级 | 工作 | 什么结果决定下一步 |
| --- | --- | --- |
| P0 | 修准确对象可见性及合法局部修订信息 | 原拒绝提案有明确、可执行的修复路径 |
| P0 | 收拢失败尝试与维护终结、恢复 | 不再静默 complete；正常修复能完成；业务不重做 |
| P1 | 精简公共工具合同 | 相同能力下输入减少，合法动作与维护没有退化 |
| 条件分支 | 调整推理／输出容量 | 修复后仍有截断才进入；只检验一个定位明确的假设 |
| 条件分支 | 减少重复 sidecar 生成 | 共享成本下降后该负担仍显著才做 |
| 后续研究 | 自然机会下比较 State–Attention | 普通路径能完成且任务具有可识别机会后再恢复 |

不新建候选、训练 controller、换模型、建图数据库、引入审核 Agent、恢复 H1—H6、增加多个决策槽或迁移 Product。也不增加大量日志来替代问题修复。

普通路径修好不等于 Decision Basis 已有方法贡献。后续若重新比较，仍可用 Notes、Sparse Basis、Sparse Basis＋Attention，但必须共享新写入／恢复／工具合同；若没有自然自动取材或版本重核机会，不启动新的三臂分数比较。

## 12. 本轮交付与后续完成判定

本轮交付的是源码及轨迹核对、原因分析、具体修复设计与可执行 Goal。没有修改实现、请求配置、测试集或历史结果；只读执行过当前纯主体校验的提案重建，没有模型调用和测试套件执行。

下一轮工程完成应回答：

1. 同一来源已经看过，为什么还拒绝？——可见性按准确对象与当前范围统一。
2. 这张卡怎样合法更新？——主体约束、继承关系与新增依据已经明确交付。
3. 修订失败后发生了什么？——能修复、明确放弃或保留 pending，不会消失为 processed。
4. 业务已成功但维护失败，怎样继续？——沿原操作身份恢复维护，业务不会重复。
5. 仍然昂贵在哪里？——按共享合同、有效动作、失败和恢复分解，而非只算 Basis 大小。

质量或成本仍无优势可以如实结项；关键缺陷尚未修好不能仅凭测试通过标记完成。即使诊断题全部通过，结论仍限于这些已暴露任务，ordinary 默认与方法收益未确立的判断不自动改变。
