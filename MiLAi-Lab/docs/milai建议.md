# 一、首先准确重构你的论文

## 1. Research problem：你究竟在研究什么？

你的问题不是一般性的“LLM 如何记住更多历史”，而是：

> **长期个性化交互中，如何维护具有正确主体、适用情境和证据依赖的持续理解，并区分“当前任务暂时不适用”与“长期理解需要修订”，使后续任务在有限计算预算内使用当前有效的记忆。**

它包含四种不同的失败：

| 失败类型 | 具体含义                                |
| ---- | ----------------------------------- |
| 归属错误 | 把第三方要求、模型推断或任务约束记成用户本人的长期属性         |
| 范围错误 | 把“这次客户汇报简短”概括成“用户总是不喜欢细节”           |
| 更新错误 | 新反馈到来后，旧概括继续支配后续任务，或者修订破坏仍然有效的部分    |
| 使用错误 | 找到了主题相关的记忆，却没有取得或正确应用其中的条件、例外、否定与时效 |

这些正是附件提出的问题，而不只是我替你重新包装的动机。

进一步限定：**当前 MiLAi 主要属于非参数化、文本型、个性化 agent memory。**它包含来源记录、条件性理解和任务工作状态，但尚未展示程序技能学习、跨任务策略学习或模型参数持续学习。附件也明确不把模型训练、多模态记忆和通用 agent 框架作为当前前置条件。

## 2. Core hypothesis：你的核心假设是什么？

附件列出 H1—H5，但它们不是一个同等重要的研究假设，而是五条不同的研究路线：接口易用性、条件性修订、State 的独立贡献、材料组织效率，以及批量摄取成本。

最值得作为论文主假设的是：

> **将任务局部适用性与持久理解修订显式分离，能够在新反馈到来后减少旧理解误用和跨情境泛化错误，同时保留未受影响场景中的有效知识。**

这里有三个必须同时满足的结果：

**该改的改正确；不该改的不被破坏；变化能够影响后续行为。**

“答对更多题”只是可能的外在结果，不是这个假设本身。

H1、H4、H5 更适合作为系统设计或效率分析；H3 可以支持主假设，但“State 能改善检索”本身还不足以构成主要科学结论。

## 3. Method：最关键的技术机制是什么？

按照附件，当前方法可以重构为：

$$
\text{不可变来源}
\rightarrow
\text{可修订、带条件的理解}
\rightarrow
\text{任务状态驱动的取材}
\rightarrow
\text{回答或进一步修订}
$$

具体是以下四层。

**第一层：来源与理解分离。**
Observation 保存实际取得的内容、角色和事件身份；MemoryCard／Interpretation 保存 Host 对内容的整理、主体、情境、确定性和持久化范围。来源存在不等于内容真实，引用存在也不等于总结被来源完整支持。

**第二层：版本和声明依赖约束。**
修订必须针对实际读过的准确版本；来源变化或依赖版本变化后，相关理解显示需要重新核对。程序维护版本一致性，但不会自动发现全部隐含语义依赖。

**第三层：任务状态与长期修订分流。**
TaskState 的主体、场景和不确定性影响有效查询；Attention 在候选和预算内选择材料；Revision 改变长期表达。临时换场景原则上不应重写永久画像，永久理解错误也不应只靠当前任务绕开。

**第四层：有界模型决策、确定性执行。**
历史按合法前缀摄取，每批一次模型提案，程序执行保存、修订和版本检查；答题使用有界工具循环。当前批次提案最多 16 项操作，相关旧记录预算为 12,000 字节。

必须明确：**跨查询范围账本、完整紧凑／展开视图规划、多范围命中与会话邻接仍是目标设计，不是已经得到验证的方法贡献。**

## 4. 预期 contribution 应如何表述？

目前最忠实的贡献组织是：

| 贡献类别                      | 你实际拥有或计划拥有的东西                         | 目前证据状态            |
| ------------------------- | ------------------------------------- | ----------------- |
| Problem novelty           | 条件性用户理解在任务切换、反馈修订中的适用性问题              | 问题描述明确；是否新需对照已有工作 |
| Method novelty            | State／Revision 分流，以及来源、版本和依赖约束下的取材与维护 | 操作基础存在；独立新机制尚待确认  |
| System novelty            | 将上述能力组织为统一工具、生命周期、恢复和评估执行链            | 当前最具体的产出          |
| Evaluation novelty        | 针对范围误用、错误归属、修订副作用的受控测试                | 尚未形成正式研究评估        |
| Empirical finding novelty | 哪些错误确实由条件性修订解决，哪些由检索或 Host 决定         | 尚无足够结果            |

你已经在文档中区分工程与研究，但仍有一个实质性混淆：

> **“程序支持某种正确行为”被放得很接近“Host 会稳定选择该行为”，而这两者之间正是尚未完成的研究问题。**

附件自己也承认：两类操作接通，不代表真实模型已经形成稳定有效的策略。

## 5. 最合理的一句话核心 claim

在尚未取得结果时，应该写成研究目标：

> **MiLAi 研究在相同证据访问权与计算预算下，来源可追溯的条件性记忆修订，是否能够减少长期个性化中的范围误用与陈旧理解沿用，并避免损害未受影响的情境。**

取得充分证据后，才可以把“是否能够”改成“能够”。

## 2.3 哪些碰撞最可能削弱 novelty claim？

### HiMem 与 TierMem：会削弱整条“来源—理解—取材—再修订”叙事

这两项工作意味着，不能把以下链条作为新的核心思想：

> 保存原始材料 → 生成紧凑知识 → 判断材料不足 → 回到原文 → 更新知识。

MiLAi 与它们并非完全相同，但“没有使用相同数据结构”不足以构成强区别。你需要证明的是**准确版本、范围和修订约束在特定失败条件下带来了不可被简单路由替代的收益**。([arXiv][6])

### MemSlides：会直接削弱“临时任务状态与长期偏好分离”的概念创新

它不仅有 short-term／long-term 两个存储层，而是明确按照当前任务意图选取长期偏好、以当前请求局部覆盖冲突，并只把稳定信号写回长期画像。

因此，“别人只是分层，而我区分长期偏好与临时约束”不能成立。你可争取的区别是**记忆本身的语义局部修订与跨情境不干扰**，不是再次提出两类生命周期。([arXiv][7])

### CUPMem 与 StateAuditor：会削弱“新信息到来后旧理解仍影响行为”的问题创新

前者把写入时的状态裁决及传播做成具体操作；后者进一步指出，更新状态即使存在，输出仍可能隐含依赖旧状态。

所以“检索成功不等于正确使用记忆”已经不是足够新的 scientific finding。你必须进一步定位：**哪种条件性变化、哪种依赖遗漏、哪种局部修订副作用，现有裁决或回答审计仍无法解决。**([arXiv][8])

### Kumiho：会削弱“准确版本、可追溯依赖、变化传播”的结构创新

它已经明确区分 `Depends_On`、`Derived_From`、`Supersedes`，并通过版本引用和影响遍历查找需要重新评估的下游对象。

我没有将其形式正确性主张视为已完成独立证明；但这些公开的操作描述已经足以成为 prior art。**MiLAi 不用图数据库，是实现取舍，不是对这些机制的首次提出。**([arXiv][9])

### MemR3：会削弱 State／Attention 的闭环创新

显式维护“已有证据／尚缺什么”，再决定检索、反思或停止，已经是它的中心机制。

你的潜在差异在于**coverage 对查询、状态、版本与材料身份的准确绑定**，以及是否能减少无效调用。但这需要一个专门的失效与恢复实验，不能只用总体 QA accuracy 支撑。([arXiv][10])

### ReFind：主要不是“你抄了它”，而是“为什么需要你的系统”

它代表 reviewer 最有力的反问：

> 给一个足够好的 agent 原文搜索、会话定位、时间过滤和邻接读取，为什么还需要预先维护这么多理解对象？

这也是为什么仅战胜弱 RAW_RETRIEVAL 不够。([arXiv][20])

## 2.4 其他不能遗漏的边界

**效率方面。**ReadAgent 已研究 gist memory 与原文回看；LightMem 已研究压缩、语义分组与延迟 consolidation。它们分别压缩了“先紧凑后展开”和“少量在线调用”的新颖性空间。([arXiv][21])

**学习方面。**PersonaMem-v2 不只是 benchmark，还提出学习 agentic memory；Mem-α、MemRL、MemCon 分别覆盖学习记忆构建、运行时 episodic utility 更新和自适应管理。MiLAi 当前没有对应的 learned policy，不能因为记忆会变化就认领同等意义的 continual agent learning。([arXiv][22])

**来源与可信性方面。**TMA-NM 已把来源身份绑定到可信接入边界，并处理总结、工具回声与伪造佐证造成的权限提升；EAL-Bench 已研究没有外部攻击者时，记忆更新如何把材料错误转化成行动权限。这些不是 MiLAi 当前必须承担的安全任务，但它们排除了“来源绑定本身是新机制”的宽泛主张。([arXiv][23])

**同源记忆不能重复计为独立证据，也不能轻易升级成新贡献。**CAMA 已研究相关记忆造成虚假多数，并使用 provenance 与查询相关依赖估计进行证据仲裁。([arXiv][24])

**程序／轨迹记忆方面。**Voyager 的可执行技能库、Agent Workflow Memory 的工作流复用属于必须理解的相邻方向，但它们不是当前 MiLAi 的最近方法对手：你尚未学习或复用可执行策略。([arXiv][25])

**Novelty Search 的结论：目前没有确认一个“已实现、操作级、可独立归因”的新算法。**这不是证明不存在创新空间，而是说现有宽泛贡献表述已经被相当密集的 prior work 覆盖。

# 三、Novelty Kill Test

## A. Combination-of-existing-techniques test

**目前很大程度上是。**

去掉名字后，你的方法接近：

> 来源日志与身份绑定
> ＋ 带元数据的可修订记忆
> ＋ 乐观版本检查与声明依赖失效
> ＋ 混合检索
> ＋ 任务状态 query expansion
> ＋ evidence-gap 式检索控制
> ＋ 批量 LLM 写入提案
> ＋ 生命周期与预算工程。

上述组成分别已被 Mem0、Zep、Kumiho、MemR3、TierMem 等覆盖。([arXiv][15])

更严重的是，**最关键的语义决策——临时要求、例外、更正、长期偏好如何区分——当前主要由 Host 执行，而不是一个明确的新推断或修订算法。**

这不使系统没有价值，但会让 reviewer 合理地将其归为 engineering integration。

## B. Obvious-extension test

**多数组件组合属于自然 extension。**

熟悉这些文献的研究者很自然会想到：

把 episode 和 note 分开；给 note 加主体、时间和情境；新信息到来时检查旧 note；把任务信息加入检索；材料不足时展开原文；给更新加版本保护。

真正不明显的部分应当是某个具体选择，例如：

> 为什么某种局部修订规则比“让 LLM 重写整条记忆”更能保留无关条件？
> 为什么某种范围失效规则能在相同候选和 token 下避免遗漏，而不是简单去重就够？

你还没有用实验把这样的非显然选择建立起来。

## C. Mechanism novelty test

| 当前或计划操作                        | 是否已确认有新颖性？     | 判断                                 |
| ------------------------------ | -------------- | ---------------------------------- |
| 程序绑定真实来源角色                     | 否              | 重要的正确性边界，但已有来源绑定类方案                |
| 来源与理解分别保存                      | 否              | Zep、HiMem、TierMem 等已有              |
| 相关旧记录＋批量新增／更新决策                | 否              | Mem0 及后续方法已有                       |
| 固定版本引用、依赖变化提示                  | 否              | Kumiho 等已有相近操作                     |
| State 文本加入 query               | 否              | 目前主要是上下文增强查询                       |
| GAP 驱动扩展与停止                    | 否              | MemR3 已直接研究                        |
| coverage 精确绑定 query／state／材料版本 | **尚未确认**       | 可能是有价值的执行语义，但“更准确的缓存失效”不是自动成立的方法创新 |
| 跨查询、版本、范围、视图的呈现账本              | **尚未确认，而且未完成** | 值得研究；必须胜过简单 interval 去重和重新读取策略     |

附件清楚说明，版本和来源检查不能保证理解语义正确；这是你不能跨越的论证边界。

## D. Necessity test

以下替代解释都很强：

**更好的检索。**当前 lexical 路径只是子串计数，不是 BM25，而且同一来源的多处命中可能只保留一个范围。先修这两个问题，就可能获得大部分收益。

**更好的阅读模型。**历史轨迹已出现取得相关原文后仍答错。若决定性条件已经呈现而 Host 仍误解，进一步增加 memory machinery 未必命中瓶颈。

**更好的 prompt。**一个保存同样条件信息的普通文本 note，加上“不要把局部要求推广成全局偏好”，可能达到相似效果。

**更多有用计算。**candidate 可以通过额外 State 处理、查询与回看获得更多推理机会。若 baseline 获得相同预算用于 query expansion、reranking 或再次阅读，你的优势可能消失。

因此，**strong raw retrieval、same-information flat memory、oracle evidence** 是不可回避的三个对照。

## E. Ablation survival test

我最怀疑删除后可能变化不大的模块是：

| 模块           | 为什么可能没有独立收益                               |
| ------------ | ----------------------------------------- |
| 独立 State API | 当前主要功能可能被“把同样情境直接放进 query”替代              |
| coverage 状态机 | 若测试没有跨查询／版本变化，正确绑定不会被触发                   |
| 版本冲突保护       | 单 writer、顺序摄取任务可能很少发生实际冲突                 |
| 声明依赖传播       | 真正关键的隐含依赖可能根本未被声明                         |
| 复杂材料规划       | 修好 chunk、BM25、邻接后，简单 token packing 可能已经足够 |

这不是建议删除正确性保障，而是：**不能把低触发率的工程保障当成当前 accuracy 提升的原因。**

# 四、创新性分解评分

评分针对**附件中的当前方案和证据**，不是对未来升级版预先打分。

| 维度                                 |       分数 | 理由                                                      |
| ---------------------------------- | -------: | ------------------------------------------------------- |
| Problem novelty                    | **3/10** | 范围控制、状态更新与旧记忆行为影响已被 PersonaMem、MemSyco、STALE 等明确研究      |
| Conceptual novelty                 | **3/10** | 来源／理解、临时／持久、检索／修订分离均已有直接先例                              |
| Algorithmic novelty                | **2/10** | 当前关键语义策略主要由 Host prompt 实现；确定性部分多为已有工程机制                |
| Agent-memory-specific insight      | **5/10** | 对来源身份、适用性、历史版本与材料实际可见性的区分较细，但还没有转化为已证实的新规律              |
| Difference from nearest prior work | **2/10** | 与 HiMem、MemSlides、CUPMem、Kumiho、TierMem 的差异目前主要是组合与执行细节 |
| Potential scientific significance  | **6/10** | 若能证明选择性修订既改正目标又不破坏其他情境，结论具有价值                           |
| Empirical contribution potential   | **6/10** | 存在构造强因果诊断与质量—成本边界的空间；但当前不是已有 empirical contribution     |

问题相关 prior art 的直接依据包括 MemSlides 的生命周期分流、STALE 的更新—行为缺口与 MemSyco 的适用范围任务。([arXiv][7])

**当前分类：Engineering integration。**

更乐观但仍合理的潜在终态是 **Meaningful extension** 或 **Strong system contribution**。目前不支持称为 New paradigm；New mechanism 也尚未建立。

# 五、这是 Paper Idea，还是 Project Idea？

## Project value

**有实际价值。**

保留来源、避免错误归属、让修订可追溯、明确生命周期、恢复和失败状态，是一个长期助手系统应认真处理的事情。附件对这些边界的设计较具体。

但“一个系统值得做”和“该系统值得以新方法论文发表”不是同一命题。

## Research value

当前 research value 处于**可形成、但尚未形成**的状态。

做完系统后，reviewer 完全可能仍然说：

> “This is mainly an engineering improvement with limited methodological novelty.”

原因不是它没有训练模型，也不是规则系统天然不能发顶会，而是：

**你尚未指出一个非显然的机制选择，并排除同信息、同预算的更简单解释。**

## 真正应该证明的 scientific claim

我建议收敛为：

> **在存在情境局部例外、持久偏好变化和错误归属修正的连续交互中，显式限定修订影响范围，可以比普通追加、整体重写和强原文检索更可靠地实现选择性适应：受影响任务变正确，而未受影响任务不退化。**

可以定义一个主指标：

$$
\mathrm{SelectiveRevisionSuccess}
=
P(
\text{目标变化正确生效}
\land
\text{无关情境保持正确}
\land
\text{后续任务使用正确状态}
).
$$

这比三个 accuracy 的平均值更有辨识力：系统不能通过“全部偏好都不采用”来掩盖错误修订，也不能通过“全部覆盖为最新表达”获得虚假的更新成功。

这是**建议你证明的命题**，不是附件已经证明的结果。

# 六、实验设计能否真正证明 Claim？

## 6.1 Claim → Evidence → Current Experiment → Missing Evidence

| Claim                | 需要什么证据                                | 当前实验是否覆盖                     | 缺失实验                       | 严重程度             |
| -------------------- | ------------------------------------- | ---------------------------- | -------------------------- | ---------------- |
| H1：按意图接口更容易使用        | 同能力、同信息，仅改变接口；区分字段错误、语义错误和任务质量        | 未隔离                          | 接口对照与工具错误分类                | 中；不宜作为主 claim    |
| H2：条件性 Revision 优于追加 | 同一初始记忆与新反馈；比较追加、整条覆盖、条件性修订；检查无关条件     | **未覆盖：BASELINE 已有 Revision** | 明确关闭／替换修订策略；成对受影响／未受影响查询   | **致命**           |
| H3：State 有独立贡献       | 相同历史快照、相同情境信息、相同预算；排除 query expansion | **未覆盖：两组分别构建历史**             | 共享快照；直接 query 拼接对照         | **致命**           |
| H4：范围／视图规划提高效率       | 相同候选池和 token 预算；不同组装策略；测必要条件覆盖        | 主要模块未完成                      | 固定候选重放；新版本／未读范围／上下文裁剪测试    | 高                |
| H5：有界摄取降低总成本         | 建库、更新、查询全部成本；不同复用次数下质量—成本曲线           | 只有旧版本成本，不能归因 v3              | batch／逐条策略对照；break-even 分析 | 高                |
| 来源／版本约束减少错误使用        | 区分结构合法与语义支持；制造源修正、依赖变化和错误归属           | 部分工程测试                       | 语义误用率、错误依赖、缺失依赖的行为测试       | 高                |
| 遗忘正确且不会恢复            | 明确遗忘范围；新任务、handoff、恢复、原文重发布均不复现       | 已知边界未闭合                      | 旧 checkpoint、外部缓存和原文访问路径测试 | 高；若不作此 claim 可降级 |
| 能改善长期 agent 行为       | 多任务序列中的实际行动和后续适应                      | 当前主要为 QA／MCQ                 | 至少一个有工具行动及连续反馈的任务协议        | 高；若限定个性化记忆可不强求   |

归因缺口不是外部推断：附件已明确说明独立建库无法单独测 State，且 BASELINE 已有修订能力。

## 6.2 最危险的协议问题：全部合法原文会在答题时重新发布

附件说明，每道 benchmark 题开始后，系统重新获得全部合法原始历史。

**这不自动构成数据泄漏。**只要历史截止点正确、没有未来消息、各臂信息权相同，它可以是合法的 archive-backed memory 设定。

但它改变了论文能证明什么：

> 你当前测试的更接近“原文档案上的可维护语义缓存”，而不是“系统依靠自己保留下来的长期记忆完成任务”。

建议明确区分两种协议：

| 协议                 | 答题时能访问什么       | 可以检验什么             |
| ------------------ | -------------- | ------------------ |
| **Archive-access** | 全部合法原文＋方法生成的记忆 | 整理、修订与取材是否优于直接搜索档案 |
| **Retained-only**  | 仅摄取阶段实际持久化的对象  | 保留、遗漏、长期维护与遗忘是否有效  |

不一定必须两个都作为主结果，但不能在第一种协议上得分，却认领第二种能力。

另外，**原文重发布必须尊重已执行的遗忘范围**。不能删除了 memory card，下一题又从原文把相同信息取回来，然后声称遗忘成立。

## 6.3 Baselines：哪些 reviewer 极可能要求补？

| Baseline                             | 重要性              | 正确实现方式                                                |
| ------------------------------------ | ---------------- | ----------------------------------------------------- |
| Full context                         | 必须作为参考，限确实可容纳的历史 | 超窗标为不适用或单独报告；截断后不能仍称 full context                     |
| Sliding window／rolling summary       | 必须               | 分开报告窗口与持续摘要，不用极弱的一句话摘要充数                              |
| Vanilla dense RAG                    | 必须               | 作为检索基础参照，而不是最终强对手                                     |
| **Hybrid retrieval＋reranking**       | **绝对不能省**        | 真 BM25＋dense＋统一 reranker；候选预算与其他臂一致                   |
| **Agentic raw retrieval**            | **绝对不能省**        | 允许同样的查询改写、邻接、时间定位和有界回看；ReFind 是直接相关对手                 |
| **Same-information flat memory**     | **绝对不能省**        | 保存同样的主体、条件、来源信息，只去掉复杂结构／控制；prompt 同等强调适用范围            |
| Representative memory system         | 必须               | Mem0 或 HiMem 等可复现方案，不只和自家 BASELINE 比                  |
| Nearest mechanism baseline           | 随主 claim 必须      | 修订主线优先 HiMem／CUPMem；State 主线优先 MemR3；分层材料主线优先 TierMem |
| Oracle evidence／oracle scoped memory | 必须做诊断            | 仅提供正确证据或规范化条件，不提供正确选项标签或最终答案                          |

这些最近邻分别针对修订、检索控制、分层证据访问和原文替代解释，不能拿任意一个“memory system”代替所有类别。([arXiv][6])

**不需要把全部 15 个系统都跑一遍。需要的是覆盖最危险的替代解释。**

## 6.4 Benchmarks：是否真的测试你的 claim？

| Benchmark            | 真正测到什么                                 | 对当前主线的价值与限制                                                                    |
| -------------------- | -------------------------------------- | ------------------------------------------------------------------------------ |
| **LoCoMo**           | 长期对话相关回忆与问答等任务                         | 适合通用 sanity check；单用 QA 子任务不足以证明条件性修订或行动学习。([arXiv][26])                       |
| **LongMemEval**      | 信息抽取、多会话推理、时间、知识更新、拒答                  | 更新和时间子类有用，但总体分数不能分离修订与检索。([arXiv][27])                                         |
| **MemoryAgentBench** | 增量交互中的检索、test-time learning、长程理解、选择性遗忘 | FactConsolidation 等适合更新控制；不能把其中的 overwrite 能力自动解释成用户删除合规。([arXiv][28])         |
| **LongMemEval-V2**   | 从网页环境历史轨迹中取出经验，供固定 reader 回答           | 已确认存在；不是 V1 简单扩容。其 context-gathering 协议不直接测在线 agent task success。([arXiv][29]) |
| **PersonaMem-v1／v2** | 动态画像、隐式偏好、个性化响应与记忆学习                   | 与你最相关；v2 的方法部分也应作为 prior work，而非只借其数据。([arXiv][30])                            |
| **MemSyco-Bench**    | 适用范围、记忆与证据冲突、有效版本选择、正确个性化              | **直接针对你的范围误用 claim，应覆盖相关子任务。**([arXiv][31])                                    |
| **STALE**            | 状态更新识别、错误前提抵抗、隐含行为适应                   | **对修订主线比再增加一个一般 QA 集更关键。**([arXiv][8])                                         |

此外，检索已发现 **PersonaMem-v3**，其范围扩展到跨平台用户理解和 agentic tasks。它不是当前最小实验包的必选项，但不能再把 v2 描述成该系列最新工作。([arXiv][32])

### 最小成本但有说服力的补充协议

建立一个**独立、明确标注为新构建的 paired diagnostic set**，不改写原生 benchmark 成绩。

每条基础历史包含一个条件性要求，再加入一种变化：临时例外、持久偏好改变、第三方归属澄清或无关新信息。随后分别查询：

| Probe       | 测试目的        |
| ----------- | ----------- |
| 被变化影响的当前任务  | 是否正确适应      |
| 未被变化影响的其他情境 | 是否发生附带破坏    |
| 临时任务结束后的新任务 | 临时要求是否错误持久化 |
| 涉及另一主体的任务   | 是否发生错误归属    |

关键是**同一基础历史上的成对反事实比较**，而不是为你的方法编一些容易答的例子。

先用少量独立历史做可行性检查；正式规模由方差和目标效应决定。场景、表述模板及主体应跨开发／测试分离，预期标签由明确场景规范和独立核验形成，不能由被评估 Host 自己宣布正确。

## 6.5 必須报告的指标

你的主指标应是：**原生任务分数＋选择性修订成功率＋范围误用率**。

此外，至少报告以下四组：

| 组别    | 必须指标                                                                              |
| ----- | --------------------------------------------------------------------------------- |
| 记忆语义  | update correctness、未受影响知识保留率、错误主体归属、陈旧理解采用率、有效偏好被错误压制率                            |
| 证据链   | 必要条件的 retrieved recall 与 **actually-presented recall**；记忆内容的证据支持 precision；来源可追溯率 |
| 控制行为  | 实际 LLM calls、无进展率、重复范围比例、版本冲突与真实写入成功分开统计                                          |
| 成本与规模 | 建库／更新／查询 tokens，p50／p95 latency，存储增长、索引增长、冷／热缓存成本                                 |

两个容易混淆的地方：

**检索召回不等于呈现召回。**正确窗口在候选里，却没有交给 Host，属于材料组织失败。

**旧版本不等于错误版本。**回答过去时点的问题可能需要旧状态；你应测“不适用于当前问题却被采用”，而不是机械惩罚所有旧记录。

若保留遗忘 claim，还必须分别报告**显式删除、知识过时处理、容量淘汰**，不能合成一个“forgetting accuracy”。

# 七、最关键的七个 Ablation

不是每个模块都需要一个开关；下列实验直接针对你的可证伪机制。

| 实验                            | Remove／change 什么                                    | 对应 hypothesis              | 预期结果                   | 不符合预期意味着什么                                         |
| ----------------------------- | --------------------------------------------------- | -------------------------- | ---------------------- | -------------------------------------------------- |
| **A1：条件性修订 vs 追加／整体重写**       | 同一初始快照和新反馈，替换更新策略                                   | 条件性修订能兼顾适应与保留              | 目标正确率提高，未受影响条件不下降      | 修订可能只是压缩／去重；或者局部更新策略并不可靠                           |
| **A2：Revision × State 的 2×2** | 两个机制分别开关；从同一初始状态开始                                  | 所谓“双向配合”是否真实存在             | 完整组合在目标错误上具有可解释的交互收益   | 只能声称两个独立组件，不能认领协同机制                                |
| **A3：结构化条件 vs 同信息普通文本**       | 条件信息和 prompt 保持相同，只改变组织与执行约束                        | 收益来自机制，而非多写了条件             | 结构／约束在多次变化后仍有收益        | schema 可能只是 prompt packaging                       |
| **A4：State vs 直接 query 拼接**   | 使用相同状态文本、同一 memory snapshot                         | State 是否超出 query expansion | 在固定查询内容后，仍改善选择或减少无效回看  | State 的独立贡献消失；应合并成普通检索增强                           |
| **A5：版本／依赖约束**                | 保留相同元数据，但关闭失效与更新保护；加入真实源变化                          | 约束是否减少可观察的错误使用             | 陈旧依赖采用下降，必要重新读取增加但成本可控 | 约束未接入行为、依赖未声明，或任务根本不触发机制                           |
| **A6：精确范围账本 vs 简单去重**         | 与 seen-session、seen-turn、普通 interval 去重比较           | 更精确记忆可见性是否值得               | 新范围、新版本和被裁剪内容不会被误抑制    | 复杂账本无必要，或仅节省少量重复显示                                 |
| **A7：同预算强替代解释**               | 把 candidate 的额外预算给 baseline 做有效改写、rerank、回看；并比较摄取策略 | 收益不是更多调用／tokens            | 同成本仍有质量增益，或同质量成本下降     | 主要贡献是额外 inference-time compute，而非 memory mechanism |

A6 只能在对应实现完成后运行；附件目前尚没有跨查询范围账本，不能现在就把它写入已验证 ablation。

对 A2，可预先报告：

$$
\Delta_{\text{interaction}}
=Y_{11}-Y_{10}-Y_{01}+Y_{00}.
$$

但交互应在预先声明的指标尺度上解释。没有显著交互不说明两个组件都没用；它只削弱“协同带来额外收益”的说法。

**预算控制需要两条轨道。**一条固定证据、候选、模型与实际 token，用于机制归因；另一条允许各方法按自然方式运行，比较完整质量—成本曲线。只设相同“最多八次调用”，不等于实际计算量相同。

# 八、最危险的 Confounders

| Confounder    | 当前危险在哪里                                    | 控制方式                                       |
| ------------- | ------------------------------------------ | ------------------------------------------ |
| **记忆构建差异**    | BASELINE／CANDIDATE 分别摄取，差异可能早于 State       | 冻结同一快照做读取机制实验                              |
| **可访问证据差异**   | 原文与整理记录都可访问；不同 baseline 可能不对等              | 明确 archive-access／retained-only；统一合法前缀     |
| **检索强度差异**    | 真 BM25、reranker、多范围等新改进可能只进入 candidate     | 共享检索底座；改变候选选择时单独报告                         |
| **实际计算不一致**   | 相同上限不等于相同 tokens、calls、reranker candidates | 记录累计实际用量；做 matched-cost 与 Pareto 两种比较      |
| **信息量与表示混淆**  | candidate 有明确情境，baseline 没有                | 同信息 flat-text 对照                           |
| **Host 能力**   | 读到原文仍错，memory 效应可能被推理瓶颈掩盖                  | oracle evidence／oracle card；第二模型家族         |
| **Judge 偏差**  | 当前 Host 与 Judge 同模型                        | MCQ 确定性评分；自由回答增加异家族 judge 和盲审抽样            |
| **重复使用四道开发题** | 迭代可能过拟合少数工具轨迹                              | 冻结开发集；按用户／历史划分未触碰测试集                       |
| **统计非独立**     | 同一历史的多题共享记忆错误                              | 按 user／history cluster bootstrap，不把每题当独立样本 |
| **模型与运行时漂移**  | API 别名、权重、vLLM、量化与 prompt 变化               | 固定模型身份、权重 hash、配置、prompt 与数据 manifest      |
| **缓存不公平**     | 某臂先触发 embedding，另一臂只享受缓存                   | 分列冷启动、复用成本与实际共享花费                          |
| **调参公平**      | MiLAi 反复调 prompt，外部方法用未调默认配置               | 相同开发预算，公开搜索范围与最终配置                         |

附件已承认同模型自评，也明确要求多题共享历史时不能夸大独立样本数量；这些原则需要落实为最终报告，而不只是协议说明。

还有一个必须先修的测量问题：**内层 VERSION_CONFLICT 可能被记为成功操作。**在这个问题修复前，不应发布“更新成功率”或“工具成功率”的效果结论。

### 成本必须按生命周期算

对同一历史服务 \(N\) 次任务，比较：

$$
\overline C(N)
=
\frac{C_{\mathrm{build}}+C_{\mathrm{maintenance}}}{N}
+
C_{\mathrm{query}}.
$$

若比较 memory 与 raw retrieval，在查询成本差为正时，可以计算建库成本的摊销临界点；若 memory 查询也更贵，则不能靠“以后多用几次”自动摊平。

附件旧版本记录了摄取 **6,713,570 tokens**、答题 **903,206 tokens**，两者均包含 embedding；它们既不是纯 Host tokens，也不是当前 v3 的成本证明。

这些数字不足以推算美元费用，但足以支持一个执行顺序判断：**先做成本分解，再扩展实验矩阵。**

# 十、Minimum Publishable Version

这里的“minimum publishable”是形成完整证据链的最小方案，**不是承诺达到某个会议录用门槛**。

## Method

建议只保留：

**来源引用＋条件性理解记录＋明确的局部修订规则＋最小任务适用性选择＋共享强检索底座。**

其中局部修订规则必须比“让 Host 自行决定”更明确：新信息影响哪个主体、哪类情境；什么只进入 task overlay；什么修改 durable record；怎样保留未受影响条件。

暂时不把 H1、独立 Attention controller、跨查询多视图账本、复杂 handoff、平台级遗忘保证都作为论文贡献。保留必要工程保护，但不围绕所有功能各写一个 claim。

## Benchmarks

**最低两个公开任务集＋一个成对机制诊断。**

我建议主线使用 **PersonaMem-v2 的未触碰测试部分＋STALE**；补充成对 scope／persistence 测试。MemSyco 的范围与有效记忆选择子任务应作为相关验证。你已有 LongMemEval-S 适配器，因此它是合适的第三个通用检查，但不应替代针对性更新测试。

若资源只能支撑极少实验，宁可减少泛化声称，也不要省掉“未受影响情境”的测量。

## Models

**最低两个不同家族的 Host。**

主模型跑完整主表；第二家族至少跑 candidate、强 raw retrieval、同信息 flat memory 和最近修订基线。仅换同家族大小主要是规模鲁棒性，不能完全替代跨家族验证。

## Baselines

最低不可省的类别是：

**full-context 参考、rolling summary、vanilla RAG、强 agentic raw retrieval、同信息 flat memory、HiMem 类最近双记忆方法、CUPMem 类修订方法。**

Mem0 是有价值的常用代表性对照；若继续以 State controller 为主贡献，则 MemR3 也变成必选，而不是可选。

## Ablations

最低保留 A1、A2、A3、A4、A7。
如果版本／依赖是核心 claim，再保留 A5。
若不研究材料规划，就不需要为了“系统完整”运行 A6。

## Analysis

至少完成：

**修订适应与附带破坏；错误阶段分解；质量—成本曲线；历史长度／更新次数退化；按历史聚类的置信区间。**

最小证据链应该是：

> 条件性更新会产生范围泄漏
> → 普通追加／整体重写／强原文搜索仍存在该失败
> → 局部修订规则针对性减少失败
> → 同信息、同预算与删除模块后仍能归因
> → 在第二模型和独立历史上成立。

| ----------------------- | ---------------------------------------------------------------- | ------------------------------- | ----------------------------------------------- | -------------------------------------------------------------------- |

## GO

当 E2 的选择性修订收益**胜过同信息简单基线**，E1 确认命中真实瓶颈，而且 E4 至少出现一个有实际意义的质量—成本优势区域时，继续投入。

下一阶段再要求独立历史、第二模型和统计区间确认。

## PIVOT

出现以下结果应改题，而不是继续堆模块：

**Oracle 原文有用，但结构化记忆不比强检索好：**转向检索／材料呈现。
**局部修订有效，State 独立收益为零：**删除独立 controller 贡献。
**只省成本，不提升语义正确性：**转为边界明确的系统效率论文。
**只有 oracle scope 决策有效：**真正问题是 scope inference，而不是存储层。

以下情况足以否定当前核心方案的继续投入价值：

**在专门触发范围变化的任务上，删除核心机制仍基本不变；同信息简单记忆与强 raw retrieval 在相关预算范围内持续占优；即使给正确的条件性记忆也没有可恢复收益。**

但你目前四道开发题没有提升，**还不足以支持 KILL**。它只说明尚未观察到正面证据。

**Summary。**系统包含完整的来源、版本、任务状态、检索、恢复与预算执行链。

**Strengths。**确定性执行与模型语义判断有清晰职责划分；没有把本地版本检查夸大为分布式事务。

**Weaknesses。**原文、当前理解、历史版本与索引可能持续增长；字节预算不是端到端 token 预算；全部原文在答题阶段重新可用；遗忘与旧快照恢复的保证尚不闭合。  

**Questions for authors。**建库成本在多少次任务后摊平？p95 latency 如何变化？更新次数增长后存储与检索成本怎样？为何一个原文搜索 agent 不能获得相同效果？

**Most serious rejection reason。**复杂性增加尚未换来可复现的质量—成本优势，且 agent 实际任务价值不足以由 QA 分数代替。

# 十三、最危险的三个问题

## Risk #1：你的“核心贡献”已经被多篇 prior work 分别或联合覆盖

**为什么危险？**
不是只有“动态记忆”这种宽泛词撞车；临时／持久分流、版本依赖、写入裁决、充分性路由都已有具体操作。换名称无法解决。

**怎么验证？**
把论文 method 压缩成十行伪代码，对每行标注最近 prior work。再问：删除哪一行会失去论文独有的可验证性质？

**怎么修？**
选定一个窄性质，例如“局部修订不干扰其他情境”，围绕它设计明确操作和成对实验。没有独有性质，就按系统／实证贡献诚实定位。

## Risk #2：现有对照无法证明你想证明的机制

**为什么危险？**
分别建库混淆 State；双方都有 Revision 混淆修订；全部原文重新开放混淆长期保留能力。你可能跑完大量题，却仍无法回答“提升从哪里来”。 

**怎么验证？**
先运行共享快照、同信息 flat baseline、受影响／未受影响成对 probe。

**怎么修？**
先冻结因果对照，再扩展 benchmark；将 archive-access 和 retained-only 分开命名与报告。

## Risk #3：强 raw retrieval 或更好的 reader 可能消除全部优势

**为什么危险？**
当前检索底座仍有基础缺口，历史错误又并非全部来自检索。你可能花主要精力完善了一个不是瓶颈的层。 

**怎么验证？**
E1 oracle 分解＋E4 强 raw／成本对照，先于复杂材料账本和全量评估。

**怎么修？**
检索瓶颈就修检索；reader 瓶颈就缩小对 reader 的要求或更换模型；只有成本收益就收敛为效率贡献；持续被简单方法支配则停止当前路线。

# 十四、真正升级问题的三个方向

以下是研究方向，不是已经完成的原创性认证。**建议选一条，而不是全部叠加。**

## 方向一：从“可修订记忆”升级为“具有跨情境不干扰目标的局部修订”

**新 research question。**
一项局部新反馈如何只改变应该改变的适用范围，同时维持其他主体、场景和时间条件？

**当前方法为什么不够。**
`context` 是表达载体，version 是一致性约束；二者都没有定义“允许改变哪些语义”。Host 可以合法提交一个版本正确、语义范围却错误扩大的更新。

**新 insight。**
更新成功不是“新表达被写进去”，而是**目标适应与非目标保持的联合性质**。

**需要的 mechanism。**
让修订提案显式包含：目标主体、受影响条件、变化类型、保留条件。程序执行局部 patch；语义不确定时保留未决或 task-only 状态，不默认覆盖整条 durable record。

目标可表为：

$$
c\notin \mathcal C_\Delta
\quad\Rightarrow\quad
\mathrm{Apply}(M_{t+1},c)=\mathrm{Apply}(M_t,c),
$$

其中 \(\mathcal C_\Delta\) 是变化真正影响的情境集合。这个性质只在 scope 判断正确的前提下可验证，不能靠形式符号掩盖语义判定错误。

**关键实验。**
同一更新后的 affected／unaffected／future-task 成对测试，对照 CUPMem 式裁决、整体重写、追加以及同信息文本。

**与已有工作的区别。**
不能声称首次区分临时与长期；MemSlides 已做。可争取的是**面向记忆语义修订的非目标保持证据**，而非幻灯片制品局部编辑或一般 current-state adjudication。是否形成足够新的操作仍需针对性核查。([arXiv][7])

**实现成本：Medium。**主要成本是清晰的更新语义和可靠标签，不需要先建设完整图系统。

## 方向二：从“减少重复检索”升级为“变化与上下文裁剪下的证据可见性维护”

**新 research question。**
当原文局部被读过、来源后来更新、Host 上下文又被裁剪时，怎样避免把“曾经呈现过”误当成“现在仍可用”？

**当前方法为什么不够。**
相同参数的只读缓存不能表示跨 query 的局部范围、新版本和上下文淘汰；整个 session 排除又可能隐藏尚未读过的必要信息。附件明确还缺少这种账本。

**新 insight。**
材料是否需要重新取回，不应只依赖“历史上读没读过”，还应依赖**当前版本和当前模型实际可见性**。

**需要的 mechanism。**
一个小型账本记录：

$$
(\text{task},\text{source},\text{version},\text{span},\text{visibility epoch}).
$$

以新版本、未读范围和上下文淘汰为明确重新取材触发条件；coverage 仅认证当前可见、当前有效的证据集合。

**关键实验。**
固定候选和 token 预算，组合“同源多范围＋来源更新＋上下文淘汰”，比较 no-cache、seen-session、简单 interval 去重与完整账本。

**与已有工作的区别。**
ReadAgent、TierMem 已有紧凑到原文的访问，ReFind 已有重复访问控制。你的机会不是再次发明缓存，而是证明**某类 memory 特有的可见性错误与一个足够小的修复机制**。([arXiv][21])

**实现成本：Medium。**语义推理需求较低，但必须准确模拟实际上下文裁剪；仅保存“已呈现”日志不够。

## 方向三：从“我的记忆系统更好”升级为“什么时候根本不该构建语义记忆？”

**新 research question。**
原文可用性、用户状态变化频率和未来任务复用次数，分别如何决定结构化记忆相对直接搜索的净价值？

**当前方法为什么不够。**
当前把完整原文访问与语义记忆合在一个协议里，也尚未系统分解建库摊销和更新失真，容易把特定环境下的效果误认为普遍优势。

**新 insight。**
长期记忆的价值可能不是单调随历史长度增长，而取决于三个因素的相互作用：**可重读性、变化密度、复用程度**。

**需要的 mechanism。**
这里不应再增加复杂 agent。需要的是可审计的 archive-access／retained-only 开关、受控更新流、统一预算与生命周期成本记录。贡献重点是**评估协议和经验规律**，而不是把这些开关命名为新算法。

**关键实验。**
在相同基础历史上控制原文访问、更新密度和任务复用次数，比较强 raw、flat memory、代表性结构化 memory 与 MiLAi，寻找优势何时出现、何时反转。

**与已有工作的区别。**
ReFind 已挑战结构化记忆必要性，TierMem 已研究访问成本与回写摊销。你必须新增**连续修订导致的适用性错误与原文访问权交互**，而不只是再报告一次“RAG 也很强”。([arXiv][20])

**实现成本：Low–Medium；实验成本 Medium。**它可能比再构建一个大系统更容易产生清楚、可证伪的科学结论，也允许有价值的负面结果。

# Research Verdict

## 1. 我真正的核心贡献

目前可确认的产出，是一个将来源、条件性理解、版本依赖、任务状态和执行预算接在一起的研究原型；**不是已经确立的新 Agent Memory 范式**。

最值得争取的论文贡献，是证明：**条件性记忆的局部修订能够改善受影响任务，同时保留未受影响情境，并且这种收益不能被同信息简单记忆或同预算强原文检索解释。**

## 2. Nearest Prior Work

最危险的五个对手是：

| Prior work       | 直接碰撞               |
| ---------------- | ------------------ |
| **HiMem**        | 原始经验／持续理解与检索后重整    |
| **MemSlides**    | 持久偏好／临时任务约束分流      |
| **CUPMem／STALE** | 写入时更新裁决、失效传播与后续行为  |
| **Kumiho**       | 固定版本、类型化依赖、影响分析    |
| **TierMem**      | 来源链接、充分性判断、原文展开和回写 |

这些碰撞针对方法骨架；**MemR3 是 State 主线的直接对手，ReFind 是系统必要性的直接对手。**([arXiv][6])

## 3. Novelty

**并不新：**动态记忆、条件字段、来源与摘要分离、版本历史、反馈修订、GAP 检索、批量写入、紧凑到原文展开。

**可能形成贡献但尚未确认：**一个明确的局部修订操作及其跨情境不干扰证据，或一个针对版本变化与上下文淘汰的最小证据可见性机制。

当前最合理定位是 **engineering integration，有望收敛为 meaningful extension 或实证／系统论文**。

## 4. Feasibility

完整路线工程复杂度高，且 formal evaluation 持续后置会增加做完系统仍无论文证据的风险。附件当前仍只有四道固定开发题，没有正式全量效果或泛化结论。 

收敛为“条件性局部修订＋强检索＋受控评估”后，工程上可行；精确算力与费用仍取决于尚未提供的硬件、历史复用和实际模型调用数据。

## 5. Evidence Gap

最缺的三项证据是：

**同信息简单基线之上的机制收益；修订目标改善且非目标不退化；包含建库与更新的同预算质量—成本优势。**

## 6. Reviewer Attack Surface

最容易被攻击的三个点是：

**最近 prior work 碰撞；State／Revision 归因不成立；弱检索或额外计算制造表面提升。**

## 7. Best Paper Framing

建议 framing：

> **Scope-Preserving Revision for Personalized Agent Memory**
> 研究长期个性化记忆如何在接受局部新反馈时，实现目标适应而不破坏其他适用情境。

这个 framing 不是靠标题获得 novelty。它要求 method、指标和实验全部围绕**选择性适应**展开，不再把系统所有功能一起称为贡献。

## 8. Minimum Experiment Package

**两个公开任务集、一个成对机制诊断、两个模型家族；强 raw、同信息 flat memory、最近修订方法；五个关键消融；历史聚类统计与生命周期成本分析。**

若保留 broad agent learning claim，再补实际连续工具任务；否则应明确限定为 personalized conversational memory。

## 9. Next 3 Experiments

**第一，Oracle 证据／条件卡分解。**先确认 memory 层存在可恢复空间，避免把 reader 错误当成记忆问题。

**第二，局部修订的成对反事实测试。**同时测目标适应与非目标保持，这是最有机会形成科学结论的一步。

**第三，同预算强原文检索对照。**检验系统是否真的必要，并把所有额外调用纳入成本。

**最终判断：不建议继续按“补齐 MiLAi 全部架构功能后自然形成一篇新范式论文”的路线投入。建议立即转入上述三个证伪实验；只有选择性修订的独立收益站得住，再扩展系统与论文。**
