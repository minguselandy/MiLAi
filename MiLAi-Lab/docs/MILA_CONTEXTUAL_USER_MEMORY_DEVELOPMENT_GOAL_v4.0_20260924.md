## 4. 摄入协议：降低表达负担，保留准确来源与恢复

### 4.1 程序提供句柄，Host 表达操作

摄入材料同时发布一个小型句柄表，绑定已经交付的来源、准确范围或旧记录版本。Host 只选择句柄、局部新对象别名、操作和必要语义内容；转换层还原现有内部类型。短句柄只简化传输，不改变支持组的 AND／OR 语义。

- 来源句柄绑定原始身份、真实角色、版本／内容散列和实际交付范围。目标句柄绑定 Host 看到的记录版本；不要求模型重复长 ID、身份元数据或手写 `start/end`。
- 句柄随该批材料冻结，恢复时仍能解析到同一版本和范围。未交付范围不可引用；未知句柄报错；不存在“找不到就使用整份来源”的回退。
- 需要更细范围时由材料接口发布准确摘录。首版不强制逐句分类，不要求 Host 再抄一遍原文，也不强制每份独立想法具有外部支持。
- 不用短语法隐藏实际操作数。新理解、支持、撤回和 review 仍计入提交与容量统计；不把机械装配工作伪装成模型完成的新推理。

### 4.2 按错误类型处理，不建立统一重试循环

| 失败 | 处理 | 保留的行为 |
| --- | --- | --- |
| 输出截断／JSON 不完整 | 保留原始回执，标记该提案未提交；调整后续容量或显式重做该批 | 不执行前半段，不补猜剩余操作 |
| 集合字段出现完全相同引用 | 仅对已声明为无序集合的字段稳定去重，记录规范化前后差异，再做最终校验 | 操作序列、依赖顺序、不同范围和不同版本不去重 |
| 来源范围越界／句柄未知 | 拒绝受影响提案或局部组，报告实际原因 | 不裁剪、扩大范围或伪造来源 |
| 版本冲突 | 标记同批重复修改、旧快照或先行操作导致的版本变化，交付当前真实状态供重新判断 | 不改成最新版本后强制覆盖 |
| 局部组失败 | 保留成功组及回执，失败组保持未完成 | 不回滚其他已提交组，不把部分成功报告为全部完成 |
| 相同历史构建失败 | 复用现有构建一次和向 probe 传播失败的逻辑 | 不为每问重新调用摄入模型 |

解析与规范化集中在外部提案入口；内部函数使用已解析类型。不在每层重复校验，不增加宽泛异常吞噬或失败后默认成功。

保持当前提交粒度：ordinary 以单操作、support／events 以现有局部组为单位记录结果。不为统一回执而承诺整批原子提交，也不将多个成功操作误计成一次全部成功。

### 4.3 分批按请求容量，而不是只按字符数

单次请求应满足：`已序列化输入 tokens + 预留输出 tokens ≤ 固定模型上下文容量`。输入包括系统指令、schema、当前历史、旧记录、来源材料和聊天模板，不能只算新消息正文。

1. 使用已固定的 Host tokenizer／聊天模板在本地计数，记录计数身份与预留量。与服务端模板存在差异时明确保留余量和误差，不能把 UTF-8 字节估计称为实际 tokens；费用预算和上下文容量是两个约束。
2. 先保留消息／会话边界和时间顺序，再按旧记录、支持项及预计操作输出选择批次。首版使用固定规则和少量参数，不训练分批器。
3. 过大的单条消息不得丢弃或静默截断。优先通过已有准确范围材料分段交付，绑定同一原始事件及完整覆盖记录；做不到时明确停止为未完成，不能伪造完整摄入。
4. 分批及提案输出上限一起冻结；统计实际输出与预留偏差。缩小尚未执行的批次必须留下新边界与原因，不重建已成功前缀。
5. 机制比较使用相同历史边界。需要按运行时旧记录负担调整时，配对臂使用共同可容纳的边界；无法做到就将结果降格为不同分批的系统比较，不能单独归因机制。
6. 摄入不能看到未来问题或 gold。不能为了制造修订机会，刻意先让 Host 形成错误理解；同批已有早期要求与澄清时，直接形成正确理解是合法结果。

### 4.4 四种进度分开，恢复只补未完成工作

| 进度 | 精确含义 | 不代表什么 |
| --- | --- | --- |
| 来源接收 | 哪些原始消息／范围已保存，合法前缀到哪里 | 已完成理解或已建立支持 |
| 提案有效 | 哪个冻结输出通过解析、规范化和结构校验 | 其中每组均已提交 |
| 局部提交 | 成功组、对象／版本、别名映射和失败回执 | 整批维护完成 |
| 本批维护结清 | 没有未处置的协议失败／未提交操作；语义待复核另列 | 所有理解必然正确，或争议已经消失 |

复用现有 checkpoint 和原子文件写入，在同一恢复边界保存对象状态、批次／提案／组身份及回执；不另建事务服务。准确的别名映射要能跨成功组恢复。已冻结的有效提案优先重放未提交部分，不因恢复而再次请 Host 生成一遍；已提交组不重复创建对象。

故障恢复必须演示：第一组提交、第二组失败或进程中断后，能够定位持久化边界，恢复不重复对象、不跳过未完成部分。没有持久化成功证据的变更回到相应 checkpoint 处理，不能仅凭日志中的“开始提交”认定成功。远端请求是否已计费与本地对象是否已提交分开；无法确认的 usage 保持 unknown，不承诺网络请求恰好执行一次。

允许有明确原因的 `unresolved` 语义待复核，但它不得掩盖截断或未提交操作。完整场景执行验收要求来源覆盖完整、协议／提交故障结清；剩余语义未决项须被材料正确表达，单独计数，不能据此宣称全部语义维护成功。

旧 v6 部分进度只作诊断输入，不按新字段含义静默恢复。协议和 checkpoint 身份变化后用新运行目录，从合法原文重建；不迁移旧运行结果。

## 5. 被动条件上下文：不依赖主动 State

新增或收拢一个最小 `QueryContext` 值对象，在 `start_task` 后建立，由 search/read/支持适用性及材料组装共同使用。实现可复用 TaskState 存储，不需要第二套长时记忆或新的 Agent。

| 信息 | 来源与处理 |
| --- | --- |
| 用户、任务身份、合法历史前缀 | runner／可信适配器确定；与评分字段隔离 |
| 当前问题与明确要求 | 原生用户可见输入，保留原文 |
| 原生时间、明确主体／场景条件 | 数据确实给出的元数据，或 Host 从当前可见要求提出并关联出处 |
| 需要推断的条件 | Host 当前调用显式提出，标记为推断；不伪装成用户声明 |
| 缺失或相互冲突的条件 | 保持未知／争议，不能自动补为全局成立 |

纯文本问题中的语义不通过关键词规则“可靠提取”，也不额外调用一个分类模型。先注入程序可确定的上下文；Host 在既有 search/read 调用中可附上必要条件及其依据。条件键沿用已交付记录或明确约定，避免记忆和查询使用彼此不可比的任意别名；程序核对引用与类型，不认证推断为真。

原生事件时间与系统 `known_at` 的含义分开。问题日期不能直接替代系统获得记录的时间；合法历史前缀也不依靠篡改时间字段来实现。每问从同一历史快照的独立副本开始，当前条件不污染其他问题或耐久偏好。

**验收：**对同一条条件性理解及相同支持，明确匹配、明确不匹配、缺少条件分别产生可解释的 `USABLE / UNUSABLE / PENDING` 适用结果及原因；汇总同时保留无支持、冲突等其他状态，不能只报 USABLE。该能力在 `contextual=False`、工具中没有 `memory_state` 时也成立。

被动上下文及共同的条件表达对 ordinary 和候选一致。主动 State/Attention 的查询策略控制继续作为独立开关，本轮不新开其效果比较；基础条件修复不能被表述为主动控制方法收益。

## 6. 任务完成、差量交付与成本

### 6.1 所有臂共享任务边界

共享 Host 指令统一表达以下规则，并产生新的提示身份：

> 用合法记忆确认用户过去的信息和当前适用约束。当前请求允许提出建议时，可以依据这些约束生成新建议，但不得将建议冒称为用户过去经历、已认可的决定或历史事实。完成任务所必需的具体事实缺失时，说明缺口；不要仅因历史没有现成答案而拒绝。历史事实问答仍只能依据取得的材料回答。

规则由当前用户问题决定是否适用，不按 benchmark 名称或 case ID 切换。ordinary、原文检索和候选同时使用；原生 Judge rubric 不改，不增加一个更宽松的候选专用 Judge。

结果分别记录：Host 是否正常返回、答案能否原生评分、偏好／约束是否正确使用、任务是否完成。后两项使用原生维度或对暴露答案的人工诊断，不能伪装成数据集新增金标。成功结束工具循环不等于用户任务完成。

### 6.2 差量先查关系新鲜度

在现有 delivery 用例补一个必要情形：来源正文、版本和范围未变，但支持撤回、关联更正或任务适用性改变；再次读取必须交付新的状态，旧正文仍可按驻留条件省略。覆盖材料组装到交付的实际链，不只检查 ledger 的孤立字段。

若现有保留元数据的逻辑已经满足要求，保留实现和该窄回归；失败时只修复视图重算或相关修订失效键。不建立复杂全局账本，不因形式上正文仍在 transcript 就认定模型必然正确使用，也不因一次答案变化就断定差量是因果根源。

### 6.3 成本口径与可行动记录

| 阶段 | 本轮最少记录 |
| --- | --- |
| 摄入 | 输入／输出 tokens、请求、截断与结构拒绝、失败输出、成功操作／组、未结清部分 |
| 作答 | 请求及输入／输出 tokens、重复无新信息的工具轮次、退出原因 |
| 材料 | 正文、引用／状态元数据、关联更正的 token 规模；分项按固定 tokenizer 计量，不冒称严格可加 |
| 评分 | Judge 模型、请求、输入／输出 tokens、有效评分分母 |
| embedding | 请求、tokens、缓存命中；共享缓存实际成本与独立启动估计分开 |
| 本地执行 | 提交／复制、检索、组装的测得耗时；复制对象规模和触及对象数 |

使用现有 trace 增补少量字段和汇总函数，不建设遥测平台。Judge 属于离线评测成本，部署查询成本单列；输入加输出不可标为“仅输出 tokens”。跨模型 tokens 可作为分模型资源账，但没有价格或硬件测量时不声称精确费用。所有失败请求和 unknown usage 保留，不因没有分数从成本分母剔除。

H5 继续是可选工程策略。本轮不重复其确认实验；先解释支持记忆为何多次搜索／读取／作答。旧确认中差量相对支持全文省约 10.8% 作答 tokens，却从 3/4 降为 2/4，独立生成 tokens 仍比 ordinary 高约 47.5%；不能改写成总体效率已成立。

## 7. 机制可达性与研究问题收敛

### 7.1 五环节 trace，不增加分析 Agent

| 环节 | 所需证据 | 断点说明 |
| --- | --- | --- |
| 机会存在 | 合法历史确有相关变化；需要修订的旧对象当时已提交 | 没有机会／同批首次整理已吸收变化／旧对象尚不存在 |
| 材料可见 | 新来源和准确旧对象实际交给 Host | 未检索到／未展开／预算排除／条件未知 |
| 操作提出 | 原始提案含该机制的语义操作 | 只新增叙述／无修改需要／模型未表达 |
| 提交成功 | 回执及前后对象、支持或时间状态改变 | 结构拒绝／范围错误／版本冲突／仍待维护 |
| 后续使用 | 新状态进入后续材料，答案与之相符或明确不采纳 | 未再读取／材料陈旧／已见但未用／无法判定 |

机会审计基于合法历史及已经暴露的 trace，不读取正确答案来制造运行时条件。人工标注与运行输入隔离。最后一环不能只因出现一次 read 就自动记为成功；给出相关材料和答案片段，证据不足记 unknown。人工诊断不需要额外 LLM Judge，也不等于因果收益证明。

每环报告分母：适用机会数、其中可见数、提出数、成功数、可证实使用数及 unknown。不能将“不适用”计作机制失败或成功。

### 7.2 六候选的新定位

| 候选 | 本轮定位 |
| --- | --- |
| H1 支持保留修订 | 优先审计真实替代支持及局部撤回机会；没有多支持／撤回链就不能认领保留收益。已有 4/4 对 2/4 的系统退化继续保留 |
| H2 更正关联读取 | 既有证据只支持“关联材料读取”；确有旧解释及后来更正才进入机制比较 |
| H3 有界影响维护 | 暂停效果比较；只处理共享摄入／上下文中阻断执行的问题 |
| H4 事件区分 | 审计事件是否可见、旧对象是否存在、操作是否可表达；不直接再跑分数比较 |
| H5 差量交付 | 保留可选入口和关系新鲜度窄检查，不作为主要创新或默认 |
| H6 原文重整理 | 视为摄入协议压力路径；不以未完成长历史推断收益 |

本轮只保留一个可被反驳的研究问题进入验证包 C：**相同合法信息、记录粒度和可比预算下，选择性维护支持或读取当前更正，是否比直接检索原文、普通更新更能完成任务，额外成本是否值得？**

已有来源追溯、统一工具、版本和支持图不重新宣称创新。新增贡献只能来自实际触发、明确对照和质量／成本结果；没有真实机会时承认当前样本未覆盖，不扩候选掩盖问题。

## 8. 结构整理与高效开发约束

### 8.1 沿状态所有权做小幅收敛

| 当前位置 | 本轮收敛方向 |
| --- | --- |
| `methods/contextual_user_memory.py`、`contextual_memory/store.py` | 明确来源／版本存取、支持关系及任务上下文的所有者；先抽取修复需要的窄读写方法 |
| `contextual_memory/revision.py`、`materials.py`、`retrieval.py` | 通过需要的接口读取状态，限制跨模块直接修改；不将全部字段搬进一个任意可写的巨型 State |
| `runners/contextual.py` | 历史构建、单 probe、冻结评分及汇总形成独立可调用单元；只在真实职责稳定后移动文件 |
| `runners/contextual_ingestion.py` | 一处负责请求材料、句柄转换、解析和提案回执；不复制一套恢复循环 |
| `harness/contextual_artifacts.py` | 复用原子写入、预算和 trace；容量规划与消费账分开 |

先给当前局部提交加轻量计时。只有本轮真实 workload 表明复制成为显著耗时／内存负担，才比较受影响对象提交或撤销记录；否则保留现有深拷贝。无收益的结构移动、空转发层和预留扩展框架不做。

### 8.2 有限并行与模型分工

沿用用户指定档位：Sol xhigh 负责常规实现与集成；Luna max 处理窄范围源码核对、失败分类、文档／汇总等任务；Astra xhigh 只处理已定位但常规实现无法解决的语义或恢复难题。不是每个改动都经过三个模型。

需要并行时，一名集成者维护核心接口，至多两个互不写同一文件的窄任务；例如只读旧 trace 分析可与独立 QueryContext 设计并行。协议、恢复和 runner 的依赖改动顺序集成。共享接口由负责实现者直接决定，不增加常驻审核 Agent、轮流审查或形式审批。

参考源码已在本地，继续复用已固定的 ReFind、ReMe、OpenViking 及其他参考项目清单；只在修改对应机制前阅读相关实现和记录差异，不重新下载整套项目，不引入外部框架作必要运行依赖。

### 8.3 检查保持必要且窄

优先复用现有 ingestion、revision、runner、delivery、budget 定向用例。仅补 benchmark 无法可靠观察的边界：集合去重／准确句柄、同批冲突、部分提交恢复、三态条件、关系变化后的交付。不要为每个辅助函数新增镜像测试，也不建大型故障注入矩阵。

运行受影响文件的静态检查和相关窄测试；移动包代码才运行依赖边界检查，修改打包才构建包。修复后通过的检查不反复扩大重跑，除非新改动或新失败需要。

保留三个能力边界：材料预算明确限制正文还是完整回执，极小预算不声称任意字节严格满足；英文结果不支持中文词法质量保证；删除仅覆盖声明的本地受管范围，不宣称清除了其他目录、冻结答案和远端请求。对本轮修改触及的边界做窄检查，不升级为生产治理工程。

保留实际的 archive-backed 使用条件：当前作答可检索完整合法原文，不把结果描述成只依靠压缩记忆的能力。所有臂得到相同合法信息，raw 不能被人为削弱；当前问题和 gold 不参与历史整理。
