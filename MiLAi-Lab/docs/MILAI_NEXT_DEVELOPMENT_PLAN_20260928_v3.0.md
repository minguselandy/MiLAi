## 2. 结果基线：哪些是确定事实，哪些不是

### 2.1 N2：小 bank、历史充分时，复杂读取没有额外收益

| 方法 | 最终回答 | 生成调用 | 生成 tokens | Embedding tokens |
| --- | --- | ---: | ---: | ---: |
| full_history | 2/2 | 2 | 1,836 | 0 |
| query | 2/2 | 3 | 3,189 | 387 |
| all | 2/2 | 3 | 3,447 | 0 |
| query_enhanced | 2/2 | 5 | 3,889 | 433 |
| a_selector | 2/2 | 6 | 5,540 | 0 |

这是两个相关、已暴露前缀的固定 bank 比较，不是五种方法统计等价。共同合法历史已提供答案；候选 ID 覆盖、工具读取次数与答案收益不能互相替代。A 的一次对象类型误用仍保留，不因最终答对而擦除。[S2]

### 2.2 N3：正文正确、来源绑定与总成本必须分开

| 方法 | 正文＋无关保持 | 显式来源绑定 | strict 联合 | 生成 tokens |
| --- | --- | --- | --- | ---: |
| all | 2/2 | 2/2 | 2/2 | 1,846 |
| U | 2/2 | 1/2 | 1/2 | 2,110 |
| U=A | 2/2 | 2/2 | 2/2 | 2,466 |
| oracle U | 2/2 | 1/2 | 1/2 | 1,386 |

all 是本轮非 oracle 可执行方案中，严格质量完整且总生成成本最低的方案。oracle U 是诊断 mask，不是可部署方法。U 维护段少用 472 tokens，但 selector 多用 736，净增 264。空 U 没有阻止 CREATE；缺口是创建时漏了显式证据字段，不能称为没有创建或选错旧对象。[S3]

### 2.3 N5：业务完成不代表持久记忆闭环成立

| 工作负载 | H_shared | all_shared | 正确解释 |
| --- | --- | --- | --- |
| 原生 MERIT 五 episode | 5/5 | 5/5 | 普通 memory 与 State 均全程为空；完整合法历史支持业务 |
| 构造长期计划初次形成 | 0/2 | 0/2 | 明确保存要求未转化为实际记录 |
| 构造提醒形成 | 0/1 | 0/1 | 后续删除缺少真实目标，上游链已断 |
| 严格完整生命周期 | 0/1 | 0/1 | 不能被业务或恢复正确补成通过 |
| 真实业务与闭合回合后恢复 | 限定通过 | 限定通过 | 同一真实预约可读回，无重复动作；不是任意崩溃保障 |
| State 正文预交付对照 | 未激活 | 未激活 | 不是“State 有效”，也不是“State 被证明无效” |

all_shared 曾把单轮 TEMP 格式带入下一轮；没有持久 TEMP 记录，不能归因于 State 写入。其普通计划在业务成功后仍写“Nothing is reserved”，恢复时继续交付；最终回答却使用真实工具结果答对。H_shared 有未写入却声称计划仍已保存的行为。[S4]

### 2.4 结论边界

原生零记录不自动违反原生任务；明确要求长期保存的构造任务，零记录就是未履行该要求。对删除应记录“形成失败导致未覆盖”，而不是“无可删即删除成功”。空 State 臂的天然措辞与 UUID 差异不构成 State 效果。

N5 六条命令全部完成是执行事实；其中的消息和两个实验臂不是独立场景数。闭合 checkpoint 后重开进程，不等于在未确认外部副作用时安全重放。

## 3. 首断点与竞争解释

| 现象 | 已支持的首断点 | 尚未区分的解释 | 下一最小动作 |
| --- | --- | --- | --- |
| 明确要求记住却仅确认 | Host 未提出持久写入；Store 为空 | 完整历史替代感；多工具选择负担；维护职责弱于业务职责 | 在新冻结小任务上比较普通工具路径、明确职责路径和轻量完成反馈 |
| TEMP 延续 | 下一轮答案没有遵守单轮范围 | 近期助手格式复制；未正确使用用户限定 | 独立作用域反例；不新增永久 TEMP 状态或删历史 |
| 预约后旧断言保留 | 实际业务回执已交付，但未修订普通记录 | 把计划视为静态资料；以业务答复为回合终点 | 同一事项真实结果后的维护检查，保留已成功业务 |
| 声称 saved 却无记录 | 回答措辞与实际操作不一致 | 把 checkpoint 历史或口头确认当作保存 | 用实际提交支持报告，仍单独评估正文 |
| State 从未形成 | 没有可供预交付的 State 内容 | 当前任务不需要它；工具分工不清；写入策略没有履责 | 不强制造 State；先建立普通持久闭环 |
| oracle 也漏来源字段 | 提案缺少显式绑定，非 Store 丢字段 | 共享输出合同或空候选形式影响表达 | 若真实使用确受影响，单独修共同字段合同；不训练 selector |

**本轮未发现足以解释上述失败的漏消息、Store 未执行或业务回执未送达证据。**不得为了继续开发而假定一个没有依据的底层 bug。选定源码显示，N5 复用了 `SYSTEM_PROMPT` 和 `host_both` 的责任说明，提供两类记录工具；这些内容的存在不证明模型已经掌握语义责任，也不能被简化成“完全没有提示写入”。[S4][S7][S8]

## 4. 下一阶段问题与可证伪假设

### 4.1 开发目标

> 在完整 CRUD、真实来源和实际业务工具均可用的情况下，让 Agent 用最少必要步骤兑现明确的记忆要求，保持当前与长期范围不同，并在后续会话使用实际保留的正确内容。

“至少一种持久表示可用”可以满足用户需求，不强制普通 memory 和 State 双写，不要求固定卡数，也不把所有 user 消息复制到长期库。

### 4.2 三个假设

- **H-F（形成）：**明确且统一的写入责任与结果表达，可能降低“口头确认但未保存”，且不增加临时信息或引用内容的误存。
- **H-M（维护）：**同一 ReAct 循环能在真实新结果到来后对相关持久事项作最小维护，而不重做业务、不覆盖无关事项。
- **H-R（使用）：**在真实会话切换及合理的信息访问边界下，实际保留的内容能支撑后续任务，而不仅依赖完整聊天重放。

State–Attention 的新研究假设暂不进入必需实现。只有 H-F/H-M/H-R 出现足够的投入信号，且有实际的读取或更新瓶颈，才重新研究 A/U 或稀疏工作视图。

### 4.3 不能预先认领的结论

本版没有确立新的算法创新；没有证明单写者必然优于双写者；没有证明“加一个终结字段”能解决语义形成；没有证明长上下文是失败原因。任何新闭环都首先是工程／策略候选，性能变化必须与同信息、同提示和可比预算的强简单方法比较。

## 5. 保留的底座与主动不做的事

### 5.1 保留

继续复用现有 LangGraph ReAct、LangMem/strict 工具、owner namespace、Store、公开 checkpoint、实际来源、版本与真实业务日志、原生评分、冻结和连续计账。严格 UPDATE 的已有对象检查、缺失/null 正文零写拒绝、真实错误回执和既有部分成功边界继续有效。[S5][S7][S9]

ordinary memory 作为最小路径的持久内容入口。多局部 State、普通 patch、全读和普通 query 保留为可开关能力与历史对照。新方案不迁移旧库、不改变 Product/Archive。

### 5.2 不做

不重建 Agent runtime；不新增全库依赖图、第三份“最新事实库”、全局仲裁器、常驻审核 Agent、夜间反思服务或学习型 selector。不要通过新增一套 journal 宣称任意跨存储原子性；不要把代码拆文件作为算法进展。

不恢复旧 v8 的重型逐来源 `saved/no_change` 归组或强制全文审阅流程。历史版本可以说明这种合同曾被实现，但不能作为当前 LSA 的默认成功方案，也不能混用其模型和运行数据。

不要求每轮调用 State、每项内容双写、每次工具回执都持久化。对模型未识别的语义要求，不用服务端关键词规则、题号分支或 gold 标注自动补上。

不部署第二模型，不修改共享 vLLM/parser/thinking/容量，不开启后续参数矩阵。确需改变其中一项时，另立明确的实验身份与资源范围。

## 6. 建议的最小机制：同一 Host 的记忆责任与真实结果对齐

本节是待实现候选，不是当前源码事实。工作名称只用于区分实验臂，不作为 novelty 主张。

### 6.1 先建立强普通对照，再增加一个窄候选

| 实验臂 | 固定共同部分 | 独立变化 |
| --- | --- | --- |
| **B0：普通工具式记忆** | 相同 Host、strict CRUD、来源、业务工具和历史访问协议 | 普通自然 ReAct，直接使用记忆工具 |
| **B1：明确职责的普通 ReAct** | 与 B0 相同 | 一份预先冻结的通用责任说明：明确保存须真实持久化，临时要求不得长期化，已知当前断言变化后需维护或如实说明未完成 |
| **C：轻量结果闭环** | 与 B1 的语义说明、输入和 CRUD 相同 | 在现有最终响应中表达一个简短记忆结果；程序只核对其操作依据；允许至多一次有界纠正入口 |

B0/B1/C 初步均使用普通记忆入口，不默认预交付 State，不启用独立 A/U 或自动边界写入。关闭第二类工具本身属于系统设计差异；若与旧 N5 比较，必须另列桥接实验，不能将旧双库结果与新单库结果相减后归因于 C。

B1 必须是足够强的普通对照，不故意写弱提示。预先冻结一份通用说明，不围绕已暴露的 Riley/TEMP/金额继续调措辞。若 B1 已解决问题且比 C 更简洁，采用 B1，并停止 C 的方法优越性主张。

### 6.2 C 的输出不复制长期事实，也不要求逐来源填写报表

建议在既有终答 envelope 中使用一个小字段；名称与最终 schema 可在实现前定稿：

```text
memory_result:
    status = committed | no_change | unresolved
    receipt_refs = 本轮真实记忆操作回执引用，必要时为空
    note = 简短理由或剩余问题，可省略
```

这些不是新记忆正文、不是第二份事实状态，也不新建永久责任数据库。优先利用现有 tool_call_id、回执和 scope；确需附加映射，只保留本轮必要信息。

- `committed`：实际发生了对应的持久操作；引用必须属于当前 owner 和合法执行。它不认证内容正确、不证明覆盖全部要求。
- `no_change`：本轮未选择持久变更。可以合理，也可能错误；是否履行用户请求由独立评分判断，不由程序自动放行成语义成功。
- `unresolved`：存在尚未完成的维护、缺信息或真实操作失败。任务已完成的部分保持，不把它伪装成全部完成。

已经存在等价正确记录时可以不新增，但若声称“已保留原约定”，应有可核对的已有记录读取或实际前态依据，而非凭助手旧话语推断。首版不对任意自由文本做正则“saved”审查；结构化结果和自由回答不一致仍列为失败，不篡改输出修分。

### 6.3 程序核对与语义判断严格分开

程序可以核对：回执是否真实、目标是否存在于合法 namespace、操作是否提交、结果是零写/变化/部分完成、哪些业务副作用已经发生。

程序不能仅凭这些字段判断：用户确实需要保存什么、正文是否充分、某个 source 是否支持全部概括、`no_change` 是否符合用户原意。不得自动把完整新消息补成 memory，也不得把保守输入依赖当作模型建立的语义依据。

C 的最大失败模式是模型把明确保存错误归为 `no_change`。出现时应保留失败，说明“真实回执闭环”只减少假报告，尚未解决操作选择；不能继续加一层自动分类器将它隐藏。

### 6.4 有界纠正，而不是强制完成循环

仅在候选 C 声明了需要继续维护，或结构化完成声明引用了不存在/失败的回执时，提供一次同 Host 的纠正入口。该入口包含实际新观察、相关当前记录和已发生回执，仍使用既有 CRUD。

该入口不独立开审核模型，不重发用户业务请求，不开放再次执行已完成业务。可在剩余原工作流调用容量内读取并维护；再次结束仍不完整就返回真实未完成。它是至多一次重新进入维护流程，不是“每失败一次再重试一次”的无限循环。

纠正前后的全部调用、tokens、工具及 Store 开销计入 C。给 B1 同等最大调用能力，并另报告允许 B1 利用相当预算正常回看／复核的比较；不能把更多计算直接算成闭环机制收益。

### 6.5 完整增删改查的含义

| 输入情况 | 合理行为 | 禁止的替代 |
| --- | --- | --- |
| 新的明确长期约定 | CREATE 或在确属同事项时 UPDATE | 仅确认；无依据复制两库 |
| 同事项真实变更 | 原目标更新，保留仍有效部分 | 相似话题全部改成最新一句 |
| 当前任务查阅 | SEARCH/READ 或已有材料足够时直接回答 | 为证明机制使用而额外写入 |
| 明确本轮临时要求 | 当前任务内使用 | 自动升级为永久偏好 |
| 明确删除已存提醒 | 定位实际已存目标并按授权退出 | 用删除整个 owner 历史代替；无目标即宣称完整生命周期通过 |
| 业务成功/部分成功 | 依据真实结果判断是否维护当前断言 | 把工具 status=success 等同于全部业务成功 |
| 没有新的复用信息 | no_change | 强制生成一张新的核实总结卡 |

“提醒记录”在本研究中只表示持久备注，不自动表示已经设置定时通知或日历事件。实际预约/退款状态必须以真实业务工具为准；记忆保存成功不产生这些外部动作。

## 7. 两种使用协议必须分开冻结

### 7.1 Archive-access：完整合法档案仍然可用

所有方法都可以通过相同规则使用当前 owner 已访问的合法历史；明确是内联还是工具检索，两者不能混写。该设置评价记忆整理是否提供质量、延迟或成本的额外价值。

原生 N5 的短任务在这种设置下不形成专门记录也能通过，这是有效结果。不撤销其 5/5，不通过删除必要历史重新计算旧分数。若新任务明确要求持久保存，仍单独评价是否兑现该要求。

### 7.2 Retained-memory：会话切换后只用实际保留内容

新会话获得当前请求、正常业务工具和各方法在前序阶段真实持久保存的材料；旧 checkpoint 不通过内联、`read_history`、摘要缓存或后台索引偷偷回流。运行器可以为审计保留完整历史，但 Host 的信息权限必须与审计权限分开。

这一设置不是为了给候选制造优势，应作为事先声明的使用合同共同施加于全部实验臂。跨会话状态查询工具保持相同；不能仅为候选保留正确业务结果。

强原文方法允许明确保存原始观察，并从其持久档案检索；这也是合法记忆策略，其保留、索引、查询和存储成本全部计入。不能禁止 baseline 存原文，再声称结构化记忆不可替代。

### 7.3 两种协议的共同边界

- 同一任务的原始输入、消息顺序、业务世界和评分规则不变。原生 benchmark 若有指定历史协议，主成绩遵守原协议；额外 retained 条件标为新协议诊断。
- 不因为形成失败，操作员事后补种正确记录；后续因上游失败无法完成，应保留整个生命周期失败及其首断点。
- 不人为隐藏工具可以合法查询的当前业务状态。若业务查询已经足够，承认该环节没有证明记忆必要性。
- 真实用户偏好、未执行的项目约定等不能从业务查询恢复的信息，才可能直接检验跨会话保留；不能把目标答案临时注入运行器。
- 两种协议的结果分表，不合成一个“总体准确率”；同一基本任务在不同协议中的路径也是相关样本。

## 8. 工作包与阶段依赖

新编号使用 **P0—P6**，不覆盖原 N0—N6。默认只推进到当前门槛允许的最小切片。

| 包 | 类型 | 核心交付 | 进入下一步的条件 |
| --- | --- | --- | --- |
| P0 | 只读核对与协议冻结 | 基线、来源、代码路径和测试集合 | 当前事实清楚；没有把已完事项重新开发 |
| P1 | 最小候选实现 | B0/B1/C 配方与共用结果记录 | 窄测试通过；候选没有副作用伪造或隐藏调用 |
| P2 | 形成与非误存诊断 | 从空库开始的小规模真实 CRUD 路径 | 至少有可解释的实际形成信号，且负例没有明显被破坏 |
| P3 | 生命周期验证 | 形成→变化→使用→退出→恢复的连续任务 | 能区分任务、记忆与维护结果；不拼接局部成功 |
| P4 | 独立确认与成本 | 少量未用于调试的任务族及相同计算对照 | 收益超出提示、工具简化或额外计算的解释 |
| P5 | 条件性 State–Attention 再准入 | 固定 bank/前态上的具体新机制问题 | 已有实际非空内容与合理选择瓶颈，旧负面结果未被改写 |
| P6 | 报告与论文决策 | 完整正负结果、复现入口与贡献取舍 | 可据失败关闭本 Goal；不以 Product 上线作为结束条件 |

建议依赖为 `P0 → P1 → P2 → P3 → P4`。P2/P3 无有效信号时，P4/P5 可以不触发；P6 始终执行收口。P5 是独立研究再准入，不是为了让所有包都执行而设置的必做项。

### P0：用最新源码核对真实接口，不重跑全部历史

**输入：**报告提交、实际方法提交、PR 拓扑、当前代码和原制品索引。

**最小工作：**

1. 在独立工作树中记录实际基线与允许改动范围；保留旧 C5、旧 v27 和历史报告，不 reset/clean 原开发树，不自动合并 stacked PR。
2. 只读重建当前最终系统提示、工具 catalog、`host_both` 指令和实际历史投影的组合。已有指令已经包含写入所有权；不能仅阅读通用提示后宣称没有责任说明。[S7][S8]
3. 核对 strict 工具、共享写入执行器、事件 ack 和结果提取现状。ack 表示处理状态，不等于 semantic saved；Bank 元数据 put 不等于创建了 State。
4. 对旧 N5 选一条明确形成失败和一条过期记录链作离线定位。缺少私有 HTTP 时以公开证据范围为止，不重造历史参数或“重算”不存在的日志。
5. 冻结本轮三个候选的真实输入差异、来源可见性、调用能力、评分分母和停止条件。

**产物：**一份短协议＋方法差异表；使用现有 manifest 结构即可。不新增全仓冻结平台、另一条费用账本或大型审查流程。

**验收：**明确哪些是源码事实、哪些是报告陈述、哪些是新候选；普通工具和候选能在相同合法信息下比较。对准备环境的探测不构成部署变更，也不恢复模型实验。

### P1：只实现最小闭环，不改变记忆正文算法

**改动上限按职责定义，而非机械行数定义：**B0/B1/C 配方选择；终答候选字段；真实回执的窄解析；一次纠正入口；现有 trace 中增加必要评价字段。

优先复用 `build_agent`、共享工具和现有 Host 循环。不能把 C 写成一套新的 Agent，再让 B0 保留旧运行器；不能在同一提交改变 State 粒度、patch、query、模型参数和业务工具。

**确定性检查只覆盖新增边界：**

| 检查 | 要求 |
| --- | --- |
| 声称 committed 但没有成功回执 | 不报告为真实提交；候选是否修复单列 |
| 引用其他 owner 的真实回执 | 不当作当前用户保存依据；不返回对方正文 |
| 读取后确实已有等价记录 | 不强制再次 CREATE；语义等价由 Host/评分决定 |
| 业务已发生、维护失败 | 保留实际业务结果，不因重新进入维护而重做业务 |
| 多操作中部分成功 | 保留已成功项与实际错误，不能整体说全部保存 |
| no_change | 不产生额外写入；不自动记为用户要求已满足 |
| 工具超时或未知业务结果 | 按既有运行合同处理，不盲目重放，不伪造失败或成功 |
| 非法终答超过一次纠正机会 | 保留未完成和成本，不无限递归 |

上述工程检查不能证明 B1/C 会正确识别保存需要。受影响单测、类型、边界和必要构建按现有 CI 矩阵运行，不要求每次小修改重跑所有历史 benchmark。

**回滚：**候选可关闭；旧方法可从原 commit 复现；不在当前库上强行回滚已经发生的业务世界。

### P2：从空库验证“形成”和“不误存”

**默认规模：**先准备 6 条新的独立短交互脚本，至少两类应用表述；每条约 2—3 个公开回合；B0/B1/C 各执行一次。规模是低成本开发建议，不是统计保证，也不是授权后必须凑满的计数。

六类行为建议为：明确新长期约定、旧约定真实更正、独立事项新增、纯引用的“记住”话语、仅本次要求、只读复用且无新信息。需要已有记录的脚本先由同一方法自然形成，不人工补种成功前态。

这里的“新”指未用于修复和筛选该候选，不是声称来自真实未见用户。输入是明确构造的开发诊断，不能挂原生 benchmark 名称。评分标签独立保存，不进入 prompt、工具说明或运行分支。

**记录链：**合法请求 → 实际提案/未提案 → 工具回执 → Store 当前内容 → 后续独立会话的实际使用。

**输出：**显式形成率、误存率、修改保持、保存声称一致性、后续使用和全部费用。若从未写入，仍报告完整链失败，不只展示能够复述历史的答案。

**门槛：**至少在两个独立脚本中得到可解释的端到端改善，同时临时/引用/只读负例不被破坏，才考虑扩大到 P3。少量场景零退化不构成普遍安全保证。B1 已持平或更好时优先保留 B1，不为 C 继续新增提醒。

### P3：真实连续任务，先完成一个可审计闭环

保留一个已暴露小单元作回归，另用新冻结的连续开发脚本验证泛化方向；两者分表。默认只比较 P2 最强简单方法与一个确有信号的候选，不强制候选是 C。

首个连续单元应包含以下事件，但不是给 Host 的固定工具清单：

1. 用户 A 明确保存长期计划，Store 从空开始。
2. 用户 B 保存独立计划，不借用 A 的材料。
3. A 只在本轮改变格式；下一轮恢复适用范围。
4. A 修改一个约束，其他仍有效条件保留。
5. 新增一个独立提醒备注，与原计划分开。
6. 执行真实隔离业务，返回成功或可核对的部分成功。
7. 重新开启进程/会话，读取当前事项及实际业务结果，不重复动作。
8. 授权退出实际形成的提醒，保留其他合法信息；后续不再把它当作活跃要求。

不必每个脚本都包含八步。首批可用 2—4 个不同事项族，每个 6—8 回合，避免一个超长脚本把多种失败全混在一起。出现明确重复错误后先定位，不继续铺满矩阵。业务工具执行真实隔离 SQLite 或本地文件副作用，不接外部高风险生产系统。

**执行要求：**形成失败后不补种；失败维护不重做业务；因 upstream 缺记录导致删除未覆盖，严格链仍失败。需要验证 DELETE 本身时，另列从真实成功形成快照开始的条件诊断，不将它拼接成原失败链成功。

**模式顺序：**先验证正常 Archive-access 下不会为了保存破坏业务；再以共同 Retained-memory 合同验证跨会话使用。若两种协议共同执行，提前登记，不根据某臂表现临时切换。

### P4：只有有效信号才开展小范围独立确认

冻结代码、通用提示和协议后，选择未参与 P1/P2 修改的任务族或原生子集。不是简单换数字、实体名或 seed 就称为新任务类型。

优先追加最强简单对照、真实原文保留/检索方法；明确采用仓库锁定版本和实际入口。当前文档未重新检索外部项目最新性能，不能据旧 Mem0 四题结果给方法排名。

保持原生输入和 checker。额外 memory formation、保持、退出评分是补充任务，不悄悄修改原生分母。必要语义 Judge 按既有 vLLM 路径离线执行，参数与 rubric 冻结，费用单列；程序评分能覆盖的事项不增加 Judge。

若首轮仍是形成不稳定或正确材料消费失败，不直接部署第二模型“救分”。可以另立一个有授权的模型能力诊断，但其结果是模型/配置效应，不补正旧方法成绩。

## 10. 评价：五个层次分别评分

### 10.1 必须分列

| 层次 | 评价对象 | 不可替代的其他层次 |
| --- | --- | --- |
| 执行真实性 | 工具实际调用、Store 读写、业务世界、真实 ID | 不证明满足用户要求 |
| 任务质量 | 原生 checker 或冻结任务 rubric | 不证明已形成持久记忆 |
| 记忆质量 | 当前正文、主体、范围、时间与实际状态 | 不证明后续一定会正确消费 |
| 维护状态 | 真实成功、零写、部分成功、未完成 | 不由候选自报字段单独决定 |
| 后续使用 | 新会话或后续实际行动中是否正确利用可得材料 | 不由“取到一个 ID”替代 |

### 10.2 主指标

- **明确形成成功率：**分母是事先定义的明确持久要求；分子是实际产生或合法保留了足以支撑后续用途的记录，不要求指定库名或特定卡数。
- **必要更新＋保持联合成功率：**既改变目标事项，又保留仍有依据的其他内容。
- **误持久化率：**临时、引用、未采纳建议或普通查询被错误升级为持久事实的比例。
- **保存声称错误率：**回答或结构化结果声称完成持久化，但没有对应真实记录或回执依据。
- **闭环成功率：**在同一实际运行中形成、维护、使用和需要的退出同时成立。
- **业务成功与额外负担：**原生任务分数、真实动作数量、调用/输入/输出/存储等成本并列。

已有同内容正确记录可满足“已保留”，不要求再 CREATE；但仅在 checkpoint 里有整段聊天，不等于已经满足声明的独立记录要求。若协议允许持久原文档案作为实现，也按其真实可用性评价，不偏向结构化卡。

### 10.3 分母和缺失状态

提醒没有形成：原完整生命周期判失败；独立删除能力标为未覆盖，不当成一次 DELETE 失败。条件诊断从成功快照开始时另列分母，不修补原链。

任务未完成、未执行、未评分、评分器失败、普通判错分别保存。基础设施错误会影响实际完成覆盖，但不能伪称原生 checker 已判错。所有失败保留成本。

对多个 owner 或多回合任务按基本脚本/arc 聚类，不把调用、消息或重复生成当独立样本。开发小样本报告逐例和效应，不做无意义的显著性结论。正式确认规模由 pilot 方差与最小有意义效应决定；不显著不代表等价。

### 10.4 没有触发的处理，不应被评价为有效或无效

运行前写明处理变量应在哪些合法事件中产生差别；运行后报告实际激活比例及产生的材料差异。State 全空、无自然修订、没有需要检索的缺口时，该项因果问题记为不可估计，而不是凭总分给模块排名。

不能为了触发而注入正确 State、编造旧错误或添加无业务依据的干扰。确需 oracle/受控破坏，只作为单列诊断上限。

## 11. 真实 Agent 的通用行为边界

### 11.1 不把观察、解释与执行事实合成一个权威序列

用户说过、助手曾建议、工具尝试过、真实执行成功、用户已认可，是不同事实。错误回执里回显的参数只能证明曾尝试，不能作为执行后的世界状态。记录新版本也不自动比原始来源更可信。

结构工具应继续返回准确业务 ID 和字段。模型可以引用真实对象，但程序不能根据期望结果把 `crate` 改成 `crates`、修正数量或将自由文本映射成 gold 对象。

### 11.2 当前任务与持久写入各有责任

显式新长期信息即使不影响当前回答也可能需要保留；当前重要工具输出不一定值得长期整理。没有信息时允许询问或说明缺口；不能以“不确定”代替本来可完成的明确保存。

局部任务约束只在适用轮次生效。后续答案的格式泄漏不必通过永久 State 修复；先检查同一 Host 是否按当前任务消费原始范围。

### 11.3 中断与降级

业务成功但维护失败，报告业务结果和未完成维护；新一轮只处理未完成事项，不重放已知副作用。维护成功而业务失败也应分列，不能因已有记录就宣称业务完成。

删除只按本轮声明的受管范围验证。删除记录、撤回当前要求、移出工作上下文、物理遗忘和删除外部服务历史不是同一种保证。保留档案不等于可以悄悄恢复已撤销的活跃提醒；需单列重新激活/复现检查，不增加无限删除平台。


## 13. State–Attention 的重新准入条件

### 13.1 保留目标，停止当前已无信号的默认实现

State 可以继续表达当前目标、临时约束、活跃记录引用和待核对问题；可以有多个局部 State，也可以在不需要时为空。它不是必须存在的持久用户画像，更不是为了产生实验对照而由程序自动填入的正确答案。

Attention 的作用是选择当前值得读取或核对的材料。需要更新的范围与当前读取集合不必相同；空 U 仍允许新事项 CREATE。这些设计边界保留，但不意味着独立 A/U 模型调用已经有用。

### 13.2 P5 进入条件

以下条件同时满足，才考虑启动新 State–Attention 切片：

1. 已有合法形成或独立诊断取得的非空记录，记录身份与范围明确；若使用 oracle/人为种子，明确只是条件诊断，不宣称自主形成。
2. 真实任务或实际增长的 bank 显示普通 query/all 的瓶颈；不能为候选临时填入无任务依据的干扰。
3. 能说明一个具体操作差异，例如按任务范围延期读取，或受影响引用变化后重新核对，而不是再写一个“重要性”评分。
4. 能固定 bank/前态、共同信息与预算，并有同内容 State＋普通 ReAct、普通 query/all 或强 raw 对照。
5. 新研究不需要同时改变写入策略、材料角色、历史权限和模型部署；无法分开的系统差异明确作为系统比较。

### 13.3 首次重新进入时只选一个问题

可选其一，不全做：

- **读取问题：**相同信息下，稀疏当前任务视图能否减少无效读取，同时保持任务质量？
- **更新问题：**同一真实新观察下，使用现有检索定位更新候选是否比独立 U 模型更经济？
- **使用问题：**在实际记录被修改后，对曾交付引用给出有界版本提示，是否减少错误沿用？

上述都不是新的既定能力。当前未运行的 retrieval-based U、版本反馈、第二模型与训练 selector，仍不能被写成有效或无效。

版本提示若实施，只说明实际交付对象发生 changed/missing 或 inventory 变化。交付不等于采用，版本变新不等于正确，普通 memory 与 State 的绑定范围需要写清；不要为了修普通 memory 漏维护而扩成全库语义依赖图。

### 13.4 再次无收益时怎样处理

若普通 query/all 或同内容工作笔记继续持平且更便宜，保留简单方法，关闭该 selector 或提示机制。可以保留实验入口用于复现，但从论文主贡献中移除。只有出现新的、事先明确的任务条件，才建立新假设，不重复旧小切片换提示求胜。

### 14.1 沿现有职责修改

`shared_record_use.py` 当前把 N5 的方法身份与配置边界写明，包括完整历史、shared 工具、无自动维护与无 selector。新 v3 配方必须具有新的 recipe/method 身份，不能直接放宽旧 validator 后复用旧 freeze。[S6]

### 14.2 三种提交分开

1. **等价整理：**请求、schema、字段与顺序保持在声明范围内一致；用已有差分或窄回归，不声称语义提升。
2. **行为候选：**责任说明、完成字段、纠正入口、历史权限等变化单独可开关、单独冻结。
3. **结果发布：**报告、成本、曝光记录与 manifests 追加，不在发布时重跑模型或改分。

main 是否落后、PR 是否 draft、当前分支是否有 WIP，都在执行前记录。CI 通过只证明其实际源码树的工程检查；不自动合并、不关闭旧 PR、不把其他 commit 的绿色 CI 借给候选。

### 14.3 验证程度与变更相称

复用已有 core/foundation/external 依赖矩阵，不再重复 WP0 开发。纯文档只检查链接、代码围栏、术语与数值；协议改动检查真实序列化和回执边界；运行接线改动检查实际 ToolNode、Store 和恢复要求；只有新模型行为才运行必要小样本。

Mock、真实内存 Store、本地 SQLite、真实模型 HTTP、原生任务和跨环境确认是不同证据。测试通过数不与任务数相加。已有未发生的崩溃组合不为“覆盖全面”而大规模故障注入。

### 14.4 回滚边界

代码通过关闭候选配方或回到其明确基线撤销，旧制品保留。新的语义 memory 写入不能通过还原代码假装未发生；原生业务世界按实际状态继续记录。对隔离测试可以新建世界重跑，但必须新 run 身份，不能称为原会话恢复。

## 15. Go / Pivot / Stop 与完整收口

### 15.1 GO：只在证据支持时扩大

P2 的明确形成与负例均有可解释改善；P3 中同一运行能够完成至少一种真实维护—复用闭环，且未通过牺牲业务、owner 边界、作用域或大量拒答换分；全部额外调用计入后仍有合理投入空间。

这只是进入确认阶段的门槛。稳定收益、跨模型与论文结论还需要独立数据及统计精度。

### 15.2 PIVOT：根据断点改变最小问题

| 结果 | 调整方向 |
| --- | --- |
| B1 与 C 一样好但更省 | 采用普通职责说明，不保留结构终结的创新主张 |
| C 只减少假 saved，实际形成仍失败 | 定位成报告真实性改进；下一研究仍是操作选择，不能宣布记忆闭环解决 |
| Archive 通过、Retained 失败 | 定位形成、检索或当前内容缺失；不称历史删除“太难”而忽略该使用场景 |
| 记录正确但行动参数错误 | 转到实际使用/工具参数形成；不继续改存储结构 |
| 形成可靠、业务后维护不可靠 | 单独研究结果后维护责任；不增加全轮重复整理 |
| 普通 raw 档案已足够 | 采用更简单保留/检索，研究结构化维护的适用边界而非强求全面优势 |
| State 仍不自然需要 | 不强制造 State，不触发 P5 |

### 15.3 STOP：停止一个候选，不抹除整个项目

相同新冻结任务中，C 被强普通法持续支配；删除候选机制结果不变；提升完全由额外调用、信息权或强制写入造成；完成策略继续增加流程成本而没有改善形成/保持/使用。这些结果足以停止该候选的默认化或论文主张。

小样本未显著不等于无效；停止依据应结合效应方向、范围和真实失败链。不能在一项假设失败后不断换名增加模块，使它永远无法被否定。

### 15.4 Goal 完成标准

本新 Goal 可以在负面结果下完成，前提是：必需切片及门槛已执行或作出有依据的未触发决定；成功失败、成本与来源可复核；候选取舍明确；未完成和能力范围如实列出。

研究总目标和 Product 状态独立保留。条件分支未触发不自动使执行 Goal 未完成；执行 Goal 完成也不自动意味着论文可投或产品可用。

## 16. 回到论文目标：不要把最近的工程补丁当作创新

这版首先解决可用性与可检验性。明确保存职责、真实提交回执、单次纠正、普通 CRUD 和工作状态本身都不能预先认领为原创算法。

可保留的科学问题是：

> 在持续任务中，明确、有限的记忆维护责任能否减少漏存、误存与过期认识，并在相同合法信息及可比计算下改善后续使用？在这一基础上，State–Attention 是否有超出强 ReAct 与普通检索的独立价值？

证据链必须是 `问题 → 非显然的机制选择 → 强简单对照 → 作用范围和失败条件 → 独立确认`。不是 `新增模块 → CI 通过 → 个别任务答对 → 宣称新范式`。

若结果只支持接口可靠性，按工程贡献定位；若能解释什么时候专用记忆没有收益，可以形成有边界的实证结论，但仍需要与已有研究核查差异。本文件没有开展新的系统性文献检索，不能宣称这种问题或候选此前无人研究。

论文相关后续最多三个条件动作：确认一个清楚的 scientific claim；针对最终真实机制检索最近方法并按实际实现做对照；有独立效果后再安排第二模型或新原生任务族。不要为投稿形式临时加入训练、多 Agent 或更复杂符号系统。
