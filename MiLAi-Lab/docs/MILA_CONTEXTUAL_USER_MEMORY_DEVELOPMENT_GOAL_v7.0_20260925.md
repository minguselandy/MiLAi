# MiLAi Lab v7：观察驱动记忆的详细设计与开发安排

**执行顺序：完成通用能力开发 → 完成集成与必要窄检查 → 冻结可运行版本 → 根据实际能力选择 benchmark → 适配原生任务并进行小规模测试。**

本次设计修订落实用户“先完成开发，然后选择 benchmark”的要求。上一版预选的 MERIT 任务链保留为调研样本，不再绑定本轮实现、验收题目或运行次数。三道已暴露 MemSyco 题也只是后续回归候选，开发期间不围绕其答案调整接口。

本轮交付目标：同一个 Host 在持续工作中取得真实观察，按需读取、维护任务状态或修订一个独立事项；新会话能够重新取得当前理解并用于实际行动。程序维护来源、身份、权限与版本，Host 负责语义理解和行动选择。

本文是执行中的详细开发计划；实际完成情况见第 18 节和开发记录，未冻结部分不能当作已验收能力。前沿机制已转化为具体工作包；吸收设计不等于已经复现论文效果。Goal v6 保持关闭，历史失败、得分及费用不变。

## 1. 范围、起点与完成状态

### 1.1 继续使用的基础

当前实际实现为方法 v10 / write v9 / ingestion v25 / material view v5 / operation v2。38 个运行文件与 v6 最终冻结源码一致，身份见文件头；仓库 HEAD 不能单独替代当前源码散列。

已有来源接收、准确引用、CREATE/REVISE、CAS、版本历史、局部提交恢复、普通维护权限、材料投影及 State→search。v6 最终三个暴露原题、五条路径通过原生评分，实际 CREATE/REVISE 为 29 次，另有 13 次 NO_CHANGE。不能把 42 个 settled units 全部算作实际变更。

v6 累计 243 次生成，输入加输出 969,510 tokens，embedding 93,390 tokens，未知用量为 0；最终 43 次生成包含在其中。这些是历史开发记录，不是本轮的独立对照。

### 1.2 本次源码核对发现的真实落点

| 当前实现 | 需要改变的行为 |
| --- | --- |
| ordinary 已经没有强制 State 开场 | 保持 ordinary；增加 optional State，而不是重复取消一个不存在的 ordinary 前置步骤 |
| State 的 subject/context/uncertainty 直接进入检索 query | 显式查询投影；未知、假设、条件与搜索意图分开 |
| `ContextualHost.run()` 每次新建 transcript、MaterialView、DeliveryLedger 和读缓存 | 同一会话多轮复用会话对象，新会话准确清空；引用绑定随实际可见上下文生存 |
| Host 通过 `dispatch.__self__` 寻找 ContextualMemory | 显式绑定记忆实例，组合分发不再依赖函数绑定形态 |
| Host 对工具分发结果统一调用记忆 `receipt_outcome()` | 业务结果单独解释，不能被判为 UNKNOWN_MEMORY_TOOL 或触发记忆副作用 |
| `publish()` 保存来源，但不等于材料已经交付 | 接收、交付、允许引用、持久保留四步明确化 |
| user 角色默认映射为 current_user | 保留单用户历史适配；多主体环境增加可信 actor 标识，角色本身不能合并身份 |
| 旧记录已经有主体、事项、context、来源和依赖 | 共用写入规则并改善事项粒度；不再新增同义字段冒充修复 |
| 最终 29 次提案均主动选择 explicit | 修复理解与表达规则，不能只改变字段默认值 |
| 当前 REVISE 末端统一返回 SAVED/COMMITTED | 精确区分真正版本／来源变化与无变化，汇总不按成功状态词推算变更数 |

### 1.3 本轮明确边界

只开发 Lab，保留 ordinary 默认方向，H1—H6 不扩张。保持原始来源与可修订理解的差别；Host 不承担 Evidence/Note 真假分类。

复用现有存储、检索和事务。新增结构限于会话、可信业务结果及窄的连续任务适配；不建设多 Agent 运行系统、训练管线、知识图谱、后台反思、全局事件总线或新的数据库。

普通维护继续没有破坏性权限。真实删除沿既有授权与清理合同；空操作、混合意图、部分提交和未知结果不能靠静默修正绕过。Product 迁移、全量测试、全量 benchmark、本轮之外的候选效果比较均不在范围内。

## 3. 总体架构与状态所有权

```text
应用／后续 benchmark adapter
  ├─ 新用户消息、真实文档、真实工具结果
  ├─ 合法身份、当前任务、允许工具、来源保留策略
  └─ 同会话续接／新会话边界
              ↓
来源接入（程序）→ Observation → 精确材料交付与可引用句柄
              ↓
HostSession + ContextualHost（一个模型循环）
  ├─ 回答／业务工具 → BusinessToolResult → 新 Observation
  ├─ memory_search / memory_read → 当前材料
  ├─ 可选 memory_state → 当前任务状态
  └─ memory_save → 当前事项或作者经验
              ↓
ContextualMemory：来源、理解、版本、依赖、权限与既有局部提交
              ↓
同会话继续；或保留持久记忆、清空会话后进入新任务
              ↓
外部 scorer / artifacts：冻结结果、任务分数、实际使用与完整费用
```

| 状态 | 唯一所有者 | 其他模块的访问方式 |
| --- | --- | --- |
| 原始来源、retained、记录、版本、依赖、TaskState | ContextualMemory 与现有 store | 使用 publish/save/read/search/update_state/checkpoint 等窄方法 |
| transcript、短句柄、可见范围、交付记录、当前轮读缓存 | HostSession | Host 和材料入口读写；环境不能自行标记“模型看过” |
| 工具允许列表、来源角色、actor 标识、会话边界 | 可信适配器和运行上下文 | 运行前绑定；不接受模型参数扩大权限 |
| 文件／业务数据库等真实工作对象 | Business environment | 只有对应业务工具修改，记忆回执不修改它 |
| gold、原生 checker、私有世界快照、未来任务 | scorer／benchmark adapter 的私有侧 | Host 不可读取，也不写回记忆 |
| 请求费用和冻结制品 | 现有账本与 artifacts | 各阶段追加真实事件，汇总不创建第二套账本 |

不新增一个包含上述全部字段的“大状态类”。HostSession 只承接原本就在 Host 内部的会话状态，ContextualMemory 仍拥有持久与任务记忆。

## 4. 窄接口与数据设计

以下为拟议签名，实现时以现有风格命名；必须保留这些职责和语义，不要求再造通用接口框架。

```python
# 同一会话复用；未传 session 时保持一次调用的便利入口
ContextualHost.run(messages, *, session=None, max_calls=None, envelope=None)

# 可信接入，不是模型工具
accept_observation(memory, session, observation, *, retention, max_bytes)
# 完成 publish → 合法保留 → 材料投影 → 实际交付绑定

dispatch_action(name, arguments, *, memory, business_tools)
# 按已注册工具类别分流；记忆回执与业务结果独立处理

project_query(query, *, task_context, state, explicit_filters)
# 返回真实 effective_query、过滤条件及投影来源

run_task_session(turns, *, memory, host, business_tools, input_policy)
# 顺序接收真实轮次；不包含 benchmark gold 或评分逻辑
```

拟增加两个小类型：

- `HostSession`：会话身份、transcript、MaterialView、既有 DeliveryLedger、实际可见绑定和轮内缓存。可以位于独立小文件；不持有业务世界、scorer 或第二份记忆库。
- `BusinessToolResult`：实际输出、调用身份、`succeeded/failed/unknown` 执行状态及可形成 Observation 的返回内容。由可信工具适配器构造；不是模型可填的“执行证明”。未执行的无效请求在入口另行记录。

复用 Observation，拟增加一个可选 `actor_ref` 表达接入方确知的发话者身份。保留 role 表达 user/assistant/tool，artifact/session/event 表达准确事件；about_ref 仍表达记录关于谁。不要用一项字段承担这三种含义。

已有 Interpretation.subject 表达事项，context 表达适用叙述，certainty 表达证据强度，conditions 表达可求值条件。首版不再增加 matter_id、topic_id、verified 或逐句证据数组。

TaskEnvelope 继续只管记忆阶段和允许的记忆操作。业务工具权限由运行入口给定的实际工具映射控制，不把 allowed_operations 扩成第二套细粒度业务权限系统。

## 5. P1：会话复用与同一 Host 的工具循环

### 5.1 显式绑定记忆

ContextualHost 明确接收 memory 实例，MaterialView、删除续处理检查和 State 策略均使用该实例。迁移仓库内已知构造点，取消依赖 `dispatch.__self__` 推断对象的逻辑；不保留两套同时生效的隐式／显式绑定规则。

配置入口校验一次业务工具名与记忆工具名不冲突。执行时用固定映射分流；不要用名字是否包含 memory、delete 或 refund 猜测类别。

### 5.2 同会话连续轮次

首次调用创建 HostSession；后续调用只追加当前实际新消息，保留之前真正交付的材料和句柄，不重建全部历史。调用者传入增量消息，不把上一轮完整 transcript 再提交一次。

当前 `run()` 的“返回 final answer”只结束一次用户轮次。会话由可信驱动器显式关闭。新轮次刷新当前请求、基础条件及查询覆盖绑定，保留仍合法的工作状态；不能调用会清理任务来源的 `start_task()` 冒充同会话续接。

必要时增加一个窄的 `advance_turn()`：更新当前问题和当前轮条件，失效旧 coverage；不删除该会话来源和 TaskState。它不自动总结历史或改写旧事实。

预算提示、最后一次响应约束等控制消息按当前轮构造，不成为下一轮的用户来源，也不能将“禁止继续调用工具”遗留到下一轮。JSON-action 模式用 user channel 承载工具结果时，来源角色仍由可信工具调用确定，不能按传输 role 误记为用户说过。

### 5.3 缓存、进展和执行结果

轮内完全相同的记忆读取可以沿现有规则复用已交付结果。新 observation、记录变化、查询条件变化、新轮次或可见上下文变化时清空相应缓存。第一版采用这些明确边界清空，不建立全局缓存依赖图。

业务动作不接入记忆读取缓存，也不按重复参数自动重放。工具结果未知时，保留 unknown，由可用业务查询或应用恢复处理；不能自动再次执行一个可能已经生效的写操作。

`receipt_outcome()` 仅接收记忆工具结果。业务执行成功、失败和未知由 BusinessToolResult 返回，Host 据此继续行动。业务结果中的 status 不触发 memory cleanup、不会改写原始任务目标。

**实现出口：**旧的一次性问答构造点和新的多轮入口都使用同一个 Host 循环；实际业务动作、观察和记忆调用可以交替进行。此时只宣布工程接线完成，自主语义效果等待开发后的真实模型验证。

## 6. P2：可信增量观察、主体与保留策略

### 6.1 接入路径

每个新事件执行以下确定性步骤：

1. 适配器给出真实正文、role、artifact/session/event 及已知 actor；不从 Host 文本中的“用户说”反推来源角色。
2. 通过现有 publish() 得到准确来源。相同事件重复输入复用身份，事件 ID 相同而内容不同仍是合同错误。
3. 按运行入口声明的保留策略处理来源，不让模型填写授权快照。
4. 用公共材料投影交付实际正文范围和引用句柄。
5. 只有真正进入 transcript 的范围才写入 seen/visible_source_ranges，并允许作为修订依据。

直接用户消息可以在原始消息旁附来源句柄和已交付范围，不必重复一份全文。工具结果同样尽量只交付一份正文，内部回执和 trace 保留准确输出。超预算时明确展示范围；未展开内容不自动视为模型已读。

### 6.2 多主体身份

`role=user` 只表明消息角色。接入方明确属于记忆拥有者时填 `actor_ref=current_user`；应用有稳定人员标识时填作用域内 actor；未知时保持 unresolved。程序不从相似姓名推断跨事件同一人。

MaterialView 的主体目录从已交付来源及可信 actor 构造，短句柄绑定到稳定 actor 或准确来源锚点。save 的 about_ref 只能使用已交付的主体。无需新增主体表，全局人物合并不在范围内。

适配现有单用户历史时，适配器明确发布 current_user，保持既有数据含义。新多主体任务不能继续把所有 user 消息默认映射为 u0。无法定位具体人但事项清楚时，可以保存有范围的作者记录，不能伪造一个客户画像。

### 6.3 来源与理解分别保留

| 路径 | 来源保留 | 理解维护 |
| --- | --- | --- |
| 普通在线会话 | 未明确持久保留的来源为会话材料 | Host 可 CREATE/REVISE；持久记录依赖的来源沿现有逻辑一同保留 |
| 明确保留原始材料 | 复用 RETAIN_SOURCE | 可以没有总结，不额外调用模型生成卡片 |
| 授权的历史导入 | 保留适配器允许的完整历史来源 | 复用现有 ingestion，不修改原始语序或自动跳过失败维护 |

来源保存成功与语义维护成功分别记录。未保存为长期记忆的会话观察可以在会话结束后退出，不偷偷放入新的隐蔽历史库；若后续评估允许所有历史原文持续检索，各臂必须声明并遵循相同规则。

一般更正是一个新的观察，随后修订理解。`Observation.supersedes` 仅表示可信接入确认的来源替代，不把“用户改变偏好”自动变成删除或覆盖早先原话。

### 6.4 工具证据的强度

工具调用被提出、被执行、返回成功、通过指定检查、被用户接受是不同事件。BusinessToolResult 只描述实际执行；验证和用户接受需要对应的新观察。

一份文件的某版通过某项检查，只支持这项局部事实。环境返回的错误可支持“这次调用失败”，不自动支持普遍规则。benchmark 的评分结果不能回传为可用于维护的 observation。

**实现出口：**输入和工具两条路径都能形成可引用材料；事件去重、身份和会话边界可确定性核对，不需要额外来源分类模型。

## 7. P3：共用的事项写入合同与经验表达

### 7.1 单一规则来源

把分散在工具描述、INGESTION_PROMPT、普通在线提示中的共同写入规则收敛到 `write_contract.py` 或相邻的一个小模块。历史提案和在线工具共用定义，阶段只补自己的输入格式和容量信息。

基本规则保持简短：说明关于谁、哪个可独立改变的事项、当前采用什么理解、适用哪里、依据是什么。当前已有材料足够就直接执行；没有持久变化不必调用 NO_CHANGE。

| 操作 | 必要语义 | 程序负责 |
| --- | --- | --- |
| CREATE | 一个新的可独立维护事项或明确的作者想法 | 新身份、来源绑定、已有精确重复处理 |
| REVISE | 已交付目标、完整的新正文与当前依据／独立依赖 | 准确目标版本、CAS、旧版保存、局部提交 |
| RETAIN_SOURCE | 保留已取得原材料 | 准确内容和来源身份，不额外推导事实 |
| NO_CHANGE | 有提案协议需要回执时，声明本批没有变化 | 真正无副作用；在线可以直接不调用 |

操作需要的 source_refs/dependencies 仍遵守完整替换合同，空数组含义不能含糊。不能用“为了简洁”自动保留本应撤销的依据，也不能把自己旧版加成独立依赖。

### 7.2 独立事项和局部修订

旧记录视图按“主体→事项→当前正文→适用范围→必要依据”组织，复用已有字段。检索仍用现有能力，不加入特殊主题词、题号或 gold 同义词。

当两项认识可分别变化，就分开维护；临时例外写清范围；同一事项的一次变化优先修订正确目标，而不是滚动追加人物小传。第一次建立记录时形成合适粒度，后续一次只重写需要变化的事项。

程序只能验证目标已交付、版本合法和引用可用，不能以词面相似证明“同一事项”。Host 语义选择要在真实模型运行中评价。首版不做全库拆卡，不新增 SPLIT 原子操作；旧冻结卡不转换后冒充新协议产物。

### 7.3 正文、证据强度与时间

永久正文使用可独立理解的人、事件和范围，不依赖 sN/rN/pN 等批次句柄。句柄只出现在结构化引用字段。不对正文中的相似编号自动替换或删除，不把原文没有的人名、动机和日期补出来。

explicit 表示材料直接声明了所记录内容；inferred 表示明确标注的解释；uncertain 表示尚未解决。它们均不改变治理权威。新接口要求 Host 明确表达证据强度，不能依赖缺省 explicit，也不能全部设 uncertain 逃避语义判断。

混合直接陈述与推断时，去掉无用解释；有复用价值的解释明确标注，必要时按事项独立记录。首版不建立逐句证明结构，不新增语义审查 Agent。两条陈述共同出现不证明因果。

确切日期才进入结构时间字段；相对时间、未知时间留在正文或 context，程序到达顺序另行记录。conditions 只接收已有定义的可求值条件，范围叙述不强迫结构化。

### 7.4 把 ReasoningBank 的经验用途落到已有记录

Host 在观察到实际成功或失败后，可以保存一条作者经验，例如“在这类文档的这个检查要求下，需要补足哪些内容”。subject 表达做法或任务事项，context 表达适用范围，source_refs 指向真实执行／检查结果，正文区分观察与推断。

经验记录不声称是用户偏好，不需要新增经验表或工具，也不在每次结束时强制提炼。用户反馈改变适用条件时修订同一经验；只有一次结果时不写成普遍必然规则。

### 7.5 变更和无变化必须可区分

比较提交前后的正文、元数据、版本与来源保留变化；实际发生变化才计入 memory_changes。相同正文和元数据的 REVISE 不因为走到 SAVED 分支就增加变更计数；若只新保留来源，应只报告真实来源变化。

复用现有对象比较和提交路径，不建立新的事务日志或复制框架。一次局部失败仍保留已提交结果，不能让汇总把完整请求当作全部失败或全部成功。

**实现出口：**历史和在线使用同一语义合同；当前表达、作者经验、准确依据和版本分别可见；正常不写入不会增加一轮管理调用。

## 8. P4：可选 State、查询投影与身份兼容

### 8.1 策略明确化

| state_policy | 运行行为 | 使用定位 |
| --- | --- | --- |
| off | ordinary 自由循环，保留基础任务条件 | 默认方向 |
| optional | memory_state 与业务／记忆工具一起可选 | 本轮完整实现的主动 State 能力 |
| forced_legacy | 保留可识别的旧 State→search 接线诊断 | 不作为自主策略证据 |

开关控制 Host 工具与执行顺序，不暗中改变来源范围、写入规则、模型权重或材料格式。State 不是每轮开场表格，也不要求调用后必须立刻 search。

### 8.2 工作状态更新

context 承接当前工作说明；uncertainty 承接待查问题；intentions/conflicts 引用已交付记录；条件和时间沿现有出处规则。只更新提出的字段，保持其余合法工作状态，不强制输出七节摘要。

coverage 继续绑定真实搜索与状态签名。UNKNOWN 表示未确定，GAP 表示当前查询存在缺口，不能解释为整库不存在；新观察、问题变化和有效条件变化使旧覆盖结论失效。

State 自由文本可以包含假设，必须保持其地位；不将一次“没找到”自动持久化为用户事实，也不把 State 当作来源证据。

### 8.3 一个查询投影函数

1. effective_query 使用本次明确 query；省略时使用当前轮真实问题。
2. 已声明的时间、主体、适用条件通过原有明确参数处理，记录来自当前调用、可信任务输入还是有依据的 State。
3. State.context/uncertainty 不再自动拼接为检索文本。需要查询其中某个问题时，Host 在正常 search 参数中明确提出。
4. intentions/conflicts 可按既有合法引用影响材料展开；未知条件仍未知，不从 gold 或常识自动补齐。
5. trace 记录实际投影与过滤条件。不得把自由文本描述与结构化覆盖状态混为一个真假判断。

显式参数优先于当前任务的缺省值；State 只补充未指定且有合法依据的部分。主体自由字符串不能自动变成强过滤条件。

### 8.4 新旧身份边界

目前 contextual 同时进入 history_write_identity 和 checkpoint。新合同拆开“如何产生记忆”与“Host 如何读取／使用 State”：写入身份包含规则、来源策略、主体／观察协议、摄入方式和相关模型身份；读取执行策略另列。

只允许完全一致的新写入身份共享历史快照，运行各自独立副本。旧 v6 checkpoint 保留原身份，不能改布尔值强行兼容。需要新语义时从合法原始历史重建；旧制品只读诊断不算新写入效果。

**实现出口：**off 与 optional 共用同一底层记忆合同；选择 State 的能力接通，是否适时使用在开发后评价。没有实际需要时不调用是合法结果。

## 9. P5：公共模型材料与成本控制

### 9.1 一条材料路径

来源直达、read/search、写入回执都经过现有 MaterialView 的公共绑定与投影。新增的 observation 入口复用该路径，不复制一个格式相似但绑定不同的模型视图。

模型默认看到：短引用、必要版本／角色、主体与事项、当前正文、适用限制、少量必要依据及展开入口。完整 ID、散列、旧版本链、局部提交诊断保留在内部和制品中。

同一响应内按准确对象版本及范围去重，多个关系连接到已交付正文；不同事件即便文字相同仍分别保留。必要更正与会误导的旧正文共同预算，不能只留下旧内容。

### 9.2 控制额外输入

先去重复的工具说明、材料外壳和宽卡重写，再考虑其他优化。协议声明在当前会话中保持单一有效版本；新增主体后只更新必要的可选范围，避免不断追加整份工具手册。

记录内部序列化体积和实际送入模型的输入 tokens，两者不能混用。低字节预算时明确不足或缩小真实正文范围，不能保留超预算引用后称严格满足限制。

本轮不重启 H5 跨回合差量。已有重复读取提示只在正文确实仍在当前 transcript 时使用；若将来压缩 transcript，必须同步失效可见性和引用。本轮容量不足时如实停止该任务或等待明确续接，不暗中删除材料再沿用“已经读过”。

### 9.3 真实使用记录

在现有 trace 增补最少关联字段：session/turn/event、tool_call、来源引用、record version、实际交付范围、操作决策与后续工具调用。完整思维链不是交付要求。

形成一条可复查链：观察已接收 → 材料实际可见 → 提案 → 真实变更 → 后续读取／交付 → 业务行动及环境结果。查不到时能定位在哪一环中断。

原始出处可读、记忆被引用、正确值进入工具参数、任务成功与相对基线收益分别报告。它们不是同一个指标，也不需要新的评审平台。

## 10. P6：通用连续任务驱动与开发集成入口

### 10.1 先开发通用入口

`run_task_session()` 只接收公开当前轮输入、工具映射、运行上下文和来源保留策略，不认识任何 benchmark case_id、gold、客户订单字段或评分方法。

同会话续接保持 HostSession 和业务环境；新会话调用 start_task 并新建 HostSession，保留合法持久记忆和应用决定持续的业务世界。session_id/turn_id/event_id 由适配器稳定生成，模型不自行重命名会话。

checkpoint 沿现有机制保存持久状态；同任务恢复使用真实 handoff，不能把跨任务 handoff 当成隐式携带完整旧 transcript。第一次只支持现有范围的同步恢复，不新增分布式持久化系统。

### 10.2 通用开发样例

提供一个很小的本地文档工作样例，支持真实读取、按期望版本修改、执行确定性检查三种动作。工具只操作本次临时工作目录，返回真实结果，不依赖外部服务。

示例覆盖：读取原文 → 修改 → 检查发现限制 → 得到新用户反馈 → 维护当前事项 → 新会话重新取得相关记录。这是通用接口使用示例，不是自建正式 benchmark，也不产生准确率结论。

开发联调可使用脚本按次序调用这些接口，证明文件、引用和版本确实变化；必须标记为确定性接线验证，不能冒充真实 Host 自主调用。开发期间不围绕脚本预期次序修改模型策略。

业务适配器实现真实工具即可，不要求所有后续环境都实现同样的读文档工具。未来 benchmark 自己提供原生工具映射，通过同一结果接口接入。

### 10.3 基础配置与能力说明

交付通用 ordinary/off、ordinary/optional 两份配置样例，均不包含 benchmark 选择或题号；冻结 forced_legacy 的诊断用途。配置记录来源策略、主体协议、模型与 embedding 身份、工具模式和单工作流容量。

说明已经实现的能力与尚待模型验证的语义能力。中文词法检索现有限制、受管删除范围和当前容量边界仍如实记录，不因增加业务入口而升级为生产能力。

## 11. 代码布局与改动边界

拟新增文件控制在确有独立职责的范围，优先三个：

```text
src/milai_lab/runners/
  contextual_host.py          # 模型循环；调用 Session、dispatcher 和 MaterialView
  contextual_session.py      # 新：会话状态、轮次边界、实际可见性
  contextual_agent_tasks.py  # 新：通用连续任务、来源接入、业务工具结果与分发
  contextual_ingestion.py    # 历史输入专用；复用共同写入规则
  contextual_profiles.py    # 写入身份与 State 读取策略
  contextual.py              # 现有问答入口；只做必要接线，逐步收窄
src/milai_lab/methods/contextual_memory/
  models.py                  # Observation.actor_ref 等必要共享类型
  write_contract.py          # 共用写入语义、已有确定性校验
  query_context.py           # 查询投影与条件出处
  material_view.py            # 来源直达和工具材料共用投影
  materials.py               # 当前状态与必要关联材料组装
examples/                    # 新：一个很小的真实本地任务使用样例
```

示例可以是单文件，不创建新的测试框架。若业务分发使 `contextual_agent_tasks.py` 出现两个明显独立职责，再抽一个小文件；不先建立抽象工厂、插件注册器或多层基类。

现有核心继续拥有持久数据。新模块通过窄方法访问，不复制所有字段再跨模块任意修改。只因主类行数多而搬文件没有优先级；先修复实际所有权交叉。

输入边界完成必要验证，内部依赖明确合同。保留权限、准确引用、CAS、作用域、身份、日期等真实边界；不层层重复校验，不捕获所有异常返回空成功，不自动改用最新版本。源码组织改动与语义变化分别记录身份，便于后续解释实验结果。

## 12. 详细开发顺序与依赖

以一个可独立集成的工作单元安排任务，不设脱离代码情况的硬小时数或代理 token 上限。各工作包结束时交付代码、调用入口和简短实际行为记录；不要求逐包购买模型调用。

| 顺序 | 工作包 | 前置 | 主要产出 | 完成判据 |
| --- | --- | --- | --- | --- |
| P0 | 接口与源代码基线 | 本设计 | 2 个小类型、actor/会话/策略合同、现有调用点清单 | 接口责任明确，基线散列固定；没有 benchmark 字段进入核心 |
| P1 | Host 会话与分发 | P0 | 显式 memory、HostSession、分流回执、轮次容量与缓存处理 | 单次与连续轮次共用循环，业务结果真实返回，旧调用点已迁移 |
| P2 | 增量来源与主体 | P0；与 P1 对接 | 输入／工具两条 observation 路径、actor 与引用绑定、保留策略 | 新来源可合法引用，角色与主体不混用，会话边界不遗漏 |
| P3 | 事项与经验写入 | P2 | 共用写入规则、正文／范围／certainty 合同、准确 NO_CHANGE | 历史与在线接口一致，变更数来自实际变化 |
| P4 | State 与查询 | P1、P2 | off/optional/legacy、查询投影、advance_turn、身份兼容 | 不强制开场，自由文本不隐式污染 query，共享快照规则准确 |
| P5 | 材料与使用记录 | P1、P2；集成 P3/P4 | 公共材料入口、去重复外壳、精简实际使用链及成本字段 | 可追溯完整链，同一正文只按准确范围交付，计账不丢失败 |
| P6 | 通用连续任务集成 | P1—P5 | task driver、本地真实工具样例、通用配置与能力说明 | 所有已采用机制存在真实消费者；没有未接通的默认分支 |
| P7 | 开发冻结 | P6 | 相关静态检查、必要窄检查、使用说明、源码／配置身份 | 状态 DEVELOPMENT_COMPLETE_READY_FOR_BENCHMARK_SELECTION |
| E0 | 选择 benchmark | P7 | 适配度比较、选择理由、小样本 manifest、预期测量问题 | 先固定题目及评分，再运行模型；未根据成绩换题 |
| E1 | 原生适配与试运行 | E0 | 薄 adapter、数据散列与原生评分对照 | 只改适配层，不改原题／环境效果；协议差异清楚 |
| E2 | 小规模对照与报告 | E1 | 完整制品、真实使用链、原生分数与阶段成本 | 工程执行、任务结果、收益结论分别报告 |

开发阶段关键路径为 P0 → P1/P2 → P3/P4/P5 → P6 → P7。表中的并行依赖不代表允许两个代理同时修改同一共享文件。benchmark 专属 adapter 在 E1 编写，不提前把 MERIT 或其他数据结构放入核心。

如果 E1 暴露通用能力缺陷，返回对应 P 工作包做窄修复，生成新的源码身份，再冻结同一选择继续验证。不是为了“先开发完成”而禁止正常修复；也不能把分数反馈变成题目专属路由。

## 13. 多 Agent 开发安排与性价比

开发协作与运行方法分开：开发可以并行，运行时只有一个 Host。沿用户指定档位使用 **Sol xhigh 常规开发、Luna max 窄任务、Astra xhigh 疑难处理**。

| 角色 | 常规所有权 | 交付方式 |
| --- | --- | --- |
| 主开发 A：Sol xhigh | P0；models、核心、write_contract、query_context、profiles；P2/P3/P4 主体；最终集成 | 先给简短类型／接口约定，按依赖推进；共享文件只由 A 修改 |
| 开发 B：Sol xhigh | contextual_host/session/agent_tasks；P1、P6；材料调用接线 | 在接口确定后并行；需改核心时提供具体调用需求，不同时改 A 的文件 |
| 窄任务 C：Luna max | 既有代码调用点迁移、manifest、单个必要用例或文档 | 每次限定明确文件和结果；材料文件若委派 C，则 B 当时停止编辑该文件 |
| 疑难支援：Astra xhigh | 难以定位的跨层身份、状态恢复或语义合同问题 | 读取已有失败最小证据，给窄结论／修复；不作为每包固定审核步骤 |

推荐两条主线，第三个代理按实际窄任务启用。不要为了并行把一个函数拆成多个互相等待的代理任务，也不为同一个报告安排多轮审查。主开发完成一次集成检查即可，新增问题再定向处理。

先做不消耗模型的实现与窄验证。后续所有 vLLM 实验由单一入口调度，避免代理各自重复摄入相同历史、并发抢资源或漏记失败。模型切换不按项目名自动升级；Astra 仅在问题需要时使用。

## 14. 开发完成的判据与必要窄验证

“开发完成”表示实现与集成就绪，不表示自主记忆质量已经证明。P7 至少具备：

- 一个 Host 循环同时支持记忆和真实业务工具；会话续接与新会话边界实际执行。
- 输入和业务观察均可发布、投影、引用；多主体绑定与来源保留清楚。
- 共同 CREATE/REVISE/RETAIN_SOURCE 合同可运行；State 可选，查询投影存在真实调用者。
- MaterialView、快照和使用链记录接通；通用配置和使用样例可执行。
- 已知 TODO、空实现、只写提示但未消费的开关没有被列成已完成能力。

开发期间只保留六组有必要的合同检查，优先复用现有用例：

| 检查组 | 核对的工程合同 |
| --- | --- |
| 会话与分发 | 同轮来源、跨轮句柄、业务回执分流、旧控制提示不阻断下一轮 |
| 来源与身份 | 重复事件、实际交付范围、user 角色与可信 actor、来源保留边界 |
| 写入与变更 | CREATE/REVISE 版本、独立依赖、无变化与真实来源变化分别计数 |
| State 与查询 | 不调用也可完成、显式查询、coverage 失效、合法条件未知 |
| 材料与恢复 | 当前／历史限制保留、别名未漂移、新会话不继承临时可见性 |
| 通用集成 | 实际本地读／改／检查贯通，持久与任务状态边界，费用事件无重复 |

不为低风险文字改动新增测试，不写镜像实现的大量断言，不运行测试全集。包代码移动时运行边界检查；包装配置未改不构建包。新增 schema 复用已有 grammar 检查，确认部署的生成后端能表达分支，不能只证明 JSON Schema 自身合法。

开发阶段不开展 benchmark 跑分或模型驱动的逐题提示调参。确定性接线样例不声称模型自主使用过功能；真实 Host 的语义验收留到 E1/E2。

## 15. 开发后如何选择 benchmark

### 15.1 选择依据

P7 冻结后，用已实现能力选择测试集，而不是用目标答案反向设计记忆。正式运行前记录：能力覆盖、许可与源码可取得性、原生任务边界、环境成本、评分方式和信息泄漏风险。

优先选择同时具备以下条件的一套连续任务：有完整合法历史；有真实新观察或明确更正；后续任务需要使用旧信息；业务动作产生可检查效果；可选一个完整小单元运行；原生工具和评分可保持不变。

只读数据说明和任务结构来确定选择。若需要检查某题的 gold 才能诊断覆盖问题，该题标记为已暴露开发样本。不能先跑候选成绩，再选对 MiLAi 最有利的题或删除失败环节。

### 15.2 当前候选池，不是已承诺执行清单

| 候选 | 可能覆盖的能力 | 选择时需要解决的实际问题 |
| --- | --- | --- |
| MERIT | 跨 episode 更新事实、真实工具参数与程序评分 | 官方强制 read/write 与 MiLAi 自主循环不同；合并消息只评分第一 TaskSpec；原生分母要保留 |
| MemoryArena | 更复杂的跨任务依赖、环境行动与记忆复用 | 额外服务／数据成本、公开实现与许可边界、当前 Host 适配成本 |
| MemSyco 既有暴露题 | 用户偏好变化、主体与范围、语义回归 | 可作小回归，不能替代连续工具执行证据，也不是新的独立样本 |

MERIT 已生成的 `arc0-000` 保留为候选检查样本：5 个 episode、7 条消息、2 个 dependent episode，生成器 leak check 当时通过。这个事实不表示当前已经选定它；原始序列、世界和散列保持不变，清单状态已降为研究候选。已有阅读暴露应如实记录。

如果上述候选与已实现能力均不匹配，再定向检索一个更合适的公开基准，先取得参考源码和原生评分；不同时接入多个环境。本轮不预定全量 benchmark 或完整 STALE 重跑。

### 15.3 规模、对照与配置在选择时确定

默认只选一个完整的小单元，保持原始会话／任务链边界。若需要保留语义回归，再从已有暴露题里选少量相关项；不自动执行上一版的“三题五路径＋固定 MERIT 十次 episode”组合。

先写清本次回答的问题，再选择最少比较臂：

- 验证系统可用：先 ordinary 的完整小单元，定位执行问题。
- 比较 State 策略：同一写入与材料合同、相同初始世界，off 与 optional；能够共享的快照必须通过身份验证。
- 评价结构化记忆相对简单方法的价值：选择原文检索或同粒度 ordinary 作强基线，不只比较两个复杂配置。

一次只回答一个主要效果问题，不形成多个 benchmark × 多模型 × 多策略网格。连续任务中两臂产生不同记忆时是系统策略比较，不能宣称是单一步骤的纯因果消融。

来源是否全量保留、每会话上下文边界、动作预算、模型和材料格式对比较臂一致。预算按原生任务和模型容量确定并冻结，实际请求全额计入；不因先验偏好给某臂额外重读、正确提示或未来消息。

### 15.4 原生测试与评分

原题、顺序、工具语义、世界生成器、gold 和 rubric 不修改。benchmark adapter 只做输入与工具转换、合法来源接入、制品冻结及原生评分调用。

保留 native completed／score available／success 的区别。没有形成有效评分记为未评分，不算全错。程序评分可用时直接使用；确需 LLM Judge 时只用 vLLM，冻结答案后执行原生 rubric，Judge 输入不回流到 Host。

若改变官方控制器，报告明确列出差异。例如 MERIT 的强制开场 read 和结束 write 被自主循环替换时，应称“原生任务上的 MiLAi 控制器实验”，不能称完全复现官方 harness。

## 16. 真实功能使用、研究问题与结项

真实实验至少检查一条必要的修订链：旧理解确已存在 → 新观察实际可见 → 正确 REVISE 提交 → 后续独立任务取得当前版 → 合法业务动作使用其内容。也记录直接使用原始来源完成任务的路径，不降低其原生得分。

为“覆盖”功能而强制 State、预置错误记忆或制造第二个支持不被允许。State 自发未触发时记录未触发；必要性尚未成立，不把直接行动解释为失败。工程 Goal 可以完成而 State 收益仍未知，但不能称 State 效果已证明。

创新研究只保留三个可证伪问题，沿同一实现测试，不新建 H7—H9：

| 研究问题 | 应观察什么 | 不能据此认领什么 |
| --- | --- | --- |
| 独立事项的局部修订能否降低连带误改和输入成本？ | 无关事项是否保留、当前变化是否生效、重写与材料开销 | 独立条目本身不是新发明 |
| 同一 Host 能否在不漏维护的前提下减少无效管理？ | 自主读写的适时性、直接行动比例、后续任务与成本 | 暴露工具不等于学会了 AgeMem 的训练策略 |
| 可追溯更正能否进入后续行动并产生相对简单方法的价值？ | 实际版本—材料—动作链和强基线结果 | 值匹配或一条成功轨迹不证明独立因果收益 |

P7 标记 `DEVELOPMENT_COMPLETE_READY_FOR_BENCHMARK_SELECTION`，E0 之后才能标记评估选择完成。E2 分开报告工程执行、原生质量和收益。允许以负面或不确定效果结束限定实验，不能为了追求胜出持续调题或扩大规模。

若关键功能只是代码存在而无消费者，开发项未完成；若模型在确有机会时没有使用，记录可达／策略问题，针对普遍原因修复。若在所选基准中根本没有机会，则说明测量缺口，不伪造一条链。

## 17. 成本、错误处理与开发效率

累计请求、tokens 和复核次数的硬停止继续为 null，保留单工作流容量和输入／输出预算。每次新增模型调用对应明确修复、尚未完成的验证或必要对照，不进行无目的重复。

v6 的封闭账本保留；v7 所有失败、重试、修复及评估连续入账。Host 输入／输出、embedding、Judge 和开发代理 tokens 分列。没有实测价格或 GPU 用时，不把 tokens 直接说成精确费用。

模型侧只用一个已有 vLLM 接入；不因任务困难自动换更大 Host 或增加外部 Judge。开发代理的 Sol/Luna/Astra 分工不等于实验使用不同模型。禁止引入未计费的摘要、分类、验证调用。

失败先按实际边界定位：来源未交付、合法操作未提出、目标语义错误、提交失败、材料未进入后续行动、或原生任务未完成。保留最小足够制品，不为每次尝试复制一整套环境，也不堆积防御性重试。
