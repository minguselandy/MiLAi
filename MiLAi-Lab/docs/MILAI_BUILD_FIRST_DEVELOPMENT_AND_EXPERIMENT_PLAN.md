## 2. 本阶段唯一目标：交付一个能持续使用的端到端功能候选

### 2.1 用户可见的目标功能

完整候选应能够完成以下行为，而不只是让某个SDK函数返回成功：

| 用户行为 | 系统应有的功能 |
|---|---|
| 提供新事实或要求记住 | 保存原始来源，形成需要长期使用的信息，依据真实提交说明结果 |
| 更正已有信息 | 找到相关事项，落实新内容；旧陈述作为历史保留，仍有效的限定不被无意删除 |
| 增加局部例外 | 例外只作用于明确范围，一般规则在范围外继续可用 |
| 取消例外或调整共同条件 | 按真实新要求改变适用安排，不重新猜测已经丢掉的一般规则 |
| 查询现在或过去 | 使用实际保存的信息，区分当前解释、历史报告、未来计划和未知信息 |
| 业务部分完成后继续 | 使用实际回执继续剩余任务，不重复已完成副作用；明确记忆是否提交 |
| 请求遗忘 | 沿用现有可见性处理，后续读取与恢复不得绕过它 |

“应该能够完成”是开发目标，不表示当前已经稳定做到。

### 2.2 不以内部动作计数定义正确性

**不把UPDATE次数、condition节点数量或override使用次数当作功能成绩。**

新增带日期的事件、修订现有语义记录、在读取时重建当前解释，都可以是合理实现。只有当它们导致当前事实、历史、范围或用户任务错误时，才据此认定失败。

本版继续采用“原始事件保留＋可修订语义记录＋只读查询视图”的主方案。同时保留追加式事实记忆作为强对照，最后由公开数据和完整任务评价决定写时维护是否值得。

### 2.3 功能候选与产品发布分开

功能候选可以存在已知语义失败，但应具备完整可调用路径、真实持久状态和可解释的操作结果。语义失败进入后续迭代，不阻断无关功能的集成。

跨用户暴露、错误业务对象、重复副作用、数据损坏和虚假成功回执属于阻断问题，需要先修受影响路径。它们不是为了论文评分设置的附加门槛，而是现有系统本来就需要遵守的功能边界。

## 3. 首选工程方案：复用原型，接通一条正常维护链

```text
当前用户消息／真实工具回执
        ↓
原始事件可靠保存
        ↓
一次候选陈述提取（临时结果，不是已保存事实）
        ↓
现有dense定位相关旧事项
        ↓
原始证据＋实际旧状态＋候选提示
        ↓
现有事项级全量／局部编辑器
        ↓
同一个MemoryService提交结果
        ↓
实际回执＋语义记录／历史
        ↓
共同检索与只读适用视图
        ↓
普通Host回答／继续真实业务
```

### 3.1 明确的第一版选择

**将已有两阶段原型接入开发功能配置，作为待评候选；保留现有单轮流程作为对照，不先开发三种路由器。**

首次实现直接复用现有候选字段与批次查询。每个正常来源批次至多安排一次提取和一次编辑；不要把每个候选都变成一个新的多轮Agent。原文始终交给编辑器，候选为空不自动禁止编辑，候选非空也不强制写入。该行为已经在原型声明中明确，应沿用。[S3]

这是工程上的先选一条可实施路径，不是方法优越性的结论。后续若单轮同样好或更好，可以删除额外抽取阶段。Host仍提供现有的当前维护权限；用户明确要求只读、不保存或取消保存时，候选非空也不能恢复写权限。

### 3.2 当前事实与必要语境

当前消息决定本次要处理的变化；已有来源可帮助解析“那个计划”“原来那项”等指代，但必须标明是旧语境，不能重新当成当前事件。第一版复用已有近期消息或显式引用读取，不额外建设语境选择模型。

抽取结果是候选陈述，不能在不知道旧库的情况下自称“已确定为新事实”。是否重复、是否更正、是否值得持久保存，由同一编辑器结合实际旧状态决定。

### 3.3 定位先用已有方案，不在集成阶段优化检索

首版继续使用现有BGE-m3、普通dense和既定候选规模，保留原文与来源元数据。不要同时接入混合检索、reranker、时间过滤、多后端和Agent检索循环。

如果集中测试显示“一次消息的某项变化已提取，但对应旧事项始终不在候选中”，再增加逐候选检索与去重这一项改动。这样能明确判断改进来自目标定位，而不是与编辑器和Reader同时变化。

### 3.4 事项级编辑与事件历史

一次事件允许同时新增独立事项并修订相关旧事项。新岗位事件不应删除整张财务卡；新增退休活动也不应自动证明旧就业状态仍然适用。

同一逻辑事项应优先保持可追溯的连续关系，但不为维持某个record ID而错误合并不同事件。原始事件和旧版本保留；当前语义解释只声明实际有依据的部分。

不要为完成本轮工程新增全量自动拆卡／合卡平台。复用已有事项字段与编辑器，先把新事件的正常处理跑通。

## 4. 工程实施拆成四个交付包，不先逐包跑科研矩阵

### 包A：统一维护编排，把实验原型接到普通Host

**优先完成。**

工作内容：

1. 从现有配对驱动中抽出最小的“提取→定位→编辑→提交”编排；传入现有模型调用函数、MemoryService和配置，不让方法层自行创建模型或业务连接。
2. 由普通Host和benchmark入口调用同一编排。方法内容、输入投影、候选映射和编辑操作不复制两份。
3. 保留单轮与两阶段两种明确recipe，用一个清晰配置选择；不再增加一组临时feature开关。
4. 保留当前schema、普通ID、版本与提交机制；模型只使用本次实际交付的引用。
5. 函数返回实际结果和未完成事项，最终回答不靠模型自行猜是否保存成功。

建议落点：`methods/edit_memory.py`、`methods/functional_edit_memory.py`、`runners/edit_benchmarks.py`。需要独立编排函数时放在方法层已有合适模块；不要让普通Host导入benchmark runner内部工具。`tools/run_edit_change_pairs.py`只保留复现用途。

**完成标志：**普通入口可以处理一条真实新消息，产生实际提案与回执，随后查询到结果；不是只在配对脚本或模拟transport中运行。

### 包B：接通当前／历史／例外的只读呈现

工作内容：

1. 在现有读取与渲染路径中，清楚呈现一般规则、仍活动例外、共同条件、历史报告和未确定部分。
2. 对已存在、来源支持的`modifies/overrides`关系做确定性展开；不让Reader从不透明ID重复重建同一关系。
3. 例外撤销后依据实际剩余状态呈现一般安排；若一般规则原来就未保存，明确缺失，不能由程序补写正确答案。
4. 保留陈述者、所述对象、报告时间与明确生效时间的区别。时间未知时不猜，未来计划不写成已经完成。
5. 同一Reader先整理必要证据，再直接回答。不增加回答后审查Agent，不修改旧实验答案。

建议落点：`memory/edit_units.py`中的现有渲染与修订证据读取，`memory/retrieval.py`及普通读取适配。只读视图不是第二份长期事实库，不拥有独立写入权威。

**完成标志：**通过普通Host可以分别询问当前与历史；同一个实际状态可以按明确范围显示适用安排。对“整体每周三次”不能无依据推出“每个子组都三次”。

### 包C：接好真实结果、重启、遗忘与未完成维护

工作内容：

1. 用户消息与实际工具结果分别保存为来源；模型生成的解释不能替代业务回执。
2. 新流程复用既有请求／操作身份与回执，避免Host与独立Writer对同一事件重复执行相同维护。
3. 已确认的提交或业务效果在重启后复用；未知业务效果先通过实际工具查询，再决定后续动作。
4. 记忆未提交时保留原始来源及未完成状态，向用户明确说明；不能因为原文保存成功就声称语义记忆成功。
5. 遗忘后的可见性对检索、候选上下文和恢复路径一致生效，沿用现有边界，不新增“全面删除认证”。

建议落点：既有`application/` journal与recovery、`memory/service.py`及普通Host集成点。LangGraph区分线程状态的checkpointer与跨线程数据的store；本版复用这种职责分工，不再构建一套恢复存储。[D1]

**完成标志：**一个已完成步骤不因回答失败而重做；一个未完成步骤仍可显式继续；恢复后的记忆与实际结果一致。

### 包D：整理成一个能直接运行和评测的候选

工作内容：

1. 保留一个开发功能配置、一个实验配置入口；运行命令复用现有CLI，不先建设新控制台。
2. benchmark适配与普通Host使用同一方法实现；隔离的数据namespace是实验隔离，不是互相竞争的事实系统。
3. 接通现有作者评分输出，形成、更新、最终状态和QA分别保存；评分异常不阻塞未受影响的功能调用。
4. 结果保存与事后评分解耦：运行时保存预测和必要快照，集中评分时不重新调用Writer／Reader。官方协议明确要求的诊断调用仍如实执行和计账。
5. 更新一份简短使用说明和一份当前问题表；不为每次提示调整新增一份准入JSON或重复状态文件。

**完成标志：**用同一个候选，既能在普通Host执行日常任务，也能在公开开发数据上产出预测并评分。到这里再启动集中测试和方法比较。

## 5. 最小接口约定：沿用现有对象，不扩建合同体系

以下只是表达职责的伪接口，不是仓库当前已经支持的新API或命令：

```python
# 组合函数使用现有Source、MemoryService、provider和回执。
maintain_event(event, context, memory_service, model_call, recipe)
    -> maintenance_result

# 只读：呈现实际状态、历史与来源，不创建新的业务事实。
read_memory(question, memory_service, query_context)
    -> evidence_view
```

`maintenance_result`应复用现有回执，仅需让调用方知道：哪些操作实际提交、哪些没有变化、哪些未完成，以及对应来源和记录。不是新增一份宣称任务必然正确的“完成证明”。

每次读取只返回实际可见材料。身份、权限、当前版本、实际写入与副作用在负责边界处理一次；方法内部不要层层重复检查同一件事。

### 不新增或恢复的内容

不增加SHA／文件树校验、替代哈希、递归内容指纹、来源置信度门禁、Reviewer循环、全量守卫矩阵、多事实数据库、业务领域关键词路由和无限重试。普通Git版本、现有运行配置与日志足以说明某次实验使用了什么。

已存在且能保护用户数据或真实副作用的检查不能一刀切删除；需要去掉的是重复与无意义检查，不是权限、实际版本和事务本身。校验代码的清理合并到相关功能改动中，不另开长期“消除所有校验”的重构项目。

## 6. 开发期的测试压缩到什么程度

### 6.1 每个工程提交只做必要检查

改动文件的导入／语法、已有类型与格式检查，以及直接受影响的现有测试即可。修改文档不重复模型实验；不为语义提示反复重跑所有机械测试。

不设新覆盖率指标，不按测试数量汇报进展，不强求测试先行。存在真实回归时再补一个最小复现用例。安全相关路径被修改时，复用该路径已有权限和效果用例。

### 6.2 整体集成后，只先做五条冒烟流程

| 流程 | 最少覆盖内容 | 本阶段观察 |
|---|---|---|
| 1. 保存—读取—重启 | 新消息持久化、语义结果查询、进程重开 | 调用和持久化链是否真正连通 |
| 2. 更正—历史—未改内容 | 改一项值，保留历史与另一项无关事实 | 维护是否执行，当前与历史是否可读取 |
| 3. 一般规则—例外—撤销 | 新增局部例外、改变共同条件、撤销例外 | 现有算子和读取路径是否完整使用 |
| 4. 纯查询—不知道—遗忘 | 查询不写入、资料不足不伪造、遗忘后不可访问 | 正常无操作和可见性边界是否有效 |
| 5. 部分业务—恢复—反馈 | 实际部分完成、继续剩余步骤、真实保存说明 | 不重复副作用，不虚构完成 |

这五条是复用的功能流程，不是五套科研实验。可以使用已有故事；不要求全部自然语言回答在此阶段达到最终论文标准，也不为每个措辞生成几十个变体。

**处理规则：**代码崩溃、实际数据损坏、权限错误或重复副作用先修；一般语义漏写、范围理解错误和过度解释进入问题表，继续完成其他功能，再集中优化。未达目标的流程如实标记，不能因允许继续开发就写成通过。

### 6.3 CI与运行资源

保留仓库现有必需CI和合并规则，不为本版降低权限或安全检查。普通本地开发与受控Lab冒烟不再新增“每次运行前核对所有远端blob、全部历史manifest或逐字段摘要”的步骤。

正在运行的旧实验不热改、不覆盖、不擅自停止。工程开发可以在独立工作区推进，不必等待其全部Judge结束；共享模型资源的真实调用需要顺序安排。这是资源限制，不是算法必须等待旧矩阵完毕的科学前置条件。

## 7. 功能接通后，集中跑第一轮测试，不边调边换分母

### 7.1 第一轮只做错误定位，不急于论文结论

使用既有HaluMem四个开发用户前八会话，首先运行一个完整功能候选。保留作者更新、形成、QA及实际状态；同一轮中不调整提示、模型、检索或样本。

这一轮的目的只有两个：

- 找到最常见且实际影响任务的失败；
- 判断故障是实现链缺口，还是方法决策问题。

不用每保存一个事项就调用额外Reviewer；作者评分按原协议执行，并允许在已保存预测上集中运行。快速人工检查只看最重要的失败和少量成功控制，不要求每次开发完整审读所有原文、所有推理与所有HTTP。

已有四个实际前态配对可以在本阶段作为已曝光诊断使用；它们不是新数据，不是普通Host集成的前置门槛，也不因重复运行变成独立样本。[S3]

### 7.2 问题表只保留最少字段

```text
案例／运行标识
用户任务与失败现象
最早断点
计划修改的一个机制
复测结果／仍未解决部分
```

归因使用实际材料，不凭正确答案猜测运行时看过什么。优先区分下面五类：

| 失败类别 | 先改哪里 | 不先做什么 |
|---|---|---|
| 输入或输出未完成 | 整理请求、来源分批、输出粒度 | 不增加审核Agent |
| 该改的旧事项没找到 | 候选表示或普通目标定位 | 不重写Store |
| 新事实和旧目标均已送达但漏写 | 提取／编辑职责和维护提示 | 不继续扩大材料证明 |
| 修订破坏条件、时间、归属 | 局部算子、必要语义表示与证据组合 | 不以提高拒绝率代替效果 |
| 状态正确但回答错误 | 共同只读呈现与Reader任务 | 不把问题全部归因于检索 |

### 7.3 失败不等于必须现场修好

一轮测试收集完成后，按“影响真实任务的范围＋修复价值”选择一个主要问题处理。不要遇到一条普通语义失败就停止全部队列、重新登记整套计划，再从最早步骤运行。

发现未授权真实副作用或数据暴露时停止受影响执行；普通回答错误和记忆漏写则保留为失败，继续其他隔离案例。

## 8. 方法优化按真实断点推进，每轮只改一个主要因素

### 第一个可能的优化：提取是否真的帮助维护

比较已实现的单轮与两阶段流程，使用相同当前原文、相同可用旧状态与同一编辑器。观察新要求完成、非目标损坏与最终任务，不以候选条数作为成功。

若两阶段无收益或更易丢掉指代，回到单轮方案；若有收益但目标召回仍不足，再处理定位。对照额外调用的影响要报告，但本阶段不要求两阶段更便宜。

### 第二个可能的优化：修订定位是否需要按事项拆开

只有实际出现多事项漏召回时，比较“拼接全部变化的一次检索”和“按候选检索后去重”。固定提取结果与总材料规则，避免同时换编辑器。

不要用标准答案、未来问题或隐藏旧记录ID选择目标。未找到目标可以形成新事件；是否需要回到旧事项，由后续语义评价判断，不能强制UPDATE以获得计数。

### 第三个可能的优化：条件化编辑是否优于普通编辑

在共同可用的维护链上，检验一般规则、局部例外、共同条件变化和合法撤销。M的程序只编译模型已经选择的语义操作，不替模型推断不存在的范围关系。

如果普通局部编辑同样好，应采用简单方案；如果条件化表示稳定减少附带损坏，又不妨碍合法更新，才形成方法贡献。例外词或故事模板不能硬编码进入方法。

### 第四个可能的优化：读时视图是否减少重新解释错误

固定实际记忆状态和原问题，比较普通渲染与结构关系展开。只展开实际保存的关系，不把期望答案写入视图。

若同一状态仍含来源冲突，清楚呈现差异；若来源不足则保留未知。不要把所有不确定性都硬过滤为拒答，也不让多个Reviewer投票替代真实证据。

### 不同时展开的研究

不在本阶段训练RL策略、接多后端路由、增加长期状态图、重新启动复杂主动消歧选源或自动技能演化。它们不是功能候选必须具备的能力。

## 9. 集中方法比较：保留强对照，但不为每次补丁跑全矩阵

### 9.1 主比较

在第一轮集中测试和主要修复之后，选择一个共同底座，运行：

| 方法 | 用途 |
|---|---|
| B0：普通表示＋事项全量重写 | 合理的全量维护基线，不重写整个用户档案 |
| B1：普通表示＋局部编辑 | 排除“只要少重写就足够”的解释 |
| B2：条件表示＋事项全量重写 | 分离表示的作用 |
| M：条件表示＋局部语义编辑 | 评价条件、例外及撤销算子的额外价值 |
| Append-only：带来源与时间的事实追加 | 比较写时维护与读时重建，不因其不执行UPDATE就判失败 |

各组使用同一模型、共同提取方式、同一原始输入权限、合理材料预算和Reader。记录与历史由每组从自己的空库形成。追加式对照使用同样有用的候选事实与时间来源信息，不故意做成无法检索的原始堆积。

RawRAG、Rolling Summary和已接入A-MEM复用现有适配；初期不为纳入所有外部名称延迟核心实验。正式结果至少保留与最终主张直接相关的强简单对照，额外系统按实际可用性选用。

### 9.2 研究问题与比较对应

- B0对B1：局部改写相对于完整事项重写，是否减少非目标损伤？
- B0对B2：条件表示本身是否有帮助？
- B2对M：相同表示下，局部语义算子是否增加净收益？
- M对Append-only：维护当前解释是否比读取时重新协调事件更可靠？

不要把共同检索、事项组织或抽取步骤的改进全部归给M。选择两阶段共同底座时，所有方法都可以使用它；其独立作用在小型消融中分析。

### 9.3 数据使用顺序

**开发：**既有四用户前八会话与已曝光失败用于调试和方法选择。

**长历史：**候选稳定后运行预选用户完整65会话，再继续其余开发用户形成277会话范围。若同一版本和同一配置本来就是连续运行，65只作为中间观察点，不额外重复执行一遍。发生方法变化则新的比较从独立状态重新开始，不接旧后缀。

**确认：**最终候选冻结后使用16个保留用户。测试后再改方法，该部分即视为已曝光，不能反复调试后仍称未见。

**外部验证：**继续LongMemEval已登记子集和真实可运行适配。28题是描述性子集，不是完整500题结果；需要扩大覆盖时在方法选择之后一次性确定，不在开发阶段不断更换benchmark。

**普通Host：**完整候选定稿前集中运行已有普通功能回归和必要的新故事，不为每次局部修改重新执行全部135案例／192消息范围。[S1]

## 10. 最少但足够的结果表

不再增加“通过项百分比”总评分。结果表只需要回答：

| 结果 | 评价含义 |
|---|---|
| 目标完成 | 新事实、当前更正、合法撤销是否真正得到体现 |
| 非目标保持 | 仍有效条件是否丢失、强化或错绑到另一主体 |
| 来源与时间 | 陈述者、主体、报告时间、事实生效时间是否正确 |
| 任务表现 | 官方更新／QA，以及原问题是否完整回答 |
| 可用性 | 输入失败、截断、错误提案、漏写、必要操作是否实际完成 |
| 实际消耗 | 生成、编码、Judge和延迟；未知单列，不与累计子集重复相加 |

官方分数与补充语义检查分别报告。无效Judge标签保留原值，不能静默映射后冒充原评分；复算分析作为单独版本保存。不把各方法动态生成的提取条目当成统一独立样本。

四个开发用户和多个同模板变体只适合开发判断。正式不确定性按用户或来源历史聚类，不能把同一历史多个问题当成独立用户。只使用现有Qwen家族，同家族Judge不称独立确认；抽样人工复核范围如实披露。

质量与正确性优先，但不能用无限重试堆出成功。开发调试可以有限重跑，前后结果分开；正式冻结比较不挑最好的回答，首尝试与声明的后续恢复分别报告。

## 11. 执行顺序与停止增加复杂度的条件

| 顺序 | 工作 | 本阶段交付 |
|---|---|---|
| 1 | 包A接通共同维护与普通Host | 一个真实可调用维护链 |
| 2 | 包B读取视图＋包C效果恢复 | 一个能够保存、修订、读历史并继续任务的功能候选 |
| 3 | 包D运行与评分接线，五条冒烟 | 一套可重复使用的运行入口与简短失败表 |
| 4 | 集中开发集测试 | 最早断点分布与优先修复目标 |
| 5 | 针对首要断点修改方法 | 一个因素的可解释改进，不另起平台 |
| 6 | 同版主比较、长历史、确认与功能回归 | 方法收益、适用范围及剩余失败 |

包A至D之间可以连续开发，不要求每包取得完整科研评分后才进入下一包。预备脚本、历史配对和CI是工具，不再拥有独立的开发进度目标。

### 明确的收敛选择

如果单轮与两阶段相当，采用更简单的单轮；如果普通局部编辑与M相当，采用普通局部编辑；如果追加式事实记忆在目标任务上更可靠，就保留追加式方案并收缩写时修订主张。

这些决定不等于整个MiLAi失败。总目标是可靠的长期记忆与任务完成，不是维护固定算法名称。

若条件化编辑在真实连续更正、未见来源及后续任务中确有额外价值，再集中补必要消融与论文论证。未开源或尚未正式发表的近邻作为相关工作说明，不作为工程开发的自动否决项；具体重叠按已披露机制分析。

### 原方向保留

继续保持Grounded Memory、Verified Object References、Semantic/Episodic Memory、Grounded Revision与Lifecycle Recovery；一个逻辑MemoryService，记忆自由文本不能创造业务身份或实际效果。

v13.4的Simplify仅关闭原复杂关系消歧选源分支，不禁止当前编辑方法或追加式强对照。本版不恢复其T1–T3，也不以旧退出结论代替新实验。
