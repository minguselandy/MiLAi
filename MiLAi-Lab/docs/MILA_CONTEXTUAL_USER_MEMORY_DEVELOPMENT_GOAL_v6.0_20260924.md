# MiLAi Lab：主体归属、修订依赖与同批历史整理修复 Goal

**本轮修复已经观察到的三类语义错误，并保留 v5 打通的真实执行路径：谁的经历要记对，修订不能变成对自己旧版本的活动依赖，同批早晚表达要形成清楚的当前理解。**

当前限定修复已验证，Goal 完成。用户要求移除的复核次数与累计用量硬停止已取消，费用持续记账。最终同一源码的三个原题、五条固定路径均完成并通过原生评分，主体、修订依赖、历史范围及新偏好得到实际验证，作答未新增持久事实。整体质量仍未确立；宽泛聚合、局部过度推断和早期失败不隐去。详细证据及 243 次生成的完整成本见第 13 节和[本轮结果](CONTEXTUAL_USER_MEMORY_V6_RESULTS_20260924.md)。v5 已关闭，其结果、源码快照及 114 次请求不变。

## 1. 起点与明确不重复的工作

开发开始前，38个实现文件与v5最终默认及State冻结源码一致，基线映射散列见文件头。基线运行身份为方法v8、operation v2、write v3、ingestion v9、material view v1。最终开发身份及验证限制见第11节。

已经有真实证据的能力继续使用：程序接收原始来源、同一 Host 创建／修订、准确版本与 CAS、局部提交恢复、非破坏性普通维护、精简材料、State 初始化及后续 search 消费。不要再次把实现这些组件列为交付目标。

| 已观察问题 | 实际证据 | 本轮修复目标 |
| --- | --- | --- |
| 主体误归属 | v1003 将 assistant 自述发表文章写成用户经历 | 来源说话者、记录作者和被描述主体分开；不把 assistant 自述变成用户事实 |
| 修订依赖错误 | v1003 新版本依赖自己的旧版，也出现无必要的跨事项依赖 | 版本继承由程序维护，活动依赖仅表达独立语义前提 |
| 同批历史未整理 | v977 自然一批将开始写博客和后来停写分别建卡 | 保留历史，同时形成当前事项的清楚表达，避免把早期活动当作当前建议依据 |
| 作答写入污染 | 默认作答新增无来源的持久偏好卡，混入问题与建议 | 历史维护有依据；任务推断和独立想法不能冒充已取得的用户信息 |
| 旧新选择错误 | v569 已取得新偏好，仍采用旧偏好 | 用作上述修复的有限读取回归，不另加重排算法 |

最后两项纳入前三项的共同写入与交付边界，不新增研究模块。默认原生评分 0／1／0 保留；Judge 与答案的解释差异不能直接证明记忆失效，也不能据此改计通过。

继续冻结 H1—H6，不新增候选、知识图谱、全局主题注册表、第二推理 Agent 或语义审核 Agent。不改变检索排名、top-k 默认值、模型权重或评分规则，不重写事务，不迁移 Product。

## 2. 目标流程与责任

```text
授权历史及准确角色／到达顺序
  → 程序接收来源并发布短句柄
  → 同一次 Host 提案：明确主体、当前理解、依据及独立依赖
  → 程序绑定引用，检查结构、目标版本及已知不合法关系
  → 提交当前记录，保留旧版与原始来源
  → 公共材料呈现主体、来源角色、时间语境和真实限制
  → ordinary 或现有 State 路径读取并回答原始任务
```

程序处理身份、引用、顺序、版本和确定性的关系规则；Host 判断材料说的是谁、哪些内容构成同一事项以及新信息如何改变理解。准确引用不自动证明语义支持，合法 JSON 不自动证明运行后端能生成该分支。

## 3. 修复 A：主体和依据进入同一写入合同

### 3.1 不再让 subject 同时承担身份和主题

当前 `Interpretation.author` 是记录作者；`Observation.role` 是原始说话者；自由字符串 `subject` 常被写成事项标题，默认值又是 current_user。它们不能共同代替明确的“记录关于谁”。

增加一项轻量主体引用 `about_ref`，由 Host 从本次交付的主体句柄中选择，程序绑定后保存。保留 `subject` 作为事项说明，不按自由文本中的“user”“I”等词猜主体。

| 主体引用 | 绑定规则 |
| --- | --- |
| 当前用户 | runner／适配器提供当前用户身份 |
| 某份来源的说话者 | 由准确来源句柄及接入角色绑定；不得由模型改写 role |
| 未明确的第三方或未指定主体 | 保留未确定状态及叙述，不自动绑定当前用户 |

不建设人员识别服务，也不把 assistant、tool 或 document 中出现的所有人合并成同一主体。来源说话者与正文讨论对象可以不同：用户讲朋友的经历，不等于用户自己的经历；assistant 转述用户，也不等于用户亲自确认。

说话者句柄依据 exact source 的完整 local key 稳定命名，摄入与作答投影共用规则；不是人物识别，也不将所有同角色来源合并。句柄仍只有在原文实际交付后才可用。模型可见材料先呈现主体、角色及依据，再呈现正文，防止旧正文里的局部别名盖过准确身份。

主体选择是 Host 的语义提案，程序只验证句柄与接入身份，不为其正确性背书。缺失主体不能静默补成当前用户；旧 checkpoint 的缺失值不能迁成“已经确认的用户事实”。新实验重新形成记忆。

### 3.2 依据明确，但允许独立记录

历史整理维护当前用户的情况、偏好及相关关系。其他说话者的无关自述保持可检索原文即可，不因出现在对话中而额外建立传记；有依据的用户关系、限制或语境仍可形成理解。

普通历史维护的 CREATE／REVISE 显式提交 `source_refs`，引用已交付来源。这个阶段的工作是整理已有历史，不能以保存来源代替理解，也不能把无依据推断包装成历史事实。Host 不抄写角色、散列或字符偏移。

普通服务仍允许没有外部来源的作者笔记、工作假设和任务想法。此类记录注明作者及未关联来源，缺少来源不等于无价值；但不能取得“用户已经表达过”的地位。不要重新引入 Evidence／Note 内容分类器。

作答时提出关于用户的持久理解，应关联已取得的历史依据。只有问题前提、本轮建议或模型自己的答案时，不形成新的持久用户事实；可以进入任务 State 或明确的作者记录。新用户反馈必须先按正式接入路径形成来源，再参与维护。

持久 current_user 理解至少需要非 assistant 的已取得来源：只有 assistant 生成文本时，CREATE／REVISE 明确拒绝，不能自动改主体或降为任务记录。assistant 原文、准确说话者记录和作者笔记仍可保留。此规则是来源权限的必要条件，不证明 user／tool／document 的引用足以支持全部正文；仍须检查真实提案含义。

材料投影给理解保留 `about_ref` 的可读主体、作者及所引来源角色摘要；来源入口照常可展开。不能通过隐藏 assistant 材料、把所有 assistant 内容判为无效、或禁止正常记笔记来降低错误数。

### 3.3 真实语义验收

v1003 中 assistant 发表文章的自述可以保留为来源或正确归属的整理，但不能再成为无保留的用户履历。同时，真实 user 表达的志愿服务转向必须继续被创建、修订并使用。

引用一条无关 user 消息并不能使错误归属合格。检查实际正文及其依据，不只检查 `about_ref` 或引用数组非空。若模型仍选错主体，保留为修复未完成，不能把结构校验通过当作问题解决。

## 4. 修复 B：修订历史与活动依赖分开

### 4.1 三种联系分别处理

| 联系 | 含义 | 实现方式 |
| --- | --- | --- |
| 版本历史 | 当前记录由哪个前版修订而来 | 继续由准确 target_ref 和现有 history 自动记录 |
| 来源引用 | 作者整理时用了哪些原始材料 | source_refs；不认证推论正确 |
| 活动语义依赖 | 当前结论需要另一条理解作为前提，该前提改变应重新检查 | dependencies 中的准确已交付版本 |

REVISE 的 target_ref 不应同时作为自己新版本的活动依赖。内部版本链已经保留前版，不要求 Host 为了“保留历史”再把它填入 dependencies。

对于比较或引用过去表达的任务，历史仍可通过准确版本读取和版本链展开；不要用活动依赖模拟历史引用。此轮不扩充一套通用引用图。

### 4.2 全文修订必须明确更新依据与依赖

当前 save 在省略 source_refs 时沿用旧来源，省略 dependencies 时复制旧依赖。对整段正文替换，这会把不再适用的依据和关系悄悄带入新版本。

新普通 REVISE 合同要求显式给出 `source_refs` 和 `dependencies` 两个完整数组；独立依赖可以为空。Host 应看到目标原有依赖及其准确版本、来源角色和范围，再决定哪些仍成立。不让服务自动换成最新引用，也不自动清空所有关系。

新来源不能机械覆盖一切旧依据：若新正文仍保留旧材料支持的部分，应保留相应来源；若只是重写表达、没有新来源，仍可显式引用已经交付的原依据。这里要求声明清楚，不要求每次修订都必须出现新的外部消息。

这项语义收敛落实在共享普通提案合同与提交入口；既有内部元数据补丁如需保留省略语义，应以明确内部路径区分，不能让同一个外部 REVISE 同时表示“完整替换”和“随意继承”。

### 4.3 确定性边界保持简单

- REVISE 将本记录任一版本作为活动依赖时，拒绝这一操作并给出简短原因；不静默删除该依赖后声称按原提案提交。
- 跨记录依赖继续要求准确已交付版本；程序不把语义相关自动当成必要前提。
- 真实独立依赖更新后，原有 NEEDS_REVISION 必须继续触发。不能为让材料显示正常而关闭依赖复核。
- 旧错误 checkpoint 保持原状，只读诊断；新协议从原文形成新记忆，不批量删除旧依赖来制造修复结果。

v1003 的志愿服务修订不再依赖自己的旧版，也不因无依据的 AI 兴趣卡依赖而被误标；仍保留合法修订链、来源与独立依赖能力。

## 5. 修复 C：同批整理当前理解，同时保留历史

### 5.1 一次维护处理整批关系

自然一批中出现“开始写博客→后来停写”，Host 应先比较同一主体、事项及场景内的表达，再提出该批应保留的当前理解。原始早期表达由来源保存，必要的历史脉络写入 context 或按需展开。

这不要求人为先建一个过时卡，再在同一批修订它。没有既有卡时可直接创建包含当前结论及历史限制的记录；在线到达时则正常对已交付旧卡 REVISE。

不新增同批虚构版本、复杂别名事务或第二次“审查提案”模型调用。沿用一次 Host 提案及现有局部提交。已有记录需更新时，将同一准确目标的变化合为一项操作。

### 5.2 顺序是依据之一，不是“最新一句永远正确”

从已有 source_sequence 交付简短的来源到达顺序，原 date／session 信息保留。读取源材料时也能看见相关顺序，避免只剩多个 CURRENT 标签。序号由程序提供，不让 Host 抄写为世界有效日期。

到达较晚可能是在回忆更早经历、提出假设或讲第三方。Host 仍须理解正文的时间与适用范围；临时场景变化不覆盖一般偏好，未知日期不补成系统日期。

`CURRENT` 继续表示对象当前版本，不等于正文描述的是用户现在的状态。公共材料应清楚表达这一点，保留历史／范围叙述；不要改造评分或把全部早期来源从检索中删掉。

### 5.3 不以错误合并换取少量卡片

影评博客与 fan-trailer 是不同事项，停止影评不能自动覆盖后者。不同场景下同时有效的记录可并存；无法确定取代关系时保留冲突或范围，不生成虚假的统一结论。

首版不做按相似度自动合卡，不建立主题字符串唯一约束，不按题目词汇写规则。主体引用、事项说明、来源和时间语境已经足够支持同一次 Host 判断；实际效果由固定原题检查。

自然分批与在线分批不要求卡数、措辞或版本数一致。要求当前理解不把已停止事项当作当前实践，无关事项不被覆盖，原始历史不丢失。

## 6. 保住真实执行能力与生成后端可达性

v5 曾出现 JSON Schema 静态合法，但实际 XGrammar 因字段顺序和日期正则限制而使常见输出前缀无法进入 CREATE／REVISE。新的字段、分支和必填项必须经过现有实际版本编译器的窄检查。

继续使用 op-first 分支，保留已修日期形式与日历校验；覆盖 CREATE、REVISE、带原因 NO_CHANGE 和保留来源的实际有效输出形式。不能只验证 JSON.parse 或 jsonschema，也不新建语法测试平台。

State 首轮仍只表达任务理解，取得材料后再使用引用型字段。ordinary 默认与 State 功能配置身份分开，不把强制初始化误称模型自发调用，不将功能回归当作 State 独立收益实验。

修复不能靠取消保存、取消修订、关闭 State、全量返回原文或全部答“不确定”通过。真实用户理解必须继续形成、修订、进入材料并用于完成任务。

## 8. 有限验证与成本

### 8.1 先离线，再用真实 Host

只复用受影响的现有窄检查，并补缺失语义：

1. 主体句柄、来源角色和作者不混用；无来源作者记录仍合法，但不自动变成用户事实。
2. 全文修订显式提交来源与依赖；自身版本依赖被拒，真实跨记录依赖失效仍可观察。
3. 来源序号与实际消息顺序一致；CURRENT 版本含义、叙述范围与未知时间保留。
4. 实际 XGrammar 可以接受新写入分支；保留日期与 State 分阶段 schema 的现有修复。
5. 沿用相关引用、提交恢复和材料预算检查；只有改动影响删除边界才补跑对应用例，不重跑全部生命周期矩阵。

这些检查不冒充 benchmark 结果，不修改原题或 gold。静态检查限定受影响代码；移动包边界时才运行边界检查，修改打包时才构建。没有全套测试计划。

### 8.2 固定原题与运行顺序

采用已暴露 MemSyco 三题：v11_001003、v11_000977、v11_000569。v1002、未用确认集、其他数据集和完整 STALE 不进入本轮。先固定运行身份，再调用模型；方法输入只含合法历史及任务，不含 gold、Judge 解释或本表的诊断标签。

| --- | --- | --- | ---: |
| 1 | v1003 原顺序 6 批；ordinary 与现有 state 各自形成历史并作答 | 主体正确、同事项真实修订、依赖正确；State 消费及后续取材保留 | 2×（6＋6＋1）＝26 |

共三个独立原题、五份历史构建、五份计划答案；不能报告为五个独立样本。完整保留各题原文、消息顺序、问题和评分标准。自然容量若不能容纳原计划一批，应先记录实际批数、调整请求预留；不能删历史来维持表面一批。

当前 history_write_identity 包含 contextual，ordinary 与 state 不满足共享 owner 校验，因此首版各自构建，不能手改 checkpoint 标志绕过身份。两者仅检查功能回归，不比较 State 质量，也不能互相继承答题写入。未来只有写入身份确实相同的配置才沿现有规则共享；本轮不为节省六次摄入重构 profile／缓存合同。v5 冻结答案用于诊断参照，不作为新源码的同时对照；本轮没有 H2 效果复跑。

每次摄入后检查实际提交的主体、依据和当前关系，再开始该实例答题。有明确新回归时先定位，完成有依据的修复后继续该路径；不得用下一题的通过掩盖它，也不因复核次数机械停止开发。没有需要维护的信息可 NO_CHANGE，但三项已知语义缺陷不能用“未覆盖”代替修复。

### 8.3 连续记账与按问题开展的小规模验证

2026-09-24用户明确要求“反思解决当前错误问题，移除限制”。因此取消“一次局部复核”、相同故障复现即终止开发，以及72次生成／350000生成tokens／80000 embedding tokens的累计硬停止。以上数值保留为首次计划，不能再作为阻塞修复的理由。若假设被真实结果推翻，应重新分析并修复，不进行没有变更依据的重复请求。

所有摄入、作答、Judge、诊断调用、失败和修复继续记入同一个 `v6-budget.json`，既有57次／232814生成tokens／18595 embedding tokens不清零。解除限制前账本和授权记录保存在 `v6-budget-before-authorized-unlimit.json`；v5的114次与旧账本保持封存。

开发和验证仍逐个问题开展：先检查具体失败批次，再从原文形成新历史并作答，最后检查受影响的既定实例。每次调用仍使用既有上下文及输出容量、单次批量提案和6次答题上限；不扩题、换模型、改gold或为了追分盲目重试。原固定五个答案名额及追加局部验证分开记录，不冒充独立样本。用户先轻量跑通、开发完成后才考虑大规模测试的要求不变。

Host、必要的原生 LLM Judge 均使用既有 vLLM 服务与固定身份；不启动额外语义裁判。原生分数、对来源／主体／版本的诊断分列；Judge 有解释争议时保存依据，不能人工改分或为单题更换 rubric。

| 项目 | 必须满足 | 不能作为替代证据 |

当目标修复和必需功能回归成立，原生评分仍有失败或争议时，可以分别报告“限定修复已验证”和“整体质量未确立”；不要求本轮证明统计优势，也不能声称模型已可靠记忆所有用户信息。

完成不要求 H2 赢得分数，不产生新候选或创新性结论。ordinary 保持基线；是否扩大研究，应以后续实际质量和成本证据决定。

## 12. 用户解除限制后的反思与继续开发

前次把模型生成正文与来源不一致归类为语义问题后，又把“一次局部复核”当成继续工作的障碍，未继续研究可改变的生成合同，这是处理不足。结构可达并不代表当前提案顺序有利于正确整理。现在聚焦同一个失败：检查正文先生成、引用后选择以及旧材料覆盖新观察的输入顺序，采用可泛化的小改动并真实验证；仍不引入语义分类器、第二审核模型或绕过失败验收。
