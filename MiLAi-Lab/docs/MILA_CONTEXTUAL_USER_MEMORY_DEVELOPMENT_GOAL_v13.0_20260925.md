# MiLAi Lab v13 Goal：完成正式运行入口、失败处理提示与最终连续验证

**目标：把 v12 已验收的修订和恢复能力接入正式准备／运行流程，减少修复已经提交但终结仍需补一次拒绝的操作负担，并在同一最终源码和配置上从原始初态完成一个小规模原生连续场景。**

用户本轮授权制定详细 Goal 并完成后续开发。本 Goal 中“全部开发”指核对当前代码后确定的 A—E 工程范围，包括实施、窄检查、真实有限验证和交付；不将“证明方法优越性”伪装成可以靠补代码完成的任务。ordinary、notes、State off、thinking=false 继续作为本轮默认。

**A—D 工程完成，E 的限定连续验证完成，但首次约定持久化验收未达到，任务质量未全部通过。** Host／恢复检查 28 passed，准备／MERIT adapter 检查 10 passed；相关 Ruff、mypy 通过。结项表示本轮工程与诊断交付完成，不表示所有语义问题已修复。

E 的 R1 得到原生 4/5、dependent 2/2、Host 7/7；首次未来约定零写入。针对这一新定位的问题，R2 只增加通用 finish 目的澄清，从相同原生初态完整复核，结果仍为 4/5 且首次约定仍漏存。已撤回这项无效提示，最终 46 份运行文件与 R1 冻结完全一致；没有把不同阶段的成功片段拼成最终结果。两轮全部失败和费用保留，未继续叠加提示或扩大题量。

最终结果与成本见 [v13 报告](CONTEXTUAL_USER_MEMORY_V13_RESULTS_20260925.md)。本轮累计 56 次生成、337502 输入＋7873 输出＝345375 generation tokens；18 次 embedding／2797 tokens，unknown=0、Judge=0、截断=0。

## 2. 实现范围

### A. 基线与运行身份

核对已提交的 v12 源码冻结、报告与本地制品；记录当前工作树状态。保留 v12 Goal 已完成的身份和全部失败，不覆盖原账本、源码冻结、世界或 trace。

v13 是开发阶段名，优先沿用当前 contextual-task-v12、JSON action v4、maintenance v4 及磁盘格式。仅说明与入口扩展不凭空增加协议版本；实际源码映射明确区分本次行为。

完成依据：本轮改动从已知基线开始，历史文件身份可复核；新输入和计账目录独立。

### B. 减少维护修复的操作负担

继续使用显式 repair_of、有理由的 abandoned_attempts 和 pending，不新增审核器、不自动消除失败。

两处改进：

1. memory_save 失败回执直接带出程序记录的未决操作 ID，说明它与卡片 mN 句柄的区别，以及何时使用 repair_of。
2. 后续提交成功却仍有未决尝试时，成功回执同时说明：本次提交已经发生；不要仅为补填 repair_of 重放相同写入。如果 Host 确认旧提案已被该提交取代或不再需要，可在同一次 finish 中有理由地处理旧 ID；否则继续修复或 pending。

同一卡的任意成功不能自动消除所有失败。若确有新变化仍允许再次修订，不能把“不要重复提交”变成禁止合法后续更新。

提示由当前维护状态生成，只在存在相关未决尝试时交付。保留现有安全错误码和短引用，避免暴露未交付正文或整个内部账本。没有失败的普通操作不承担额外填表义务。

完成依据：合成的真实 Host 接线中，正确 ID 可用于修复；成功提交后未决项仍存在且可在首次合法 finish 处理；无关失败仍阻止假完成。语义上的“已被取代”由 Host 判断，程序只核验真实操作和未决身份。

### C. 补齐正式准备和 MERIT 运行入口

扩展已有工具，接纳 configs/contextual-memory-v12-notes-template.json，不复制一套 v13 runner。正式入口沿用下列合同：

- 仅 ordinary／notes／State off，maintenance v4，decision feedback 与 gap focus 关闭。
- 配置路径、完整配置 SHA、模板 SHA、源码映射及模型身份必须匹配。
- 原生 MERIT 提交、生成参数、消息、工具、初始世界和 scorer 不变。
- thinking=false 在 Host 与 tokenizer 容量配置中保持一致。
- 新输出目录明确绑定同一配置和输入；已存在运行制品不被静默覆盖。
- 旧 v9—v11 的准备与身份语义保持，不通过放宽全局校验接纳新版本。

源码映射包含当前模板和本轮修改的入口。可将必要的少量版本判定收拢，但不进行跨模块大重构或引入通用插件框架。

补一条实际模板的零模型准备／校验检查，并检查错误的维护协议或启用额外控制能力不能冒充本配置。复用原生身份 fixture，不复制新的 benchmark 题目。

完成依据：从正式 CLI 可生成配置、模型清单、冻结文件、原生 selection 和运行命令；prepare-only 不调用模型；运行器接受同一组产物。

### D. 开发冻结与必要检查

B/C 完成后，运行受影响的窄测试及静态检查。新改动未触及 schema 时，核对生成 schema 身份而不重复整个部署探针集。没有包移动／新依赖就不跑打包与全量边界套件。

记录最终源码映射、当前模板、Host／embedding 权重身份、推理及容量设置。完成这些再启动真实调用，模型并发为 1。

不通过提高请求上限掩盖故障。本轮累计调用、tokens、验证次数保持 null，单条消息现有容量仍保留；实际新问题允许继续定向修复，但每次额外调用需有明确原因和新身份。

### E. 一个最终版本的原生连续验证

使用已经暴露的默认 MERIT arc0-000，原生五个 episode、七条公开消息、两个 dependent episode。使用既有冻结选择；不挑新 seed，不修改任务，不增加比较臂。

从原始业务世界、空持久记忆和新运行库开始，顺序及 episode/session 边界原样保留。Host、持久记忆、业务日志、维护和评分全部走正式入口。

观察至少包括：

1. 首次约定实际保存；同事项更正修订正确原卡。
2. 后续原生业务读取当前值，执行回执与任务要求一致。
3. 执行后记录反映真实结果，业务通过不替代维护检查。
4. 发生写入失败时有明确的修复／放弃／pending 结果；若没有发生，报告该路径本次未自然覆盖。
5. 完整输入／输出、拒绝、截断、embedding 和恢复费用连续保留。

原生 checker 直接评分，不需要另加 LLM Judge。语义维护检查使用持久记录与真实回执，不改 gold 或原生分数。出现语义限制就如实报告，不为通过而添加金额、订单、客户或工具名称专用策略。

完整运行若中断，保留未评分状态与业务效果；只能在新问题定位后修复必要部分。不同源码的前后缀不称为最终完整链；若要宣称最终源码连续通过，必须在该源码下从原始初态形成真实完整结果。
