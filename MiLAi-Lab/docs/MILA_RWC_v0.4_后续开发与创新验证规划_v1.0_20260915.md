## 0. 本轮决定

**不再扩建架构，不再重新接 baseline。以已经实现的 v0.4 为工作底座，在真实任务中改进方法，并用有针对性的对照区分：运行修复、完整方法价值、特殊政策贡献。**

本计划固定必要的执行与比较边界，不冻结认知流程。允许修改政策、记录粒度与已有材料选择方式；每项修改说明它准备改变哪个后续决定。小比较不是新的 PASS Gate，候选不必先获胜才允许改进。

优先顺序是：

> 现有版本的一次真实整体使用 → 定位有价值的记录—行动联系 → 实现或删减一个通用规则 → 同版本完整比较 → 不调参迁移 → 最有信息量的贡献拆解。

其中局部拆解可以提前帮助设计，不以总体成功率必须先显著提升为前提。完整方法尚未取得行为收益时，也不要求把 N1–N4 全部拆完。

本文交付规划，不修改仓库代码，不启动模型、容器、服务、公开保存或回归。旧实验额度不承接。

## 2. 研究方法的核心：让已有工作对下一步产生恰当影响

保持此前的真实动机：复杂工程、持续维护和多来源工作中，不重复无价值的尝试，不遗失仍有效的约束，不被旧判断固定，也不因内部控制迟迟无法交付。

本轮优先研究一个组合：

> **依据及适用范围的维护（N1），能否通过 Frame 与实际材料使用，改善下一步和交付（N4）；同时保留可暂挂、可重新判断的其他路线（N2/N3）。**

N1/N4 优先不是关闭联想与恢复方向，而是因为当前最明确的历史问题恰好是“记录写出缺口，却没有改变行动”。[S2] N2/N3 在真实机会或明确标注的续接诊断中观察，不要求每个任务都演出这两种行为。

### 2.1 更新规则的开发对象

使用现有 `working_note / cards / frame`，不增加语义依赖 DSL 或新的认知模块。

1. 记录服务于后续决定，而不是尽量复述历史。允许短记录、无变化和不建卡。
2. 新结果可能维持、缩小、拆分或推翻旧判断；不能强制每次只作局部修改。
3. 候选可以先保留，但保留不等于投入工具预算，选中不等于采信。
4. 暂停原因消失只触发重新评估；必要细节缺失时再回读。历史回执不能取代当前世界检查。
5. Frame 表达当前值得推进的问题和目的，不编译成强制工具命令。
6. 已有依据充分时可以直接交付；缺少依据时选择有价值的动作或收窄结论，不自动延长检查。

这些属于政策设计，不是关键词触发器。人类记忆与 ADHD 执行支持保留为功能启发，不作为 Agent 效果或新颖性的证明。

### 2.2 开发允许的具体变化

| 真实轨迹暴露的问题 | 在现有结构中可做的修改 | 预期变化及负面风险 |
|---|---|---|
| 记录把写文件或代码意图当成行为已确认 | 改记录选择与修订政策，保留观察的覆盖范围 | 减少无依据完成；不能因此要求所有任务无限补测试 |
| 卡片写了重要未决项，Frame 仍是泛泛“继续完成” | 改 Frame 的消费政策，使重要缺口进入当前问题 | 下一步更具体；也可能增加不必要调查 |
| 新反馈只影响一个边界，整个任务被重做 | 让维护保留仍有支持的部分及来源 | 少重建；不能保护已被推翻的基础假设 |
| 工作区正文反复出现互相冲突的旧版本 | 核对现有版本投影和卡片归档；语义冲突由模型修订 | 减少干扰；原始材料仍可读，不静默消灭反证 |
| 批处理期间 Actor 机械服从滞后的 Frame | 先核对新反馈是否真正送达，再调整已有共同提示或局部调度配置 | Actor 能修订旧安排；不能由 Host 代作领域判断 |
| Controller 大量无变化，实际没有帮忙 | 查看生命周期触发来源，必要时比较已有 batch=1/3 | 削减内部开销；不能以记录不变直接证明调用无用 |

不要在实跑前把上表全部实现。依据具体轨迹选择改动；已经正常工作的部分保持不动。

## 4. 开发安排：四个可交付工作包，不设新的准入链

### W1：让 v0.4 在一个完整真实任务中工作

**不先改算法。**以当前代码与政策跑一组新版本真实使用，观察现有改动，而不是再次回放第十三次草稿。

只补妨碍观测的局部日志缺口：模型调用类别、维护触发原因、当时剩余额度、实际工作区版本、实际送入 Actor 的引用、新反馈位置、交付状态及原生评分。已有字段直接读取；没有具体归因用途，不新增遥测字段或审计系统。

产出是一组真实结果及一个明确下一开发决定，不要求候选获胜。

### W2：围绕一个联系改进政策或实现

从 W1 或既有真实轨迹中选择一个具体问题，例如“缺口被记录但下一步未改变”。允许最多两次有解释的局部迭代；不是终身只准两个想法，而是本工作包避免无限调词。

每次只写一段：

> 观察到了什么 → 准备改变哪个通用操作 → 预测下一次选择怎样变化 → 在什么结果下删除或保留。

可以组合修改记录形成和 Frame 消费，但先报告组合。若只是输入没有实际送达，修工程，不把它命名为新机制。若是模型能力不足，不增加 Controller 层数来掩盖。

相应局部对照可以在整体分数打平时开展；不等待普通方案稳定失败。选定版本再做一次完整 SIMPLE/RWC 配对，不把两版最好结果拼在一起。

### W3：同一方法迁移到其他任务

在不同问题家族中使用相同政策、Actor 和通用运行配置。先选两个未用于该政策调试的原生任务；每个任务给三臂同一上限，方法各保留自己的维护机制。

这些任务若已出现在旧清单、读过 metadata，就称“开发迁移”，不是未打开确认集。任务真正进入政策修改后，也从迁移用途转为开发用途。

### W4：最少贡献拆解与收敛交付

选择当前最影响解释的一个问题：记录形成、Frame 消费、状态连续性、选材或条件返回。不要求全做，也不建立完整因子矩阵。

交付当前最小有效版本、实际证据与限制。若只证明工程修复有效，就如此报告；若无独立政策收益，保留简单选择，同时明确哪些机会未覆盖。

能观察 v0.4 新运行条件下的交付、任务结果、内部分工与成本；能比较当前 SIMPLE/RWC 政策差异，以及 OM/RWC 的完整方法差异。

当前阶段不要求所有三臂成功，不因 baseline 答错而删除配对，也不把没有发生回读记为回读能力失败。

## 6. 创新验证：从操作假设到可反驳的行为

| 候选 | 当前可操作差异 | 支持它的行为 | 会削弱它的行为 | 最小诊断 |
|---|---|---|---|---|
| N1 依据范围修订 | 同样新反馈下，维护哪些旧判断、怎样限定它们 | 减少局部结果过度推广；保留仍有依据的约束 | 记录更复杂但行动不变；或保留了错误旧结论 | 相同前缀下不同维护政策形成记录，共用后续 Actor |
| N2 联想/投入/采信分离 | 卡片保留线索，Frame 选择当前投入，未选原文可恢复 | 不因未证实线索偏航，又保留有用替代入口 | 只增加文本；选材遮掉关键依据 | 相同已有卡片下比较选材安排，检查真实输入和后续动作 |
| N3 可逆再判断 | 条件变化后，旧路线按当前证据重新评估 | 少重建，既不过早恢复也不永久放弃 | 阻塞刚消失就误采用，或无谓重开 | 有真实条件变化的续接，必要时与稳定变化对照 |
| N4 未决项到行动/交付 | 重要缺口是否改变 Frame、下一动作或承诺范围 | 补对关键检查，或依据充分时及时交付 | 无限验证、空泛谨慎，或仍无依据宣布完成 | 同一记录/草稿的消费对照；草稿与当前反馈必须匹配 |

### 6.1 “有机会”和“用了机制”分开

机会依据任务事实、合法要求、已出现的历史依赖与新观察确定，而不是依据候选有没有写卡片。尽可能在隐藏臂名的情况下审阅匹配成功、匹配失败和差异轨迹。

若任务客观需要复用一条历史判断，而候选没有记录或遗失它，这是该机会下的实际表现，不能因“无合格卡片”把失败排除。

若原生任务根本没有条件恢复，就不产生 N3 分母。不同方法自身引出的机会数量不同，只作描述，不直接比较这些事后比例为因果效果；主比较仍按共同任务根进行。

### 6.2 用一条短行为链解释，而不保存隐含思维过程

复用现有原始请求与工具日志，关联：

> 当前反馈 → 旧/新工作记录或 Frame → 下一次实际输入 → 实际动作/回答 → 实际结果。

这证明控制产物进入了后续工作；仅有顺序关系仍不等于控制造成收益。下面的局部干预用于更准确定位。

## 7. 形成、保留、消费与选材：只拆最有信息量的一处

### 7.1 记录形成与维护

选一个真实检查点，固定当前目标、新反馈、前一工作区和合法来源。分别让普通 Controller 与候选 Controller 形成工作记录，然后由共同 Actor 继续。

如果要专门检查记录形成，保持后续 Frame/选材条件一致，或分开说明记录与选材同时变化。两份记录都由模型生成，不由研究者提供理想记录。维护生成和后续读取成本都计入。

结果可能支持“更好的记录形成规则”，但不自动支持特殊 Actor 消费政策。

### 7.2 同信息消费与 Frame

把同一时点已经真实形成的一份记录交给普通消费和候选安排，保持其余合法材料、当前反馈、预算和环境一致。

若打平，首先说明额外消费安排未显示增量；不能免费移交候选的记录后宣布整个形成过程无价值。若 Frame 和选材同时变化，则是消费/安排组合，不单独归为记忆内容。

### 7.3 状态连续性

对照继承当前工作记录与从相同合法历史重新构建。原始资料在两边均可访问，不能靠删除 baseline 来源制造优势；重建计算照计。

必须处理历史请求中的旧工作产物副本。仅去掉专用工作区插槽，但完整旧工作区仍在历史中，不是有效的去继承干预。也不能为了消融破坏工具消息配对、权限依赖或真实业务状态。

### 7.4 暂挂与返回

只有存在真实返回机会才比较“当前完整返回记录”与“普通记录/不保留特殊返回说明”的行为。不能只删除候选最关键的一条事实，再说它证明了新颖算法；要保持相同合法历史访问能力，解释是在测信息组织还是消费。

至少考虑一个合理的不采用情形：部分条件恢复、当前目标变化，或有更合适路线。恢复次数越多不是越好。

### 7.5 干预如何安全运行

- 不用过去录下的工具结果回应新的不同动作。
- 执行型分叉需要各自独立、等价的业务初态，且无未知在途动作；复用现有隔离快照能力，不新建通用克隆平台。
- 现有公开恢复要求相同保留环境及方法合同。不能伪造 environment_id、修改绑定或放宽校验，把同一检查点强塞给另一臂。
- 不具备等价环境分叉能力时，可以只做下一动作的固定输入生成诊断，不执行工具；这种结果只支持选择变化，不能填写原生成功分。
- 也可以改成从头完整运行的政策对照，保留其较弱的局部因果解释。
- 同一前缀生成成本在实际实验账只记一次；如果比较两种完整策略的估算生命周期，每种都必须包含其所需形成成本，并与真实账单区分。

## 8. 开发迁移与持续工作场景

### 8.1 沿用现有 benchmark，不重新搭平台

主来源继续固定的 Terminal-Bench 2 与已有 Harbor 接入。[S3][S4] 不以“验证创新”为由修改原任务、隐藏 verifier 或解答；多种合法解法均接受。

第一组 `multi-source-data-merger` 是使用回归/开发题。`cancel-async-tasks` 已被反复调试，适合保留历史反例，不作为新泛化证据。`db-wal-recovery` 的历史环境与容量问题保留，未有明确新问题及可用环境时不再作为默认长试验。[S2][S3]

迁移先选两个不同家族的任务。可从旧清单中的 `git-multibranch`、`constraints-scheduling`、`custom-memory-heap-crash`、`kv-store-grpc` 等候选中按既有环境可用性和研究需要前瞻确定，不按候选胜负挑题。[S4]

本次没有成功重新取得若干 pinned task metadata，也没有本地运行这些候选；名称及分组来自历史清单，不因此声称它们当前已可运行、很长或必然有记忆机会。执行前只核对选定任务的已有入口与环境，不全面下载任务库。

若候选之一实际很短，它可以保留为低收益机会/额外开销对照；不要人为加长来使 RWC 获胜。两个迁移任务的具体 ID 必须在本版模型结果出现前确定。

### 8.2 泛化和适应的口径

- 相同政策跨不同任务工作，是开发迁移。
- 同一轨迹遇到真实新反馈，Agent 自己调整，是运行适应。
- 研究者看过失败后改政策，是方法开发，不是 Agent 自适应。
- 换任务只改合法工具与来源映射，不加入任务专用认知规则，才支持接口适配性。
- 少量公开题不能证明广泛泛化；“本项目没用来调参”也不等于模型训练未见。

后续正式确认另选未参与修改的原任务/lineage，预先确定主要结果和最小有用差异，并据试运行方差设计数量；本计划不虚构统计功效，也不把两个迁移根当确认完成。

### 8.3 真实模型续接只做一次有解释目的的检查

已有公开保存/恢复接线无需为纯政策修改重跑。需要研究的是恢复后如何工作。

优先从已经产生的合法、无未知业务动作的检查点做真实模型续接。选择以下一种问题：

1. 无外生变化时，恢复是否保留工作位置而不过度重做；或
2. 新用户要求/明确环境变化出现时，恢复能否修订旧判断。

有环境副本时，在同一方法形成的前缀下比较连续与中断续接；否则使用独立从头匹配运行，不伪称完全相同前缀。旧 Host 停止，业务环境按各自合同保留。

若向原生单次任务加入新需求或条件变化，明确标为“原任务派生的续接工作负载”，独立记分，不混入官方 benchmark 成绩。不能向输入写“现在请恢复旧分支”来冒称自主发现；显式用户返回请求则如实标为显式返回。

N3 关注的是正确再判断与减少重建，而不是一定走专用 RECALL。公开字节恢复和语义续接收益分别报告。

## 9. 评价与账务：三列主结果，不合成创新总分

### 9.1 每条轨迹的结果

| 结果层 | 记录什么 |
|---|---|
| 用户交付 | 是否形成当前任务答复、交付状态、是否在 closing 阶段被迫结束、答复是否如实说明范围 |
| 任务质量 | 原生 reward、产物、关键约束、有效/未评分及原因；同一任务的子检查不变成独立样本 |
| 完整成本 | Actor/Controller/Observer/Reflector/摘要等全部生成、输入输出 tokens、工具与请求时间、失败/重试及准备和 verifier 成本 |

保留无 final 但产物可评分、已有 final 但产物错误、INCOMPLETE 与未评分等不同组合。不得从 `REVIEWED` 推导正确，也不得将无有效 verifier 的原始状态伪填为 0。

全尝试记录均保留。原生有效评分子集可以单列，但它受运行成功筛选，不能冒充全任务可靠性。用户可用性按全部已启动轨迹说明；未知费用不填零。

### 9.2 质量—成本关系

先比较是否满足任务，再在同等或相近完成度下比较成本。成本向量分别保留：生成数、输入/输出 tokens、模型等待、工具耗时及端到端墙钟。

相同调用上限不等于相同计算量。RWC 多次 Controller 和 OM 较少但较大调用的差异，必须由真实用量说明。无费率不报美元；无缓存计费证据不报缓存节省。

失败得很快不是效率胜利。除共同成功任务上的配对成本外，还报告失败及未评分尝试总成本，避免只挑便宜成功样本。

内部成本占比可以计算，但不是机制收益：

`控制相关 tokens / 全部模型 tokens`

Controller 输出没有变化也可能完成了合理复核；内容有变化也可能没有价值。不要自动给每次维护打“有用/无用”分或设固定介入成功率。

### 9.3 小样本与复现

初始三臂只有一个任务根，不报告显著性。温度为 0、有 seed 不保证完全确定。[S2] 一次差异如果决定重要开发方向，可以使用预留的配对复查，而不是反复运行直至有利。

方法运行顺序轮换，环境独立；服务明显变化时记录比较限制。软件、政策、预算改变后的结果分版本，不合并成统一最好成绩。

## 10. 资源安排：先开放小包，后续按问题选择

以下是建议的最高包络，均不是当前已分配资源。一次总执行指令可以覆盖这些有界选择，无需每次普通动作重新审批；未采用位置不自动转成其他实验。

| 工作包 | 建议计算方式 | 生成上限 |
|---|---|---:|
| 首个 v0.4 真实三臂 | 1 任务 × 3 方法 × 32 | 96 |
| 最多两次局部设计诊断 | 2 对 × 2 分支 × 8 | 32 |
| 选定改进版完整配对 | 1 任务 × SIMPLE/RWC × 32 | 64 |
| **当前开发主包合计** | 不要求三部分全用；默认先运行第一项 | **192** |
| 条件性开发迁移 | 2 新任务 × 3 方法 × 48 | 288 |
| 条件性机制/续接检查 | 合计最多 4 个续接分支 × 8；选择一个解释问题，不全做 | 32 |
| **全部建议路线最高包络** | 后两项独立决定，不自动排队 | **512** |

已有完整轨迹内的首次真实片段不再另计调试调用。续接重用的前缀账务引用原 trial；需要重新生成前缀时必须占用相应完整轨迹位置，不能作为免费准备。

48 是针对新任务的前瞻共同建议，不是给已经耗尽的候选补额度。若任务成本不适配，执行前调整共同设置并重算包络；不得运行中只放宽候选。批量 1/3、复核 0/1 的针对性比较也占上述位置，不增设参数搜索账户。

主要开发先用至多 192 次，完全可能提前结束。512 不是目标，更不是一次性发送许可。正式确认、第二模型、额外环境建设和训练不包括在内。

所有角色及已结算失败都计费。未知 Provider 用量或未知业务动作按原规则停止受影响执行；不为填满计划启动注定无解释价值的片段。

交付检查。代码形成交付版本后，结合实际改动和用户本轮测试范围安排适用检查，明确记录

## 12. 创新性判断与保留/删除决定

### 12.1 不同结果的解释

| 观察 | 开发决定与主张 |
|---|---|
| SIMPLE/RWC 在 v0.4 都顺利交付 | 当前配置运行可用；不据新旧不同预算的轨迹确立版本因果收益，也不归给 N1–N4 |
| RWC 只比 SIMPLE 好，但整体仍不及 OM | 有结构内政策信号，完整方法暂不推荐；查主要成本与可删部分 |
| RWC 与 OM 相近，但更复杂更贵 | 此工作点保留 OM；有新可反驳假设才继续改 RWC |
| RWC 质量更好但成本更高 | 报告质量—成本取舍，不称效率突破 |
| 任务均完成，候选总成本更低 | 局部效率信号；进一步看是否可迁移、是否只是调度差异 |
| 候选记录交给普通消费即可打平 | 优先删除额外消费约束，继续判断记录形成成本与价值 |
| 去掉跨步继承仍然一样好 | 不主张连续 State 收益；一般求解政策可能有价值 |
| 只有构造续接或已暴露题改善 | 限定为局部设计证据，不推广为原生泛化 |
| 四项能力有些没有实际机会 | 明确未覆盖，不伪造 0% 或补题直到出现阳性 |

### 12.2 独立创新主张需要什么

至少将以下关系说清，而不是必须凑齐某个固定测试数量：

- 相比已工作的强方法，哪一条记录更新/选择规则不同；
- 该规则确实进入后续输入与选择，且不只是额外信息或计算；
- 受控拆解支持相应贡献位置，而不是仅有事后解释；
- 同一政策在未用于修改的任务中仍有帮助；
- 近邻工作没有已经以相同操作和同类证据覆盖该主张；
- 完整维护、回读、恢复和失败成本可以接受。

工程完成、方法实际使用、局部收益、泛化、学术新颖性五层分开。固定 batch=3、交付保留、JSON 接收率改善本轮属于共享运行设计，不自动称为记忆创新。

### 12.3 开放而有界

允许新想法，但下一次运行之前必须能指出新差异和可能的反例。同一版本、同一失败、没有新解释时停止采样。停止当前版本不等于否定整个方向；也不能永远用“任务不够合适”免除候选的负结果。

不追求让 N1–N4 全部留下。最终只剩一条有用的记录更新规则，也比四个没有净贡献的模块更好。

## 13. 最小交付与下一步

只维护一份计划、一个现有格式的运行清单，以及一个紧凑结果；原始模型和工具日志沿用既有 Git 外证据目录。结果需要包含：实际版本、实际任务与暴露状态、全部尝试、原生结果、交付状态、成本、关键行为链、一个保留/修改/删除决定及尚未覆盖项。
