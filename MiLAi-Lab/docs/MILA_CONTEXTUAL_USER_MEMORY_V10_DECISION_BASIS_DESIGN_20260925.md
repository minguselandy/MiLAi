# MiLAi Lab v10 详细设计：Evidence-Grounded Decision State V0

日期：2026-09-25。状态：**B–D 已实现并通过必要窄检查；第一次 E1 已运行，候选未声明采用，方法效果未建立**。配套[开发 Goal](MILA_CONTEXTUAL_USER_MEMORY_DEVELOPMENT_GOAL_v10.0_20260925.md)以本地提交 7247742133de888276342c48638b12c81eaeec23 为基线；实际交付见[执行记录](CONTEXTUAL_USER_MEMORY_V10_DEVELOPMENT_20260925.md)，失败与费用见[结果](CONTEXTUAL_USER_MEMORY_V10_RESULTS_20260925.md)。下文保留设计时的合同说明，不用设计示例替代实测结果。

本文区分当前代码事实与拟议合同。Evidence-Grounded Decision State 是机制描述，不是新系统名；“接地”只表示声明的采用关系可定位到实际交付材料，不认证其语义支持或真实性。

## 1. 方法问题与最小边界

Memory 保存长期来源、当前理解与历史版本；Task State 保存本次目标、阶段和临时约束；Decision Basis 表达当前一个判断采用了什么，以及哪个未知可能改变下一步。

V0 只维护一个当前决策槽。它与正常 ReAct 动作同次生成，既有 ordinary 写入负责持久理解，既有业务执行日志负责真实动作。Attention 是根据当前缺口形成信息需求、再调用已有检索器，不是额外 Agent 或神经网络 attention 算子。

研究假设是：准确采用关系加上变化反馈及缺口取材，能否减少漏改、误改和重复核对。单个版本指针、一次检索改写、一次自动通知都不独立构成方法贡献。

### 1.1 已有工程证据

v9 已从原始初态在同一最终版本上连续完成既有 MERIT 一个 arc 的 5/5、依赖 2/2，以及文档四轮；State off。它证明受限闭环可执行，不证明本设计有效。

连续 tokens 相对旧基线增加约 43.5%，局部 delta 协议一次对照更便宜但元数据不同。本设计不能以“没有额外 State 请求”预先宣称省成本：生成与反复注入状态本身也消耗 tokens。[v9 结果](CONTEXTUAL_USER_MEMORY_V9_RESULTS_20260925.md)

## 3. 状态表示：五项语义信息，程序负责身份

### 3.1 Host 表达的信息

| 字段 | 拟议类型与含义 |
| --- | --- |
| decision | 简短判断或行动意图；不保存完整推理日志 |
| scope | subject_ref、item、context；分别表示已知主体、事项标识／说明、自然语言范围 |
| adopted_evidence | 已发布材料句柄列表；新采用必须能绑定实际交付版本／范围 |
| critical_gap | 空或一个自然语言信息需求，说明何种未知会改变下一步 |
| status | active、needs_recheck、deferred |

scope 中 subject_ref 复用现有主体目录；item 优先使用业务工具提供的订单号、文件身份等明确标识。context 不作为任意键值条件字典，不自动认证受众／时间匹配。当前普通条件词表只定义有限条件，不能把新 scope 字段无声送入严格求值器。

没有来源的暂定计划可以保留，adopted_evidence 可空；此时不称其已被事实支持。空 critical_gap 也不等于程序证明依据充分。

### 3.2 程序内部补充

内部记录决策 ID／revision、task 身份、采用时的准确引用与范围、观察到的版本差异、重核原因和最近评估的新观察位置。这些信息由现有执行次序和可见性导出，Host 不填写 UUID、hash、字符偏移或提交状态。

拟议内部结构示意，不是当前已上线类型：

~~~text
TaskState.active_decision: DecisionBasis | None

DecisionBasis
  id, revision, task_id                  # 程序
  decision, scope, critical_gap, status # Host 语义表达
  adopted: [exact_ref, delivered_spans] # 由句柄绑定
  recheck_reasons                       # 实际变化，不是审查意见库
~~~

不要再维护一份“State 来源已读表”。采用关系保留当时实际交付过的依据；当前是否仍能展开、是否还在 transcript 中，由现有可见性与生命周期路径检查。过去采用不等于当前重新阅读。

### 3.3 status 的含义

| 状态 | 含义 | 不表示 |
| --- | --- | --- |
| active | Host 当前采用该判断，可随正常动作使用 | 已由程序认证正确、业务已成功 |
| needs_recheck | 依据或相关观察发生变化，判断需要重新考虑 | 判断必错、所有支持失效 |
| deferred | 暂不用于当前动作，仍保留该槽等待后续信息 | 持久记忆删除、业务撤销 |
| null | 当前没有需要维护的决策依据 | 所有语义维护已完成 |

V0 不采用 resolved：它容易同时表示“缺口已解决”和“动作已完成”。业务成功由工具回执记录；本次判断完成其用途后可 clear。未来确需增加终态时，先定义其作用域。

## 4. 实际采用合同

### 4.1 从可见句柄绑定

Host 只选择 MaterialView 已发布的句柄。绑定器复用 HostSession.visible_bindings，读取对象 kind、exact_ref 和 spans，生成内部准确引用。模型不手写 card 版本或来源偏移。

- 卡片采用绑定当时已交付的准确版本。
- 来源采用绑定实际交付范围；如果一个句柄代表多个已交付片段，绑定全部该句柄对应片段，不能冒称未交付范围已读。
- 只有链接而没有正文的句柄，不允许作为新采用的正文依据；可先读取。
- 当前动作尚未返回的结果不能出现在同次 state_delta 的 adopted_evidence 中。
- 旧卡的 inherited source_refs 不自动成为本次 adopted_evidence；可以采用已经读到的卡片，但不能把它所有来源都记为本次已读。
- 不同观察正文相同仍是不同事件；同一来源多个摘要不自动构成独立支持。

已经采用过的准确关系可以继续沿用，无需为修改 critical_gap 重读全部旧正文。程序从当前 DecisionBasis 生成可选择的既有采用句柄，与新材料句柄区分；沿用记为 continued，不新增可见范围，也不认证重新核验。每次 set 显式选择保留哪些关系，不自动继承全部旧依据；已删除或不允许使用的关系不能继续沿用。这些句柄是当前对象的投影，不是第二份可见性账本。

这只能证明 Host 声明使用了合法可见材料。语义是否支持 decision、是否覆盖关键限制，需要任务与后续行为验证，不能由 CAS 或 hash 推导。

### 4.2 不追随最新版本

假设当前采用 card:7@3，随后出现 @4：内部 adopted 仍保留 @3，并产生 old=@3、current=@4 的原因。只有 Host 读取合法材料并重新声明采用，才变成 @4。

历史问题允许采用旧版，不一律以“不是最新版”拒绝。变化通知应携带既有 valid_at／known_at 和来源状态；Host 可确认旧版仍适合该历史问题。程序保存这次重核覆盖到哪个已观察变化，不在没有新事件时反复产生同一通知。

### 4.3 新判断与原判断修订

新 decision 替换旧判断时，重新给出完整的五项小状态；不默认继承旧判断的全部采用关系。重核后维持原判断也是有效结果，不能要求必须改变文本或执行 REVISE。

无需让模型给每句话列证明树。首版允许整项判断有若干采用引用，不声称已建立命题级支持完整性。

## 5. 同次生成的动作外壳

### 5.1 拟议 json_action

复用原有 tool／arguments，只在外壳增加 state_delta：

~~~json
{
  "state_delta": {
    "op": "set",
    "decision": "本次内部技术文档保留详细说明",
    "scope": {
      "subject_ref": "s0",
      "item": "当前技术文档",
      "context": "内部技术交流；客户汇报要求是否适用尚待确认"
    },
    "adopted_evidence": ["r7", "r12"],
    "critical_gap": "客户简短要求是否也适用于内部技术材料？",
    "status": "needs_recheck"
  },
  "tool": "memory_search",
  "arguments": {"focus": "critical_gap", "limit": 4}
}
~~~

示例句柄仅说明合同，实际由程序已交付目录决定，不是测试输入或固定词表。

state_delta 有三个分支：null 表示不变；set 完整替换唯一小状态；clear 清除当前槽。V0 不增加任意 JSON patch 语言。终结仍使用 finish_turn，允许同次 set／clear；不能靠 clear 消除现有未完成业务或持久维护义务。

业务动作的 arguments 保持原生 schema：state_delta 不传入 refund 等工具，不参与其业务参数身份。native transport 暂不接入此 sidecar，新候选配置固定 json_action；禁止通过静默忽略 sidecar 获得“兼容”。

### 5.2 不强制每次都产生 State

无当前决策需要保持时，可以一直为 null。已有观察足够且不需要后续复用时，Host 可直接执行普通动作。禁止为了触发率强制“先 state，再 search”。

但真实候选验收必须出现可解释的采用与反馈链。如果全部运行都为 null，应报告未使用，而不是实现有效；也不能修改原题强迫使用。

### 5.3 执行顺序

~~~mermaid
sequenceDiagram
    participant H as 同一 Host
    participant R as 执行入口
    participant M as 记忆与任务状态
    participant T as 原业务或记忆工具
    R->>H: 当前请求、实际材料、当前依据及变化提示
    H->>R: 一次响应：state_delta 与 action
    R->>R: 完整解析、schema 和可见引用校验
    R->>M: 保存本次语义状态与准确采用关系
    R->>T: 按原合同执行动作
    T-->>R: 实际结果或失败／未知结果
    R->>M: 保存结果；产生变化通知和新观察
    R-->>H: 实际回执与必要状态差异
~~~

业务动作仍由 RuntimeStore 在真正执行前保存 intent，执行后先保存 raw result；上图没有省略或替代该既有步骤。

动作成功后的来源接收、投影或记忆修订失败，不得导致业务重新执行。same-generation 只是输出编排，不是状态与外部世界原子提交。

### 5.4 失败与部分执行语义

| 情况 | 状态与动作处理 |
| --- | --- |
| JSON 截断／无法完整解析 | 不应用 delta，不执行动作，保留失败和费用 |
| delta 引用非法，或 action schema 不合法 | 整个提案在执行前拒绝；不只执行其中一半 |
| delta 合法，工具实际返回 CAS 冲突／业务失败 | 保留这次已表达的判断及失败回执，不假称操作成功；下一正常响应可改判断 |
| 外部动作结果 unknown | 沿现有未知结果核对路径；State 不得把 unknown 改成成功 |
| 动作修改了刚采用的卡片 | 根据实际回执使原采用关系待重核；不自动改绑新版本 |
| 新搜索返回了材料 | 只代表材料交付；下一正常响应再决定是否采用 |
| 状态保存后、业务 intent 前故障 | 恢复记录明确哪些步骤完成；无 intent 不声称外部业务已执行 |
| raw result 已保存、后续维护故障 | 恢复原结果并接续维护，不重复已结算业务 |

执行前校验只处理可确定的合同，不增加语义审核 Agent。needs_recheck／critical_gap 不成为新的全局业务阻断器；Host 可以在同一次正常响应内核对并决定动作，实际授权继续由原任务合同负责。

## 6. 两类变化入口

### 6.1 已声明依据的确定性变化

V0 扫描唯一决策的 adopted 集合，复用对象准确身份与既有生命周期。无需新建全局 DAG。

~~~text
实际记忆／来源变化
    -> 与当前采用对象比较
    -> 有变化：记录原因，status = needs_recheck
    -> 无相关变化：保持当前判断状态
~~~

关注下列真实事件：原卡新版本、来源替换／撤回、受管删除、当前任务范围／时间发生明确变化。只读访问与重复观察不自动制造版本变化。没有可靠语义判断的范围变化列成提示，不静默扩大适用性。

一个依据变了，另一个仍存在时，也只能提示核对。是否确为独立且足够的支持由 Host 判断；普通 adopted 列表不宣称有 AND／OR 证明语义。

Host 完成重核后可保留原判断、新增或更换依据、暂缓、清除当前槽，或者修订持久记忆。不得要求每次通知都产生持久写入。

### 6.2 无旧依赖边的新观察

V0 只有一个 active_decision，程序无需开发 subject/topic 相似度筛选器。当前新观察与这个决策一起进入正常 ReAct 输入，由 Host 判断影响。

保留普通材料发现路径；不能因为 scope 字面不匹配就挡住新约束、反例或主体澄清。此前没引用过的新来源可以推翻旧判断。

这条路径是语义能力，不是程序保证。日志区分：新观察已交付、Host 改变了判断、Host 保持了判断、没有观察到其使用。null 不能被自动解释为已经充分考虑所有变化。

### 6.3 任务范围改变

同一个任务／session 的新轮次保留唯一依据供 Host 核对，新的问题和临时约束照常交付。换 task 时默认清空当前决策；旧持久记忆仍可检索。恢复同一未完成 task 则恢复准确采用版本，随后与当前实际存储比较。

V0 跨任务复用的是持久 Memory；当前依据的持久保存服务于同一任务继续与恢复，不承诺维护跨任务的决策网络。论文中“持续维护”必须写清这个窗口。

单槽替换时历史只留在已有 trace，不再建立多个可恢复 active decisions。deferred 不意味着新建后台队列。业务未决项及长期维护 pending 继续由原协议保存，不能随着决策槽替换被丢弃。

## 7. Gap-directed Attention 的实际含义

### 7.1 两条明确路径

| 路径 | 输入和行为 |
| --- | --- |
| 普通 query／已有候选展开 | 使用 Host 显式查询，按已有 limit／范围规则查找或继续展开 |
| critical_gap 焦点 | 从当前缺口、事项和必要主体标识形成新的有效查询，重新运行现有检索器 |

V0 焦点投影只使用短信息需求和相关 anchor，不序列化整份 State、全部旧判断或来源全文。初版不增加 LLM query rewriter；Host 在正常响应中给出 critical_gap，程序确定性组织查询。

字段优先级固定：focus=critical_gap 时必须有当前非空缺口，普通 query 不同时定义另一套实际意图；缺口不存在则返回具体参数错误，不自动补题或回退到隐含查询。focus=default 使用既有显式 query。topic/context 是检索线索，不自动变成精确过滤器；过滤仍走现有合法主体、时间、来源合同。

adopted_evidence 用于定位已知材料和减少无意义重复展开，不把它们以“正确证据”身份强行加权，不屏蔽相反材料。全部比较臂保持相同原始来源访问权。

### 7.2 真实执行与成本

一次焦点搜索是一项正常工具动作，计入原请求与材料预算。工具内部不隐藏第二次模型调用，也不偷偷多跑一套未记账检索。回执记录 focus_origin、effective_query、实际过滤、命中对象和范围，能够核对查询确实改变。

默认每个显式 focus 动作发起一次检索；失败是否再查由同一 Host 在后续正常步骤决定，不添加后台重试循环。需要相同 query 但更大范围时，沿既有工具参数表达。

### 7.3 缓存与旧 coverage

现有只读缓存主要按工具名及 arguments 命中。如果 state_delta 改变 critical_gap，完全相同的 arguments 现在可能代表不同 effective_query。新实现必须在查询前解析有效输入，并以有效查询／过滤、材料代次及决策焦点代次确定缓存身份，或在对应状态变化时明确失效现有缓存。

选择最少改动的一种方案，不能同时造第二套缓存。只有判断说明变化但查询依赖不变，不要求全部来源缓存作废；状态失效、来源可见性或材料限制变化则不能沿用不兼容响应。

旧 coverage 继续绑定已交付搜索结果。新 needs_recheck 描述判断，不等于 coverage=GAP；存在缺口也不等于任何历史材料都不足。不要将两者合成一个“可执行”布尔量。

## 8. 与持久记忆和业务操作的关系

| 语义变化 | 当前决策 | 持久 Memory | 业务状态 |
| --- | --- | --- | --- |
| 仅本次报告要求简短 | 调整 scope／判断 | 不覆盖一般技术讨论约定 | 按原任务完成 |
| 今后报告统一改变要求 | 当前相关时重核 | ordinary CREATE／REVISE | 不自动触发新业务 |
| 退款金额约定被更正 | 重新核对待执行金额 | 原事项修订 | 执行仍先核对必要业务事实 |
| 实际退款成功 | 下一响应采用真实结果或清除已完成判断 | 按需要修订当前事项 | 成功由 raw result 证明 |
| 再次确认同一事实 | 可保持／不操作 | 不要求重复 CREATE | 不重复已完成动作 |
| 明确删除 | 清理受影响引用和受管正文 | 可信 lifecycle 执行 | 不把删除当作退款撤销 |

RETRACT 表示停止把理解视为当前成立，可以通过既有允许的修订／退役路径表达。V0 不新增任意撤回工具；若普通模式缺少专门退役能力，保持当前支持的操作并明确限制，不跳入 support 或 DELETE 分支。

决策依据不是持久卡的替代品。一个尚未被当前决策采用的新约定仍可能值得保存；当前决定不保存也不能靠程序缺省字段替代 Host 的语义判断。

## 9. 状态所有权、恢复和版本身份

TaskState 持有唯一 DecisionBasis；HostSession 继续持有真实材料绑定；RuntimeStore 继续持有会话／动作执行事实。不要让这些模块各存一份可变 decision truth。

新增纯模块 decision_basis.py 只负责小状态的构造、绑定后的转移、变化比较与精简投影；不进行模型调用或外部动作。引用解析复用既有材料层，不另写通用 ACL、CAS 或正文范围验证器。

checkpoint 使用唯一显式序列化／恢复函数。现有 TaskState(**payload) 的路径需要正确重建嵌套类型；不得让运行前为类型、恢复后变成任意 dict。采用版本恢复后重新检查当前可用性，不能默认为 current。

操作入口、Host 输出协议及任务状态格式变化各有新身份；在实现阶段确定实际版本号并统一更新准备／冻结清单。新增源码文件必须进入冻结映射。ordinary v9 行为和旧结果身份保留，不把新增字段悄悄塞入旧 checkpoint 冒充同协议。

受管删除需清理采用关系及 decision、scope、gap 中受影响的受管正文，沿现有删除效果处理；删除后不能从决策快照恢复文本。clear 当前决策本身则不是用户数据删除。

业务前状态与 intent 的持久化复用原 store，不引入分布式事务。恢复 trace 必须能区分 state 已保存、intent 已登记、result 已落盘和后续维护完成，禁止把同次生成误作全部一起成功。

## 10. 真实使用证据与重核指标

### 10.1 最小机制记录

在现有 trace 附加紧凑结构，不再建分析平台：

~~~text
当前 task / 决策代次
本次 delta 是否接受
采用的准确对象／范围
相关实际变化及通知原因
新观察是否已交付
effective_query 与材料身份
实际工具动作及回执
之后判断保持／改变／暂缓／清除
~~~

模型声称“已使用记忆”不是独立使用证据。至少核对提交关系、实际检索、工具参数或后续答案；单次一致性链仍不是不可替代性的因果证明。

### 10.2 修正 Precision／Recall 的定义

“触发后动作发生变化”不能作为重核正确标签。新金额需要重新计算，但计算后仍低于同一阈值、动作不变，重核也可能必要。

预先定义机会单位为某个实际决策前态与后续合法观察／变更。参考标签 need_recheck 表示该变化要求重新判断原依据是否足够；不要求最终 decision 或 action 必须改变。

~~~text
precision = 被独立标为应重核且实际重核的机会 / 实际重核机会
recall    = 被独立标为应重核且实际重核的机会 / 独立标为应重核的机会
~~~

另外单列结构通知的 precision／recall、Host 接受通知的比例、重核后仍错误的比例。不能把程序置位直接算成 Host 完成重核。

原生数据通常没有这些事件级标签。只在可事后独立核对的诊断子集计算，标签不回写数据或方法输入；不确定项为 unknown 并报告覆盖率。没有足够标注时只提供机会表，不拿模型自己的理由当 gold。

不同臂产生的判断可能不同：相同原生事件可以配对，但不能假装它们具有完全相同的内生 decision。需要分离原生结果比较与局部相同前态的干预诊断。

## 11. 小规模实验设计

### 11.1 开发完成后再冻结样本

原有 MERIT arc 保持完整历史、初始世界和 checker，用于真实业务回归。StateMemBench 需先确认官方可下载数据、原生评分、许可证及版本，本轮仅确认论文与机制，不声称数据已准备。

候选小集初始目标为 4 个完整原生场景，覆盖应更新、应保持和依赖重算；具体 ID 待开发完成后按事先声明的事件类型冻结。没有对应机会则记录缺口，不裁剪历史或修改 gold。

特别检查“目标变化前，决策是否已经建立”：如果一题的所有历史都先摄入、随后只问一个问题，旧值与更正可能在首次 decision 形成前已经一起可见。这样的题可以测试当前状态恢复，却未必测试 adopted version 变化后的重核。

不能为了 E3 提前泄露未来问题、人为生成错误 State、把原始一次摄入改成只给关键段，或制造必需的修订调用。原始消息顺序和合法任务时点不变，各臂使用相同分块规则。

现有 MERIT runner 每个 episode 使用不同 session，同 episode 的多条消息才连续；不能为凑重核次数把跨 episode TaskState 强行合并。若原生任务只提供跨会话持久记忆变化而没有当前决策存续窗口，明确其不支持 E3／E4 的完整结论。

### 11.2 匹配基线

所有臂共享同一 Host 权重／推理配置、检索底座、合法历史、业务工具、原始结果日志、权限、增量写入、维护终结和恢复能力。原题和原评分完全一致。

强 ReAct 基线允许维护普通工作笔记、写出判断／引用／不确定性、主动重新查询和修订记忆；不能为了候选赢而禁止它使用这些能力。笔记和结构状态各有可比输入／输出容量，全部计费。

基线拥有准确材料引用，但程序不将笔记中的任意字符串认证为 adopted binding，也不追加候选自动通知。它仍拥有基础来源失效与权限边界；消融不能绕过这些保证。

### 11.3 四个问题与运行顺序

| 对照 | 只应改变什么 | 能声称什么 |
| --- | --- | --- |
| E1 强笔记 vs V0 | 笔记状态与整个候选控制方式 | 初步整体价值；不能把收益全部归为五字段表示 |
| E2 V0 普通搜索 vs gap focus | 焦点投影，其他表示和反馈保持 | 定向查询的增量；普通臂仍能生成好 query |
| E3 V0 自动通知 off/on | 已采用依据变化通知，其他路径相同 | 自动重核反馈的增量；语义新观察在两臂都可见 |
| E4 按需重建 vs 维护依据 | 状态形成／复用时机 | 在原生复用窗口中的质量和累计成本差异 |

若要单独认领“表示价值”，需另将 E1 中绑定后的状态结构与控制变化拆开：保持同样字段和信息，只移除自动反馈；不从 R vs 完整 V0 的比较直接得到该结论。

先 E1，确认机制实际运行和任务不退化后再做 E2/E3 的窄消融；E4 要有自然连续复用窗口。复用同一个冻结候选作为多个对照的公共结果，不为每个表重复请求。局部同前态分支只做机制诊断，后续状态分歧如实保留。

不强制跑齐四张表；未执行项写明原因。负面或不确定结果允许研究结项，不能靠叠加模块、换更大模型或多次重试同题掩盖。

### 11.4 按需重建与复用成本

按需重建参考 StateMem wrapper 的思想，给它同样合法可访问历史及材料。若给予完整 transcript，必须计入实际输入；若只给检索片段，则明确是受限变体，不能声称复现原 wrapper。

两条轨迹都从同样初态开始；读取模型答案后不能将一臂记忆写入另一臂。创建、摄入、State 维护、查询、失败和终结开销都计入累计部署路径，Judge 独立列出。

N=1、2、4、8 只用于原生轨迹确实包含的连续决策前缀。禁止靠反复同题或拆分新题制造复用优势；独立 probe 的副本运行也不能冒充一个连续任务。

### 11.5 评分与报告

原生 checker 优先。需要 LLM Judge 时通过 vLLM，冻结模型、rubric 和解析，不修改评分标准迎合候选；若与论文 Judge 不同，不直接比较其公开分数。

报告任务结果、实际操作、记忆终态、决策状态、触发链和费用。标明已暴露样本、开发诊断、未使用确认样本；失败、未评分、机会不足分别呈现，不合成一项准确率。

## 12. 开发任务与窄验收

| 顺序 | 任务 | 最小验收 |
| --- | --- | --- |
| 1 | 小类型、采用绑定和精简投影 | 已见句柄绑定准确；版本变化不漂移；无第二份可见性表 |
| 2 | json_action sidecar 和统一执行入口 | delta＋普通动作／finish 同次生效；无未来结果采用或业务前成功声明 |
| 3 | 变化反馈与新观察消费 | 有关／无关变化区分；新观察不受旧依赖排除 |
| 4 | gap 投影与缓存 | 真正的新查询；同参数新焦点不会复用旧结果 |
| 5 | checkpoint、恢复、任务切换、删除 | 状态可还原；不重复业务；不复活被删正文 |

## 13. 论文主张与失败判据

可以提出的待验证主张：显式保存当前判断实际采用的版本，在记忆和观察变化后让同一 Host 选择性重取材料与重核，从而改善持续任务中适应、保持与成本的平衡。

V0 失败或不足的典型结果应如实保留：

- 所有 state_delta 为 null：方法未被使用。
- State 有字段、effective_query 没变化且没有采用反馈：只有表示，没有证明控制。
- 通知很多但 Host 未消费：只证明程序能置位。
- 减少过时使用，却误改更多有效认识或大量拒答：选择性适应未成立。
- 强工作笔记同样完成且更便宜：新增机制暂不值得成为默认。
- E3／E4 没有原生适用机会：未获得证据，不等于机制被否定。
- 只在固定已暴露例通过：工程诊断成功，不升级成跨模型或未见任务结论。

保持 ordinary 默认。先交付可审阅的小实现，再用有限原生任务判断是否值得继续；结果不支持时保留结论，不扩张成新的大框架。
