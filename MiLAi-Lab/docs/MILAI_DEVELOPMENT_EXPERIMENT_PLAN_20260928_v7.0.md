# MiLAi 开发与实验规划 v7.0

## 执行摘要

**本轮不换研究方向，不重写记忆数据库，不再把一次失败自动升级成新架构。**承接《MiLAi 记忆架构复盘与可实施设计》，保留成熟运行底座、唯一逻辑记忆提交入口、多个带依据的局部工作状态、结构化请求组装与完整增删改查；先解决自然语言意图没有进入正确动作、对象身份被改写、实时查询被记忆搜索替代等实际断点。[S0][S1]

推荐顺序：

> **核对实际模型协议 → 对齐协议间信息和执行权限 → 小规模真实调用校准 → 修复精确对象与结果衔接 → 仅在漏存仍存在时验证有限记忆子任务 → 连续任务验证 → 研究 State–Attention 的独立收益。**

本规划优先保证任务可用性，但不把更多调用预先判为错误，也不把额外调用预先判为有效。所有新增机制必须与相同信息、相同操作能力的简单路径比较；成本按完成整条任务及后续复用核算。

### 首批应交付的最小成果

| 交付 | 具体内容 | 不是 |
| --- | --- | --- |
| 一个协议能力清单 | 实际模型、模板、parser、native 支持、thinking 支持及请求预算 | 对官方推荐的盲目复述 |
| 一条共用材料路径 | JSON-action/native 都取得同一合法记忆、当前请求、历史和工具结果 | 简单切换 `tool_mode` |
| 一个小型完整执行对照 | 既检查首动作，也执行工具并检查持久记录与新会话复用 | 只统计 CREATE 提案 |
| 一份可定位的结果报告 | 分开意图、参数、执行、记忆、后续使用和成本 | 一个掩盖首断点的总体百分比 |

**最先安排的实验只有协议校准。**第二模型、对象引用适配、同步记忆子任务、长期负载和独立 selector 均有条件触发，不在同一次首批执行里全部展开。

# 2. 问题分解与研究假设

## 2.1 不再用一个总失败解释全部问题

```text
真实输入
  → 意图识别／动作选择
  → 对象及参数构造
  → 工具执行与持久提交
  → 结果理解与状态更新
  → 后续取材与任务完成
```

一次漏存可能造成多个后续回答失败，不能把它们计为多个独立根因。反之，记忆丢失也不能解释一条已明确提供查询对象的当前 lookup 为什么没有调用业务工具。

## 2.2 保留的竞争解释

| 假设 | 已知依据 | 区分实验 | 可推翻它的结果 |
| --- | --- | --- | --- |
| H1：自定义 JSON-action 增加工具选择负担 | schema 允许合法 `answer`；真实出现零写入确认 | 同模型、同材料、同能力下比较 native 与 JSON-action | native 同样漏存或更差，不能再归责 JSON 协议 |
| H2：当前推理模式不足以支持组合意图 | 当前固定 non-thinking；形成与业务并存时失败 | 在已验证协议下比较支持的 thinking/non-thinking | 更多推理只增加成本或误存，不能视为修复 |
| H3：精确身份被当成可改写文本 | plural key 被改写 | 原始参数合同 vs 有来源的对象引用适配 | 引用适配不能改善或错误转移到对象选择 |
| H4：明确记忆工作没有形成独立执行责任 | 请求存在、工具存在，却直接终答 | 直接工具策略 vs 有限同步记忆子任务 | 子任务仍漏存，或把漏存改成大量误存 |
| H5：需要的业务状态没有被正确路由 | 空 memory search 替代实际查询 | 当前计划问、历史问、实时状态问成对验证 | 正确路由后参数或执行仍失败，瓶颈在下一层 |
| H6：State–Attention 有后续价值 | 既有能力未在真实选择问题中独立验证 | 固定 bank、同 writer、同能力的读取／工作状态比较 | 简单 all/query 同样正确且更便宜 |

**假设不等于诊断结论。**不要因为 native 是官方推荐、thinking 更贵、引用更结构化，就预先认定它们会成功。

## 2.3 当前问题与论文主张分开

H1–H5 首先是可用性修复。若收益全部来自模型协议或工具 API，按基础工程报告，不重新归因给 State–Attention。

长期研究问题仍是：在模型与工具适配可靠、操作能力和信息权利相同的条件下，多个带依据的局部工作状态与 Attention 是否改善选择性适应和质量—成本边界。

修复底层不是放弃方法；也不能因已经投入很多轮就要求每项旧模块必须保留在论文主方法里。

# 3. 保留架构与接口合同

## 3.1 目标架构

```text
实际用户输入／工具观察
         │
         ▼
现有来源与会话存储
         ├──────────────┐
         ▼              ▼
MemoryService       TaskState（可含多个局部项）
唯一逻辑提交入口    当前目标、临时值、依据、待办、结果
         │              │
         └──────┬───────┘
                ▼
已有 RequestContext / Renderer
同一合法材料，不同模型协议编码
                ▼
同一 ReAct Host
记忆读写／业务行动／询问／不操作／结束
                ▼
已有执行器、真实回执与恢复记录
                └──────────→ 新观察
```

`MemoryService` 是现有严格工具与 Store 的逻辑接口，不是新增网络服务。优先复用已有函数，不为图中的每个框创建一个类或文件。

## 3.2 四种数据职责

| 对象 | 最小职责 | 禁止推论 |
| --- | --- | --- |
| SourceEvent | 真实来源角色、原文、事件身份、取得时间 | 接收到一段话不等于内容真实 |
| MemoryRecord | 可继续维护的事项、范围、相关来源背景 | 有 ID 或引用不等于认识正确 |
| TaskState | 当前任务使用的事实／假设及其依据、已提出操作和实际结果 | 工作假设不能反过来成为自身证据 |
| OperationResult | 已执行动作、目标、返回内容、成功／失败／部分／未知 | 工具成功不等于完成全部用户意图 |

不要求给每句话建立类型或完整支持图。只对当前失败确实需要的身份、范围、状态增加明确表达。

## 3.3 State 可以缓存工作事实

允许：

```text
总计划：8件，依据 memory:M 的当前已读内容。
本次仅执行：3件，依据当前用户消息。
已执行：reservation:R，依据实际工具回执。
未完成：label，依据同一回执中的部分失败。
```

禁止的是两个长期 writer 无协调地分别修改“总计划”，不是禁止 State 显示数值。

缓存绑定已读版本或内容签名；若现有 ordinary record 没有版本机制，可使用程序侧准确内容签名识别变化，但不能宣称因此获得数据库 CAS。依据变化后重新解析，必要时由 Host 重核；不能只自动替换版本号而保留原推论。

## 3.4 完整 CRUD 与退出语义

- CREATE：新增独立事项、合法来源保留或明确标注的认识。
- READ：搜索、准确读取、必要来源展开。
- UPDATE：同一事项真实变化，保留未受影响内容。
- RETRACT：撤回不成立的认识或依据；不篡改来源原话。
- DELETE：按授权清理目标；不以“当前不相关”代替遗忘意图。
- NO_CHANGE：没有需要持久变动的信息，允许直接继续任务。

不要求每次都调用 NO_CHANGE 工具。机会性学习可以不写，明确保存命令则需完成相应请求或如实报告未完成。

## 3.5 执行闭环与语义完备性严格分开

```text
已经登记的操作 + 成功回执 → 该操作已完成。
一次 CREATE 成功 ↛ 全部请求已完整保存。
模型未登记保存意图 ↛ 程序可以自动知道遗漏的义务。
```

完成边界基于真实操作状态，不恢复 C 的模型自报 `committed/receipt_refs`。

## 3.6 公共安全与保留边界

用户／任务隔离、实际业务权限、来源身份与已有删除约束对所有实验臂一致。审计历史不自动进入 Retained 任务；对工具错误中的参数，保留“曾提出但未成功”的身份；未知外部执行结果先核实，不盲目重放。

安全与可用性都不得依赖通过评分标签推断用户意图。

# 5. P0：基线与故障复核

## 5.1 输入与输出

输入：架构复盘、v6 冻结报告、S4 公开输入、原始可访问的冻结 trace、对应代码与依赖。

输出：复用现有 manifest 机制形成一份 `protocol_capabilities` 和一份 `failure_chain`；不另建大型审计平台。

## 5.2 必查内容

| 范围 | 核对项目 |
| --- | --- |
| 模型身份 | 实际服务返回名、权重／revision（可取得时）、量化、模板与 tokenizer |
| 工具协议 | 当前 JSON-action、可用 native parser、工具目录传递、finish reason、参数解析 |
| 生成配置 | temperature、seed 支持、thinking 开关的实际语义、输出容量、并行调用设置 |
| 请求材料 | current_request/system、full/compact、原用户文字、全部合法记录、工具结果、历史角色 |
| 回执 | tool_call_id 配对、正确作用域、失败与部分副作用、持久记录变化 |
| 计量 | 实际 provider ID、usage、reasoning 计数是否另列、失败也计账 |

若有项目规范明确禁止变更共享服务，继续遵守。需要 parser 或模板变动但无法隔离时，native 分支标 `BLOCKED_ENVIRONMENT`，不是方法失败，也不自动改共享部署。

## 5.3 固定四类首断点

至少建立以下链条，每条附实际输入、实际提案、实际执行和后续结果证据：

1. 明确记住但零 CREATE。
2. 完整业务 key 被改写。
3. 应查实时状态但只搜索记忆。
4. 上游失败导致 partial 场景未激活。

旧结果永远保持原分数；局部重放和组件诊断另立身份。

## 5.4 回归不是继续搜索措辞

可复用旧 H/I 与 v5 当前／历史等用例测试接口，但它们都是已暴露诊断。不能在同一输入上反复换提示，直到出现一次期望动作再继续后续链。

同一 temperature=0 请求可预定重复以测量操作变化；它不是逐字确定性保证。记录当时服务条件，不在无法确定原因时写成“vLLM 非确定性导致”。

## 5.5 P0 验收

能力、输入权利、来源、模式与未验证项清楚；已知报错不被吞掉；不新增真实实验 calls。原始私密文件不可用时标明缺口，仅以公开精简证据设计下一次独立运行，不重建伪造历史。

<a id="p1"></a>
# 6. P1：模型—工具协议校准

## 6.1 本次源码复核发现的两个接线条件

**已观察：**固定提交中，`request_view.project()`、`MemoryBoundaryView.fit_final_request()` 和相应材料交付记录在 JSON-action 分支内执行；native 分支直接将 `wire_messages` 与 `tools` 交给 client。[S3]

**已观察：**`persistent_memory.py::_validate()` 对现有配方硬性检查 `tool_mode=json_action` 和 thinking=false。[S4]

因此不能只改配置后跑 native，也不能把绕过记忆投影的 native 结果当成同信息协议比较。这是接线范围差别，不是对尚未运行 native 的故障结论。

## 6.2 最小实现

在已有 RequestContext/Renderer 上增加协议适配，不新造 Agent runtime：

```text
真实 graph/messages + 当前合法记录
        → 共用来源／任务／记忆内容投影
        → JSON-action 编码器 或 native 工具编码器
        → 实际模板与完整工具目录的容量检查
        → 同一个执行器
        → 共用实际结果审计与交付记录
```

旧 JSON 路径保持旧默认行为。历史 C、M1、ODR 等继续保留，新的校准配方不要隐式启用；native 对不支持的旧扩展明确报不兼容，不静默丢弃。

## 6.3 等价比较的真实含义

不同协议不可能请求字节完全一样。必须验证：

| 应相同 | 可不同且必须记录 |
| --- | --- |
| 用户原文、合法历史、实际 Memory 正文、owner、业务初始状态 | 工具目录的协议表示 |
| 工具名称、能力、必需参数及执行侧校验 | JSON-action envelope vs native tool_calls |
| history/current_request placement、full/compact 选择 | 模板中原生工具专用标记 |
| 读写权限、业务权限、错误返回内容 | 解析器、finish reason、原生调用 ID 格式 |
| 每回合容量和异常处理策略 | 对应协议的真实 token 成本 |

对旧 JSON 路径仍做编码级回归；对跨协议做内容及能力等价，不伪称字节等价。

如果 native 必須更换模板／parser，实验名称明确为“协议组合比较”，不能称纯 `tool_mode` 单变量。

## 6.4 原生调用的最小正确性

应实际验证：无工具终答、单工具、多工具、工具拒绝、调用后再回答、当前同 ID 更新、删除后读取、未知工具、无效参数、截断、部分返回和 owner 隔离。

语法不合法时执行器拒绝，不能将无效工具调用转换成成功答案。合法无工具回答继续允许；开放聊天条件不使用 `tool_choice=required` 逼出写入。

native 同一响应中若含叙述和 tool_calls，叙述不当作已经执行的事实；先执行实际调用，等待后续终答或明确未完成。

依赖前一个工具结果的调用不得提前编造参数。核对实际 ToolNode 顺序／并发语义，不仅看提示词写的“按顺序执行”。同一校准批次对依赖操作使用一致调度，不顺便优化并行度。

## 6.5 容量、推理与输出处理

实际模板、tools 和 reasoning 引导均进入输入容量核算；业务答案与隐藏 reasoning 分离。只保存可审计的工具动作、最终答案和服务提供的 usage，不要求导出完整私有推理链。

thinking 模式可能占用更多输出容量。首先保持明确可比较的预算；若任务需要增大 reasoning/output 配额，另记为预算条件，不把增加计算的收益全部归因于模式。

服务未提供独立 reasoning 计数时标 unknown，不填0；服务已将其计入 completion 时不重复相加。

## 6.6 配方和兼容性

通过显式的研究 profile 定义允许的协议与参数范围，不把旧 `_validate()` 的限制简单删除为“任何配置都允许”。

建议的描述性身份，而非新论文方法名称：

```text
protocol: json_action | native
reasoning: non_thinking | thinking
view: full | compact_v6
placement: system | current_request
writer: host_direct | synchronous_subtask
object_interface: original | resolved_reference
```

这些是计划中的配置维度，不表示现有 CLI 已支持所有组合。只实现当前实验需要的组合，不增加全组合平台。

## 6.7 P1 验收与回滚

- 旧 JSON 请求及回执行为没有被未声明改变。
- 两种协议都实际经过相同合法材料投影，native 不少读／多读历史。
- 工具执行、当前回执、失败和成本能够一致记录。
- 可解析性通过只是开始，不认作任务有效。
- 协议不可运行就保持当前 JSON；不通过关闭权限或参数校验获得通过。

<a id="p2"></a>
# 7. P2：精确对象、查询与结果消费

## 7.1 区分对象身份与描述

模型可以生成简短标题，却不能因此改变业务 key。优先复用工具已经返回的真实 ID／key，实际内容与显示名分开。

拟议的内部映射只需要：

```text
scope / owner
object_ref
original_key_or_id
source_event_ref
resolution_status
```

`resolution_status` 至少区分“用户文字中出现”与“经业务工具解析”。有一段原话不等于存在已验证的业务实体。

## 7.2 无新增权利的准确解析

已有工具返回稳定 ID 时：Host 选择这个真实对象，程序解析回原 API 参数。

只有自然语言名称时：保留完整名称；业务系统有查询就取得候选；多个候选需消歧。不能通过隐式单复数归一、模糊匹配、测试 gold 或标题补全来代替选择。

原业务 API 没有可查询身份时，可将选中的准确原文片段作为待用字符串，但其实体有效性仍未确认；不声称“对象已经认证”。

## 7.3 两种实验设置分开

**原工具合同设置：**继续用原始字符串 key，保留其精确复制错误。这是与历史结果和原生 benchmark 对齐的设置。

**引用适配设置：**允许 wrapper 解析真实引用。所有比较方法共享该 wrapper；评价包含查找／消歧成本，名称为应用接口适配，不冒充未改 benchmark 成绩。

不要只为候选给结构化 ID，然后声称 memory 算法优于原工具 baseline。

## 7.4 计划、部分执行和实时状态

```text
总计划数量 ≠ 本次执行数量。
计划地点 ≠ 所有后续动作的默认对象。
最后观察 ≠ 无条件实时状态。
一次 memory search 空结果 ≠ 外部业务对象不存在。
```

通过工具描述与真实结果保持用途清晰，不用样本 ID／关键词直接路由。

已有足够新的真实回执能回答当前问题时不重复查；用户明确要求“现在重新核实”或存在外部改变时使用合适查询。工具不可用时说明依据和未知，不以旧 memory 顶替。

## 7.5 部分副作用与恢复

主操作成功、附属动作失败：保存真实 ID 和各阶段结果，只重做未完成部分。若原 API 没有独立恢复能力，应说明限制，不虚构一个新工具。

超时／中断导致执行结果未知：先查询或报告不确定，不能因本地没有成功回执就断言外部未发生。

不追求分布式 exactly-once 的虚假保证；只在现有执行日志与接口能力范围内提供可解释恢复。

## 7.6 P2 验收

对象引用不越 owner，不改变原始 key；未知／错误引用不静默落入其他对象；执行参数来自本次授权；错误提案不变成事实；实际失败能够续接或如实结束。

<a id="p3"></a>
# 8. P3：明确记忆工作与有限同步子任务

## 8.1 三种输入不混为一谈

| 模式 | 谁明确任务 | 评价要求 |
| --- | --- | --- |
| 显式应用命令 | 应用／UI 通过真实授权传入保存、更新或删除要求 | 可要求在该操作完成后确认；不是自主意图识别成绩 |
| 开放自然语言 | 同一 Host 从用户文字理解记忆意图 | 必须允许只读、引用、临时、拒绝与 NO_CHANGE；不能由 gold 强制 |
| 机会性学习 | 系统尝试保留有未来价值的信息 | 独立评估误存和成本，不在每回合默认形成长期画像 |

只有第一种模式可以由可信 API 指定操作类别。第二种不允许用“包含 remember”这样的关键词或离线义务表直接强制 CREATE。

## 8.2 首先保留直接工具模式

协议校准后若开放请求已经可靠，继续由同一 Host 正常调用完整 CRUD。不因为规划包含 P3 就必然新增写入模型调用。

任务状态只追踪已经识别的维护工作及实际操作结果。未登记的意图遗漏仍然是模型问题，不能用状态机名称掩盖。

## 8.3 漏存仍存在时的唯一有限候选

候选为同步、有限的记忆子任务，不是 Reviewer，也不是末尾失败后重试 C：

```text
本次真实新增材料 + 必要同回合上下文 + 相关旧记录
          → 同一模型生成真实 CRUD 操作或 NO_CHANGE
          → 唯一提交入口执行
          → 实际回执进入当前工作状态
          → 原任务继续
```

额外调用计入总成本。默认一个语义提案入口；需要进一步读取时，复用正常工具路径和同一公共回合容量，不无限“反思直到写入”。结构错误和未完成按真实状态返回。

## 8.4 避免选择偏差与双写

若研究“边界子任务能否发现 Host 漏掉的自然语言意图”，触发不能依赖 Host 已经选择写入。该候选在事前规定的公开输入边界评估新材料，连同只读、引用、临时和无变化消息一起计费；不能只在已知正例上运行。

在此比较中：

- 直接 Host writer 与子任务 writer 不独立写同一事件的同一事项。
- 子任务使用同一 CRUD 能力；Host 保留记忆读取和业务能力。
- 新工具结果若改变持久认识，进入新的有身份事件边界；不得每次 pre_model 重新应用之前事件。
- 要保留或删除什么仍是语义判断；程序只负责执行和事件处理身份。

现有幂等事件／编辑身份可复用。两个真实用户事件即使文本相同仍然是两个事件；不得按文字去重忽略重复的真实增量。

## 8.5 不回到“终答证明”

子任务输出的是实际操作，不是 `saved=true`。程序保存真实记录和回执；Host 最后陈述仍需符合发生过的事实。

没有成功提交不得在程序层标记完成；Host 若最终仍虚称保存，必须计错，不能通过 UI 隐藏答案或自动改写句子制造通过。

一次操作成功不证明一组复杂意图已全部完成，离线评价仍检查内容、范围和独立事项保持。

## 8.6 覆盖原则

合法独立想法可以保存并标明是作者判断；不是所有记录都必须有外部事实证明。provenance 自动记录实际上下文来源，semantic support 只在模型实际提出时表达，二者不合并。

更新采用同一事项目标；独立事项可 CREATE；当前例外进入工作状态；真实长期变化进入持久记录；撤回或删除按明确范围处理。

## 8.7 P3 验收

新增子任务只有在至少两个不同失败模式／事项族上改善真实完整链，且引用、临时、只读和删除边界无新增系统性损害时，才有继续验证价值。改善写入率但制造误存，不视为成功。

它可以更贵，但必须报告每个新增成功生命周期的实际额外成本；如果原生直接工具已足够，就不采用它。

<a id="p4"></a>
# 9. P4：带依据的 TaskState 与 State–Attention

## 9.1 不重建旧的大 State 平台

复用当前任务状态和 RequestContext。允许多个局部工作项，但只记录当前任务确实需要的目标、约束、依据和已知结果。

状态变化示例：

```text
用户计划 → 记忆记录已保存。
本次操作 → 尚未执行。
真实结果 → 主操作成功、附属动作失败。
后续目标 → 核实附属动作，而不是重做主操作。
```

程序只根据工具回执更新已执行状态；模型判断当前目标与未完成语义。没有实际执行时不能产生“已完成”。

## 9.2 依据失效不是全局重算

当前工作缓存引用的记录发生变化或被删：标记需核对，按当前问题重新读；不能仅把旧引用指向新版本就保留旧结论。

历史问题允许读取合法历史版本；当前 query 不因此“永远选最新”。没有声明的语义依赖，程序不声称自动发现。

## 9.3 A 与 U 的职责

- A：当前任务、范围、未决问题与实际预算决定读取和核对什么。
- U：真实新信息决定哪些已有事项可能需要维护。
- A 不限制一条明确的任务外长期记忆请求。
- U 不等于所有读取结果；普通读取不产生永久写入义务。

先由同一 Host 的已有 search/read 和相关记录检索实现，不默认分别新增 selector 调用。

## 9.4 Attention 的重新准入

有以下任一**实际可观察**问题即可提出针对性比较，不必只等超容量：

1. 同主题不同范围的记忆混用。
2. 当前／历史／计划／工具观察无法正确选用。
3. 普通 query 找不到必要事项，而合法档案中存在。
4. 材料超过预算，简单取前 k 遗漏关键约束。

但“工作焦点有必要”不等于“独立 LLM selector 有必要”。先比较同信息 State 文本、普通检索与有状态的工作视图。不能让 Attention 弥补零 CREATE，或替执行器纠正未被识别的错误业务 key。

## 9.5 留存主线而非强制激活

如果当前任务无需 selector，就明确报告未触发。若独立选择成本不值得，保留已有工作状态和正常取材，不以“论文需要 Attention”为由增加一轮调用。

<a id="experiments"></a>
# 10. 实验 E1–E6：有限、可归因、执行完整

## 10.1 所有实验的公共条件

相同合法输入、owner、工具能力、memory 初始状态、业务初始状态、当前请求、历史访问合同、评价标准和版本身份。

开发时只更改正在检验的轴。所有已暴露题都标为开发／回归；人工设定初始正确 memory 的实验标为组件诊断，不计自然 formation 成绩。

最终答案按用户可见文本评分：JSON-action 解码后的 `answer` 与 native 的最终自然文本面对同一内容／格式要求，外层协议不被误当作用户答案格式。

## 10.2 E1：同模型工具协议校准——首批必做

**问题：**动作遗漏是否与当前自定义工具表达有关？

**条件：**

- J：历史 JSON-action、non-thinking、冻结失败视图配置。
- N：相同模型、non-thinking、相同内容与权限、经工程验证的 native 工具协议。

主比较保持 `current_request` 与 full/compact 选择相同，优先使用实际失败配置作为定位条件；不顺便回退 full。若无法保持，按协议组合标注差异并限制结论。

**微任务集合建议：**六种意图结构，每种两个预定重复、两个协议，共24条微轨迹。每条含1–3条公开消息，并执行完整工具与必要新会话复用。

| 结构 | 需要观察 | 反例／负例 |
| --- | --- | --- |
| 保存计划但不要执行业务 | 实际 CREATE、准确内容、无预约 | 不把保存当成执行许可 |
| 修改原事项，保留其他条件 | 原 ID 更新、保持有效字段 | 不是新增冲突副本 |
| 查询业务当前状态 | 必要实时查询，不止 memory search | 不先修改计划以“匹配”结果 |
| 普通只读问答 | 正确答案，可零写入 | 不因工具能力存在就强制调用 |
| 命令式引文／未采纳建议 | 不误当长期偏好或业务指令 | 不用关键词强制写 |
| 临时要求＋后续正常任务 | 当前遵循、以后不泄漏 | 不把一次格式永久化 |

旧 H/I 可以占据开发定位子集；新结构在所有候选与停止规则冻结前设计。重复属于同一任务的可靠性观察，不视为新独立样本。

**记录：**首动作、所需操作是否出现、参数正确性、实际提交、内容与范围、后续使用、假保存、全成本。

**判断：**native 有稳定且有意义的改善才进入后续默认候选；持平则可按兼容性／成本保留当前 JSON。不能仅凭一条 CREATE 提案、2/2 或降低 JSON 错误率宣布修复。

## 10.3 E2：推理模式校准——有需要才做

在一个已接通的协议上比较 non-thinking 与真实支持的 thinking，不同时换模型、模板内容和 writer。

建议从 E1 冻结集合中选4种有代表性的困难／负例结构，每模式两个预定重复，共16条微轨迹；选择标准在看 E2 答案前写明。

两种成本视角分别报告：

1. 在可比总输出／计算预算内的质量。
2. 合理允许更长推理后的质量与真实新增成本。

截断是预算事件，不能一边给 thinking 不足空间，一边宣称其语义较差；反之，增加大量预算后的提高不能叫无成本改进。

若服务未提供可靠 thinking 支持或需要未经授权重启，标为未执行。不要用在用户正文追加“想得更久”伪装成原生模式诊断。

## 10.4 E3：对象身份和计划／实际状态——独立接口实验

固定协议与 writer，比较原 key 合同与带来源的对象引用适配。适配必须对所有方法公开，并单独标为应用设置。

建议4种场景、两种接口、两个预定重复，共16条组件轨迹：

- 完整复数名称与相似名称。
- 总计划8件、本轮只执行3件。
- 多个合法对象，需要实际消歧。
- 实际状态与最后记忆观察不同，需要查询。

准确前态的对象选择诊断与从自然形成开始的端到端轨迹分别报告。不得通过引用 wrapper 修改任务数量、替模型选择对象或自动补缺失参数。

指标包括错误对象率、参数误改率、解析／额外查询成本、真实 world 效果。语法更稳定但业务对象选错仍失败。

## 10.5 E4：有限同步记忆子任务——仅在漏存仍存在时

固定经校准的协议和对象接口，对比：

- Direct：同一 Host 自主调用记忆工具。
- Bounded：预定公开输入边界上的有限同步记忆子任务，使用唯一提交入口；不在每次模型续接触发。

建议6种输入意图各一条完整多 session 链、两臂，共12条开发轨迹。范围包括明确保存、同事项更新、独立事项、临时、引用与只读；可将明确删除作为其中一条链的后续步骤。

**所有输入都计入 Bounded 的判定成本。**不能只对正例调用子任务。对机会性记忆是否有价值单列，不以 harmless contextual note 自动认定误存。

默认不再增加第三个“先写后审核”臂。若需要同计算控制，给 Direct 一次正常、无 gold 的继续执行机会，或在固定预算档比较；计费和权限一致，不能只给候选多一次机会而隐去。

此实验检验的是写入职责划分，不将更多写入率本身认作好结果。

## 10.6 E5：连续任务与部分副作用——综合验收

使用8条在修复内容冻结前定义的独立任务链、每条4–6个公开消息／多个 session；候选与最强简单基线各一次正式运行，建议16条完整轨迹。

至少覆盖：

| 任务族 | 必须区分的状态 |
| --- | --- |
| 保存计划→局部执行→查询 | 总计划、当次参数、实际结果 |
| 主动作成功→附属动作失败→续接 | 已完成与未完成，不重复成功动作 |
| 工具超时→结果未知→核实 | 未知不等于没发生 |
| 跨场景偏好 | 长期范围、一次性覆盖、后续恢复 |
| 当前／历史反向查询 | 新认识、历史原话、问题时间目标 |
| 更新一件事→复用两件事 | 独立信息保持 |
| 删除／不再使用→后续询问 | 当前记录退出与历史保留合同 |
| 双 owner／双 session | 隔离、引用和任务身份 |

partial 场景的注入必须是事前定义的业务环境行为，且工具真的执行相应步骤。若上游漏存造成它未激活，端到端仍失败；另起合法前态组件诊断检查 partial 处理，不将该组件通过回填原链。

世界状态评分以实际执行分支为准；前序目标没完成仍失败，后续如实报告“不存在”可在自己的义务上通过。

## 10.7 E6：State–Attention 的独立价值——保留而不强制

只有 P4 所述真实取材／范围问题出现时进行。先固定一份合法 bank 与 writer，比较：

1. 普通 all／query。
2. 相同信息的普通工作笔记或 State 查询增强。
3. 带依据的局部工作视图与 Attention。

同一初始状态、同证据权利、同业务工具和可比预算。若采用独立 selector，其调用计入；没有必要就不执行独立 selector。

先做读取侧对照，再开放连续写入观察。不能在分组、形成、提示、检索、模型全部不同的情况下把差异归因给 Attention。

不通过随机垃圾、任意砍窗口或隐藏 baseline 可取得的澄清制造优点。确需预算压力时，预先声明来自真实部署约束或自然任务累积的预算，并报告合理的多档边界。

## 10.8 第二模型：诊断支线，不是最后奖励

当 E1/E2 仍无法解释行为时，可以在已授权、已具备服务的独立模型家族上做4–6个固定短链的诊断；不要求当前模型先全部通过。

保持合法信息和语义任务。模型确需不同原生模板时记录成模型＋协议组合，不宣称只改变权重。相同家族不同量化不算独立家族。

新权重下载、服务部署、共享资源变更仍需另行授权；不可用时标 `NOT_RUN/BLOCKED_ENVIRONMENT`，不得伪装完成。

# 11. 数据、评价与统计规则

## 11.1 四层义务继续使用，不重新发明评分器

复用已有离线 `obligation_trace.py`：

- 当前任务的显式要求。
- 持久形成／更新／删除及保持要求。
- 后续使用要求。
- 额外完整性诊断。

“完整计划”的必要内容可以由清楚的上下文语义决定，不必机械要求用户逐字段枚举；解释必须在看答案前冻结。仅因 scorer 更喜欢更长回答而新增的字段属于诊断，不用于事后制造任务失败。

原 v3/v4/v5/v6 分数、冻结文件及评分修正说明不修改。本轮只在新身份下评价自己的输入合同。

## 11.2 禁止把评价器接进运行时

runtime 不读取 rubric、expected action、gold key、must_save 标签、题号到工具的映射，也不读取同任务其他臂的未来结果。

应用显式命令模式中的授权字段必须来自真实接口，不得从测试义务表生成。测试前程序预置的正确 memory 或 world 只能在明确标注的组件实验中使用。

## 11.3 七层结果分别报告

| 层 | 指标 |
| --- | --- |
| 意图／动作选择 | 所需操作出现率、漏调用、合法不操作、错误工具选择 |
| 参数 | 目标 key/ID、数量、范围、已有值与新值绑定 |
| 执行 | 实际成功／失败／部分／未知；是否超出授权 |
| 持久记忆 | 内容、范围、当前性、重复、保持、实际删除 |
| 当前回答 | 义务满足、假保存、当前格式、拒答与不确定性 |
| 后续任务 | 跨 session 使用、历史/当前选择、真实业务目标 |
| 资源 | 每阶段完整 calls/tokens、延迟、Store 与恢复负担 |

能够执行更多操作不自动加分；少写入、少 embedding 若来自漏保存也不是压缩收益。

## 11.4 条件化诊断，不乘几个任意“质量分数”

报告：

```text
操作已正确选择时，参数正确的比例。
参数符合任务时，实际执行成功的比例。
持久内容正确且已交付时，后续使用正确的比例。
```

分母是实际满足前置条件的事件，另报端到端总分；不要把互相相关且定义不同的百分比相乘，声称得到任务成功概率。

假保存包括自然语言承诺和程序回执状态，分别评分。程序执行正确不能替代内容正确；模型承诺不能修改真实执行日志。

## 11.5 统计单位与随机性

脚本／用户任务链是主要独立单位；同链多个义务、不同 session、重复请求不是独立样本。所有均值附独立脚本数、义务数、重复次数和缺失情况。

小批首先报告逐例差异、效应量和范围，不以小样本 p 值决定架构。样本足够时才按脚本聚类估计区间；不将156条相关义务当作156个独立实验。

temperature=0 重复可不同。固定重复数、顺序及一次正式尝试，保留全部结果；不得抽样直到某种协议连续成功。

## 11.6 故障安全与语义评分区分

跨 owner 写入、越权删除、未知外部结果盲目重放、伪造执行回执，触发该危险路径的立即停止与隔离。

普通漏答、错误 key 被工具拒绝、合法无操作但未完成意图，保留为语义失败。若环境仍安全、每个 job 独立且已终止，继续完成事前冻结的其他任务覆盖，不因为一个失败自动取消剩余诊断。

如果发现评价合同与实际世界分支冲突，保留原 guide，形成有依据的修正说明；模型结果不变，旧口径与纠正口径并列。

# 12. 成本、服务约束与执行范围

## 12.1 完整成本公式

对实际发生的 provider 请求求和，而不是按逻辑模块重复计费：

```text
总生成成本 = 形成 + 维护 + 检索/材料推理 + 行动/回答 + 失败恢复
embedding、Judge、开发代理成本单列。
```

一个调用同时维护 State 并选择行动，只收费一次。thinking tokens 若包含于 completion 不重复计算。无 usage 保留 unknown，不估作0。

## 12.2 分两种效率结果

1. 固定任务和预算下的成功率、严重错误与完成率。
2. 达到同等任务质量时的全生命周期成本。

native 请求编码、对象查找、写入子任务和恢复都计入。只报告更便宜的成功子集会产生偏差，必须保留全部失败和未完成。

额外一步可能提高任务成功，因此“新增 calls>0”不是自动拒绝条件；也不能因为某一步叫维护，就不计算它。

## 12.3 每批执行前填写资源清单

```text
锁定 scripts / sessions / repeats / arms
预计公开消息数
公共消息生成上限
现有模型与模板的实际容量
预估 calls 和 tokens 的区间及依据
当前连续账本身份
依赖服务、共享资源、串行/并发设置
异常与任务终止的处理
```

预估仅用于决定是否投入，不编造精确 GPU 小时或货币费用。既有运行上限继续遵守；本文不创建未经同意的全局预算停止器，也不解除现有约束。

## 12.4 首批不做全矩阵

首先只做 E1。E2、E3、E4、第二模型、E5、E6 不同时全开。

例如 E1 建议24条微轨迹，不意味着每条只有一次模型调用。发生工具执行和新会话复用后，实际 calls 按真实请求统计。因安全故障被取消的 job 单列，不能从计划分母静默消失。

## 12.5 服务不擅改

不为了 native 自动重启共享 vLLM；不猜 parser 名称；不下载权重；不打印 DSN、token 或私密路径内容。

确需新服务参数时，先给出最小环境差异、隔离方案与回滚；得到对应授权后使用新 run/config 身份。

# 14. 决策门槛、故障修复与回滚

## 14.1 区分三种 Gate

| Gate | 是否可要求零错误 | 含义 |
| --- | --- | --- |
| 确定性合同／安全 | 对已覆盖不变量应零违反 | 正确权限、真实回执、无静默参数修改 |
| 机制可达性 | 必须真实发生相关操作 | 不能用未触发的 selector／partial 能力讲收益 |
| 模型任务效果 | 报告失败与不确定性，不用小样本100%宣称普遍可靠 | 判断实际修复是否值得继续 |

同一模型在短诊断中未达到100%，不自动禁止第二模型、其他独立故障诊断或固定批次剩余覆盖；也不因此放行 Product。

## 14.2 每个假设的决策

| 假设 | 继续该修复的信号 | 不采用或继续诊断的信号 |
| --- | --- | --- |
| H1 协议 | 所需动作和完整链在多个结构上改善，负例无新损害 | 只提高 JSON 合法率；调用与最终内容无改善 |
| H2 推理 | 额外推理减少明确漏操作／错误参数，成本可解释 | 更贵但相同或更差；截断未分清 |
| H3 引用 | 减少重命名且对象选择仍正确，额外查找成本合理 | 模糊绑定到错误对象或依赖人工 gold |
| H4 同步写入 | 漏存改善，误存/重复/范围错误没有系统性增加 | 只是更多 CREATE；终答仍假保存；两 writer 重复处理 |
| H5 用途路由 | 计划、历史、实时问答各取正确依据 | 只在预先知道工具答案时成功 |
| H6 State–Attention | 同 bank 同 writer 下有独立质量／成本价值 | 普通 State 文本或 query 已经持平且更简洁 |

初步修复可设置项目投入信号，如至少两个不同意图结构出现一致改善；这不是统计显著性或顶会门槛。正式稳定性需要新任务和更多独立证据。

## 14.3 有限修复，而不是失败就换题

一次批次失败后：

```text
冻结失败
→ 定位首断点与最简竞争解释
→ 检查是否是执行/配置问题
→ 在同一假设下选择一项最小改动
→ 冻结新版本和相反用例
→ 运行预定完整比较
→ 接受、保留未决或撤回该改动
```

每个具体假设首先允许一个有证据支持的修复候选；若还需第二个，必须说明新证据区分了什么，不能只是换措辞。停止的是本次无信息增量的尝试，不是因为一轮失败就宣布 State–Attention 方向无效。

## 14.4 四类结案状态

- `SUPPORTED_FOR_BOUNDED_USE`：在明确范围内通过，接受 opt-in 配方；不是 Product GO。
- `INCONCLUSIVE`：证据不能区分解释，保留不确定，不选最好轨迹。
- `REJECTED_CURRENT_PATCH`：当前修复无收益或有损害，撤回该改动，保留底座与研究问题。
- `BLOCKED_ENVIRONMENT`：协议／服务不可用或授权不具备，不算模型算法失败。

原 Goal 收口不改。新 Goal 可以通过修复、负面结果或环境阻断完整结案，但必须明确哪些质量目标仍未达成。

## 14.5 回滚边界

协议回滚：切回旧配方，不改已有记录。对象适配回滚：保留原始 key 与真实业务副作用，撤掉 wrapper 不撤销已发生现实动作。同步 writer 回滚：停止新边界处理，已合法提交的记录不因实验退化被默默删除。

数据库／业务状态按运行 namespace 隔离；研究回滚不等于真实操作补偿。需要补偿必须依据真实工具能力与授权。

# 15. 复现、文档与完成条件

## 15.1 执行前冻结顺序

1. 核对合适的代码基线与干净独立工作树，保留所有旧 WIP。
2. 实现并通过必要窄测试，发布本次代码提交。
3. 固定任务、义务、重复、顺序、模型/模板/工具、材料权限与成本起点。
4. 在已发布提交上 prepare，核对 freeze，再执行。
5. 每个 job 使用新 namespace/Store/checkpoint/world；不覆盖旧 attempted 目录。

## 15.4 原长期目标如何延续

如果 native 适配已经解决大部分动作问题，它成为共同底座，后续 State–Attention 对照也共同享有它。

如果仍需同步记忆子任务，其作用和成本单独报告，不能算作 Attention 收益。

如果工作状态／Attention 最后没有额外收益，保留可用普通记忆与实证结论；如果有收益，再用独立任务族、适当跨模型和长期任务建立论文证据。

不将“当前小样本无错误”称为广泛稳定，不将外部项目论文的成绩当作 MiLAi 已验证能力。
