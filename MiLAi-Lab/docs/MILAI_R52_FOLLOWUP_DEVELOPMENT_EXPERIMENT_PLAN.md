## 1. 决策摘要：保留整体方法，收敛下一轮工作

### 1.1 不再误判项目阶段

r52 已经跑完同版 L1、L2、L3 和冻结后创作的新 L4，140 项已回填。原“W1 续办遗漏保存”已有直接修复证据；旧 CI 分层、分页进度和异常效果分类不再作为待从零开发的问题。[S1][S2]

但执行完成不等于功能全部正确。下一轮不重建 Store、恢复平台或多假设记忆系统，而是按以下顺序推进：

1. **使记忆正文与其所选证据一致，完整保留必要限定。**
2. **使核对与重新提案不会把正确内容引向更差版本。**
3. **使 Reader 在证据不足时补读，在证据充分时不过度扩写。**
4. **使截断、核对不可用和无进展循环有明确终态，且不重做已成功业务。**

普通行动误选与请求声明偏差作为集成回归重点，不通过放宽业务保护“修复”。功能质量稳定后，才进入 F5 的效率优化。

### 1.2 总方法保持的五个部分

| 原主线 | 下一轮保持的职责 | 下一轮不做的替换 |
| --- | --- | --- |
| Grounded Memory | 原始来源先保存；形成内容与实际选源关联；原文、语义记录和实际效果分报 | 不换成仅存原文的系统来回避语义形成失败 |
| Verified Object References | 对象身份和可操作性仍来自可信应用及真实工具结果 | 不让自由文本、Source hash 或评估答案创造对象／授权 |
| Semantic/Episodic Memory | 保留长期约定与具体经历的组织能力，保留现有兼容数据 | 不把类型标签当作范围正确性的证明，不为了分类重写旧库 |
| Grounded Revision | 同 ID、读取版本、局部更新、原支持继承、no_change、撤销和历史 | 不改成每次更正新建相似卡，不将最新观察默认视为已生效事实 |
| Lifecycle Recovery | 复用 v7 续办、真实发现、任务限制与 journal，覆盖原保存请求 | 不因新的语义支持失败宣布恢复机制整体未实现，不建第二套任务真相库 |

原总方向来自项目既有约束。保留一个逻辑 MemoryService，普通检索和工作上下文仍是默认路径；模型负责语义选择，程序负责可机械验证的身份、权限、版本与实际效果。[S8]

### 1.3 本轮成功标准

**功能修复成功：**在指定场景和冻结配置下，任务结果、持久终态、必要限定、支持来源、实际动作和最终回答共同满足既定要求。

**不是成功标准：**减少 token、降低调用次数、任何新模块优于所有框架、某个案例多跑一次碰巧通过、核对器输出 supported、CI 全绿、把 PARTIAL 改名为稳定版。

机械安全项须无已知回归；语义质量用固定样本、分项评分与原要求判断。不把小样本零错误外推为普遍保证。

### 1.4 现状与早期设计偏好的差异要公开保留

早期材料反对用常驻 verifier、强制工具或审查循环制造研究成功；r52 实际配置已经使用同模型形成／修订核对，以及 required 声明／补全策略。[S5][S8]

本文件不掩盖这一差异，也不把当前系统称为“无核对、完全自主”的原始方法。**先冻结 r52 作为真实对照；拟变更必须单独说明作用阶段、调用、权限与失败语义。**本轮不再增加常驻核对 Agent，不无限投票，不用强制工具调用次数代替用户任务完成。

## 3. 整体实现链与不可放宽的边界

```text
实际用户消息／实际工具回执
  → 原始事件持久化与可见性检查
  → 当前请求及必要历史引用解析（保留 r52 v7）
  → 形成／局部修订提案：目标、正文、明确所选来源
  → 确定性身份与版本检查；声明的同模型支持核对
  → 同一个 MemoryService 的提交／no_change／pending／unknown
  → 普通检索、实际正文与必要邻接边界交付
  → 回答或受当前许可约束的业务操作
  → 实际结果／journal → 结果修订 → 新进程发现与剩余工作
```

以下不变：

- 历史请求证明请求内容，不证明业务已发生；工具回执证明观察，不自动证明当前授权或永恒有效。
- 模型可以维护语义摘要、计划和不确定判断，但不能把它们升级为可信执行效果。
- 未选来源可以是当前模型看到的上下文，却不自动成为已存字段的支持来源；要用其内容，必须显式选中或按既定未改字段继承规则保留。
- 读取不产生事实修订；混合查询与真实更正按实际内容分别处理，不用“有问号就只读”替代语义判断。
- 原事件保留、语义提交、业务完成、最终答复和整体任务完成是不同状态。
- 不自动读取隐藏DB、gold、E*、故障标签或答案来完成任务；E*只能用于运行后诊断且不是穷尽语义证据集合。
- 所有新暂存提案、核对结果、读取缓存均服从同一owner／可见性／遗忘合同，不产生隐私旁路。

## 5. W1：有限改动的形成与修订保真

### 5.1 问题判断

当前核心风险不是“没有引用”，而是“有真实引用，却漏掉限定、选错支持，或把多个语义角色混成一条确定事实”。新接口仍应复用单正文和逐字段选源，不重新强制双正文＋自由scope整卡改写。[S3][S4][S5]

### 5.2 拟实现：先把支持正文交给模型，再只生成必要变化

形成／修订输入中明确分开：当前请求、待改记录、未改字段、所选实际来源正文。不要只展示opaque ID或一个主题短词。对条件所在的相邻段落，允许按公开原文边界补读；不能因为模型只选了数字，就假定附近限定已被覆盖。

第一版不新增持久本体。可在现有提案中使用**短期比较视图**呈现：

| 维度 | 内容与证据地位 |
| --- | --- |
| 改变的命题 | 模型提出，不是程序真值 |
| 必须保留的已知限制 | 来自旧记录及其仍可见支持；哪些仍适用需结合更正判断 |
| 新消息明确改变／取消的限制 | 显式引用更正；不得机械永远继承旧限制 |
| 尚不确定的时间／范围 | 继续保持不确定，不能从观察时间补出生效时间 |
| 所选支持 | 程序解析真实片段和区间；语义支持仍未经确定性认证 |

这些维度是工作输入和诊断信息，不要求每个普通偏好都生成冗长表格，不另开一轮模型来填表，也不把模型抽取的“限制清单”认作穷尽列表。

### 5.3 典型修复行为

**未定开始周：**把“拟由每周两次调整到三次，但尚未选定开始周”保留为计划与时间未知，不能写成“目前每周三次”。也不能在来源不足时反向断言“两次一定仍有效”。历史记录、拟变更和已知当前状态分别表达。

**业务结果与情境：**卡片既表达“标签已完成”又表达“仅用于本地试验”，则应分别选择实际结果来源和情境来源。不能让旧用户请求证明标签已完成，也不能让工具状态默认支持用户情境。

**显式取消：**取消某个限制时，允许删除该限制，不因“保留原范围”规则拒绝真实取消；目标版本与撤销依据仍要校验。

**技术来源：**不自动扩写缩略词全称、因果原因、推荐规则或正式章节号。未请求且未被来源支持的解释不进入事实正文；确需推断则明确标明，不能升级为原规范断言。

### 5.4 支持选择的边界

保持逐字段支持和未改字段继承。新增值使用实际新选片段；未改值继承对应的旧支持，而不是继承整张旧卡的全部引用作为任意新断言的证明。多个来源组合只在来源可见且实际选择时成立。

程序能验证来源身份和精确未改内容，不能证明任意自然语言的完整蕴含关系。更长引用、更多引用、短语命中都不能替代语义验收。临时上下文也不自动转入field_support。

### 5.5 代码落点与回归

优先核查 `memory/functional.py` 的形成／更正DTO与材料、`memory/service_tools.py` 的参数沟通、`memory/service.py` 的支持与版本继承；本轮源代码改动落在实际函数，不新建平行服务。[S6][S9]

验收包括：同ID数值改变且限制保留；不确定时间不变成已生效；明确取消可成立；多来源分别支持情境和结果；只读不写；原来源不可见时不偷用缓存。旧版本和已确认业务效果不得被为“修正文案”而重写。

## 6. W2：核对可靠性与有界重新提案

### 6.1 先测核对器，不先替换系统

r52核对会将 verdict不是supported或存在差异的提案挡在提交之前；有效判定按精确输入缓存，已尝试而无有效结果则不可静默再试。这些是当前源码行为，不代表语义核对可靠。[S6]

先使用固定提案和固定证据，区分正确接受、错误接受、正确拒绝、错误拒绝、不确定、格式无效、截断、内部矛盾。评分者不能直接使用同一核对器自己的 verdict 作为真值。

### 6.2 拟实现：消除输出合同自相矛盾，但不洗掉真实反对意见

保留逐字段评估，使用单一、可解释的判定合同。若模型输出“supported且有无支持差异”，标记 `assessment_inconsistent` 并保留原结果；不清空差异，不强改成supported，不把它当确认的语义错误。

候选可将机器可检查的输出规则收敛为：

```text
每字段结果：supported / unsupported / uncertain
supported：没有报告阻断差异
unsupported：指出原文与提案的具体缺口／矛盾
uncertain：指出缺少的证据或无法确定的关系
```

程序检查的是字段齐全、枚举、身份和内部一致性，不验证这些理由真实。结构化输出只能帮助结构控制；不能因此宣称语义正确或保证不截断。[E2]

### 6.3 拟实现：按维护事项限制循环，而不只按提案hash

建议首版最多**一个初始语义提案＋一次明确修订提案**。这是待验证的新行为合同，不是r52现有上限，也不能拿来重解释旧结果。

额度绑定同一owner、公开请求及实际目标／已登记维护事项；改变句式、来源顺序或tool-call ID不能重置。多项独立真实请求分别登记，但仍受原每消息总上限约束；无法可靠拆分时保守按同一请求处理，并如实报告未完成事项，不能编造语义等价去重。

上述两次提案仅作为X2的候选控制，不自动替代功能默认；若真实更正完成率因此下降，不因少调用或少写错误而晋升。确需多步补充不同真实证据时，应在下一候选冻结中明确安排，不能在看见失败后原地放宽。

精确相同的被拒提案复用原拒绝结果；不同提案保留独立内容与结果，但共享事项级上限。第二提案必须响应实际缺口，不以“绕过核对”为目标。原文保留、旧卡保持、pending可查询；**pending不算语义保存成功**。

不让同一个用户重申后永久无法恢复：新明确请求可建立新的维护尝试，但须先检查最新版本、权限、未决效果与幂等状态；旧attempt不删除，原业务不重复。

### 6.4 截断缓存不是语义判定

将 `review_supported / review_declined / review_uncertain / review_inconsistent / review_unavailable` 分开。没有完整响应的 attempted 状态不能永久冒充“内容不受支持”，也不能被清空成“未尝试”。

基线保留不自动重试；若引入显式核对恢复，只在新冻结策略中、确认没有执行语义提交且旧响应不可能再次触发提交后允许一次，并持续原计账。必须使用新的attempt身份、保留原proposal及来源绑定，重新检查可见性。不能借核对恢复重做业务动作。

### 6.5 防止“越改越差”

在开发评分中对每个提案分别判定核心命题、限制保留和支持充分性，记录：

- 初始正确却被拒的比例；
- 重提后从正确变为错误的次数；
- 最终获准但比原提案丢失更多条件的次数；
- 成功与失败均使用了几次实际核对与Host提案。

机械上保留未改字段和原片段，无法机械证明的语义变化交给独立于运行时的来源审查。不要新增第三个评审Agent来假装解决这一问题。

### 6.6 安全的诊断对照

“无同模型核对”仅可作为**隔离、离线的固定提案诊断**，不连接业务、不改变默认、不得作为质量模式偷偷放行。要改默认核对政策，必须先有误拒／漏放和端到端证据，另行显式决策。

## 7. W3：普通读取补全与最终回答保真

### 7.1 分开三个诊断问题

1. 正确材料是否进入候选池？
2. 实际模型请求是否交付完整的必要正文与更正边界？
3. Reader是否正确使用了已交付证据？

r52读取中，24/30覆盖至少一个已枚举E*，另两题有报告确认的替代来源；其余四题有边界／正文／分支／第二原文缺口。与此同时，8题核心满分但额外解释有误。[S3] 不能用任何一个覆盖数字宣称全部失败都是装包问题。

### 7.2 拟实现：以已有B1／普通检索为主，修补公开边界

保留候选范围、实际排序、owner、快照与分页机制。对含原文／更正文的来源，优先把公开标题和对应正文边界共同呈现；代码片段不能脱离“原文应改为”的方向提示。使用公开段落、标题和来源关系，不使用E*或题目答案定位。

当整个来源放不下时，明确列出已交付区间、遗漏与实际可用的source/page句柄。不得把相同页面重复返回解释成“另一个来源也已核实”。

程序可记录本消息读取进度签名：`source/version/ranges`。再次检索未新增区间且仍有遗漏时，给出真实的“未取得新材料”反馈，并展示既有分页／定向读取入口；不伪造模型工具调用，不静默读取隐藏内容。

**同一快照的完整性不等于主题证据完整性。** 若候选本身不含另一原文，应如实说明，不能把complete_snapshot写成“全部相关证据齐全”。

### 7.3 拟实现：回答完成用户要求，但不附加无依据的解释

复用现有回答通道，不新增通用答案纠错Agent，不重写已经交付或封存的回答。

| 用户请求 | 预期输出行为 |
| --- | --- |
| 询问当前记忆 | 直接给已知值及必要限制；未知生效时间保留未知 |
| 比较两个来源 | 两边实际读取后再比较；缺一边则只回答可支持部分并明确缺失 |
| 询问历史原话 | 从真实版本和区间提取原文；意译不加“原话”标签 |
| 要求技术原因 | 只解释来源支持的原因；推测标为推测，不能把作者试探性语言改为事实 |
| 询问遗忘后内容 | 不披露被撤销材料；可见性不足不说明“从未提供”，也不凭global epoch断言某主题已忘 |
| 正常开放式解释 | 仍完整回答，不以一句拒答或删去必需条件逃避评分 |

对保存确认、实际效果和精确引文，优先使用程序已确认的结果或原文；对普通语义解释仍单独评分。给一个正确状态标识不能抵消同一回答中的错误断言。

### 7.4 不通过压缩任务来“提高保真”

不能只复述原文而不回答用户问题，不能用“无法确认”替代档案足以支持的回答，也不能为避免错误省去用户明确要求的步骤。原题utility、完整回答合同和合理不确定性同时报告。

**验收重点：**原题正确且无附加错误；必要条件与新旧关系保留；档案有解时能通过合法入口获得正文；档案不足时不作无依据确定性声明；所有读取仍无事实写入。

## 8. W4：提供方可靠性与阶段化失败处理

### 8.1 先确认实际阶段，不归罪于一个总预算

区分请求解释、执行提案、形成核对、修订核对、普通最终回答。每个阶段记录实际wire中的thinking、采样、输出上限、工具schema、finish_reason、content/tool_calls可用性以及已发生效果。

r52配置中执行模型为同一Qwen，native、temperature=1、thinking=true、8,192输出；声明阶段标记thinking disabled和greedy，实际核对阶段是否套用同配置要核对实际HTTP。**不能把已经关闭thinking的核对失败再建议为“关闭核对thinking即可解决”。**[S5]

### 8.2 最小改进安排

先固定一份运行源码和输入，做阶段探针；然后每次只改一种通信因素，如精简核对输出结构或执行阶段的thinking设置。若切换thinking需改变模板／容量合同，则把这些作为同一个明确配置变化登记，不只修改一个JSON标志后宣称相同协议。

不部署新模型，不更新整个依赖栈，不默认增加输出上限。功能确有容量不足的证据时允许另立质量配置，但须同时保留原配置失败，不能把更多预算本身宣称为方法修复。

### 8.3 按效果而不是文本猜测恢复方式

| 失败阶段 | 必须保留的状态 | 允许考虑的后续行为 |
| --- | --- | --- |
| 工具调用前截断 | 没有已接受操作，不宣称遗忘／写入发生 | 新策略中显式有限重新生成；保留原失败及费用 |
| 核对截断 | 核对不可用、未形成有效提交许可 | 保留原文／旧卡，pending；按W2单独规定的显式恢复处理 |
| 业务效果unknown | 原journal仍unknown/pending | 先真实发现，不盲目重放mutation |
| 业务／记忆已提交，最终回答截断 | 保留已确认效果，不因答复失败回滚或重做 | 复用现有无工具的回执说明恢复；不得把reasoning冒充final |
| 额度用尽 | 原始终态和剩余工作明确 | 终止当前执行，不以新tool-call ID重置额度 |

同一故事再次偶然成功不能证明协议修复。比较固定多种输入、记录每次首次失败和重复运行，不只保留最后一条成功轨迹。

### 8.4 重启与缓存合同

已有同ID、版本、请求和费用持久化继续复用。新增事项级额度、核对状态和临时支持关系必须在进程重开后保持；遗忘发生后不能从核对缓存恢复被撤销正文。不要将checkpoint恢复与跨线程记忆混用，二者分别负责线程状态与应用持久数据。[E1]

这里不承诺分布式exactly-once、远程多用户认证或物理擦除；仍限于既有协作串行SQLite和公开工具合同。

## 9. W5：行动选择与恢复的集成防回归

v7恢复原保存请求作为现有基线，不另做任务平台。需要继续检查显式保存、普通新断言、纯查询、混合更正、自然续办、取消保存和遗忘之间的差异。

当前任务不明确时，保留未解析状态；不得从最近一条历史请求自动选择全套权限。工具目录与能力来自实际适配器，模型声明不能创建不存在的工具或新权限。

两工作流仍须检查：查询实际状态后仅办理未完成且当前允许的阶段；已成功动作不重复；已知no-effect也遵守用户“一次”限制；外部编辑使审批失效；历史发布不等于当前版本已发布。

**必要反向控制：**

| 输入关系 | 正确行为 |
| --- | --- |
| 原任务要求业务＋保存，现要求继续全部未完成事项 | v7解析可见原请求，实际查询后只完成缺项 |
| 原任务要求保存，现明确“只查，不保存” | 当前限制优先，不恢复旧写权限 |
| 业务已完成，现仅补记结果 | 不重复业务，选实际回执及必要情境来源 |
| 来源被遗忘或跨owner | 不从缓存或封存attempt补回权限／正文 |
| 历史记忆说已完成，当前后端未完成／版本变化 | 以实际查询为当前观察，动作仍受当前授权约束 |
| 原错误提案已被guard拒绝 | 记录为错误提案，不记作模型正确或实际副作用 |

多余操作提案、被挡动作、真实副作用分别统计。不要为让意图解释通过而放宽业务保护，也不能仅靠guard最终挡住来宣布行动选择修复。

## 10. 开发实验设计：先局部归因，再统一回归

**X0–X5仅为本文实验索引，不改变原L0–L4、历史E0门槛或已有cohort名称。**

所有下列样本量是**建议的开发规模，不是统计功效保证或已运行数量**。执行前按W0实际来源可用性冻结；不能凑不足原件或事后按结果挑选。

### 10.1 X0：机械、SDK和实际模板检查

复用现有测试，不把已通过模块重写。新增检查集中在：

| 检查族 | 必须覆盖 |
| --- | --- |
| 限定与支持结构 | 未改字段不覆盖；不同新增字段不自动共用来源；不存在／跨owner／撤销来源拒绝 |
| 核对状态 | 矛盾结果不放行；unavailable不是unsupported；原结果缓存与新显式恢复身份可追溯 |
| 事项级预算 | 换措辞／tool-call ID不重置；多事项不会错误共享业务幂等键；重启额度持续 |
| 分页与读取进度 | 首单元超限仍推进；重复页不冒充新证据；明确来源边界；遗忘使旧游标失效 |
| 效果与故障 | 写前拒绝、写后unknown、业务已提交而回答失败分开；无业务重放 |
| 实际通信 | 模型可见schema与提示示例一致；生产tokenizer核算完整请求；thinking配置与模板相容 |

禁止网络的机械检查、实际安装SDK、生产tokenizer脚本响应和真实模型运行分别登记，测试个数不相加为自然模型样本。

### 10.2 X1：固定提案的核对诊断

建议从实际历史选12个证据事项，覆盖限定范围、时间未知、否定／规范强度、取消、多来源结果、正常改写。每事项保留一份受支持提案和一份受控错误提案，共24提案；错误构造明确标注，不冒称自然失败发生率。另有无法判断的真实提案则单列，不强制补足标签。

比较两个核对条件：r52原核对，与W2单一判定合同候选；原文、提案、字段、模型和可见输入相同。最初24×2是48个核对执行条件，不是48个独立历史。受控输入不连接业务Store。

固定来源审查先于新结果；valid/invalid/uncertain的判据保留理由和原文位置。报告误拒、漏放、无法判断、矛盾和截断，不只给overall accuracy。

**进入条件：**候选不能靠放行更多无支持事实降低误拒；不能靠全部拒绝提升安全。误拒与漏放的配对改善均需解释，不能把样本不足的无差异说成非劣证明。

### 10.3 X2：真实形成与修订的局部对照

建议先取24个固定开发请求：r52形成的16个失败，加8个事先选定的已通过匹配请求；选择清单在运行前固定。若取不到原件，不能按报告反向模拟原提案，应降低或更名该实验。

优先逐步比较，不做全因子大矩阵：

| 条件 | 变化 | 用途 |
| --- | --- | --- |
| A0 | r52完整配置 | 当前强对照，不拿早期弱版替代 |
| A1 | 仅W1证据／限定输入组织 | 识别形成修复的独立作用 |
| A2 | 在通过诊断后，仅增加W2核对／有界重提 | 识别核对链对最终质量的额外影响 |

各组使用独立库、相同初始状态和真实输入；保存原提案、被拒提案与最终提交。第三条件必须在前两条件有可解释结果后才准入，不默认全部运行。

r52既有保存来源和旧scope不因新配置被就地改写。除最终功能结果外，报告“初始正确→核对拒绝→修改错误→提交”路径数量。减少token但仍无记忆，不能算功能修复。

### 10.4 X3：读取／回答2×2机制实验

建议12题：报告中4个实际交付缺口，4个核心正确但附加解释错误，4个事先固定的通过控制。去重后不足则如实减少，不能把一个题复制充数。

|  | 原回答组织 | 保守但完整的证据化回答组织 |
| --- | --- | --- |
| 原材料装包 | B0 | B1 |
| 公开更正边界／邻接正文装包 | B2 | B3 |

固定候选池、排序与原文范围规则；B2/B3只能基于公开边界扩展，不能手工喂入E*。四格最多48个问答执行条件，用于分别归因交付和回答，不是48个独立问题。

原utility和完整回答合同并列，追加读取／来源区间实际送达逐项记录。为诊断临时交付全量档案的结果只能另列oracle诊断，不计为可部署方法成绩。

### 10.5 X4：提供方阶段探针

建议12个预先固定的小型请求，覆盖普通回答、工具前声明、带限制的语义提案、核对输出四类。先跑当前配置，再只改变一个通信因素。两个条件最多24个请求条件；多步请求的实际调用数另计，不预写成24次模型调用。

对出现截断的固定输入可做预注册重复验证，但所有输出均保留，重复不作为新独立语义任务。不用“重复到成功”报告修复。对纯协议回放先用脚本和实际模板验证，再准入真实提供方。

### 10.6 X5：一个候选的同版完整回归

局部机制有结果后，只选一个当前候选，冻结源码、profile、模型、提示、上限和评分，再运行：

| 集合 | 范围 | 身份与作用 |
| --- | --- | --- |
| 现有通信控制 | 恢复、保存、只读、取消、历史、遗忘与回答 | 防止新方案破坏已修复能力，保留原案例身份 |
| L1回归 | 原24案／48消息 | 原rubric与当前合同分别评分 |
| L2回归 | 两工作流12故事／26消息 | 多余提案、实际效果、记忆终态、W窗口分别检查 |
| L3形成回归 | 原57请求 | 不是未见验证，不删成功例或失败例 |
| L3读取回归 | 原30题 | 原utility、完整回答与交付分别检查 |
| r52 L4回归 | 原12故事／31消息 | 现在已曝光，明确改称旧L4回归 |
| 新功能确认 | 建议另12个实质不同故事；消息数在创作时冻结 | 候选冻结后创作，不仅换名称／UUID；不是自动的正式泛化证明 |

已完成的r52队列永远保持原结果。上述是新候选的回归，不是“补完尚未执行的r52”。不得在同一cohort内改提示或选最优答案。

## 11. Baseline安排：定位缺陷，不先做排行榜

| 对照 | 本轮用途 | 公平性要求 |
| --- | --- | --- |
| **r52完整方法** | 主基线，判断局部修复是否有效 | 固定实际核对、required策略、模型和预算身份 |
| **B1 Chain-RAG／StrongRawRAG** | 只读任务中检验是否由语义卡失真引入错误 | 相同公开来源、Reader、工具、预算与角色，不偷偷给新方法额外档案 |
| **Receipt-RAG式简单回执对照** | 两工作流检查结果存储／恢复是否已经足够 | 同一业务保护与真实回执；涉及普通语义任务时也提供合法原文读取 |
| **原文片段保留对照** | 测量概括导致的限定损失 | 只能作为抽取式对照，不替代“语义形成成功”要求 |
| **无核对固定提案诊断** | 测核对的漏放／误拒净作用 | 隔离运行，无实际业务，不是默认安全策略 |
| Mem0／SimpleMem等 | 本轮不新增大规模接入 | 保留现有版本；只有需要外部系统结论时另立协议 |

B1 Chain-RAG与StrongRawRAG是不同实现，不互相替代身份，也不把r52的普通词法读取自动称作StrongRawRAG。选择已经忠实接入的一种简单读取对照即可，缺失适配需明确记录。

第一轮仅需要当前r52与对应局部候选。没有必要给每个实验配齐所有baseline。不可把曾经的Ordinary弱结果作为当前主要方法优势。

保留v13.4 Simplify：没有重新建立跨历史重复的关系消歧缺口，T1–T3仍未恢复。B1作为简单方案并不表示已经解决所有语义问题。[S10]

## 12. 指标、评分与接受条件

### 12.1 始终分报的五组结果

| 结果组 | 必报内容 |
| --- | --- |
| 存储与来源 | 实际记录、同ID版本、quote身份、字段支持选择、原始事件与语义卡的区别 |
| 语义保真 | 必要限定遗漏、范围扩大、规范强度改变、时间误归因、无依据新断言、新旧混淆 |
| 读取与回答 | 实际区间交付、未补读缺口、原utility、完整回答正确性、合理不确定性／过度拒答 |
| 核对与运行 | 误拒、漏放、矛盾、无有效响应、语义重提次数、按阶段截断和预算失败 |
| 行动与全程 | 多余提案、被挡动作、真实错误／重复副作用、恢复完整性、最终解释与持久终态 |

以原请求／故事为主要功能单位；字段、引文、工具调用和模型请求只作相应诊断分母，不能累加为更多独立任务。

### 12.2 功能修复的决策规则

- **已知确定性安全回归：零容忍。** 跨owner、来源身份破坏、未知效果盲重放、已忘内容泄露、伪造提交回执阻止候选晋升。
- **明确宣称修复的缺陷：必须有正例与反例直接回归。** 失败仍在就只能标PARTIAL，不用其他成功抵消。
- **L1：**保留原最低22/24作为必要条件；但r52已达24/24，候选比r52退化不能仅凭仍高于22宣布改善，必须单列退化与取舍。
- **L2／L3／旧L4：**不降低原评分要求；至少完整报告候选相对r52的配对改善和新增失败。不能只提高总体数量却重新引入核心修订缺陷。
- **新确认：**关键边界通过且未出现与声明冲突的新失败。小样本通过仅是限定功能证据。
- **发布结论：**若FUNC-08或其他核心能力仍不满足，继续PARTIAL／NO_GO；没有为本轮临时降低“完整功能通过”的定义。

允许在有证据的范围内交付“某功能限定可用”，不要求每个组件都证明算法创新；也不把所有任务缩成简单问答以求全绿。

### 12.3 评分身份与统计

形成保真以本任务实际来源为基准，不要求所有来源逐字抄录，但所有影响被保存命题的必要限制都要保留。技术知识不在来源时，不能用外部知识帮输出补成立；需要技术正确性评价可另列，不改变来源支持评分。

开发阶段可由Root审查，但写明实现者／作者／评审重合。关键核对误拒例尽量由不参与运行策略的人或另一独立审查过程复核；若做不到，保持单团队限制，不假称独立Judge。

保存评分前后的分歧与裁定。比较按来源组／故事配对；重复seed或重试不是新历史。需要论文非劣／显著性时另设统计协议和样本量，不能把当前开发数据中的“不显著”称非劣。

### 13.2 何时停止什么

| 事件 | 行动 |
| --- | --- |
| owner泄漏、错误／重复实际副作用、状态损坏 | 立即停止受影响环境及准入，封存、定位后新候选 |

## 14. 容量、费用与运行身份

### 14.1 基线身份

r52包含以下实际设置：65,536上下文、8,192普通材料、8,192输出、每消息24次生成、3次额外读取、1次格式再提案；执行native／thinking=true／temperature=1。声明和核对使用的实际有效参数应从wire与提供方适配共同核对，不由顶层参数推断全部阶段相同。[S5]

本阶段不强求降低这些上限，也不把“用了更少调用”当唯一改善。新语义重提上限和任何通信变化都必须登记为新profile，不能把示意配置直接塞进未知键严格校验的现有prepare()。[S6]

### 14.2 连续账本保留

r52终态报告记录：总账15,390次generation，59,863,812 known／59,894,199 charged tokens；历史unknown usage 1、差额30,387、embedding 964,645。v13.5累计5,664次／32,171,526 tokens。[S2]

这是报告时点，不是下次执行时的实时余额。启动前读实际账本，增量追加，不清零。编程代理费用、美元、GPU时间和物理I/O未测，继续未知，不填0。

按request_mode、Host、formation review、revision review、读取、最终回答和恢复分组计数；reasoning已含在completion时不重复相加。缓存命中降低重新调用不等于已注入模型上下文的token免费。

### 14.3 运行与回滚

每个条件独立root／bank／cohort，同源任务配对但不共享生成后的事实库。原始attempt、proposal、review、receipt、Store投影、HTTP和评分文件保持。

业务效果不能因回滚源码而回滚成未发生。旧候选用独立实验根，不能用旧源码继续写入新冻结数据库。封存语料／日志不自动上传Git；保留原许可与隐私限制。
