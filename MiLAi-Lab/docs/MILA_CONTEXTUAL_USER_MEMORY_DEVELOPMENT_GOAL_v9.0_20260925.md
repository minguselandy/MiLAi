## 3. 工作包与执行顺序

### A. 当前提交的连续基线与输入冻结

在修改运行代码前，使用已提交 v8 源码及原方法参数，从空记忆库和原始业务世界运行同一个已暴露 MERIT arc，完整保留 5 个 episode、7 条公开消息。固定文档四轮同样从原始文件与空库验证一次完整序列，新进程步骤保持原样。

两者是基线尝试，不保证通过。失败时保留完整前缀、实际世界、维护状态和费用，停止该条失败轨迹，不在中途换源码继续并称其连续通过。随后按真实问题开展 B–D，不反复运行同一未改变配置寻求通过。

原 v8 账本封存为 137 次生成／948575 generation tokens／5432 embedding tokens。本轮新账本引用该历史基线，所有新增请求进入 v9 账本。若执行器通过配置指定账本路径，制作独立执行配置并披露仅账本路径等运行位置差异，分别保存原配置和执行配置散列；不能谎称两份配置字节完全相同。

**交付：**基线运行清单、连续尝试结果、失败位置、阶段成本；明确源码、模型、配置、初始世界与输入身份。

### B. 收敛终结合同，并处理部分来源审阅

复用现有观察、写入及未完成操作状态，由程序生成当前提交摘要；Host 不再填写每份来源到每个提交的全量对应表。

Host 保留三个语义选择：相关变化已处理、本次不选择持久化、仍有必须完成的维护。它只列真正剩余的事项，不重复记录引用、版本和提交状态。

来源阅读范围由真实 transcript 与绑定计算。当前任务要求和明确要求全文审阅的材料保持相应约束；普通上下文未读部分可以标为未审阅，而不因取得一份大结果就强制全读。可信输入约束不能被 Host 用“不选择持久化”降级。

**交付：**一个维护决策入口、一份程序生成回执、真实范围与未完成项持久化；没有新的维护审查模型。

**验收：**零写入时不能生成假提交；例行查询不再要求 Host 声称其被写入；未完成操作仍阻止伪 complete；部分阅读不冒称全文审阅。

### C. 当前事项与可写材料的统一交付

使用现有 `MaterialView`、准确版本和可见范围，向 Host 区分当前可修改目标、已交付的相关正文、仅有链接的来源，以及目标原有的依据关系。

同一事项的主体、业务标识、范围和当前状态共同呈现。只读再次核实可产生新观察；没有新的可复用含义时，不要求再 CREATE 一段重复摘要。不能按相似文字自动合并事项，也不要求每个订单只有一张卡。

**交付：**共同材料投影与写入解析使用同一可见性来源；无额外语义分类调用。

**验收：**仅有链接不会被提示成已读；撤回目标已有依据不必伪装为重新阅读；实际正文被移出 transcript 后提示同步失效。提示清晰不等于服务器预先担保未来 CAS 或语义正确。

### D. patch 的增量依据合同

保留当前完整 REVISE，同时增加显式增量分支：准确目标版本＋正文 patch＋新增／撤回来源及依赖。程序从准确旧版本计算完整结果，保留未改谱系；Host 不再重抄全部旧引用。

新增引用仍满足实际交付要求；继承引用仅说明谱系沿用，不标记为本轮已读或重新验证。主体、结构化范围、时间、持久性等元数据变化仍走完整替换。全局语义变化不能因使用字符串 patch 就自动视为局部。

**交付：**一个确定性的增量归一化函数，复用现有提交路径、CAS、来源和依赖检查；版本回执记录继承、新增、撤回及本次实际阅读范围。

**验收：**旧依据未重读时能表达合适的局部维护；已撤回、失效或不允许访问的依据不能隐式洗成有效；版本冲突不自动换最新版本重试；完整替换与增量分支不混用。

### E. 最终连续验证与交接

B–D 实现及必要窄检查完成后，冻结最终源码与执行配置。用原始初态连续执行同一 MERIT arc；文档序列从头完成原四轮，按原请求跨进程。执行中修代码后必须使用新运行身份，旧运行保留；不能以末轮重放替代最终连续验收。

补一个小型局部对照：共享最终终结合同、材料视图、目标与新观察，仅比较完整依据重列和增量依据。优先使用已暴露的退款维护单元；它属于协议成本诊断，不另计为新独立 benchmark 题。

补轻量复现模板与准备说明：本地生成模型／tokenizer 身份，配置服务地址和路径，按固定上游准备原始任务，区分确定性样例、真实模型运行及历史制品查看。配置模板不能通过关闭身份检查运行旧库。

**交付：**结果报告、完整费用、有效配置、输入／源码身份及可解释运行说明。费用没有优势时保留负面结论；连续验证失败时明确未满足的验收，不因实现完成关闭为验证成功。

### 5.2 必要的确定性检查

| 检查簇 | 必须证明的合同 |
| --- | --- |
| 终结 | 无假提交；相关剩余项保留；未完成操作不被吞掉 |

| 业务后恢复 | 真实结果已保存、维护中断，同 session／turn 重开后不重做业务；unknown 仍先核对 |

## 6. 结果指标与费用

每个运行分别记录：原生分数／分母、Host 完成、维护完成、实际业务执行次数、同事项当前正文、剩余项、未审阅范围和恢复结果。

机制链记录“材料已交付 → 模型提出 → 实际提交 → 后续消费”。程序预取单列，不当作 Host 自主搜索；`memory_utilized` 只作一致性线索，不当作记忆不可替代的证明。

成本按输入／输出、embedding、失败／截断、写入拒绝、终结拒绝、业务前后分列。基线连续运行、开发诊断、最终连续运行、局部对照各自记账；全部新增费用进入 v9 总账，不修改旧成绩或清零成本。

“查询 → 业务执行 → 原卡修订 → 结束”是退款例的理想四步路径，不是硬性调用上限，也不要求为了达到四步跳过必要阅读。最终是否划算，由相同条件下实际成本与错误决定。

## 7. 开发协作与性价比

常规开发使用 Sol xhigh；Luna high 通常只负责确有需要的源码／数据下载。用户已明确授权 Luna high 将全部开发提交并推送到 GitHub；此 Git 发布授权不改变模型开发分工，也不意味着 v9 实现已完成。Astra xhigh 只处理具体疑难，例如继承依据与实际可见性的语义冲突，不承担逐提交常驻审查。

开发时可以将终结合同与增量写入作为两个独立工作包并行，先冻结窄接口。`contextual_host.py`、`contextual_user_memory.py` 由集成人统一修改，避免多人同时编辑；材料视图由单一负责人维护。模型实验只有一个入口，遵守当前服务并发 1。无需为这轮文档创建代理或启动并行模型请求。

不设置累计硬停止，也不以调用额度耗尽替代问题定位。新增复验必须对应代码、配置或待验证问题的明确变化；这是一项效率原则，不是新的复核次数限制。
