## 1. 本轮决定：停止增加层数，接好少数关键转换

继续一个逻辑 MemoryService，保持：

**Grounded Memory、Verified Object References、Semantic/Episodic Memory、Grounded Revision、Lifecycle Recovery。**

本轮不重建分页、工作集、Episode、版本历史、对象绑定、整理或恢复平台。状态视图、普通 Host、共同维护与 benchmark 入口已经存在；当前需要改进的是它们如何衔接。[S03–S09]

优先完成四项用户能力：

1. “不要再办理业务，只保存已发生的结果”能进入正确的保存路径，不变成取消业务，也不重新办理。
2. “预订存在、标签失败；后来标签成功”能按分项保留实际观察，而不是被概括成整体失败、发货或取消。
3. 修改一个值或一个条件时，不损坏同一事项中未被更正的主体、计划性质、其他对象、条件及其来源。
4. 问当前、问原话、问过去保存内容时，能选对实际材料，并如实说明本轮保存和剩余工作的状态。

**工程优先不是把输出合法当成功。**工程完成标准是正常路径能执行、正确材料能到达、实际效果与未完成项可访问；语义质量在随后的集中实验中单列。如果局部发现普通语义错误，记录后继续接完其他功能；越权、数据损坏、重复业务效果则立即修复。

### 1.1 默认方法做减法

- 新功能候选优先使用简单 `staged`：一次选择相关事项，再打开和处理；保留 `legacy` 为对照。
- `state_driven` 保持可选：只有确实需要新的来源、历史或目标时继续读取，不为每题固定增加第二轮。
- 保持现有 Qwen3.6 家族、BGE-m3 和普通检索底座。更换模型、强化学习、新 reranker 或多审核 Agent 不作为首批依赖。
- 选择、编辑和结果读取使用同一个请求和现有工作项，不新增第二套事实状态。
- 旧冻结故事或已准备的 PR #118 复核继续使用原配置；不能为了采用 staged 而悄悄改变该配对复核。

这些是本轮工程取舍，不是 D1 已被证明优于 D2 的因果结论。[S05]

## 3. 本轮问题诊断：按最早断点，而非按错误码堆修补

### 3.1 控制语义混入事实判断：当前最高优先级

`61d281d` 的原抽取候选为正向预订计划，续办复用这些候选，没有重新调用Extractor。错误“用户取消预订”首次出现在Editor正式提案，并引用原预订请求。当前“不再重做业务”并未被程序直接放入可选新证据别名，但仍影响了模型的事实解释。[S02、S04–S05]

**已确认：**错误在Editor正式语义输出。

**推断：**来源形状的控制对象和事实包混合，可能诱发“限制执行＝取消业务”的误读。换到System只是一项表示候选，不是因果证明。

### 3.2 工具结果仍被当成长篇自由文本重新理解

真实业务是预订存在、标签曾失败而后成功，但保存中出现整体失败、普通属性变成condition；结果抽取还发生length。[S04–S05]

源码已经有 `ObservationProfile`、`ObservationField`、`VerifiedObjectRef` 和 `derive_observations()`。后者按实际Tool来源和公开字段映射提取字面值，明确不把响应状态自动解释为外部效果，且默认不宣称实时有效。[S06–S08]

**因此不是缺少观察基础设施，而是应更直接地使用已有观察来组织结果维护。**本次未完整审计每条Host运行的所有profile开关和私有请求，不声称现实现完全没有使用这些能力。

### 3.3 小输入也会漏写或误写

历史已经存在空旧库、小输入、候选送达后的正式空输出；最新取消错误的修复投影仅3,621 tokens。[S02、S05] 因此，上下文长度是一个因素，不是所有失败的统一解释。

应同时减少“当前需要处理的信息量”和“当前需要做出的语义选择种类”。不得通过强制非空、执行推理草稿或追加审核者制造保存成功。

### 3.4 条款级局部操作仍可能是复合句重写

已记录的局部替换曾丢失同句其他宠物、旧目标或限定；来源角色正确也可能对应错误的“User reports”正文。[S05] 单元未删除、操作成功、支持存在，均不证明语义保持。

### 3.5 读取目的已保持，证据可达性和答案仍需改进

PR #117解决的是目的持久性，不补出固定池外的历史，也不保证模型选择了身份卡、正确解释时间或区分原话与保存版本。[S03、S09] 后续要验证实际使用，不能继续重复开发同一个字段。

### 3.6 运行环境故障掩盖了主异常

721最早异常为作者retrieval使用SQLite时disk full，随后finally中的COMMIT把外层异常变成“no transaction is active”。根分区／默认tmp已满，/cra仍有空间。[S05]

这是运行工程问题，应单独修，不因此调整记忆算法或给未运行方法记零。只增加必要的启动环境设置与原异常保留，不建设新的存储监控平台。

## 4. 目标架构：同一服务中明确三类输入，不增加三套状态库

```text
当前请求与实际权限 ──────────→ 本次维护范围
可见原请求／待办引用 ─────────→ 需要完成的工作
真实User／Tool来源 ──────────→ 可用事实证据
实际旧记录与版本 ────────────→ 被维护的当前解释
                                  │
                        一次事项选择／必要时直接打开
                                  │
                     现有编辑器＋现有提交与版本机制
                                  │
                实际保存结果／未完成项／当前读取视图
                                  │
                    普通Host回答与显式剩余任务续办
```

### 4.1 三类输入的职责

| 输入 | 可以做什么 | 不能做什么 |
|---|---|---|
| 本次控制与权限 | 决定本轮允许哪些动作、先做什么、何时停止 | 不能证明对象已取消、已送达、已完成 |
| 原始证据与实际观察 | 支持具体命题、报告、业务结果及其时间 | 历史User要求不能自动证明工具已执行；旧回执不等于现在仍如此 |
| 工作状态与视图 | 决定本步看什么、哪些任务待处理 | 不能作为新事实、独立证据或第二份真值库 |

源码默认值与历史原件保持兼容。新设计首先通过内部消息构造和调用组合实现，不优先修改公共Product API／Schema。

LangChain官方区分单次模型输入、持久state、长期store和runtime context；本文只借鉴职责划分，不要求升级框架或引入新中间件平台。[W01]

### 4.2 通用性约束

当前命令可以同时包含“控制”和“新事实”。例如“不要再执行预订；另外把提醒改到周五并保存”，前半句是执行限制，后半句是有来源的更正。不能将整个当前消息永久排除在证据之外。

对“取消订单”也要分情形：请求取消不是已取消；实际工具取消回执是观察；用户报告过去已取消可保存为报告，但不会创造可执行的业务效果。不要实现一条“禁止保存取消”或基于词表的规则。

所有来源都保持实际owner、speaker和subject的区别。只有来源表达本人姓名或真实别名关系时才形成主体关联，不能依据owner字符串、问题答案或gold补姓名。

## 5. 开发包A：接好请求范围与事实输入，优先复用PR #118

### 5.1 直接复用已有修复

保留PR #116的原请求参考投递、单System消息拼装、当前User全文、原回执与当前权限分离。PR #117的目的保持直接复用。PR #118若尚未合并，应在独立开发分支整合其具体源码，不重复实现，也不把合并等同于效果通过。[S02–S04]

### 5.2 统一消息构造

续办路径、普通维护与容量计数复用一个实际消息构造函数，避免fit测的输入与真正HTTP输入不同。

首版继续使用现有模型模板支持的单System方式。控制段落说明当前范围；Human事实部分只呈现本次合法可用的来源、实际旧状态与候选提示。引用中的用户内容不能被视为可覆盖系统权限的高优先级规则。

PR #118把原文JSON引用放入System是一个待验证的呈现方案，不是安全边界。实际授权仍来自运行时，证据资格仍来自实际来源交付；JSON引用本身不证明模型不会混淆。

### 5.3 按实际工作选择恢复材料

对于“保存业务实际结果”，优先定位同一已验证对象的实际Tool结果和原保存事项。原User请求只用于保留情境、对象和仍适用的要求，不能替代结果来源。

不要默认先反复续写“原计划”，然后希望它自然变成实际结果。已有真实结果时，直接让该结果对应的保存工作进入现有维护链；业务已完成就不重新执行。来源不足但当前允许查询时，通过真实lookup／observe取得观察；当前不允许查询时，明确使用的是哪个已保存观察，不冒充实时状态。

继续保留实际旧attempt和失败结果。新语义尝试使用已有resume能力和当前授权，不重置调用额度，不盲重发业务mutation。

### 5.4 当前任务尚未识别时的行为

不再用全局`none`推导“用户禁止保存”。分类仍允许空，但反馈说明“本次未发起维护”，不要伪造用户动机。

应用请求卡尚不能覆盖所有纯memory-only待保存事项，这是PR #116已经声明的边界。[S04] 先复用已有`pending_maintenance`作为同一引用目录的补充；不要复制一份请求存储或新建分类Agent。此项与结果保存链合流，不以全部历史场景枚举作为前置条件。

**包A完成标志：**保存范围和事实来源在正常Host中可追踪；“不重做业务”不再通过程序路径改变对象事实；混合更正仍能获得其实际来源。模型是否仍误解，由集中复核如实记录。

## 6. 开发包B：真实观察优先的结果维护，不再要求模型重造业务事实

### 6.1 复用已有ObservationProfile，而不是建设观察服务

涉及文件：

- `contracts/memory.py`：现有ObservationField／ObservationProfile／VerifiedObjectRef。
- `application/refs.py`：各应用公开字段语义与版本域。
- `memory/observation.py`：现有字面字段投影及观察视图。
- `application/adapters.py`、`native_journal.py`：真实调用、原回执、观察和操作历史。
- `methods/functional_edit_memory.py`与共同维护入口：将选定观察用于结果保存与读取。

新增应用只实现公开适配合同或profile，不修改记忆核心，不写“若目的地是某某”一类领域分支。[S06–S08]

### 6.2 把“观察”和“解释”分开呈现

以下仅为设计示意，不是新实验原件，也不要求原工具返回相同字符串：

```text
实际对象：由已交付VerifiedObjectRef指定
观察来源：真实get_reservation回执
观察时刻：该来源的实际时刻
原字段：status="found"，label_status="completed"
历史观察：早先label_status="failed"
缺失字段：没有发货或物理送达的确认

本次工作：保存已观察结果；不执行新的业务操作
```

程序提供原字段与已声明含义；模型可以将它们组织为“预订存在、标签后来完成”等说明，但不能从调用开始、配置、尝试次数推导发货、交付或取消。

**不把业务结果压成一个总成败标志。**预订、标签、审批、发布等各分项保留自己的观察和历史。请求执行状态与业务对象状态分列。

### 6.3 减少结果抽取的实际负担

首版给结果维护输入一份紧凑的实际观察和必要原始证据，完整回执仍能按需读取；不用在每个阶段重复整个journal、调用栈、解释性schema和历史记录。

若现有profile已经完整表达本次字段，复用其候选观察，不再让通用Extractor重新猜字段值。是否需要进一步语义概括仍由当前任务决定；有未结构化正文时，仅对相应正文使用现有抽取流程。这是受真实来源类型与公开合同控制的通用分支，不是按benchmark答案路由。

该变化要单独命名为结果维护候选并在各方法可比路径共同使用。不能给M独享程序生成的正确答案，也不能将确定性观察保存计为LLM语义形成成功。

### 6.4 不用失败摘要覆盖真实观察

原始Tool事件及其真实字段即使已经保存，也不等于自然语言语义卡完成。结果摘要失败时，用户仍可通过既有来源／观察入口访问真实结果；反馈必须分开“原始观察可读”和“语义维护未完成”。

不新建长期真值副本。需要物化字段时沿用现有观察存储与引用，不复制到多个竞争Store。后续摘要不得回写原回执。

### 6.5 更新观察时保持版本与时间含义

- 不按消息到达先后无条件覆盖冲突观察。
- 文档内容版本不等于审批／发布效果的排序版本；复用现有各字段version_domain。
- 预订回执没有可比较的业务版本时，保留观察时刻与来源；最新已观察不等于永远实时。
- 缺字段不是false，部分回执不清空未出现字段。
- 工具超时或unknown不编造结果；后续查询按已有恢复边界进行。

这些边界已部分体现在当前ObservationProfile和投影代码中，继续复用，不逐层复制校验。[S06–S08]

**包B完成标志：**正常结果查询和保存能使用实际分项观察；长日志不必全量进入Extractor；摘要失败不会使真实结果不可访问，也不被伪装成完整保存成功。

## 7. 开发包C：让局部修订真正局部，保持普通事实简单

### 7.1 先明确模型这一步只处理哪项变化

编辑输入围绕当前事项，提供：当前原文、需要处理的候选提示、实际旧正文、未改限定和可选证据。候选是提示而非命令；模型可以发现候选不忠实或无需保存，但不能将其视为来自新的独立来源。

一条消息涉及多个事项时，复用已有逐候选检索与目标合并能力；只有已观察到合成查询漏目标时再启用相应模式，不重新建设检索器。旧目标已经送达但仍漏写时，改检索不能被当作主要修复。

### 7.2 划分内容的标准是独立可变且语义自足

例如“岗位、收入值、季节波动、储蓄用途”可由几个相互关联的单元表示，使只更正数值时不必重写整句。但不能把“膝盖恢复前每周只跑一次”拆成互不相连的碎片。

首版只改善新形成及实际待修改的复合条款，不离线重写全库，不新增自动聚类／拆卡／合卡循环。仍无法可靠拆分时保留完整有来源的语句。

### 7.3 普通属性不是condition

物品数量、包装规格、观察状态、尝试次数等首先是属性或经历。只有实际来源说明某条规则何时、对谁或在何条件下适用，才建立condition或override。

模型选择添加限制时，只表达目标条款、限制文本和来源；已有编译层负责节点和关系操作。复用现有语义操作，不让模型在多层接口反复声明同一条关系。对缺少目标的提案返回真实错误，不静默把content转换成condition。

先定位`EDIT_APPEND_CONDITION_TARGET_INVALID`的实际提案属于新增、复用还是错误分类，再在对应现有入口简化表达。不要通过全面放宽schema消除错误码。

### 7.4 保留旧支持和改变断言是两件事

已有`from_unit`／`assertion.keep`的支持继承修复直接复用。不再次要求模型抄一份等价的支持集合，不宣称零拒绝就证明该分支在实验中发挥作用。

改变的断言需要对应实际依据；旧岗位所属行业不自动延续为新岗位行业；“考虑”不变成“已计划／已完成”；Assistant建议不因被模型选为evidence而成为User报告。

关系两端的来源不自动支持关系本身。未修改单元保留原来源；修改后保留的旧限定也应继续可追溯。

### 7.5 空提案保留合法，不靠强制动作提高成绩

当前旧库为空、纯查询或无可保存变化，都可以不写。明确保存却没有提交时，按实际状态保留pending／未完成反馈，不虚称“已有记录”。

不增加强制每候选一条操作、自动重试直到非空、私有reasoning转提交或Reviewer循环。若集中实验仍显示大量“小输入＋候选完整＋合法空输出”，再只比较一个更直接的输出表达或任务组织方式；不能同时更换格式、解码、采样和模型后归因。

**包C完成标志：**现有编辑器在普通Host中能完成增量变更并保留实际未改单元；错误或未完成维护仍可解释。创新性由后续相同底座下的对照判断，不以操作名证明。

## 8. 开发包D：读取、反馈和续办使用同一任务目的

### 8.1 目的保持已实现，下一步是使用效果

PR #117使`read_goal`不再由已打开材料类型反推，省略／null继承本请求目的。[S03、S09] 后续只完善呈现和调用组合，不增加第二个目的分类模型。

同一用户问题可同时涉及：当前适用状态、原始说法、实际保存历史。当前卡、旧revision、原始Source分别承担相应证据，不能互相替代。

### 8.2 默认一次选择，允许有理由的补读

短而充分的材料可直接使用；需要筛选时先目录、后完整相关事项。条件、一般规则、活动例外以及已有明确主体关联应作为必要语义一起展开，不能只优化最小token数。

D2继续作为按需能力：确实缺少原文、历史版本或另一个相关事项时再读。固定池不存在的材料，不靠重复目录搜索制造；普通Host可以使用现有来源／历史工具，实验扩展范围则必须各组等权开放。

### 8.3 分开三种进度，复用现有字段

| 进度 | 对应事实 |
|---|---|
| 阅读／导航 | 某记录或来源的哪些范围实际读过，当前驻留什么 |
| 执行／提交 | 哪次调用发生、哪次提交有回执、哪项尚未知 |
| 用户任务 | 还有哪些被要求完成的保存、业务或答复没有闭合 |

不把“选过”直接当“保存完”，不把selector的done当语义完成。已完成调用不自动再次运行；只有新的实际材料、明确续办或现有未完成工作才继续，沿用同一根任务和预算。

无需新增庞大状态枚举。主问题是解释与使用现有状态，而不是再创建一个任务引擎。

### 8.4 当前反馈只描述当前路径

最新61最后答复把先前“不允许保存”和本轮“已允许但失败”混在一起。[S05] 在现有renderer中按当前attempt及原任务结果组织：

```text
实际业务：预订仍存在，标签已经完成。
本轮操作：没有重复办理业务；已尝试保存结果。
保存情况：本轮结果抽取未完成，语义记录尚未正确同步。
已有内容：指明当前实际保存版本，而不是把旧失败说成新成功。
```

上例是呈现目标，不是固定中文模板要求。普通自然回答可以更简短；涉及准确状态时引用实际字段和回执。没有再次live query就说明材料来自先前观察，不暗示本轮重新确认。

### 8.5 错误旧记忆如何处理

PR #118及后续呈现修复不会自动删除已保存的错误取消或发货。[S02] 在具备实际更正证据、当前允许维护并选中相关事项时，通过现有版本修订撤销无依据断言，保留错误版本的可追溯历史。

不从私有评分标签批量“修好”旧库，不默认新查询就获得修改权。正常只读可以说明来源之间存在冲突，而不是把有问题的语义卡当成业务现实。

**包D完成标志：**当前与历史任务能使用对应证据；保存失败不会被解释成权限拒绝或业务失败；显式续办只完成剩余工作；遗忘和只读继续生效。

## 9. 工程运行底座：只修已发生的环境与错误传播问题

### 9.1 临时目录与磁盘

使用现有运行配置或启动脚本设置可写的runtime目录；部署环境当前可选/cra，代码不硬编码该绝对位置。设置TMPDIR与SQLITE_TMPDIR应发生在初始化相关库、创建SQLite连接和worker之前。

启动时做一次运行目录可写与可用空间检查即可；不在每个工具调用前重新核对整个文件树，不引入内容哈希、封存inventory或自动清理策略。空间不足时停止启动并报告路径，不能自动删除用户原件、失败轨迹或共享账本。

SQLite可能为排序、临时表等使用临时文件，默认临时目录与数据库路径不一定一致；故仅将主DB放在有空间的位置并不足以证明该风险消失。[W02]

### 9.2 保留最早异常

在自己拥有的调用或事务包装边界保留原异常；发生错误时不在finally中无条件COMMIT。若实际代码来自第三方Store，先确认锁定版本和责任位置，再做局部适配或上游补丁，不在runner里全局monkey-patch。

SQLite在部分错误下可能结束或回滚事务，所以后续“无活动事务”不一定是首故障。[W03] 最终报告应保留disk full为根因，清理阶段错误另附。不要将数据库失败改记为LLM无答案。

### 9.3 真实模型模板和输出截断

消息拼装和容量计数使用同一函数及实际已安装模型模板。保留单System；本地调用未发出HTTP不能按实际模型请求计费。

对结果抽取length，优先缩小无关输入、避免重新生成程序已知字段和过长输出，再依据实际原因决定任务分批。不要把扩大max_tokens、禁用thinking或切换格式作为无证据的一揽子修复。

截断输出不作为可提交JSON片段使用。旧失败保持；新尝试必须有明确身份和真实记录，业务不随之重做。

### 9.4 不把复现记录变成开发障碍

版本、实际配置和原始结果应保留，但不得要求每次局部改动都通过新的SHA、全仓树身份或大规模字节复验。既有Product/Archive制度不是本轮随意删除的对象；本轮不新增类似门禁，也不以它们代替真实功能。

**包E完成标志：**正常运行目录明确，真实模板可用，最早错误不会被清理异常掩盖；实验启动不会因为旧文档里的PID或状态自动恢复。

每个包交付时，在现有问题表补一句：这次改变了模型看到什么或程序执行什么；是否把已有工程事实又交给模型猜；是否新增了一项可以删掉的重复状态。

发现语义失败后先看原输入、正式输出、真实提交和实际交付，不立刻换方法。若只是同一输入的随机输出差异，不宣称架构原因；若发现新状态仅有名字、从未影响实际输入，删掉它而不是再补报告。

## 12. 功能完成后的集中实验与方法优化

### 12.1 实验顺序

**第一轮：完整候选的功能诊断。**固定一版、一个默认staged配置，用已曝光开发历史完成预测。先读取实际失败，必要评分独立执行；不要每个中间commit都跑五方法长历史。

**第二轮：必要的最小机制对照。**只比较本轮实际改变的一个因素，例如控制呈现、结果观察投递、条款组织或读取呈现；不是同时换采样、检索、预算和Reader。

**第三轮：同版方法与连续历史。**共同底座稳定后，使用B0／B1／B2／M／Append-only，保留原任务的四开发用户各方法277会话范围。65为同一轨迹子集，不重复启动。一个方法的历史从自己的空库自然形成，不把别的方法正确状态注入。

**第四轮：冻结后确认。**16保留用户、LongMemEval、原计划外部强简单与实际适配、native／drift／recovery、完整Host135case／192message及新故事、原六项研究交付继续保留。它们是最终研究范围，不是包A–E开发的前置条件；收缩原范围应单独登记，不能把未运行改记通过。[S05]

### 12.2 只做对结论有用的局部对照

| 要检验的因素 | 固定什么 | 比较什么 | 不能宣称什么 |
|---|---|---|---|
| 控制与事实分离 | 相同实际旧状态、原来源、候选、编辑器、预算 | 61式投递与PR118式投递 | 一次输出改善不能证明机制普遍有效；不要解析私有推理补提交 |
| 真实结果投递 | 相同公开实际Tool回执、对象、当前权限和语义任务 | 原长回执抽取与现有ObservationProfile紧凑投递 | 不得注入隐藏world或gold；字段呈现正确不等于自然语言语义完整 |
| 局部保持 | 实际前态与同一更正 | 普通局部替换与改进后的自足单元／条件编辑 | 不用什么都不改获得高保持率；允许明确撤销 |
| 读取目的与关系使用 | 同一已存状态、原问题、合法固定池、预算 | 简单staged与必要补读；旧目的覆盖与目的保持 | 固定池外历史不可由目的字段产生；更多证据要单列 |

涉及相同输入下的随机差异，选择少量已曝光关键案例预先确定少数重复次数，保留全部输出。它用于诊断，不把seed当独立历史，不展开全面参数搜索。

### 12.3 正式指标保持分层

复用原始日志与现有分析器，仅增补必要分类：

- **执行可用性：**请求是否实际发送、解析是否完成、提交是否有回执、未完成项、容量／磁盘／模板／transport失败。
- **记忆语义：**新要求落实、未改语义保持、合法撤销、主体与来源、计划／完成与时间范围。
- **任务效果：**后续QA、实际业务结果与剩余保存是否完成。
- **资源：**实际调用、累计token、峰值完整输入及已知unknown；不把未执行当效率提升。

这些指标不合成一个未经定义的总准确率。HaluMem保留作者全部机会和有效判断分母，无效标签原样；参考更新查询只在原声明评估阶段使用，不进入Writer。资料未支持的更强gold要求与来源忠实性分开报告。

LongMemEval仍不把answer_session_ids等答案定位标签给方法。Host可读原始Episode不代表benchmark的include_raw=False可以暗改；需要原文辅助，做等信息扩展设置。

### 12.4 正视强简单方法

Append-only不是NeverWrite；它实际保存新事件、按来源与时间读取，是有效强对照。执行更多UPDATE不是总目标。

若single_pass与两阶段相当，优先更简单者；若staged与多轮相当，不默认多轮；若普通局部编辑或追加式已经更可靠，功能版使用它，不强留条件化标签。

条件化潜在贡献仍聚焦：在相同可用底座下，明确局部覆盖和撤销是否减少连续变化中的非目标损坏与范围错误。需要实际机制使用与任务收益，不靠condition节点数量或框架命名成立。

### 12.5 故障与旧结果处理

721旧根保持FAILED；最后未保存的回答不冒充完整预测。新实验从新根开始；不拼接旧后缀成连续历史，不自动恢复旧进程。纯离线评分可以读取已保存结果，但部分范围必须标明。

历史unknown不重置；读取型模型请求未确认与真实业务mutation未知分开核对。启动前确认当前资源，而不是依据本文固定快照执行。
