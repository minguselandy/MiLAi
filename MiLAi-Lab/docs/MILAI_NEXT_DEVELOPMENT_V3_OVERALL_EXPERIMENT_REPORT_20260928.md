## 方法比较

本轮 B0 是 v3 普通 ReAct 配方，B1 增加冻结责任说明，C 与 B1 共享语义说明并增加结果字段和有限核对。
这些名字不等同历史 SER 的原生 B1。三臂均有相同合法普通记录、同一工具目录、实际可见回执标识，
没有 State 双库或自动语义写入；共同 Retained 合同下，每个后续 session 只获得当前请求和真正持久的普通记录。

| 生成调用 / tokens | 22 / 19,752 | 22 / 26,206 | 25 / 33,027 |

C 初始五次不受支持声明均触发一次纠正，随后三次实际写入、两次仍空库假 saved。
三次补写中又有一次把真实记录 UUID 当作 tool receipt ref，正文正确但结果协议仍不成立。
C 最终 12/15 结构声明受实际操作支持；这项机械比例既不能代替内容/范围评分，也不能证明完整用户要求已满足。
没有更改答案、补填 gold、替换失败样本或追加措辞试验来改善它。

B0/B1 的具体失败是当次 BRIEF 被遗漏，并未存成长期偏好或泄漏到后续。
C 通过该格式项，这个正例保留；不能声称 C 在所有质量轴都被支配。
但它在 sample plan 与 editorial 初始形成失败，后者后续仅形成新 link 偏好，无法恢复从未保存的 heading/date。
修订 0/1 是完整链失败，不能歪称 C 的 strict UPDATE 执行失败。

最早断点在 Host 的操作选择及约束消费。实际 HTTP、真实 Store、工具结果和后续请求已核查，
不支持“保存被程序丢掉”“输入没送达”这类解释。结构结果可能替代了实际操作意图，也可能增加引用/输出负担；
六例不足以确定唯一机制。结果字段可检查事实支持，却不能自动获得记忆维护能力。
