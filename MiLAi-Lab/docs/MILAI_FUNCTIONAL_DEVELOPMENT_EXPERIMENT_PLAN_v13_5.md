## 1. 本阶段的决策与成功标准

### 1.1 从研究筛选切换到功能交付

v13.4 已完成条件退出：G1 未建立跨历史重复的关系消歧缺口，因此 T1、T2、T3 不准入。这个结果不证明所有简单方法都充分，也不关闭整个 Agent Memory 功能方向。[R1 §G1与研究主张]

本阶段不再要求每个功能修复先证明新颖性、显著优势或成本下降。开发顺序固定为：

```text
功能正确与诚实状态
→ 跨会话、跨进程、跨工作流可用
→ 功能回归稳定
→ 效率与成本优化
→ 有独立证据时，再讨论算法研究主张
```

**“允许增加必要调用”不等于“无限运行”。** 仍需实际上下文上限、并发限制、可中止的运行预算与逐请求计账，但不把 2,048 token、一次读取或最少生成次数作为本阶段的功能通过条件。[U1]

### 1.2 功能完成意味着什么

一个用例只有同时满足以下条件，才能被记为完整功能通过：

1. 用户本轮任务得到满足，或在客观缺少依据／权限／服务时得到准确的限制说明。
2. 实际持久状态与对外说明一致；保存、修订、业务执行分别有真实效果证据。
3. 必须保留的身份、范围、历史与来源没有被本轮维护破坏。
4. 后续新会话或新进程可以继续使用这些状态，不依赖隐蔽的旧 Python 对象或未声明的完整 checkpoint。
5. 没有跨 owner 暴露、错误对象副作用、重复业务效果或虚假保存成功。

答复可用、原文已存、语义形成成功、完整任务成功是分开的结果。不得用其中一个替代其余结果。

### 1.3 不属于本阶段成功条件的事项

- 不要求 MiLAi 在当前阶段显著优于所有 baseline。
- 不要求 Semantic/Episodic 分类先获得独立算法贡献。
- 不要求固定小材料预算下达到最佳覆盖。
- 不要求新复杂选择器、常驻 verifier 或额外审查 Agent。
- 不因功能检查通过而自动晋升原研究要求、正式泛化结论或 Product 状态。

### 2.1 使用结果时必须保留的限制

本轮材料是 32 个 RFC 与 64 个勘误，仅覆盖规范／勘误工作流。32 个 RFC 不等于 32 个独立来源；存在宽依赖族。Reader 评分是方法解盲前冻结的开发语义审查，但不是独立 Judge 或第二模型家族。[R1 §来源依赖、许可与统计限制]

128 个方法配对中，123 对实际输入相同；追溯题唯一正差来自相同输入，不能归因于 selector。temperature=0 也没有保证输出逐字一致。[R1 §分题型效用与相同输入]

新功能实验可以将这些已曝光失败转为明确命名的回归材料，但不得重开原 T0、改写原输出、回填原 gold，或将这些内容重新标为未见样本。

## 3. 实现范围：保留主干，减少分支

### 3.1 继续保留

- 一个逻辑 MemoryService，复用现有 Store、Source、版本和 journal；派生索引不是第二套业务真相系统。
- B1 Chain-RAG 的简单读取思路与原文回退能力。
- Grounded Memory、Verified Object References、Semantic/Episodic、Grounded Revision、Lifecycle Recovery 的总方向。
- 模型负责语义理解与选择，程序负责可验证身份、引用、版本、存储和真实副作用。[R2]

### 3.2 本轮必须完成

可靠原文保存与状态回执；基于真实片段的语义形成；完整原文与历史读取；同 ID 局部修订与 no_change；owner 隔离与明确遗忘入口；业务 partial／unknown 处理；重启后继续；可执行的集成回归入口。

### 3.3 本轮不扩展

复杂关系消歧选择器、Q1／价值预测器、自然 EC²／HEC、多世界信念库、独立 Attention、常驻语义判真平台、全自动反思 Agent、多模态、新分布式存储后端、全量外部框架矩阵。

EDM／CEP 的已有设计只复用对当前功能直接有帮助的局部行为，例如局部修改、精确 no-op、完整证据单元；不以完成全部历史算法命名模块为前置条件。

### 3.4 对旧规划的明确变更

| 旧开发倾向 | 新功能阶段规则 | 如何避免覆盖历史 |
| --- | --- | --- |
| 固定 2,048 材料作为主要实验条件 | 新增功能／质量 profile，可增加材料与显式读取 | 旧 2,048 结果完整保留，新配置另立 cohort |
| 一次生成、一次维护作为强约束 | 常规路径优先简单；确需格式修正时允许事前声明的有限再提案 | 首次结果、每次调用和终态分别记录 |
| 每个模块先证明算法贡献 | 先验证功能要求；算法优势后置 | 只改变开发准入，不提升旧研究状态 |
| 原文、结构形成和语义正确混成一个保存状态 | 分开持久化效果、结构结果、语义质量与待处理状态 | 新状态映射不回写旧成绩 |
| 继续复杂关系消歧研究 | 保持 Simplify，T1–T3 不重启 | 后续重开必须有独立问题证据与新决定 |

新 profile 不是对旧失败的免费补答。只有实际修改、冻结和新运行产生的证据，才能说明修复效果。

## 4. 目标功能链与最小状态合同

```text
真实用户消息／真实工具回执
        │
        ▼
原始事件可靠持久化 ──失败／未知──► 如实返回，不确认成功
        │
        ├── 程序提取实际来源片段、对象引用和字面观察
        │
        ▼
模型形成语义记录或提出局部更正
        │
        ├── 成功：提交记录／版本，产生真实回执
        └── 不合法或未知：保留原文，记录失败／待处理，不伪造语义卡
        │
        ▼
B1 式普通检索＋当前记录＋必要历史／原文
        │
        ▼
完整证据交付；必要时显式读取下一页或指定来源
        │
        ▼
回答／获授权业务行动
        │
        ▼
真实执行结果 → 修订／状态发现 → 新进程继续
```

### 4.1 不混用的结果维度

| 维度 | 建议状态 | 说明 |
| --- | --- | --- |
| 原事件持久化 | `captured / failed / outcome_unknown` | 是否真实保存原始输入 |
| 语义维护 | `committed / no_change / pending / rejected / failed / not_requested` | 是否形成或修改语义记录 |
| 读取 | `found / partial / omitted / unavailable / not_found` | 必须说明正文送达范围；空检索不证明业务对象不存在 |
| 业务结果 | `confirmed / partial / known_no_effect / outcome_unknown` | 与记忆保存分开 |
| 语义审查 | `pass_scoped / partial / fail / unreviewed` | 运行后质量判断，不由模型自报成事实 |

以上是建议的逻辑状态，不要求覆盖现有 API 命名。实现应优先建立兼容映射，避免为新名字批量改造调用方。

### 4.2 对外可用性

系统应支持以自然语言提出“记住”“改成”“之前是什么”“查看实际操作状态”“忘记这条记录”。内部 ID、hash、Source 引用与读取版本由程序和工具目录提供，不能要求普通用户手写 UUID。

内部方法名称不得直接变成用户的使用负担。公开报错说明实际缺失项，并给出一次可执行的下一步，例如选择两个同名项目之一；不输出只对开发者有意义的长字段校验栈。

## 6. F1：保存、形成和读取可用闭环

### 6.1 F1-A：原文先可靠保存，语义整理可以单独失败

**实施顺序。** 先捕获实际用户／工具事件并得到 durable receipt，再做语义形成。若原事件写入失败或结果未知，不声称成功；也不能据一个未知的原事件状态继续发行权威引用。

**分层结果。** 原事件成功、语义形成失败时，原文仍可检索，并明确标为尚未形成或待处理。已有合法语义记录不因本次失败被清空。系统不得以“引用格式失败”把已经保存的原始内容从普通读取路径中隐藏。

**降级不是完整成功。** 原文回退可以使本轮用户查询得到帮助，但指标必须显示其依赖 raw fallback；不能把它算成语义卡形成质量通过。

**暂不引入新队列服务。** 待处理事件复用现有持久状态，在显式重试／下一次合法维护入口恢复；尚未实现异步任务时，不向用户承诺“稍后自动处理完成”。

### 6.2 F1-B：模型选择真实片段，程序生成精确引文

本轮 55 份不逐字 quote 表明，形成协议需要区分“选择证据”与“复制证据字节”。[R1 §实际执行与验证]

建议实现：

```text
程序：Source 原始正文 → 稳定片段边界 → 实际 fragment handle
模型：选择已发行 handle，提出摘要／范围／记录关联
程序：校验 owner、来源版本、片段身份 → 从原始正文提取 quote
```

模型不用重写 quote，不用生成 hash，也不必手写字符偏移。确需细粒度引用时，只接受绑定到实际源版本的明确片段或可验证区间；多语种／Unicode 原件的提取坐标必须与实际保存的正文一致，不能用归一化后的索引截取原文。

**示意合同，不是现有 API：**

```json
{
  "summary": "用户在项目材料中希望使用公里作为距离单位。",
  "source_fragments": ["frag-7"],
  "scope": {"project": "用户明确提及的项目"}
}
```

`frag-7` 必须由实际工具发行，程序解析后提取原文。示例中的项目文本不能被复制进实际结果充当默认值。

验收时分开记录：句柄有效、quote 字节真实、结构合法、摘要语义受到支持。前三项可以机械检查，最后一项仍由开发审查评价。不能把“引用真实”标成“全部结论真实”。

### 6.3 F1-C：简化形成参数，给出可修正的真实反馈

先复用现有模型和结构化输出能力，输出只保留任务所需的摘要、来源句柄、必要范围、修改目标。模型不重复填写程序可确定的身份字段。

对 schema 失败返回原字段路径、错误类型和允许的形状。第一版可以显式配置“初次提案＋最多一次格式再提案”；该再提案必须由原合法执行流程发生，记录全部费用，不静默 coerce，不补造内容／来源，不进行无限修复。

该行为属于新功能 profile。旧 v13.4 无重试、整份 unknown 的结果保持不变。新增配置必须在观察本轮输出前冻结，同时报告首次合法率和最终完成率，不能只保留最终成功。

一批记录中若允许独立项分别提交，应在执行前声明逐项事务边界，并返回每项效果；涉及同一更正或共享身份的关联项不能半提交后整体报告成功。第一版优先少量明确提案，不为吞吐引入复杂批量执行。

### 6.4 F1-D：保存承诺在实际效果之后

| 场景 | 允许的对外说明 |
| --- | --- |
| 原文已保存，语义维护 pending | “原始内容已保存，记忆整理尚未完成。” |
| 语义记录已真实提交 | “已保存为记忆。”并按实际范围说明 |
| 原卡与新内容一致 | “已有这条记忆，无需更新。” |
| 写入失败／结果未知 | 明确失败／未知，不提前确认成功 |

显式“记住／更新”请求必须有最终确认之前的提交路径。可以使用 Host 记忆操作工具，或事前声明的保存编排；若系统仍使用 Host final 之后的 Writer，则该 final 不能承诺尚未发生的语义提交。

不使用事后重写答案来修补已经发出的假保存承诺。若另有程序生成的状态通知，应单独标为状态通知，不能替换原 final 后再评分。

### 6.5 F1-E：完整正文、关系与历史都能被实际读取

以 B1 为简单主干，先沿普通相关性检索和来源链读取，不新增消歧预测器。

**完整单元可达。** 保存完整源正文及现有无损片段。材料中的每个正文段必须能追溯到实际来源；截断和未送达分别标记，不用 Source 元数据头代替证据。

**大组可拆读。** 一组公开关系超过本轮材料上限时，允许按原来源／段落／成员边界分多次读取。每个成员保留其上下文和显式依赖提示；必要条件、否定、例外和被引用成员不能静默丢失后报告完整。

**不按 gold 拆组。** 拆分边界来自公开结构和原文，不按题目正确答案定制。E* 只供运行后分析。

**重叠正确处理。** 同一 Source 版本上的真实交叠区间可以机械去重；仅文本相似、同名字段或不同版本不能合并。去重后仍须检查未覆盖的剩余区间。

**分页匹配原快照。** 显式 query 和普通包各有实际结果快照。游标解析回发行它的结果集，并继续校验 owner、版本、hash 和可见范围，不能改用最新结果或放宽 guard。

**允许明确追加读。** Agent 可调用原文、历史、下一页等工具；系统公开自动展开策略时，内部读取记为框架行为并计账，不伪造成模型主动调用。停止条件、轮数和预算应可见。

### 6.6 F1 通过条件

原文与语义效果可区分；实际片段能生成逐字引文；失败后的原文仍可查；完整源、历史版本和分页入口可用；功能模式下无需用户手写内部 ID；无假保存成功与跨 owner 暴露。

通过以上不代表 Reader 一定理解正确，Reader 消费仍在 F4 分开验收。

## 7. F2：局部修订、范围、时间与历史一致性

### 7.1 找到原记录，而不是继续创建副本

新更正先通过实际已选候选、来源回链或明确查询定位原记录。语言不同不改变业务身份：中文 Source 与英文形成卡若已有真实关联，应沿关联找到原 record ID。

相似度只能给出候选，不是身份凭据。同名不同项目保留多个结果；目标不明确时请求一次必要澄清，或者保存原始更正为 pending。不能任意挑选后声称修改成功。

### 7.2 局部 patch 的最小语义

- 没有提及的字段保留，不把省略等同于清空。
- `changes=[]` 或精确同值更新不新增事实版本，不更换旧事实的支持来源。
- 明确 remove/retract 才撤销范围或事实；保存撤销事件和历史，但不把已撤销内容继续作为当前事实交付。
- 同值的再次确认可以保存为新的观察，不必生成内容相同的事实版本。
- 修改部分必须有实际支持来源；未改部分保留已有支持。程序保留关系不等于证明任意自然语言的蕴含。
- 对跨多个字段的一次语义更正，使用明确事务边界；提交失败不能留下半个“成功更新”。

初始实现不要求完整的通用 JSON Patch 平台。优先支持项目实际需要的 set、明确删除与精确 no_change，并让行为可测试。

### 7.3 保留范围、否定与表达强度

把“周二上午”改为“周四下午”，不应顺带删掉“本季度”“仅设计审查”“不适用于其他会议”。也不能把“通常”“建议”“可以”悄悄升级为“总是”“必须”“禁止”。

可以使用现有轻量 scope 字段辅助保留；不能让模型在 scope 中填写任意 Source 对象或支持表。字段合法与范围语义正确分别验收，不新增庞大领域本体。

### 7.4 日期与历史的两种问法

至少区分：

- **陈述历史：** 当时用户说过什么、系统当时记录了什么。
- **当前判断下的历史适用：** 根据后来更正，过去实际应该适用什么。

保存／观察日期不自动变成生效日期。没有明确时间锚点的“本周”“下周五”保留其来源及已知参照，不用实验运行日期补成绝对时间。不能从一条更正默认推出“从今天才改变”或“过去一直如此”。

第一版依赖原始更正链、明确时间与不确定性说明即可，不恢复多假设消歧研究。

### 7.5 查询不产生新的事实依据

普通查询只读取事实；访问日志与缓存可变化，但事实内容、当前版本和支持关系不应因查询复制旧答案而改变。

一条消息同时包含查询和更正时，维护实际更正部分；不要按问号、语言或案例 ID 禁写。Host 答案和已检索旧卡不是新用户事实来源。已存在的事实未发生变化时，应返回 no_change。

### 7.6 读取版本、提交冲突与重开

读取返回真实 record ID 和读取时的 revision／hash。提交校验该版本；不能自动换成当前最新版本使旧提案看似有效。

冲突时保留原提案并返回真实冲突，允许合法重新读取后提出新操作。重新读取与再提案是新的实际步骤，不免计费，不冒充第一次成功。

### 7.7 最小遗忘与访问隔离

提供明确的“忘记指定记忆”路径，先确定 owner 与目标。普通检索、显式历史读取、来源回退及派生缓存都必须尊重遗忘结果，不能删除语义卡后又从 raw fallback 回灌。

删除范围应明确：仅语义条目、对应用户可见来源、还是更广的记录集合。若底层只支持可见性撤销而不能物理清除，必须如实说明，不能宣称彻底删除。审计至少保留操作身份和效果，避免不必要地复制被删除正文。

研究封存原件与运行时用户记忆分开处理；不为一个功能测试改写 v13.4 原封存结果。遗忘测试使用隔离副本。更复杂的数据保留制度不在本轮定义。

### 7.8 F2 通过条件

同 ID 修订、必要历史可查、未改范围保留、明确撤销有效、no_change 不增版本、读取版本冲突真实、查询后事实终态未损伤。通过最终答复不能掩盖后台维护造成的新错误。

## 8. F3：工具执行、结果修订与生命周期恢复

### 8.1 业务现实只能来自真实业务接口

Verified Object References 来自已获授权的实际对象查找、可信应用绑定或真实工具回执，不从记忆自由文本生成。记忆的 Source hash、记录 ID 或“已保存”回执均不能成为业务权限凭据。[R2]

未知工具没有公开字段／效果合同，就保留原始返回和未知语义，不凭字符串推断“失败说明没有副作用”。对已支持工具，可以确定性提取对象 ID、状态、版本等字面观察；模型不再重复抄写这些字段。

### 8.2 六种业务情况

| 情况 | 正确处理 |
| --- | --- |
| Clean／confirmed | 报告实际成功，保存相应观察，不重复已完成动作 |
| Partial | 分别保留成功与失败子步骤；只继续仍获授权的剩余动作 |
| Known no-effect | 记录确实无副作用；重试前确认授权、前置条件和后端合同仍有效 |
| Unknown，效果实际已发生 | 不直接重放 mutation；先通过合法发现接口确认效果 |
| Unknown，效果实际未发生 | 对 Agent 同样呈现未知；合法发现后才能决定后续动作 |
| Stale observation | 历史观察保持原值；必要时读取当前状态，不能将旧值自动改称现状 |

两种 unknown 的隐藏区别只用于测试环境与评分，不给 Host／Writer 提示实际注入结果。

### 8.3 三个真实中断窗口

| 窗口 | 必须恢复的内容 | 禁止行为 |
| --- | --- | --- |
| W1：业务可能发生，结果尚未可靠保存 | operation 身份与 unknown 状态；通过公开查询发现实际效果 | 直接再次 mutation，或把超时解释为无副作用 |
| W2：回执已存，记忆投影／修订未完成 | 重开原资源，根据同一回执补完可重放的记忆操作 | 为恢复而重复业务动作 |
| W3：记忆已提交，最终回执／答复丢失 | 返回或读取已有真实提交效果，避免重复修订 | 把“没有收到答复”当成“没有提交” |

仅在后端合同明确支持幂等请求／事务时，使用该能力。没有发现接口或无法唯一识别实际效果时，保留 unknown 并说明需要人工确认；这不是失败的伪装，也不能被记为已恢复成功。

本轮保证限定在实际后端、合作锁／事务和测试并发条件内，不声称任意外部系统的 exactly-once。

### 8.4 两个工作流与入口条件

建议优先复用既有设计中的“预订—标签”和“文稿编辑—审批—发布”。这只是复用顺序，**F0 必须核对本地真实入口和效果合同**；本报告本身没有证明它们在 v13.4 中已运行。

文稿编辑后是否失去旧审批、发布是否绑定当前版本，应以实际公开业务合同和真实后端状态为准。sandbox 发布记录不等于向外部受众成功送达。

若第二工作流入口尚不可用，先修复它并标明未完成；不能通过给同一工作流换名称，充作跨工作流通过。

### 8.5 F3 通过条件

真实业务与记忆效果分别可追踪；partial 和 unknown 得到正确处理；新进程能恢复而不重复副作用；最新状态与历史状态均准确表述；SDK 证据采集在资源关闭前完成，关闭后仍能独立重开验证。

## 9. F4：集成、Reader 质量与日常使用

### 9.1 功能应从统一入口真正可用

只提供独立 helper 或测试函数，不算集成功能完成。正常对话与显式保存／更正请求必须经过同一套已声明能力；所有入口都应能正确绑定 owner、Source、版本、配置和预算。

功能版本应提供一个清楚的 opt-in profile 与统一启动／验证说明。旧默认路径先保留，完成同版本集成回归后再提出默认切换；不在实验中静默切换旧方法。

### 9.2 Reader 错误单独修复

报告中的 RFC9605、RFC9115、RFC8345 相关错误发生在充分证据已送达之后。[R1 §覆盖、预算与最早断点]

新的 Reader 开发要求：

- 回答直接来自所交付原文，保留条件、例外、否定与原规范语气。
- 区分原文事实、基于原文的推理和缺乏依据的补充；不添加任务不要求的技术规则。
- 数值或编码解释确需计算时，只能使用已存在或明确加入的通用计算能力，记录输入输出；不能针对某个 RFC 编号加入答案分支。
- 对不完整依据给出局部结论和缺口，不把“档案中未查到”写成世界中不存在。
- 必要的澄清不计为多余，但不能用不断澄清代替已经能够完成的正常任务。

先检查真实材料和输出，再修改一个通用因素。无需为此增加常驻 verifier。独立 Judge 缺失不阻止开发复核，但开发复核仍不得冒称独立评分。

### 9.3 状态报告与错误处理

错误信息至少区分：输入／schema 错误、来源不可用、目标不唯一、版本冲突、读取结果失效、存储结果未知、业务结果未知、预算耗尽、提供方故障、普通语义错误。

不能捕获所有异常然后返回“没有记忆”或“操作完成”。反复同形错误应结束本次受影响步骤并提供真实状态，而不是无限模型修复循环。

如果使用有限再提案，允许的对象是当前公开流程内的可修正格式／目标错误；权限失败、来源完整性失败、未知 mutation 和账本故障不自动重试。

### 9.4 日常使用文档

至少交付保存、读取、更新、历史、遗忘、查看实际业务状态、恢复 pending 的操作说明。示例使用自然语言，不要求用户了解内部字段；开发说明同时给出回执层次与失败恢复方法。

“已处理事件”表示某次维护已有真实处理凭据，不表示以后无法根据新证据修正该事实。访问审计、语义事实和派生索引分开说明。

## 10. 功能／质量模式：容量足够，但运行有界

### 10.1 容量规则

每个实际请求必须满足：

```text
system + tool_schema + live_context + memory_material
+ 实际额外说明 + output_reserve + safety_margin
≤ 已验证模型／Provider上下文能力
```

计数使用实际 tokenizer／chat template 与最终请求，不能只数单独 material。selector 元数据即使不进入 Provider，也要独立记录系统处理成本；如果进入请求，就纳入实际输入 token。

不改变用户原始事件或偷偷截断旧引用来满足上限。若当前材料放不下，明确分页或提示缺口；功能模式可以采用更充分的初次材料与合法追加读。

### 10.2 起始配置建议

以下数值只是**待 F0 验证、在新结果产生前冻结的起始建议**，不是现有能力声明，也不是功能通过指标。

| 配置项 | 建议 |
| --- | --- |
| 初次 memory material 目标 | 8,192 tokens；若实际上下文剩余不足，按已验证容量降低并明确说明 |
| 输出预留 | 4,096 tokens 起步；用实际服务能力核对 |
| 每公开消息总 generation 安全上限 | 24 次起步，Host、Writer、再提案共同计入，跨同消息的进程重启持续 |
| Writer 常规维护 | 优先一次；可声明最多一次格式再提案，不引入额外判真 Agent |
| 显式追加读取 | 初始上限 3 次；超过时保留未完成状态，不假装证据充分 |
| 并发 | 初期保持串行，避免将资源争用引入功能诊断 |
| 自动 mutation 重试 | 禁止对未知副作用直接重试；仅按实际幂等／发现合同处理 |
| 成本 gate | 只作安全限制和事实记录，不要求 token／费用下降 |

材料 8,192、总生成 24、追加读 3 不是不可调整的研究门槛。遇到正常功能确需更大容量时，先核对最早断点，再在新配置中调整；原预算下的中断与失败照实保留。

**每消息上限不等于每轨迹上限。** 多消息轨迹的总预算应在运行队列中另列，不能将重启后的同消息计数重置，也不能声称 24 是整条轨迹的累计上限。

### 10.3 不把资源中断与语义错误混为一谈

记录 `COMPLETED / FAILED / BUDGET_EXHAUSTED / PROVIDER_ERROR / UNKNOWN / NOT_RUN` 等真实执行结果，并另列语义质量。提高预算后的新版本若通过，只能说明该新设置可完成，不能反推旧设置不是失败。

不因为预算暂时不够而自动宣布“没有研究价值”；也不因为放宽预算而宣布算法优越。本阶段只问功能是否可正确完成。

## 11. 开发实验：分层检查，不铺满方法矩阵

### 11.1 L0：确定性／SDK／协议检查

下表是 **16 类必须覆盖的测试族**，不是已经执行的 16 个测试或固定 pytest 数量。底层实现需要多少测试用例，由边界覆盖决定；机械检查不得计作模型样本。

| ID | 测试族 | 关键通过条件 |
| --- | --- | --- |
| M01 | 原事件存储失败与 unknown | 不发虚假成功，不发行不可信来源 |
| M02 | 同路径新进程重开 | 实际记录、版本和来源可读，不靠进程内对象 |
| M03 | 多语种片段与逐字 quote | 按源版本精确提取，不用归一化索引错切原文 |
| M04 | 非法／跨 owner／过期片段 | 拒绝真实错误，不静默换 Source |
| M05 | 大组分解与公开依赖 | 成员可达，条件与依赖缺失有明确说明 |
| M06 | 重叠区间与正文遗漏 | 精确去重，剩余区间不遗漏，不把头部算正文 |
| M07 | ordinary／explicit 快照分页 | 已发行的正确 cursor 可读；错快照／错 owner 被拒 |
| M08 | 当前与历史版本读取 | 原版本内容不被最新值替换 |
| M09 | 空 patch／同值／部分修改 | no_change 不增事实版本，未改字段保留 |
| M10 | 显式撤销、null 与缺省 | 不把省略当删除，撤销具有真实效果 |
| M11 | 读取版本冲突与重放 | 原读取版本被校验，不发生部分覆盖或重复修订 |
| M12 | Query-only 与混合更正 | 纯读取不改事实，真实更正不因问句而被全部丢弃 |
| M13 | 保存时序与分层回执 | semantic commit 之前不确认语义保存成功 |
| M14 | 遗忘与缓存／raw fallback | 被遗忘内容不从另一读取路径回流 |
| M15 | W1／W2／W3 与 unknown | 按实际窗口恢复，无重复业务副作用 |
| M16 | SDK 关闭顺序与共享计账 | snapshot-before-close、资源释放、实际 usage 与账本一致 |

明确区分 Mock、实际安装 SDK、新进程、真实故障注入和模型调用。合成 world 仅证明相应合同，不外推到未测试后端。

### 11.2 L1：原 E0 正常功能回归

复用原 24 个正常场景与其冻结要求；本次没有获得全部原 fixtures／rubric，执行者需先读取，不在此重新编造原题或重新定义原门槛。

以新功能 profile 单独运行新 cohort。保留原有 22/24 门槛，同时追加本轮核心失败的直接验收：真实保存、同 ID 修订、来源与范围保留、查询后的事实终态、必要历史送达。

**22/24 不是免除关键缺陷的通行证。** 任一跨 owner 暴露、虚假成功、错误对象／重复副作用、不可恢复数据破坏或已知核心修订缺陷尚未解决，都不得宣布完整功能版通过。

旧 E0 的分数不改写为新版本分数。任何对原功能合同的调整都必须先发布明确变更说明；不能看输出后再降低要求。

### 11.3 L2：两工作流的最小生命周期集成

建议每工作流使用第 8 节的六种情况，共 **12 个新开发轨迹**。每条保留完整自然请求、公开工具、实际回执与恢复步骤，不把同一轨迹的多条消息算作独立轨迹。

第一轮先单方法验证完整功能，不立即展开四主臂。若需要区分问题是否来自 MiLAi 的维护路径，再选择 B1／Receipt-RAG 的局部对照，不为功能验收强制复现所有外部框架。

W1／W2／W3 是额外的确定性故障窗口检查；若在同一故事上组合多个故障，应报告基础故事数与变体数，不把它们当成独立工作流。

### 11.4 L3：v13.4 失败回归，明确属于已曝光开发

F0 从原最终 JSON 中抽取：

- 55 个 quote 非逐字与 2 个 JSON 无效的原形成输出及对应来源，用作接口错误定位。旧输出只读，新接口形成另跑新样本／新 cohort，不对旧输出静默修复。
- 涉及装包问题的 26 个问题／13 个历史及实际候选，用于固定候选、固定源的通用读取回归。
- 7 条 Reader 错误所涉及的 4 个问题，用于充分证据条件下的消费回归。

这些集合可能重合。必须通过实际 case ID 求并集，不直接相加成更多独立题目。若缺少原 JSON、实际请求或权限许可，相关项保持未验证，不从报告文字重造并冒称原实验。

运行时不能读取 E*、评分或正确答案。新的分组／分页算法从公开结构形成；E* 仅用于运行后定位已枚举证据覆盖，不覆盖原 T0 结果。

### 11.5 L4：小规模未曝光功能确认

功能修复基本稳定后，建议使用约 **12 个新的自然交互故事**做确认，覆盖普通偏好、混合查询更正、临时范围、历史问题、缺失生效时间、业务继续和恢复。具体分组和容量在看输出前固定。

此处是功能确认，不是正式泛化 benchmark，也不是 v13.4 T1–T3 的恢复。来源相互依赖、模板近似、模型家族和独立评审限制继续如实记录。没有可用独立来源时，不能把已曝光材料重标为未见。

### 11.6 实验停止与继续规则

- 权限／owner 暴露、来源完整性损坏、未知业务效果被错误重放、假保存成功等，停止受影响步骤或共享缺陷影响的队列，先修复再建立新 cohort。
- 普通语义错误保留原答案，可按冻结协议继续采集其他不受影响场景；分析后再修改，不在同一方法身份内临时改提示。
- 提供方故障、存储不可用、计账异常、输出截断和未运行分别保留；不能删除分母或只选择最好一次。
- 每次修复必须新增直接回归证据。不能仅凭最终一次全绿覆盖早期失败，也不要求为每个局部修复重新运行全部历史大矩阵。

## 12. Baseline 的本阶段用途：定位缺陷，不强求赢分

| 对照／参考 | 本轮用途 | 是否强制全量运行 |
| --- | --- | --- |
| 上一个固定功能候选 | 检查本次修复是否回归其他功能 | 关键受影响场景必须有对照或原证据 |
| B1 Chain-RAG | 判断原文／完整更正链是否已足以完成读取 | 作为简单读取参考；不重复旧 T0 大矩阵 |
| FullHistory／FullSource | 在容量允许时诊断“证据有无”和 Reader 理解 | 仅诊断；截断时标 partial，不能再称 Full |
| Receipt-RAG＋普通原文读取 | 检查业务结果／恢复是否仅需简单回执方案 | 只在需要定位时运行小切片 |
| Mem0-TraceEqual | 检查已支持外部 adapter 的摄入、snapshot、关闭和重开 | 若本次修改影响 adapter，则必须跑相应工程检查；不强制全 benchmark |
| SimpleMem、Hindsight、HiMem 等 | 后续研究比较 | 本功能阶段不因尚未复现而阻断独立功能开发 |
| B2／B3／自然 B4／复杂候选 | 保留 v13.4 结果与未运行状态 | 不为本轮新功能自动扩展 |

所有实际比较保持相同合法信息、工具保护和功能 profile；算法特有额外能力必须披露。需要跨会话的任务不允许某一方法免费借用未声明的完整 checkpoint。正常业务查询对所有方法开放，不能为了制造记忆必要性而关闭。

功能阶段可以接受“与简单方案同样正确但成本更高”的候选，前提是成本可承受且安全有界；它只通过功能要求，不构成方法优势。效率阶段再决定是否值得保留新增复杂度。

每个实际轨迹至少记录：

| --- | --- |

| 验收层 | 通过后可以说什么 | 不可以说什么 |
| --- | --- | --- |

## 15. 工程落点、交付与实施顺序

### 15.1 复用既有职责，不做目录重构

下表沿用历史项目职责，**实际路径与函数须由 F0 在本地最新工作树核对**。[R2]

| 职责 | 建议归属 | 本轮改动 |
| --- | --- | --- |
| 来源、回执、版本与数据合同 | `contracts/` | 最小来源片段、保存效果、局部修改与读取覆盖合同 |
| 持久化、Source、修订与读取 | `memory/` | 引文提取、no_change、范围保留、遗忘一致性、重开 |
| 简单检索和材料呈现 | 现有 `methods/`／读取实现 | 复用 B1，改善大组／片段／历史交付；不重造 selector |
| 业务对象与恢复 | `application/` | 真实引用、partial／unknown、恢复窗口 |
| 外部后端 | `integrations/memory/` | 仅修受影响的实际 SDK 摄入与资源生命周期 |
| 模型与额度 | `providers/`／现有计账模块 | 实际请求计量、功能容量、错误反馈；不混入案例策略 |
| 执行与结果 | `runners/`、`harness/`、`analysis/`、现有 scripts | 同版本运行、完整分母、终态检查与汇总 |

### 15.2 可实施的交付顺序

| 包 | 交付物 | 完成判据 | 依赖 |
| --- | --- | --- | --- |
| F0 | 实际源码／环境／配置／账本入口记录 | 不把历史能力当作当前能力，受影响原语可检查 | 无 |
| F1-A–D | 原文保存、真实片段引用、简化形成接口与效果确认 | 保存诚实、quote 精确、语义失败可降级读取 | F0 |
| F1-E | 完整源与历史读取、分页快照 | 关键正文真正进入实际请求，错误游标不误放行 | F0，可与形成路径分工推进 |
| F2 | 同 ID 局部更正、范围／历史／遗忘 | no_change 不增版，未改部分不丢，查询后状态不损伤 | F1 |
| F3 | partial／unknown 与重启恢复 | 无重复效果，真实结果和维护状态可继续 | F1/F2 所需原语 |
| F4 | 同一功能 profile、E0 与两工作流、使用说明 | 核心功能及阻断项逐项验收 | F1–F3 |
| F5 | 后续效率设计 | 只在功能基线冻结且可回归后启动 | F4 |

多个独立源码模块可由不同负责人推进，但同一文件一次只有一个负责人。实际付费运行由统一执行入口负责，避免共享模型服务／账本并发导致不可解释差异。

### 15.3 每次修复的最小闭环

```text
记录原失败及实际配置
→ 最小复现（优先机械／SDK，必要时真实模型）
→ 明确唯一修改意图
→ 受影响检查＋关键默认兼容检查
→ 新 cohort 运行并保留首失败
→ 实际请求／SDK／业务 world／维护后状态核对
→ 写结论与尚未解决项
```

文档、hash 和审计应服务于这个闭环，不把资料归档数量当作功能进度。只读核查不等于运行复现，测试定义数量不等于执行通过数量。

### 15.4 最终必须交付的内容

1. 可启用的功能配置与统一运行入口说明，明确真实支持的后端和工具。
2. 实际源码修改、相应机械／SDK 测试和失败复现材料。
3. 原 E0 新 cohort、两工作流、已曝光失败回归与新功能确认的分开结果。
4. 来源、保存效果、维护后终态和业务副作用的实际证据；原完整账本增量。
5. 功能限制、pending／unknown 处理、恢复／遗忘说明和回滚方法。

完成报告应回答“哪些真实路径可以使用”，而不是只说“新增了多少模块”。

## 17. F5 后置事项：功能稳定之后再做什么
