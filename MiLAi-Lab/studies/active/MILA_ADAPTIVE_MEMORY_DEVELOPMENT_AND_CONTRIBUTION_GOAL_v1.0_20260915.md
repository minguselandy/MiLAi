## 3. 首版方法决定与版本合同

### 3.1 名称与角色

总设计中的 `ADAPTIVE_MEMORY_DEV` 是组合方法的设计统称。本 Goal 将其细化为：

| 项目 | 拟定标识 | 含义 |
| --- | --- | --- |
| 方法实现 | `milai-adaptive-memory-v0.1` | 独立轻量 Host 循环，复用现有组件 |
| 普通政策 | `ADAPTIVE_MEMORY_SIMPLE` | 普通观察整理、纠错、进展与下一步维护 |
| 候选政策 | `ADAPTIVE_MEMORY_CANDIDATE` | 同一能力下实现 N1–N4 的候选工作规则；效果分析可以先聚焦 N1 与 N4 |
| 终端适配器 | `hiagent-method-adapter-v0.7` | 新方法注册、动作分派、账务和状态载荷接入后的目标版本 |

这些是开发目标版本，当前实际版本仍为 RWC v0.4／OM v0.1／适配器 v0.6。若实现时已有其他改动占用版本号，按实际版本递增并更新 manifest，不覆盖已发布版本。

首版由 Actor 和一个维护／Controller 角色组成。维护角色在不同输入模式下执行 OBSERVE、COMPACT、REVISE 或 REVIEW，使用同一模型和共同输出合同；它们是完整功能的不同调用用途，不是四个并行 Agent。

### 3.2 首版完成的功能决定

| 决定 | 首版具体做法 | 理由 |
| --- | --- | --- |
| 执行主干 | Actor 正常推进，真实新反馈直接进入下一次输入 | 不要求每步先控制 |
| 历史组织 | 子目标仅标记事件范围；新组合不另跑每段摘要 | 观察日志已承担压缩职责，避免重复计算 |
| 维护调度 | 容量／原文积累、生命周期事件和显式请求进入统一计划 | 完整支持维护机会，不增加语义触发模型 |
| 当前工作安排 | 仅 Frame 发布当前建议；观察日志记录历史，working_note 记录当前工作 | 不并排发布 OM suggestedResponse 与 RWC Frame |
| 维护权限 | 更新记忆、选择 ACT／RECALL／DELIVER；业务工具仍由 Actor 与原 Host 执行 | 保留完整控制能力和既有权限边界 |
| 路由 | Actor 可执行、回读、请求维护、提交草稿；Controller 可回读后修订、返回 Actor 或处理草稿 | 回读后的认知更新、分支返回和交付均形成完整闭环 |
| 文本交付 | 实现可选复核，默认每目标最多 1 次；关闭、无变化或资源不足时按 v0.4 语义结束 | 复核可用，但不成为普通文本交付的唯一许可 |
| 对照 | 两个新政策共用 Actor、调度、读取、投影、结束规则和预算 | 将政策增量与共同结构改动分开 |

**首版保留 Controller 的完整认知操作能力，并改变它与执行快循环的组织关系。** Controller 不必每轮调用；一旦调用，可以整理、修订、选材、请求回读、根据真实返回重新判断，以及处理已有交付草稿。复用旧 RWC 的操作语义，不继承其每个子目标边界都先控制和摘要的整套调用顺序。

新配置支持 `max_delivery_reviews=0/1`，首次完整使用默认 1，普通与候选一致。关闭复核、进一步减少维护、限制回读深度或精简政策，属于完整基线形成后的优化选择；不能将这些功能先删除，再把补齐功能作为“有收益才允许”的后续工作。

因此，新组合与 OM 的差异包含更新结构、投影、结束规则和请求能力；整方法比较报告组合收益，不能将全部差异归于“分段解耦”。

### 3.3 功能开发与后续优化分开

| 首版必须可用 | 完成功能后再依据轨迹优化 |
| --- | --- |
| 观察、归并及当前观察纠错 | 阈值、批大小、维护是否合并、非必要维护是否延后 |
| 卡片创建、修订、暂存、退役与重新采用 | 卡片粒度、目录长度、默认展开和保留策略 |
| Frame、选材、新反馈直达 Actor | 选材政策、稳定前缀、重复材料和真实缓存收益 |
| Actor／Controller 两种历史读取及回读后更新 | 是否需要 Controller 回读、回读深度和哪些路径可简化 |
| ACT／RECALL／DELIVER、草稿接受／修订／继续 | 默认复核次数、额外消费政策和有价值的介入位置 |
| 开始、继续、目标变化、显式保存与恢复 | 无变化恢复时减少重建、状态载荷与维护成本 |

“功能存在”不等于每个任务都必须使用它；“后来可以删除”也不意味着首版可以缺少总设计要求的正常路径。

## 5. 最小状态、来源和单一工作视图

### 5.1 方法内部状态

```text
AdaptiveMemoryState
    goal / goal_revision
    events / pages / source bindings
    raw_tail                    尚未被观察日志替代的页
    actor_seen_pages            实际送入 Actor 请求的页
    covered_ranges              成功观察所替代的页
    observation_groups          当前观察组，带 handle / revision / 来源范围
    workspace                   复用 working_note / cards / frame
    pending_request             一个显式维护请求，或空
    pending_control             回读后续接／草稿复核等尚未完成的控制过程
    pending_final / review_count / draft_feedback_revision
    maintenance_attempt         最近适用维护输入的身份
    calls / usage / phase / delivery state

MemoryView（装配结果，不另存一份持久状态）
    current observations
    working_note
    one frame
    selected current cards and source pages
    fresh feedback / recent raw pages
    bounded source and card catalog / omitted ranges
```

保留 `MemoryCard(handle, text, source_refs, revision, retired)` 与 `FocusFrame(question, intent, selected_refs)` 的现有职责。目标、依据范围、暂缓理由和不确定性继续用自然语言；不增加 confidence、DONE、风险枚举或“失败两次换路线”等认知状态机。

`MemoryView` 是当前状态的一次投影，不是另一个写入者，也不在 checkpoint 中重复序列化整份展开上下文。

### 5.2 观察组必须可直接修正

现有 OM 观察组包含正文与来源范围，主要通过追加和整体归并维护。新方法为活动组分配 Host 管理的 `obs:N` 和 revision，使维护者可以明确替换其中一个组的正文。

- 修订活动组：handle 不变，正文有变化时 revision 增加；旧正文退出当前观察视图。
- 新观察：Host 根据本次成功覆盖的批次新建组，来源范围由程序生成。
- 归并：对本次明确送入的活动组生成一个新组，继承其来源范围；旧组退出活动视图。
- 旧版本保留于既有执行审计轨迹；首版不新增任意派生版本数据库。公开恢复保证当前状态和原始来源可回读，不承诺任意历史派生正文的版本查询。

归并后的旧 `obs:N` 可返回“已归并”的元数据及原始范围入口，不能把新组冒充旧组原文。Frame 可选当前观察组、卡片和原始来源。归并替换了已选组时，Host 将相应当前选择映射到新组并登记该机械变化；显式历史回读仍区分原组身份，不能借重定向假称旧正文已被读取。

### 5.3 引用与披露依赖

原始事件、工具回执与范围使用既有合法句柄；卡片和观察组使用 Host 公布的内部句柄。模型不能自建来源身份、修改版本、权限或覆盖范围。

`source_refs` 表达回读入口，不证明条目成立，也不证明正文在当前调用中被阅读。实际送达页由请求记录确认。观察组采用真实输入范围的保守并集；修订保留未被证明可移除的旧依赖，并加入本次实际输入的披露依赖。首版不训练或调用模型推断精确句子级来源图。

派生材料不能因为换了 handle、删除了可见引用或修改了正文就摆脱来源治理。公开保存与读取继续走既有授权及依赖检查；不另造权限系统。

### 5.4 三种位置绝不混用

| 状态 | 何时改变 | 不能表示什么 |
| --- | --- | --- |
| Actor 已接收页 | 该页正文确实进入一次 Actor 请求，调用账务按既有生命周期登记 | Actor 已理解、维护者已整理 |
| 观察覆盖范围 | 指定原文批次形成合法非空观察并原子接收 | 模型对批次内容的语义完全正确 |
| 维护尝试身份 | 对相应输入快照尝试过一次维护，包括无变化或无效输出 | 原文已经可以移除 |

跳过维护、仅修订卡片、接受 `{}`、输出拒绝均不推进原文覆盖。读取长回执的一页，不等于读完该回执；摘要替换页正文后，原始来源仍须可按范围恢复。

## 6. 调度算法：快循环持续推进，维护有明确位置

### 6.1 初始配置

以下为新方法首个配置的建议值，沿用当前 OM 的已知容量设置作为起点，不声称最优：

| 参数 | 初值／规则 |
| --- | --- |
| 模型与窗口 | 使用执行时可用的共同 Provider/profile；首次优先沿用原 65,536-token 配置并记录实际值 |
| 观察触发 | 未观察原文约 12,000 tokens；可覆盖页仍须满足已送达 Actor 等条件 |
| 日志归并触发 | 当前观察正文约 16,000 tokens，或实际输入容量需要 |
| 近期原文 | 保留最近 2 个事件的原文入口，按页装配；不截断后冒称完整消息 |
| 默认分页 | 4,000 字符；单次显式读取不超过既有 16,000 字符合同 |
| 输出预留 | Actor 4,096 tokens；维护 2,048 tokens，模式间共用 |
| 一般维护机会 | 通常由一次调用完成；必要归并、观察及回读后修订可连续处理，逐次说明职责和记账 |
| 回读扩展 | 复用既有有界控制规则，初值最多 2 次；始终保留返回 Actor 的资源 |
| 交付复核 | 支持 0/1，首次完整配置每目标最多 1 次；普通和候选一致 |
| 结束预留 | 维护不得占用最后一次 Actor 生成 |

所有阈值经过实际 tokenizer 与完整消息装配核算。字符分页不是 token 预算；系统提示、工具合同、目标、来源目录、记忆、原文和输出预留都计入窗口。

### 6.2 维护模式与选择顺序

| 处理位置 | 模式 | 触发和输入 | 处理结果 |
| --- | --- | --- | --- |
| 待处理控制 | REVISE／REVIEW | 上一次 RECALL 的真实返回，或已有当前草稿 | 完成回读后修订，或进行有界草稿复核 |
| 1 | COMPACT | 活动日志达到归并阈值，或基本工作视图无法容纳；送入可处理的活动组 | 合并这些组，保持来源并集；可同时修订工作区 |
| 2 | OBSERVE | 原文达到阈值，存在已给 Actor、且不在近期保留范围的可处理页 | 处理一个能放入维护输入的批次；可同时纠正旧组与工作区 |
| 3 | REVISE | 有尚未处理的显式维护请求，且未被前两种机会完成 | 使用请求、相关条目和当前反馈更新认知；不替代原文 |
| 无 | 不维护 | 没有适用输入，或相同输入已尝试且无新依据 | 直接装配 Actor 输入 |

有显式请求时，优先把请求及其相关条目装入本次适用维护。请求引用的正文或目录必须明确呈现；容量无法容纳时保留该请求，不声称已处理。若完整呈现后模型返回无变化，结束这次请求尝试，把结果交给 Actor，不反复调用格式修复器。

COMPACT 与 OBSERVE 同时需要时，先处理容量问题；随后确有可处理原文且需要完成本次整理，可继续 OBSERVE。Controller 请求回读后，也允许用真实返回继续修订。不要用“一边界最多一次模型”限制完整功能；同时不把同批材料无职责地依次送给多个角色。

一次调用可以整理并修订工作区；原文覆盖和组归并仍各有明确输入批次。首版可采用分开的 OBSERVE／COMPACT 调用完成完整路径，后续再依据成本考虑合并输出。任何归并未缩短内容或没有新处理范围时，不因重装配而重复同一操作。

### 6.3 生命周期触发与正常推进

初始目标、外部新要求、工作段变化、工具反馈、恢复、回读返回和草稿产生都作为已有生命周期事件进入新方法。触发政策决定是否需要维护，不能靠遗漏事件来减少调用。

首个配置中，普通工具反馈和子目标改名不单独强制维护；新目标直接进入 Actor 并清理旧 Frame／旧草稿，若已有工作需要重新组织，可触发 REVISE。显式请求、Controller 回读返回和适用的草稿复核要有完整后续处理位置。仅重新装配输入不会制造新维护事件。

显式交接可以直接保存现有状态，也允许有资源且有明确需要时先进行交接整理；不能要求必须调用模型才能保存。恢复后保留原来的待处理请求、回读位置和适用维护，目标有变化时重新判断；无变化恢复不强制重建全部记忆。

### 6.4 防止重复工作，但不写语义规则

尝试身份由模式、真实批次、相关状态版本和请求构成。未变化的同一输入不反复维护；失败或无变化保留原文。不能把维护返回的 `{}`、系统提示或拒绝反馈自身当成新的业务证据，制造下一次同内容调用。

正常新反馈、不同来源页或用户新目标可以产生新维护机会。重复显式请求仍计入 Actor 与维护成本，由有界总预算收口；首版不增加“连续几次无变化必须换策略”的程序规则。

### 6.5 完整循环伪代码

```text
初始化：记录 method / policy / model / budget / source / environment 合同
追加真实目标，建立原始事件与页，工作区可为空

step：
    处理既有未知用量、未知副作用和授权停止条件
    若已结束：返回当前终态，不再次维护

    若有当前草稿：
        按复核开关、目标复核额度、草稿有效性和余额处理 REVIEW
        显式 DELIVER 则交付；可选复核无变化或不可用则走已有结束语义
        已交付则立即返回；过期草稿不能直接交付
    若仍需工作且余额为 0：沿既有合同结束并说明未完成

    若仍需工作且余额允许保留 Actor：
        选择待续接控制或 COMPACT / OBSERVE / REVISE
        对适用输入调用 maintenance，规范化并原子应用
        ACT：返回执行；必要的另一整理批次按真实职责处理
        RECALL：读取真实来源，在额度允许时继续维护，否则把返回交给 Actor
        DELIVER：仅在存在仍适用草稿时处理；无草稿不猜测交付
        无效输出：保留状态和原文，给出简短反馈，回到可用执行路径

    根据当前目标、最新反馈、最新记忆版本与合法来源装配 Actor 输入
    余额为 1 时附 closing 状态
    调用 Actor，登记实际送达页与真实用量

    final：形成待交付草稿；有复核机会则进入 REVIEW，否则交付 UNREVIEWED
    closing 且非 final：不执行新的业务或内部请求，结束为 INCOMPLETE
    exec：执行实际业务工具，保存真实返回，进入下一个 step
    read / retrieve：读取合法历史，保存返回和实际范围，进入下一个 step
    maintain：登记一个显式修订请求，进入下一个 step
```

控制完成当前整理、必要回读或草稿处理后，把执行权交还 Actor 或结束。普通字段变化不自动产生下一次控制；连续调用必须对应待处理范围、容量整理、真实回读返回或草稿复核。读取失败、输出不适用或记忆暂时落后不扩展成多层 fallback。

## 7. 模型合同：稀疏修订、一次接收、一个写入者

### 7.1 维护输入

维护者读取：独立的当前用户目标、本次模式与处理范围、当前观察组、短工作记录、Frame、选中或请求涉及的完整卡片、相关真实新反馈，以及有界的其他来源目录。

它不能只读自己此前选中的内容。新反馈优先保留，未选材料保留可访问入口。OBSERVE 的覆盖批次与用于帮助判断的近期反馈分别标注，防止模型写出一段摘要后程序误删所有输入原文。

### 7.2 维护输出

以下是新方法拟议合同示意；实际句子、引用和条目由任务生成，不作为固定诊断内容注入：

```json
{
  "group_updates": [
    {"handle": "obs:3", "text": "旧判断只在已观察的条件内成立；当前新结果改变了其中一项条件。"}
  ],
  "workspace_update": {
    "working_note": "保留其他仍有依据的工作，处理这次变化影响的部分。",
    "put_cards": [
      {"handle": "card:2", "text": "修订后的工作判断与需要保留的约束。", "source_refs": ["H006", "H010"]}
    ]
  },
  "frame": {
    "intent": "依据当前结果调整受影响部分；若现有材料不足，再取得必要细节。",
    "selected_refs": ["card:2", "H010"]
  }
}
```

OBSERVE／COMPACT 使用可选 `observations` 文本，表示本次相应批次的整理结果；其对应范围由 Host 决定。REVISE／REVIEW 可只提供 `group_updates`、`workspace_update`、`frame` 或必要路由。所有模式共用可选 `dispatch`，交付修订使用其中的 `dispatch.delivery` 字符串；模型不填写页覆盖、revision、依赖版本或运行阶段。

当前工作安排不重复输出 `continuationHints`、`suggestedResponse`，统一由 Frame 表达。Controller 路由沿用现有 `dispatch.kind`：ACT、RECALL、DELIVER。Provider 的结构化输出 schema 与本地接收器采用同一完整合同，不能一端支持稀疏更新和回读、另一端仍要求全字段或拒绝该路由。

### 7.3 接收语义

| 表达／情况 | 处理 |
| --- | --- |
| `{}` | 普通阶段合法无变化，继续 ACT；草稿复核阶段按无显式路由且无内容变化处理，不解释为语义批准 |
| 缺省 workspace_update／frame／group_updates | 相应内容保留 |
| working_note 缺省或 null | 沿用现有保留语义；空字符串明确清空 |
| Frame 部分更新 | 未提供字段保留；空 selected_refs 明确清空 |
| put_cards 新卡片无 handle | Host 分配 handle；已有卡片需使用公布的 handle |
| retire_cards | 沿现有卡片退役语义保留返回入口，不回滚真实世界 |
| group_updates | 只能更新本次输入公布的活动组；不凭未知编号猜测 |
| OBSERVE 合法非空 observations | 创建新组，仅移除本次声明批次中的原文页 |
| OBSERVE 只有卡片或 Frame 更新 | 应用合法修订，但原文仍未被观察替代 |
| COMPACT 合法非空 observations | 替代本次组批次，继承范围；未送入的组保留 |
| COMPACT 缺少 observations 或为空 | 不移除旧组；合法工作区修订仍可原子接收 |
| 空 observations | 视为没有覆盖输出，不清空历史 |
| 对同一组同时提出被归并和单独更新 | 本次更新有歧义，拒绝整份提议并给出简短反馈 |
| 缺省 dispatch | 普通阶段默认 ACT；复核阶段应用 v0.4 的阶段语义 |
| RECALL | refs 为字符串列表，start／length 共用；保存真实返回后继续适用控制，不丢原反馈 |
| DELIVER 无 dispatch.delivery | 仅在有仍适用草稿时接受原稿 |
| DELIVER 有 dispatch.delivery | 以明确修订正文交付，沿用原权限和当前草稿合同 |
| 无草稿 DELIVER／未知回读引用 | 不猜测、不部分提交；普通阶段交回 Actor，复核阶段按既有可选复核不可用语义处理 |
| 无效 JSON、未知句柄、非法范围、含义冲突 | 不部分提交，保留旧状态和未观察原文；不额外调用修格式模型 |

一次响应先规范化，再一次校验、一次原子应用。`observations` 缺省是合法的稀疏更新；字段存在但类型错误是无效输出，两者不能混为一谈。内容没有变化不增加 revision；接收成功和语义正确分别记录。

模式相关检查直接在一个接收边界完成，不建立多层 validator，不为假设中的任意模型格式增加修复分支。可以复用已有明确、无歧义的规范化规则，原始返回仍保留用于诊断。

## 8. Actor 输入、历史回读和显式修订

### 8.1 Actor 实际看什么

Actor 输入按实际容量装配以下内容：独立用户目标与工具合同；真实新反馈；当前 Frame 与短工作记录；当前观察组；选中卡片和选中原文；必要近期完整交互；有界目录与未展开范围。

共同 Actor 政策明确：工作记忆是建议及历史表述，真实新反馈可以否定它。Frame 可以滞后，不能覆盖新要求或工具返回。未解决问题只有实际影响当前决定时才值得增加工作；任务已有足够依据时正常交付。

原文按 `(ref, revision, start, length)` 去重。同一卡片或观察组默认只投影当前版本；修订前的完整正文不通过旧工作区消息继续自动回放。执行日志保留旧版本不等于每次将其重新送入模型。

模型读取过但尚未被观察覆盖的原文仍保存在 raw_tail；容量不足时可以暂不自动展开部分旧页，但必须留下真实省略记录和读取入口。未呈现页不能计作已阅读，不能因目录里有摘要便计作全文覆盖。

### 8.2 一个清楚的历史读取合同

新配置的 `retrieve` 采用与现有 RWC 机械范围一致的字符串列表：

```json
{
  "action": "retrieve",
  "arguments": {"refs": ["card:2", "H010"], "start": 0, "length": 4000}
}
```

`refs` 为已公布句柄的字符串列表，start／length 对本次列表共用。不同范围分次请求；不提供另一套对象数组外壳。模型已有的其他 Actor 字段继续按共同 Actor 合同填写，示例只展示相关字段。

Controller 使用同一内部读取意图，经现有外壳表达：

```json
{
  "dispatch": {"kind": "RECALL", "refs": ["card:2", "H010"], "start": 0, "length": 4000}
}
```

Actor retrieve 与 Controller RECALL 的来源能力、范围规则和返回表示一致，区别在于返回后继续哪个调用角色。已有反馈即使尚未送到 Actor，也不能被这次控制回读覆盖或消费掉。

复用一个内部读取函数分派卡片、观察组、原始事件和工具回执；输出真实正文、revision、总长度及本次范围。原有 `read(ref,start,length)` 作为单个业务回执读取继续可用；它与 retrieve 复用相同范围检查，不增加隐式全文读取。

历史来源范围回答“过去记录了什么”。读取当前文件、当前服务或当前状态必须使用真实业务工具。一次回读不会自动采用旧路线，也不回滚文件、恢复权限或推进原文观察覆盖。

### 8.3 按需修订请求

为避免 Actor 每轮填写额外字段，首版只增加一个可选内部动作：

```json
{
  "action": "maintain",
  "arguments": {
    "reason": "当前结果改变了之前使用的判断，需要修订工作记录后继续。",
    "refs": ["obs:3", "card:2"]
  }
}
```

该动作登记请求，下一边界进入适用维护；不执行终端操作，不获取额外权限。若已有 OBSERVE／COMPACT 机会，可一并处理请求。没有维护余额时保留结束机会，不能为了处理请求追加生成。

请求本身消耗一次 Actor 生成，维护另计一次；这是真实方法成本，不称为免费自适应。普通政策与候选都获得此动作和相同提示，不要求每次失败或不一致都调用它。

Actor 需要原文时先 read／retrieve，已经有足够材料时可直接 maintain。Controller 需要已知历史细节时使用 RECALL，并在真实返回后继续修订；需要当前业务状态时交还 Actor，通过真实业务工具取得。两种路径都要实现，后续再判断哪些调用可合并或省略。

### 8.4 使用时纠错的完整路径

```text
旧观察或卡片实际参与一次工作
    → 新反馈与它不一致，或暴露适用范围不足
    → Actor 用当前材料重新判断；必要时取得历史或当前世界信息
    → 下一次自然整理、一次显式 maintain，或 Controller 的 RECALL 返回
    → 替换受影响观察／卡片，保留其他有效工作，必要时调整 Frame
    → 下一次真实 Actor 请求使用更新后的视图
    → 调查、修改、采用／不采用旧路线，或收窄交付
    → 真实结果与完整成本
```

如果仅 Actor 临时理解正确、存储中的错误记录没有修订，应记作即时纠错；如果记录更新后尚未再次使用，应记作更新发生。只有完整链条才支持“修订后重新使用”的行为描述；净收益仍需对照。

## 9. 结束、异常和保存恢复

### 9.1 结束规则

维护仅在至少保留一次 Actor 的前提下调用。最后一次 Actor 获得 `call_budget.closing`，应给出当前结果或如实说明未完成；若仍要求新工具或 maintain，Host 不执行该请求，沿既有规则给出 INCOMPLETE。

正常 final 形成草稿后，不为了清空 raw_tail 再启动普通整理；只处理适用的可选复核。复核可以接受、修订或要求一项有价值的继续工作，使用同一维护角色，不新增 Judge。

| 草稿情况 | 首版结束处理 |
| --- | --- |
| 显式合法 DELIVER | 接受原稿或修订正文，标记 REVIEWED |
| 复核关闭、额度已用或余额不足 | 仍适用的草稿按 UNREVIEWED 交付 |
| 复核阶段无显式路由且无内容变化 | 结束可选复核，仍适用原稿按 UNREVIEWED 交付；不把空对象解释为确认正确 |
| 复核提议因格式或内部引用问题被拒绝 | 保留原状态；原稿仍适用且原来源授权有效时，按可选复核不可用交付 UNREVIEWED |
| 明确继续／必要回读 | 在剩余资源内执行相应路径；需要业务动作时交还 Actor |
| 后续新反馈使草稿失效 | 旧稿不直接交付，由 Actor 修订或说明未完成 |
| 最后 Actor 仍请求新动作 | 不执行新动作，沿既有路径标记 INCOMPLETE |

复核额度按同一用户目标累计，修订草稿或回读不重置额度；一轮复核中的回读后续调用也全部计费。REVIEWED／UNREVIEWED 表示内部交付路径，INCOMPLETE 表示指定未完成结束路径，均不替代原生质量评价。

接受原稿使用 `{"dispatch":{"kind":"DELIVER"}}`；修订交付使用 `{"dispatch":{"kind":"DELIVER","delivery":"修订后的实际答复"}}`。二者都要求已有当前草稿；新方法不引入另一套交付外壳。

若用户或新业务反馈使尚未交付草稿失效，不能直接交旧草稿。没有可用上下文、未知用量、未知副作用或授权失效时沿既有停止合同处理，不以“总要 final”为由伪造当前结论。

### 9.2 可用性优先的异常处理

记忆提议无效时，保留旧视图和原始反馈，给 Actor 一条简短说明即可；不在正常输入中展开内部校验细节。合法输出无变化属于正常情况。

工具故障、模型调用故障、格式故障和方法语义失误分别记录。未知副作用不重放业务动作；未知用量不自动重试。只有真实发生且影响正常使用的错误才增加针对性兼容，不建设推测性的异常处理矩阵。

### 9.3 checkpoint 必须保存的新内容

方法载荷保存当前观察组与修订、工作区、原始页和来源范围、Actor 已接收页、观察覆盖、待处理请求、控制回读续接位置、当前草稿与有效性、复核已用次数、维护尝试身份、目标版本、交付状态和累计成本。绑定 method version、policy hashes、模型与容量、预算、来源及业务环境。

继续使用显式已知静止点保存和同一保留业务环境恢复。保存不强制先运行模型。恢复后不重复已执行业务动作、不重置预算、不将未观察页标成已整理；新目标清理旧 Frame 和旧 final，真实要求直接进入输入。

旧 RWC／OM checkpoint 继续由旧方法处理。新方法不通过伪造 method、环境 ID 或放宽合同实现跨方法迁移；首版没有自动旧状态转换。

### 9.4 公开保存恢复的最小接入

现有 `HiAgentTerminalSession.checkpoint_data()`／restore 分派识别现有 Host 类型和方法格式，需要新增新方法分支；不能只实现内存 snapshot 后就宣布公开恢复完成。

`tools/workspace_checkpoint.py` 的公开传输、压缩、CAS 和回执能力原则上复用。新方法放入自己的版本化状态载荷；除非源码表明传输不支持必要内容，否则不修改公开 namespace、Runtime 或产品 Schema。

继续遵守当前公开载荷 65,536 字节、解压 archive 8 MiB 和业务环境保留限制。超限不能默默丢掉未观察页、来源或账务。首版完成一次新方法的公开新进程保存／恢复检查即可；纯政策变化不反复重跑全部旧方法矩阵。

## 10. 创新政策：先完成功能，再判断 N1–N4 的贡献

### 10.1 首版完整能力与优先观察问题

N1–N4 的操作在首版都应能工作：依据范围修订、联想暂存与焦点分离、可逆再判断、未决项影响行动与交付。它们共用现有记录、Frame、读取与路由，不分别建立新模块。

首个真实使用可以优先观察下面这项联系，但它不限制其他功能开发：

**在已经需要维护的机会中，明确修订正在影响当前决定的旧判断及适用范围，并使 Frame 和实际选材相应改变，能够减少错误沿用和无价值重建；其成本足以低于带来的任务价值。**

这个假设包含形成与安排的组合，尚未证明。低频调度、句柄、稀疏更新和结束预留是共同工程能力，不直接命名为原创记忆机制。

### 10.2 普通与候选的差异

| 项目 | ADAPTIVE_MEMORY_SIMPLE | ADAPTIVE_MEMORY_CANDIDATE |
| --- | --- | --- |
| 观察与进展 | 正常总结已发生事项与当前工作 | 相同基础能力 |
| 发现记录错误 | 允许根据新事实纠错和回读 | 强调识别当前决定依赖的旧表述，修订其依据及适用范围 |
| 已有工作 | 正常保留有用信息 | 明确区分受影响部分与仍有效约束；基础假设失效时允许整体重建 |
| 替代线索与焦点 | 允许保存、选择、暂缓和读取其他条目 | 区分联想入口、当前投入和已有依据，避免未经确认线索持续占据主工作集 |
| 返回旧路线 | 允许回查历史并结合当前目标继续 | 必要条件失效时停止沿用；阻塞解除后重新判断，不自动恢复采用 |
| Frame | 正常给出下一步目的 | 只有实质影响当前决定的缺口才改变下一步或交付范围；足够时结束 |
| Actor 与调度 | 共同实现与政策 | 完全相同 |
| 输出能力与权限 | 观察、更新、选材、请求、回读均可用 | 完全相同 |

普通维护不能被要求只追加、禁止纠错、删除来源或没有下一步建议。候选也不强制建立卡片、每轮列风险、先测试再行动或必须回读。

### 10.3 N2／N3 的完整开发路径

N2 完成“保存线索 → 当前不选中 → 目录仍可找到 → 需要时进入工作集”的路径；线索允许尚未被证明有用，不能以未证实为由禁止记录，也不能保存后自动采信。

N3 完成“记录暂缓理由及来源 → 离开当前投入 → 相关变化出现 → 用当前可见材料或回读取回细节 → 修订旧判断 → 重新采用或继续暂缓”的路径。Actor 和 Controller 均可推动此过程，必须能把判断变化落实为 Frame、卡片状态或下一操作。

这些是首版功能验收项，不等待 N1／N4 获得正面结果才开发。语义收益仍按自然机会评价，不强迫每个任务使用全部路径。后续是否保留特殊 N2／N3 提示、是否简化返回流程，由真实使用和拆解决定。

### 10.4 每次政策改动保留五项说明

1. 实际观察及相应输入／输出位置。
2. 要修改的通用操作，和它借鉴的已有机制。
3. 预期哪一次选择、修改或交付会变化。
4. 哪种结果支持保留，哪种反例支持删除或收窄。
5. 新增维护、回读、提示长度及实现成本。

不注入任务 ID、评测答案、已知失败关键词或专用路由。组合修改按组合报告；没有拆解时不拆分归功。

### 13.3 一次方法过程检查

检查一个有明确维护机会的输入：哪些原文被整理、哪些记录改变、哪些旧正文退出自动展开、下一次 Actor 实际看见什么、来源如何回读、增加了哪些调用。可以用受控响应单独覆盖阈值触发，但不把人为压低阈值的轨迹当成自然效率结果。

## 14. 真实使用与有界开发实验

### 14.1 E1：首个完整新方法使用

首题继续使用 `multi-source-data-merger`，定位为已暴露开发题和使用回归。运行：独立 OM、ADAPTIVE_MEMORY_SIMPLE、ADAPTIVE_MEMORY_CANDIDATE。旧 RWC 结果留作历史，不默认再跑第四臂。

| 项目 | 建议固定设置 |
| --- | --- |
| 每方法生成上限 | 32 次，所有角色、失败调用合计 |
| 方法状态 | 各臂从相同原生初态和独立业务环境开始，不共享工作区 |
| 新方法参数 | §6 初值，共同 Actor，共同维护调度，max_delivery_reviews=1 |
| OM | 保留 om-sync-port-v0.1 独立算法及选定阈值，不强制 Observer／Reflector |
| Provider | 相同实际模型版本、窗口、解码参数和输出条件；优先复用可用历史 profile |
| 历史 profile 参考 | Qwen3.6-35B-A3B-FP8、65,536 窗口、temperature=0、top_p=1、seed=213、thinking=false；执行前记录实际可用性，不假定未变化 |
| 任务 | 复用既有原生适配、来源固定方式和 verifier；锁定任务 commit、文件与环境修改 |
| 顺序 | 首个新批次预先固定 OM → SIMPLE → CANDIDATE；单次顺序不提供随机化或稳定性证据 |
| 结果 | 当前交付、原生 reward／有效性、产物、全角色调用和 tokens、各阶段时间 |

不同方法可以选择不同上下文、维护次数和工具路径，这是算法差异。公平条件是相同起点、合法来源和业务能力、模型与明确资源上限；不要求输入字节完全相同。候选相对同结构普通政策的比较才固定相同调度和表示能力。

若三臂都很快完成且没有有价值的修订机会，报告可用性，不人为拉长任务直到出现阳性。若新方法较贵且无价值，保留 OM 在该工作点的决定。

### 14.2 E2：最多两对局部诊断

在完整功能基线和真实使用之后，围绕一个已观察的问题选择形成、消费、保留、选材或调度中的一项。每对 2 个分支，每分支最多 8 次全角色生成；最多两对。第二对必须有前一结果支持的新问题，不以“再试一次可能会好”作为理由。工程调试不需要等待语义实验，但不能借诊断预算不足留下首版必要功能未实现。

一次诊断保留真实输入、前缀账务、分支差异、生成选择和实际执行情况。没有可独立分叉的业务环境时，只做固定输入的下一动作诊断，不执行工具、不报原生分。

### 14.3 E3：一次有理由的完整配对

如果局部开发形成值得完整使用的新版本，最多安排一次 2 方法 × 32 次完整配对。根据尚未回答的问题，在运行前固定配对：

- 新方法对 OM：判断修改后的完整方法是否值得。
- 同版本普通对候选：判断政策增量。

只选其中一种，不默认两种都跑。更新了方法或政策，就记录新版本和输入冻结；历史 v0.1 的成绩不冒充改进版成绩。未形成候选时 E3 不启动。

### 14.4 不将问题全部归为记忆

把方法选择、实现错误、工具超时、容量不足、接口拒绝、依赖安装和 verifier 故障分别诊断。隐藏评测材料不进入求解输入。修复适配或容量问题后产生的是新执行条件，不把跨条件差异直接归于政策。

原生 verifier 的下载与准备时间独立记录；旧 RWC verifier 曾有长依赖准备，不应记成 Controller 的耗时。没有有效原生评分时保留未评分原因，不用内部 review 替代。

## 15. 最少贡献拆解：一次只解决最关键解释

| 问题 | 固定什么 | 改什么 | 能回答什么 |
| --- | --- | --- | --- |
| 形成是否有价值 | 同一真实输入、前一状态、合法来源、共同 Actor | 普通／候选维护生成记录 | 维护形成的组合是否影响下一步；若 Frame 也改变，明确是组合 |
| 纯记录形成 | 在上述基础上固定后续 Frame 与选材 | 记录正文／条目修订 | 记录内容的局部价值，不偷带选材变化 |
| 特殊消费是否必要 | 同一时点已生成的同一份记录、同一来源 | 普通消费／候选 Frame 或复核消费方式 | 是否可以保留形成规则而删除额外消费；只改变实际待测位置，不另造 Judge |
| 跨步继承是否必要 | 相同合法历史、目标与工具 | 继承记录／按需从历史重建 | 连续性是否节省重建或提高判断；重建成本计入 |
| 选材是否关键 | 同一记忆和读取能力 | Frame 选择／普通选择 | 工作集的增量；所有关键反证保留合法入口 |
| 调度是否关键 | 同一记录政策、Actor、来源和上限 | 两种明确维护安排 | 调度的质量与完整成本变化；不借历史 batch 轨迹归因 |

记录由真实模型形成，不由开发者提供理想答案。为了做形成拆解而固定 Frame，是明确的局部干预，不声称该输入代表完整方法自然运行。

“去继承”必须同时排除旧记录从其他消息、观察组或历史快照泄漏；原始历史仍然可读。局部续接不把旧动作的返回配给新生成的另一动作。没有等价环境不能伪造环境绑定绕过恢复检查。

共享前缀引用原账，新增生成全部计入；重新生成前缀也占预算。同一前缀的多个分支不是多个独立任务样本。动作变化只能说明选择变化，工具结果才能支持行为后果，净收益需要有效对照。

## 16. 迁移、恢复使用与后续研究

### 16.1 M4：两个预选问题家族

沿用上一轮在结果前已选定、尚未运行的 `git-multibranch` 和 `constraints-scheduling`。它们已经进入项目清单和开发讨论，属于开发迁移，不标为完全未暴露的正式确认题。

在新候选结果出现前登记这两个任务的来源和环境要求；执行时只核对必要可用性。核心政策、Actor 和一般维护规则冻结，允许任务路径和工具环境适配。任务不可运行时记录原因；需要替换则提前说明来源和准备依据，不能按候选胜负换题。

默认每题只运行“选定新方法＋OM”两个方法，每臂最多 48 次生成。政策问题优先由 E1/E2/E3 解决，不要求所有任务三臂齐跑。若研究问题改变，先记录配对变更，再运行；不把不同配对混作同一统计比较。

### 16.2 一次有明确目的的真实模型恢复

公开往返的工程检查不等于模型善用恢复记忆。若需要研究续接，从已计费真实轨迹选择一个保留环境，保存后新 Host 继续，观察“无变化时少重建”或“相关要求变化后修订旧判断”中的一个问题。

优先用 E2 的一对诊断位置替代重复诊断，不另加续接矩阵。若缺少真实前缀，生成前缀计入相应完整运行上限；不设置免费准备。加入新要求的单次原生任务标为派生续接工作负载，独立报告，不混入官方 benchmark 成绩。

### 16.3 M5／M6 的后续边界

需要跨会话任务时，先选择一个确有必要且本地可运行的来源子集，再制定有限执行范围。总设计提到的 MemoryArena／ClawMark 不是当前接入前提。

若某项操作出现可保留信号，再对 HiAgent、Mastra OM、MemR³、ACE 及与该操作最近的方法核对版本和实现差异；不以系统名称数量替代具体比较。本 Goal 不新增外部查新结论，外部机制沿用总设计的阅读记录。

正式创新确认需要独立来源、冻结政策、足够反例和波动依据；两项开发迁移不够。GEPA 式外层优化、AgentFold 式训练、异步维护、跨 Host 与长期治理仅保留演进位置，不成为首版开发任务。

## 17. 资源建议、成本记录与停止规则

### 17.1 新建议预算与旧账彻底分开

| 项目 | 上限计算 | 建议生成上限 | 启动条件 |
| --- | --- | ---: | --- |
| E1 首次完整使用 | 1 任务 × 3 方法 × 32 | 96 | 新方法路径可正常运行 |
| E2 局部诊断 | 最多 2 对 × 2 分支 × 8 | 32 | 真实观察提出明确可区分问题；可替换为一次有目的续接 |
| E3 改进版完整配对 | 1 配对 × 2 方法 × 32 | 64 | 形成值得完整使用的修改，并预先选定比较问题 |
| 当前开发主包 | 96 + 32 + 64 | **最多 192** | 默认先 E1；后两项依发现选择 |
| 条件性 M4 迁移 | 2 任务 × 2 方法 × 48 | **另计最多 192** | 有明确需要迁移的同一版本，单独登记执行范围 |

本文件的新分配为 **0**，上述均为建议上限。384 是两部分全部启动时的算术包络，不是一次启动计划、默认额度或必须消耗的数量。旧轮未用额度不转入这里。

每次实际执行前将已确定的方法、任务、模型、每臂上限与原始证据位置写入 manifest。已有明确执行授权覆盖的工作直接按范围推进；不为每个普通开发切片增加确认环节。本文本身仅交付方案，不发起任何模型请求。

### 17.2 统一成本账

```text
总生成 = Actor + maintenance(OBSERVE / COMPACT / REVISE / REVIEW)
       + 该方法实际存在的 observer / reflector / summary / review
       + 其他真实生成与失败调用
```

每次尝试记录 role／mode、输入输出 tokens、Provider usage、失败与未知项。Observer、摘要、维护和局部诊断均不是免费步骤；同一模型、同一 Host 也不意味着零额外计算。

分别记录任务准备、模型等待、工具执行、verifier、工程测试和人工分析可识别的时间。任务与工具期限沿用原生合同；不能为了候选的内部控制链单独放宽业务资源条件。

无费率不推算金额，无缓存计费记录不推算缓存节省。稳定前缀、少发字符、较少调用都只是机制现象，效率要在任务完成度和完整成本上判断。未知用量沿现有停止／核对合同，不当作零结算。

### 17.3 有界收口

局部输出拒绝先核对明确合同；可通用修复就修复并登记版本。语义负结果保留，不连续改写提示直到偶然获胜。两对诊断后没有新的可反驳解释，或没有形成可推广修订，关闭余量和未启动位置。

预算到限给出当前交付与准确未完成范围；不通过增加隐形复核或重启会话重置额度。基础设施故障保留成本和失败状态，不能丢弃后只报成功轨迹。

## 18. 结果最小记录与决策规则

### 18.1 每次完整运行只抓住三项主结果

| 主结果 | 记录内容 |
| --- | --- |
| 任务质量 | 有效原生 reward、产物、约束、失败或未评分原因 |
| 实际行为 | 当前交付与结束路径；一段有意义的反馈→记忆→输入→动作→结果链，或明确没有该机会 |
| 完整成本 | 全角色生成与 tokens、工具与失败、准备／verifier 时间、未知项 |

辅助日志沿已有 emit／manifest 扩展：维护原因与模式、输入页及条目版本、覆盖前后差异、补丁接收或拒绝、投影中的实际引用、Actor 选择、真实结果。仅登记用于回答问题的字段，不建设卡片数、回读次数、措辞质量的独立排行榜。

机会由任务和已发生事实定义；使用由实际输入与行为定义；收益由对照定义。记录出现“依据范围”、多一次 final 或少一次 Controller 都不自动构成创新证据。

### 18.2 保留、删减与停止

| 结果 | 决定 |
| --- | --- |
| 新普通与候选都更容易交付 | 保留共同运行改进；不归功于特殊政策 |
| 新组合不如 OM，且无可解释局部价值 | 在该工作点保留 OM，关闭无目的追加 |
| 候选优于同结构普通，但完整方法仍更差／更贵 | 保留局部规则假设，删减方法负担；不推荐完整候选 |
| 同质量下完整成本更低 | 保留效率假设，再看迁移与稳定性 |
| 纠错后错误旧正文仍自动进入后续输入 | 属于实现或投影欠项，修复后重新标记版本，不称语义政策无效 |
| 修订输入确实改变动作，但任务未改善 | 保留行为事实，检查代价与替代解释，不升级为净收益 |
| 候选记录配共同 Actor 已足够 | 在已完成功能基线上简化消费配置或删除无价值的特殊政策，保留形成规则 |
| 去继承仍同样好 | 不主张跨步连续性收益；可能是一般求解政策有效 |
| 同一规则在不同任务失败 | 记录适用边界；逐题修改的结果归为开发，不能混报迁移 |
| 没有新解释且局部无差异 | 暂停该版本，不重复采样寻找偶然优势 |
