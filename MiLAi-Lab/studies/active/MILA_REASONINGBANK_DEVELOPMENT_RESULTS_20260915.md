## 保留的开发失败与修正

1. v0.1 将小写标题判为错误；v0.2 仍因模型使用非标准标题标签而拒绝经验。
   两次 native DB 10 均为 correct，但银行未提交，原始输出和全部成本保留。
2. v0.3 按逻辑 Memory Item 拆分并保留其原文，不把正文标题名当成内容有效性的判据。
   这更接近官方原始 Markdown 存储；仍拒绝空条目、无条目标识和超出预定条目容量。
   采用独立的后续 DEV 两题验证，未对失败记录补造成功银行。
3. 旅行首次 chat/tools 请求因现有服务未启用 auto tool parser 返回 HTTP 400。
   其 reservation 保持未结算，6244 token 上界单列；未在同一 worker 自动重发。
   新配置复用部署模型自身 `/tokenize` 渲染的工具模板，将相同 token IDs 发到
   `/v1/completions`，在本地按模板 XML 解析函数名及参数。原生工具及参数 schema 不变。

## v0.4 的单次有界调整（已完成并选定）

v0.3 候选在旅行 58 人中仅留下 13 个终止会话；多组进行上百次合法回读。
接入检查发现：调用方先 `start()` 做采用，再发布既有计划；Actor 当前视图只展示来源标签。
v0.4 将已授权的基础／前序计划在采用前发布，并将其原文展示给采用器与 Actor。
保留原来源读取和反馈触发修订；政策文本不变，DB／OS 无任务事实时不增加新的输入字段。
这项改变属于事实可见性的工程／表示组合，不能提前归为修订收益。

只对同一预选 8 个旅行 VALID 组运行候选 v0.4，4 个 worker，每组 4M tokens／512 次生成／1800 秒。
HTTP 等待上限从 180 秒改为 600 秒；这是额外的传输变化，不能把版本差异解释为事实展示的纯因果效应。
正式旅行比较将对所有方法采用同一 600 秒传输设置。新阶段预分配 32M tokens／4,096 次生成，
不是实耗。版本选定前不读取 TEST 成绩，不再增加提示变体。

窄改动后 16 项相关测试通过，boundary、全仓 ruff、mypy 和构建通过。
此前冻结 v0.3 完整回归为 4,643 passed／1 skipped（可选 Host SDK wheel），耗时 4,177.63 秒；
完整回归未为这次局部改动重复运行。
