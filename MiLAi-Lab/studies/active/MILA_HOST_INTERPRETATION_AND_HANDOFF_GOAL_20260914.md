# Goal：解释提示复测与交付文本的实际贡献

**当前终态：本轮有界开发与实验已完成。** [结果报告](MILA_HOST_INTERPRETATION_AND_HANDOFF_RESULTS_20260914.md)：两波12次生成、7个合法final和1个保留的格式拒绝，无未知用量；全回归4439 PASS/1可选SKIP。保留简单方案，没有稳定提示或交付净收益结论。下文是执行时合同，不是尚待补跑的矩阵；发送前原文已随run/code快照保存。剩余36次上限不使用，跨来源/持久化/确认等条件性工作未启动。

本轮执行依据：用户“根据实验结论，优化 goal，完成实验任务”。前一 [v1.1 结果](MILA_HOST_CONTINUATION_RESULTS_20260914.md)及其已关闭 Goal 保留，不追加旧包、不继承剩余额度。本文件是新有界实验，不重开 Gate A—E，不开发 State 机制。

## 1. 为什么改变目标

v1.1 在完整材料可见时，普通 N/R/S 仍遗漏关键耗时定位；EXPLAIN 在唯一一对中改善了定位，但存在其他错误，而且相同 R 请求产生过不同输出。10 次生成均无 work_update。因而当前最有信息量的两个问题是：

1. 原样通用解释提示在反序复测中是否继续改善形成和最终判断，还是只是局部输出变异？
2. 从同一个形成终点分叉，原始证据和其他历史保留，只去掉阶段交付文字，会怎样改变后续判断？

第二项第一次直接干预交付信息通道，不以“写入了”“文本不同”代替贡献证据。它不是产品默认历史裁剪，也不是假装模型窗口不足。首批不要求自主写工作区，不声称已测持久 Memory 或短稿独立机制。

## 2. 不动的部分

- 原样复用 `task-a-v2` 的原材料与定义；A 仍是一个已经暴露的来源。
- 固定现有 `continuation-interpretation.json` 的 R 与 EXPLAIN，不改词、不加入案例答案、未来观察或更多字段。
- 同一个已授权 loopback vLLM HTTP、真实 tokenizer、解码参数及普通 NOTE 消费政策；不操作 GPU、不修改服务、不增加模型 Judge/Reviewer。
- 按实时服务容量配置输入与 4096 输出预留；不使用固定 8k/16k 输入限、有限 K 或 512 交付硬门。只读源与算术工具保持可用；不生成执行任意代码。
- 用户目标、权限、新观察、全部已发布证据与普通历史维持共同规则。Host 负责解释，代码只复制、标注、取回和记录。
- 未启用的工作区不强行启用；若实际写入，两个分叉均保留同一份，单独报告替代信息通道，不能称为完整 memory-off。
- 历史失败、未知费用和回归异常不改写；不碰 Product 默认、Canonical、公开部署或 Schema。

## 3. 固定的小比较

每次形成只实际生成一次，再复制同一形成终点到两个彼此隔离的普通消费者：

| 消费条件 | 实际差异 |
| --- | --- |
| FULL | 原样保留 stage_answer，在普通 assistant 历史位置一次呈现 |
| NO_HANDOFF | 仅将该 stage_answer 的 text 换成明确的实验留空标记；公开历史 H 读取返回同样的留空版本，不能绕路取回原稿 |

双方所有原始证据、其他动作与回执、源目录、阶段标志、系统提示、任务与预算相同；不删除交付所在交换中的源正文或阶段通知。标记说明没有交付文字，不提供答案或“请忽略旧结论”等政策。完整原稿仍在 evaluator/raw 日志，不进入 NO_HANDOFF。保留一份工作区不等于去除其语义内容，此处只估计 stage_answer 文本通道的影响。

发送前固定次序，不按输出挑分叉或重复：

| 波次 | 形成顺序 | 第一形成的消费顺序 | 第二形成的消费顺序 |
| --- | --- | --- | --- |
| W1 | R → EXPLAIN | FULL → NO_HANDOFF | NO_HANDOFF → FULL |
| W2 | EXPLAIN → R | FULL → NO_HANDOFF | NO_HANDOFF → FULL |

共 4 个形成终点、8 个消费分叉；若各段直接交付，实际 12 次生成。每段允许最多 4 次正常决策，因此新总上限 48 次，所有失败占额；没有额外调试生成配额。重复不是新 lineage，也不是独立确认。FULL 与 NO_HANDOFF 是配对条件，不是两个独立任务。

不要求所有分支正确才算实验完成。没有合法交付时，保留该形成失败与原因，不造理想稿、不补根；对应消融标为无可移除交付/未运行，而不是成功分母。已知局部失败且账目闭合时允许继续下一预定独立分支；未知用量、污染或接口不可信时停止受影响批。

## 4. 先写清判读，不用模型打分

在新输出出现前冻结下列开发审阅项，依据现有原始数据和定义逐项解释，不按特定关键词自动打分：

| 项目 | 所需判断 |
| --- | --- |
| 旧批具体定位 | 是否明确识别 R12/R22 的 transaction exit 为主要已测分量（约164.426/309.995ms），不只泛称数据库/hold |
| 嵌套与残差 | 不把 hold-enter-exit 自动命名为事务外、连接释放或其它未测活动；嵌套量不重复相加 |
| 量级一致性 | 不把旧批约166/312ms application 说成“很快/不是长尾”，不混用普通请求与慢请求的数值 |
| 新批区间 | 对 R32 约42.394ms 前区间按 MCP client start→handler start 理解；不移入 handler 内或当作已证实调度/网络原因 |
| 历史适用性 | 不用 B3 的另一测量结果抹去 B1/B2 原来有效的定位；允许新旧批原因不同 |
| GC 范围 | B1 未观测不当零；B2/B3 客户端窗口结果不推广到全部进程或所有批次 |
| 工作推进 | 给出至少一个可推进且解释会区分什么的检查；合理假设不判作无依据采信，但假设不能当已证明原因 |

形成与最终分别审阅；不把某一正确数字当整任务 PASS。项目取值为 supported / omitted / incorrect / not_applicable，给原文依据与说明，不压成创新总分。可报告全项达标数，但未知、遗漏和不可裁定必须保留。

`FULL vs NO_HANDOFF` 只隔离保留该文本的整体贡献，包含长度、重复强调与表述的影响；不直接等同认知惯性。所有原文仍可读，所以不证明短稿不可替代。只有相关内容在形成时正确，才进入正确形成后的消费子集；当次消费者失败不能反过来被排除。若正文正确而稿误读，记录错误传播方向，不把初始误读叫长期固着。

## 5. 最小实现和成本

只加一个邻近分叉 runner 和对应测试，复用既有 Host、Task、Provider、政策、日志与真实容量计数；不修改旧入口默认行为，不引入新的 admission/cache/评分框架。

- HTTP 单请求在途，单请求60秒，单段最多4次；每个形成+单消费路径墙钟900秒，整包3600秒。共享形成耗时计入每条路径的预算，不用分叉重置它；实际账单只计一次。
- 真实 tokenizer、身份检查与生成分别记录；所有 input/output、失败和可选记录成本计入。未知用量保留 reservation 并停发，无自动重试。
- 报告实际总账；策略路径成本另列 `本次形成 + 对应消费`。不能把共享形成重复相加到实际账单，也不能宣称一次实验已测完整产品生命周期成本。
- 发送前检查模型、实际容量、源 hash 与政策 hash。实际 wire 保存到 Git 外，验证原始正文全在场、交付一次或受控留空、同一形成两路没有互相消费结果。
- 邻近测试先覆盖形成分叉、无交付、历史读取不能绕回、原材料保护、独立副作用和未知用量停发。随后按仓库要求运行 boundary、pytest、ruff、mypy、build；全回归沿用现有分片/关闭可选诊断定时器方案，不为此加新优化。

## 6. 保持灵活但不追逐阳性

允许最多一次有证据的局部接线修正，必须在首次真实生成之前，或者在保留失败后另立运行版本且仍处总额内。不得修改认知提示、任务答案、审阅标准来补救当批输出。后续政策改动是新开发问题，不在这轮悄悄混跑。

若运行暴露另一具体问题，先在结果中说明；不自动追加第三轮、不用完余额、不加第二模型。没有更清楚的可检验差异，就暂停这个版本。局部打平限制当前主张，不宣布整个 Memory 方向无效。
