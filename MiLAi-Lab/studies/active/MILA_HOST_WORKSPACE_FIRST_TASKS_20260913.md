# 工作区策略首批任务：一份真实证据包、一项可执行工程任务

## 1. 采纳范围与实际进度

首批起步安排为两个工作过程，NOTE／REVIEW／REGULATED 各一条轨迹，共六条。统计单位仍是两个 root，不是六个独立样本。一个包先可用就先调试，不等两包齐备；不要求每次修改跑满六条，效果比较仍需同任务公平对照。首轮选择共同材料/共同呈现规则，工作区从空开始，由各臂自己形成；不固定五轮，不默认模型 Judge，不增加自然 Note 写入资格门或数据库持久化前提。

这是[工作区策略设计](MILA_HOST_WORKSPACE_POLICY_DESIGN_v0.1_20260913.md)的任务附件，不是新总 Goal 或新准入平台。受控材料模式是本批选择，不撤销真实 `MANAGED_WORKSET` 的实现，也不把共同材料胜出变成未来组合探索的前提。

此前只读选样已定位 A 的原始日志及逐请求记录，读取部分数值，并核对 B 的官方任务、环境与测试源码。本次局部修订配合插件原型开发，不新增模型运行。任务包、隔离环境、逐项参考评分仍未建成，不能称“两题已合格/可直接运行”。

| 候选 root | 具体来源 | 主问题 | 不能承载的结论 |
| --- | --- | --- | --- |
| A：读取长尾诊断续接 | MiLAi 2026-09-06 事务计时、客户端 GC、MCP 边界三批原始观测 | 能否保留结论范围，并用新证据选择下一项检查 | 真实修复收益、冷持久化、完整根因已经查明 |
| B：异步任务执行器的取消兼容 | Terminal-Bench 2 的 `cancel-async-tasks` | 能否在实现、测试与修订中保留并发及清理约束 | 原任务没有外生 A→B→A，不能据此验证条件重激活 |

## 2. A：真实长尾证据回放

### 2.1 为什么选它

同一排障过程里存在至少两类不同位置的长尾。旧结论在其观测范围内可以成立，新一批观测却不能全部照搬。它能检验“继续利用已有定位，但不把局部解释推广成全局原因”，不需要制造遥远目标或再部署服务。

任务目标拟写为：依据分批到达的已记录测量，给出当前可支持的定位、尚不能确定的原因，以及一项有区分价值的下一步检查；不得以关闭审计、降低持久化保证或更改负载上限替代诊断。

### 2.2 已定位的原始材料

以下根目录在本地存在，原始材料保持原位；不把整个运行目录挂载给模型。

- [事务测量根](../../artifacts/v02-e2e-generality/p1-transaction-load-20260906a)：baseline 的 `arrival-events.json` 为 300 条，`mcp-events.json` 为 315 条（含非测量调用），`timing-correlated.json` 为 300 条。
- [客户端 GC 观测根](../../artifacts/v02-e2e-generality/p1-client-gc-20260906a)：baseline 有 99 条关联测量，以及带起止时刻、事件和丢失计数的 `client-gc.json`。
- [MCP 边界测量根](../../artifacts/v02-e2e-generality/p1-mcp-boundary-20260906a)：baseline 有 300 条关联测量、MCP 事件及 GC 记录。

`arrival-events.json`、`mcp-events.json` 和 GC 文件是保留的事件材料；`timing-correlated.json` 是已有程序生成的关联结果，不冒充未经处理的日志。任务包需保留选中行与原事件关联，不能只有事后结论报告。

本轮读取到的样例：事务批次一条调用为 173.056 ms，连接取得 0.035 ms，事务退出 164.426 ms；GC 批次一条调用为 319.975 ms，事务退出 309.995 ms；后续边界批次一条调用为 51.368 ms，handler 内仅 7.012 ms。这些数值说明有可区分的观测区间，不证明磁盘、网络或某个调度器就是根因，也不代表这几批具有可比较的性能处理。

[事务报告](MILA_V02_TRANSACTION_TIMING_20260906.md)、[GC 报告](MILA_V02_CLIENT_GC_DIAGNOSTIC_20260906.md)、[边界报告](MILA_V02_MCP_BOUNDARY_TIMING_20260906.md)只用于离线制定核对项；它们的定位结论不进入模型初始输入。

### 2.3 信息释放与工具返回

| 工作段 | 共同外生输入 | 模型的选择空间 |
| --- | --- | --- |
| 开始 | 症状、用户约束、计时字段含义、第一批选定原记录 | 比较区间、提出解释、读取同批已发布原行 |
| 续接 | 后续客户端 GC 记录及对应请求 | 检查前一解释仍能解释什么，是否需改变调查方向 |
| 新观测 | 后续 MCP 边界记录、版本与测量条件 | 区分不同长尾位置，不追认旧批次未测量的分段 |
| 交付 | 已发布材料均可查 | 提交有范围的诊断和待验证下一步，不强制唯一检查顺序 |

打包时可按每批最长若干请求与时间相邻正常请求做确定性选取，记录具体原行与理由；不只保留支持某个预设机制的例子。这是有意选取的诊断样本，不用于估计自然长尾率或 SLO。

释放规则在该次受影响任务比较前写清，例如每个证据段允许相同数量的决策机会再发布下一批；不能根据某臂是否已经猜对来提前/延后。不为所有任务共用一个“五轮模板”。各臂事先知道还会补充历史测量，但不知道内容；阶段答复只结束本段，不永久结束整项回放。最终综合交付与阶段答复分开，由任务事件安排决定，不根据工作记录关键词结束。

允许的读取只返回已发布文件中的真实内容，允许本地计算。若模型提出当前包中没有的现场检查，记录为建议并明确“没有该测量”；不能播放专家历史上另一次检查的结果，伪装成执行了模型的动作。后续批次始终标为外部提供的历史观测。

模型可见副本只含需要的字段和中性引用；剔除凭据、服务控制入口、实验臂答案和结论性文件名。标识重映射保持关联一致，数值、测量版本与覆盖缺口不改写。禁止挂载 `runtime.env`、secret 目录、整套旧实验报告或其他臂输出。

### 2.4 评价

主结果是“诊断结论是否被所给证据支持”，不是是否猜中一个未被测明的根因。具体审阅项包括：不把事务退出时间直接等同 fsync；不把 handler 外差值直接等同网络；缺少 GC 观测不填零；不把不同请求或不同批次的定位互相覆盖；下一检查能缩小已指出的不确定性。

同时评价正向进展：是否取得尽可能具体且有范围的判断，指出最影响下一步的不确定性，并说明建议的检查为什么能推进工作。始终回答“资料不足”不自动算好。明确标为可能性、待检验的解释允许出现；只有把它当作已确认依据或据此错误行动，才计无依据采信。不要求复现专家检查顺序。

区间算术可确定性核对；诊断与检查价值允许多种正确表述，由开发者结合原记录审阅并保存证据指向。没有独立人类裁定时，明确为执行者离线审阅，不称独立 human gold。未决分歧保留，不用一个自动关键词匹配器强给 PASS。

## 3. B：`cancel-async-tasks` 可执行开发候选

### 3.1 已核对到什么

官方任务要求在 `/app/run.py` 实现异步任务执行函数，限制并发，并在键盘中断时执行任务清理。[任务说明](https://raw.githubusercontent.com/harbor-framework/terminal-bench-2/main/cancel-async-tasks/instruction.md)。

它的环境定义使用 Python 3.13，配置不要求 GPU 或 MCP 服务；官方难度为 hard。因此“单文件、依赖小”不代表当前模型容易完成。[任务配置](https://raw.githubusercontent.com/harbor-framework/terminal-bench-2/main/cancel-async-tasks/task.toml)、[Dockerfile](https://raw.githubusercontent.com/harbor-framework/terminal-bench-2/main/cancel-async-tasks/environment/Dockerfile)。

官方检查包含并发执行、上限约束及几种任务数/上限关系下的中断清理。测试入口还会安装工具和复制辅助脚本，因此不能只凭一个 Dockerfile 声称环境已经齐备或完全离线。[测试入口](https://raw.githubusercontent.com/harbor-framework/terminal-bench-2/main/cancel-async-tasks/tests/test.sh)、[测试源码](https://raw.githubusercontent.com/harbor-framework/terminal-bench-2/main/cancel-async-tasks/tests/test_outputs.py)。

本轮读取的是官方 main 上的文件，尚未绑定固定 commit、镜像 digest 或本地任务包，也没有拉取镜像、运行 checker。正式打包只固定这个任务及其必要依赖，不拉起整个 Terminal-Bench。

### 3.2 任务过程与历史价值

三臂从相同原任务、相同代码初态和空工作区开始，独立实现与运行自己的测试。初期正常结束的测试结果可能支持“这部分行为成立”，却不能推出中断/排队边界全部正确。后续真实测试反馈应促使修改实现，同时保留仍有效的并发约束和已验证行为。

这是一项实现与兼容维护任务，不是已经存在的“旧方法 X 失效又恢复”的时间线。历史依赖来自各臂自身先前实现、测试、错误和判断。若所有臂一次就完成，照实记录，不强制加入假故障或规定必须先用某个错误方案。

每次代码修改都在该臂独立的临时任务工作区执行；共同初态、Python 版本、工具、限额和环境规律一致。不同代码必须获得它实际运行的 stdout/stderr/退出状态，不能用统一预录测试结果替代。

模型可执行开发测试；用于正式评价的隐藏脚本与官方解答不预先挂载给它。允许不同实现，只要真实调用任务、遵守并发、正确清理且满足当前合同。不能仅凭输出目标字符串就认定完成；必要时检查代码和实际回调副作用，不新增评分平台。

优先尝试原任务的小范围入口；集成过重或难度不适时可以及时拆小或替换，标明派生内容与理由，不强制先跑通官方全套。若需要后继需求/依赖变化，也另标派生开发变体并保留原任务，不混报官方成绩。未经额外变化与行为机会，本 root 不计算条件重激活率或跨会话 Recovery。

### 3.3 可用性优先的有限准备

只确认所选任务的源码/依赖可取得、能启动一次 CPU 测试、checker 会区分明显正确与错误的行为。原测试不可靠或环境成本超出小任务范围时，保留事实并另选具体任务；不要修建整个 benchmark 运行框架。替换必须发生在相关新比较前并留存旧 root，不只保留候选赢的题。

不修改共享 MiLAi Product 工作树、不接公网服务、不操作 GPU。沿用现有安全任务环境，实验模型将来仍只经授权的 HTTP 路径使用。

### 3.4 本地替代候选为何未直接采用

已检查本地文本保真修复报告、当前 domain 文件与邻近测试。但旧运行 `installed-artifact.json` 指向的仍是当前源码路径，该路径已经包含修复；已检查的文件提交历史没有提供可用旧版本。这不能证明旧源码在所有位置都不存在，但不足以建立原始修复初态。

因此该案例暂保留为备选，不从最终修复反向制造一个“历史原版”并称为真实任务。若后续明确构造复现，只能标为真实缺陷派生，不将当前已修好的 Product 当待修复目标。

## 4. 六条轨迹的共同约定

| 项目 | 首批设置 |
| --- | --- |
| 工作区 | 每臂为空开始，容量共同，text 的 512-token 开发初值可用；允许不写 |
| 政策 | NOTE、同调用 REVIEW、REGULATED；都能记条件、改判断、正常读源与验证 |
| 材料模式 | 首批 `COMMON_CONTEXT`；可依具体问题直接转 managed 组合探索，不以共同材料胜出为门 |
| A 的共同性 | 外生证据按共同顺序释放；实际读取/计算按各臂动作返回 |
| B 的共同性 | 相同初态、环境规律、来源/呈现能力；不是声称不同代码获得相同实际输入 |
| 轮次 | 每 root 先设明确共同开发上界，实际步数由轨迹观察；A 的阶段答复不取消后续外生材料 |
| 用量 | 全部正常调用、状态维护、读源、测试、失败及调试另次尝试入账；此文件不授权调用 |
| 判断 | 任务 A/B 独立报告，不把诊断审阅分与代码测试分混成一个总分 |

`COMMON_CONTEXT` 在本批表示禁用策略特有的材料裁剪/展开、使用共同提供规则。只有具体请求材料确实相同，才标为同输入；各臂自产工作记录和交互结果允许不同。对因动作不同而产生的轨迹差异，应分析过程，不能造假结果以维持字节相等。

机械检查只确认入口、结果来源和基本运行成本，不能预测模型需要多少步骤。模型轨迹先使用明确的共同开发上界，实际步数从运行获得；后续调整保留版本。不把 6 条轨迹简写成 6 次生成。无累计 raw-token 硬上限不等于无限调用，仍有逐任务明确停止条件，保留未知用量。不得为可选 workspace 格式问题重放已成功动作。

## 5. 轻量任务包与完成标准

每个包只分三部分：模型可见任务/合法材料、正常执行或回放入口、模型不可见的评价依据。来源路径、版本、许可/使用范围、提取规则与暴露状态写一份短 manifest 即可，不另建数据平台。

完成打包时应能回答：初始输入是什么；每次新材料为何出现；这个动作得到的结果从哪来；最后依据什么判好坏。任一问题说不清，就补对应文件，不扩成另一个全链准入 Goal。

主要结果分三列：任务质量，关键行为，全部成本。记录但不奖励 State 长度/更新次数/分支数量。重新运行测试可能是必要验证，只有在源码、条件和待验证问题均无变化且没有新增价值时，才将重复工作列为可能浪费。

打平先区分任务没有需要、处理未启用、或有机会但无净价值，结合具体新假设决定修改、删减或暂停；不得不断换题只保留阳性。形成的记录有用但普通 review 消费即可打平，就分别解释形成与消费的价值。只在 managed 模式改善时报告选材或组合收益。所有臂普遍失败时先检查难度与故障层，不认定 Memory 失效，也不要求 baseline 全对才允许探索。

开发可以修改提示、释放顺序或换例，但每次保存版本与理由；不能回填旧结果。一个任务没有信号不阻断整个研究，首批也不要求每个任务同时具备中断、世界变化、恢复和联想。确认阶段再按原问题来源选择未参与调试的案例，不按行或改名变体制造独立样本。
