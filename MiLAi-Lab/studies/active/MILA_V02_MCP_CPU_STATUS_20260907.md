# MCP运行时CPU与状态：有限并发实测

用户要求“测试一下mcp运行时cpu压力和状态”。SIM02结束后独立执行无模型测试，
复用此前范围检索的1000条完整合成来源，未重新导入或修改SIM02产物。
沿用Product pin `56a0dab6df6dedd4540d3cc5a59fc1f9013505275e91cb7050b3d8eb56482e0c`。

结论：本轮MCP进程未接近单逻辑核满载；主要CPU消耗在API与数据库。
8并发出现数据库CPU配额节流，同时P95升至873.883ms；不能仅凭相关性确定延迟原因。
测试前后API/MCP健康检查均200，无异常工具失败、来源越界、OOM或采样错误。

CPU 100%表示一个逻辑CPU；相邻同阶段采样差分求时间加权均值，排除跨阶段区间。
峰值是采样窗口值，不是瞬时值。PG采用cgroup总CPU/RAM，其他组件为进程CPU/RSS，
不可把两种内存口径直接相加。PG采样窗口可能跨配额周期，短时峰值不代表修改了2CPU配额。
本轮PG2CPU/1GiB保持不变；c8采样覆盖的50个配额周期有5个被节流，
`throttled_usec`差分1,965,576，不能直接当作单个请求额外等待时间。
PG CPU PSI some约4.18%，内存事件oom/oom_kill/max/high前后均0。

API、MCP、worker和客户端亲和性均CPU0/1；两者是同一物理核的SMT线程，
因此不能解释为两颗独立物理核。客户端包含检查和采样开销，也与服务共享这些逻辑CPU；
本次没有通过干预实验分离其影响。数据库不绑定该亲和性，独立受容器CPU配额约束。
