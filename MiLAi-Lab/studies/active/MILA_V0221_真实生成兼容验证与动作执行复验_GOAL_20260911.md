## 2. 范围与解决方案

### 2.1 只改变 Lab 的前瞻运行接线

沿用已经实现的 `UNIQUE_ITEMS_RUNTIME_V1`：

```text
完整公共 Schema + 原完整资料 + 已知动作意图
                         ↓
显式 wire 变换与实际请求冻结 → 容量 / 授权 / 用量门
                         ↓
真实 vLLM 生成 → 原始响应与用量先记录
                         ↓
严格 JSON + 完整公共 Schema 校验
                         ↓
W2：只验证，不派发业务
W3：原 Session / 执行器复验 → 隔离 World 效果 → 公开回读
```

生成 grammar 只移出已审阅位置的 `uniqueItems`；完整公共 Schema 仍呈现给模型并执行验收。
wire 接受集合较宽，不声称 grammar 等价、生成分布或成本不变。
不自动去重、排序、补字段、改值、缩小合法目标集；不移除业务约束以获得通过。
未审阅的 Schema 运算符仍在发送前拒绝，不在本批扩展兼容编译器。

本轮可实施的新工作限于：授权边界的版本化接线、批级停发、真实完整请求构造/容量核验、
兼容探针和已知意图复验 runner、证据与验收报告。它们尚不是已完成功能。
复用现有 `WireProvider`、`WireSchemaAdmission`、`Session` 和 ActionAdapter，不另造业务执行器。

## 3. W0：历史未知账与真实请求授权

### 3.1 两条允许进入真实诊断的路径

**路径 A：取得可信历史回执。** 只接受能绑定原请求 ID/时间/载荷的 Provider 或服务端记录；
通过独立、追加式 reconciliation 制品说明结算依据，不修改冻结原账本/HTTP 证据。
CPU 校验、没有业务 dispatch、服务健康或新请求成功，都不是旧生成零消耗的证明。

**路径 B：用户明确授权保留历史未知账，开展本 Goal 的独立、有界新诊断。**
授权只改变特定新批能否发送，不消除旧未知、不将旧预约释放为零、不授权重试旧 HTTP 500。
必须记录用户授权依据以及被接受的历史未知请求清单；不能由 Agent 自签“允许继续”。

本次“生成后续 Goal 文档”只授权文档。尚未选择/满足上述路径，当前不能发送。
若后续授权仅覆盖 W2，W2 PASS 后只交付 W3 准入结论，不启动 W3。
只有明确覆盖 W2 及条件 W3 的执行授权，才允许在所有门通过后进入 W3。

### 3.2 授权制品与实现要求

新批 `authorization.json` 至少固定：

- Goal/版本、批 ID、授权来源及时间、允许阶段、到期时刻、请求上限和并发上限；
- endpoint/model、Schema/代码/安装后端指纹、历史账本路径/hash；
- 精确历史未知 request ID、原预约、处置方式；明确 `historical_usage_settled=false`（路径 B）；
- 新未知即停发、禁止自动重试、禁止扩任务和共享服务变更。

历史清单必须同时包含旧兼容批与失败 V2 批，不能仅挂载一个空新账本。
原账位于 `/cra/memory/mx_memory/evidence/v0220/` 下的
`provider-compat-v1/provider-ledger.jsonl` 与
`v2-candidate1-v1/episodes/v2c1-01/provider-ledger.jsonl`；实际 request ID/hash 由只读核验填入。

**当前 Provider 没有上述豁免功能。** 新批策略入口须分别验证追加式可信结算（路径 A）或
明确授权的历史承接（路径 B）；仅有 companion 文件而当前读取器未校验它，也不能视为已解锁。
如采用路径 B，先实现/审阅一个明确版本的新批策略入口；
不能修改旧 `new_generation_allowed`、伪造 SETTLED 或删除历史输入。
仅精确匹配且已授权的历史未知可被承接；未知清单变化、账本损坏、旧边界违规、授权过期或范围不匹配均拒绝。
任何本批新未知仍阻止全部后续发送。不得把新未知追加到白名单后自行继续。

零模型正负控必须覆盖：未授权、范围外、hash 漂移、伪造回执、新未知、进程重启、重复启动、
新目录绕过、W2 到 W3 越权，以及已有授权被用于另一批。默认行为继续 fail-closed。

`G_AUTH`：可信结算与执行授权，或精确历史例外与执行授权，均有可验证记录。
W0 未满足时可完成离线准备，但状态为 `AUTHORIZATION_PENDING`，不是 GPU/模型失败。

### 4.3 批级停发与回归

用单写者批协调器统一 W2/W3 的授权、次数、截止时间与全部 episode 账本。
每个冷进程不能只检查自己的新账；上个 episode 新出现的未知/违规必须阻止下一进程启动。
冻结请求后不可在 preflight 中变更；HTTP 原始响应/usage 先落盘，再判完整输出合同。
已知 usage 的非法输出是有成本的失败，不能当成未调用；未知业务提交与未知生成费用分列。

先运行安装代码 CPU 全矩阵、原完整 Schema/执行器反例、模拟 HTTP→Session→SQLite、
跨进程停发与授权负控，以及 AGENTS 要求的五项检查。新机制实现不在这些检查中混入。
报告区别 `OFFLINE_REFERENCE / MOCK_HTTP / CPU_ONLY / LIVE_GENERATION`。

`G_PREFLIGHT`：授权策略离线校验、完整 8 对合同、实际请求容量、后端身份和证据链均通过。
CPU/离线可先做；在线只读检查的身份与容量结果在获准新批中记录。通过不等于真实解码通过。

## 5. W2：完整合同的有界真实生成兼容验证

### 5.1 请求矩阵

两遍独立冷客户端，每遍按四根固定顺序依次执行 `full → finish-only`：**8 次/遍，最多 16 次**。
每次只生成一次；第一遍全部 PASS 才运行第二遍。第二遍事前已列入计划，不是失败后的重试。
每遍新进程、无客户端会话/输出继承，不要求重启共享模型服务或清除服务器缓存。
因此只能称客户端冷启动重复，不能称模型/GPU 冷启动或统计独立样本。

- full：提供明确、完整的合法 `put_record` 意图，要求输出相应动作；不是“任意输出 finish 即通过”。
- finish-only：验证该根结束合同和真实服务通路，单独计数，不替代 full 成绩。
- 首次模型调用前固定每根的完整记录参考。优先在已有 25 份参考中按固定对象 ID 顺序，
  选含本次延后唯一性校验数组的合法记录；不存在此类数组的根选旧 single 记录。
  该机械选择及指令只服务于兼容校准，不能根据生成结果换记录，也不代表业务样本抽样。
- 保留原完整公共资料和全部合法目标，明确 `INTENT_ORACLE / VALIDATE_ONLY`。
  evaluator 只导出该已授权动作的必要值，不暴露私有 checker、未来事件或其他业务答案。
- 不接业务 dispatcher、不写 Note。预期动作在独立副本上预先机械校准；模型输出只做验收。

### 5.2 成功定义

逐请求要求：

1. 真实服务返回可追踪响应，usage 完整、一致、与实际输入/输出边界相符。
2. 原始可见输出为严格 JSON，通过**原完整公共 Schema**；所有字段和值未被自动修改。
3. full 输出忠实表达已给定的完整动作意图；finish-only 输出符合结束合同。
4. 原文/哈希、模型可见 canonical、wire、完整校验结果和未派发业务证明齐全。

`G_LIVE_COMPAT` 要求 **16/16** 满足以上条件，新未知/静默修复/权限越界/非预期失败均为 0。
同时单列 full **8/8** 与 finish **8/8**，不把简单结束输出稀释完整合同失败。
这一门证明所选完整合同和合法实例的真实通路，不证明全部合法值、总体成功率或自然任务能力。
即使均通过，离线重复项负控仍不可省略；没有生成重复项不等于后置校验不再需要。

首个非预期 HTTP、用量、JSON、Schema 或意图偏差即停当前候选；已知成本照计。
区别服务失败、合同编码失败、格式合法但值未保真的失败；不能统一叫 GPU 故障或 Memory 失败。
未运行项保留位置和原因，不补题、不加 probe、不启用“修好再自动跑一次”的隐式循环。

## 7. 次数、时间、成本与停发

| 阶段 | 实际生成前提 | 最大生成次数 | 时间界限 |
| --- | --- | ---: | --- |
| W0/W1 | 离线准备；在线只读诊断按准入记录 | 0 | 实施时冻结离线/只读检查 deadline，不无限轮询 |
| W2 | 明确授权 + 完整预检通过 | 16 | 批 1800 秒；每次请求最多 60 秒 |
| W3 | 授权包含 W3 + W2 全矩阵通过 | 24 × 4 = 96 | 批 7200 秒；每链 300 秒，每次请求最多 60 秒 |
| W4 | 只读审计与结论 | 0 | 不追加模型/Judge |

全阶段理论上限 **112 次**，不是最低必须消费量；当前授权分配为 0。
每次输出上限 4096，累计 raw-token 硬上限 `null`。遵循“功能实现优先，token 最后优化”，
但不取消请求次数、deadline、上下文、逐次预约和真实费用核对。
