# V0224：后续 B/C 的完成期限

用户要求完成任务优先，不以严格计算效率阻止实验。CPU 第 9 条在动作完成后的
退出校验期间被旧 300 秒外层终止，证明该限制仍会阻断完整流程。
尚未创建或执行任何正式 B/C 实例，因此在首次真实请求前声明这一范围明确的修订。

新 B/C 执行 revision 为 `V0224_BC_LIVE_COMPLETION_02`。
单冷 worker 整体保护为 3600 秒，P3/P4 阶段与授权总窗口各最多 36 小时。
启动、claim、当前控制检查、事后 terminal 派生与父进程 timeout 使用一致的声明值。
它们用于结束失控生命周期，不用于评定效率、速度或 SLA。
原 B/C 300 秒/1800 秒/7200 秒期限不再是本新实例的通过条件，不能声称满足了旧期限。

每次真实生成 HTTP 仍最多 60 秒，辅助 identity/tokenize 保留原有界请求策略；
固定端点、模型、并发 1、输出 4096、输入上界、零自动重试和未知用量立即停止不变。
完整矩阵仍是 P3 16 条、P4 24 条，上限 112 次生成和 504 次显式 Provider HTTP。
完整授权意图、B1/D11 Schema 与原接受检查、CAS、幂等、回执、World 回读、
R03/R04 fresh scope 与历史账务均保留。没有改变任务答案、提示策略或抽样来争取通过。

实现采用独立 v2 文件；正在执行的 CPU 补全部分及其冻结的 225 个源码不改。
新的 live Batch 仅复用已经明确审阅的期限方法，实际请求依然走有界真实 HTTP 适配器。
通过功能 Gate A、完成相应源码审查与工程增量检查、冻结具体新实例后才执行。
本修订不是真实 B/C 通过，也不授予 E 的记忆研究结论。
