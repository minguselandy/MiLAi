# MiLAi：基于证据与效用的经验选择、修订及跨任务改进 Goal

本轮目标：**在已经可运行的 ReasoningBank／MiLAi 经验链上，完成可拒绝的经验选择、有证据的适用范围修订，以及修订后的再次使用；以实际任务收益和完整成本判断应保留哪些操作。**

开发采用“先完成功能，再优化”的安排。首版要有完整的检索、采用、执行、反馈、修订、保存和后续消费过程，也要有可运行的 MemRL 方法参照；不把第一道任务的胜负设为继续实现的条件。随后才减少无效维护、调整选择策略和收缩没有贡献的部分。

本文件将 [v2.0 优化设计](../../docs/archive/MILA_EVIDENCE_AND_UTILITY_DRIVEN_OPTIMIZATION_v2.0_20260916.md) 转为实施 Goal，补入运行快照、源码边界、工作包、评价协议和交付标准。它是**下一版本的计划**，不改变既有 v0.6 的冻结合同或旧研究的暂停状态。文档生成与本次修订都没有启动、停止、恢复实验或分配模型额度。

## 2. 本 Goal 的成功定义与范围

本轮分别交付三个结果，不能互相替代：

1. **功能完成**：检索可以真正选择空集合；经验有条件地参与当前工作；反馈能改变当前解释、采用关系或持久条目；更新版本可再次检索、使用及恢复；MemRL 参照和共同可用性修复能够运行。
2. **研究完成**：DB、OS、完整旅行组的预定覆盖有终态或明确失败；固定库、在线流和显式评分反馈条件分别报告；必要的贡献拆解完成。它不要求候选获胜。
3. **推广判断**：只有质量、行为证据和完整成本支持时才推广新政策。功能完成但收益不成立时，保留可用实现和负结果，默认方法可以继续是更简单的对手。

首版包含：可拒绝选择、条件化经验形成、依据修订、版本与效用联动、MemRL 接入、OM 容量改进、旅行共同输入核对、独立来源评价。简易效用估计器属于后续优化工作包，但其数据及版本接口在首版中保留。

新候选暂定为 `milai-experience-revision-v0.7`，采用独立配置；该名称表示开发目标，尚未实现。共同执行层、OM 容量修复和 MemRL 移植分别记录版本及来源，避免只有候选名字变化却无法解释实际差异。

本轮不引入新的认知 Agent、通用 RL 训练平台、多套向量库、Canonical 自动升级或第二求解模型。第二模型仍按当前用户决定暂缓；所有结论明确限于当前 Qwen。`multi-source-data-merger` 只保留快速使用回归的位置。

## 3. 总体方案：保留执行主干，改变经验对工作的影响

```text
当前任务、必需事实、原生工具合同
                 │
                 ▼
       原有 Host／原生 Agent 执行主干
                 │
经验检索 → 采用选择：空／紧凑经验／必要来源回读
                 │
                 ▼
  一个当前工作视图：采用范围、必要记录、可选 Frame
                 │
                 ▼
           Actor 执行真实任务
                 │
             真实新反馈
                 │
       ┌─────────┼──────────┐
       ▼         ▼          ▼
  改当前解释  改采用关系  有依据地改经验版本
       └─────────┼──────────┘
                 ▼
      原有结束提炼／提交 → 后续任务再次使用

离线：实际请求、动作、结果、账务 → 配对诊断／效用校准
```

共用 Provider、权限、事件、预算、来源和原生环境，不强迫 MemRL、RB、OM 采用相同维护调度。OM 不挂在所有方法下作为第二条维护链。新 MiLAi 配置沿用已有采用调用与结束提炼；不默认每次工具反馈再增加 Judge 或 Controller。

首版先完整实现这条链，允许存在尚未优化的采用成本。以后如果证据支持用简单估计替代某次模型采用调用，再作为独立版本优化；不能把删去调用和特殊修订政策的效果混报。

## 4. 信息对象：复用现有结构，只补必要的效用记录

| 对象 | 内容与生命周期 | 实现要求 |
| --- | --- | --- |
| 原始来源 | 任务、实际请求、工具反馈、原生历史 | 继续保留可回读原文；摘要不能替代其真实性 |
| 经验条目 | 条件、可复用操作、局限、来源、版本 | 复用现有卡片正文／来源／revision，不新增公开认知 Schema |
| 当前采用判断 | 本任务采用哪些经验、适用到哪里、暂不采用什么 | 复用采用记录、工作记录及 Frame；可以与长期条目不同 |
| 待确认修订 | 当前证据不足以支持的解释或泛化 | 保留在任务工作层；默认不替换有效经验，不建立额外审批服务 |
| 效用侧记录 | 经验版本或经验组合、条件、使用与成本样本、反馈类型 | Lab 内部制品；与银行及方法版本绑定，可重建，不是事实权威 |

效用记录至少关联 `scope / memory_ref / revision / selector_version / feedback_regime`，并引用既有任务、决策和实际请求记录；有配对数据时再关联组合和对照来源。不要把一个经验在所有任务上的成功率直接当成其全局价值。

**结果关联当时实际呈现的版本或经验组合，不按结算时的条目 head 查找版本。**候选被检索、被选中、进入组装但未发送的请求，都不等于实际呈现。复用真实请求及 `confirm_actor_input` 等已有记录；未确认送达的调用保留成本／未知状态，不能伪装成有效使用样本。一次任务中若多个版本实际进入过不同请求，保留按请求排序的暴露序列，不把最终结果全部归给最后版本，也不平均分给所有卡片。

经验正文修订后，旧版本的效用历史仍可审计，**新版本不能无条件继承旧版本的实测高分或低分**。新版本进入未校准状态，但前身版本、修订原因、来源和已知负面历史仍保留可查；“未校准”不等于“没有历史”。采用统一且在开发期固定的冷启动策略，反复改写不能自动获得额外探索机会。撤销、追加、恢复也应保留版本对应关系，无需新增继承评分模型。

效用更新区分以下信号，复用日志中的来源／角色信息即可，不建设新的反馈平台：

| 信号 | 含义及用途 | 不得混同 |
| --- | --- | --- |
| 已观察事实 | 工具真实返回、发生的动作、实际体积与成本；可支持当前解释或条件修订 | 工具执行成功不自动证明整项任务正确 |
| 模型自判 | 模型对成功／失败、适用性或原因的判断；可用于既有提炼政策 | 不标记为原生正确标签，不作为 O-H 的新正确性监督 |
| 原生结果反馈 | 按 R 协议在允许时点公开的结果；可供声明的效用更新 | H 条件不得暗中读取，缺失不等于失败或零 reward |
| 配对增量结果 | DEV 的真实采用／空采用分支形成的质量与成本差异 | 不是单次采用样本天然具有的因果贡献 |

O-H 可以积累成本及可见业务证据、修订经验，不能用自判填补缺失的原生正确标签。正式结果分析可以在方法之外读取评分；分析可见与方法可见须分开记录。

必需事实与可选经验在装配时分别处理，但不要求建设三个存储系统。旅行原生给定计划、当前用户要求和本方法合法前序计划属于任务材料；不能因选择器拒绝经验而被一起清空。

## 5. 改进 A：可拒绝的经验选择

### 5.1 A1：先完成真实的采用选择

复用 `ExperienceRevisionSession.start()` 中已有的 adopt 机会。输入包括当前任务、合法事实、候选经验及来源入口、原生剩余行动额度、当前材料体积；输出沿用稀疏工作区合同。

允许三类行为：

| 选择 | 适用情况 | 下一次实际请求 |
| --- | --- | --- |
| 空集合 | 经验无关、当前已知、条件不匹配，或不能改善当前工作 | 保留原生任务材料；可选经验正文和依赖该经验的采用注释退出 |
| 紧凑采用 | 能复用过去工作，替代当前重建或减少具体错误 | 只投影选定版本及必要采用范围，避免重复展开整条轨迹 |
| 目的明确的回读 | 一个缺失历史细节会影响是否采用或下一动作 | 回读合法来源，再按真实返回决定；不把回读次数当收益 |

**空集合必须在实际 Provider 请求中成立。**当前选空后仍可能存在消费说明、采用注释、经验目录等附加内容；实现时逐项决定是否仍有用途。不能表面上清空正文，却继续注入要求 Actor 逐项评价经验的长提示。来源访问能力保留在正常工具或有界入口中，不要求反复发送全目录。

空采用仍可能已经花费一次采用调用。报告必须计入它；“注入更少”本身不能证明净成本下降。用户任务、最新反馈、权限和交付机会继续沿原 Host 合同处理。

选择应回答：**这份经验能够替代哪一项重建、避免哪一种已知误用，或者帮助处理哪个当前选择？**不强制模型每次填写收益预测表，也不要求报一个未经校准的精确分数。

### 5.2 A2：以有依据的效用估计优化选择

**首版 A2 只学习固定经验包的采用／不采用。**先固定包构造函数 `M(x)`，动作空间为：

\[
a\in\{\varnothing,\ M(x)\}.
\]

默认包构造沿用现有 RB 检索：取排名第一条历史任务记录的经验条目，按固定顺序、条目边界和声明的输入预算投影，绑定准确版本。没有候选或没有能完整装入的条目时返回空包。包构造不调用模型改写或压缩；现有经验形成成本仍计入。两分支使用同一构造结果，一支注入、一支不注入，其余求解／修订合同相同。

A2 的一次选择位置固定在任务开始的采用边界；本任务随后正常处理反馈与修订。首版不学习任意卡片组合、动态压缩、回读次数或逐步预算分配；这些能力仍可按现有接口使用，但不扩大 A2 动作空间。空选择只移除可选经验，保留 §4 的必需事实。

目标是估计这份固定经验包相对于空采用的条件收益。研究目标可写为：

\[
\Delta U(x,a)=E[Y_a-Y_{\varnothing}\mid x]
-\lambda_t E[\Delta T\mid x,a]
-\lambda_b E[\Delta B\mid x,a]
-\lambda_l E[\Delta L\mid x,a].
\]

其中首版 `a=M(x)`，`Y` 是事先声明的任务质量，`T/B/L` 分别是完整 tokens、业务动作和时间。该式定义待估计目标，不宣称系统已经知道反事实收益。质量、成本和时间仍分别报告，不用一个加权总分掩盖失败。

首版拟合采用**小型 L2 正则线性回归**，以每个独立 DEV 配对的实测 `ΔU` 为目标。只使用四个可直接取得的基础特征：检索相似度、包 tokens 占可用输入额度的比例、包内条目数、当前剩余业务动作占原生上限的比例。标准化参数在拟合集上计算；常量特征省略。成本单位、权重、正则强度和采用阈值在 DEV／VALID 上登记后冻结，首版不做模型族搜索或特征自动搜索。

每个样本绑定前置状态、`M(x)` 的条目／版本、两分支实际请求和结果；同题重复先在题内汇总，不能当成新的独立任务增加权重。模型估计为正且达到固定阈值时采用，否则选空；空包直接返回空，不运行一次无意义的采用生成。小样本下估计器可能没有可用增量，允许 VALID 选择 A1，不把能拟合出系数当成学会了效用。

本首版 A2 的在线参数保持冻结；其四个特征不含在线原生结果分数。因此，O-R 即使记录了新的版本效用，也不能声称这些分数已影响 A2。R 条件候选默认使用能读取版本效用记录的 A1 配置，登记效用如何进入实际采用输入；若后来将效用加入 A2 特征或包排序，须另记配置并重新校准，不能追认首版已经实现。

实施顺序：

1. 从已暴露 DEV 中预选独立任务状态，固定共同经验库、包构造和选择位置。建立“采用 `M(x)`／空采用”的真实配对；有副作用的分支各用独立等价环境。
2. 记录前置特征、实际选择、输入材料、所有维护成本和结果。重复一小部分预选配对估计服务波动。不能给新动作播放旧动作的工具返回。
3. 按上述四特征和回归方案拟合，在 VALID 校准，锁定包构造、特征、系数及选择规则。第一版不建设训练调度平台。
4. 测试时直接计算选择，不额外请求模型生成适用性特征或紧凑包；按准确配置与 A1 比较。

效用学习只使用允许的 SUPPORT／DEV 数据。历史日志没有记录反事实选择概率，不能直接宣称无偏离线策略评价。失败任务中的经验未必有害，成功任务中的所有经验也未必有功；首版以实际采用**组合**作为主要归因单位，不把一个成功标签平均写给全部检索条目。

首版直接复用已经完成的检索、经验正文／版本、token 计数和行动额度。它们不增加特征生成调用，但原检索、embedding、存储、形成及计数成本并非消失。以后若加入模型产生的语义特征，新增调用全部归入该 A2 变体，不能先运行 A1 再宣称省去了采用调用。任务 ID、黄金答案、隐藏评分器字段不能作为推理时特征；O-H 新流中的经验与效用侧记录仍从声明的空初态开始。

A1、A2 分别保留 `selector_type`、包构造版本和实际配置身份。纯粹判断是否节省选择调用时，两者使用相同 `M(x)`，A1 也限于采用／不采用；原完整 A1 若还改变了包、回读或 Frame，则比较属于完整选择政策。最终不把两类结果合并成一个无法区分的 v0.7 得分。

对冷启动和低覆盖条件保留声明的探索机会。开发阶段可以在支持／开发任务中安排小比例探索；正式冻结库不因测试分数再调参数。样本不足时保留 A1 或已固定的简单规则，不把未经校准的估计包装成“学会了自适应”。

## 6. 改进 B：条件化形成与有证据的修订

### 6.1 先区分要修改的对象

| 发现 | 默认修改对象 | 何时可以改变持久经验 |
| --- | --- | --- |
| 读错当前工具返回、误解当前问题 | 当前任务解释／Frame | 新证据同时揭示了旧经验的错误或过宽条件时 |
| 经验本身合理，但当前条件不满足 | 当前采用关系 | 不因本题不适用而删除全局经验 |
| 旧经验把局部结果泛化成普遍规则 | 经验适用范围或正文版本 | 可指出旧主张、相关条件及真正支持修改的来源时 |
| 只有新猜测，尚不能区分解释 | 任务层待确认记录 | 不把假设直接写成新经验事实 |

这项区分落实在已有模型修订判断与程序应用边界中，不新增三个认知控制器。程序负责版本、来源可达性和原子应用；模型负责判断语义关系。**引用合法只能证明有来源，不能证明来源支持修改后的结论。**

### 6.2 两个已有修订时点都要可用

**使用中修订**：经验已参与当前输入，新反馈改变其适用判断时，Actor 可利用现有修订入口请求更新。收到反馈后当前工作可以立刻收窄采用范围；无需等待长期经验提炼，也不要求先增加业务检查。

**任务结束修订**：沿用现有结束提炼中的 `new_memory / revision` 处理，合并新经验和有依据的旧条目修订。该调用发生在任务结束后，不能解释为它改善了刚完成的同一任务；价值应在后续任务中观察。

效用归属与版本发布采用以下逻辑顺序，复用现有输入确认及提交过程：

1. 每次实际 Actor 请求绑定当时呈现的版本／组合；持续保留该任务的暴露序列，不以最终 head 回填。
2. 任务终结时固定已发生的输入、动作和成本；按 H／R 合同附加允许的方法反馈。若效用更新被允许，目标是这些已呈现版本／组合，F 的冻结状态不得因此被持久改写。
3. 结束提炼提出的新版本绑定旧版本、修改内容及真实依据；新版本进入未校准状态，保留前身历史。即使提炼调用早于账务结算，结果归属仍按第 1 步固定，不能改变。
4. 在后续实际呈现新版本后，才形成它的使用结果样本。任务内修订若在同一任务的后续请求已经呈现，则保留两个版本的时序，不将整项结果单独归功于新版。

例如，任务 t 仅呈现 `card:1@1`，结束后才产生 `card:1@2`：t 的使用结果样本关联 `@1`；`@2` 记录修订依据，使用效果等待后续任务。修订调用费用仍计入 t 的完整方法成本，并单列为版本转换／维护成本，不能当成 `@2` 已被使用的证据，也不在下一任务重复计费。这个顺序不要求新增归因 Agent 或事务框架。

模型输出无需每轮填满字段。没有新依据就保留原版本；没有值得迁移的新增经验也允许无新增。不能通过每题强制 patch 或自动把成功转成规则来保证“机制触发”。

### 6.3 经验形成优先表达可复用条件

复用 RB 成功／失败两种提炼路径，保留自判和真实轨迹。经验应能够说明适用条件、可复用操作和证据局限；不把本次任务的所有步骤复制成下一题的检查清单。

例如，一次写操作返回 `[]`，能否支持“已执行”“影响了目标行”“满足全部要求”，取决于真实工具合同及可见结果。这三种主张不能互相替代。当前银行样例仍把 `[]` 推广成写入成功确认，适合作为已暴露的诊断材料；**不能据此把“任何写操作都再 SELECT 一次”写成通用政策**。DB 原生行动预算很短，多一次低价值检查本身可能妨碍交付。

若上游接口确实有稳定但未说明的返回语义，可以给所有方法提供同一份真实工具说明。不能凭空新增 `affected_rows` 等上游未返回的信号，也不能把 verifier 结果伪装成工具反馈。

### 6.4 将七次自然更新做完证据链审查

v1.0 的只读核对确认七次更新均为 `post_task`，均从 revision 1 变为 2。后续暴露统计只在同一已终结在线流内追踪准确的卡片版本：

| 域／任务 | 流 | 卡片 | 后续存在该版本 Actor 暴露记录的任务 |
| --- | --- | --- | --- |
| DB 265 | O-1 | card:4 | 无 |
| DB 235 | O-4 | card:1 | 492 |
| DB 324 | O-4 | card:8 | 无 |
| DB 482 | O-4 | card:15 | 无 |
| OS 162 | O-2 | card:1 | 无 |
| OS 328 | O-3 | card:11 | 460 |
| OS 333 | O-4 | card:16 | 无 |

两条后续暴露是**继续检查的入口**，不是两次有效纠错；另外五条没有后续暴露，不能因此证明修订无用或有益。修订后的剩余任务是否存在适用机会，也应单独判断。

D0 对七条都补齐：旧主张、实际来源内容、修改范围、证据是否充分、后来是否检索／采用、真正发送的请求片段、后续动作及结果。对存在后续暴露的两条优先做行为审查，不继续重跑七条来制造更多 patch。

条目版本变更与效用绑定一起提交；旧正文、依据和旧效用可回查。没有语义证据的方案保留在任务层，必要时先暂停当前采用，不以机械字段“valid=true”代替语义判断。

## 7. 新增方法参照：MemRL，先核实算法和反馈合同

本轮只新增一个完整方法参照。MemRL 以相似检索和经验价值更新组织选择，适合比较“相关经验是否值得用”。它已研究价值驱动记忆，因此“经验带分数”“不用时可拒绝”不能单独作为 MiLAi 创新声明。[MemRL 论文](https://arxiv.org/html/2601.03192v1)、[官方仓库](https://github.com/MemTensor/MemRL)。

### 7.1 v1.0 补核出的实现差异

v1.0 编写时读取了官方 `llb_rl_runner.py`、`rl_llb_config.yaml`、`value_driven.py` 及部分服务源码。LLB runner 取原生 `evaluation_record.outcome == CORRECT` 作为成功依据，并据此更新价值、形成记忆；默认配置有 20 次数据重放、每题 15 轮。它们与当前隐藏评分、DB 3／OS 5 轮的合同不同。[官方 runner](https://github.com/MemTensor/MemRL/blob/main/memrl/run/llb_rl_runner.py)、[官方配置](https://github.com/MemTensor/MemRL/blob/main/configs/rl_llb_config.yaml)。

因此不能把官方在线 MemRL 放进当前 O 表格，却给它独享评分反馈；也不能删掉价值学习后仍称为完整 MemRL。配置中的 `mode=test` 不能替代对真实只读评价路径的核对。冻结评价必须显式保证经验内容、Q 值及索引都不因 TEST 更新。

LLB 使用的具体检索／排序路径仍需在固定 commit 上完整追踪。通用选择器的注释、配置项不等于 LLB 调用链实际执行了全部行为；尤其要核对相似度过滤、Q 排序／混合、探索、空返回及更新归因。**本次尚未完成上游版本冻结或本地复现。**

### 7.2 接入范围与保真说明

拟议名称为 `MEMRL_LLB_PORT_v0.1`，与论文成绩及完整上游配置明确区分。首版保留任务意图检索、价值参与选择、声明的探索、经验形成、反馈更新、持久化及冻结评价；不接 MDP 扩展、Best-of-N 或额外大型搜索。

| 项目 | 首版决定 |
| --- | --- |
| 上游来源 | 固定官方 commit、许可、调用路径和提示散列；不依赖移动的 main 复现 |
| 求解模型 | 当前共同 Qwen；不继承上游模型成绩 |
| embedding | 使用现有 bge-m3；维度、归一化、索引版本单列为移植差异 |
| 行动条件 | 与同格 Native／MiLAi 使用相同原生限制；DB 3、OS 5 的本地工作点单列 |
| 学习遍数 | 首版支持集一次顺序形成；不暗中运行默认 20 遍；需要多遍时另列训练与成本 |
| 反馈 | 采用下文 F-R／O-R 显式协议；不改写当前旧 O 的隐藏反馈规则 |
| 测试期 | F-R 冻结所有长期状态；O-R 先计当前题，再发布允许的结果反馈 |

保真检查要有一段完整真实过程：检索什么、什么状态影响选择、任务结束后更新什么、下一任务真正收到什么。受控输出来检查代码路径，真实任务来检查算法是否工作；两者不能混为语义收益。

## 8. 改进 C：共同执行可用性

### 8.1 旅行：先核对事实、传输和真实动作

优先比较本地与固定上游的首个实际请求、工具定义、模型原始输出、解析动作、工具结果和计划提交。检查当前 completion/XML 传输是否与声明的工具合同一致，不能只比较最终自然语言计划。

处理顺序：

1. 核对给定 base plan、当前人员约束和本方法前序计划是否按同一规则提供；保留必要来源入口。
2. 核对原生合法工具能否被模型正确表达、解析并执行；区分未提出工具、格式不合法、工具失败和无须工具。
3. 若任务缺少当前事实，提供一般的工具用途和真实约束说明；不要加入路线答案、实体特例、黄金计划或候选专用帮助。
4. 所有共同修改先在同一条件下应用到 Native、旧 MiLAi、新 MiLAi 及 OM。共同修改带来的改善首先归于执行条件。

无工具调用不自动是缺陷，若已有事实足够，直接交付可能合理。反过来，提出一份非空计划也不等于约束满足。按原生 PS／SPS／SR 及覆盖记录报告，不把 reference-based 得分提升为对所有可行计划的完备判定。

### 8.2 OM：从已存在的容量判断推进到可完成的维护

每个角色都应满足：

\[
T_{\text{完整序列化请求}} + T_{\text{输出预留}} + T_{\text{测量余量}}
\leq C_{\text{实际模型窗口}}.
\]

完整请求包括指令、原生历史、任务事实、观察、近期原文、来源目录、工具 Schema 和模板包装。Actor 现有 `_fits()` 保留；重点改动是让 Observer／Reflector 的输入批次与最终 Actor 投影共同服从容量，而不是仅依据固定阈值调用一次后失败。

具体开发：

- Observer 从实际可装入的完整消息／有明确范围的分页中选择批次；过大的单条来源用已有分页能力处理，记录精确覆盖。
- Reflector 的结果实际替换旧的活动日志；旧原文及引用保留可回读，不继续重复展开全部旧视图。
- 每次维护记录待覆盖材料量、完整输入体积及目标投影体积，明确是否取得进展。无进展时停止重复相同调用，保留未处理位置并返回可解释状态。
- 同一装配机会的维护次数有配置上限，按真实成本调节；不通过无限压缩或无限重试“保证能跑”。
- 来源注册表保留完整映射，Actor 只获得有界目录和必要页。缩短正文不能同时生成更大的逐页遗漏说明。
- 必需任务材料本身超过窗口时如实报告容量不匹配；不能删除当前要求、假装已整理未处理原文，或暗中换更大模型。

首版让已发生的容量失败能被正确定位、适当整理并继续；随后再优化批大小与提示。不要一开始通过极低阈值强迫每题维护。

### 8.3 服务波动：有限诊断，不扩建服务项目

v2.0 记录 100 对首请求中有 82 对返回正文不同，这是需要保留的波动证据，不能直接认定根因是动态批次。开发记录模型身份、可见采样参数、模板和服务版本；对于无权读取的服务启动参数标明未知。

对预先选定的小部分 DEV 配对重复，交错方法运行顺序，记录时间和批次。多个 seed 不增加任务来源多样性。线上服务并不天然保证相同请求逐字一致，参见 [vLLM 可复现性说明](https://docs.vllm.ai/en/latest/usage/reproducibility/)。

不在本 Goal 中重启共享推理服务或修改其调度。vLLM 的 batch invariance 作为独立环境下可能的后续验证，不能仅凭通用支持列表假定当前精确 Qwen 型号已验证适用。[官方说明](https://docs.vllm.ai/en/latest/features/batch_invariance/)。

| **D5 收口** | 整理最小有效操作、未证实部分、使用边界与恢复说明 | 完整报告、方法说明、冻结制品、余额关闭记录 | 可以得出保留简单方法；不能把未运行部分写成完成 |

执行上让 D0、D1、D2 按真实依赖交替或并行推进：修订审查服务于 D1，MemRL 来源固定服务于其移植，暴露清单在确认集冻结前完成，OM／旅行检查服务于各自修复。D0 不是整包完成后才准入开发的总门槛；某个参照尚未可运行，也不阻止其他方法的有效开发。D3 在相关功能可用后开展，D4 使用已经完成并冻结的方法，最后 D5 收口。主线保持完整功能和跨域覆盖，不因某一局部优化没有阳性就退回只做一题。

## 11. 实验协议：主方法、反馈条件和跨任务状态分开

### 11.1 主比较继续保留隐藏 TEST 评分

| 条件 | 初态与更新 | 主臂 | 回答的问题 |
| --- | --- | --- | --- |
| **F-H** | 各方法从其固定 SUPPORT 库开始；长期内容、索引、效用及选择器参数冻结 | Native、OM、新候选 | 经验是否比原生执行值得，新方法是否优于有竞争力的外部方法移植 |
| **O-H** | 各方法从空库开始，独立流；仅用真实可见轨迹在线更新 | Native、OM、新候选 | 不知道隐藏评分时的持续经验使用与方法竞争力 |
| **G-H** | 每个完整旅行组独立；合法前序计划和组内状态可继承；组间不提交测试经验 | Native、新候选、修复后的 OM；旧 MiLAi 用于预选解释子集 | 真正相互依赖的多会话任务是否改善 |

H 表示 TEST 的隐藏原生正确标签不进入方法。DEV／VALID 的评分可以用于离线研究和版本选择，但不能把 TEST 标签加入实时效用更新。O-H 允许更新经验内容，不等于允许用隐藏 reward 更新 Q。

**H 主比较预先选定 OM 为强记忆参照，三臂数量保持不变。**依据是当前四个 DB／OS 格中 OM 的正确率均高于 v0.6，且成本较高，正好需要比较质量与完整代价。使用经过 D2 修复及版本冻结的本地 OM，不继承 Mastra 官方成绩。不能在看到新 TEST 后改选较弱对手；参照仍有失败时保留失败及覆盖，不能用历史成功数据替换。

v0.6 主要用于既定 DEV／VALID 回归及预选贡献诊断，不再占用 DB／OS 新确认的一个完整主臂。它指冻结的记忆算法；共同执行层改变时标明“v0.6 算法＋共同执行条件”，相应比较各臂共用新 scaffold。历史 v0.6 成绩只作背景，不直接代替新的配对数据。

RB 保留为可运行方法及形成／检索参照，不在每个格补跑一整臂。纯选择拆解固定同一检索入口和包，修订拆解采用新候选的只追加变体。这样由 Native 回答记忆是否值得、OM 回答 H 条件方法竞争力、v0.6／同结构拆解回答改进来自哪里。

### 11.2 MemRL 使用独立、明确的反馈协议

| 条件 | 评分何时可见 | 学习与冻结方式 | 比较对象 |
| --- | --- | --- | --- |
| **F-R** | SUPPORT 任务结束并计分后，允许公布一个原生结果值；TEST 不公布 | 支持期学习；TEST 冻结经验、Q、索引和参数 | MemRL、同反馈权限的新候选、Native |
| **O-R** | 当前任务结束且计入结果后，才向所有方法开放声明的结果值 | 更新只影响后续任务；当前题不得重做 | MemRL、同反馈权限的新候选、Native |

R 不提供黄金答案、验证 SQL／脚本或其他方法轨迹。是否只返回成功 bit 或其他原生标量，在首个开发运行前固定；LLB 首版使用原生正确性 bit，与 MemRL 读取成功结果的机制一致。

F-R／O-R 的结果独立报告，不与 F-H／O-H 合并，也不把 R 条件改善全归给算法。新候选使用评分的方式必须明示：仅更新效用或同时用于经验形成，需固定一版。首版建议仅将结果交给效用更新，条件／证据修订仍依据可见业务轨迹；这项与 MemRL 的形成差异据实记录。

同反馈权限下允许两方法按各自算法使用结果，因而这首先是端到端比较。需要归因到单个修订操作时，另在预选开发诊断中固定反馈用途和其他操作；不为形式一致删掉 MemRL 的核心经验形成。H／R 使用不同确认题集，各自表内可以配对，**两表分数不能直接相减作为开放 reward 的效果**。只有专门提出该问题时，才安排同题、独立环境及记忆库的开发 H／R 对照；它不是本轮新增必跑矩阵。

不能把 LLM 自判换成环境评分后仍使用旧的 RB 名称，也不能把只有相似检索而无价值学习的系统写成 MemRL 完整移植。若参考移植尚未达到保真要求，报告“未完成参照”，不填一个误导性的 baseline 分数。

## 12. 数据安排与泛化：开发题和确认题从开始分开

### 12.1 先盘点暴露，再确定新确认集合

已被阅读、调试或根据其结果修改政策的旧 TEST，作为本轮开发／回归材料。D0 汇总两轮研究、所有诊断、旅行组及关联来源簇的暴露并集，再从现有保留来源中选新集合。过去清单中的“保留”只是候选，不自动等于本轮仍未暴露。

按数据库结构／模板及 OS 初始化来源分簇，旅行按完整组及共享 base 来源分簇。没有完整生成谱系时如实保留近重复风险；不把来源分组写成绝对无污染证明。任务答案不参与划分，不按维护触发或候选是否获胜筛选任务。

### 12.2 建议覆盖规模

这是工作量安排，不是由这些数字自动保证统计功效；实际 ID、来源簇、次序和额度须在相应运行前固定。

| 用途 | DB | OS | 旅行完整组 | 使用规则 |
| --- | ---: | ---: | ---: | --- |
| 功能开发与优化 | 24 项已暴露题 | 24 项已暴露题 | 4 组已暴露题 | 不要求每题跑所有臂；覆盖选择、修订、真实工具与容量路径 |
| 版本选择 | 12 项开发验证题 | 12 项开发验证题 | 4 组开发验证题 | 首次本轮政策比较前固定；用于选一个版本，不逐题改答案 |
| 主域确认 | 目标 80 项新题，F-H／O-H 共用任务集合但环境／库独立 | 同左 | 目标 20 个新组 G-H | DB、OS、旅行都进入本轮交付范围，不由前一域胜负触发 |
| MemRL 反馈参照 | 24 项预选新题，F-R／O-R | 同左 | 不新增旅行 MemRL 接入 | 与主确认题来源隔离，避免带评分经验流入隐藏评分条件 |

SUPPORT 优先复用原先划定的 DB 40、OS 40、旅行 20 组来源，重新形成的制品只用本方法、本反馈条件的数据。已有库只有在来源、反馈、形成政策与版本合同一致时才能复用。特别是 R 库不能回流到 H 条件。

同一新确认集合的 F-H 与 O-H 需各自独立运行，不能让一种协议的执行结果进入另一种。每域 80 项 O-H 的起始安排仍为 **8 条独立流，每流约 10 项**，但确认前须结合来源关系和任务内容同时检查独立流数量、流内自然技能复用及后续任务长度；不能仅为了增加独立流而过早重置可能有用的经验。

流构造只依据来源、可见任务内容和原生次序，在生成新 TEST 结果前冻结。D0 可用已暴露材料判断十任务流是否明显缺少复用空间；确需较长流时，在同一 80 项覆盖内预先登记流数、长度和降低独立流数量的代价，不额外跑一套长短流矩阵。各方法使用相同顺序，保持整簇，不按候选是否后来形成 patch 重新排列任务。

修订后剩余任务数、基于任务关系判定的潜在复用机会、实际呈现及使用结果分别记录；没有自然修订仍计入整体成绩，流尾新版本主要提供形成证据。不能删除末尾无复用样本，也不能追加特制任务让某次修订显得有效。少量独立流限制不确定性估计，短流限制长期累积结论，两者都报告。

以上主 H 包为 DB／OS `2 域 × 80 题 × 2 协议 × 3 臂 = 960` 个任务单位；G-H 为 `20 组 × 3 臂 = 60` 个组单位。MemRL 反馈包为 `2 域 × 24 题 × 2 协议 × 3 臂 = 288` 个任务单位。组单位包含多人会话，这些数均不是生成次数，也不是已授权的调用额度。

旧 MiLAi 的旅行解释子集、开发、支持形成及贡献拆解另列单位和成本，不隐含在上述主比较数量中。

若暴露盘点后剩余来源不足，缩减**事先声明的独立来源规模和结论**，或登记新来源；不得把旧题改名为新题。若资源不足，先共同缩减每域的配对数量，保留三个域的覆盖，不再次只完成 DB 后无限期搁置 OS／旅行。

A2 校准和消融使用独立开发位置；正式后不再按测试输赢修改政策。不同任务可以产生不同 State，但核心采用／修订规则保持相同；换环境只作必要工具、来源和格式适配。

### 12.3 本轮泛化主张的范围

| 设置 | 能支持的主张 | 不能支持的主张 |
| --- | --- | --- |
| DB、OS、旅行都参与 DEV／VALID，随后固定方法评价新来源 | 同一方法在参与开发的多个领域内，对未调试任务／来源的泛化和适配 | 完全未见领域的零样本迁移 |
| 若预先选择只用 DB 配对拟合 A2，并在 OS 保持包构造、特征、系数和阈值不变 | 选择器跨域校准迁移；标明 OS 仍曾参与整体方法开发 | 整个 MiLAi 方法从未接触 OS |
| 只使用当前 Qwen | 当前模型和声明容量下的结果 | 跨模型泛化或任意模型通用性 |

首版 A2 默认可以联合使用 DB／OS 的开发配对拟合；因此默认不提出跨域校准迁移主张。若要研究第二行，可在原有开发范围内预先安排，不增加第四个 benchmark，也不把它变成功能完成的门槛。分清支持库形成材料、政策调试材料、选择器拟合／校准材料与确认材料；同一方法在多域新题上有效，不代表这些域从未影响设计。

## 13. 最小贡献拆解：一次回答一个操作问题

| 问题 | 配对条件 | 需要固定的内容 | 可支持的结论 |
| --- | --- | --- | --- |
| 拒绝选择是否有价值 | 允许空采用 vs 固定采用同一检索结果 | 同一经验来源、共同执行、形成政策 | 选择增量；同时计入采用调用 |
| 改善来自何处 | A1 二选一采用 vs A2 轻量二选一 | 同一 `M(x)`、选择位置、信息及反馈协议 | 选择质量与选择自身成本；与完整 A1 的差异另报 |
| 修订旧经验是否必要 | 有依据的版本修订 vs 只追加 | 检索、选择、来源访问、共同消费 | 旧经验纠正的增量，区别于新记忆增加 |
| 特殊消费是否必要 | 同一份模型生成记忆，普通消费 vs 候选消费 | 内容、版本、选材、当时可见事实 | 只限制消费政策，不否定记录形成价值 |

优先选择 D0／DEV 中已经出现真实机会的一项；首轮不运行四项完整矩阵。固定输入的下一动作诊断可降低成本，但只回答选择变化，不能填入原生成功率。

有副作用的执行分支必须有独立等价环境；公开 checkpoint 当前要求的环境身份及版本合同继续有效。不能为实验分叉伪造恢复身份，也不能把开发者编写的理想经验与模型自然形成的经验当成同成本对照。

机会定义来自任务与发生的事实。候选未记录或未采用本该有用的经验，仍计入主结果；任务没有出现某种机会时，不为该机制填零成功率或强迫触发。挑出的解释片段不代替完整任务集合。

## 14. 评价标准：质量、行为、完整成本一起看

### 14.1 主指标

- DB／OS：原生正确率、计划／完成／评分覆盖、结束原因。旅行：原生 PS／SPS／SR、完整组和人员覆盖，分开报告。
- 行为：实际采用版本、真实输入片段、后续动作、可见反馈、修订及再次消费。暴露记录只能证明输入路径，不能证明收益。
- 成本：Actor、采用、提炼、自判、修订、Observer／Reflector、参考方法价值形成的全部生成；另列 embedding、rerank、工具、容器准备、评分、失败和未知用量。
- 实用性：是否及时交付、是否保留真实完成范围、是否因维护失去业务行动或结束机会。

采用更少、卡片更多、修订更频繁、正文更谨慎、final 更多，都不单独构成成功。失败更快不算效率胜利；`REVIEWED` 不是业务正确性标签。

### 14.2 比较与不确定性

使用同任务／同完整组配对差异，F 按来源簇、O 按独立流、旅行按组及共享来源关系处理相关性。报告区间与配对原始分布；少量在线流的 bootstrap 区间不能包装成精确的普遍结论。多个 benchmark 分数不任意平均成一个总智能分。

同一模型在相同首请求下也可能有波动。预先选小部分 DEV 配对重复并交错顺序；正式比较冻结运行方式，不在看到输赢后只补跑不利结果。运行中断造成的时间不可比位置单列，不能用中断前后总墙钟声称推理加速。

### 14.3 实用收益标准与结论强度

每个收益结论必须带参照身份，差值定义为 `新候选正确率 − 参照正确率`，token 比定义为 `新候选完整 TEST tokens / 参照完整 TEST tokens`：

| 比较 | 参照 | 可以作出的判断 |
| --- | --- | --- |
| H／R 中记忆是否值得增加 | 同格 Native | 相对原生执行的质量／成本价值 |
| H 中方法竞争力 | 同格冻结版本 OM | 相对这一本地外部方法移植的净收益 |
| R 中方法竞争力 | 同格 MemRL 本地移植 | 在相同结果反馈权限下的完整方法竞争力 |
| 版本回归 | 同共同执行条件的 v0.6 | 相对旧版本的改进，不能替代 Native／强参照结论 |
| 操作贡献 | 同信息、同包或同结构的指定消融 | 该操作的配对增量及新增成本 |

前述 Native 与强方法比较分别继承当前研究的实用目标：质量路径为配对正确率差异的 95% 区间下界至少 **+5 个百分点**、TEST token 比不高于 **1.25**；效率路径为下界至少 **−2 个百分点**、token 比不高于 **0.80**。形成成本和生命周期成本另列。区间下界达到 +5 比点估计增加 +5 要求更强；不能在报告中互换。

“比旧 v0.6 省 20%”只支持版本成本改进。推荐用于该工作点需同时看相对 Native 和指定强参照的质量／成本，不可挑其中较容易的一组门槛作为综合胜出。若只对一个参照有信号，就限定该结论；研究仍可完成，局部有用操作仍可保留。机制拆解报告针对性的配对行为、质量和成本差异，不强制每个操作单独达到完整方法的 +5 门槛。

这是实用差异目标，不是 80 项一定足以检出的承诺。D0／DEV 可依据配对波动评估所需样本；如需修改目标，应在新确认数据运行前记录理由和协议，不根据新 TEST 结果放宽。

二元正确率门限不直接套到旅行多指标上。旅行在开发验证后、确认前登记主指标及最小有用差异，并同时约束完整组覆盖和成本。未达到确认强度仍可报告开发信号，不能升级为跨任务或跨模型创新成立。

3. 获取新配置的单位成本分布后，按各域／各角色实测 p90 估算批次额度，并留出已知失败、工具准备及结算余量。任务复杂度明显不同的旅行组按会话数分层估算。
4. 正式计划同时预留 DB、OS、旅行和 MemRL 参照份额；逐批实际分配，不能让前一域超支后无记录地取消后续域。
5. 生成、tokens、业务动作和时间分别限制；不能仅凭同样总调用数声称公平。维护调用计费，但不冒充 SQL／bash 原生动作。
6. 未知用量保持待结算或上界，失败和中断不删除。没有计费费率不推算美元，没有服务缓存计费记录不宣称缓存节省。

当前 209,920 次生成等正式上界属于已有冻结研究，不是本 Goal 的实际花费，也不是可自动继承的余额。本 Goal **分配为零**；上节是建议任务覆盖，后续执行按新清单逐包登记实际额度。并发遵守现有声明容量及剩余占用，不通过增加 worker 改变共同服务条件。

## 17. 交付清单与决策规则

最终开发交付应包括：

- 新候选配置、MemRL 本地移植及来源／差异说明；旧方法仍可独立运行。
- 七条修订审查、完整功能过程、至少一条实际新版本再使用的轨迹说明；没有自然机会时如实区分受控路径验证与真实收益。
- 新来源和暴露清单、SUPPORT／DEV／VALID／TEST、F／O／G 与 H／R 的隔离合同。
- DB、OS、完整旅行组的结果和未完成覆盖；最少贡献拆解；全角色成本及形成摊销。
- 受影响检查及必要回归记录、保存恢复说明、方法使用说明和终态账务。

| 观察到的结果 | 处理决定 |
| --- | --- |
| 真空采用降低负担，但复杂效用估计无增量 | 保留拒绝能力与简单选择，删除无效估计复杂度 |
| 条件化形成有效，特殊消费打平 | 保留形成规则，使用普通消费 |
| 修订增加，但新版本未影响有机会的后续工作 | 不主张纠错收益；检查选择与使用联系，避免增加修订频率 |
| 新版本确实纠正后续误用且收益覆盖成本 | 保留该具体修订操作，再判断跨来源稳定性 |
| 仅共同工具／容量修复改善各臂 | 记录工程收益，独立于经验政策贡献 |
| 只在 R 条件有效 | 明确需要任务结果反馈，不能宣传为隐藏反馈下的在线自适应 |
| 完整候选仍不如 Native 或强参照 | 功能交付可以完成；不推广默认算法，保留更简单方法 |
| 预定域或协议没有运行完 | 报告未完成，不能用开发成功或测试通过数替代研究覆盖 |

本轮希望收敛出的是：**经验能在值得时进入工作，不适用时退出；新的真实依据能纠正它对后续选择的影响；整个过程不妨碍任务正常完成。**不要求所有组件都证明必要，也不在功能未完成前先用一次小实验裁掉整条研究路线。
