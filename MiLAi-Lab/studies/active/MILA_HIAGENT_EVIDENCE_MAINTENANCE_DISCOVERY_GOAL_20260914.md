# HiAgent 后继 Goal：依据维护方法开发与原生任务探索

## 1. 目标与推进原则

**实现一个实际运行的依据维护候选，与可用的 HiAgent 简化版、普通 REVIEW 同场执行复杂原生任务，用任务结果、真实选择和完整成本决定保留、修改或删除什么。**

本 Goal 的中心是开发与实验，不是继续审阅设计。默认工作循环为：**改一处实现 → 跑真实任务 → 看结果及相关轨迹 → 提出下一处可迁移改动 → 换任务检查。** 不等普通方案先失败，不要求候选先通过所有单机制消融，不为填满矩阵而运行。

原始 v1.0 为未启动规划；用户指示执行后，本 Goal 已完成有界研究及最终工程验收。见[结果报告](MILA_HIAGENT_EVIDENCE_MAINTENANCE_DISCOVERY_RESULTS_20260914.md)：8 次实际尝试、60 次生成，1 次政策修订，迁移未评分，研究结论 KEEP_SIMPLE_SPECIAL_POLICY_NOT_SUPPORTED。已关闭模型额度，不再追加抽样；下文保留原始规划合同。旧 Goal 和 HiAgent 首轮关闭的 7 次余额未转入。

固定的是权限、来源、真实执行与账务；允许演化的是记录内容、维护政策、粒度和输入组织。允许组合探索，但组合结果先按组合解释，不把三个改动写成一个已经隔离的因果变量。

## 2. 从当前已完成状态直接开始

依据[HiAgent 实跑报告](MILA_HIAGENT_BASELINE_EXECUTION_20260914.md)：

- 当前为 `LIVE_MECHANISM_OBSERVED / NATIVE_TASK_FAILED / ENGINEERING_COMPLETE`。算法 `hiagent-terminal-v0.1`，终端适配 `hiagent-terminal-adapter-v0.1.1`。
- 一个已暴露开发任务 `cancel-async-tasks`：修复尝试原生检查 5/6，reward 0；不是六个独立任务。11 Actor、45 摘要、10 子目标；9 次后续 Actor 输入使用摘要，真实 retrieve 为 0。
- 包含首次非法动作失败，共 57 次生成、50,153 tokens，全部结算。重复摘要占修复尝试约 60.1% tokens；这不是候选尚未运行时可以提前兑现的节约。
- 当前 4479 项工程测试具有终态覆盖：4478 PASS / 1 可选 SKIP；构建及其他检查完成。**不为开始本 Goal 重跑这份既有验收。**

复用既有 Harbor 0.23、任务快照、HTTP Provider、tokenizer、终端执行、receipt、方法事件和 native verifier。源码来源与移植差异沿用[基线说明](MILA_HIAGENT_BASELINE_IMPLEMENTATION_20260914.md)。不另建 admission、缓存服务、记忆库、评分平台或任务世界。

本轮重点不是证明“维护发生了”——已有真实证据；而是让维护对后续工作产生值得保留的作用。

## 3. 要开发什么

### 3.1 工程对照 H_ONCE：闭合段只摘要一次

从当前 HiAgent 增加一个显式新模式或子类，不改旧模式含义：

- 第一次需要展示闭合段时生成摘要；其原始段和摘要政策未变时，后续直接复用这份摘要。
- 当前段保留详情；历史展开、原始 receipt 回读、真实新观察的处理继续沿用基线。
- 复用仅在当前 trial 内；新 trial、段内容或政策版本变化不能拿旧结果顶替。使用现有对象中的摘要和来源身份即可，不建设跨进程缓存层。
- 未知用量仍停发；已结算但降级的摘要应明确标注，不能隐藏补生成或把回退当高质量摘要。

**这是工程对照，不是创新主张。** 首轮无缓存 HiAgent 留作历史原型；若需要声称 H_ONCE 的实际相对收益，另用保留位置做同期比较，不能只拿历史分数相减。

### 3.2 方法候选 EVIDENCE_0：由真实反馈维护当前行动依据

不再让 Actor 顺手填写可选 Note。由 Host 在收到新的完整动作／观察之后、下一次 Actor 决策之前，发起明确的维护调用：

```text
当前用户任务 + 上一版依据记录 + 尚未维护的新动作/真实回执 + 合法来源入口
    → 同一模型的独立维护调用
    → 更新后的自由文本依据记录

当前用户任务 + 更新记录 + 未经摘要替代的新观察/当前工作详情 + 请求展开的历史
    → Actor 决定下一动作
    → 原生环境执行并产生真实结果
```

初版每批新终端回执最多一次维护；没有新回执、仅重装相同输入时不重复维护。`final` 不再追加一轮无后续用途的总结。所有调用共享预算；维护与 Actor 都使用同一已支持模型，不在 Runtime 中隐藏语义处理。

维护任务是更新“后续行动可以依据什么”，不是复述每个步骤：

1. 保留哪些观察支持当前判断，以及支持到什么范围。
2. 新反馈改变局部时，保留仍成立的部分，缩小或撤回受影响判断；未知不能写成已证实。
3. 区分动作被执行、检查通过、以及用户要求已满足；自建检查覆盖什么，由实际输入与返回决定。
4. 可以保留未验证的新线索和返回入口，但不因联想到就采信，也不规定必须暂停或恢复。

这些规则由模型解释，不编码成关键词、固定状态图、任务 ID 分支或“每 N 步必须换子目标”。记录允许无实质变化；维护调用本身仍入账。程序只管理调用时机、可访问引用、输入装配与保存。

初版可以让依据记录替换过去段的默认摘要视图，保留当前详细交互和同样的原始历史恢复能力。新观察必须直接进入 Actor，不能仅通过维护模型转述。用户目标与权限独立保留；旧记录不能覆盖它们。不得把完整旧正文又全部附在记录旁边，却声称已测试记录主导的输入组织。

EVIDENCE_0 同时改变维护频率、记录对象和输入组织，**先作为组合候选**。有净收益后再拆；不要求开发前把全部因果消融做完。

## 4. 开发执行顺序：先跑起来，再按结果改

### 第一步：小实现后立即进入原生任务

完成 H_ONCE 与最小 EVIDENCE_0，跑受影响的邻近测试和边界检查，即可开始实跑。已有原生入口、隔离和计费不重新验收一遍；只检查本次确实改变的路径。

首个真实轨迹前只需留下：方法版本、任务、共同模型／预算、实际输入策略。用已有运行清单即可，不先写第二份设计评审报告，也不等全仓回归。

### 第二步：首批公平比较

在已可运行的 `cancel-async-tasks` 上执行 **REVIEW / H_ONCE / EVIDENCE_0**。允许先运行候选观察实际机制，再补齐同任务对照；不得用历史 NOTE/REVIEW 代替同期结果。

三臂提供相同任务初态、原生合同、工具权限、模型配置与总资源机会。REVIEW 在正常决策内复核，不强制增加独立 Reviewer，也不禁止其自然记下条件和不确定性。不同记忆方法的输入组织可以不同，但必须明确记录；这是方法级比较，不冒充逐字相同输入的纯政策实验。

不要给任何臂加入已知失败测试的名称、正确修复、特定取消方式或答案提示。该任务已参与假设形成，所有结果只算开发结果。

### 第三步：尽早把同一版本带到另一个任务

首选同一固定 Terminal-Bench 2 快照的 `query-optimize`，用于检查从实现任务到数据／约束任务的迁移。若原生环境依赖在现有范围内无法低成本解决，备选 `build-cython-ext`；后者仍只是跨 root 的工程任务迁移，不冒称跨领域。

本次只核对了备选任务的本地 metadata：文件存在、CPU 配置、GPU=0；**未证明它们的环境和 verifier 已可运行**。任务固定来源为 `2fd12b88aafdd04a52c298e3940bcb189f9766d6`，沿用现有目录，不重新下载全库。

在读取该任务运行结果之前记录版本与顺序，先按原政策执行，不逐题改认知提示。环境不可用可以换备选；模型做错不能删题补一个候选赢的任务。若根据该任务修改方法，它对新版本就成为开发来源，保留第一次迁移结果。

`multi-source-data-merger` 可用于便宜的补充诊断，但历史上已有多臂成功，不能仅凭它打平或省少量 tokens 就声称复杂能力突破。ClawMark、新 benchmark 后端和密封确认池不属于本轮必交付内容，不为“第二来源”重新搭平台。

### 第四步：根据轨迹做最多两次方法修订

只有出现具体解释时才改。每次只记三句话：**观察到什么困难；改变哪条通用操作规则；接下来在哪个不同任务或对照中检查。** 不再追加长篇 review。

可以调整维护粒度、提示、记录表达、摘要复用与输入组合；不要求所有探索严格单变量。不得只加“更仔细”、堆题目专用提醒、固定每轮必须维护多少条或抽样直到出现胜出。

方法修订与接口修复分列。接口修复若改变共同执行合同，下一组公平比较统一采用修复版；修复前的失败、用量和未评分状态全部保留。

## 5. 只运行能改变判断的对照

主比较固定为 REVIEW、H_ONCE、EVIDENCE 当前版本。NOTE 继续可用；若担心 REVIEW 政策本身造成负担，可用保留位置补一条 NOTE，但不是每题都增加第四臂。

有信号后，从以下选择**最有信息量的一项**，不要求全做：

- **同维护时机的普通增量摘要**：与 EVIDENCE 使用同一输入、维护时机、Actor 和历史展开规则，仅将“依据范围修订”换成普通过程／结果更新。区分通用增量维护与候选语义规则。
- **同信息普通消费**：把候选在当时形成的记录交给普通消费政策，不回填未来信息，形成成本不免除；判断特殊消费政策是否必要。
- **取消跨步记录继承**：检查收益是否来自状态连续性，而非当前回合的一般求解提示。
- **无缓存 HiAgent 同期参照**：只在需要量化 H_ONCE 的工程改善或解释异常时运行，不把低效原型当唯一强对手。

若一个组合先有效，可以暂时保留组合；未做拆解就不写独立机制结论。缓存对照的成功不成为候选探索的前置门。

## 6. 资源与自主范围

规划起点是两组各三臂，即 **6 个 trial，最多 384 次生成**。另保留最多 6 个 trial，用于有解释的修订、迁移、失败后的新尝试或一项拆解；**总上界 12 个 trial / 768 次生成，不要求跑满**。

| 项目 | 执行约定 |
| --- | --- |
| 单 trial | 初始最多 64 次生成，Actor、维护、检索决策及失败请求共同计数 |
| 调试／重跑 | 也占 12 个 trial 和总生成上界；不是额外免费配额 |
| 启动方式 | 用户指示执行后，首批分配不超过 3 个 trial；后续在上界内根据实际结果自主选择下一批 |
| 配置 | 同一配对使用相同模型、解码设置、业务工具与原生时限；顺序跨任务轮换 |
| 上下文 | 开始时读取实际模型窗口；当前已测为 65,536，不照搬 8k 或 512-token 硬门 |
| 输出与记录 | 初始每调用输出预留 4096；记录长度是软建议，容量由真实窗口和输出共同约束 |
| 账务 | 分列 Actor、维护、输入、输出、工具、环境、verifier 和开发成本；不设新的累计 raw-token 硬门 |
| 服务 | 只用现有授权 vLLM HTTP；不操作 GPU、不重启或修改共享服务 |
| 并发 | 默认串行；不为吞吐优化增加工作包 |

64 是运行保险丝，不是认知步骤要求。如果多臂明显受额度截断影响，可以在**新的完整比较组开始前**统一提高每 trial 上限，必要时修改现有 1..64 参数约束；减少可运行 trial 数，仍不得超过 12 trials / 768 总生成。时限或容量同样只能前瞻、对整组一致调整并单列本地配置，不在候选快失败时单独加时。不得复活旧失败轨迹，不能把截断写成完整性能结果。

实际生成用量未知、Provider ledger 未结算或环境副作用不明时立即停发，不自动重试。新权限、共享服务改变、扩大总资源范围需用户确认。普通任务失败、合法的低分、单个假设不成立无需升级成全项目阻塞。

模型之间不传递其他臂的产物或 grader 信息；每条 trial 使用独立初态。辅助 `/models`、tokenizer HTTP 与生成调用分别记录。没有美元费率就不编造美元费用。

## 7. 少审阅，但保留能防止误判的信息

这里减少的是开发者反复审批与全轨迹精读，不是删去 REVIEW 基线，也不是取消维护算法。

- **每批先看 native reward、通过项、产物和成本，再看能解释差异的少量关键片段。** 没有差异或异常时，不逐条给摘要人工打分。
- 保留已有请求、响应、来源、回执和版本日志；不开新审计服务，不在每个动作前重扫历史证据和代码闭包。
- 不使用默认 LLM Judge、评分模型重评或多个 Reviewer；原生 verifier 有具体争议时只核查受影响项。
- 不为本轮开新一轮广泛查新。候选出现可重复信号后，只针对实际起作用的操作核对最近方法；尚未完成时不声称新颖。
- 环境小修按实际进展处理；若一次排查已转为搭平台，就换已列备选或报告该来源未完成。时间提醒用于反思，不把“多一秒”制造成新的实验失败门。

每个版本只需要已有日志加一条短修改说明和结果表；不用另写准入报告、设计审阅报告和“准入的准入”。

## 8. 以什么结果判断

主结果依次是：**完整任务是否完成、关键约束是否满足、全部尝试成本是否值得**。保留原生 reward 和子检查，不把 5/6 检查换算为任务成功率，也不以最终正确抹去错误副作用。

过程只辅助解释：局部结果是否被扩大成整体确认；新证据出现后是否恰当修订；是否重复无新增价值的工作；记录是否实际进入下一次决策。必要重测不自动算浪费。没有 retrieve 或返回机会就报告未观察，不强迫任务演出恢复。

| 观察 | 判断／动作 |
| --- | --- |
| H_ONCE 更便宜，质量相近；EVIDENCE 没有额外价值 | `ENGINEERING_GAIN_ONLY`，保留简化方法；不称记忆创新 |
| REVIEW 相同或更好且更便宜 | 对当前版本 `KEEP_SIMPLE`；有新的具体解释才修订 |
| EVIDENCE 原生任务或完整成本改善，但只在开发题出现 | `LOCAL_METHOD_SIGNAL`，将同版带到另一任务，不写泛化结论 |
| 同版在不同任务上仍有净收益 | `TRANSFERABLE_DEVELOPMENT_SIGNAL`；仍非密封确认或产品收益 |
| 同维护时机的普通更新打平 | 将贡献收窄到维护流程／记录形成，不坚持特殊调控规则 |
| 记录形成了但行动无改善，或维护开销吞掉收益 | 修改或删除该部分；不能以“记录更合理”代替效果 |
| 维护／消费未真正运行，或任务／评分不可用 | 明确实现问题或缺失证据；不能得出 Memory 机制负结论 |

使用按任务配对的胜／平／负和成本差，不将同一 root 的重跑、子检查或摘要调用当独立样本。预算耗尽、无效评分和失败尝试进入总表；不得只统计成功样本或挑最好一次。

## 9. 工程检查的位置：最后收口，不阻断每轮探索

开发循环跑受影响的邻近测试、边界及必要静态检查即可；不能用相同全仓回归替代下一条真实轨迹。只有相关实现变化才重测对应路径，既有 4478 PASS 不重复作为开工任务。

最终选定要交付的代码后，按 [AGENTS.md](../../AGENTS.md) 完成边界、全仓 pytest、ruff、mypy 和构建。全仓回归安排在最终收口阶段，正常情况下不因每次提示试验重跑。若发现真实回归缺陷，修复并验证受影响范围；不得为了凑“只跑一次”忽略缺陷。

研究结论与工程状态分列。全回归未完成就明确未完成，不能借用历史通过或重复相加凑全量；也不把等待工程终态写成新增算法研究。退出本轮自己启动的 trial 和进程，不改其他工作使用的服务。
