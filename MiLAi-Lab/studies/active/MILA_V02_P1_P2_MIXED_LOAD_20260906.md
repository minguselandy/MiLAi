## 冻结条件与实际比较

配置：`configs/v02-fixed-arrival-mixed.json`。
复现入口：`uv run python tools/run_v02_mixed_pair.py --root artifacts/v02-e2e-generality/<new-run-id>`。
本次产物：`artifacts/v02-e2e-generality/p1-mixed-20260906a/`，含运行前的两臂配置、源码摘要、
公开接口事件、计时、资源采样和清理。Product pin未变：
`e5dc1dafc1246153f753f5d6b2a71060a9ef6688ce70948bc0a796dac630a7a7`。

两个独占服务按baseline→mixed顺序运行，一次只运行一个负载臂；各自公开保存相同逻辑的
1,000条合成State及3份512/2048/8192字节来源。每条State有一个真实来源引用；实际MCP
读取覆盖TASK/SESSION/PROJECT三份完整State，每份对应一个来源。正文首尾字段保留。
两个服务的原始capture请求正文摘要一致，活动State替换服务分配的来源ID后正文/版本一致，
工具catalog相同。UUID、租户、资源URL和捕获时间分别属于各自服务；不声称数据库逐字节相同。

每臂同样预热12次读取，然后三轮、每轮按5秒排程100次MCP读取（20次/s）。mixed另排
50次SDK capture（10次/s）。读取和导入的客户端在途上限分别6/2，总计不超过8；种子写入
上限4，零重试。每轮结束后检查这50个outbox的evidence投影，并逐条公开GET核验正文hash；
这部分确认不混入保存回执延迟或读取负载窗口。必要持久回执不等待GET或索引。

本机2核affinity、8 API线程、API池最大8；PG 2 CPU/1 GiB、bridge网络。使用现有
deterministic hash provider、无收费依赖或生成、无rerank。两个服务同样预热，但不证明
缓存状态逐项相同；单次固定顺序未消除宿主机/磁盘时间变化。这里比较已有产品在两种
工作负载下的行为，没有改变Product实现，更没有把混合负载作为新的Memory算法。

计时从预定发送时刻至完整响应，包含调用方调度迟到。过载时不等待空位后偷偷漏发：
记录客户端容量拒绝；失败后未发送、超时结果未知分别记录。成功分布不填入超时阈值。
预注册候选门为读取P95≤50ms，且每轮mixed/baseline P95≤1.5；后者是候选50%退化容限，
不是已有收益结论。服务网关入口到输出完成仍没有直接测量，不把客户端结果称网关SLO。

## 归因和剩余缺口

600/600计量读取唯一关联到Runtime及MCP日志。平均池获取仅约0.018–0.022ms，没有扩池依据。
baseline最大一次客户端调用284.81ms，其中连接持有264.30ms、池获取0.014ms；mixed最大
一次66.07ms，其中MCP handler外57.01ms、Runtime应用5.86ms。两个尾部位置不同。
连接持有包含事务、查询、线程调度等，handler外也混有编码、调用方调度和传输；没有
进一步证据时，不能把它们归为纯SQL、磁盘或网络瓶颈。

保留固定配置下的退化负结果。下一步需要针对这些具体等待区间核查，再决定是否修复
单点；不先扩大连接池、增加索引模块或移动门槛。普通租户公平份额、明确服务背压、范围
检索流量、较大/持续负载和完整网关SLO均未验证。当前仍只是1,000条State上的三个已知
作用域读取，不能称1,000条范围检索或完整P1/P2验收。
