# MiLAi：基于参考方法的 Host 记忆调控详细设计

## 0. 决定摘要

**不重建 RWC。保留本地 H_ONCE 方法基线和 WORKSPACE_SIMPLE 同结构对照，新增一个依据 Mastra Observational Memory 同步机制设计的外部方法移植；用 MemR³ 和 ACE 检查控制与更新规则的具体差异。**

本设计的主线是：已有方法的完整运行机制 → MiLAi 现有对象与生命周期映射 → 明确的候选增量 → 实现中的短行为检查。不是再列一批 benchmark，等待模型自行发明记忆使用方法。

建议下一开发版继续使用既有 Controller—Workspace—Actor、卡片、Frame、ACT / RECALL / DELIVER、来源投影与 checkpoint。增加或调整的内容集中于方法配置、记录更新政策、必要的外部方法移植和接口可用性。**架构能力可以完整保留；每次任务可以只使用其中必要部分。**

来源类型在全文中分为：

- **[R] 项目材料**：附件中的状态、接口设计、版本和运行记录。本次没有对应源码仓库、原始请求及修复报告的完整内容，不能独立确认实现现状。
- **[B] 外部来源**：本次读取的论文、官方项目说明、API 文档及成功读取的源码。
- **设计建议**：下面给出的映射、接口与算法，不代表已经实现，也不自动修改旧 Goal 的执行范围。

## 1. 从最新 MiLAi 状态开始

最新可用性 Goal 把 `milai-rwc-v0.2 / hiagent-method-adapter-v0.4.2` 作为继承起点，记载独立卡片、Frame、路由、去重、本地与公开恢复已经实现；缺省字段规范化和本轮可用性改进仍为提案。[R1]

同一 Goal 记载：v0.2 的 16 次 Controller 返回中有 9 次拒绝；四次原生尝试没有自然 RECALL 或分支返回；一次合并任务配对双方成功，候选少一次生成、少 1,573 tokens，但只能作为局部观察。不能借此证明泛化收益。[R1]

此前 H_ONCE 已运行闭合段首次摘要与缓存；EvidenceHost 已使真实反馈后的维护进入 Actor 输入。EVIDENCE_1 与同维护时机 INCREMENTAL 的结果和调用数相同，多 215 tokens。因此，**已有维护过程并非完全未测试，特殊更新政策也没有已证实的收益。**[R2]

本设计不再重复建设上述能力，不追溯改写旧负结果，也不把最新 Goal 的拟议默认值当作已实施能力。

## 2. Baseline 选择：区分比较对手、实现参考与近邻

### 2.1 建议的方法集合

| 定位 | 名称 | 当前处理 | 能回答什么 |
| --- | --- | --- | --- |
| 现有正常执行参照 | 原 Actor / 原入口与其正常历史管理 | 只在判断新架构开销时选用，不要求每次都跑 | Controller 架构是否拖累正常工作 |
| 主方法基线 | `H_ONCE`，本地 HiAgent 移植 | 保留，不重写 | 分段摘要与回读已经做到哪里，新方法是否有增量 |
| 同结构简单对照 | `WORKSPACE_SIMPLE` | 与 RWC 共用接口、调度、Actor、来源、卡片和预算 | 特殊政策是否优于普通维护 |
| 首个新增外部方法移植 | `OM_SYNC_PORT`，Mastra OM 同步机制 | 新增一个小型方法实现，不引入完整 Mastra 框架 | 观察日志、近期原文和按需回读是否已经足够 |
| 消费控制近邻 | MemR³ | 先对照算法；有检索控制问题时再移植相关路径 | 证据—缺口驱动路由与 MiLAi 有何操作差异 |
| 维护近邻 | ACE | 先学习条目级更新；跨任务经验学习不进入当前主线 | 增量维护不是新概念，差异究竟在哪里 |
| 后续训练参考 | AgentFold | 不作为提示即可复现的首版对手 | 同调用控制与动作可怎样训练和优化 |

**只新增 OM_SYNC_PORT 一个外部方法，不同时接入五个系统。** H_ONCE 已提供一个可运行的研究方法底座；OM 增加不同的维护组织方式；WORKSPACE_SIMPLE 保证候选不能只赢一个较弱的存储或摘要对照。

### 2.2 HiAgent：按子目标组织工作记忆

论文 §3 给出的运行机制是：模型形成子目标，将相应 action/observation 归入段；完成子目标后以摘要替换自动展开的详细历史；需要时再次展开对应轨迹。摘要也考虑子目标是否完成。[B1]

**继承操作：**段管理、摘要缓存、当前段细节、按需展开。

**不追认：**本地 H_ONCE 的缓存、终端适配、来源治理与官方原始实现不完全相同；成绩应使用本地方法名，不写“原论文完全复现”。本次成功读取论文及仓库首页，关键 raw 源文件重新获取未成功；具体源码分支继续以已保存的本地实现及其差异记录为准。[B1][B2][R2]

### 2.3 Mastra OM：不只是摘要，还有任务续接提示和来源回读

官方文档描述 Observer 将消息整理为观察日志，Actor 消费观察与尚未整理的近期消息；观察日志达到阈值后，Reflector 对其归并。同步模式可以通过关闭 async buffering 选择。retrieval 模式为观察组保留原消息范围，并提供无需向量库的浏览回读。[B3]

API 还公开了 `currentTask`、`suggestedResponse` 及其开关。因此，“保存当前任务与下一步建议，再交给 Actor”不能单独作为 MiLAi 的新颖性。文档还提醒，自带控制流的 Agent 可以关闭 `suggestedResponse`，避免两个安排来源竞争。[B4]

**用于独立 OM baseline 时：**按选定的上游配置保留续接提示；不能为了突出 RWC 的 Frame 而悄悄删掉。

**作为 RWC 的实现材料时：**不再并排注入一个 OM suggested response。RWC 只保留一个当前 Frame，避免两个记忆过程争抢下一步。两种配置必须分名，不混报。

本次读到了官方文档/API，未成功取得关键 TS 实现文件，因此这里是可实施的机制移植设计，不是源码逐路径复现已经完成。

### 2.4 MemR³：显式状态和真正的路由

MemR³ 用证据—缺口记录驱动 retrieve / reflect / answer。论文同时包含最大迭代、连续反思限制以及已经检索片段的屏蔽规则。[B5][B6]

MiLAi 可以学习状态如何决定下一操作，但不应照搬“读过就不再读”到可逆返回，也不能把“预算到限回答”解释为证据充分。

**特别区别：MemR³ 的 retrieve 包含查询构造与搜索；RWC 的 RECALL 主要是读取已知引用。**二者不等价。若以后移植 MemR³，检索必须通过已有合法搜索路径，不能只把 retrieve 字符串重命名成 RECALL，就声称完整方法已经复现。

旧仓库地址本次重定向到 `mbzuai-ai4bio/memr3`；官方 README 列出 `src/memr3_base.py` 等入口，但本次未成功读取该核心文件正文。[B6]

### 2.5 ACE：借增量思想，不把 TODO 当已有能力

ACE 论文把 Generator、Reflector、Curator 分工和条目级增量作为核心，通过反馈维护后续使用的 playbook。[B7]

本次成功读取的官方 `playbook_utils.py` 中，`apply_curator_operations()` 的操作分支实现 ADD，UPDATE / MERGE / CREATE_META / DELETE 仍写在 TODO 中；辅助函数另有计数更新。这只是该公开代码路径的状态，不是说整个论文或所有 ACE 实现都不能修订。[B8]

因此，不把该函数直接当完整“撤回—修改—恢复”实现，也不将补齐其 TODO 视为原创算法。当前借鉴条目级维护即可，不引入跨题 playbook 学习、额外 Reflector/Curator 或自动 helpful/harmful 计数作为真值。

### 2.6 AgentFold：先行结构，不是零成本提示替代品

AgentFold 用专门构造的轨迹和监督微调学习上下文管理与动作的联合输出；论文明确讨论仅靠提示的格式与准确性不足。[B9]

MiLAi 当前允许分离 Controller/Actor 是合理实现选择；后续可研究融合、蒸馏或训练，但不提前假定当前模型具备这种联合能力。

## 3. 基于 MiLAi 的系统边界

```text
用户 / Benchmark 原生任务
             │
             ▼
现有 Host：目标、授权、事件、预算、原生工具协议
             │
             ├── H_ONCE：分段摘要与历史展开
             ├── OM_SYNC_PORT：观察日志、近期消息、按需回读
             └── RWC：Controller → Workspace/Frame → Actor
                                 │                │
                                 └── Sources ◄────┤
                                                  ▼
                                           真实动作 / 真实结果
                                                  │
                                         返回同一 Host 生命周期

来源取得 / Working State 保存恢复：既有公开适配
Runtime：身份、权限、版本、CAS、幂等、生命周期、机械存取
```

方法入口共用既有 Provider、执行器、来源能力、日志与 checkpoint 适配。**不同 baseline 可以有不同维护时机；不能为了共用 RWC 类而强迫所有方法每轮调用 Controller。**

RWC 内部保持一个 Host、一个工作区写入者、同一模型的两个逻辑职责。Controller 不执行终端命令；Actor 不获得额外授权；Controller 的工作安排和卡片都是可错数据。

Evidence 记录原始观察与来源，不自动证明解释成立；Canonical 是另一条治理路径；Runtime 的 retrieval continuation 只保留机械 cursor/frontier，不放语义目标或暂挂原因；HOST_WORKING 保存工作认知；Context 是这些材料的有界投影。这些边界来自 MiLAi 项目材料，不因加入外部方法改变。[R3][R4]

## 4. OM_SYNC_PORT 的详细实现

这是新增 baseline 的方案，不是给候选偷偷增加第二套维护器。

### 4.1 最小内部对象

```text
ObservationGroup
    text                 观察内容，自由文本
    source_ranges        对应原消息/事件范围
    revision             Host 管理

ObservationMemory
    groups               已整理的观察组
    raw_tail             尚未被整理替换的消息范围
    continuation_hints   上游配置允许的当前任务/续接建议
    covered_ranges       实际处理的范围，不代表模型理解
```

这里只保存基线需要的内容，不混入 RWC 的特殊依据政策和分支控制。source_ranges 通过已有来源注册表映射，不让模型填写真实路径或权限。

### 4.2 同步维护算法

```text
收到一批真实消息/工具结果：
    追加到原始事件记录与 raw_tail

在下一次 Actor 前：
    若 raw_tail 达到已配置的观察阈值：
        Observer(已有观察 + 待整理消息)
        成功后保存观察组及其原消息范围
        已覆盖旧消息退出自动展开；保留近期窗口
    若观察日志达到已配置的归并阈值：
        Reflector(观察日志)
        成功后替换日志视图；原始来源范围仍可回读
    Actor 输入 = 当前真实任务 + 观察日志 + 续接提示 + 近期原文

Actor 需要精确历史：
    使用相同来源权限读取对应原消息范围
    返回内容进入正常任务上下文
```

观察和归并都是真实模型调用；不得以“工具内部操作”为名漏记。接收失败时不删除原始 tail；没有发生观察也属于正常 baseline 行为，不能为了有一份日志强制每轮更新。

同步、无向量检索和 thread-local 是本地移植的明确配置。上游的异步缓冲、跨线程浏览、多模态等不默认纳入，不冒称完整 Mastra 产品复现。[B3][B4]

### 4.3 阈值与 MiLAi 的容量

上游默认阈值不直接搬入本地模型。先使用当前 Provider 实际窗口与输出预留，满足：

```text
可信任务/工具合同 + 观察日志 + 近期原文 + 回读内容 + 输出预留
    <= 当前模型可发送容量
```

阈值是触发点，不是硬上限；下一批工具结果可能很大，因此投影仍需保留完整消息组、分页和未展开标记。短任务没有达到观察阈值时，不能据此说 OM 不会维护；可以在单独开发片段中验证触发路径，但不把刻意调低阈值的结果冒称默认配置。

## 5. RWC 候选：在既有结构中增加什么

**核心假设：维护的不仅是过去做过什么，而是当前选择依赖什么，以及新反馈应当改变哪部分选择。**

这不是建立事实真值机。模型仍可能错误识别依赖；实现必须保留原证据、新观察与纠正路径。

### 5.1 数据结构不再扩一层

沿用现有对象：[R1][R3]

```text
WorkspaceSnapshot
    working_note
    cards
    frame
    revision / provenance / coverage metadata  # Host 管理

MemoryCard
    text
    source_refs
    revision / archival metadata              # Host 管理

FocusFrame
    question
    intent
    selected_refs
```

不新增 TRUE/FALSE/ACTIVE/PARKED 认知状态图，不新增自动依赖传播 DSL。未被选中的卡片只是没有占据当前工作集，不表示错误；归档只是目录操作，不表示永远无用。

### 5.2 N1：让更新对象从“过程”转向“有范围的行动依据”

Controller 根据当前可见新反馈，决定哪些旧表述仍有依据、哪些应缩小范围、哪些需要撤回或重建。可以只改一张卡片，也可以在基础前提被推翻后重写整个工作判断；不奖励修改得少。

例如，记录不应从“编译成功”自然滑向“任务已经全部验证”。它可以保存“实现完成并通过当前编译；行为边界仍未运行”，再判断缺口是否值得影响当前行动。

重要的是后续 Frame 与选材是否随之改变，而非加入“依据范围”几个词。此前 EVIDENCE_1 的记录仍未促成任务收益，这一负结果继续成立。[R2]

### 5.3 N2：候选保留、当前投入、结论采信分开

允许保存尚未证明有价值的线索；不要求先有两个可行方案。不强制每轮造卡片，不按分支数评分。

当前主要材料由 Frame 选择，未采用线索保留简短目录入口。选择一种材料意味着值得看，不意味着内容可靠。真正的新观察和反证不参加旧焦点的过滤。

### 5.4 N3：返回是重新判断，不是固定 RECALL 仪式

必要条件失效时停止沿用；暂停原因消失时重新评估；当前依据足够且符合目标时才重新采用。

- 依据已经在当前输入且适用性可判断：直接判断，不增加读取。
- 只有摘要或缺少关键细节：RECALL 原始来源。
- 需要知道当前环境而非过去发生什么：Actor 使用既有业务工具核对当前状态。

历史回读、当前世界查询、重新采用，是三种不同动作。不能用读回旧字节替代核对当前事实，也不能为了显示创新而强制回读。[R1 §7.3 的拟议修订]

### 5.5 N4：让未决项影响下一步，但不机械阻止交付

Frame 的 intent 说明接下来要取得的进展，而不是指定工具命令。Actor 可以质疑它。

最终草稿进入既有有界复核：继续一项有价值的检查、收窄承诺，或直接交付。检查必须与当前任务有关；“仍可能存在未知问题”不能无限阻止完成。

交付复核不是独立 Judge，不读取 benchmark gold 或隐藏测试，不把 Controller 接受草稿当作 verifier PASS。

## 6. RWC 的完整运行算法

### 6.1 三个计算过程，两个模型职责

令 W 为工作区、E 为新事件、G 为当前真实目标、F 为 Frame：

```text
(W', F', d) = Controller(G, W, E, 可用来源目录, 可选最终草稿)
C            = Project(G, W', F', E, 合法原始历史)
a            = Actor(C)
E_next       = Execute(a) 或 FinalProposal(a)
```

Controller 和 Actor 使用模型；Project 和 Execute 的机械部分使用已有代码。不得为了新政策另加路由模型、JSON 修复模型或终态评分模型。

### 6.2 Controller 的输入

依次包括可信政策、独立用户目标、新观察、当前工作记录、正在使用的卡片、Frame 和有界来源目录。历史卡片不必全文一起发；缺少细节时允许回读。新观察说明实际覆盖范围，不将分页第一页标成全部事件已处理。

### 6.3 Actor 的输入

保留原任务与工具合同、当前新观察及未结操作、当前 Frame、短工作记录、已选卡片/来源和必要近期完整交互。工作区作为数据，不提升为 system 级事实指令。

同一来源版本与范围只展开一次。只按文本相同去重不够：相同输出可能来自两次独立执行，二者的事件身份应保留。

### 6.4 来源索引防止焦点封闭

Actor 和 Controller 都要有一条读未选来源的入口。使用已有 exact/path/symbol/lexical 或分页目录能力，不先部署 embedding、图存储或第二搜索框架。大目录不能每轮全量发送；但分页入口不能被 Frame 删除。

Controller 只看见选中内容时也可能固着，因此新事件直达、目录可浏览和合法回读都保留。这降低信息封闭风险，不保证语义判断永远不遗漏。

### 6.5 生命周期与伪代码

```text
启动或恢复：
    建立当前目标/权限/方法配置
    核对未结业务操作
    恢复合法工作区与尚未呈现反馈

循环：
    收取新事件
    按当前方法生命周期判断是否需要维护
    若需要：
        调用 Controller 一次
        规范化、机械验证、原子接收；失败保留旧工作区
        记录此次尝试覆盖的输入，不等于内容已吸收

    RECALL：
        读取已公布且合法的来源
        追加真实返回和覆盖信息
        回到原循环；未送到 Actor 的原新反馈仍然保留

    ACT：
        按最新有效 Frame 装配实际输入
        调用 Actor
        工具动作走原执行器；真实结果入事件记录
        最终草稿进入同一目标版本的有界复核

    DELIVER：
        仅在已有待复核草稿时允许
        交付原稿或同轮修订稿

    中断/交接：
        保存工作区、方法版本、来源映射与各接收方未处理范围
```

这段伪代码说明调用关系，不声称项目已有同名函数。预算到限、用户要求停止和未知副作用按既有合同处理，不为展示完整循环继续请求。

## 7. 模型接口：按最新 Goal 放宽表达，而不改变语义

沿用 `workspace_update / frame / dispatch`，不再开发另一套 JSON 协议。以下是拟采纳的稀疏更新例子，不是本次已经运行的输出：[R1 §4]

```json
{
  "workspace_update": {
    "working_note": "现有结果只支持已检查的条件；新的失败影响其中一项边界，需要针对该范围继续判断。"
  },
  "frame": {
    "question": "新结果改变了哪些必要判断？",
    "intent": "检查受影响范围，保留仍有依据的工作",
    "selected_refs": ["src:17", "src:23"]
  }
}
```

句柄必须是实际已公布对象。具体任务文本由 Controller 自行形成，不能把这段示意注入真实任务当作正确诊断。

语义固定如下：

| 表达 | 结果 |
| --- | --- |
| `{}` | 保持工作区与 Frame，默认 ACT；不是接受最终草稿 |
| 缺省/null workspace_update | 保持内容 |
| Frame 部分更新 | 缺省字段保留，空 selected_refs 明确清空 |
| 新卡片不带 handle | Host 分配编号并公布，不要求额外模型调用取编号 |
| DELIVER 不带 delivery | 仅在已有待复核草稿时，接受原稿 |
| 未知引用或无草稿 DELIVER | 拒绝整份提议；不猜测意图，不部分提交 |

新卡片当轮不能被未公布的自造 handle 引用；可以先使用已知来源引用，待 Host 公布后再选择卡片。首版不引入响应内临时 ID 解析。

规范化失败不重放业务动作，不隐藏原始新反馈。Controller 接收率、空更新、降级和真实控制使用分开记录。来源引用缺省不消除已经存在的披露依赖。

## 8. 状态与反馈的最小可靠语义

### 8.1 维护尝试、内容变化与实际发送分开

一次 Controller 调用可能无更新，也可能被拒绝。两者都不能被解释为“已吸收全部新信息”。

复用现有事件位置或范围记录，至少能区分：Controller 收到了哪些内容；工作区内容在哪一版变化；Actor 实际收到了哪些反馈。不要用一个 cursor 同时表达这三件事。

RECALL 绕转不能将尚未送给 Actor 的原工具结果丢掉；接收了 `{}` 也不增加内容 revision。失败后可沿原 ACT 继续，但报告为明确降级，不算完整控制成功。[R1]

### 8.2 可信版本与语义适用性分开

来源快照版本正确不表示某结论适用于当前任务。旧测试对应旧代码时，Host 可以呈现两者版本关系；是否需重测及重测哪部分仍由模型判断，不自动全量重测或全量失效。

### 8.3 不改变外部边界

明确终态的业务错误应成为反馈；动作状态不明则沿现有只读核对路径，不能重发可能已提交的动作。权限、授权撤回和 checkpoint CAS 在相应边界核对，不在每次纯内部对象访问重算全部合同。

派生记录不洗白恶意来源中的指令。关注引用与披露依赖始终分开；来源失权时不能继续发送已含其敏感内容的缓存摘要。[R1][R3]

## 9. 检查点、长期记忆与恢复

复用 `tools/workspace_checkpoint.py` 与公开 Working State。保存当前方法标识/政策版本、工作区、Frame、合法来源定位、未结操作定位及未处理事件范围。

恢复顺序：当前目标和权限 → 公开读取 → 来源可披露性与未结动作核对 → 未处理观察 → 同一 Controller/Actor 循环。新目标清理旧 final 与相应控制状态，不能靠伪造新目标版本重置预算。

卡片在一次任务内暂存不等于必须写 Note。只有确有跨会话或更长范围复用价值时，再按现有能力持久化。Working State、普通 Note、Canonical 的用途不合并。[R3][R4]

本地 snapshot 通过只证明本地续接；公开字节恢复通过只证明公开存取；真实模型如何使用恢复内容需单独观察。旧公开恢复使用脚本回调的限制继续保留。[R1]

## 10. 高效实现：先移除重复计算，再改变算法调度

### 10.1 第一版立即采用

维护按真实新事件去重；未变化段使用 H_ONCE 缓存；未变卡片不重写；Controller 产物不逐版自动回放；来源范围去重；长原文按需展开；全角色共用账务。

控制—行动的分离可以保留。没有证据前不强迫融合，也不把“同一模型”当作“没有额外推理成本”。

### 10.2 不同时运行多层维护器

OM_SYNC_PORT 不挂 RWC Controller；RWC 不在每轮再跑 Observer + Reflector + Curator。RWC 的同一次 Controller 可以完成记录修订和工作安排。

若长工作区确实需要整体压缩，可以复用既有摘要路径，但归并替代当次相同内容的重复维护，而不是叠加一个新角色。每次新增调用必须承担明确的计算职责。

### 10.3 调度优化明确是后续变体

当前 RWC 默认一批新反馈一次 Controller；OM 保留自己的阈值触发。这两者先如实比较完整成本。

若 RWC 大量调用没有内容或行为价值，再试一个有解释的批处理/延迟方案，并让 WORKSPACE_SIMPLE 使用相同调度。不能悄悄给候选减少调用，却把收益全归给特殊依据政策。

提示缓存收益依赖真实 Provider 的命中与计费记录。稳定前缀、卡片不变只创造缓存条件，不保证命中；记录重排也可能破坏命中。不得把输入 tokens 降低与价格折扣混为一谈。

### 10.4 总成本

```text
总生成 = Actor + Controller/Observer + Reflector/摘要 + 其他实际生成
总资源 = 所有尝试的模型用量 + 工具工作 + 原生环境/验证 + 持久化
```

运行成本、开发调试成本和人工阅读成本分列。没有费率就不计算美元；未知用量不填零。成功任务成本和全尝试成本均保留。

## 12. 使用形式与泛化约束

用户只选择方法并给出正常任务。以下是配置意图示意，不是现有 CLI 参数声明：

```yaml
method: MILAI_RWC        # 或 H_ONCE / OM_SYNC_PORT / WORKSPACE_SIMPLE
provider_profile: existing
memory_scope: task
checkpoint: existing_public_adapter
```

程序绑定真实模型与资源，不让模型在状态里改这些参数。环境适配只负责：任务输入、真实执行、来源读回、事件返回、原生结果。政策不能按 task ID 切换答案规则。

面向代码、数据处理和研究协作时，核心政策相同，State 内容可以完全不同。泛化的是“根据新证据维护行动依据和工作集”的更新规则，不是所有任务都使用相同栏目和阶段。

不宣称适用于尚未接入的浏览器、图像或跨服务任务。多模态附件未被对应模型看到时，不能通过文字占位声称它已理解图像。

## 13. 验证只伴随开发，不重新主导开发

### 13.1 先确认方法真实运行

检查的是：维护从什么真实输入形成；替换了哪些自动展开内容；下一 Actor 实际看到什么；需要时是否能取得原始来源；完整成本是多少。

这是实现学习，不是新的 Gate。无需强制模型产生暂停、恢复或额外卡片。脚本强制回读只证明接线，用户明确要求返回属于显式返回，自主选择另列。

### 13.2 比较分两层

**方法层：H_ONCE / OM_SYNC_PORT 与完整 RWC。**共享任务初态、模型能力、权限、正常工具和总体资源规则；保留各方法本身的维护时机，不强行凑相同角色次数。结论是端到端方法差异。

**政策层：WORKSPACE_SIMPLE 与 MILAI_RWC。**同 Controller 触发、同 Actor、同窗口、同卡片/回读/交付能力，只改政策。结论是该架构内的政策增量。

不必每题同时跑所有方法；根据当前要判断的差异选一对。一次开发比较没有统计确认效力。

### 13.3 首批继续使用已经可用的原生任务

沿用现有 Terminal-Bench/Harbor 入口与原 verifier，不另开任务搜集项目。已暴露 `multi-source-data-merger` 可检查完整使用；`cancel-async-tasks` 仅在有明确新目的且环境可用时使用。原生来源、任务权限、真实环境结果和历史限制来自项目材料。[R1][R2]

隐藏答案和测试不进入在线维护；Controller 对自测的解释仍可能错误。原 verifier 有效性与方法行为分别报告，不用 State 标题、卡片数或关键词给分。

### 13.4 有信号后最少拆解

记录形成、跨步保留、工作集选择、消费政策分别看。把候选记录给普通 review 后打平，只能首先限制消费贡献；形成成本保留。取消跨步保留而性能不变，说明连续性贡献未获得支持。改写提示、模型或上下文后，结果不与旧版拼接。

开发允许改任务和组合，但保留全部版本与失败；选定政策向另一类任务迁移时，不逐题加入新规则。没有新解释就不重复抽样，局部失败也不自动推翻所有未测试能力。

## 14. 创新主张：从已有能力中分离可检验差异

| 不能单独主张的概念 | 直接近邻 | MiLAi 尚需证明什么 |
| --- | --- | --- |
| 子目标摘要和历史回读 | HiAgent | 维护依据范围及其后续行为是否有增量 |
| 外部观察、续接提示与来源范围 | Mastra OM | 不只是有 Frame，而是依据变化确实改变选材和行动 |
| 证据—缺口控制下一步 | MemR³ | 面向真实环境变化的修订与可逆使用是否产生不同结果 |
| 条目级增量维护 | ACE | 更新粒度与采用关系是否有独立价值，不是补 CRUD |
| 同调用上下文管理 | AgentFold | 当前提示型/分离调用方案能否在质量和成本上成立 |

候选贡献可以写为：

> 在 Host 现有行动循环中，以可修正的行动依据记录连接反馈、工作集与下一步安排；对历史经验的采用关系可以暂停、修订和重新评估，同时保留合法来源与工作位置。研究其能否在共同资源条件下减少错误沿用、无效重建和无依据交付。

这不是已证实的新颖性。人类记忆与 ADHD 执行支持方法只保留为功能设计来源，不替代与上述计算方法的差异证明。
