# V0223：准入成本分解与执行有效性恢复

本版是**后续工作合同，尚未执行**。本次只编制 Goal 和同步导航，不运行新测量、不实现优化、不启动 CPU 或真实 P3/P4 实例。

## 1. 目标与非目标

**把真实规模准入的成本拆清楚，只消除可证明冗余的工作，在保持原语义和期限的前提下，判断现有执行仪器能否恢复到有足够余量的离线工作点。**

本 Goal 只回答三件事：

1. 当前准入时间分别花在读/hash、解析、历史重建、动态状态检查、收口及进程开销的什么位置？
2. 去掉重型观察器之后，剩余主要成本是什么；能否通过至多一个最小、通用的去重改动降低它？
3. 完整准备和实际 40 个冷进程是否在原期限内通过，并满足预先冻结的余量门？

不研究 Memory/State、任务推理、模型选择或提示优化；不再优化 B1/D11；不增加 adapter、跨进程缓存或新的审计框架。
**零模型、零 HTTP，包括 tokenize、身份 GET、健康检查和云端回退。** 仅允许新隔离目录中的本地 CPU、Mock、SQLite 和文件操作。
不操作 GPU、驱动、容器或共享服务；不改 Product、Client、MCP、公网部署、A0 默认、权限和 Schema NO-GO。
不换 task、缩小原正式矩阵、读取保护池/C 或修订行为真值。

实现/测量须在后续明确执行指令下启动，且先通过 §4 的 K0 冻结；本次文档完成不等于 Gate A 通过。

## 3. 允许优化什么：静态完整性不等于动态权威

当前 [read scope](../../tools/v0222_admission_read_scope.py)在首次读入和关闭时分别检查路径身份、内容与 hash；
[Batch](../../tools/v0222_presentation_batch_v2.py)还会在收口后检查期限、stop 和 ownership。
现有[接线不变量](../../docs/V0222_SCOPED_ADMISSION_V2_DESIGN_OFFLINE_20260912.md)仍有效。

**“manifest 中固定了 hash”不是“文件在运行期间不可修改”。** 新方案不能仅凭 mtime/size、只读权限、旧 PASS、
SQLite 锁或一个签名，跳过文件变化检测。既有两次内容观察也不宣称连续不可变保证。

| 对象 | 本阶段允许的处理 | 必须保留 |
| --- | --- | --- |
| 同一次 scope 内已验证的相同 bytes | 复用既有解析结果；合并相同用途的纯计算、重复遍历或重建；显式传递中间结果 | 完整引用闭包、冲突 hash 检查、不同用途的语义验证、返回值隔离 |
| 固定源码、fixture、历史 ledger | 区分其确定性计算与重新取证成本；先测再决定有无可合并项 | 原边界上的新鲜读/hash、路径身份和关闭检查；不能把旧验证结果当当前证据 |
| 活动 ledger、中央/地方事件镜像 | 当前边界重新读，并从当前事务状态核对 | 事件顺序、状态机、计费、预约、未知用量、重复副作用检查 |
| 授权、owner、CAS/head、World version、operation/receipt、stop、期限 | 每个需要它的动作/准入边界重新验证 | 收口后仍有效；拒绝不可被静态计算结果覆盖 |
| 独立 parent gate、World/readback | 保留原责任与输入覆盖 | 不用子进程 PASS、Note 或 reference 替代独立验收 |

静态复用只限**已证明输入相同、用途相同、生命周期不扩张**的纯工作，不缓存“准入成功”。
先查清现有 scope 已经消除哪些重复，不能把现有去重当新成果。
如主要成本只能通过跨准入 PASS 缓存、移除二次读取或新的持久快照架构降低，记为范围不足，转入简化 testbed 的方案决策；本 Goal 不自行实现。

### 4.1 K0：冻结实际规模与输入

执行前必须冻结：

- 当前可执行 revision、Python/包版本和改动清单；保留 V0222 已封存源码与原始结果，不覆盖旧依赖制品。
- 57 个历史 ledger 的路径/hash、各自角色、事件/行数与重叠关系；不只硬编码历史费用总数。
- 实际源闭包的路径、唯一文件数、总 bytes、引用次数、JSON 文档数、JSONL 文件/行数；由旧制品复算，不能只写“5k+”。
- 历史失败前缀的 55 scopes 与调用边界映射。55 是该失败前缀，不是完整成功准备的预定 scope 数，更不是 55 个独立样本。
- 原 16 P3 + 80 P4 请求参考、24 效果链、16+24 冷进程矩阵及顺序；新实例只派生必要 ID/路径，语义值与检查器不变。
- 动态 SQLite/事件初态、允许的机械 ID 映射、负控注入时刻、错误预期；新建副本验证，不写原停止批。
- 下述重复数、排序、阈值、所有计时起止点和一个新 CPU-only 根目录；具体 run ID/hash 在执行前填入，不沿用旧授权或旧 binding。

预期规模参照：旧准备包含 55 scopes、57 ledgers；旧实测文件闭包已超过 5k。
文件数相同不足以证明同工作量，必须核对 bytes、解析量、引用重叠、history FSM 和动态 SQL 的覆盖。
新增计时源码使闭包发生的必要变化单列，不删除旧证据依赖来换取速度。

### 4.2 K1：只用粗粒度、可解释的时钟

主时钟为 `time.perf_counter_ns()` 或同一 monotonic 时钟；UTC 仅记录日期。
禁止以 `sys.setprofile`、`sys.settrace`、cProfile 或每个 code object 的回调作为新主测量。
不读取 frame locals、prompt、凭据或业务正文来计时；不对每个文件输出高频日志。

每个 span 只需：

```text
run_id / pid / operation_id / scope_id / parent_span_id
category / start_ns / end_ns / terminal_status
count / unique_files / read_bytes / hash_bytes / json_docs / jsonl_rows / sql_rows
```

记录下列区间，计数器在所属工作边界汇总：

1. scope inventory / closure traversal：引用解析、闭包遍历、去重和冲突检查；
2. source stat/read/hash：首次与关闭两遍分开，读与 hash 可作为组合项，不伪称纯 I/O；
3. JSON/JSONL parse：严格解析、复制及数据构造成本可分项；
4. history reconstruction：固定历史的事件状态机与费用重建；
5. dynamic ledger/SQL validation：当前事务、stop/owner/版本/预约/镜像检查与锁等待；
6. final closure/revalidation：收口协调、最终时间/动态复核、事务退出及失败记录；
7. process overhead：父进程 spawn 到 exit，子进程导入/入口/报告/退出；不得只测 worker 正文。

scope、history 和 closure 可能包含读/解析，**inclusive spans 不相加**。
用父子关系与非重叠区间计算 exclusive wall：

```text
T_admission_wall = sum(exclusive component wall) + unattributed_wall
T_process_wall   = startup/import + execution + report/exit + unattributed_wall
```

生成器 `yield` 不是准入结束；计时必须包含 scope.close、最后期限检查、事务结束和必要异常清理。
在被包围的 operation 中，业务 body 与准入开销分开；计入总 Session 时按时间区间并集，不能重复加嵌套耗时。
独立父 gate、初始化、参考准备、报告 IO 都单列并计入其所属真实期限；不能将重工作移到计时窗口外“获得”加速。
进程 CPU 可辅助记录，但不把 wall 减去 HTTP 的差值称为 CPU；不同进程的 monotonic 绝对值不直接拼接。

### 4.3 测量模式、重复次数与开销约束

两种模式复用同一业务逻辑和输入：

- U：全函数 profiler 关闭；只记最外层时间与终态。
- S：同样关闭 profiler，增加上述 coarse spans/counters；不改变校验分支。

先在**真实闭包和动态快照**下，复现首条 P4 参考的两次准入路径。
固定三对新进程，顺序 U/S、S/U、U/S；共六进程。每个进程从相同初态开始，不跨进程传递解析对象或准入结果。
这是实际规模的成对开销校准，不复跑历史整批，也不采用 80-file micro 的比例替代。

预先冻结的测量合格线：U/S 输出与检查覆盖一致、无缺失结束 span；S/U 外层墙钟中位数比不超过 1.10。
小样本只作开销校准，报告每对时间和最大值，不作总体显著性主张；不从正式时限中扣除计量开销。
若不满足，记 `MEASUREMENT_NOT_READY`，不得继续堆探针或启动 K3；下一修改须另行说明。

随后只运行一次 S 模式的 55-scope **历史成本前缀诊断**，保留原校验顺序和原停止语义。
不能将其完成与否记成完整参考准备通过。若当前更快的逻辑会自然越过原失败位置，按冻结前缀结束诊断，K3 再验证完整准备。
前缀复演不得等待/伪造 deadline 以强造失败；真实时间相关拒绝单独记录，不按 wall 差异判语义不等价。

所有进程新启动；不清 OS 页缓存、不清共享 cache、不调 CPU/GPU/系统配置、不暂停他人作业。
“cold”只指无继承进程状态。记录可见资源竞争，但不通过事后剔除慢样本改变门；测量不可比时保留并停止判断。

### 4.4 K2：由结果选择至多一个最小改动

先产出“重复工作账”：调用方、边界、输入身份、验证用途、调用次数/bytes/rows、exclusive 时间、能否合并及理由。
针对测得的最大**可避免**成本选一个候选，不因名称像 cache/history 就先优化它。
新改动只允许：相同作用域/相同已验 bytes/相同用途的重复纯计算消除，或不改变输入与行为的低开销计量落实。
不引入任务专用路径，不用聚合历史总数替代原事件状态机。

如果去掉 profiler 已足够，零静态优化也是合法选择，结论记 `MEASUREMENT_OVERHEAD_REMOVED_ONLY`；
不能宣称已证明 hash/历史重建存在可消除主瓶颈。若静态去重确有降低，需同时报告调用/解析/重建次数与真实墙钟差异。

候选冻结后，对同一真实规模前缀作一对 U 模式原/候选比较，保留各自完整负担；不选择最快的一次。
历史带 profiler 的 48 秒仅作背景，不是新无探针候选的直接加速比分母。
只在不变量全通过后进入完整测量；首次正式候选失败即保留终态，不悄悄换版本再跑同一正式实例。

## 5. A1/A2：语义等价与动态负控

优化前后比较同一冻结输入，机械映射新 scope/PID/operation ID 后，以下内容必须一致：

- 完整依赖闭包、每一路径的预期 hash/身份检查、执行源码副本与 Python/包校验；
- 每类验证用途和接受/拒绝结果，而不仅是最后一个 `PASS` 字符串；
- 严格 JSON/JSONL、旧历史承接、当前 ledger FSM、已知/未知用量与预约语义；
- 授权/stop/owner、CAS/head/World version、operation/receipt、事件顺序和独立效果；
- 首个失败分类、收口异常附记、回滚、迟到结算和无重复副作用；
- 完整 Schema/intent/reference/checker 输入，不允许以性能修复名义改变业务结果。

语义差分中的时间型负控使用两边相同的受控时钟事件；真实性能测量使用真实 monotonic，不冻结/回拨/延长时间。
静态有效性相同、但原实现耗尽真实期限而候选没有，须单列为性能结果，不能掩盖其他拒绝分类变化。

必须覆盖：

| 负控 | 必须看到的结果 |
| --- | --- |
| 首读后、收口前修改文件；在两次准入间修改依赖；同 size/mtime 的内容变化 | 原定边界拒绝；不能复用旧 PASS |
| symlink/路径替换、hash 冲突、漏一条 SQL 或文件内依赖、相同 bytes 不同验证用途 | 全闭包与对应语义校验仍到达；不因 seen 跳过 |
| 调用者改动返回 JSON 对象 | 不能污染下一引用或让关闭验证失真 |
| grant/scope/owner/stop/阶段状态变化；收口期间时间到期 | 当前边界及收口后拒绝；无发送/提交资格 |
| stale CAS、重复 operation ID 的不同载荷、重复 receipt | 保持原冲突与幂等规则、独立 World 无重复效果 |
| 当前 ledger 插入/删改/次序错、中央/地方镜像不符、新未知用量 | 新鲜核验拒绝；旧未知仍承接，不能记零或当已结算 |
| body 失败再 close 失败、停批/回滚失败、迟到用量 | 首因保留、附记可见；结算不恢复执行资格 |
| 子进程 PASS 但 parent gate/World 不符；单个入口绕过 guard | 不准入；零真实网络出口 |

每个适用动态边界都要有检查覆盖记录，不只测同一函数一次。
原实现若没有某项保证，须明确“既有保证/新增要求/尚无保证”，不能事后改写其能力；
凡需要扩大安全模型、删除父审计或改变收口/事务责任才提速，一律不属于本 Goal 的等价优化。

## 6. A3/A4：实际规模、完整冷链和余量门

### 6.1 冻结的时间口径

本版选择 **30% admission share**，不用运行后再挑阈值：

| 区间 | 原硬期限，不延长 | 新离线余量门 |
| --- | ---: | --- |
| 每个 P4 参考 Session | 60 秒 | Session 内全部准入时间并集 ≤18 秒；从原 Session 起点到完整终态 ≤60 秒 |
| 单正式链的 CPU replay | 300 秒 | 该链及归属它的父准入总开销 ≤90 秒；整链不超过 300 秒 |
| P3 / P4 冷阶段 | 1800 / 7200 秒 | 实测整个 CPU 阶段分别 ≤900 / 3600 秒；含父/子准入、调度、finish/gate、报告与退出 |
| 将来的单 HTTP | 60 秒 | 本 Goal 不发送，也不把 CPU 结果当作实时 HTTP 余量证明 |

18 秒是**一个 Session 全部准入合计**，不是每次准入 18 秒；前两次合计满足也不代表后续链满足。
同时报告初始化、seal、完整准备、全矩阵及报告的生命周期总墙钟，禁止只以准入比例很低掩盖总时间很高。
新计时与结果落盘的真实成本全部计入；不因日志写在关闭后就免计。

有限完整矩阵以**每个 Session/链均达标及最大值**判门；若报告经验 P95，采用 nearest-rank，
同时注明独立冷进程数、root/Session 聚类和最大值。55 scopes/57 ledgers 不是独立重复；不宣称总体 P95/SLA。
CPU 阶段预留的 50% 只是线下 headroom 门，不是把未来 HTTP 延迟从 60 秒改小，也不保证线上一定通过。

### 6.2 真实规模 Gate A 的唯一新实例
